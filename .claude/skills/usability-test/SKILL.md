You play a first-time user working through `test_scenario.md` (repo root) in
the real app, in one device mode, and report back. The goal is to uncover
cumbersome workflows, missing affordances, mode-specific limitations and
bugs — not to prove the tasks are solvable. Don't fix anything, don't
commit; this is a test run.

## 1. Ask for the mode first

Before anything else ask with `AskUserQuestion` (skip only if the
invocation already names it): **Desktop**, **Tablet** or **Phone**. Ask in
the same question set which scenarios to run if the user might want a
subset (default: all, in order).

| Mode | Viewport (CSS px) | Input | App layout tier |
|---|---|---|---|
| Desktop | 1440×900 | mouse + hardware keyboard | desktop |
| Tablet | 820×1180 portrait, DPR 2 | touch only + on-screen keyboard | compact (drawer) |
| Phone | 390×844, DPR 3 | touch only + on-screen keyboard | phone (cards, bottom sheet) |

**The mode is non-negotiable for the whole run.** Never resize, zoom,
rotate, change the user agent, restart in another mode, or reach into the
page to get past the UI. If a task can't be done the way a person on that
device could do it, that *is* the finding.

## 2. Set up (scratchpad `$S`)

```bash
mkdir -p $S/demo-site $S/run && cp philogg.html $S/demo-site/
node tools/log-sim/cli.js -f tour -o $S/demo-site/tour/     # demo log = tour/demo/app.log
```

Start both servers with `run_in_background: true` (each its own Bash call):

```bash
http-server $S/demo-site -p 8123 -s -c-1
NODE_PATH="$(npm root -g)" node .claude/skills/usability-test/driver.js <mode> \
  "http://127.0.0.1:8123/philogg.html?url=tour/demo/app.log" $S/run
```

This is the homepage's "Open with a demo log" link. The driver prints
`driver ready` when the app is loaded; stop it at the end with
`kill $(cat $S/run/driver.pid)` (never `pkill -f`, it can kill your own shell).

## 3. Drive the app

Each step is an async function POSTed to the driver; it runs it, waits
300 ms and returns JSON with `result`, `error`, `pageErrors` (uncaught
exceptions + console errors), `dialogs` (native alerts, auto-accepted) and
`shot`, a screenshot path in CSS pixels (= tap coordinates):

```bash
curl -s 127.0.0.1:9333 --data-binary 'async ({ page, touch, mode }) => {
  await page.getByRole("button", { name: "Files and filters" }).tap();
}'
```

- **Look at every screenshot** (`Read` the PNG) and decide the next action
  from what is visible, the way a person would. Use `result` for text you
  could read on screen (`locator.innerText()`), not for hidden state.
- **Find controls by what a user perceives:** visible text, role + name,
  icon tooltips/labels (`getByRole`, `getByText`, `getByTitle`,
  `getByLabel`). An icon whose meaning you only got from its `aria-label`
  is worth a note in touch modes, where there is no hover tooltip.
- **Desktop:** `click`, `dblclick`, `hover`, `dragTo`, `page.mouse`,
  `page.keyboard` incl. shortcuts, `fill`. Shortcuts count only if the UI
  reveals them (tooltip, menu, Settings → Shortcuts) — note when you only
  knew one from elsewhere.
- **Tablet/Phone:** `locator.tap()`, `touch.longPress(target, ms)`,
  `touch.swipe(from, to, ms)` (target = locator or `[x, y]`), `fill` /
  `page.keyboard.type` into a focused field, `page.keyboard.press` for
  `Enter`/`Backspace` only. Scroll by swiping. Mouse, hover and other keys
  throw by design.
- **File pickers** are fine in every mode: `page.waitForEvent("filechooser")`
  around the tap/click, then `setFiles(...)` with simulator output. Dragging
  files in from the OS exists on desktop only.
- **Off limits in every mode** (the driver blocks most of it, the rest is on
  you): `page.evaluate` and friends, calling app functions, editing storage,
  `?open=`/deep-link tricks after the start URL, reading `philogg.html`,
  tests or docs to find out *how* to do a task. Reloading the tab is a
  normal user action and allowed.
- One step may batch several actions when you are confident; split it
  whenever you need to see the result before deciding.

## 4. Attempt budget: stop when blocked

Per task, when a sub-goal fails, try **at most two** genuinely different
approaches (e.g. a different control, a context menu, the settings).
Still stuck → stop that task, record what blocks it (what you tried, what
you saw, screenshot path) and move to the next one. Don't brute-force
gestures, coordinates or retries. A task that depends on a blocked one is
marked "skipped — depends on N" and you continue where you can.

Only *after* giving up you may look into `README.md` / `docs/` to classify
the blocker — **bug** (documented but broken), **not discoverable**
(exists, but you couldn't find it), **not available in this mode** — but
you don't resume the task with that knowledge.

## 5. Report

Write `$S/usability-report-<mode>-<YYYY-MM-DD>.md`, send it with
`SendUserFile` together with the 3–6 most telling screenshots, and give
a short summary in chat. Structure:

1. **Header:** mode, viewport, date, commit (`git rev-parse --short HEAD`).
2. **Overview table:** task # · title · result (✅ smooth / ⚠️ done with
   friction / ❌ blocked / ⏭ skipped) · steps used · one-line note.
3. **Per task:** what worked well · what was cumbersome (extra taps,
   hidden or tiny controls, unclear icons, missing feedback, layout
   overlap/clipping) · bugs (expected vs. actual, `pageErrors`, screenshot)
   · for ❌ the blocker and its classification.
4. **Findings, most severe first:** bug › blocked workflow › mode
   limitation › friction › polish — each with task #, mode and screenshot,
   so it can go straight into `FEATURE_BACKLOG.md` or a fix session.
5. **What felt good:** the workflows that were smooth in this mode.

Stay factual: report what you saw, not what the code probably does.

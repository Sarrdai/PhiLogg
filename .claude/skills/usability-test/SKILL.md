You play a first-time user working through `test_scenario.md` (repo root) in
the real app, in one device mode, and report back — or, in mode **MCP**, an
external agent (like Claude Code) that a person asked to do the tasks over
PhiLogg's MCP server while they watch the window. The goal is to uncover
cumbersome workflows, missing affordances or tools, mode-specific
limitations and bugs — not to prove the tasks are solvable. Don't fix anything, don't
commit; this is a test run.

## 1. Ask for the mode first

Before anything else ask with `AskUserQuestion` (skip only if the
invocation already names it): **Desktop**, **Tablet**, **Phone** or
**MCP**. Ask in the same question set which scenarios to run if the user
might want a subset (default: all, in order; tasks 16–20 are the ones
written for both the GUI and MCP).

| Mode | Viewport (CSS px) | Input | App layout tier |
|---|---|---|---|
| Desktop | 1440×900 | mouse + hardware keyboard | desktop |
| Tablet | 820×1180 portrait, DPR 2 | touch only + on-screen keyboard | compact (drawer) |
| Phone | 390×844, DPR 3 | touch only + on-screen keyboard | phone (cards, bottom sheet) |
| MCP | 1440×900 (the window the person watches) | MCP tools only (`tools/list`, `tools/call`) | desktop |

**The mode is non-negotiable for the whole run.** Never resize, zoom,
rotate, change the user agent, restart in another mode, or reach into the
page to get past the UI (in MCP mode: past the tools). If a task can't be
done the way a person on that device — or an agent with those tools —
could do it, that *is* the finding.

## 2. Set up (scratchpad `$S`)

```bash
mkdir -p $S/demo-site $S/run && cp philogg.html $S/demo-site/
node tools/log-sim/cli.js -f tour -o $S/demo-site/tour/     # demo log = tour/demo/app.log
```

Start both servers with `run_in_background: true` (each its own Bash call):

```bash
http-server $S/demo-site -p 8123 -s -c-1
NODE_PATH="$(npm root -g)" node .claude/skills/usability-test/driver.js <mode> \
  "http://127.0.0.1:8123/philogg.html?url=tour/demo/app.log" $S/run
```

This is the homepage's "Open with a demo log" link (mode `mcp`: the log the
person opened before asking you). The driver prints
`driver ready` when the app is loaded (port 9333; pass another one as a
fourth argument if that's taken); stop it at the end with
`kill $(cat $S/run/driver.pid)` (never `pkill -f`, it can kill your own shell).
Saved files land in `$S/run/saved/`.

## 3. Drive the app

(Mode MCP: section 3a instead.)

Each step is an async function POSTed to the driver; it runs it, waits
300 ms and returns JSON with `result`, `error`, `pageErrors` (uncaught
exceptions + console errors), `dialogs` (native alerts, auto-accepted),
`saved` (files the step saved, see below) and `shot`, a screenshot path in
CSS pixels (= tap coordinates):

```bash
curl -s 127.0.0.1:9333 --data-binary 'async ({ page, touch, mode, files }) => {
  await page.getByRole("button", { name: "Files and filters" }).tap();
}'
```

- **Look at every screenshot** (`Read` the PNG) and decide the next action
  from what is visible, the way a person would. Use `result` for text you
  could read on screen (`locator.innerText()`), not for hidden state.
- **Find controls by what a user perceives:** visible text, role + name,
  icon tooltips/labels (`getByRole`, `getByText`, `getByTitle`,
  `getByLabel`). An icon whose meaning you only got from its `aria-label`
  is worth a note in touch modes, where there is no hover tooltip.
- **Desktop:** `click`, `dblclick`, `hover`, `dragTo`, `page.mouse`,
  `page.keyboard` incl. shortcuts, `fill`. Shortcuts count only if the UI
  reveals them (tooltip, menu, Settings → Shortcuts) — note when you only
  knew one from elsewhere.
- **Tablet/Phone:** `locator.tap()`, `touch.longPress(target, ms)`,
  `touch.swipe(from, to, ms)` (target = locator or `[x, y]`), `fill` /
  `page.keyboard.type` into a focused field, `page.keyboard.press` for
  `Enter`/`Backspace` only. Scroll by swiping. Mouse, hover and other keys
  throw by design.
- **Opening files** works in every mode: `page.waitForEvent("filechooser")`
  around the tap/click, then `setFiles(...)` with simulator output. Dragging
  files in from the OS exists on desktop only. The folder picker (Open →
  Folder…, folder watch) can't be simulated: on desktop it answers as
  cancelled and says so in `dialogs` — note the task as not testable here.
- **Saving files** (Save session…, Save filter…, Export / Share → Save
  file, CSV, themes, …) is captured, not shown: on desktop the save dialog
  is a stand-in that accepts the suggested name at once; tablet/phone have
  no save dialog (like Safari on iPad/iPhone), so the app downloads
  directly. Either way the step's `saved` lists each file as `{ step, via
  ("save picker" | "download"), name, size, path, excerpt }` (excerpt = the
  first 600 characters, `(binary)` for images); `Read` the `path` for the
  whole file. `files.saved()` returns every file saved so far, and
  `files.cancelNextSave()` (desktop only) makes the next save dialog report
  "cancelled", to check that cancelling saves nothing and says nothing
  alarming.
- **Off limits in every mode** (the driver blocks most of it, the rest is on
  you): `page.evaluate` and friends, calling app functions, editing storage,
  `?open=`/deep-link tricks after the start URL, reading `philogg.html`,
  tests or docs to find out *how* to do a task. Reloading the tab is a
  normal user action and allowed.
- **The app does the analysis, not you.** Never compute an answer in code
  that a person couldn't work out at a glance: no loops that scroll and
  collect rows, no state kept across steps (`globalThis`, files), no
  sorting, pairing, counting or arithmetic over scraped text in a step or
  afterwards, no reading the log file itself. If the app offers no way to
  get the answer, or you can't find one within the attempt budget, that
  *is* the finding: report the task as ❌, don't work around it.
- One step may batch several actions when you are confident; split it
  whenever you need to see the result before deciding.

## 3a. MCP mode: work through the tools

The desktop app's MCP server hands every `tools/call` to the page
(`window.philoggMcpCall`, `docs/llm-assistant.md` → "MCP server"). In mode
`mcp` the driver plays that server: `POST /mcp` answers `initialize`,
`ping`, `tools/list` and `tools/call` like the desktop app does, and each
call runs through the page's real bridge (✦ marking, one undo step per
call). Not covered: the HTTP checks and the bearer token, which
`cargo test -p philogg-mcp` tests. GUI steps are refused in this mode.

```bash
node .claude/skills/usability-test/mcp-call.js --list                  # once, first
node .claude/skills/usability-test/mcp-call.js get_overview
node .claude/skills/usability-test/mcp-call.js create_filter '{"parentId":"f1","pattern":"timeout","mode":"text"}'
```

`mcp-call.js` prints exactly the text a client hands the model, then a
`--` line with `isError`, the screenshot of what the person now sees and
any page errors the call caused. Every call is also logged to
`$S/run/mcp-log.jsonl`. `curl -s 127.0.0.1:9333/look` takes a screenshot
without calling anything.

- **Start like a client:** read the `--list` output (names, descriptions,
  input schemas) — that and the tools' answers are all you know. Don't read
  `philogg.html`, tests or docs to find out how a tool behaves.
- **Answers come from tool results, never from screenshots.** A real
  agent can't see the window. Look at the screenshots to judge what the
  person watching experiences (does the tree show what you made, does the
  view follow, is it legible?) and report that, but don't read answers
  off them.
- **Reason like an agent, don't harvest.** Combining what tools return
  (compare two medians, pick the top row, read one stack trace) is the
  normal job. Paging `get_entries` through a node to count, sort or pair
  rows yourself is a workaround: if no tool gives the answer, that *is*
  the finding.
- **A task the tools can't do at all** (undo, saving a file, searching
  without filtering, …) is ⏭ "not available over MCP" — name the tool
  that would be missing, don't count it as a failed attempt.
- **Note friction on the agent's side:** unclear descriptions, error texts
  that don't say how to recover, ids you had to guess, answers cut off
  (`truncated: true`), more calls than the task should need.

## 4. Attempt budget: stop when blocked

Per task, when a sub-goal fails, try **at most two** genuinely different
approaches (e.g. a different control, a context menu, the settings; in MCP
mode a different tool or a reworded pattern — not the same call with a
tweaked argument).
Still stuck → stop that task, record what blocks it (what you tried, what
you saw, screenshot path) and move to the next one. Don't brute-force
gestures, coordinates or retries. A task that depends on a blocked one is
marked "skipped — depends on N" and you continue where you can.

Only *after* giving up you may look into `README.md` / `docs/` to classify
the blocker — **bug** (documented but broken), **not discoverable**
(exists, but you couldn't find it), **not available in this mode** (in MCP
mode: no tool for it) — but you don't resume the task with that knowledge.

## 5. Report

Write `$S/usability-report-<mode>-<YYYY-MM-DD>.md`, send it with
`SendUserFile` together with the 3–6 most telling screenshots, and give
a short summary in chat. Structure:

1. **Header:** mode, viewport, date, commit (`git rev-parse --short HEAD`).
2. **Overview table:** task # · title · result (✅ smooth / ⚠️ done with
   friction / ❌ blocked / ⏭ skipped) · steps used (MCP: tool calls, of
   which `isError`) · one-line note. In MCP mode also each task's answer,
   so it can be checked.
3. **Per task:** what worked well · what was cumbersome (extra taps,
   hidden or tiny controls, unclear icons, missing feedback, layout
   overlap/clipping; MCP: confusing descriptions or errors, missing
   parameters, wasted calls) · bugs (expected vs. actual, `pageErrors`,
   screenshot)
   · for ❌ the blocker and its classification.
4. **Findings, most severe first:** bug › blocked workflow › mode
   limitation › friction › polish — each with task #, mode and screenshot,
   so it can go straight into `FEATURE_BACKLOG.md` or a fix session.
5. **What felt good:** the workflows that were smooth in this mode.

Stay factual: report what you saw, not what the code probably does.

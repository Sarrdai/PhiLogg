Raw ideas only, not yet elaborated. Pick items up individually before

**IDs (`Nr`) are unique and permanent, not a sort order.** When adding a new
item, read `LAST_ID` above, add 1, use that value as the new entry's `Nr`,
then update `LAST_ID` to the same value — regardless of the priority you give
it. Removing or moving an entry never changes its `Nr`; removing an item
(e.g. because it was implemented) does not change `LAST_ID` either — its ID
is simply retired, never reused.

**Priority (`Prio`) — the rightmost column:**

- **1** — done soon / quick to implement.
- **2** — mid-term.
- **3** — long-term.
- **(empty)** — not planned, but not permanently rejected either; revisit later.
- **verworfen** — rejected, kept for documentation with the reason stated in
  `Details`. Adding a rejected entry requires a stated reason.

**Sorting:** by `Prio` (1, 2, 3, empty, then verworfen), then by `Nr` within
each priority. Re-sort after changing any priority.

| 80 | Derive a level from a numeric code (e.g. RFC 5424 syslog severity) | `applyFormatMatch` (`philogg.html:7939`) takes the `level` named group verbatim (`trim().toUpperCase()`) — there's no value-transform step. A plain RFC 5424 syslog format (`<PRI>1 ts host app pid msgid [...] msg`) has no textual level at all, only a numeric one: PRI = Facility×8+Severity, Severity 0–7 = Emergency…Debug (fixed by the spec, RFC 5424 §6.2.1). Without a mapping, the raw PRI/severity value becomes the level string and the entry falls into the `OTHER` catch-all, losing level-bar filtering and colour. Proposed shape: an optional `%severity`/`%pri` token in the pattern vocabulary (or a mapping option in regex mode) that decodes the captured numeric value through a fixed 8-entry table onto one of the format's level names (custom names via `LogFormat.levels` already cover non-standard labels, see `PROJECT.md` → "The log formats it parses"). Purely additive — touches only `applyFormatMatch`/the format compiler, no schema or node-model change. Independent of #81 (multi-pattern parsing) — useful for any single, pure syslog file today already. | 2 |

| 81 | Log files with several interleaved grammars in one file (multi-pattern parsing) | Triggered by a sample file mixing two independent grammars line-by-line: format A (log4net-style `ts [] LEVEL Logger  - message`, continuation lines via tab-lists/indentation/free text, entries separated by 1–2 blank lines) and format B (RFC 5424 syslog: `<PRI>1 ts host app pid msgid [structured-data] message`, block-wise with no blank lines, not guaranteed chronological within a block), plus mixed LF/CRLF line endings at arbitrary positions (already harmless — `text.split(/\r\n|\n/)`, `philogg.html:7763`, accepts both anywhere). Today's model is one `LogFormat` per file, pinned via filename glob for the file's whole session-cache lifetime (`PROJECT.md` → "The log formats it parses"); `isHeaderLine`/`parseHeader` know exactly one format per parse run. Any non-matching, non-empty line already becomes a continuation of the previous entry (`parseLogTextAsync`, `philogg.html:7748`), which already covers all of format A's continuation-line variants for free; blank lines are already silently skipped, no special boundary handling needed. Researched how established tools handle this (see conversation): none solve "several header grammars racing per line in one stream" cheaply. lnav (closest comparison, a terminal log viewer built for exactly this) "locks on" to one format regex per file and its own docs recommend splitting genuinely mixed formats into separate files and merging instead. Splunk keeps line-breaking as one shared, permissive rule per sourcetype and reclassifies per already-broken event afterwards (`TRANSFORMS`, regex on content). Logstash is the only one with true pattern racing (`grok` with `break_on_match`), but as a pipeline filter stage running after the input is already split into events by its codec. Three implementation options were discussed, none decided: **(a)** extend the core dispatch itself — `isHeaderLine`/format resolution from "one format" to "ordered list of formats, first match per line wins"; smallest change to the parser, but requires the involved formats' regexes to be mutually exclusive (same requirement lnav imposes on its own format regexes), which the app cannot verify automatically, and still merges both grammars into one entry list. **(b)** Splunk-style: one shared, permissive boundary rule plus per-entry reclassification afterwards — closer to the existing continuation fallback, but it's unclear what a single boundary rule covering two structurally different headers would even look like without collapsing back into (a). **(c)** a meta-format/preprocessing step: a format definition that references a *declarative* (never freely executable — see below) line-classification rule plus several target formats; the load pipeline would create multiple virtual child files from one physical file, each parsed under an existing, ordinary single-format definition, then either loaded individually or recombined chronologically via the existing `mergeFiles` merge feature — "load only one part" falls out essentially for free this way, which (a)/(b) don't give. Cost: breaks the current fixed 1-file-→-1-node relationship (`createFileNode`/`loadFileDescriptors`, `philogg.html:8461`/`22624`); `probeFileTimeRange` (`philogg.html:8061`, head/tail-chunk probe for the folder-watch minimap) and `appendTailText` (`philogg.html:23173`, incremental live-tailing) would both need to know the split logic too, and apply it incrementally to newly appended bytes, or minimap preview and live-tail silently break for meta-format files. Explicitly **not** an embedded script/arbitrary-code mechanism — a format definition turning into automatically-executed (and potentially shareable) code would break the "no build tooling, no dependencies, nothing runs but the viewer itself" premise; formats aren't export/importable today unlike the filter library, and should stay that way if this ever carries a "script". A further open risk regardless of option: `entryComparator`/`mergeFiles`' fast path assume a file's own entries are already chronological (comment at `philogg.html:7586`); the sample file explicitly has non-chronological order within a B-block (line 22→23 descending) — needs clarifying against the link filter's binary search and minimap/plot rendering before implementing any option. Format B's structured-data extras (`linenumber`, `errorcode`, `errortext`, `agent`, `system`) don't fit the fixed entry schema (`ts, level, thread, location, method, message`); recommendation from the discussion is to deliberately *not* extend the schema for this — leave them inside `message` (automatic, zero-cost) until a concrete filtering need for one of them shows up. Level derivation from a numeric code (format B has no textual level) is intentionally split out as its own, independently useful item — see #80. Recommendation before building any of the above: validate the need without touching the app first — split the sample file into two files by grammar with an external, one-off script and recombine them with the existing merge feature; only invest in (preferably) option (c) with a declarative rather than script-based classification rule if that turns out to be a recurring need, not a one-off. Reference material (sample log + format description) was supplied as chat uploads for this discussion, not checked into the repo — re-request it or capture a synthetic equivalent (e.g. via `tools/log-simulator.html`'s pattern language, see its token-vocabulary comment at `unescapePatternText`) before implementation. | |

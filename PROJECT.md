# LogTrail — Project Documentation

**Read this file first.** It's the entry point for understanding what LogTrail is, how it's built, and why it's built that way, before touching `logtrail.html`.

## What this is

LogTrail is a **local, single-file, offline-capable log viewer** built to replace LogViewPlus for a specific pipe-delimited log format. It's one self-contained `.html` file — no build step, no external dependencies, no CDN calls, no server. Opening the file in a browser is the entire deployment story. That constraint is deliberate and has shaped almost every architectural choice below — keep it intact unless the person explicitly asks to relax it.

- **File**: `logtrail.html` (~8,232 lines: inline `<style>`, inline `<script>`, vanilla JS, no framework, no build tooling)
- **Runs from**: `file://` directly, or any static host — must keep working both ways
- **Dependencies**: none. Not React, not a charting library, not a font CDN. Custom SVG charting was built from scratch specifically to avoid a dependency.

## The log format it parses

Pattern (log4net-style conversion pattern): `%d\t%p\t"%t"\t%l\t[%method]\t%m%n`

Tab-separated columns: `timestamp \t level \t "thread" \t file \t line N \t [method] \t "message"`. The parser (`parseHeaderLine`, `parseLogTextAsync`) is tolerant: it detects a new entry via a timestamp-shaped line prefix (`HEADER_RE`), and any line that doesn't match is treated as a continuation of the previous entry's message (handles multi-line stack traces). Parsing runs in async chunks (`PARSE_CHUNK_LINES = 4000`) with `setTimeout(...,0)` yields between chunks so the UI stays responsive on large files, and reports progress that drives the loading overlay (file read = 55% of the bar via `FileReader.onprogress`, parsing = 45%, see `READ_WEIGHT`/`PARSE_WEIGHT`).

## Core data model

Everything lives in one global `state` object (search `const state = {`). The two things to understand first:

### 1. The node tree

`state.nodes` is a flat `{id -> node}` map; `state.rootIds` lists the file (root) node ids in load order. Every node is either:

- **`type: "file"`** — holds the actual parsed `entries` array. Root-level only (`parentId: null`). Has a `merged: true` flag if it was created by the file-merge feature (see below); in that case its `entries` is the chronologically-sorted union of its source files' entry *objects* (reused by reference, not cloned).
- **`type: "filter"`** — has a `parentId` (its place in the tree), a `children` array, a `name` (display label), and a `filterType` that determines what `getEntries(node)` computes. See the filter type table below.

Filters chain: a filter's result is always computed from its parent's result (`getEntries(node.parentId)`), then narrowed/transformed. This is why the tree visually nests — each indent level is another transformation of the level above.

**Two filter types don't fit the pure-tree model** (`and`, `or`, `link`): they need a *second* input that isn't their tree parent. That second reference is stored as `linkedId` on the node. `parentId` is still used for tree placement (which of the two source filters the new node is nested under), `linkedId` points to the other one. **Consequence**: because a node's true dependencies aren't fully captured by parent→child alone, cache invalidation on move/delete is a **global sweep** (`invalidateAllCaches()`) rather than a subtree walk — cheap enough since moves/deletes are infrequent user actions, and it's the only way to guarantee correctness once cross-references exist. **Consequence 2**: `and`/`or`/`link` nodes *are* Ctrl+C/Ctrl+X/drag-and-drop-able, same as any other filter — `moveNode()` only ever touches `parentId`, so `linkedId` survives a move completely untouched, and `cloneSubtree()` now carries `linkedId` (plus `linkDirection`/`linkN` for `link` nodes) onto the clone rather than dropping it. These were originally excluded on the assumption that "can't safely carry the second reference along" applied to both operations; on closer inspection it only ever applied to *cloning* dropping the field, which is now fixed. The one genuine risk — moving/pasting a node so that its own `linkedId` target becomes its ancestor, which would make `getEntries()` recurse into itself forever — is guarded narrowly by `wouldCreateLinkedCycle()` (checked in `moveNode()`) and `subtreeHasLinkedCycle()` (checked before a clone in `pasteClipboard()`), not by a blanket type restriction. A blocked cut/paste keeps the clipboard active (instead of silently clearing it) and shows a toast, so the person can just try a different target.

**`context` looks similar to `link` (a second, non-parent source of entries) but deliberately isn't built the same way.** Its "other side" is always the node's own root file (`getRootFileId(node.parentId)`), never another arbitrary node, so it needs no `linkedId`, no cycle guard, and no entry in the global-sweep reasoning above — it's a plain single-parent filter as far as move/copy/cache invalidation are concerned. See "Time context filter" below.

### 2. Filter types

| `filterType` | Needs | What `getEntries` does |
|---|---|---|
| `text` | `value: string` | case-insensitive substring match against `entry.raw` |
| `after` / `before` | `value: number (ts)` | `entry.ts >= / <= value` |
| `extract` | `value: pattern string` | compiles the pattern (see below) and keeps entries whose `message` matches; **also** drives the extraction table view when this node is active |
| `and` / `or` | `linkedId` | set intersection / union (by `entry.id`) of this node's parent-chain result and `getEntries(linkedId)`; `or` re-sorts by `ts` after merging |
| `link` | `linkedId`, `linkDirection: "before"\|"after"`, `linkN: number`, `linkOrderEnforced: boolean`, `linkExclusive: boolean` | nearest-neighbor pairing (see below); result is an array of synthetic **pair entries**, not normal log entries |
| `context` | `contextBefore: number (ms)`, `contextAfter: number (ms)` | windowing around reference entries (see below); result is real entries from the root file, not synthetic ones |

`createFilterNode(parentId, filterType, value, inverted = false)` builds `text`/`after`/`before`/`extract` nodes. `createAndOrNode` and `createLinkNode` build the two-reference types, `createContextNode` builds `context` nodes.

### 2a. Inversion (NOT)

Any filter node can carry an `inverted: boolean` flag, orthogonal to `filterType` — it's a post-processing step in `getEntries()`, not a separate type. Once the node's normal `result` is computed, an inverted node replaces it with `parentEntries` minus `result` (set difference by `entry.id`), so "NOT" always reads as "everything my parent had that I would otherwise have kept."

This is deliberately **generic** rather than reimplemented per type — it works unchanged for `text`, `after`, `before`, `and`, `or` — but it's **withheld for three types** where the generic definition breaks down:
- **`link`**: results are synthetic pair entries (`buildPairEntry`) whose ids never match `parentEntries`' ids, so the set difference would just be all of `parentEntries` — not "unmatched refs," just wrong.
- **`extract`**: an inverted extraction filter would keep only rows that *don't* match the pattern — i.e. exactly the rows with nothing to extract — so the extraction table would always render empty.
- **`context`**: every reference entry's own window always contains itself, so `result` is always a superset of `parentEntries` — a parent-relative difference would always be empty.

Both restrictions are enforced in the same place they'd otherwise be violated: the tree context menu omits "Invert (NOT)" for `link`/`extract`/`context` nodes, and the filter popup disables/unchecks its NOT checkbox the moment the input is detected as an extraction pattern (`updateInvertAvailability()`, on the same `input` listener as the live-match preview). `getEntries()` also guards `filterType !== "link" && filterType !== "context"` directly, so the invariant holds even if `inverted` were ever set some other way.

Two entry points toggle it: the **NOT checkbox** in the Ctrl+F filter popup (sets it at creation time, `text` filters only — `after`/`before` created via right-click-a-row don't offer it at creation) and **right-click → "Invert (NOT)" / "Remove NOT"** on any existing eligible filter node (toggles it after the fact, for any type including `after`/`before`/`and`/`or`). Both paths converge on the same flag and the same `getEntries()` logic.

Toggling `inverted` is a **structural-equivalent change** for caching purposes even though it touches neither `parentId` nor `children`: it changes the node's own result, which every descendant's cached result transitively depends on. It goes through `invalidateAllCaches()` — the same global sweep already used for move/delete — rather than a targeted single-node cache clear, for the same reason `and`/`or`/`link` need the global sweep (§1): a narrow invalidation would have to also chase the affected node's entire subtree, which the sweep already does for free. `cloneSubtree()` carries `inverted` onto the clone like every other field, so copy/cut/paste and drag-and-drop preserve it.

In the tree, an inverted node's label gets a `"¬ "` prefix and its type tag turns red (`.tree-row.inverted .tree-type-tag`) — visible without opening the node.

### 3. Memoization

Every filter node caches its computed result on `node._cache`, since a filter's own type/value never change after creation — only *structural* changes (move, delete) can invalidate a result, so `getEntries()` is a cheap cache hit on every render except right after such a change. This is what makes the tree, level-quick-filter counts, and breadcrumb cheap to recompute on every render without visibly recursing the whole chain each time.

Two companions ride along with `_cache` (cleared in the exact same places, nowhere else):

- **`node._levelCounts`** (`getLevelCounts()`): per-level entry counts for the node's own result, used by `renderLevelBar()` on every `render()`. Previously an O(n) `levelBucket` pass over the active view ran on every render — including when merely flipping back and forth between two already-computed filters.
- **Scoped invalidation for tail ticks** (`invalidateCachesForRoots(changedRootIds)`): `onTailChange` used to call the global `invalidateAllCaches()` every 1.5s poll, after which the next render recomputed *every* filter chain in the tree (`renderTree` reads every node's count) — including filters under files that hadn't changed at all. The scoped variant recursively marks a node dirty iff its root file changed or it transitively depends on a dirty node via its `parentId` chain or its `linkedId` target. Cross-file `linkedId` references are unsupported by design (bulk combine only pairs same-file filters), but drag-and-drop reparenting can't structurally rule them out, so `linkedId` is followed explicitly rather than assumed same-file; a pending-guard treats hypothetical cycles conservatively as dirty (the `linkedId` graph is acyclic by construction — targets always pre-exist and are never reassigned). Structural user actions (move/delete/invert/edit) still use the global sweep — rare, and trivially correct.

## Value-extraction pattern language

A filter query is auto-detected as an extraction pattern (`isExtractPattern`) the moment it contains a placeholder token; otherwise it's a plain `text` filter. `compileExtractPattern(pattern)` turns the template into `{ regex, columns, regexStr }` — `regexStr` (the raw source string, added alongside the compiled `regex`) exists purely so the live pattern preview (see "Extraction: live pattern preview + ignored columns" below) can build its own second `RegExp` with the `d` (match-indices) flag without touching the hot-path `regex` used for actual matching.

Placeholders: `[value:float]` `[value:int]` `[value:time]` `[value:word]` `[value:hex]` and the bare wildcard `[*]`. `time` matches either a clock time (`16:23:27.697`) or a number+unit duration (`500ms`, `3.5s`). Columns are auto-named `value`, `value 2`, `value 3`... (never the type string itself — that caused a "floatfloat" header rendering bug early on, fixed by decoupling name from type). Regex is case-insensitive; a trailing `[*]` is greedy (captures the rest of the line), a mid-pattern `[*]` is non-greedy.

Right-click a message → **"Extract numbers from this message"** auto-generates a suggested pattern (`buildNumericExtractPattern`) by replacing every number token with a typed placeholder, recognizing embedded clock times/durations as a single `[value:time]` rather than splitting on the colons. It's inserted into the filter popup for review, not auto-submitted.

## Link filter: nearest-neighbor pairing

Built for the "give me the last position reading before each offset-computed event" use case. `getEntries` for a `link` node walks its reference-side entries and, for each one, binary-searches (`lowerBoundByTs`) the target side for the Nth entry strictly before/after it in time (`findNthOccurrence`); references with no match are dropped (no placeholder rows), duplicates are allowed. Each match becomes a **pair entry** (`buildPairEntry`) that **duck-types as a normal entry** — same `id`/`ts`/`level`/`message`/`raw` fields — specifically so every other mechanism (text/time filters, the level quick-filter, and crucially the extraction engine) works on link results completely unchanged. The two real underlying entries are combined into `message`/`raw` with the separator `PAIR_SEPARATOR = " ⟶ "`, which is why an extraction pattern spanning both sides of a pair looks like:

```
Position x=[value:float] y=[value:float] ⟶ Offset computed: [value:float]
```

### Chained links (multi-hop tuples) — design, bugs fixed, and the new dialog

A "chained link" is a `link` node whose reference side (`parentId`) is itself another `link` node's result — the existing tree-nesting mechanism already allowed building this by hand (link A→B, then link (A→B)→C), and it's now also what the multi-hop dialog below generates under the hood. Three bugs in that mechanism were fixed this session (see `REQUIREMENTS-link-chaining-and-multiway.md`, supplied by the person, for the original repros):

- **Wrong time anchor when chaining.** `buildPairEntry(refEntry, targetEntry)` now stamps a second field, `matchTs: targetEntry.ts` — the actual matched entry's own timestamp — alongside the existing `ts` (still `refEntry.ts`, unchanged, since BASELINE anchor semantics and the display-facing pair timestamp weren't part of the bug and nothing asked for them to change). `getEntries()`'s `link` branch now searches from `refEntry.matchTs ?? refEntry.ts` instead of always `refEntry.ts`, so a second hop anchors on the *previous hop's actual match*, not the original outer reference's timestamp. A plain, non-chained `link` node is unaffected (a real entry has no `matchTs`, so this falls back to its own `.ts` exactly as before).
- **Highlighting stopped at one nesting level.** `computeHighlightMap()`'s `link` branch used to colour `pair.first.id`/`pair.second.id` directly — correct only when both sides happen to be real entries. It now calls `getTupleEntries(pair)` (below) and colours every id that comes back, so a coloured rule on a chained link colours every real entry at every nesting level.
- **Double-click jump broke on the nested side.** Same root cause, UI-facing symptom: `buildPairRow`/`revealInHighlightView` need a *real* entry id to resolve through `entryIndex`. `renderLinkView` now also flattens via `getTupleEntries(pair)` and renders one row per real entry (with `N-1` `Δ` labels between them) instead of always exactly two rows via `pair.first`/`pair.second` — so a 3+-way tuple gets a 3+-row `pair-block` in the Link view for free, and every row's double-click always has a real id.

**`getTupleEntries(entryLike)`** is the fix's shared primitive: `entryLike.isPair ? getTupleEntries(entryLike.first).concat(getTupleEntries(entryLike.second)) : [entryLike]` — recurses through arbitrarily many nesting levels instead of assuming exactly one. This is the "proposed (not mandatory) helper contract" from the requirements doc, kept as the actual implementation shape.

**Design direction chosen: A ("fix the nesting, keep pair-of-pairs"), not B ("native flat tuple").** The requirements doc offered two directions; A was chosen because it's the smaller, lower-risk diff — `and`/`or`/`link`'s existing `linkedId`-based tree structure, `cloneSubtree`/`snapshotSubtree`/save-load serialization, and the cycle guards (`wouldCreateLinkedCycle`/`subtreeHasLinkedCycle`) all continue to work completely unchanged, since a chained/multi-hop tuple is still just nested `link` nodes under the hood, not a new shape. The cost is that consumers which used to assume "exactly one level of `.first`/`.second`" needed to switch to `getTupleEntries()` instead (three call sites: `computeHighlightMap`, `renderLinkView`, and nothing else touches `pair.first`/`pair.second` directly) — a small, closed set, which is what made A viable here. Direction B (a flat `entries: [...]` array + one `buildTupleEntry`) would have removed the "one level of nesting" assumption at its source rather than patching each consumer, but was judged not worth the larger diff (new node shape, new serialization fields, `and`/`or`'s and the extraction engine's `⟶`-joining logic would all need re-auditing against the new shape) for what direction A already delivers correctly.

### Multi-way link definition in one dialog

The bulk "Link…" action (right-click / action-bar on a 2+ filter multi-selection, same file) now accepts **2 or more** filters, not just exactly 2 (`describeBulkActions`: AND/OR stay 2-filter-only — generalizing set intersection/union to N filters wasn't asked for — but Link's bulk action is offered for any 2+, labeled "Link… (N-way)" past 2). `openLinkDialog` builds a dialog with a **Reference** dropdown (`#linkRefSelect`, unchanged) plus a dynamically-rendered list of **hop rows** (`#linkHopsList`, one per remaining selected filter, `renderLinkHops()`) — each hop has its own `#` (N) input and before/after direction select, worded as "Find the Nth **{target}** entry {before/after} {anchor}", where `{anchor}` is the reference's name for the first hop and "the previous match" for every hop after that (the optional UX polish the requirements doc suggested, since the old single-hop "before/after TargetName" wording read ambiguously about what was before/after what).

**Hop order = selection order** (the filters' order in the `ids` array passed to `openLinkDialog`, minus whichever one is chosen as reference) — `state.multiSelect` is a `Set`, which preserves insertion order, so this is just the order the person Ctrl-clicked the filters in. There's no separate drag-to-reorder UI; re-selecting in a different order is how to change hop order.

**Create is sugar over the existing chaining mechanism**: it walks the hop rows in order, calling `createLinkNode(curRefId, hop.targetId, hop.direction, hop.n, {orderEnforced, exclusive})` once per hop, where `curRefId` starts as the chosen reference and becomes each new hop node's own id for the next iteration — i.e. it builds exactly the same chain of nested `link` nodes a person would otherwise build by hand, node by node, in the tree. This is also why Bug 1's fix (`matchTs`) is what makes the dialog's multi-hop result correct, not new dialog-side logic.

### Opt-in options: order enforcement & exclusive matches

Both are per-`link`-node boolean flags (`linkOrderEnforced`, `linkExclusive`), set via the two checkboxes in `#linkDialog`, **default `false`** (unchanged behavior when off) — carried through `createLinkNode`'s new optional 5th `opts` argument (`{orderEnforced, exclusive}`), and persisted alongside `linkDirection`/`linkN` everywhere that already serialized those: `cloneSubtree` (copy/paste), `snapshotSubtree`/`restoreSubtree` (undo/redo), `serializeFilterBranch`'s `serializeSubtree` + `importFilterJson`'s `materialize` (filter save/load `.json`), and `serializeFilterTreeForCache`'s `ser` + `materializeCachedFilters`'s `materialize` (session cache). Additive-only fields, so `FILTER_FILE_VERSION` was **not** bumped — a filter file saved before this feature loads exactly as it did before (both new fields simply materialize `false`), and files saved with them set load correctly on older... well, there is no older-version reader to worry about going forward, but the point is nothing about the existing format 2 envelope changed.

- **Exclusive matches** (`linkExclusive`): once a target entry has been matched for one reference entry, no later reference entry in the *same node's* result can reuse it — implemented as `findNthOccurrenceExcluding()` (a variant of `findNthOccurrence` that skips ids in a running `usedIds` set) plus a `usedIds` `Set` scoped to one `getEntries()` call. **Scope chosen: globally across every tuple the node produces** (not per-hop-within-a-tuple) — the requirements doc flagged this as the more likely reading of the request and asked for it to be confirmed; going with it here since a chained/multi-hop tuple is still evaluated one `link` node at a time (each with its own `getEntries()` call and its own `usedIds`), so "global" here means "across this one node's reference entries," which is the natural unit exclusivity would apply to.
- **Enforce chronological order** (`linkOrderEnforced`): after a hop finds a candidate match, the match is **rejected (treated as no match, same as an unmatched reference — dropped, not retried)** if `match.ts < anchorTs` (the timestamp the hop searched from — the previous hop's `matchTs`, or the outer reference's own `ts` for the first hop). **Semantics chosen**: this makes the *whole chain's* timestamps non-decreasing hop-over-hop, regardless of which individual hop searched "before" vs "after" — chosen over the other candidate reading ("each hop's own direction is internally consistent") because it's the one that actually catches the requirements doc's own REPRO case (a "before" hop landing chronologically earlier than the very first reference entry, not just earlier than its immediate anchor) and because pairwise-adjacent monotonicity is transitively equivalent to whole-sequence monotonicity, so no extra history-tracking beyond "compare this hop's match against the anchor it was searched from" is needed.

### Same-timestamp tie-break

**Person-reported follow-up** (screenshots of the multi-hop dialog + the Full/Filtered split): linking `"Target Real"` (anchor) to the nearest preceding `"Target Vir"` matched an entry roughly 11 seconds too early, even though the Full log clearly showed a `"Target Vir…"` line immediately followed by the `"Target Real…"` reference line. Root cause, confirmed before touching anything: `findNthOccurrence`'s `before`/`after` search compares timestamps with **strict** `<`/`>`. The log format only resolves to the millisecond, and this data bursts several log lines per control-loop tick at the *exact same* millisecond — so the `"Target Vir"` line sitting right next to the reference in the file shared its exact timestamp, made it a tie, and got excluded from "before" entirely (symmetrically true for "after" — both directions already treated ties as neither before nor after, this wasn't new or asymmetric, just surprising once a log has bursts). The search then kept walking backward past the whole tied cluster until it found an entry with a *strictly* earlier millisecond — 11 seconds earlier, from the previous cycle.

**Fix, exactly as requested**: when candidates tie with the reference on `.ts`, fall back to **log/array order** to decide before-vs-after, instead of excluding them.

- `buildOrderIndexMap(fileId)` builds a fresh `Map<entry.id, index>` from the root file's own `entries` array — "log order": parse order for an ordinary file, the already-chronologically-sorted union order for a merged file (see "The node tree"). Built once per `getEntries()` recompute of a `link` node (O(file size), same cost class as the `context` filter's own per-computation pass — not cached on the file node, to avoid new invalidation bookkeeping for what's still a rare, structural-change-triggered recompute; revisit if profiling ever shows this mattering on a file with many link nodes).
- `findNthOccurrence`/`findNthOccurrenceExcluding` now take the reference **entry** (not just its `ts`) plus this map: within the contiguous run of candidates sharing the reference's exact timestamp, the map locates where the reference itself would sit by log order, splitting that run into a "before" side and an "after" side — exactly mirroring what strict `ts` comparison already does for non-tied candidates, just scoped to the tie. If either id can't be resolved in the map (e.g. a dangling `linkedId`, or — see below — a chained link's synthetic outer reference), the comparison degrades gracefully back to the old "exclude the tie" behavior rather than guessing.
- `buildPairEntry` had the same issue one level up: which side becomes `.first`/`.second` (display order, and the `⟶`-joined `message`/`raw`) used to default to "reference first" on any tie. It now takes the same `orderIndexMap` and, when both ids resolve, breaks the tie the same way — so the *displayed* pair order matches the log, not just the *matched* pair.
- `buildPairEntry` also gained `matchEntry` (the real `targetEntry` object a hop just matched, alongside the existing `matchTs`): a **chained** link's reference entry is a synthetic pair, whose own id never appears in a file's `entries` and so can't be looked up in the order map directly — `matchEntry` gives the *next* hop's tie-break a real entry id to resolve instead, the same way `matchTs` already gives it a real anchor timestamp (Bug 1 fix, see "Chained links" above). A plain, non-chained reference has neither field, so both simply fall back to the reference entry itself.

Verified against the exact reported shape (a decoy tie 11s earlier, then a same-millisecond burst with the target immediately preceding the reference, in both `before`/`after` directions), a plain no-ties case (regression guard — completely unaffected), and tie-break combined with exclusive matches (two references and two targets all sharing one timestamp, exclusivity still hands out the log-nearest *available* target to each). See `tests/logtrail.regression.test.js` Group 23.

### Backward compatibility

Everything above is additive: existing saved filter JSON / session-cache entries with `linkedId` + `linkDirection` + `linkN` and no `linkOrderEnforced`/`linkExclusive` fields continue to load as plain two-way links with both new flags defaulting `false` — verified by a regression test that materializes a hand-built pre-feature `link` JSON node and asserts both flags come back `false`. A multi-hop tuple built through the new dialog does **not** get its own `filterType`; it's plain nested `link` nodes, so it round-trips through save/load exactly the way manually-chained links already did (each hop pulls in its own ancestor chain per the existing `linkedId`-target rules in "Filter save / load").

## Time context filter: window around reference entries

Built for the "show me everything that happened around this event" use case — deliberately simpler than the link filter it's modeled on. `getEntries` for a `context` node takes its parent-chain result as reference entries, builds a `[ts - contextBefore, ts + contextAfter]` window (both in ms) around each one, merges overlapping/touching windows into a sorted, non-overlapping range list (`mergeContextRanges` — an interval merge; this is the one deliberate answer to "what happens when two references' windows overlap": they become one group rather than staying as separate, duplicate-prone groups), then binary-searches (`lowerBoundByTs`/`upperBoundByTs`) the **whole root file** for entries inside those ranges. Unlike `link`, the result is **real entries from the file**, not synthetic pair objects — so any filter can be nested underneath a `context` node exactly like under any other filter, and a reference entry's own row shows up at its normal chronological position (it's always inside its own window) rather than needing a special anchor-row construct.

`node._contextRanges` (the merged range list) and `node._anchorIds` (the set of reference entry ids) are computed alongside `node._cache` in the same `getEntries()` branch and read directly off the node by the renderer — they're not separately invalidated because they're only ever populated together with the cache they ride along with.

**Rendering**: the log view (not a separate view like the link pair view) draws a left-side bracket per row when the active node is a `context` filter — `contextRangeIndex()` (binary search over `_contextRanges`) tells `renderVisibleRows()` which merged group a row's timestamp falls into; a row gets `.ctx-start`/`.ctx-end` classes by comparing against its *actual* neighbors in `currentViewEntries` (not just the virtualized render window), so the rounded bracket caps land correctly regardless of scroll position. Reference entries get a small accent dot (`.ctx-anchor-dot`). Brackets are suppressed under an active column sort (`state.sortColumn`), since sorting would scatter a group's rows apart and the bracket would stop meaning anything.

**Creating one**: right-click a single filter node (not a 2+ multi-selection) → "Time context…" opens `#contextDialog`, a small before/after-in-milliseconds form (mirrors `#linkDialog`'s structure but needs no target-filter picker, since the target is always the root file).

This is the intended way to pull values from *both* sides of a pair into one extraction-table row.

## Header / toolbar layout

The header (`#toolbar`) is just the brand mark/name (`.brand`) on the left and, on the right, the undo/redo/bookmarks/shortcuts icon buttons, the theme toggle, and "Open files…". The header used to also carry a small subtitle ("local, single-file log viewer") next to the brand name — removed per a person UI-adjustment request; `.brand-tag` no longer exists in either markup or CSS.

**`#viewBar`** — a single row at the top of `#content`, above `#fhSplit`, that merges what used to be **three separate toolbar rows**: the breadcrumb (active filter chain), the level quick-filter, and the Full/Filtered/Stacked toggle. `#fhTabs` (the toggle), `#btnPinBookmarks` (the pin-bookmarks toggle, moved in from the header — see "Pin bookmarks into the Filtered View") and `#levelBar` are `float:left`, so they stay **pinned to the top-left line** no matter how long the filter chain gets, in that DOM order (tabs, then the pin toggle, then the level pills); `#breadcrumb` is a plain block (not flex) with `display:inline-block` chips, so it flows text-style around those three floats on the first line(s) and then uses the **full row width** on any line it wraps to below them — a filter chain long enough to wrap doesn't push the toggle/pin/level-filter down or squeeze itself into a narrow leftover column, it just drops to its own full-width line(s) underneath. `#viewBar` itself is `display:flow-root` so its own height always reaches the floats' bottom edge even when the breadcrumb is short or empty (a plain float doesn't otherwise contribute to a parent's auto height). Flexbox can't produce this "first line shares space, later lines full width" shape — a flex item's box is always one rectangle — hence floats + normal block flow instead; see the CSS comment directly above `#viewBar` if this needs touching again. **`#viewBar` also needs its own `flex:0 0 auto`** — that's a separate concern (how `#viewBar` behaves as a flex ITEM of its parent `#content`, a flex column, not how it lays out its own children) that got dropped once already and let `#content`'s flex-shrink algorithm compress `#viewBar` below the floats' actual height whenever the window was short on vertical space, clipping/overlapping the toggle+level-filter against the table below; `#statusStrip`/`#timelineMinimap` carry the same declaration for the same reason. The row itself is **always visible**, exactly like `#breadcrumb`/`#levelBar` always were as standalone rows before — only `#fhTabs` is hidden/shown by `renderMainView()`, not the whole row: no file loaded, or the active node is an extraction filter (no Highlight companion) → `fhTabs.style.display = "none"`; otherwise `"flex"`. `#levelBar`, `#btnPinBookmarks` and `#breadcrumb` stay visible and populated in **every** state, including extract mode, since `renderExtractTable()` still calls `applyLevelFilter()` and the filter chain is still useful navigation there — this is the one behavioral thing to keep in mind if `#viewBar` is touched again: don't reach for hiding the whole container, only `#fhTabs`. `#btnPinBookmarks` keeps its own `.toolbar-icon-btn`/`.active` look (an icon button, styled like the other header toggles it used to sit next to) rather than being restyled as a `.level-btn` pill — it's an additive OR toggle, not a subtractive level filter, and looking identical to the pills would misrepresent what it does; it's positioned in the same floated row as the level pills, not literally nested inside `#levelBar`. **Sizing (bugfix, same session)**: `.toolbar-icon-btn`'s fixed `29x29px` box is correct in the header, where every neighboring button is the same square — but here it made `#btnPinBookmarks` visibly taller than `#fhTabs`/`#levelBar`/`#breadcrumb`, which all get their height from `padding:4px` + `border:1px` + content instead of a fixed box (see `.crumb`'s own CSS comment for the underlying mechanic). Fixed with a `#btnPinBookmarks{width:auto; height:auto; padding:4px 8px}` override, scoped to the id (not `.toolbar-icon-btn` itself, so the header buttons using that class are untouched) — the button now sizes around its 12x12 icon exactly the way `.level-btn` sizes around its text, landing at the same row height instead of towering over it. See "Highlight view (Filter/Highlight split)" → "Layout" for the toggle itself.

**Breadcrumb chips are sized to match the level filter pills** (`.crumb`'s `font-size`/`padding` mirror `.level-btn`'s exactly — same 10.5px text, same 4px 9px padding — so the two pill styles read as one consistent row instead of the breadcrumb looking subtly smaller/shorter). **Matching font-size and padding alone wasn't actually enough** — `#breadcrumb` used to carry `line-height:26px` (leftover from before the chips were resized, meant to space wrapped lines apart), silently inherited by the inline-block `.crumb`/`.crumb-sep` and adding ~26px on top of their padding, since an inline-block's own single line of text IS sized by line-height. `.level-btn` never showed the equivalent problem because it's a flex container — flex layout ignores line-height for its own box sizing entirely, so the mismatch was invisible on the level side and only visible on the breadcrumb side. Fixed by removing the line-height from `#breadcrumb` and setting `line-height:normal` explicitly on `.crumb`/`.crumb-sep` instead; the gap between wrapped lines now comes purely from their own vertical margin. **Lesson for future work here**: `font-size`/`padding` parity between two differently-laid-out elements (flex vs. inline-block) doesn't guarantee height parity — check `line-height` too, since it only affects one of the two layout modes.

**Same row, a third round: top alignment.** Even with matching height, `.crumb`'s chips weren't reliably lining up vertically with `#fhTabs`/`#levelBar`'s floated tops — `vertical-align:middle` aligns an inline-block relative to its *parent's* font baseline/x-height, not to wherever a float happens to start; the two only coincided by accident, dependent on inherited font metrics, and could drift. Fixed by switching `.crumb`/`.crumb-sep` to `vertical-align:top` with `margin-top:0` — since `#fhTabs`/`#levelBar` are the first content in `#viewBar` and floats don't push the following normal-flow content's *starting* y-position down (they only narrow the available width), a float's top and `#breadcrumb`'s first line both begin flush at `#viewBar`'s content-box top; pinning `.crumb` to the top of its own line box (instead of centering it against a font-metric reference) makes it coincide with that same y-position structurally, not by coincidence. The wrapped-line spacing that used to come from `.crumb`'s top+bottom margin now comes from `margin-bottom` alone (`0 4px 6px 0`), matching `#fhTabs`/`#levelBar`'s own `margin-bottom` for a consistent gap. `.crumb-sep` keeps a small top margin (`4px 3px 6px`) to roughly center its thin "›" glyph against the taller padded pill beside it, rather than sharing the pill's own top-alignment reference — it has no padding/border of its own, so top-aligning it flush would visually sit too high next to the pill's text. **Chips are also clickable**: `renderBreadcrumb()` attaches a click handler per chip that sets `state.activeId`/`state.multiSelect` to just that node and calls `render()` — the exact same single-select behavior a plain (non-Ctrl) tree-row click already does (see `renderNode`'s row click handler) — so the breadcrumb doubles as a quick "jump to an ancestor filter" shortcut without any new selection machinery. Works for every node in the chain, including the file root at the start and the currently-active node's own chip (a harmless no-op re-selection).

**Round 4 (person screenshot, this session, 2026-08-14): #fhTabs is the actual height reference, not the pills.** Despite three rounds of matching `.crumb`/`.level-btn` to *each other* (padding, then `line-height:normal`, then `vertical-align:top`), the View-Toggle (`#fhTabs`) still rendered visibly taller than everything beside it — because none of those rounds ever compared against `#fhTabs` itself. Root cause: `#fhTabs` is structurally a **nested double box** — `.view-tabs`' own `padding:2px`+`border:1px`, wrapping `.view-tab`'s own `padding:4px 11px` — while `.crumb`/`.level-btn`/`#btnPinBookmarks` are each a **single box** (one padding+border layer). At equal content height, that's an inherent ~4px of extra chrome on `#fhTabs`' side that no amount of padding/line-height *parity between the pills* could ever close — the three earlier rounds were solving the wrong equation. Also discounted incorrectly by round 2's reasoning (see its comment above): a flex container's own auto height **is** affected by `line-height` when the flex item is inline text (verified empirically this session), so `.level-btn` was never actually immune to line-height the way that comment claimed. Fixed by pinning **explicit, non-`"normal"` `line-height` values** (removing all remaining font-metric/platform dependence — `var(--font-ui)`/`var(--font-mono)` are system-font stacks, which is exactly why "close but not quite" kept recurring across rounds) so the arithmetic is provably equal regardless of platform: `.view-tab`'s `line-height:12px` reproduces `#fhTabs`' own pre-existing rendered height (no visible change to the reference itself) — outer `padding(4)+border(2)` + inner `padding(8)+line-height(12)` = 26px total. `.level-btn`/`.crumb` get `line-height:16px` — `padding(8)+border(2)+line-height(16)` = 26px, matching exactly (the extra 4px of line-height is precisely what the missing nested-box chrome cost them). `#btnPinBookmarks` gets a direct `height:26px` (simplest option there, since it's already flex-centered — no line-height math needed). `.crumb-sep`'s top margin grew `4px → 7px` to keep its glyph roughly centered against `.crumb`'s now-taller box. Verified against a real Chromium render (not just jsdom, which has no layout engine and could only assert the declared CSS values): all four elements now measure exactly 26px. See `.view-tab`/`.level-btn`/`.crumb`/`#btnPinBookmarks`'s own CSS comments for the full arithmetic if this row needs touching again.

**Keyboard shortcuts popup** — the reference list of shortcuts (Ctrl+F, F2, Ctrl+C/X/V, Del, B, arrow keys, etc.) used to be a permanent strip pinned to the bottom of the sidebar (`#shortcuts`, direct child of `#sidebar`). Per a person UI-adjustment request it's now a popup (`#shortcutsPanel`) behind a new header button (`#btnShortcuts`, `ICON_HELP`), positioned/opened/closed via the exact same pattern as the pre-existing `#bookmarksPanel` (`getBoundingClientRect`-based fixed positioning below the button, `.hidden` class toggle, closes on outside click via the shared `document` click listener and on `Escape`). `#shortcuts`'s own content/CSS is otherwise unchanged — it's just nested inside the popup now (`overflow-y:auto` added so a long list scrolls within the popup's `max-height` instead of growing it unbounded).

## The three "active node" views

`renderMainView()` picks a view based on the active node's `filterType`, all mutually exclusive:

1. **Log view** (default) — virtualized (`ROW_HEIGHT = 28`, `BUFFER_ROWS = 10`) so it stays smooth at any file size; only the rows in/near the viewport are ever real DOM nodes. Has the level quick-filter bar, click-to-select + arrow-key navigation, right-click context menu (filter before/after this, extract numbers), double-click **reveals the entry in the Highlight view** (see below) with flash highlight, and a resizable detail panel at the bottom (drag the handle above it) showing the full selected message with preserved line breaks. The tree sidebar's width (`#sidebarResizer`) and, in Stacked layout, the Filtered/Full split (`#fhSplitResizer`) are resizable the same way — see "Highlight view" below.
2. **Extraction table** (`filterType === "extract"`) — spreadsheet-style grid, not virtualized (extraction results are expected to be selective). Has its own Table/Plot tab switcher (see Plotting below). Cell selection is a `Set` of `"row,col"` keys (not a rectangle) specifically so Ctrl+click can build **non-contiguous** selections (e.g. columns 1 and 3, skipping 2) — plain click/drag/shift-click still do contiguous ranges. Copy is always plain TSV (paste-ready for Excel) via `copyTextToClipboard` (Clipboard API with an `execCommand` fallback for `file://` contexts where the modern API may be restricted). The pattern is shown above the table as numbered, colored chips (`COLUMN_PALETTE`, cycles if >6 columns) with **bidirectional hover linking**: hover a column header/cell → its chip highlights; hover a chip → its column highlights; hover a row number → all chips highlight (the whole pattern produced that row). The only view with **no Highlight-view companion** — double-click still does the old destructive full-log jump (`jumpToFullLog`), since there's nowhere else in this view to reveal the entry.
3. **Link pair view** (`filterType === "link"`) — each pair rendered as two individually-clickable/double-clickable rows joined by a visual brace with a Δ-time label between them. Right-click the brace = context menu on the *combined* pair entry (so "Extract numbers" works across both sides); right-click one row = context menu on just that side; double-click a row = reveals that row's real underlying entry in the Highlight view, same as the log view (see below — link view is a Filter-view "flavor" for this purpose, not a separate case).

**Log view and link view are both "Filter view" flavors**, each paired with a **Highlight view** — see the dedicated section below.

## Highlight view (Filter/Highlight split)

Two side-by-side views of the same file, introduced together as `#fhSplit`: the **Filter view** (UI label "Filtered") is the pre-existing log/link view, narrowed by the active filter-tree node. The **Highlight view** (UI label "Full") is always the active node's *whole root file* (`getRootFileId(state.activeId)`, unaffected by which filter node is active), with any filter-tree node that has a highlight colour set colouring its matching rows. Internally every identifier still says "Highlight" (`renderHighlightView`, `#highlightWrap`, `highlightColorMap`, `fhLayout`, …) — only the button label was renamed to "Full"; a full internal rename was judged a much bigger, riskier diff for what was a label-only ask, so it was left alone. The point of the split is tracking 2–3 patterns across the *whole* file while the Filtered view stays narrowed to something specific — e.g. filter down to one thread's messages in the Filtered view while the Full view shows where ERRORs and a particular retry pattern land across the entire file.

**Turning on a highlight rule**: each filter-type tree row (not file rows, not `extract` rows — see `renderNode`) has a small colour **swatch** button where the old multi-select checkbox used to be (see "Tree interactions" below for where that checkbox went). Click it to open a small custom colour picker (`#colorPickerPopup`) — a hue wheel (`conic-gradient` disc, click anywhere to pick a hue at a fixed 68%/55% saturation/lightness) plus a row of curated presets, deliberately **not** the native `<input type="color">` (Windows' native picker UX varies too much to be predictable here). Right-click the swatch, or "Clear colour" in the picker, clears it. The colour **is** the on/off state — no separate boolean; an uncoloured node just isn't a highlight rule. Two colours can coincide across different nodes (not deduplicated — may be intentional grouping) and travel with the node through filter save/load JSON, copy/paste (`cloneSubtree`), and undo/redo (`snapshotSubtree`/`restoreSubtree`), the same way `inverted`/`linkedId` do.

**Computing matches** (`computeHighlightMap(fileId)`): walks every node under the file (not just the active chain — a highlight rule anywhere in the tree should show up), and for each coloured filter node adds its colour to every entry it matches, via `getEntries(node.id)` — cheap since `getEntries` is already memoized per node. `link` nodes are a special case: their results are synthetic pair entries, not real ones, so every real underlying entry — via `getTupleEntries(pair)`, which recurses through arbitrarily many nesting levels for a chained/multi-hop link, not just `pair.first`/`pair.second` one level deep, see "Link filter" → "Chained links" — gets the colour instead of the synthetic pair id. A row matching several rules gets several small colour markers (`.hl-marker`, thin stripes in the left gutter) rather than one blended colour — there's no natural priority between arbitrary user rules the way `LEVEL_SORT_RANK` orders log levels, so no attempt is made to pick a "winning" colour. **Shown in both views**: originally Full-view-only, `renderVisibleRows()` (the Filtered view) now renders the same markers from the same `highlightColorMap`, computed once per `renderMainView()` call (before either view's own render) rather than twice, so the Filtered view's first paint after a node/filter switch already has the right colours instead of showing the previous node's map until the next scroll. The Filtered view's own `.ctx-bracket` (time-context filter) uses the same left gutter slot — a row that's both context-bracketed and highlight-matched shows both markers overlapping; accepted as a known edge case rather than adding a second gutter lane.

**Selection stays unified**: `state.selectedId` is shared between both views (it always was, for the detail panel — see `updateDetailPanel`), so `updateSelectedRowClass` now syncs the `.selected` class on whichever of `#tableRows`/`#highlightRows` currently has that row rendered, regardless of which view the click came from. Plain click in either view just selects (`selectEntry`/`selectHighlightEntry`) — no scrolling of the other view. Double-click in the Filter view (or a link-view pair row) calls `revealInHighlightView(entry)`: selects the entry, reveals the Full panel (switches to it, in tabs layout — a no-op in stacked layout, both panels are already shown), and sets `state.highlightScrollTargetId` to scroll/flash it there — **without** touching `state.activeId` or the level filter, unlike the old `jumpToFullLog` this replaced. This is deliberately not routed through `render()`: a full render would reset the Filter view's own scroll to the top (see `renderTable`'s "any other change... starts back at the top" logic), exactly the destructive behavior this was built to avoid.

**Level quick-filter applies to both, in lockstep**: both views already computed their entries via the same global `state.levelFilter`/`applyLevelFilter` (empty set = show everything, non-empty = only those levels) — that part was never the gap. The gap was *rendering*: `renderLevelBar()`'s toggle-button click handler used to call `renderTable()` alone, so the Filtered view updated instantly but the Full view kept showing the previous level selection until some unrelated render happened to touch it (a node switch, a resize). It now calls `renderMainView()` instead, which re-renders whichever Filtered-view flavor is active *and* the Full view together — same single source of truth, now with a single render path too.

**Layout**: a single tri-state toggle (`#fhTabs`, three buttons: "Full" / "Filtered" / "Stacked") — `applyFhView(view)` is the one entry point, `fhLayout` ("tabs" | "stacked") and `fhActiveTab` ("filter" | "highlight") are still the two pieces of underlying state, persisted to `localStorage` the same way the theme toggle is (a display preference, not session/filter data). "Full"/"Filtered" set `fhLayout` to `"tabs"` and pick which panel shows; "Stacked" sets `fhLayout` to `"stacked"` directly, showing both panels at once, **Full on top / Filtered on the bottom** (that's the actual DOM order inside `#fhSplit` now, not just a CSS `order` override) — `#filterSlot` at a resizable explicit height (`#fhSplitResizer`, drag handle between the two panels, same mechanism as the detail panel's resizer below, and same bottom-panel sign convention: dragging the handle down shrinks the panel below it), `#highlightWrap` filling whatever's left above it. Session-only, not persisted, same as the detail panel height. Each panel also carries a small top-right **identifier badge** (`.fh-panel-badge`, "Full" / "Filtered") that's only shown in Stacked layout — in tabs layout the active `#fhTabs` button already says which one is showing, so the badge would be redundant there.

`#fhTabs` itself lives inside `#viewBar`, a single merged toolbar row that also holds `#levelBar` and `#breadcrumb` (see "Header/toolbar layout" below) — only `#fhTabs`'s own visibility is toggled by `renderMainView()` (hidden with no file loaded or on an extraction node, since extract has no Highlight companion); `#levelBar`/`#breadcrumb` stay visible in every state.

**Rendering**: the Highlight view has its own complete copy of the Filter view's virtualization scheme (`renderHighlightView`/`renderHighlightVisibleRows`/`scrollToHighlightIndex`/`setHighlightScroll`, `#highlightBody`/`#highlightSpacer`/`#highlightRows`) — a second, independent scroll container. It reuses the Filter view's `.row-grid`/`.log-row`/`.col-*` CSS wholesale (extended the relevant ID selectors rather than duplicating rules) so the two views' rows line up visually. One deliberate behavioral difference from `renderTable()`: **it does not reset scroll to the top on every render.** The Filter view resets on every tree/filter change because that always means "new content" there; the Highlight view's content (the whole file) usually hasn't changed across those same actions, so resetting it every time would make it useless as a stable reference while browsing the Filter view. It only resets when the root file itself changes (`lastHighlightRootId`).

## Plotting (inside the extraction table's Plot tab)

Custom SVG chart builder, no library. Line / Bar / Scatter, chosen per-plot via `plotConfig`. Only columns with a numeric-capable type (`isPlottableType`: `float`/`int`/`hex`/`time`) are offered as axis candidates; `time` values are parsed to milliseconds (`parseTimeToMs`) so time columns are plottable too.

- **Line/Bar**: multi-select Y columns (checkboxes, colored to match their extraction-table chip); line points are connected in **row order**, not sorted by X value, because extracted rows are already in the log's chronological order and that's almost always the meaningful sequence.
- **Scatter**: single X, single Y, optional third **color-by-value** column rendered with a blue→yellow→red gradient (`plotColorScale`) plus a legend.
- **Axis scaling**: `niceTicks()` is a standard "nice numbers" algorithm (picks a 1/2/5×10ⁿ step) so tick spacing looks sensible regardless of whether the data is in the hundreds (mm) or 10⁻⁵ range (µm) — this was a specific requirement, not an afterthought. Manual min/max override inputs exist per axis for when auto isn't wanted. For comparing multiple Y-series that live on very different scales in the *same* chart, there's a **"Normalize each series (0–1)"** toggle (only shown with 2+ series selected) — auto-scaling alone can't fix that case since it's one shared axis across series.
- 3D scatter was explicitly deferred (lower priority per the person).
- **Gotcha already hit and fixed**: don't auto-refill an "empty" multi-select (Y columns) on every re-render — it fights the natural "uncheck the old one, check the new one" interaction, since the render in between the two clicks sees zero-selected and silently restores a default. Fixed by only auto-picking Y defaults once per extraction (`plotConfig.yColsInit`), not every render.

## Value assertions (extraction columns)

Per numeric-capable extraction column (`isPlottableType`: `float`/`int`/`hex`/`time` — same set the Plot tab already offers as axis candidates), an optional expected-value check: either a **range** (min and/or max, either side optional) or a **target ± tolerance**. Stored as `node.assertions = { [colIndex]: { mode: "range"|"target", min, max, target, tolerance } }` on the `extract` node itself — lazily created the first time a column gets one, never on other filter types.

**Checking a value**: `checkAssertion(node, colIndex, rawValue, type)` parses the cell via the same `parseValueForPlot` the Plot tab uses, and returns `true` (violated) / `false` (passed) / `null` (no assertion configured, or the value didn't parse as a number — an unparseable cell is neither a pass nor a violation, same "leave it alone" stance sorting already takes with unparseable values). `assertionSummary(node, colIndex)` scans the current `extractRowsData` once to produce the `{violations, checked, total}` used for the header badge.

**UI**: a small target-icon button (`.extract-assert-btn`, `ICON_TARGET`) appears in every numeric column's `<th>`, next to the existing sort button — same `stopPropagation` pattern on `mousedown`/`click` so opening the dialog doesn't also trigger the header's column-selection drag. Clicking it opens `#assertDialog` (mirrors the `#contextDialog`/`#linkDialog` small-modal pattern), where Range/Target±Tolerance is a two-button mode toggle rather than a dropdown. Once a column has an assertion, its header shows a small badge — "N of M outside range" — colored via `--level-error` only once `violations > 0` (a configured-but-currently-passing assertion stays quiet, not attention-grabbing). Violating cells in the table get `.assert-violation` (a `--level-error-soft` tint + colored text, same visual language as `.log-row.lvl-error`).

**Plot tab**: a point/bar whose value on *either* axis fails that axis's column's own assertion gets an extra error-colored ring/border drawn on top (line: outlined circle; bar: colored stroke; scatter: larger outlined ring) — on the theory that a plot is often where an out-of-range value actually gets *noticed*, since the table's cell tint is easy to scroll past. The ring color (`PLOT_ASSERT_COLOR`) is a plain hex literal matching `--level-error`, not a CSS custom property — kept consistent with every other plot color (`COLUMN_PALETTE`, `PLOT_COLOR_STOPS`), since the whole chart is built as raw SVG attribute strings in JS, not as CSS-styled elements.

**Persistence**: assertions travel with the node through `serializeFilterBranch`/`importFilterJson` (filter save/load JSON) and `cloneSubtree` (copy/paste), the same way `inverted`/`linkedId`/`contextBefore` etc. do — an assertion is part of what makes an extraction "the same filter," not a transient view setting. They are **not** reset when the extraction pattern is edited to add/remove columns; a stale assertion on a column index that no longer means what it used to is a known sharp edge (see Known limitations). `node.ignoredColumns` (see "Extraction: live pattern preview + ignored columns" below) follows this exact same 4-touch-point precedent (plus `snapshotSubtree`/`restoreSubtree` for undo/redo, which assertions also already went through).

## Column statistics

Min / max / mean / stddev per numeric-capable extraction column (`computeColumnStats`), rendered directly above the table (`#extractStatsBar`, `renderStatsBar`) — no toggle, always visible when at least one column is numeric, empty (and collapsed via `:empty{display:none}`) otherwise. Single pass to collect values + running min/max/sum, second pass for the variance sum — two passes over `extractRowsData`, not `Math.min/max(...spread)`, specifically to avoid the call-stack argument-count ceiling some engines hit on very large arrays (extraction results are already documented as "not virtualized — fine for realistically-sized results," so this stays in that same performance envelope rather than trying to be smarter). Numbers are formatted with the Plot tab's existing `formatAxisNumber` (nice/short representation) rather than a separate formatter.

## Extraction: live pattern preview + ignored columns

From person-supplied `REQUIREMENTS-extract-preview-and-ignore.md`: two related gaps in the extraction workflow — no preview of what a pattern actually captures *while typing it* (only an after-the-fact match count), and no way to have a placeholder anchor the pattern without becoming a permanent column.

### Ignored columns — data model (Option B)

**Option B chosen** over the doc's alternative ("a new `[ignore]` pattern token"): `node.ignoredColumns: number[]` — indices into the compiled pattern's columns — on the `extract` node itself, lazily created the first time a column gets ignored, same convention as `node.assertions`. Chosen because it's the smaller, self-contained change the doc itself flagged as the likely winner: the regex/matching is **completely untouched** (an ignored placeholder still anchors the pattern exactly as before), it's a pure display/export-time filter, and it doesn't need to decide how a new token interacts with column auto-naming (`value`, `value 2`, ...) the way a `[ignore]` token would. `isColumnIgnored(node, colIndex)` / `setColumnIgnored(node, colIndex, ignored)` are the two small helpers everything else goes through.

**A structural consequence worth understanding before touching extraction code again**: `extractColumns` (the module-level global) is no longer a dense, positional array — it's the *currently visible* subset of the compiled pattern's columns, and it can have gaps. Each surviving element keeps its original compiled-pattern position as a stable `.colIndex` property (this is the number `node.ignoredColumns` contains, the number `data-col`/`data-sort-col`/`data-assert-col` DOM attributes carry, and the number `node.assertions`/`plotConfig.xCol`/`.yCols`/`.colorCol`/`extractSortCol` are keyed by) — while `row.values` in each `extractRowsData` entry stays the **full, unfiltered** array (one value per compiled column, ignored or not), since matching itself never changes. `findExtractColumn(colIndex)` resolves a stable `colIndex` back to its (visible) descriptor, returning `null` when that column is currently ignored — every colIndex-keyed lookup (`computeColumnStats`, `assertionSummary`, `openAssertDialog`, `extractRowComparator`, the Plot tab's axis-candidate derivation) goes through it rather than bracket-indexing `extractColumns` directly. The cell-selection subsystem (`rowCells`/`rangeCells`/`columnsRangeCells`/`allCells`) was adjusted the same way — it walks `extractColumns`' actual `.colIndex` values instead of assuming a dense `0..length-1` range, so a shift-click column-range spanning an ignored column simply skips it rather than silently selecting hidden data.

**Excluded from**, per the requirements doc's list — all confirmed by Group 24's regression coverage: the extraction table (`renderExtractTable` never emits a `<th>`/`<td>` for an ignored column), column statistics (`computeColumnStats` returns `null` for one), the Plot tab's axis-candidate list (an ignored column is simply absent from `extractColumns`, so the existing `plottable` derivation — and its already-existing stale-selection reconciliation for `plotConfig.xCol`/`.yCols`, originally built for pattern edits — transparently also handles a column being ignored/un-ignored, no extra code needed there), copy-to-Excel/TSV export (`copyWholeExtractTable` now maps through each *visible* column's `.colIndex` rather than joining `row.values` wholesale; `extractSelectionToTSV` needed no change at all, since the cell-selection generators above already never produce a selection cell for an ignored column). Value assertions: an ignored column gets no assert button (no `<th>` at all), but — same accepted sharp edge as assertions surviving a pattern edit — an assertion configured *before* a column was ignored is left in `node.assertions` untouched, not deleted; it simply stops being checked/shown while the column stays ignored (`assertionSummary`/`computeColumnStats` both return `null` via `findExtractColumn`).

**Two toggle surfaces**, both wired to the same `setColumnIgnored`:
- **Post-creation**, in the existing `#extractPatternView` (the colored-chip template view above the table): `renderExtractPatternView` gained an optional third `opts` argument, `{ onToggle(colIndex) }` — when present, every chip becomes clickable (`.chip-toggleable`) and dimmed (`.chip-ignored`) when ignored, `title` reflecting the current state. `renderExtractTable` passes the **full, unfiltered** column list here (re-derived from `spec.columns` — NOT the filtered `extractColumns` — since this function independently re-walks every raw placeholder token in the pattern text and must produce exactly one chip per token regardless of ignore state) plus an `onToggle` that calls `setColumnIgnored`/`renderExtractTable` directly on the live node.
- **While authoring**, in the new `#filterPopup` preview (see below) — clicking a highlighted span toggles a *popup-local* working set, `filterPopupIgnored` (a `Set`, module-level `let`), applied to the node only on submit. Pre-populated from the edited node's existing `ignoredColumns` in edit mode (`openEditFilterPopup`), empty in create mode, cleared on close — so a filter can be created with columns already marked ignored, and re-opening Edit shows the current state immediately. `createFilterNode`/`updateFilterNode` both gained a 5th optional `ignoredColumns` parameter for this (backward compatible — every other existing call site is unaffected).

### Live pattern preview (`#filterPatternPreview`, in `#filterPopup`)

While typing/editing a pattern, `evaluateLiveMatch`'s existing 150ms debounce now also calls `updateFilterPatternPreview(val, baseEntries)` (one shared timer, not a second competing debounce) — it finds the *first* of `baseEntries` (the same rows `evaluateLiveMatch`'s match-count already uses) the compiled pattern actually matches, and renders that real message with each capture group's substring wrapped in a `<span>` colored via the same `columnColor`/`COLUMN_PALETTE` scheme the table and post-creation pattern view use, so colors stay visually consistent across all three. `white-space:pre-wrap` (matching `#detailMessage`'s own handling) so a multi-line stack-trace sample renders faithfully. Exact per-group `[start,end]` offsets come from a **second** `RegExp` built from `spec.regexStr` with the `d` (match-indices) flag (`m.indices[i+1]`) — the compiled `regex` actually used for matching is untouched, this is purely a preview-time convenience. No matching sample yet → a muted "No matching sample message yet." note (same spirit as the live-match count's `--warn` "0 of N" state, just phrased for a single-message preview). Hidden entirely for a non-extraction (plain text) filter or an invalid pattern.

**Gotcha hit and fixed**: the preview span's click handler must call `ev.stopPropagation()`. Without it, clicking a span — whose handler synchronously does `filterPatternPreview.innerHTML = ""` to re-render — detaches the clicked span from the DOM *while the click event is still bubbling*. The existing global "click outside a popup closes it" handler (`document`'s click listener, `!filterPopup.contains(ev.target) && ...`) then sees a detached `ev.target`, `contains()` correctly returns `false` for it, and the popup closes itself out from under the click. The post-creation pattern-chip toggle already had this same guard for the identical reason (a chip click re-renders the whole `#extractPatternView`); this is the second instance of the same class of bug, worth remembering for any future click handler that re-renders its own clicked ancestor. **A third instance turned up in the very next session** (person-reported): `treeContextMenu`'s click handler — right-click → "Edit filter…" opened `#filterPopup`, then the still-bubbling click reached the same global handler and closed it right back, since `closeTreeContextMenu()` only toggles a class rather than removing the menu item, so `ev.target` was simply *outside* `#filterPopup` this time rather than detached — same root cause (a click that opens something else must not keep bubbling to a close-on-outside-click listener), different trigger. Fixed the same way; see "Status / changelog" for the bugfix-session entry.

## Tree interactions

- **Edit a filter** (`F2` with the node active, or right-click → "Edit filter…"): reopens the `#filterPopup` pre-filled with the node's current value/NOT state, submit button reads "Save" instead of "Add filter". Only offered for `text`/`extract` filters (`openEditFilterPopup`) — the two filter types with a plain value the popup's single input can represent; `and`/`or`/`link` derive their value from two other nodes, and `context` has its own before/after dialog. Updates the existing node in place (`updateFilterNode`: value, `filterType` — typing/removing extraction tokens can flip which one applies —, `inverted`, `name`) rather than creating a new child, then `invalidateAllCaches()` (same global sweep as move/delete/invert, since every descendant's cache derives from this node's result). The live-match preview evaluates against the node's *existing parent* in edit mode (not its own current result) — same base entries as when it was first created. Deliberately not undoable, same as the invert toggle — see "Undo / redo" below.
- **Highlight-colour swatch** (visible on filter-type tree rows, left of the icon — replaces the old always-visible multi-select checkbox that used to sit here; see "Highlight view (Filter/Highlight split)" above): click opens the custom colour picker, right-click clears the colour. Not shown on file rows or `extract` rows (which get an empty spacer instead, for column alignment) — see `renderNode`.
- **Ctrl+click** is the way to build a multi-selection now that the checkbox is gone — it already did this independently of the checkbox (toggles the clicked node into/out of `state.multiSelect`, same as before), so nothing else needed to change here when the checkbox was removed. Also updates the active/viewed node, which the old checkbox intentionally didn't.
- **Single click** (on the row body, not the swatch): sets both the active (viewed) node and resets multi-select to just that node.
- Each row also shows a small **type tag** (`FILE`/`TXT`/`TIME`/`TBL`/`AND`/`OR`/`LNK`, via `typeTagFor(node)`) and, for filter nodes, a **row-count percentage bar** against the parent's count (`getEntries(node.parentId).length`) — a quick visual for how much a given filter narrowed the data. Root file nodes have no parent to compare against, so they render an empty placeholder there instead.
- The moment `state.multiSelect.size >= 2`, an always-visible **action bar** (`#treeActionBar`, `renderTreeActionBar()`) appears above the tree with the applicable buttons — no right-click needed to discover what's possible.
- **Right-click** still opens the equivalent bulk-action context menu (`openTreeContextMenu`) when the clicked node is already part of a ≥2-item selection, for people who prefer it or are mid-drag with the mouse already there.
- **Both surfaces share one source of truth**: `describeBulkActions(nodes)` computes which actions apply (and the explanatory note when none do) and `performBulkAction(action, ids)` runs them — the action bar and the context menu are just two different renderers over the same logic, so they can never drift out of sync:
  - 2+ **files** selected → **Merge**: new chronologically-sorted root file (`mergeFiles`), name = source names joined with " + ", entries reused by reference. **Starts with zero filters** — this was an explicit requirement so existing per-file filter trees aren't disturbed; copy filters over manually afterward if needed.
  - exactly 2 **filters from the same root file** → **Combine (AND)**, **OR**, **Link…**. Different root files → an explanatory disabled note instead (cross-file filter combination is intentionally unsupported; merge the files first if you need it — filters only ever operate within one tree).
  - anything else (mixed types, wrong count) → an explanatory note, never a silent no-op.
  - "Link…" opens a small modal (`#linkDialog`) to pick which of the two is the reference/anchor, direction, and N; the other two actions apply immediately.
- Selected/checked rows get a stronger highlight than before: `--accent-soft` background *plus* the existing 1.5px accent ring (previously ring-only) — see the "Visual language" section for why rings were preferred over fills originally, and why this case gets both.
- The per-row delete (hover-only ✕ icon) is unaffected by any of the above — it stays available on every row regardless of swatch/multi-select state, so bulk selection is never the only way to remove a single node.
- **Copy/Cut/Paste** (Ctrl+C/Ctrl+X/Ctrl+V, operating on `state.activeId`) work for every filter type, including `and`/`or`/`link` (see the Core data model section for why those were briefly excluded and how that was fixed). Copy duplicates and stays pasteable multiple times; Cut is a one-time move, clipboard cleared only once the move actually lands (see below). Del deletes the active filter; arrow keys navigate rows in the log view — both predate the multi-select work and are unaffected by it.
- **Right-click a single node** (not part of an existing 2+ multi-selection) opens a per-node menu — Copy, Cut, Paste (when the clipboard has something), Delete — the mouse-only equivalent of the keyboard shortcuts above, sharing the exact same underlying functions (`pasteClipboard`, `deleteNode`) via `treeCtxId`. Right-clicking a node that *is* part of a ≥2 multi-selection still opens the bulk-action menu instead (`openTreeContextMenu` branches on this).
- **Drag-and-drop**: any filter row is `draggable`; every node (file or filter) is a valid drop target to become the dragged node's new parent. `dragover`/`drop` call the same `moveNode()` cut/paste already uses, so the linked-cycle guard applies here too — a row that would create one never even gets the `drag-over` highlight, and a rejected drop shows the same toast as a rejected paste. The window-level "drop a file to load it" overlay (`#dropOverlay`, `position:fixed` over everything) is gated by `isFileDrag()` (checks `dataTransfer.types.includes("Files")`) specifically so it doesn't pop up — and swallow the tree's own drop target underneath it — while dragging a filter row; only a real OS file drag shows it.

## Undo / redo (filter-tree delete & move)

Deliberately narrow scope, matching the feature backlog: only filter node **delete** and **move** (drag/drop reparent, and Ctrl+X-then-paste, which is also a move) are undoable — not file deletion, not value/type edits, not checkbox/inversion/assertion toggles. A small snapshot-based command stack was chosen over deriving undo generically from every tree-mutating function, since the tree's structural invariants (a node's own `parentId` vs. the *other* nodes that might reference it via `linkedId`, see Core data model) are easier to reason about as "restore exactly this snapshot" than as a generic inverse of arbitrary mutations.

**The only two call sites** a user-facing delete/move should ever go through are `deleteFilterNodeWithUndo(nodeId)` and `moveFilterNodeWithUndo(nodeId, newParentId)` — every existing trigger (Delete key, per-row hover ✕, tree right-click menu, drag-and-drop `drop` handler, Ctrl+X-then-Ctrl+V's move branch) now calls one of these instead of `deleteNode`/`moveNode` directly. Anything that bypasses them silently isn't undoable. The one intentional exception is `importFilterJson`'s cleanup of a dangling `linkedRef` on a hand-edited file — that's not a user-initiated delete of an existing node, so it calls `deleteNode` directly.

**Snapshotting**: `snapshotSubtree`/`restoreSubtree` deep-clone a filter node's whole subtree the same way `cloneSubtree` does for copy/paste, with one crucial difference — **original ids are kept**, not reassigned. This matters because `getEntries()` already treats a missing `linkedId` target as "fail gracefully, empty result" (see Core data model) rather than crashing; keeping the same id means that if some *other* node elsewhere had a `linkedId` pointing into the deleted subtree, restoring it under its original id transparently heals that reference again — no separate bookkeeping needed for "what else pointed at the thing I deleted."

**The stack**: `undoStack`/`redoStack`, capped at `UNDO_STACK_LIMIT = 50` (oldest entries drop off silently). `pushUndo()` — called only from the two wrapped mutators above — always clears `redoStack`, since a genuinely new action makes any previously-undone branch unreachable (standard undo/redo semantics). `undo()`/`redo()` themselves move the same action object directly between the two stacks (applying the inverse or re-applying the forward mutation) without going through `pushUndo`, so they never clear each other's history — undoing three deletes and redoing one still leaves the other two redoable.

**UI**: `#btnUndo`/`#btnRedo` (toolbar, left of the theme toggle) — disabled via the plain `disabled` attribute when their respective stack is empty, tooltip names which action would be undone/redone next. `Ctrl+Z` undoes, `Ctrl+Shift+Z` **and** `Ctrl+Y` both redo (the second purely for muscle-memory compatibility with editors that use one or the other). A toast (`showCopyToast`) confirms which kind of action was undone/redone, since the tree can be deep enough that the effect isn't always visually obvious at a glance.

## Bookmarks

`state.bookmarks`: `Map<entryId, { note, bookmarkedAt }>` — **not part of filter save/load**, since a bookmark anchors a spot in the *data*, not a filter definition; it doesn't belong in a filter-tree JSON file the way `inverted` or a value assertion does. Originally session-only; now persisted across reloads by the session cache (as file + entry ordinal, since entry ids don't survive a reload — see "Session cache"). Deliberately scoped to real log entries selected in the plain log view (`state.selectedId`) — not link-view pair entries or extraction-table rows, which have synthetic/derived ids that are never added to `entryIndex` (see Core data model), so a bookmark on one could never be resolved back to a real row later. The row context menu (`#ctxBookmark`) and `openContextMenu` hide/no-op that menu item when the right-clicked entry isn't in `entryIndex` for exactly this reason.

**Toggling**: right-click a row → "Bookmark this row" / "Remove bookmark" (`#ctxBookmark`, label reflects current state), or press **B** with a row selected (`state.selectedId`). Bookmarked rows get a small filled star (`.row-bookmark-dot`, reuses `ICON_BOOKMARK_FILLED`) in the same left-gutter slot the context-filter bracket/anchor-dot uses — the two can in principle land in the same visual spot if a row is both a context-filter reference *and* bookmarked; accepted as a minor, rare cosmetic overlap rather than reserving a second gutter slot for it.

**Jumping**: `jumpToEntry(entryId)` is a generalized version of the existing `jumpToFullLog(entry)` — the latter assumes the entry belongs to whatever chain is *currently active* (true for every existing caller, which all operate on a row already on screen), which doesn't hold for a bookmark clicked from the panel while a completely different file/filter is showing. `jumpToEntry` instead resolves the entry's own root file via `findRootIdForEntry(entryId)` (a linear scan over `state.rootIds`, O(root file size) — fine since this only runs on a rare user click, not a render-path hot loop, same reasoning already applied to the timeline minimap's per-render rebuild) before switching `state.activeId`, clearing the level filter, and setting `state.scrollTargetId`, same as `jumpToFullLog`.

**Panel**: `#btnBookmarks` (toolbar) shows a count badge (`.toolbar-badge`) when non-empty and opens `#bookmarksPanel`, a `position:fixed` dropdown (same positioning style as the context menus) listing bookmarks sorted by entry timestamp, each with a level badge, truncated message, an editable note (plain `<input>`, saved on `change`), and a remove button. Clicking a row (outside the note input, which stops propagation) calls `jumpToEntry` and closes the panel. A bookmark whose entry no longer resolves (`entryIndex` lookup failed — e.g. the file was closed) renders as "Entry no longer available" with only a remove action, rather than being silently dropped from the list.

## Pin bookmarks into the Filtered View

From `FEATURE_BACKLOG.md` item 1 (person-requested, modeled on glogg/klogg's "marks" — lines marked in the main view that always break through the search pattern into the filtered results, merged in log order). Deliberately built as an extension of the existing Bookmarks feature rather than a third marker type, to avoid a second visual marker competing for the same left-gutter slot the bookmark dot and context-filter anchor dot already share (see "Bookmarks"), and because a bookmark's existing meaning — "this entry matters regardless of context" — already implies the pin semantics; introducing a parallel concept would just duplicate it.

**Toggle**: `state.pinBookmarksInFilteredView` (bool, default `false`), a toolbar button `#btnPinBookmarks` (`ICON_PIN`, a map-pin glyph). It's a plain persistent on/off switch, not a popup — styled via a general-purpose `.toolbar-icon-btn.active` state (reused accent colors, same ones `.crumb.current` already uses) rather than anything bookmark-specific, so any future toolbar toggle can reuse it. Deliberately styled as its own control rather than a `.level-btn` pill: the level pills are subtractive (AND — narrows the result set; empty selection is the "show everything" special case), while pinning is additive (OR — adds entries the filter chain would otherwise exclude). Visually identical pills with inverted logic in the same row was judged a likely source of confusion, so pinning keeps its own distinct look instead. **Location (moved this session, person-requested)**: originally sat in the header next to `#btnBookmarks`; now lives in `#viewBar` itself, floated between `#fhTabs` and `#levelBar` — the row that controls what the active views show/hide, which is what this toggle does, so it belongs there rather than among the header's mostly popup-trigger buttons. The move is purely positional: same element, same id, same `.toolbar-icon-btn` class and click handler, still deliberately *not* inside `#levelBar` itself or restyled to match `.level-btn` (see "Header / toolbar layout" for the float mechanics).

**Merge logic** (`getVisibleEntries()`, the function `renderTable()`'s plain-table path already used for "node filter + level quick-filter"): when the toggle is on, the filter-tree result is unioned with the bookmarks belonging to the *active root file* — resolved via a new `getPinnedBookmarkEntries(rootId, orderIndexMap)` — and the union is re-sorted into that root's own chronological (array) order. A pin is **absolute**: it bypasses both the filter tree's own result *and* the level filter, the same way glogg/klogg's marks bypass the search pattern — consistent with the "regardless of the filters" framing the feature was originally requested with. `getPinnedBookmarkEntries` reuses `buildOrderIndexMap` (already used for the link filter's same-timestamp tie-break) as a combined membership test ("does this bookmark belong to this root") and position source for the final merge sort — a single O(root size) map build per render instead of an O(root size) scan per bookmark the way `findRootIdForEntry` would cost if reused here instead.

**Gotcha (bugfixed this session, person-reported)**: `toggleBookmark()` is a second choke point that can change WHICH rows the Filtered view shows, not just `render()`/`renderTable()` — while pin mode is on, adding or removing a bookmark can add or drop a row, so `toggleBookmark()` must recompute `currentViewEntries`/`pinnedOnlyIds` (i.e. call `getVisibleEntries()` again) itself before its own `renderVisibleRows()` repaint, guarded behind `state.pinBookmarksInFilteredView` so the common (pin-off) case is untouched. Deliberately does **not** call `renderTable()` for this — that always resets scroll to the top, which would yank the reading position on every bookmark toggle. See "Status / changelog" for the fix.

**Scope decisions made this session** (the backlog doc's open questions):
- *Persistence*: yes — part of `state`'s persisted settings, same tier as `levelFilter`/`sortColumn`. Written to and restored from all three existing settings carriers: the IndexedDB session cache (`buildCacheMeta`/`restoreSessionFromCache`), and the portable session export/import JSON (`buildSessionExport`/its import counterpart) — kept alongside `levelFilter`/`sortColumn` in all three places rather than singled out, since it's the same kind of view preference.
- *Extract / Link views*: **unaffected, deliberately** — not by an explicit guard, but structurally: `getVisibleEntries()` is only ever called from `renderTable()`, which only runs for the plain-table path (`renderMainView` routes extract nodes to `renderExtractTable()` and link nodes to `renderLinkView()` instead, neither of which calls it). This falls out of the existing view-routing, not a new special case, and matches the precedent already set by Bookmarks itself being scoped to real `entryIndex`-backed entries only (extraction rows and link pairs have synthetic ids that were never bookmarkable to begin with).
- *Visual treatment*: rows present only because of a pin (not because they matched the filter chain) get `.pinned-row` — an inset left `box-shadow` (`--accent-strong`) rather than a background tint, so it doesn't fight the existing per-level row background (`lvl-error`/`lvl-warn`/etc.). A bookmarked row that *also* genuinely matches the filter does **not** get this class — it's a normal match, not a "here only because of the pin" row, and `renderVisibleRows` distinguishes the two via a `pinnedOnlyIds` set refreshed on every `getVisibleEntries()` call. The status strip also surfaces a `"· N pinned"` suffix when `pinnedOnlyIds` is non-empty, so a row that visibly doesn't match the active filter text doesn't read as a bug.

**Non-goals**: no cross-root/cross-file pinning (scoped to the active root, same as the merge's `orderIndexMap`); no changes to the Bookmarks panel, notes, or `jumpToEntry` themselves — this is purely additive to how bookmarks are *surfaced* in the Filtered View.

## Tailing (live file updates)

Files opened with a **FileSystemFileHandle** (File System Access API — the "Open files…" picker via `showOpenFilePicker`, or drag&drop via `DataTransferItem.getAsFileSystemHandle()`, both Chromium) get a `node.tail = { handle, offset, pending, failed, busy }` and are polled every `TAIL_POLL_MS` (1500ms) by `tailTick()`: `handle.getFile()` returns a *fresh* snapshot each call, and if it grew, only the new byte range (`file.slice(offset)`) is read and parsed incrementally by `appendTailText()` into the existing `entries` array — handling chunks that start mid-entry (stack-trace continuation lines written across polls) and keeping an unterminated trailing line in `tail.pending` until its newline arrives. On any change, caches are invalidated globally (`invalidateAllCaches`, same `linkedId` reasoning as for moves), so **filtered views update live too**. Truncation/rotation (`size < offset`) resets that file's entries and re-reads from 0; a read failure (file moved, permission revoked) sets `failed` and stops polling that file. Files loaded as plain `File` objects (Firefox, the legacy `<input>` fallback, drops without handle support) are byte snapshots and simply never get a `node.tail` — they load normally, without tailing. Tailed files show a pulsing accent dot (`.tree-live`) in the tree.

**Follow behavior**: while `state.tailFollow` is true and the active node's root file is tailed (`isTailedLogViewActive()`), the log view scrolls with the newest entry. Manual scrolling away from the bottom or clicking/selecting a row (incl. arrow keys) disengages follow; the floating **`#tailJumpBtn`** ("Newest", bottom-right over the table) jumps back to the end and re-engages it. Programmatic scrolls (follow itself, jump-to-entry, node-switch reset) are distinguished from user scrolls via a timestamp (`lastProgrammaticScrollTs`, all programmatic writes go through `setTableScroll()`) so they never disengage follow. Tail-driven re-renders route through `pendingTableScroll` (`"bottom"` = follow, `"keep"` = preserve reading position) so `renderTable()`'s normal reset-to-top never yanks the view during live updates; follow only moves the view when the file *behind the current view* grew.

## Filter save / load (JSON files)

Right-click a filter → **"Save filter…"** writes a `.json` file via `showSaveFilePicker` (download-link fallback where that API is missing); right-click any node (filter or file) → **"Load filter…"** reads one back via `showOpenFilePicker` (hidden `<input>` fallback), inserting the result at the clicked node. `serializeFilterBranch()` / `importFilterJson()` do the actual work; format is `{ format: "logtrail-filters", version, activeRef, roots: [...] }`, `FILTER_FILE_VERSION = 2`.

**What gets saved** is the *branch* a filter belongs to: its ancestor chain from just below the root file, plus its own full subtree — that's what makes the overall result reproducible on load, not just the single clicked node.

**and/or/link nodes and their `linkedId`**: since bulk-combine only ever pairs two filters from the *same* file (`describeBulkActions`), a `linkedId` target is always reachable somewhere in the same file's tree — but it can sit outside the branch above (a sibling chain). Rather than dropping such nodes, `serializeFilterBranch()` pulls in the target's own ancestor chain too (not its subtree — just enough to recompute its result via `getEntries()`), transitively, so a combined filter is never silently broken or its logic altered, even when the target chain's own ancestor is itself an `and`/`or`/`link` node. Each independent chain this produces is written as its own entry in `roots`, tagged `attach: "target"` (the primary chain — goes exactly where "Load filter…" was invoked) or `attach: "file"` (a pulled-in dependency — always recreated directly under the target file's top level, never nested inside the clicked node, even when loading deep inside an existing structure).

**Loading onto a different tree re-evaluates, it doesn't replay a stored result**: nothing beyond the filter *definitions* (type/value/inverted, `linkDirection`/`linkN`/`linkOrderEnforced`/`linkExclusive`, `contextBefore`/`After`) is written to the file — every load creates fresh nodes with new uids, and `getEntries()` is always computed lazily against whichever file the reconstructed chain now structurally sits under. So an `and`/`or`/`link` filter loaded onto a different file (or a different point in the same file) is re-applied against that destination's own data, not the source file's original computed entries. Internal `linkedId` references are serialized as per-file `ref` numbers and remapped to the new uids on import; a corrupt/hand-edited file with a dangling `linkedRef` has that one combined node dropped (with its subtree) rather than left in a broken half-wired state.

**Known gap**: loading never checks whether the destination already has an equivalent branch — every load creates a fresh, independent copy, so loading the same file twice (or onto a tree that already has a matching chain) produces visible duplicates. No dedup/merge-with-existing-branch logic exists; flagged as a possible future addition, not built.

## Session cache (survives a browser reload)

The working session — loaded files, the complete filter tree per file, bookmarks, and a small set of view settings (level quick-filter, column sort, active node) — is persisted automatically and restored on the next page load. No user action required; a "Session restored" toast confirms it happened. Theme and the Full/Filtered/Stacked layout preference already lived in `localStorage` before this feature and stay there (display preferences, not session data).

**Storage**: IndexedDB (`localStorage`'s ~5 MB quota is far too small for log files), DB `logtrail-session-cache`, two object stores. `files` holds one record per root file — keyed by `node.cacheKey`, a random id assigned at file creation, because runtime node ids are fresh uids every load and can't key anything persistent. The stored text is **rebuilt from the parsed entries** (`rebuildFileText`: `entries.map(e => e.raw).join("\n")` — `raw` accumulates continuation lines, so multi-line stack traces round-trip; blank lines and pre-header junk the original parse already dropped are the only loss, and re-parsing the rebuilt text is a fixed point). `meta` holds a single `"session"` record: file order, serialized filter trees, bookmarks, settings.

**Filter serialization** reuses the filter-save/load JSON's field set and `ref`/`linkedRef` indirection (`serializeFilterTreeForCache` / `materializeCachedFilters`, deliberately parallel to `serializeFilterBranch` / `importFilterJson`) — but without the branch/chain-pulling logic, because the cache always writes each file's *entire* tree, so every `linkedId` target is trivially included. Restore materializes fresh uids and remaps `linkedRef`s per file, dropping dangling ones the same way filter-file import does.

**Bookmarks** are persisted as *(file cacheKey, entry ordinal, note, bookmarkedAt)* — entry ids don't survive a reload, but entry order within a rebuilt file is identical, so the ordinal is a stable address. An entry shared between a merged file and a source file is recorded against the first root that contains it (save and restore use the same first-wins scan order). Dangling bookmark ids (entry lost to tail rotation / file delete) just don't get written. This supersedes the old "bookmarks are session-only" limitation; they're still deliberately **not** part of the filter save/load JSON (a bookmark anchors a spot in the data, not a filter definition).

**Write strategy**: `meta` is small and rewritten via a single debounced hook at the end of `render()` (`schedulePersistMeta`, 400 ms) — every state mutation already ends in a `render()`, so no per-mutation persistence calls exist anywhere. File texts are written once on load (`loadFileDescriptors`) / merge (`mergeFiles`), and debounced per-file on tail changes (`schedulePersistFileNode`, 4 s — well above `TAIL_POLL_MS`, since rebuilding a large file's text every poll tick would be wasteful). A `pagehide` listener flushes pending debounces (an IndexedDB write started there normally completes even though its promise never resolves). Deleting a file deletes its `files` record immediately (`cacheDeleteFile`); the meta record follows via the normal render-hook rewrite.

**Restore** (`restoreSessionFromCache`) runs once at boot, after the initial empty-state render, reusing the loading-progress overlay per file. It's guarded by `sessionRestoreInProgress` so its own intermediate renders don't persist half-restored state, and any error abandons the restore (whatever loaded stays usable) rather than blocking the app on a corrupt cache. Every failure path in the storage layer (`openCacheDb`/`cacheStoreOp`) resolves `null` instead of throwing — no IndexedDB (private mode, old jsdom) just means the feature silently turns off and the app behaves exactly as before it existed.

**Escape hatch**: `localStorage["logtrail-cache-enabled"] = "0"` disables the whole feature. Deliberately no UI for it — clearing happens naturally by deleting files, and a toolbar toggle for a should-just-work feature felt like clutter; revisit if a real need shows up.

## File filter history (per-file memory across sessions)

Person-requested follow-up to the session cache, from a design discussion the same session (2026-08-14) before being built. Solves a different problem than the session cache: the session cache restores a whole *session* automatically on reload; this remembers filters *per file*, indefinitely, independent of any particular session, and offers them back — never auto-applies them — the next time a file with matching content is opened, even in a brand new tab/session that never touched the old one.

**Storage**: a third IndexedDB object store, `fileHistory`, in the same `logtrail-session-cache` DB (`CACHE_DB_VERSION` bumped 1→2 so `onupgradeneeded` creates it for existing users). One record per qualifying file, **keyed by the file's own content fingerprint** (`getFileFullHash`) rather than by session/`cacheKey` — this is the mechanism that makes the memory outlive a session: nothing about "which session wrote this" is stored at all, only "what content this filter tree belongs to". A record holds `{ name, fullHash, entryCount, timeSpan, filters, savedAt }` — `filters` is the same `serializeFilterTreeForCache` shape the session cache and filter-save/load JSON already use. **Deliberately scoped to the filter tree only** — no bookmarks, no view settings, no active-node ref — at the person's explicit request when this was scoped; those live in the session cache already, and duplicating them here would raise exactly the staleness/re-anchoring questions the session cache's own bookmark-ordinal scheme already has to deal with, for a part of the feature nobody asked for.

**Qualifying** = a real (non-merged) file with at least one real filter child. An empty tree has nothing worth remembering; a merged file is excluded even once it has its own filters, since `mergeFiles` starts every merge with a deliberately empty tree by design (see "Tree interactions" / multi-select bulk actions) — remembering filters *for a merge* would be remembering filters for a combination that's unlikely to recur byte-for-byte across sessions the way a single source file's content can.

**No cap on the number of remembered files.** This was an open question going into the build (an earlier draft considered a "last 10–20 files" LRU cap) — resolved against a cap because the two things that usually justify one don't apply here: storage size doesn't scale with log file size (a serialized filter tree is a few KB at most, not the log text itself — unlike the session cache's `files` store), and the natural per-record key (content fingerprint) already means loading the same content twice overwrites in place rather than accumulating duplicates, so there's no unbounded-growth-from-normal-use failure mode to cap against either. A long tailing session doesn't spam the store: a new record is only written when the filter tree is actually saved (debounced from `render()`, `schedulePersistFileHistory`, same 400 ms window as `schedulePersistMeta`), not on every tail-growth tick — a file that keeps growing under a stable filter tree just keeps overwriting its own single record under its (also-changing) current fullHash, and each earlier snapshot's record is left behind, which is a *feature* here (see tier 2 below), not a leak. If unbounded growth ever becomes a real concern in practice (long-lived shared/kiosk profiles), the natural follow-up is a **time-based expiry** (drop records unmatched for N months) rather than a count cap, since relevance here tracks recency of a match, not an arbitrary "last N files" number — deliberately deferred rather than speculatively built.

**Matching** (`matchFileHistory`) reuses the exact same tiered content-fingerprint technique Session export/import's `matchExportedFile` already established, just run in the opposite direction: one just-loaded candidate file checked against every stored record (since the history store is unbounded, unlike export/import's "handful of currently loaded files"), instead of one export record checked against a handful of loaded candidates. **Tier 1**: exact whole-file fingerprint match. **Tier 2**: the loaded file's own time span fully *contains* a stored (smaller) snapshot's span — the file has grown (typically via tailing) since that snapshot was saved — confirmed by re-slicing the loaded file down to that historical window (`windowSlice`, reusing `lowerBoundByTs`/`upperBoundByTs`) and checking both the entry count and the window's own fingerprint match the stored record exactly. Ties within tier 2 (a file grown past several old snapshots) resolve to the most recently saved one. **Tier 3 deliberately gets no preview at all**, not a lighter-weight one — an ambiguous/unverifiable match here would need the same manual-disambiguation machinery Session export/import's tier 3 dialog uses, which is disproportionate for a convenience feature; a miss just costs a missed convenience, never a wrong restore.

**Where the lookup happens**: `loadFileDescriptors` (the single funnel behind Open Files, drag-drop, and File System Access picker loads), right after the file finishes parsing and its `cacheKey` write fires — a freshly loaded file always starts with zero filter children at that point, so the lookup can only ever attach a *candidate* match, never something that competes with real filters already on screen. The result is stored as `node.filterHistoryMatch = { filters, tier }` on the file node itself. **Not run** for `mergeFiles` (excluded by design, see "Qualifying" above) or `restoreSessionFromCache` (that flow already brings its own filters back via the session cache — running this lookup there too would be redundant and could theoretically flash a ghost preview mid-restore for no benefit).

**UI**: a "ghost preview" (`renderFilterHistoryPreview`, called from `renderNode`) renders directly under a file's tree row, in the same visual slot real filter children would occupy, whenever `node.children.length === 0 && node.filterHistoryMatch` — condition-based, not event-based: no separate "was this offered/dismissed already" flag exists anywhere. One grayed, non-interactive row per node in the stored tree (`renderGhostRow` — icon, name, type tag, mirroring `renderNode`'s own visual language closely enough to read as "this is what your filters looked like", but with no click/drag/context-menu handlers at all), a short note line (entry count, "File has grown since —" prefix on a tier-2 match), and a **Restore filters** button that calls the existing `materializeCachedFilters(fileNode, match.filters)` and re-renders. **Disappears automatically** the instant the file gets *any* real filter child — whether via Restore or the person just creating their own filter without ever clicking it — because that's the entire visibility condition; this is exactly the "goes away once you've started your own filtering, restored or not" behavior requested when this was scoped.

**(Resolved) Emptying the tree back out now overwrites the old restore state instead of resurrecting it.** Previously `node.filterHistoryMatch` was never deleted, only hidden by the `children.length` condition above — so deleting every filter the person had just added made the tree empty again, the condition flipped back to "showable", and the ghost preview resurfaced showing the *original, pre-session* filters, not anything reflecting what the person had just done. Fixed this session (2026-08-14, person-reported via screenshot): `buildFileHistoryRecords()` (see "Storage" above) now tracks a per-file, session-only `node.filterHistoryTouched` flag, set the first time `children.length` goes from 0 to >0 (own filter or a Restore) — at that same moment `filterHistoryMatch` is cleared to `null`, so it can never resurface later purely because the tree emptied back out. If the tree is later emptied again (`children.length` back to 0) while `filterHistoryTouched` is set, the persist cycle now **deletes** that file's stored record instead of leaving it untouched — both directions (gaining a filter, losing the last one) overwrite whatever restore memory came before, and a file with no filters left is indistinguishable from one that never had any, including on the next reload. A freshly loaded file whose ghost preview hasn't been acted on yet (`filterHistoryTouched` still unset) is unaffected — nothing is decided about it until the person actually does something.

**Test coverage**: `tests/logtrail.regression.test.js` Group 30 (jsdom + `fake-indexeddb`) — 30a: tier-1 exact-match persistence and restore across two windows sharing one `IDBFactory` (same reload-simulation pattern Group 20 established), including the ghost preview's row count/content and the Restore button materializing the tree; 30b: tier-2 matching against a grown file, plus the negative case (a genuinely unrelated file's span doesn't overlap at all, so it's not even a near-miss); 30c: the exclusion rules (merged files, empty filter trees), the ghost preview's auto-hide once the file gets any real filter child, and (extended this session) the in-memory match actually clearing once the tree is populated; 30d: the same tier-1 round trip but through the REAL `loadFileDescriptors` entry point — an actual `File` read via `FileReader` (jsdom implements both natively, no stubbing needed), proving the `persistFileNode` → `matchFileHistory` hook wired inside `loadFileDescriptors` itself works end-to-end, not just the lower-level pieces 30a-c exercise directly; **30e (new, this session)**: the full reported bug scenario end-to-end — session 1 saves a tree, session 2 loads the same content, creates its own filter (old record correctly overwritten, already worked), deletes that filter again (ghost stays hidden, in-memory match stays cleared, stored record is removed — the actual bug), then a simulated session 3 reload of the same content finds no match at all.



- **Column sort** (`Time`/`Level`/`Thread`/`Location` headers, `.th-sortable`): clicking toggles ascending/descending (`state.sortColumn`, `state.sortDir`, arrow indicator via `updateSortIndicators()`). Applied in `renderTable()` to a **copy** of `getVisibleEntries()` (`entryComparator`) — never sorts the underlying node/file arrays in place. This matters: those arrays must stay chronological for the link filter's binary search (`lowerBoundByTs`) and the OR-filter's chronological merge to keep working; sorting only the display copy keeps the sort a pure presentation feature with zero risk to the rest of the pipeline. `Method`/`Message` aren't sortable columns (no obviously useful ordering for free text).
- **Status strip** (`#statusStrip`, `renderStatusStrip()`): a single always-visible line above the table — "N of M shown" (M = the active node's root file's total entry count via `getRootFileId`, N = `currentViewEntries.length` after node filter + level quick-filter) plus "filtered to X, Y" when level toggles are active. Only shown in the log view (hidden for the extraction table and link pair view, which have their own info lines).
- **Message hover popover — removed.** `#msgPopover` used to replace the native `title` tooltip on `.col-msg` cells with a delayed, selectable preview. It was removed for two reasons: (1) it duplicated what the detail panel (bottom of the log view, always shows the full selected message) already covers, so it added interaction surface without adding capability; (2) it caused a real, hard-to-spot bug — the popover for the *previously* hovered row lingers (by design, to avoid flicker while scanning) for up to 150ms after the pointer moves to an adjacent row, and since it's `position:fixed` with `pointer-events:auto` sitting right below/above the row it describes, it could swallow a click meant for the row now under the cursor. Caught via jsdom by checking the popover's `hidden`/`show` classes across a simulated row-to-row hover transition — see Testing approach below.
- The severity color bar (`.col-bar`, first column of `--row-grid`) was widened from 3px to 5px, since it remains the primary at-a-glance signal for scanning a long list.

## Session export / import (sharing an analysis with a colleague)

Right-click any node → **"Export session…"** / **"Import session…"** (next to Save/Load filter — same "share analysis state" mental bucket; chosen over the toolbar placement the original design draft suggested, so the toolbar stays reserved for view-level actions). Import is also offered on the tree's empty background (`treeEl`'s own `contextmenu` handler), since importing into a blank session — no files loaded yet — is a first-class flow when the export carries embedded log text. Format is `{ format: "logtrail-session-export", version, exportedAt, files: [...], settings }`, `SESSION_FILE_VERSION = 1`.

**What gets exported**: a user-picked subset of the currently loaded root files (`#sessionExportDialog`, one row per file with an include checkbox), each file's *complete* filter tree (reusing `serializeFilterTreeForCache`/`materializeCachedFilters` from the session cache — no branch/chain-pulling needed since the whole tree goes anyway), that file's bookmarks (first-wins scan across files, same convention as `buildCacheMeta`), and session-wide settings (level filter, sort, active node — recorded as `{exportId, ref}` since export ids are only stable within one export document). A per-file **"embed log text"** checkbox (deliberately per-file, not global — some logs in a session may be sensitive while others aren't) includes `rebuildFileText(node)` in that file's record, making the export self-contained for that file.

**The core problem this solves**: the person importing almost certainly has their *own* copy of the same log, not the exporter's literal file — same name, different name, or (for a tailed/live log) a newer snapshot that kept growing after the export was made. `matchExportedFile()` resolves each exported file against the importer's currently loaded files in three tiers:

1. **Tier 1 — full-content match**: the export carries a whole-file fingerprint (`fullHash`, via `fingerprintText`); any loaded file whose own full fingerprint (`getFileFullHash`, cached on `node._fullHash`) matches is a confident hit. Applied silently.
2. **Tier 2 — overlapping time window**: covers the motivating scenario (receiving copy of a tailed log kept growing past the exported snapshot). The exported file's timestamp span must be **fully contained** in the loaded file's span — a file that only partially overlaps (e.g. a rotated/truncated head) can't be verified this way and falls through to tier 3. Within the window: entry-count pre-filter first (cheap, and a strong signal — same density in the same window), then a fingerprint of the concatenated raw text of just that window, compared against the export's `fullHash`. An appended entry whose timestamp lands exactly on the window's end boundary inflates the count and correctly demotes the match to tier 3 rather than silently misapplying. Surfaced via a passive toast (`"X matched via overlapping time range"`) — applied automatically, but the person is told why, since it's a weaker guarantee than tier 1.
3. **Tier 3 — manual reassignment** (`#sessionMatchDialog`, one dialog per unresolved file, sequential): near-misses from tiers 1–2 (right file, wrong count/hash, or partial overlap) are shown first and badged "possible match"; other loaded files follow; then **"Load a file from disk…"** (opens the normal file picker, re-runs tiers 1–2 against the newly loaded file, loops back to the dialog if that still doesn't resolve it); **"Load the embedded log"** (only shown when the export has `text` for that file — materializes it via `addFile`, treated as tier-1-trustworthy since re-parsing the exporter's own rebuilt text is a fixed point); and **"Skip this file"**. Cancel on the dialog skips this file and every remaining unresolved one (already-applied files are kept). No backdrop-click dismissal on this dialog (unlike the export dialog) — a stray click mid-import shouldn't silently count as a decision.

**Bookmarks**: tier 1/2 targets are provably identical inside the exported window, so a bookmark's stored **ordinal** is trusted outright (`applySessionEntryByOrdinal`, same scheme as the session cache). A tier-3 manually-picked file has no such guarantee, so bookmarks there are re-anchored by **timestamp** (binary search via `lowerBoundByTs`) and confirmed against the hit ± 2 neighbours by **raw-line fingerprint** (`applySessionEntryByContent`) — enough slack to absorb small insertions/deletions elsewhere in the file without losing every bookmark to one nearby edit. A bookmark that can't be confirmed is dropped and shows up in the final summary toast as unplaced (`"N of M bookmarks placed"`), never silently misplaced onto the wrong line.

**Fingerprinting is deliberately not `crypto.subtle`/SHA-256**: it's a matching aid, not a security boundary (the worst-case cost of a collision is a wrongly-*suggested* match that the person can still reject in the tier-3 dialog), Web Crypto's async API is awkward for hashing several loaded files as a synchronous pre-filter, and its availability under a `file://` origin (this app's primary deployment mode) isn't worth depending on. `fingerprintText()` runs two 32-bit FNV-1a passes with different offset bases and concatenates them into 16 hex chars — cheap, synchronous, good enough for a matching aid. Do not swap in Web Crypto in a future session without revisiting this reasoning.

**Settings/active-node application is all-or-nothing per import, not per file**: if every exported file ends up skipped, session-wide settings (level filter, sort, active node) are left untouched rather than clobbering the current view for zero gained files.

**Test coverage**: `tests/logtrail.regression.test.js` Group 21 (jsdom) — export dialog with per-file include/embed checkboxes (`downloadJsonFallback` stubbed to capture the JSON, since jsdom has no `showSaveFilePicker`), tier-1 round-trip against a renamed byte-identical file (filters, `linkedId` remap, highlight colour, bookmarks with notes, settings, active node), tier-2 auto-match against a grown file (asserts `tier === 2` explicitly, to catch a future change that accidentally widens tier 1's matching instead of exercising the window path), tier-2 rejection on a density mismatch falling through to the manual dialog, tier-3 manual pick with one of two bookmarks deliberately unresolvable (proves the fallback doesn't silently over- or under-match), the version guard, and embedded-log materialization into an empty session.

## Extraction workflow: live match feedback & token chips

- **Live match count** (`#filterLiveMatch`, `evaluateLiveMatch()`): debounced (150ms) re-evaluation of whatever's currently typed in `#filterInput`, run against `getVisibleEntries()` — the same rows the new filter would actually apply to. For an extraction pattern (`isExtractPattern`), shows "Matches: N of M rows · K columns"; for plain text, "Matches: N of M rows"; an invalid pattern shows "Invalid pattern" in the `--level-error` color. Zero matches gets a `--warn`-colored nudge rather than an error, since "the pattern is fine but nothing matches yet" is a normal mid-typing state, not a failure.
- **Live pattern preview** (`#filterPatternPreview`, `updateFilterPatternPreview()`, same debounce as the live match count above): for an extraction pattern, shows the pattern evaluated against a real sample message with matched substrings highlighted in place — see "Extraction: live pattern preview + ignored columns" below for the full writeup, including how this doubles as the ignore-toggle UI while authoring.
- **Token chips** (`#filterTokenChips`, one button per placeholder type already listed in `#filterHint`): clicking inserts the literal token (`[value:float]`, `[value:int]`, `[value:time]`, `[value:word]`, `[value:hex]`, or `[*]`) at the current cursor position in `#filterInput` (`insertTokenAtCursor`), replacing any active text selection, same as normal typing would. `#filterHint` stays in place underneath as a plain-text fallback reference.
- **Extraction table column sort** (`.extract-sort-btn`, one small button inside each `<th>`): sorts `extractRowsData` itself — numeric-capable types (`float`/`int`/`hex`/`time`) numerically via the same `parseValueForPlot` the Plot tab uses, `word` lexically via `localeCompare`, unparseable values always last regardless of direction. The sort button is a separate nested control with its own `mousedown`/`click` handlers (`stopPropagation`) specifically so it doesn't trigger the header's existing mousedown-driven column cell-selection — the two interactions share the same `<th>` but are otherwise independent. **Because the sort reorders `extractRowsData` in place** (rather than keeping a separate display-order array), it also reorders the connected **Plot tab's line-chart point order** for that extraction, since line/bar plotting reads points in row order by design (see Plotting section above) — this was accepted as a reasonable trade-off over the bookkeeping risk of two parallel orderings that could drift out of sync. Sorting also clears any active cell selection in the table (`state.tableSelection = null`), since a positional "row,col" selection would otherwise silently point at different rows post-sort. Sort state resets whenever the active extraction node changes.

## Theming

Light theme lives entirely in a `:root[data-theme="light"]` CSS override block layered on the same variable names the dark theme (still the default) already uses — `--bg-app`, `--bg-panel`, `--bg-elevated(-2)`, `--border(-soft)`, `--text-primary/secondary/tertiary`, `--accent(-strong/-soft)`, plus a new `--warn` variable (used for the live-match "no matches yet" state). Level colors (`--level-error/warn/info/debug/trace`) are intentionally **not** re-themed — they read fine against both backgrounds, and re-deriving a whole second severity palette wasn't worth the added surface. `#btnTheme` (toolbar, next to "Open files…") toggles `data-theme` on `<html>` (`applyTheme()`), swaps its own icon between sun/moon, and persists the choice to `localStorage` under `logtrail-theme`; `initTheme()` on load falls back to `prefers-color-scheme` when nothing's stored yet.

## Visual language (for consistency in future work)

Dark theme by default, light theme available via `data-theme="light"` (see Theming above) — all surface/text/accent colors are CSS custom properties at `:root`, precisely so both themes stay in sync from one set of rules. Key ones: `--bg-app` / `--bg-panel` / `--bg-elevated(-2)` for surface layering, `--accent` (teal in dark mode, `#4fc7c3`) for selection/active states, `--level-error/warn/info/debug/trace` (+ `-soft` low-alpha variants, unthemed — same in both modes) for log-level coloring — applied to the row background now, not just the badge/accent-bar (an earlier iteration only tinted the badge; rows are fully tinted per level today, with hover states that intensify rather than replace the tint). `--font-mono` for anything log-data-shaped, `--font-ui` for chrome. Icons are small hand-drawn inline SVGs (`ICON_FILE`, `ICON_FILTER`, `ICON_CLOCK`, `ICON_TABLE`, `ICON_MERGE`, `ICON_COMBINE`, `ICON_LINK`, `ICON_CONTEXT`, `ICON_CLOSE`, `ICON_COPY`, `ICON_CUT`, `ICON_PASTE`, `ICON_SAVE`, `ICON_LOAD`, `ICON_SESSION_EXPORT`, `ICON_SESSION_IMPORT`, `ICON_HELP`, `ICON_PIN`) — follow that pattern (no icon font/library) if a new node type needs one. `COLUMN_PALETTE` (6 colors, teal/violet/amber/blue/pink/green) is reused for both extraction-column chips and plot series — keep that link when touching either. **Any new color needs a CSS variable, not a hardcoded hex** — that's what keeps the light theme override a single block instead of a parallel hunt through the stylesheet.

Selection styling convention established through iteration: **rings/outlines for "selected", not background fills** — a filled background for selection was found to be visually indistinguishable from the neutral hover fill, causing a "why are two rows highlighted" confusion. Log-row selection and extraction cell selection still use `box-shadow: inset ... var(--accent)` only, per that reasoning. **Multi-select in the tree is the one deliberate exception**: checked/multi-selected rows get both the ring *and* an `--accent-soft` background fill, because that state now has an explicit, always-visible checkbox as its primary affordance (see Tree interactions) — the fill reinforces "this row is part of a bulk action set" rather than competing with a hover state for meaning. If adding a new kind of selection indicator, default to ring-only unless it has the same kind of unambiguous explicit-control backing that multi-select has.

## Testing approach used during development

No test framework is shipped with the file (it's a deployed artifact, not a repo with CI). Verification during development used **jsdom** (`npm install jsdom` in a scratch dir), loading the real `logtrail.html` with `runScripts: "dangerously"` and driving it through the actual DOM — simulating file drops via a synthetic `drop` event with a `File`, clicking real buttons/rows, and reading back rendered DOM state — rather than re-implementing logic in isolation, which repeatedly caught real integration bugs (stray event-listener bubbling closing a just-opened popup, a closure-over-a-shared-loop-variable bug in hover handlers, stale-DOM assumptions in multi-step interactions). **If asked to verify a change**, prefer this approach — spin up jsdom, load the file, and drive it like a user — over just reading the code and reasoning about it, since several real bugs here were only caught this way. Needs `clientHeight`/`getBoundingClientRect` stubbed (jsdom has no real layout engine) and `navigator.clipboard` stubbed for copy-related tests. jsdom also ships **no IndexedDB** — the session-cache group injects a `fake-indexeddb` `IDBFactory` via `beforeParse` (now a devDependency in the suite's `package.json`); passing the *same* factory instance into two successive jsdom windows simulates a browser reload against the same "disk". All other groups run without it, which doubles as a test of the cache's graceful-degradation path (`openCacheDb` resolves `null`, feature silently off).

**The most consequential bug caught this way**: double-click-to-jump-to-full-log silently stopped working entirely, on every row, every time. Root cause — `selectEntry()`'s plain-click path called `renderVisibleRows()`, which does `tableRows.innerHTML = ""` and rebuilds every row as a *new* DOM node on every single click, including the first click of a double-click. Browsers only count a second click toward a `dblclick` if it lands on the *same element* as the first; since that element no longer existed by the time the second click landed, `dblclick` never fired — not intermittently, but always. Confirmed via jsdom by asserting `row === document.querySelector('[data-entry-id="..."]')` was still true *after* dispatching a plain `"click"` event on it. Fixed by having a plain click only toggle the `.selected` class on the existing rendered elements (`updateSelectedRowClass`) instead of tearing the row list down; the arrow-key path still goes through `renderVisibleRows()` via `scrollToIndex()` since it may need to bring an off-screen row into view. **Lesson for future work on this file**: recreating a DOM element in response to the first half of any multi-step native browser gesture (double-click, drag, anything relying on element identity across events) will silently defeat that gesture — verify element identity survives a single interaction before assuming a click/drag handler is "just cosmetic."

**jsdom gotcha worth knowing before writing more tests**: top-level `function` declarations in the inline `<script>` become `window` properties (so `window.render()`, `window.createFilterNode(...)` etc. work directly from a Node test), but top-level `let`/`const` — `state`, `extractRowsData`, `plotConfig`, `undoStack`/`redoStack`, and most other module state — do **not**; they only live in the shared global lexical scope, per spec, same as in a real browser. Reading (or resetting) them from outside requires injecting a second `<script>` element into the same jsdom document (`document.body.appendChild(...)`) whose body exposes getters (`window.__t = { get state() { return state; }, ... }`) or small helper functions (`window.__resetUndoRedo = () => { undoStack = []; redoStack = []; }`) — since that injected script runs in the same realm's global lexical scope, it can see the bindings directly. `window.state.foo = x` (mutating a property of the object the getter returns) works fine without a setter; `window.state = x` (replacing the binding itself) does not and fails silently.

One thing jsdom **can't** catch: real hit-testing / paint order (`elementFromPoint`, whether a `position:fixed` overlay visually covers something and intercepts its clicks) — jsdom has no layout or rendering engine, so this class of bug (e.g. the message-popover issue above, or the file-drop overlay swallowing tree drag events) has to be reasoned about directly from CSS (`position`, `z-index`, `pointer-events`) and event bubbling/timing, then verified by state-based proxies (checking `hidden`/`show` classes at the right moments) rather than by literally observing an element being obscured.

## Known limitations / intentionally deferred

- Value assertions **and `node.ignoredColumns`** are keyed by column **index**, not name — editing an extraction pattern so columns shift position (e.g. removing an earlier placeholder) leaves any assertion, or any ignored-column marker, on a later column silently pointing at the wrong data. No migration/warning exists yet; re-set the assertion / re-check ignored columns after a pattern edit that reorders columns. For ignored columns specifically, this also means the filter popup's `filterPopupIgnored` working set (pre-populated from the node's `ignoredColumns` when Edit is opened) can go stale if the pattern text is then heavily retyped in the same edit session — same sharp edge, one level earlier.
- (Resolved) Bookmarks used to be session-only; the session cache now persists them (with files, filters, and settings) across reloads. Remaining session-cache limitations: **tail handles are not persisted** — `FileSystemFileHandle` is technically storable in IndexedDB on Chromium, but re-attaching needs a permission re-prompt on a user gesture, so a restored file is a static snapshot and tailing must be re-established by re-opening the file (deferred, not built). **A restored merged file no longer shares entry objects with its source files** — it's rebuilt from its own cached text, so the identity-sharing described in `mergeFiles` doesn't survive a reload; each file still works standalone, it just costs the duplicate memory and a bookmark on a shared entry resolves to only one of the files. **Undo/redo stacks and the clipboard are not persisted** (consistent with their deliberately narrow scope). Disabling the cache has no UI — `localStorage["logtrail-cache-enabled"] = "0"` is the escape hatch.
- Session export/import (see "Session export / import" above): tier-2 matching only covers a loaded file whose time span **fully contains** the exported span — a receiving file that's a rotated/truncated *partial* overlap of the export can't be auto-verified and always falls to the manual tier-3 dialog, even though a human could often tell at a glance that it's the right file. Import has no dedup against an already-present equivalent branch, same known gap as filter save/load — re-importing the same session twice produces visible duplicate filter trees. Fingerprinting/hashing a file is O(file size) and runs synchronously on the main thread; not chunked/yielded like the initial parse, so a very large file could cause a brief UI stall during export or tier-1/2 matching on import. A merged file's re-matching is best-effort only: it round-trips fine when it happens to reproduce the same combined content and entry count, but there's no dedicated identity-matching path for "this merged file's *sources* changed" the way there is for a plain file.
- Undo/redo covers only filter delete and move (see "Undo / redo") — not file deletion, value/pattern edits, inversion toggles, or value-assertion changes. Deleting a *file* (not a filter) is not undoable.
- Filter inversion (NOT) is unsupported by design for `link` (pair-entry ids don't correspond to `parentEntries` ids — see "Inversion (NOT)"), `extract` (an inverted match set has nothing left to extract), and `context` (every window contains its own reference entry, so an inverted result would always be empty).
- The `context` filter's bracket rendering resolves group start/end caps against the full result array (not just the virtualized render window), so caps are always correct — but if a group's start scrolls more than the row buffer (`BUFFER_ROWS`) above the viewport, only what's actually rendered gets a bracket; the line simply doesn't extend into rows that were never created as DOM nodes. Cosmetic only, no functional impact.
- 3D scatter plot (explicitly lower priority, not built).
- Cross-file filter combination (AND/OR/Link across two different root files) is unsupported by design — merge first.
- Filter save/load never checks whether the destination tree already has an equivalent branch — every "Load filter…" creates a fresh independent copy, so re-loading the same file (or loading onto a tree with a matching chain) produces visible duplicates. See "Filter save / load" section above.
- Extraction table and link pair view are not virtualized — fine for realistically-sized extraction/link results, would need work if someone tries to extract from an entire multi-hundred-thousand-line file with a very loose pattern.
- (Resolved) The timeline minimap used to rebuild its whole-file background buckets (an O(root file size) pass) on every `renderTable()` call. The background pass is now memoized (`minimapBgCache`, keyed on root id + entry count + time span + bucket count — so it self-invalidates on tail append, rotation, and resize); only the overlay pass (O(current view)) still runs per render. This was the biggest fixed cost when switching between filters on large files.
- Sorting the extraction table (per-column sort buttons) reorders `extractRowsData` directly rather than keeping a separate display order, so it also reorders the connected Plot tab's line/bar point sequence for that extraction — accepted trade-off, see "Extraction workflow" above.
- Level colors are not re-themed for light mode (same hex values in both themes) — they were checked to read fine on both backgrounds, but a future accessibility pass may want theme-specific values.
- Tailing requires the File System Access API (Chromium) — Firefox and the legacy `<input>` fallback load files as one-time snapshots without live updates. Byte-offset slicing assumes the writer flushes whole UTF-8 characters (log writers do). On rotation/truncation the file node's entries are replaced and the old ids are released from `entryIndex` via `releaseEntriesFromIndex()` (no per-rotation index leak anymore); a merged file that reused the old entry objects still keeps the stale ones — and, because it references them, also keeps them alive in the index, which is intentional. Each tail change now invalidates only the caches that actually depend on the changed file(s) (`invalidateCachesForRoots`, see Memoization) instead of every cache globally — filters under untouched files stay cached across polls. Within the changed file itself, filters still recompute from scratch each tick; an incremental filter-append remains the next optimization if a single very large tailed file with deep filter chains ever feels sluggish.
- The Highlight view has no tail auto-follow of its own — while the Filter view scrolls with new tailed entries (`state.tailFollow`), the Highlight view just keeps whatever scroll position it had. Deliberate v1 scope: it's meant as a stable reference view while browsing, and follow-to-bottom would fight that. Revisit if this turns out to matter for live-tailing workflows.
- The hue wheel in the highlight-colour picker only picks hue — saturation/lightness are fixed (68%/55%) rather than a full 2D color picker. Chosen for a simpler, more predictable widget; the preset row covers cases where a specific exact color matters.
- (Resolved) In stacked Filter/Highlight layout, the Filter/Highlight tab buttons used to stay visible but functionally inert. The tri-state Full/Filtered/Stacked toggle now switches straight out of Stacked into tabs mode on the clicked panel instead of doing nothing — see "Highlight view (Filter/Highlight split)".
- A row that's both highlight-matched and part of an active time-context filter's bracket shows both markers in the same left-gutter slot (`.hl-markers`/`.ctx-bracket` both sit at `left:-9px`), overlapping rather than each getting its own lane. Accepted trade-off, not expected to come up often — revisit if it does.
- Highlight-rule matching walks every colored node in the tree on every Highlight-view render (memoized per-node via `getEntries`'s own cache, so cheap in practice) — would be the first thing to optimize if someone sets colors on a very large number of nodes at once.

- **Bugfix: Electron window control buttons (fullscreen/minimize/close) had the wrong background color** (this session, 2026-08-23, `FEATURE_BACKLOG.md` item, person-reported — "ideally Electron would keep the button backgrounds transparent and the buttons themselves would pick up the active theme's highlight color"). Root cause: `OVERLAY_COLORS` in `desktop/main.js` hardcoded exactly two `{color, symbolColor}` pairs, picked by whether `data-theme` was `"light"` or anything else — which only ever matched the original Dark/Light built-ins. Every Catppuccin flavor (each with its own `--bg-panel`, none of them `#151924`/`#ffffff`) and any custom imported theme got an overlay background that didn't match the toolbar underneath it; the per-theme accent re-pick (`applyAccentChoice`, changes `--accent` without changing `data-theme` at all) wasn't tracked either, since the poll only ever compared theme id, not the actual color. Fixed exactly as the backlog suggested: `watchTheme()` now sets the overlay's `color` to a fully-transparent `#00000000` unconditionally (Electron's documented `#RRGGBBAA` mechanism for a transparent Window Controls Overlay, landed well before the `^43.0.0` this project pins — see electron/electron#33567/#38693) instead of trying to hardcode a matching background per theme at all, and reads the renderer's own live `getComputedStyle(...).getPropertyValue("--accent")` for `symbolColor` (polled the same ~1x/second way `data-theme` was) instead of a fixed light/dark text-secondary guess — so the buttons themselves pick up the active theme's actual highlight color, exactly as requested, and the background always matches whatever `#toolbar` paints underneath it for ANY theme, built-in or custom, with no per-theme color table to keep in sync. `createWindow`'s initial (pre-`dom-ready`) overlay uses the same transparent background with the default (dark) theme's `--accent` as a placeholder `symbolColor` until the first poll resolves, same pattern the old code already used for its initial paint. Scoped entirely to `desktop/main.js` (no `philogg.html` changes) — no new regression-suite coverage (the jsdom suite loads `philogg.html` only, not Electron's main process, same as every other `desktop/main.js`-only fix in this changelog); full suite re-run clean as a sanity check, 1881 passed, 0 failed. Not independently re-verified live (no display server in this environment, same standing limitation noted throughout "Desktop wrapper" below) — reasoning checked against Electron's own WCO transparent-overlay docs/issue history, not guessed; a known, still-open upstream Electron limitation (electron/electron#48193) means the native hover-highlight color behind the symbol may not itself follow the accent color even once this ships — outside this fix's control.

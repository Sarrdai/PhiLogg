- **Bugfix: "Add to tree" button shifted the filter chain in Manual level-filter-tree mode** (this session, 2026-08-25, `FEATURE_BACKLOG.md` #37, person-reported with before/after screenshots). Root cause: `#viewBar`'s top-left row (`#fhTabs`, `#btnPinBookmarks`, `#btnMultilineMsg`, `#btnColumns`, `#btnTextMatchHighlight`, `#levelBar`) is a chain of `float:left` elements with a shared `margin:0 14px 6px 0`, deliberately so `#breadcrumb` (a plain block, not flex) wraps around however many of them end up on the line — see "Unified view bar" CSS comment. `#btnApplyLevelToTree` ("Add to tree", Settings → Behavior's `#settingsLevelFilterTreeMode` = "explicit"/Manual only) sits right after `#levelBar` in the markup but never got that `float:left`/margin rule; toggled via `display:none`/`""` rather than added/removed from the DOM, so once Manual mode revealed it, it landed as an unfloated normal-flow block sibling of `#levelBar`'s float and dropped below it — shoving `#breadcrumb`'s own wrap-start down with it, exactly the reported layout shift. Fixed by giving `#btnApplyLevelToTree` the same `float:left; margin:0 14px 6px 0;` as its siblings, so it just extends the SAME dynamic top-left line regardless of how many buttons end up there — scales to future additions to that row without further layout work, per the person's request. `tests/philogg.regression.test.js` Group 102 (new): asserts the button's computed `float`/margin match its siblings once explicit mode reveals it; Group 94 also gained one inline float assertion at the point it already exercises that visibility toggle. 1918 passed, 0 failed.

- **Bookmarks rework: auto-managed per-file "Bookmarks" filter node + general-purpose Notes** (this session, 2026-08-25, `FEATURE_BACKLOG.md` #50, implemented as one pass). Removed the old Bookmark Manager panel entirely (`#btnBookmarks`/`#bookmarksPanel`/`#bookmarksList`/`renderBookmarksPanel`/`openBookmarksPanel`/`closeBookmarksPanel`/`updateBookmarksButton`, plus the associated CSS) — bookmarks are now represented as a single, auto-managed `filterType: "bookmarks"` filter node, created directly under a file's root the moment its first bookmark is set and removed once its last is cleared (`syncBookmarksFilterNode`, called from `toggleBookmark` and every bookmark-restore path). The node is `locked: true`: colourable/styleable like any other filter node (its own highlight swatch works normally), but `deleteFilterNodeWithUndo`/`moveFilterNodeWithUndo`/`renderNode`'s drag wiring all refuse to touch it, and the tree context menu offers only "Copy" for it — only `syncBookmarksFilterNode` itself ever adds/removes it. It has no dedicated icon (falls through to the same generic fallback legacy time-filter nodes use) and is deliberately excluded from every filter-tree persistence carrier (`serializeFilterTreeForCache`/`serializeFilterBranch`/`importFilterJson`/`materializeCachedFilters`) since its membership is entirely derived from `state.bookmarks`, which is persisted separately and re-synced into a node on restore. The PIN-bookmark feature (`getPinnedBookmarkEntries`/`state.pinBookmarksInFilteredView`) is completely unaffected — still reads `state.bookmarks` directly. Alongside this: a new general-purpose **Notes** feature — `state.notes` (`Map<entryId, text>`, same id scheme/persistence tier as `state.bookmarks` but a fully separate flat store, not filter-tree data) attaches free-text notes to *any* real log entry, bookmarked or not, via `Alt+N` (add if none, edit if one exists — no separate `F2` binding), the row context menu's new "Add note"/"Edit note" item, or double-clicking an existing rendered note. A note renders as its own sub-row (`.note-row`, not part of `.row-grid` — no level marker, `--accent-strong` colour, indented) directly below its entry in both the Filtered and Full/Highlight views, gated on a new Show/Hide Notes toggle (`#btnNotes`, `state.showNotes`, default off — same "off by default" reasoning as `state.multilineMessages`), and shown in full in a new `#detailNote` block in the Entry Detail panel regardless of that toggle, so a multi-line note stays readable even with note-rows hidden. Row-height/virtualization math (`rowHeightForEntry`/`buildRowOffsets`/a new `needsRowOffsets()` helper replacing direct `state.multilineMessages` checks at every offsets-array gate) was extended to fold a note-row's own height in alongside the entry's own, keeping `.log-row`'s and `.note-row`'s real DOM heights in exact sync with what the virtualization math expects. `state.notes` persists through both the session cache (`buildCacheMeta`/`restoreSessionFromCache`) and session export/import (`buildSessionExport`/`applySessionEntryByOrdinal`/`applySessionEntryByContent`), each gaining a `notes` array mirrored ordinal/ts/raw-fingerprint-anchored alongside the pre-existing `bookmarks` array (the old bookmark-specific `note` field is gone — it was a Bookmark-Manager-only per-bookmark note, now fully superseded by this general one). See "Bookmarks"/"Notes" above for the full mechanism. `tests/philogg.regression.test.js`: Group 15 rewritten (old panel assertions replaced with node-creation/removal/locked/matching coverage), Group 104 (new, Notes), Group 20/21 (session cache/export persistence) and Group 29b (toolbar button shape) updated for the new `#btnNotes` button and the auto node's extra tree child. 1968 passed, 0 failed.

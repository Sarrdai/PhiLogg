- **Bugfix: arrow-key nav after switching filters (via Alt+Arrow or a tree click) onto a Link filter used a stale entry list** (this session, 2026-08-25, person-reported: *"Wenn ich über Alt+Pfeiltasten durch die Filter navigiere und danach... über Pfeiltasten durch die Einträge des neu ausgewählten Filters navigieren möchte, scheint es, als würde ich noch durch den vorherigen Filter/View navigieren... Ich sehe die Einträge unten im Entry Detail, während in meiner Log Liste keine Einträge selektiert werden."*). Root cause: `currentViewEntries` (the list plain `ArrowUp`/`ArrowDown` navigate via `moveSelection`) is only repopulated by `renderTable()` — but `renderMainView()` calls `renderLinkView()` instead of `renderTable()` while the active node is a Link filter, so switching onto one left `currentViewEntries` holding whatever filter's list was active before the switch. Pressing a plain arrow key then picked an entry from that stale list, updated the detail panel (which resolves any id via the global `entryIndex`, so it "worked"), but no row in the (unrelated) Link view's DOM ever matched that id — nothing visibly highlighted, exactly the reported symptom. Alt+Arrow tree navigation (`FEATURE_BACKLOG.md` #18) made this easy to trigger since it deliberately switches the active filter without touching `state.focusRegion`/`entriesView`, but a plain tree-row click onto a Link filter has the same underlying bug. Fixed with the same guard `extractWrap` already had: the plain arrow-key handler now no-ops while `linkWrap` is the visible Filtered-pane content, instead of running `moveSelection` against stale data — the Link view has its own click-driven pair selection (`linkSelectedPairIndex`), no Up/Down navigation of its own to route into instead. See "Tree interactions" above. `tests/philogg.regression.test.js` Group 108 (new). 2021 passed, 0 failed.

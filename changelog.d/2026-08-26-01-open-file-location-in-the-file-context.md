- **"Open File Location" in the file context menu** (this session, 2026-08-26, `FEATURE_BACKLOG.md` #52, generalized beyond its Electron-only backlog wording per person request: *"soll aber nicht nur für den Elektron Wrapper [gelten], sondern generell... überall dort... wo man den Pfad direkt öffnen kann"*). A file node's tree context menu now offers "Open File Location" whenever a real OS path is known AND `window.philogg` exists (new, deliberately narrow `desktop/preload.js` `contextBridge`, exposing `getPathForFile`/`revealPath`/`revealLocalUrl` — the only preload/IPC bridge this app has; see "Desktop wrapper" → "Open File Location" for the full design) — never in the plain browser build, since no web API can resolve a `File` back to a filesystem path at all, so it correctly never offers a fake affordance there rather than trying and failing. Covers files opened via the in-app picker, drag-drop, and folder watch (path resolved via `webUtils.getPathForFile` at load time) as well as ones opened via launch-arg/file-association (resolved through the existing `philogg://local/…` id → path map in `main.js`, since those never go through a `File` object at all). A plain `http(s)` `?url=`-loaded file gets "Copy URL" instead (works in every build) — proposed and agreed as the sensible analogue for a remotely-loaded log, which has no OS folder to reveal. `node.localPath`/`node.sourceUrl` round-trip through the session cache. `tests/philogg.regression.test.js` Group 109 (new, 6 assertions groups): menu-item gating for all three outcomes plus the no-`window.philogg` case, and the cache persist/restore round-trip. Not verified live (no display server in this environment, same standing limitation as the rest of `desktop/`) — `getPathForFile`/`revealPath`/`revealLocalUrl` are simulated via a stub `window.philogg` in the test, real `webUtils`/`shell.showItemInFolder` behavior itself isn't jsdom-testable. 2034 passed, 0 failed.

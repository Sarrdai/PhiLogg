- **Timeline minimap: the two range-indicator boxes and click-to-jump now all know which fh pane (Filtered/Full) is actually on screen** (this session, 2026-08-27, FEATURE_BACKLOG.md #8 + two same-day person-feedback follow-ups). Previously all three mechanisms — the "covered timespan" box, the "currently rendered" box, and click-to-jump — always resolved against the Filtered view (`currentViewEntries`/`tableBody`), even while the Full tab was the one actually visible, so interacting with the minimap silently acted on an invisible pane.
  1. **Settings → Behavior → "Hide minimap's covered-timespan box in Full view"** (new toggle, default **off** — an opt-out of existing behavior, not a bugfix): when on, `#minimapFullRangeRect` (`updateMinimapFullRange`) hides itself whenever the Full tab is the one showing (`fhLayout === "tabs" && fhActiveTab === "highlight"`); left alone in Stacked layout, where the Filtered pane sits alongside it and the box stays meaningful. Persisted via `hideMinimapFullRangeInFullView`/`philogg-hide-minimap-full-range-in-full-view` in `localStorage`, same plain-flag mechanism as the existing hover-expand settings. `showFhTab`/`applyFhView` now call `updateMinimapFullRange()` on every tab/layout switch so the effect is immediate, without waiting on an unrelated scroll or render.
  2. **Same-day clarification (person feedback): the OTHER box, `#minimapRenderedRangeRect` (`updateMinimapRenderedRange`), must NOT hide in the Full view — it must instead reflect the Full view's OWN scroll position**, not the (then-invisible) Filtered view's. The function now branches on the same `fhLayout`/`fhActiveTab` check: Full tab active → `highlightBody.scrollTop`/`clientHeight` over `currentHighlightViewEntries`, not gated by `minimapInteractive` (a Filtered-view-only concept — no column sort exists in the Full view); otherwise → the existing `tableBody`/`currentViewEntries` path, unchanged. Both branches share a new `minimapRenderedSpan(entries, scrollEl, rowOffsets)` helper for the index/pixel math. `renderHighlightView()` now calls `updateMinimapRenderedRange()` on every one of its return paths, `#highlightBody`'s scroll listener calls it rAF-batched (twin of `#tableBody`'s own listener), and `showFhTab`/`applyFhView` call it alongside Box #1 on every tab switch. **Edge case**: `renderHighlightView()` runs even while the Link view is on screen (to keep the Full view's data current in the background — see `renderMainView`), which used to be exactly what kept this box hidden there by simply never being called; now that it *is* called, an explicit guard was added at the very top of `updateMinimapRenderedRange()` (`if (linkWrap.style.display !== "none") { ...hidden... }`) so the Link view — which has no row virtualization at all — still never shows a "rendered subset" box, regardless of which fh tab was last active. The window-resize and sidebar-resize drag handlers' own `updateMinimapRenderedRange()` calls lost their old `tableWrap.style.display !== "none"` gate for the same reason — that gate would have wrongly skipped Box #2 whenever the Full tab was on screen.
  3. **Second same-day clarification (further person feedback): the minimap's click-to-jump must jump the pane that's actually visible, not always the Filtered view.** `#timelineMinimapSvg`'s `click` listener now uses the identical `fhLayout`/`fhActiveTab` branch: Full tab active → resolves the nearest entry in `currentHighlightViewEntries` and calls `selectHighlightEntry(id, { scroll: true, center: true, index })` (not gated on `minimapInteractive`, same reasoning as (2)); otherwise → the existing `currentViewEntries`/`selectEntry` path, still gated on `minimapInteractive`. Drag-select (creates a `"timerange"` filter) and the right-click time-range dialog are unaffected — both always operate on the Filtered view/tree regardless of which tab is showing, since neither has a Full-view equivalent.

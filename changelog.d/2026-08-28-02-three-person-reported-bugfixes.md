- **Three person-reported bugfixes** (this session, 2026-08-28).
  1. **Plot "Filter: time range"/"Filter: these entries" used only the X viewport, ignoring Y.** `getPlotViewportEntries()` (`philogg.html`) destructured only `xDomainMin`/`xDomainMax` off `plotLastRender`, so a row panned/zoomed OUT of view on the Y axis alone — in range on X, clipped away on Y — was still counted as "currently plotted" and included in the created filter, along with rows whose Y value for the plotted column(s) wasn't even finite (the NaN-drop `renderPlotChart`'s own `series` construction applies, which `getPlotViewportEntries` didn't reuse). Now also checks `yDomainMin`/`yDomainMax` against every selected Y column, keeping a row only if at least one plotted Y value is finite and in range. See "Plot tab" in `docs/extraction-and-plotting.md`.
  2. **Minimap drag-to-select silently stopped working.** The drag's start position was anchored as a raw `minimapWidth`-unit x value at mousedown (`minimapDragStartX`). A re-render mid-gesture — a tail tick, a level-bar toggle, a window resize, anything that calls `renderTimelineMinimap()` — can change `minimapTMin`/`minimapTMax` (and, less often, `minimapWidth`) out from under an in-progress drag; re-evaluating that same stored x against the new time range at mouseup no longer pointed at the entry actually dragged from, in the worst case flipping the from/to order and silently failing the `toTs > fromTs` guard so no filter was created at all — same class of bug CLAUDE.md's own "hot loop rebuild" gotcha already documents for the tree/rows. The anchor is now captured as a real timestamp (`minimapDragStartTs`) at mousedown instead; every pixel position the gesture needs (overlay, drag threshold, final range) is re-derived from it via `minimapTsToX`/`minimapXToTs` against whatever is currently live, so a mid-drag re-render can no longer desync it. See Group 31 in the regression suite (extended with a tail-tick-mid-drag case).
  3. **A new "Add to selection" filter was named by its initial entry count, which went stale.** `createSelectionFilterNode` named a new selection via `idSetFilterName(ids, "selection")` (e.g. `"3 entries (selection)"`) — a one-time snapshot of `ids.length` at creation time; `addRowsToSelectionFilter` deliberately never rewrites `node.name` afterward (a person may have renamed it), so growing a selection from 3 to 30 entries kept the stale "3 entries" label forever. New selections are now named as a plain ordinal via `nextSelectionFilterName()` — "Selection 1", "Selection 2", ... (counted across every `selectionFilter` node in the tree) — immune to how many rows get added later. Plot-view-created `idset` filters (no `selectionFilter` flag) are unaffected and keep `idSetFilterName`'s count-based name. See Group 124 in the regression suite.

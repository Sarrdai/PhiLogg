- **Bugfix: the load-tick tailing visualization was measurably slowing down loading itself** (this session, 2026-08-28, person-reported — *"Die Visualisierung des Ladevorgangs... scheint das Laden deutlich zu verlangsamen. Wenn ich eine andere als die gerade ladende Datei auswähle, läuft der Ladevorgang viel schneller."*). Root cause: `scheduleLoadRender`'s existing rAF-coalescing (at most one `renderLoadTickMainView()` per animation frame while the loading file is the active view — see "File loading" in `docs/persistence-and-sync.md`) wasn't enough, because `renderTable()`'s own per-frame work is itself O(entries-so-far) — it rebuilds the timeline minimap's bucket counts and rescans every entry for the widest message line on every call — and entries-so-far grows on every tick, so running that full pass every ~16ms turned an otherwise-fast load into O(n²) total work. This is exactly why switching to a different, already-loaded file mid-load felt faster: that path (`loadRenderRootIsActive`) skips the expensive full render entirely. Fixed with a real-time minimum gap between actual full renders, `LOAD_RENDER_MIN_INTERVAL_MS` (150ms), checked inside the rAF callback itself — a tick landing before the gap has elapsed skips the full render for that frame (the tree row's own live progress/count still updates every tick, unthrottled) and the next tick tries again; the true start/end of a load (`flushLoadRender`) is untouched and always renders immediately. See "Fix 4" under "File loading" in `docs/persistence-and-sync.md`. `tests/philogg.regression.test.js`: new **Group 127** — `performance.now` and `requestAnimationFrame` both mocked to prove ticks landing inside the throttle window are skipped, a tick past the window runs a full render again, and the file still finishes loading correctly despite the throttle. 2467 passed, 0 failed.

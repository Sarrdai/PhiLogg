Confirmed: the level bar's per-tick live counts (`updateLevelBarCounts`) were exactly the remaining cost — switching to a different, already-loaded file mid-load skipped them, staying on the loading one didn't. `updateLevelBarCounts` had no other caller left and was deleted outright as dead code (not just unhooked from the tick path); the filter-subtree walk the row-update function used to do (giving a filter created mid-load its own live-growing row count) was dropped too — `updateLoadRowLiveData` is renamed `updateLoadRowProgress` and now touches only the loading file's OWN row. `scheduleLoadRender`'s remaining per-tick work (the row update + a cache-invalidation call so a mid-load click doesn't see a stale count) is now also time-throttled to at most once per `LOAD_TICK_MIN_INTERVAL_MS` (200ms) of real time, rather than running on literally every chunk/byte tick. Net effect: during a load, only the loading file's own tree row (progress fill + entry count) updates at all, and at a reduced rate — the level bar, any filter created under the loading file, and the Filtered/Full/minimap view all stay frozen at their last real-render value until the load finishes or an unrelated action triggers a real render.

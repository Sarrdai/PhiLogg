- **"Detach copy" — collapses a filter node's whole dependency chain into one self-contained row** (this session, 2026-08-28, person-requested "squash": *"ich möchte einen Filter... in einen neuen Filter packen, der diese ganze Logik enthält... Hab nur noch einen Eintrag, der mir genau das liefert."*). Grew out of a design discussion about `and`/`or`/`link` nodes' live, ID-based references (`linkedId`) — cloning one via Ctrl+C/Paste (`cloneSubtree`) deliberately keeps `linkedId` pointing at the ORIGINAL target even across files, which is correct for an in-tree copy but surprising when the copy is meant to stand alone. New tree context-menu action, "Detach copy (break references)" (`detachFilterChain`), clones a node's whole *needed* chain — its own ancestors plus any `linkedId` targets' ancestors, the exact same set `serializeFilterBranch` already computes for Save/Load — into a brand-new, self-contained set of nodes, then hides every node but the originally-clicked one (`node.hiddenInTree`) so the whole private chain reads as exactly one tree row; `renderNode`/`flattenTreeIds` treat a `hiddenInTree` node as transparent (no row, but its children still render/navigate at the same depth), and the breadcrumb/filter-popup target chain filter it out too so nothing gives away the hidden structure. Reused `materializeSerializedRoots`, newly factored out of `importFilterJson`, rather than duplicating its rebuild logic — Save/Load, the reusable library, and this same-file action all now share one "rebuild a serialized branch with fresh ids, wire up linkedRef" implementation. All cloned nodes (the visible one included) share one fresh `squashGroup` id: `deleteFilterNodeWithUndo` deletes the whole private chain together when the visible node is deleted (new `"deleteGroup"` undo/redo kind, restoring every member with its original id/flags on undo) instead of leaving hidden orphans behind, and `moveFilterNodeWithUndo` refuses to reparent the visible node (its own `parentId` is required by its hidden ancestor chain — dragging or Cut+Paste would otherwise silently decouple it). `squashGroup`/`hiddenInTree` are threaded through `snapshotSubtree`/`restoreSubtree` and the session cache (`serializeFilterTreeForCache`/`materializeCachedFilters`, carried verbatim — no remapping needed since a group never spans files); deliberately **not** through `cloneSubtree` (a Copy of the visible row becomes a plain, unflagged node — same "copied away from its real parent" limitation a link-derived extraction already has) nor through `serializeFilterBranch`/`importFilterJson` (exporting a squashed node re-expands it to fully visible nodes on import — an accepted simplification, not corruption).

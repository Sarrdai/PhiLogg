- **Squash box redesign (final iteration, same session, person-refined after trying the header-row version live) + a person-reported Save/Extract matching bugfix.**
  1. **The squash box's header is now the real display row, rendered a second time — not a read-only mirror.** After trying the previous "read-only header row above the box" shape, the person asked for the header to be *identical to* the target row inside, "so both are selected when you pick either." `renderSquashGroupBox` now always renders the display node's own row first (fully interactive, unchanged), and — only once `squashExpanded` — appends a divider plus the private chain, which naturally re-renders that same display row a second time at the bottom of its own chain. Both instances share one node id, so selecting the node marks BOTH rendered rows `.active` together (the intentional "double selection... wie wir das vorher schon mal hatten"). The `.tree-squash-box` background is now **always present, even while collapsed** (previously it only appeared once expanded), so a detached filter visually reads as "logic inside" from the start; expanding just reveals the chain below the header inside the same box. The old `buildSquashGroupHeaderRow`/`.tree-squash-header` (non-selectable mirror row) is gone.
  2. **Bugfix: `filterType: "text"` (Save) with a wildcard/extract-token pattern matched nothing on a link-derived pair entry, while `filterType: "extract"` with the identical pattern worked fine** (person-reported, found while toggling Save↔Extract on a detached extraction+link chain). Root cause: a link pair's `raw` field is a non-contiguous concatenation of both source lines' full raw text (metadata in between), unlike its clean `message` join — `getEntries()`'s `"extract"` branch already matched against `message`, but `textFilterMatches()`'s wildcard-as-text branch defaulted to `raw`. Fixed to match `message` there too.

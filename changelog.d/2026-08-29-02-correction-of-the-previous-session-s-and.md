- **Correction of the previous session's AND/OR/LINK redesign: `bakedA`/`bakedB` baked conditions, replacing the still-live `inputA`/`inputB` lookup** (this session, 2026-08-29). The session below shipped `node.inputA`/`node.inputB` as a fix for the old `linkedId` model — but it was still a LIVE id lookup, just renamed: `getEntries(node.inputA)`/`getEntries(node.inputB)` resolved `state.nodes[...]` on every recompute. Person-reported repro: create filter A ("Some") and filter B ("Entry"), combine with AND, delete filter A — the AND filter's results disappeared along with it. Exactly the bug the whole redesign was supposed to fix, just moved to new field names. Base rule, now explicit: *"Filter kennen keinen Bezug zu anderen Filtern. Sie werden nur durch Verkettung auf den Output von anderen Filtern angewandt und erzeugen daraus eigenen Output."*
  - **Core data model**: `and`/`or`/`link` nodes now carry `node.bakedA`/`node.bakedB` — a flat, self-contained COPY of each side's own single condition (`filterType`, `value`, and whichever of `caseSensitive`/`columns`/`isRegex`/`contextBefore`/`contextAfter`/`countBefore`/`countAfter`/`linkDirection`/`linkN`/`linkOrderEnforced`/`linkExclusive`/`bakedA`/`bakedB` apply — see `bakeNodeCondition`), never a node id, never an ancestor chain. `getEntries()`'s `and`/`or`/`link` branch is no longer special: it reads its own input entries the ORDINARY way (`getEntries(node.parentId)`, exactly like every other filter type), then evaluates `bakedA`/`bakedB` as predicates over that pool via a new standalone evaluator, `getEntriesFromBaked`, which mirrors `getEntriesUncached`'s own per-filterType branches (same `textFilterMatches`/`wildcardMatch`/`compileRegexFilter`/etc.) and recurses into a nested baked `link` condition for multi-hop chains. Deleting, renaming, moving, or replacing the original source node(s) now has **zero effect** — verified with the exact user repro (combine "Some" AND "Entry", delete "Some", verify unchanged, delete "Entry", verify still unchanged) and an ancestor-independence case (a filter A nested under an unrelated ancestor C combines using only A's own condition, never C's restriction).
  - **No cycle guard needed at all any more** (even the "hand-edited file" guard from the previous session is gone) — `bakedA`/`bakedB` hold plain data, not node-id references, so there's nothing left to corrupt into a cycle except normal recursion into a nested baked link, bounded by ordinary data-structure depth.
  - **Unpack is now purely additive**: materializes `node.bakedA`/`node.bakedB` into two new, real, visible sibling filter nodes, wired via a FRESH combiner near the original — the original `and`/`or`/`link` node is left completely untouched (previously it was deleted and replaced).
  - **Export/library generalized to "just this filter" vs. "include ancestor chain", for EVERY filter type** — the previous session's `and`/`or`/`link`-specific "Include source filters used by combined nodes?" dialog is removed entirely (it was also the cause of a reported bug: the dialog could appear at app startup instead of only during an actual save/export action). `serializeFilterBranch(nodeId, includeAncestors)` now offers this choice for any single filter node; the imported branch always attaches under whatever node is currently active/selected at import time, never hardcoded to FILE.

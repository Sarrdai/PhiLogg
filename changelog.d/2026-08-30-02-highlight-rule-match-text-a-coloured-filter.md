- **Highlight-rule match text: a coloured filter now underlines the substring it matched, in its own colour, in both views and the entry detail** (this session, 2026-08-30, `FEATURE_BACKLOG.md` #20, entry removed). Until now a highlight rule only tinted a row's left-edge gutter — *that* row matched, without saying *where*. The inline match-text marking that already existed for the active filter path (2026-08-23) is now also driven by highlight rules.
  - **Which nodes**: every `filterType: "text"` node carrying a `highlightColor` anywhere under the active root file (`getHighlightMatchNodes`) — `computeHighlightMap`'s own node set narrowed to the one type that has a substring to mark. Deliberately not scoped to the active filter path the way the existing marking is: a highlight rule is a standing, file-wide marker, which is why its gutter markers already showed in both views.
  - **How it paints**: a 2px underline stripe in the rule's own colour, in a single lane whose depth never changes. Where several rules cover the same characters the lane alternates between their colours in 5px slices, so a rule's line runs dead straight through the overlap and the overlap costs no vertical room. Drawn as a `background-image` inside the mark's own box (`left bottom`, `100% 2px`), never as a shadow beneath it. **A stripe rather than a second background colour is what makes a priority rule unnecessary** — one character can carry the filter path's background `<mark>` *and* any number of rule colours at once, so neither has to win. Person-chosen from three offered options for the overlap case, over "highlight wins" and "filter mark wins", and from three again for the overlap *rendering* (below), over parallel per-rule lanes and a vertically split lane. `markCombinedHtml` cuts the text at every boundary either range list contributes and asks both lists per segment; the two lists are never merged (that would destroy the per-rule colour), and with no rule ranges at all it delegates straight to the pre-existing `markRangesHtml`, leaving that hot path byte-for-byte what it was. Rule colours are `escapeHtml`'d into the inline `style` — `node.highlightColor` can carry arbitrary text from a hand-edited or imported filter file.
  - **Where**: Filtered view, **Full view** and entry detail (person-chosen: consistent with the gutter markers already showing in both views). The Full view had no match marking at all before — and it still never marks the *filter path's* matches, only rules: that view is filter-path-independent by design, so the active filter's matches would be marking text in rows it makes no claim about. `buildMatchMarkContext`/`markFieldHtml` are the shared once-per-render bundle and per-field entry point all three surfaces now use.
  - **Control surface**: one view-bar toggle, `#btnHighlightMatchText` (default on, `localStorage["philogg-highlight-match-text"]`), next to `#btnTextMatchHighlight`. Person-chosen over the backlog entry's own two alternatives — a per-node toggle in the colour picker (would have meant a new filter-node field threaded through every persistence carrier, to answer a question already answered by whether the filter carries a colour) and a Settings checkbox. No Settings rows of its own for the same reason. The two buttons are fully independent.
  - **Bug fixed on the way in: `textFilterMatchSpec` ignored `node.isRegex`.** It fell through to the plain-substring path and searched the regex *source* as a literal, which is almost never present in the log — so a regex filter that matched rows perfectly well silently marked nothing inside them, ever since regex filters shipped. It now branches on `isRegex` first, in the same precedence `getEntries`'s own `"text"` branch uses, and `findMatchRanges` gained a regex branch (all occurrences, zero-width matches skipped so a pattern like `a*` can't pepper the field with empty marks). This fixes the pre-existing filter-path marking too, not just the new highlight-rule path.
  - **Two person-reported defects in the first cut of this, fixed the same session before it left the branch.** (a) *The stripes were invisible in both log views.* They were drawn with `padding-bottom` + an inset `box-shadow`, i.e. **below** the text's line box — but `.row-grid` is `align-items:center`, so every log-row cell is exactly as tall as its own line box, and `.col-time`/`.col-msg`/… are `overflow:hidden`: everything under the text was clipped away. Making the rows taller would not have been the fix (inline padding doesn't grow a line box anyway); the lane had to move *inside* the mark's own box, which is why it is a `background-image` now. (b) *An overlapped line stepped down mid-sentence.* Each stripe's depth came from the rule count of the **segment** it sat in, so the same rule was drawn at 2px next to a word and at 4px under it — in the reported screenshot, the red "Target Virtual" underline dropped a step wherever the purple "Target" rule joined it. Depth is now a property of the single shared lane and never of the segment; overlap is encoded horizontally instead. Every mark from the segmenting path also gained `.mark-seg` (no side padding, no rounded corners), since one rule's underline is routinely cut into several marks by another rule's boundary and the pieces have to join seamlessly.
  - **A third person-reported defect, found via a pixel comparison of screenshots with the button on vs. off: toggling it shifted the layout of the unrelated, pre-existing active-filter marking.** `mark.text-match-mark` (the filter-path's own background mark, unchanged since the 2026-08-23 session that introduced it) carried `padding:0 1px` — 2px of layout-affecting side padding on an inline element, unlike the purely-cosmetic background/box-shadow the rest of this marking uses. Whether a filter match rendered through the new `.mark-seg` path (padding zeroed, needed for seamless multi-rule joins) or the old plain `markRangesHtml` fallback depended entirely on whether a coloured highlight rule *also* matched the same field — so the SAME filter match was 2px narrower with the button on than off, reflowing every character after it, nowhere near any actual highlight rule. Fixed at the root rather than patched around: `mark.text-match-mark` now carries `padding:0` unconditionally, on every path — marking a substring never changes its layout width again, regardless of which feature is on.

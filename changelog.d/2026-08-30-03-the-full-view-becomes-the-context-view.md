- **The "Full" view becomes the "Context" view: the active filter's own result with the log around it, collapsed into expandable gaps** (this session, 2026-08-30, person-reported). Feedback: *"der Full View ist insofern verwirrend, das Nutzern nicht klar ist, dass sie sich noch immer auf einem Filter Node befinden und eben nicht über Full auf den File Node wechseln."*
  **Diagnosis first.** `renderHighlightView()` set `currentHighlightViewEntries = state.nodes[rootId].entries` — the root file's raw entry array, with no reference to `state.activeId` at all. The view was therefore *pixel-identical* on a filter node and on a file node: there was no wrong signal to correct, there was no signal. Two things compounded it — "Full" and "Filtered" are an opposition, so the label itself implies the filter is off, and switching tabs kept the view's own scroll position, so nothing tied what you saw to what you had been looking at.
  **The rework**, per the agreed framing (the view is *your result, seen in context* — its original purpose was "den Kontext der Filterergebnisse sehen, ohne im Tree umherzuspringen"):
  1. **The view now renders the active node's own result** (`buildContextView`): the matches, with everything the filter rejected collapsed into **expandable gap strips** between them — the GitHub-diff expander people already know (`⌃` reveals 25 rows at the top of the hidden run, the middle button reveals all of it, `⌄` reveals 25 at the bottom; a fully open gap's strip becomes its collapse control). A gap carries `before`/`after` so the still-hidden remainder is always one contiguous run, i.e. one strip per gap however it was opened. `currentHighlightViewEntries` stays a flat array of real entries, so the ~15 places that consume it (minimap, selection, Shift-click ranges, arrow-key nav, `captureViewAnchor`) needed no changes.
  2. **What counts as a match**: `getEntries(state.activeId)`, deliberately not `applyLevelFilter()`'d and not unioned with pinned bookmarks — person-stated rule: *"egal was für eine Art Filter vorausging: der Output sind die Ergebnisse, alles andere ist Kontext"*; the level quick-filter hides result rows from the Filtered view's *display*, they never leave the result set. That keeps the earlier "level filters must not narrow the whole-file view" requirement true rather than contradicting it.
  3. **On a file node nothing is marked and nothing is collapsed** (`contextActive === false`) — the view renders the plain whole file exactly as before, which is what keeps its other, older purpose (tracking several coloured highlight rules across a whole file) available.
  4. **Match rows reuse the `context`/`countContext` filter's existing `.ctx-bracket`** (plus `ctx-start`/`ctx-end` caps) rather than inventing a new marker — people already read that bracket as "the filter produced this". It gets its own gutter lane on `#highlightRows` (`ctx-active`) instead of sharing `.hl-markers`' slot, since here *every* match is bracketed and the Filtered view's rare, documented overlap would become constant. Revealed context rows recede to `opacity:.5` — opacity only, never a colour change, so the `.lvl-error`/`.lvl-warn` tinting survives; hover/selection restores full strength, and a row carrying a highlight-rule colour is never dimmed.
  5. **Renamed to "Context"** (tabs: Context / Filtered / Stacked; internals stay `highlight*`, same compromise the earlier "Full" rename made). "Context" and "Filtered" describe a containment relation instead of two filter strengths, which is what made the old pair misreadable in the first place.
  6. **Nav chip `#contextNav`** replaces the Context panel's Stacked-only `.fh-panel-badge` and is shown in tabs layout too: `‹`/`›` (previous/next match), the active node's name, "*n* / *m* matches", and expand-all/collapse-all. It is the view's textual answer to "am I still on a filter?". **`Ctrl+↓`/`Ctrl+↑`** (`nextMatch`/`prevMatch`, rebindable) do the same from the keyboard, walking real matches and skipping revealed context rows; their check sits ahead of both arrow-key blocks, which match on `ev.key` alone and would otherwise swallow the chord.
  7. **Jumping in is unchanged in shape** — double-click, `Enter`, link-view pair rows all still route through `revealInHighlightView` — but it now opens the gap the target is hidden in first, which is a correctness requirement rather than a preference (a target inside a collapsed gap has no row to scroll to). `moveHighlightSelection` gained the matching courtesy: a selection with no row here continues from its **would-be** position (`contextWouldBeIndex`, binary search over the root order), the same idea the Filtered view's temp anchor applies.
  8. **New setting** — Settings → Behavior → "Context view starts out": `collapsed` (default — the view then opens *as* the filter result, the strongest available "you are still on a filter" signal), `expanded` (the pre-rework whole-file view, still collapsible per gap), `aroundJump` (collapsed, but a jump also opens the gaps on either side of the target).
  9. **Virtualization**: the Context view always uses the offsets path now (`buildContextRowOffsets`), since gap strips make row tops variable regardless of the multiline/notes toggles — each strip's height folded into the row it follows, the leading strip into `offsets[0]`, so `findOffsetIndex`/`topVisibleEntryId`/`captureViewAnchor`/`restoreViewAnchor` keep working on it unchanged (`minimapRenderedSpan` re-keyed from `needsRowOffsets()` to the array's own presence for the same reason). Collapsed, this is *cheaper* than before: the array is sized by the match count, not the file. Opening/closing a gap goes through `captureViewAnchor`/`restoreViewAnchor` so the reading position never jumps.
  10. **Text-filter match marking now runs in this view too** (`textMatchHighlightInRows`, setting relabelled "Show matches in log rows"). Not in the original scope, added because Stacked shows the same entry in both panes at once and marking it in only one read as two different rows. *(Superseded on merge into main: the highlight-rule feature's tested design — Group 137 asserts the Full/Context view never marks the active filter path's own matches — takes precedence, so the merged Context view is filter-path-independent and shows only highlight-rule marks. See `docs/filters.md` → "Highlight-rule match text".)*
  11. **`toggleBookmark` rebuilds the Context view too** (found while reviewing the diff, not reported). It deliberately repaints row DOM directly instead of calling `render()` — a bookmark toggle must never yank the reading position — which was fine while this view was the raw file, but it now holds the *active node's* result: toggling a bookmark while standing on the auto "Bookmarks" node changes which rows are matches and where the gaps fall. Rebuilt in place there now, through `captureViewAnchor`/`restoreViewAnchor` so the reading position still holds. Covered by Group 138(l).
  All new state (`contextGaps`/`contextExpansions`/`contextStrips`/…) is module-level and session-only, deliberately **not** on the node — that keeps it out of `cloneSubtree`/`snapshotSubtree`/`serializeFilterBranch`/`serializeFilterTreeForCache` entirely. Expansions survive re-renders of the same node and are dropped on any active-node change.

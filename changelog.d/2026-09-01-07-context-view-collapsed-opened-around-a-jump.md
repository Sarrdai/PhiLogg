- **Context view: "Collapsed, opened around a jump" now follows the match navigation and mouse selection** (this session, 2026-09-01, person-requested). The setting only ever reacted to a jump coming *from* the Filtered view (double-click / `Enter` → `revealInHighlightView`); the Context view's own `‹`/`›` arrows and `Ctrl+↑/↓`, added in the same rework, moved the selection without touching a single gap — and neither did clicking another match — so the "peek at this spot" reading of the setting stopped applying the moment you started working *inside* the view it was built for. Asked for: the surrounding context should travel *with* the selection — open around the match you land on, shut again behind you — unless a gap was opened or collapsed by hand, which wins.
  1. **`moveContextMatchSelection` routes through `applyContextJumpExpansion`** like every other jump does, then rebuilds (`buildContextView` + `rebuildHighlightOffsets`) and lets `selectHighlightEntry` find the row in the **new** list — the index it computed before the expansion is stale the moment the row list changes. No `captureViewAnchor`/`restoreViewAnchor` pair here, unlike `setGapOpen`: centering the target is what positions this view, so there is no reading position to preserve.
  2. **`applyContextJumpExpansion` gained the "shut the previous jump's gaps" half.** It now computes the gap set this jump *wants* first, then — under `"aroundJump"` only — shuts whatever the last jump had opened and is not wanted again, before opening the rest. One open window travels along the file instead of every visited spot staying revealed.
  3. **Hand-set gaps are exempt, via a second set.** `contextAutoExpansions` holds the subset of `contextExpansions` that the jump machinery opened *itself* and nobody has touched since — the only gaps a later jump is allowed to shut. `setGapOpen` drops its gap out of it (open or collapse, either way the person now owns that gap) and `setAllGapsExpanded` clears it wholesale; a gap that is already open by hand when a jump happens to want it stays hand-owned rather than being adopted. Created, reset and dropped in lockstep with `contextExpansions`, so a node switch clears both.
  4. **Nothing changes for the other two setting values.** Under `"collapsed"`/`"expanded"` no set is tracked and nothing is ever shut: a match always has a row of its own, so the correctness half (open the gap a target is buried in) doesn't fire for the arrows at all, and they leave every gap exactly as it is.
  5. **A plain click on a match row is a jump too** (`selectContextRowByClick`) — picking another result with the mouse reads exactly like walking there with the arrows, chip readout included. With one requirement the arrows don't have: **the clicked row may not move on screen**. It is not centred; what shuts above it is a different height from what opens there, so `scrollTop` stops meaning the same thing across the rebuild — its on-screen offset is captured beforehand (`captureRowScreenOffset`) and restored against the *new* offsets array through `scrollToHighlightIndex`'s `opts.offset`, which `selectHighlightEntry` now forwards. Only real matches count (a click on a revealed context row is not a move to another result), and Shift/Ctrl clicks are routed straight to plain selection — rebuilding the list mid-gesture would move the rows out from under a multi-selection. Accepted consequence, confined to this one case: the rebuild replaces the row's DOM node, so while the setting is on, a native `dblclick` on a Context match row no longer fires — that handler only scrolls the row into view, which the offset restore has just done.

Same root cause the file-load half of this hit before (see "loading a second file left a stale multi-selected highlight", `tests/` Group 112c): a plain, non-Ctrl click on a tree row puts that row's id into `state.multiSelect` — it is not a Ctrl-only gesture — and node **creation** set `state.activeId` to the new node without dropping it. Since `.multi-selected` paints the same `--accent-soft` background `.active` does, the row the filter was built from kept looking selected right next to the new node's genuinely active row. Every creator now ends in one small `activateNewNode(node)` helper that sets `state.activeId` and clears `state.multiSelect` together: `createFilterNode`, `createAndOrNode`, `createLinkNode`, `createContextNode`, `createCountContextNode`, `createSelectionFilterNode`, `mergeFiles`' merged file node, and `pasteClipboard`'s clone. `createFileNode`/`activateQueuedFileNode` keep doing the same pairing inline — they need their `sessionRestoreInProgress` guard wrapped around it.

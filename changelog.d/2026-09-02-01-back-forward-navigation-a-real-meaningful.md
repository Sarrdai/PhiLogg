- **Back/forward navigation: a real "meaningful interaction" heuristic** (this session, 2026-09-02, person-requested: *"Ich möchte die Vor- und Zurück Navigation der App verbessern … den Nutzer in Ansichten und Interaktionen zurückführen … Ich kenne so einen Ansatz aus Visual Studio oder Jetbrains Rider … Oft verliert man sich im Code und kann so nochmal 'zurückfinden' auf was man zuvor angeschaut hat"*). The existing `#btnNavBack`/`#btnNavForward` (FEATURE_BACKLOG.md #53) recorded **only** changes of the active filter node, as `{nodeId, scrollTop}`. Three consequences, all fixed here:
  1. **Scrolling was invisible to the history** — worse, `trackNavScroll` overwrote the current entry's `scrollTop` on *every* scroll event, so the spot you were reading was already destroyed by the time you scrolled away from it. Scroll is now **B1**: `NAV_DWELL_MS` (700ms) after the last *user* scroll, a waypoint is pushed iff the view travelled at least one viewport height from the current waypoint's own remembered position; otherwise that waypoint is refreshed in place. Each further scroll restarts the timer, so a fast flick to the end of a file yields one waypoint at the destination, not fifty on the way; measuring against the waypoint rather than against the burst's own start is what lets several short bursts accumulate and what keeps the origin intact while you are away from it. `onNavScroll` is wired to all four scroll containers, `#highlightBody` included (only `#tableBody`/`#extractScroll`/`#linkScroll` were tracked before).
  2. **Entry jumps were invisible** — `revealInHighlightView` (double-click/Enter), `jumpToFullLog`, `jumpToEntry`, the minimap's click-to-jump and `jumpToTailedNewest` either don't change `activeId` or only change it as a side effect. They are **A2–A6** now: each freezes the current position before the jump and pushes the destination after it. A jump that also switches nodes still yields exactly one waypoint — `isSameNavPlace()` merges it into the one `render()`'s own A1 path already made.
  3. **The waypoint was too thin.** It now carries `{ nodeId, fhLayout, fhActiveTab, entriesView, selectedId, filterAnchor, contextAnchor, rawScrollTop, contextScrollTop }`, and Back/Forward restores the whole visible state: node, Context/Filtered/Stacked mode, selected row, and both panes' scroll positions. The two anchors are `{id, offset}` pairs from the existing `captureViewAnchor`/`restoreViewAnchor` — **an anchor row instead of a raw pixel offset**, because a raw `scrollTop` means something different after a tail tick, a level-filter change, a multiline toggle or a re-sort. Accepted trade-off: with nothing selected the restore is row-granular (the fallback anchor reports offset 0), so a sub-row pixel offset is not reproduced. `rawScrollTop` still covers the extraction table and link pair view, which have no entry-keyed row list.
  Explicitly **not** waypoints (tier C): programmatic scrolls (tail-follow, a jump's own scroll, a restore — recognized through the existing `lastProgrammaticScrollTs` 150ms window); the Context/Filtered/Stacked toggle and the automatic `revealFilteredView()` — the view mode is stored *in* a waypoint and restored, but switching it is not itself a step, same as a tool window in an IDE; level quick-filter, sort, multiline/notes toggles, column changes, gap expand/collapse; and **selection**, which rides along on whatever waypoint is current instead of pushing one, so an arrow-key sweep through rows produces none and B1 puts exactly one at the destination once it has scrolled far enough. `contextExpansions` is deliberately not part of a waypoint either — the restore calls `applyContextJumpExpansion()` on the context anchor, exactly as `revealInHighlightView` does, which is all the correctness it needs. Undo/Redo stays orthogonal and untouched.
  Restoring a waypoint also disengages a live tail, for the same reason picking a row does — otherwise the next tail tick would immediately undo the Back. Also: `NAV_HISTORY_LIMIT = 50` (same cap and reasoning as `UNDO_STACK_LIMIT`); the buttons carry a dynamic tooltip naming their destination ("Back to: `<node>` · `<time>`"), the way `updateUndoRedoButtons` already does; an entry whose *anchor row* is gone is no longer treated as stale (it still names a live node, and the anchor restore falls back to the view's own default) while a deleted *node* still drops out as before. Per the person's answers when the plan was put to them: no keyboard shortcut was added (`Alt+←/→` is tree navigation, `Ctrl+-` is zoom-out; `SHORTCUT_ACTIONS` is unchanged) and no history dropdown — the two buttons plus the mouse's back/forward buttons stay the whole UI.

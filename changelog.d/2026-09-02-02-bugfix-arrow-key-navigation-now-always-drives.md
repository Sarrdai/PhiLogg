- **Bugfix: arrow-key navigation now always drives the pane that is actually on screen** (this session, 2026-09-02, person-reported: *"ab und zu würde beim Navigieren der Auswahl nach oben über die Pfeiltasten … die Selektion springt Zeile für Zeile nach oben über den Rand des sichtbaren Bereichs hinaus, dann würde manchmal die Tabelle nicht mitscrollen"* — not reliably reproducible). Diagnosed first: the scroll math itself is sound. `scrollToIndex`/`scrollToHighlightIndex`'s "scroll up" branch (`rowTop < scrollEl.scrollTop` → `target = rowTop`) holds exactly against `tableRowOffsets`/`highlightRowOffsets` in every row-height mode — a fuzz over plain / multiline / notes / multiline+notes walking 60 rows up from row 200 never left the selected row outside the viewport. The bug is one level up, in **which pane the keys were moving**.
  `state.entriesView` (`"filter" | "highlight"`) decides between `moveSelection` and `moveHighlightSelection`, and it was maintained *independently* of which pane tabs layout actually shows. Row clicks, `Ctrl+1/2/3` and `revealInHighlightView` set it — but the `#fhTabs` buttons and `revealFilteredView()` (a tree click on a filter node, and every filter-creation path) switched the visible pane **without touching it**. Left out of sync, `↑`/`↓` ran against the **hidden** pane, and because `updateSelectedRowClass` syncs the `.selected` class into *both* views' rows, the selection visibly walked row by row through the pane on screen while `scrollToIndex` moved the *other* pane's scroll container — which, being `display:none`, cannot scroll at all, so that scroll was lost outright. Intermittent exactly as described: clicking any row in the visible pane re-synced it, so the same sequence often worked. The two lists line up row-for-row on an unfiltered file node, which is why the selection appeared to step one row at a time while nothing followed it.
  **Fix**: `showFhTab` pins `state.entriesView` to the tab it is showing. It is the single funnel every tabs-layout pane switch goes through (`applyFhView`'s tabs branch, the `#fhTabs` buttons, `revealFilteredView()`, `revealInHighlightView`), and in that layout only one pane exists on screen, so this is an invariant rather than a preference. **Stacked layout is deliberately exempt** — both panes are visible there, so "the one last clicked in" stays the right answer, and `Ctrl+3`'s own explicit `entriesView = "filter"` is unchanged. One ordering consequence: `applyNavWaypoint` now restores `wp.entriesView` **after** its `render()`/`applyFhView` calls instead of before them, since both can route through `showFhTab`; assigned up front it would be overwritten in the stacked case, where nothing calls `showFhTab` afterwards to put it back.
  **Also fixed, found while verifying the above**: the suite's own shard runner could report a wrong total. Both `tests/philogg.regression.test.js` and `tests/run.js` ended on `process.exit()`, but under `run.js` a child's stdout is a **pipe**, where writes are asynchronous — `process.exit()` discards whatever is still buffered, and twice in this session that swallowed a child's `##SHARD` result line, giving `2273 passed, 0 failed` instead of 2915 with nothing listed as failing. That is exactly the "a group that silently stopped running shows up as a lower count" signal `tests/README.md` tells you to trust, so it had to go. Both now set `process.exitCode` and let the event loop drain; termination is unchanged (~43s) and a forced failure still exits 1 in both sharded and single-process mode. 13 consecutive full runs green afterwards.

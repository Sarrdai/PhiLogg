- **Context view: partial expansion, a marker lane that reads, and a real toolbar** (this session, 2026-09-02, person-requested: *"Die Bedienung des Kontext Views ist noch nicht ganz rund. Die visual cues sind noch zu unscheinbar."*). Seven asks, all of them landing on the same view:
  1. **Auto-expand is the default.** `contextInitialExpansion` now defaults to `"aroundJump"`, relabelled "Auto expand around the selected row" and moved to the top of the select. The old default `"collapsed"` opened the view as the bare filter result, which made the point ("you are still on a filter") but left it inert until you deliberately unfolded something.
  2. **New setting "Lines revealed per step"** (`contextExpandStep`, `philogg-context-expand-step`, default **10**, clamped 1–1000): the width of one expansion step *per direction*, so the default reveals 10 lines above and 10 below the row you land on.
  3. **A hidden stretch is no longer binary.** `contextExpansions` went from a `Set` of open `gap.start` values to a `Map` of `gap.start` → the revealed root-index ranges `[{from,to}, …]` inside it (sorted, disjoint, merged; three writers: `revealContextRange`, `hideContextRange`, and the seeding in `buildContextView`). That is what makes "show me a bit more" expressible at all, and it is what an auto-expansion needs, since a window around a jump target sits in the *middle* of a gap. A partially revealed stretch renders `[run] → "Show more (+n)" → "… N lines" → "Show more (+n)" → [run]`: the step row exists only on a side that already has revealed rows against it, and only while more than one step is still hidden (below that it would do exactly what the "… N lines" row does). The two ends are separately operable — growing the run above never also grows the one below. With nothing revealed a stretch is just its "… N lines" row, because clicking the match itself is what opens the first step.
  4. **The bracket on match rows is gone**, replaced by the `.ctx-anchor-dot` the `context`/`countContext` filter already draws next to its reference entries. Reusing the bracket had been a deliberate borrowing ("this is what the filter produced") but it says *these rows belong together*, which is true of a time window and false of a filter result scattered across the file.
  5. **A revealed run is now one connected control.** Every revealed row carries a full-height `border-left` (`.ctx-run-line`) so the run draws one continuous line from its first row to its last, capped by the two carets that used to be the only fold affordance. The whole line is the button: a click anywhere along it collapses the run, so a block folds back from wherever you happen to be reading it.
  6. **The indent on revealed rows is gone** and the line/dots moved into the lane the bracket used to occupy (`--ctx-lane-x`, defined once). Consequence worth having: no log text moves sideways when a run opens, and the gutter reads as one column — a dot per result, a line per revealed run.
  7. **The nav chip became `#contextToolbar`**, a real row inside the table under its header, with a separate "collapse all" next to "expand all" and every button on the app's own `.toolbar-icon-btn` shape (22px, id-scoped override, the same pattern `#btnPinBookmarks` uses). It is in flow, not overlaid: it takes `CONTEXT_TOOLBAR_HEIGHT` out of `#highlightBody`'s viewport instead of covering log lines — and `setContextToolbarVisible` compensates the scroll position by exactly that number in the same step, so the rows themselves do not slide when it appears. That compensation is scoped to a bar appearing while the panel *stays* on screen; a tab switch hides the whole panel, where there is nothing visible to cancel out. With the floating chip went **Settings → "Match navigation position"** — there is no corner left to pick.
  Two model details worth keeping in mind. `contextAutoRanges` replaces `contextAutoExpansions` as "what the last jump may take back", and it records only what the jump *actually* revealed (`contextHiddenPartsOf`), so a range already open by hand is never adopted; `hideContextRange` removes precisely one range, splitting a run that merely straddles it, so a hand-revealed stretch overlapping the jump's window survives intact. And `contextRuns` lists each contiguous revealed run **once** (binary-searched per visible row by `contextRunAt`) rather than keying a map by row — a fully expanded file would otherwise cost a map the size of the file.
  **Also fixed, exposed rather than caused by the extra group**: seven more fixed short sleeps in the suite (`await new Promise(r => setTimeout(r, 20))` standing in for an async IndexedDB write/read in Groups 59a/59b, 70e, 70f and the two format-level groups) were latent flakes of exactly the kind the 2026-09-01 session already converted four of — under the heavier shard load they intermittently killed a whole shard, which shows up as a *lower pass count with nothing reported as failing*, the signal `tests/README.md` tells you to trust. They now `waitFor` the state they are about to assert on, and `waitFor` itself awaits its predicate so an async one (`listFilterLibrary()`) can be passed directly instead of being mistaken for a truthy promise.
  **Two of those conversions were wrong at first, and the same short-count signal caught them**: `resetDefaultFormat` mutates the format object *before* awaiting its IndexedDB write and only re-renders *after* it resolves, so a predicate on `state.logFormats` is already satisfied while the write is still in flight — the group finished, `withApp` tore the window down, and the pending continuation crashed in `renderLevelBar` against a dead `document`, killing a whole shard on every run. The 20ms sleep had been covering that by accident. Groups 70f and 116d now wait on a genuine POST-write effect instead (the format row's own re-render — its name text in 70f, its node identity in 116d, where a level-only reset leaves the text unchanged). The other five are fine as state predicates: `saveFormatEdit`/`saveFormatRuleEdit` update `state` *after* their await, so their state and panel-visibility predicates are post-write by construction. Worth remembering for the next conversion: the barrier has to be an effect the writer produces after its await, not one it produced before. Five consecutive full runs green afterwards, all at 2950.

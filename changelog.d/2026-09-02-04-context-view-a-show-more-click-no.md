- **Context view: a "Show more" click no longer jumps** (this session, 2026-09-02, person-reported follow-up to the entry below: *"Wenn ich auf ein Show more lines klicke, soll sich das Log nach oben oder unten erweitern … ohne dabei die Einträge der anderen Seite im View zu verschieben. Aktuell springt die Anzeige immer wieder auf die selektierte Zeile, wenn diese ausserhalb des Views liegt."*). `commitContextExpansionChange` routed every hand action through `captureViewAnchor`/`restoreViewAnchor`, the file's general scroll-anchoring pair — which **prefers `state.selectedId`** and, when the selected row is off screen, reveals it *centred* rather than pinning a pixel spot. That is the right default for a whole-view change, but wrong for a step click: the selection at that moment is usually somewhere else entirely, so revealing ten lines threw the view across the file.
  The row-level actions now pin **one named row** instead (`captureContextRowPin`/`restoreContextRowPin`: an entry id plus its distance from the scroll container's top edge, re-found after the rebuild through `contextWouldBeIndex`'s binary search rather than a `findIndex` over what can be the whole file). Which row follows from where the new rows are inserted, so each action grows its own side and holds the other one still: a **top** step pins the row *after* its filler group (rows appear above it — the log grows upwards, nothing below moves), a **bottom** step pins the row *before* it (the log grows downwards, nothing above moves), "… N lines" pins the row above it and grows downwards (row 0 for a leading group, which has no row above), and collapsing a run pins the row above the run. An index outside the list means there is nothing on that side to hold, and `scrollTop` is simply left alone — the same effect. Expand-all/collapse-all keep the old anchor: there is no side that should stay put there. `"more"` fillers carry a `side` field for this, and `appendContextFillers` passes its own `contextStrips` key through so a click knows which row to name.
  Verified in a real browser as well as in jsdom (the row on the far side of the step holds its exact pixel: 712 → 712 for a top step, and a bottom step leaves `scrollTop` at 0). `docs/ui-and-views.md`: a new paragraph and table under "Revealing a step at a time". `tests/philogg.regression.test.js`: **Group 138 (q)** — both directions on a 200-line fixture, each with the selection deliberately off screen (the exact condition that used to trigger the re-centring); confirmed to fail on 2 assertions with the pin removed. **2961 passed, 0 failed** (2950 + 11).

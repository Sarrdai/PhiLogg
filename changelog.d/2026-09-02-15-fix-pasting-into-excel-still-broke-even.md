- **Fix: pasting into Excel still broke even with the confirmed-correct decimal separator — clipboard copy now writes an Excel-native `x:num` HTML flavor, sidestepping decimal-separator guessing entirely** (this session, 2026-09-02, person-reported follow-up: even explicitly picking "." — confirmed as what that Excel install both types and calculates with — still pasted with the point missing entirely; picking "," still shifted by a factor of 10). Root cause: Excel's plain-text-paste number recognition applies its own additional heuristics on top of whichever separator character arrives, unqueryable from a web page, and can misfire regardless of which character is objectively correct — so no choice of separator in the TSV text could ever be made fully reliable. Real fix: `copyTextToClipboard(text, html)` now also writes a `text/html` clipboard flavor (via the Chromium `ClipboardItem`/`clipboard.write` API, falling back cleanly to the old `writeText`-only path where that's unavailable) alongside the plain-text TSV. Excel — like every major spreadsheet app — prefers `text/html` over `text/plain` when both are present, and reads a numeric `<td>`'s `x:num="…"` attribute as the literal value with **no locale interpretation at all** (always period-decimal, per the MS Office HTML-clipboard spec) — the exact mechanism Excel's own Ctrl+C already emits for numeric cells. `buildExtractClipboardHtml` builds this; `extractClipboardCell` produces each cell's `{value, raw, numeric}`, where `raw` (the x:num attribute) is deliberately never localized, only `value` (the visible `<td>` text / the plain-text TSV fallback) is — so Excel now gets the exact value regardless of decimal-separator settings on either end, and the Settings override below remains relevant only for the plain-text fallback and other apps.

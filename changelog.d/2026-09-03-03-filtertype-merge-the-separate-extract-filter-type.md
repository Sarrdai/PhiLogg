- **filterType merge: the separate "extract" filter type and its "Extract" popup button are retired — a wildcard "text" filter is simultaneously a normal filter and extraction-capable; double-click a Table row / click a Plot mark now reveals into the SAME node's Filtered view instead of jumping to the raw file** (this session, 2026-09-03, follow-up to `docs/ui-implementation-plan.md`'s unified-toolbar work below). Two related changes:
  1. **filterType merge.** `filterType === "extract"` and `#filterExtractBtn` ("Extract", the second popup button) are gone entirely — `commitFilter()` no longer takes an `asExtract` flag, and "Add filter" is the popup's only outcome. A `"text"` filter node whose pattern contains `[value:...]`/`[*]` wildcards now automatically both filters/highlights normally (unchanged — its matching already went through the same wildcard-regex code path a "text" node's wildcard pattern always used) AND unlocks Table/Plot (`nodeHasExtractableWildcards`, re-gated from `filterType === "extract"` onto `filterType === "text" && !node.isRegex && isExtractPattern(node.value) && compileExtractPattern(node.value)`). Inversion (NOT) is no longer excluded for such a node in the tree context menu — that exclusion existed only because the old "extract" filterType couldn't be inverted meaningfully; a wildcard "text" filter always could. `ignoredColumns`/`assertions`/`columnRenames`/`plotConfig` and their four persistence carriers (`createFilterNode`/`updateFilterNode`, `cloneSubtree`, save/load JSON, session cache) are all re-gated from `filterType === "extract"` onto `filterType === "text"` the same way. **No migration for old `"extract"`-type data** — the person explicitly said none is needed, since no version of the software has shipped yet: `FILTER_TYPES` no longer recognizes `"extract"`, so an old hand-edited/exported node of that type is simply rejected on import rather than kept loadable.
  2. **Double-click / plot-click now reveals in place.** The extraction table row's `dblclick` and the 2D/3D Plot tab's mark-click handlers, which used to call `jumpToFullLog` (jump to the node's raw root file, clearing the level filter — the only option back when an extraction node had no Filtered view of its own), now call the new `revealInFilteredView(entry, sourceRowEl, sourceScrollEl)` instead — modeled directly on `revealInHighlightView`'s Context-view counterpart. It stays on the SAME extraction-capable node (which already has an ordinary Filtered pane, see the unified-toolbar work below), switches `fhActiveTab` to `"filter"`, and selects/scrolls/flashes the row there, preserving its on-screen offset the same way `jumpToFullLog` did on the table-row trigger. `jumpToFullLog` itself is unchanged and still directly tested — it's simply no longer wired to any UI action (kept unwired, same precedent as `copyWholeExtractTable`).

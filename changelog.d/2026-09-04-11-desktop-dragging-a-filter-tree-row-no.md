- **Desktop (Tauri): dragging a filter tree row no longer triggers the "Drop Logfiles to Load" overlay** (this session, 2026-09-04, person-reported). Root cause: the desktop wrapper's native drag-drop handler (`WindowEvent::DragDrop`, `windows.rs`) fires `Enter`/`Over`/`Leave` for *any* drag the webview sees — including `philogg.html`'s own in-app HTML5 drag for reparenting a filter tree row — not only a real OS file drag, so it unconditionally showed the page's `#dropOverlay` via `window.philoggDropOverlay(true)` regardless of what was being dragged. `handle_drag_drop` now only trusts `DragDropEvent::Enter`'s `paths: Vec<PathBuf>` field (empty for an in-app drag, populated for a real file drag) to decide, and remembers that verdict in a `Cell<bool>` captured by the window-event closure so the `Over`/`Leave`/`Drop` events later in the same drag (which carry no `paths` of their own) agree with it. Rust-only change (`desktop/src-tauri/src/windows.rs`); nothing in `philogg.html` or the plain-browser build is affected. No `cd tests && npm test` run — out of scope per `CLAUDE.md` (nothing here is loaded/parsed by the jsdom suite); this environment has no GTK dev headers installed for a `cargo build`/`cd desktop && npm run build`, so verify with a real desktop build before shipping.

- **Fixed: Filter/View Toolbar hover-expand flickered or froze mid-animation at some edge positions** (this session, 2026-09-05, person-reported). Root cause: expand/collapse for `.row-action-hit`/`.tb-hit` keyed off plain `mouseenter`/`mouseleave` on each fixed-size hit-zone — but while a PRECEDING button in the row is expanding or collapsing, its growing/shrinking box keeps shoving the NEXT hit-zone back and forth under a stationary cursor, so that hit-zone's own `mouseenter`/`mouseleave` fired repeatedly off the currently-animating (shifting) geometry, visible as the state flickering between expanded/collapsed or getting stuck half-animated. Fixed by replacing the per-hit listener pair with `setupHitExpandGroups()`: hit-zones sharing a parent container are grouped, and a single `mousemove` listener on the container decides `.expanded` by testing the pointer against each hit-zone's rect — but that rect is measured and cached only while the whole group sits collapsed (never refreshed again until the group returns to fully collapsed), so the decision always uses the stable, at-rest geometry, never geometry that's mid-animation because a neighbor is resizing. `tests/philogg.regression.test.js`: Group 176a and Group 180a's hover assertions rewritten to dispatch `mousemove` (with a stubbed collapsed-state `getBoundingClientRect()` on the target hit-zone) against the shared container instead of `mouseenter`/`mouseleave` directly on the hit-zone. **3546 passed, 0 failed** (unchanged pass count — same assertions, different dispatch mechanism).

- **Fixed: deleting a filter node visibly stalled (~1s), unlike switching the active filter** (this session, 2026-09-08, person-reported perf bugfix). `deleteNode()` (`philogg.html`) ended with the global `invalidateAllCaches()` sweep — nulling `_cache`/`_levelCounts` on *every* node in the tree, not just the deleted one — so the very next `render()` → `renderTree()` had to recompute every remaining filter's count badge from scratch (`renderNode()`'s `getEntries(id)` call, once per visible row) against the full log, an O(all nodes × log size) synchronous recompute. Switching the active filter never touches any cache, so the same per-row `getEntries()` calls there hit warm caches and are instant. Root cause: a surviving node's cached result only ever depends on its own `parentId` chain (the same premise `invalidateCachesForRoots` already relies on for tail ticks, see the 2026-09-0x entry below), and deletion never changes any surviving node's `parentId` — the removed subtree is simply dropped from `state.nodes`, nothing is reparented. So `deleteNode()` now invalidates nothing at all; `move`/`invert`/edit are unchanged and still use the global sweep (not reported as sluggish, out of scope here). `tests/philogg.regression.test.js`: new **Group 189** — deleting a filter node leaves unrelated siblings' `_cache`/`_levelCounts` populated (not wiped), the deleted node is actually gone from `state.nodes`, and a filter chained off a surviving sibling still recomputes to the correct result. `PROJECT.md` §3 (Memoization) and the `invalidateAllCaches()`/`invalidateCachesForRoots()` comments in `philogg.html` updated to describe the new behavior. **3704 passed, 0 failed**.

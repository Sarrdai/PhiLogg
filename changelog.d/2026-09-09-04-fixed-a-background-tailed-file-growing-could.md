- **Fixed: a background-tailed file growing could reset unrelated in-progress UI state (e.g. a tree row rename)** (this session, 2026-09-09, person-reported: "Wir hatten jetzt schon öfter, das ein Render Dinge geändert/zurückgesetzt hat die gerade gar nicht angepasst werden sollten"). `onTailChange()` called a full `render()` on every poll where ANY tailed root grew — including one that wasn't behind the currently active view at all. `render()` always runs `renderTree()`, which wipes and rebuilds `#tree`'s entire `innerHTML`, discarding node DOM identity (an already-known gotcha, see "DOM identity across clicks" in `PROJECT.md`) — so any interaction mid-flight elsewhere in the tree got reset on the very next `TAIL_POLL_MS` tick of an unrelated background file, purely because it happened to still be growing. Fix: `onTailChange()` now only calls `render()` when a changed root is behind the active view (`getRootFileId(state.activeId)`); for a background-only change it instead calls `updateLoadRowProgress(rootId)` — the same cheap, targeted per-row count refresh load ticks already use — so the growing file's own tree row still reflects its new entry count without touching the rest of the DOM. Also did a broader review of every full-rebuild render path (`render()`/`renderTree()`/`renderVisibleRows()`/`renderHighlightVisibleRows()`) for other unnecessarily-broad call sites (duplicate/dead-code/performance review requested alongside); the render-scope rule this fix follows is now documented in `PROJECT.md` → "Known gotchas" for future call sites to check against. `tests/philogg.regression.test.js`: new **Group 196** — two tailed files, one active and one backgrounded; asserts zero `render()` calls and DOM node identity preserved for the backgrounded file's tree row across a poll tick (fails without the fix), its `.tree-count` still updating, and that growth behind the active view still triggers exactly one real `render()`. **3801 passed, 0 failed** (`cd tests && npm test`).

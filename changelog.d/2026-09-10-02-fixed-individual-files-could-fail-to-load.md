- **Fixed: individual files could fail to load under the Tauri desktop wrapper (drag&drop and the Open… dialog alike) — flashed grey in the tree, then vanished with "Couldn't load"** (this session, 2026-09-10, person-reported: "In der Tauri Variante kann ich keine einzelnen Dateien mehr Laden. Weder per Drag&Drop noch über den Dialog... erscheint kurz grau im Tree, dann verschwindet sie und das 'Could not load' Popup erscheint."). Both routes converge on `loadFileDescriptors`, so the shared point of failure was the queued placeholder's own load attempt. Root cause: `philogg.html`'s own `window` `"drop"` listener had no guard against a desktop wrapper's *native* drag-drop handling (`windows.rs`) also owning the same drop — the wrapper's own comment states the native handler "suppresses the HTML drop events philogg.html would otherwise use," but that suppression is a webview/platform behavior this page never verified, not something it enforces. Whenever it doesn't hold, one OS drop reaches BOTH the wrapper's native handler (which loads the real path through `philogg://local/…`, see `loadDesktopLocalFiles`) AND this page's own listener a second time — racing the wrapper's real load with a redundant one for the same drop, which is exactly the flash-then-vanish symptom. Fix: new `nativeDragDropOwnsThis()` (true whenever `window.philogg` exists) now gates `dragenter`/`dragover`/`dragleave`/`drop` in `philogg.html`, so the wrapper's native handling is the only thing that ever processes an OS file drop there — a no-op change for a build where the HTML-suppression already worked (those listeners were unreachable dead code then), and a real fix everywhere it doesn't. Also: `loadFileDescriptors`' "Couldn't load" toast used to swallow the actual failure (an HTTP status from `openFile`'s fetch, a parse error, …) — it now appends the reason, so a genuine read/parse failure is distinguishable from this race (or anything else) without needing devtools. `tests/philogg.regression.test.js`: new **Group 198** — the HTML drop listener no-ops when `window.philogg` exists but still works unmodified in the plain browser build, and a failed wrapper-supplied load's toast now names the reason (e.g. "HTTP 404"), not just the filename. `docs/desktop.md` updated. **3824 passed, 0 failed** (`cd tests && npm test`).

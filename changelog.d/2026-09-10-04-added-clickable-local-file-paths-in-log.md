- **Added: clickable local file paths in log lines, desktop build only** (this session, 2026-09-10, person-requested). An absolute Windows/UNC/Unix path detected inside a rendered log line's message field is wrapped in a `.fp-candidate` span (`linkifyPaths`, `philogg.html`, applied to `markFieldHtml`'s output) — in every build, so the page renders identically in the browser and desktop wrappers. Only under the desktop (Tauri) wrapper, where `window.philogg` exists, does hovering one actually verify it: a debounced hover (~180ms) calls the new `window.philogg.pathExists(path)`, backed by a new `path_exists` Tauri command (`std::fs::metadata`, `desktop/src-tauri/src/commands.rs`) — a single syscall, effectively instant even for many candidates on a page. A path that exists gets styled as a link (`.fp-verified`) and a hover popup (`#fpPathMenu`, same shape as the existing `#addToSelectionMenu`/`#treeCtxInfoMenu`) offering **"Open file"** (new `openPath`/`open_path` command, via `tauri_plugin_opener`'s `open_path`) and **"Open containing folder"** (the existing `revealPath`, already used for FEATURE_BACKLOG #52). A path that doesn't exist is never styled and never shows the popup — deliberately, since a path only means something when the log is being read on the machine that wrote it. The plain browser build (File System Access API) has no way to validate or open an arbitrary path string, so there the span renders but stays inert. `tests/philogg.regression.test.js`: new **Group 199** — the path-detection regex (Windows/Unix positives, a fraction/date/URL negative, skipping existing `<mark>` tags rather than matching across them), no popup without `window.philogg` (browser build), a verified path opening the popup with both actions working, and an unverified (nonexistent) path never getting styled or opening anything. `docs/desktop.md` updated. **3841 passed, 0 failed** (`cd tests && npm test`).

- **Fixed: clickable local file paths still truncated any filename with more than one dot** (this session, 2026-09-11, person found this themselves in two more real log lines: `Filtered C:\eula.1028.txt` and `...assembly: C:\Program Files\MyCompany\My Program\MyCompany.App.Program.exe`). The previous fix's unquoted-with-spaces alternative anchored the path's end on a *lazy* `.ext` search — "lazy" stops at the *first* dot-shaped thing it finds, so it truncated `C:\eula.1028.txt` to `C:\eula.1028` and the .NET-style dotted assembly name to `...MyCompany.App`, silently dropping the rest. That anchor's own docs had dismissed this as a rare `archive.tar.gz`-shaped edge case, but multi-dot filenames turn out to be the norm (versioned files, dotted assembly names) — not rare at all. Fixed by dropping the extension-anchor idea entirely: `FILE_PATH_RE`'s unquoted Windows/UNC alternative now lets only **directory** segments (each terminated by its own `\`) contain spaces; the **final** segment (the filename) reuses the exact same no-space class the very first version of this regex had, so it needs no "where does it end" heuristic at all — a space still ends the match exactly like it always did, and a multi-dot filename is captured in full since nothing is trying to guess where its extension starts.

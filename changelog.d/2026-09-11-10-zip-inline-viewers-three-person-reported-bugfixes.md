- **ZIP inline viewers, three person-reported bugfixes + one UX simplification: opened non-log entries actually look opened and reach Alt+Up/Down, drag-selecting text works again, and copy no longer adds extra line breaks** (this session, 2026-09-11, person-reported follow-up to the entry below). (1) **Removed click-to-highlight, kept hover-only** (the UX ask, done first since it also fixes (2)): the delegated click listener on `#inlineTextViewer` and its `.itv-line-selected` class/`state.inlineViewer.selectedLine` field are gone outright — a line highlights purely via the existing plain CSS `.itv-line:hover` rule, no JS/state involved. (2) **Root cause of "can't re-select over an existing selection"**: that same click listener fired on every mouseup inside the viewer (a click always fires at the end of a drag-selection too, not just a plain click), toggling `.itv-line-selected` right after the person finished dragging out a selection — removing the listener (fix (1)) removes the interference; verified plain drag-to-select, including starting a fresh drag from inside an existing selection, now behaves exactly like ordinary browser text selection. (3) **Copy introduced extra line breaks**: each line is its own block-level `.itv-line` div (needed for the gutter layout), and real browsers are inconsistent about how many newlines a block boundary contributes to a copied selection's plain-text serialization, especially around a selection's first/last partial line and genuinely empty lines — rather than fight per-browser DOM-to-text serialization, a new `copy` listener on `#inlineTextViewer` now intercepts the event (only when the current selection is actually inside the viewer) and writes plain text straight from `state.inlineViewer.text` itself, sliced to the exact line/character range the DOM selection covers (via `Range#toString().length` against each line's `.itv-line-content`, so it's correct regardless of how many nested tokenizer `<span>`s sit in between) — always byte-identical to the source file, never the browser's own reconstruction of it. (4) **Root cause of "opened non-log entries still look grayed"**: `.zip-entry-opened` (added in the entry below) reset `opacity` back to 1 but never reset the dim `color:var(--text-tertiary)` `.folder-watch-file`'s own base rule sets — an opened-but-not-active row was technically un-dimmed but still visibly gray, unlike a real opened `.tree-row` (default `color:var(--text-secondary)`) it was meant to match; fixed by adding the same color reset to `.zip-entry-opened`. (5) **Root cause of "Alt+Up/Down skips opened non-log entries"**: `flattenTreeIds` (which `moveTreeSelection`, the function behind Alt+Arrow, walks) only ever iterated `state.nodes`/`state.rootIds` — a non-log entry never gets a real tree node (it lives only in `zip.inlineViewers`, see the entry below), so it was never a candidate at all. Fixed by appending one virtual nav id (`zipViewerNavId(zipId, entryName)`, distinguished from real node ids by a `"zipviewer:"` prefix) per opened non-log entry, in the same per-zip/per-entry order `renderZipSection` itself renders in; `moveTreeSelection` now tracks "where we are" as either `state.activeId` (a real node) or the active inline viewer's own virtual id, and landing on a virtual id sets `state.inlineViewer` instead of `state.activeId` (landing back on a real node clears `state.inlineViewer`, matching a plain tree-row click). `docs/persistence-and-sync.md`'s "ZIP sources" section updated. `tests/philogg.regression.test.js` **Group 199**: **199l** (the old click-to-highlight test) replaced by **199n** (hover-only: no click state, the CSS rule for `.itv-line-selected` itself is gone, `:hover` rule present); new **199o** (opened-row color fix + Alt+Up/Down reaching and leaving an opened non-log entry) and **199p** (copy produces exactly the source's line breaks, including the empty-line edge case, and leaves a collapsed selection's copy untouched).

- **ZIP inline viewers, three more person-reported bugfixes: Alt+Up/Down nav order now matches the visual listing, Ctrl+C no longer steals a text-viewer selection in favor of a background-selected log row, and a copied selection no longer drops leading whitespace or gets hijacked into a native drag** (this session, 2026-09-11, follow-up to the entry below). (1) **Nav order didn't match the visual order**: the earlier `flattenTreeIds` fix (below) appended every opened non-log zip entry's virtual nav id as ONE block after the whole main tree walk, and even a real tree node for an opened log entry (`node.zipId`) sorted wherever it happened to land in `state.rootIds` — generally "whenever it was opened" — rather than its zip's own alphabetical listing position, since the main walk never excluded `node.zipId` nodes the way `renderTree`'s own walk already does (they render only inside their zip's `renderZipSection`). Fixed by excluding `node.zipId` nodes from the main walk and instead walking each zip's `zip.entries` in the exact order/lookup `renderZipSection` itself uses — real open node (with its children) or virtual nav id, interleaved at its true visual position — so Alt+Up/Down now matches the rendered top-to-bottom order exactly, including mixed log/non-log listings, regardless of open order. (2) **Ctrl+C copied the wrong thing**: the pre-existing global Ctrl+C `keydown` handler (`copyLogSelectionToClipboard`) fires whenever `state.focusRegion === "entries" && state.selectedId` — still true while an inline viewer is open and showing something else, since opening one deliberately leaves that state untouched — and it already had ONE precedence check for a real text selection (the Entry Detail panel), but not for a selection inside `#inlineTextViewer`; since the handler runs on `keydown` and calls `preventDefault()` itself, it pre-empted the inline viewer's own `copy`-event listener entirely rather than merely racing it. Fixed by extending the existing `sel.anchorNode` containment check to also cover `inlineTextViewerEl`. (3) **Leading whitespace dropped + drag-like feel near a selection**: both traced to the same cause — browsers natively make text inside an ACTIVE selection draggable (the same gesture that lets selected text be dragged into another input), with zero app code opting in; clicking/dragging at or near an existing selection in the viewer was being hijacked into that native drag instead of a plain re-select, and since a hijacked drag never produces a fresh `Range`, the subsequent Ctrl+C copied whatever selection pre-dated the drag (typically not starting at column 0), silently losing the line's leading whitespace. Offset computation itself (`itvContentOffset`, the `copy` handler) was verified correct for every DOM boundary shape a real selection can produce — the bug was upstream of it, in the selection never being replaced. Fixed with one `dragstart` listener on `#inlineTextViewer` that unconditionally calls `preventDefault()`, opting the whole viewer out of the native drag gesture — no other mousedown/mousemove/custom-selection JS exists on the text content area, so click-and-drag now falls straight through to ordinary browser text selection. `docs/persistence-and-sync.md`'s "ZIP sources" section updated. `tests/philogg.regression.test.js` **Group 199**: new **199q** (a 3-entry zip — image/text/log, opened out of alphabetical order — ends up in Alt+Up/Down order matching the alphabetical render order), **199r** (Ctrl+C with a background-selected log row AND a genuine inline-viewer text selection leaves the global handler un-prevented), **199s** (a copy starting exactly at column 0 preserves leading whitespace; `dragstart` on the viewer is prevented); **199o** updated for the corrected cross-zip nav order.

(2) **Multi-line copy, rewritten from scratch**: re-investigating from the actual current DOM structure (not the prior fix's assumptions) found the real root cause all three earlier attempts missed — `itvLineElFor(node)` resolved a selection boundary's line via `node.closest(".itv-line")`, which returns `null` whenever the boundary's container is `#inlineTextViewer` itself rather than something nested under a specific line. That's exactly what a real drag reports when it starts before the first line's text or ends past the last line — "select all lines from the very start," the person's own description — so the `copy` handler silently bailed out and let the browser's own inconsistent block-serialization copy through, the very behavior it existed to prevent. Rewritten to find every touched line directly from the `Range` via `Array.from(...).filter(lineEl => range.intersectsNode(lineEl))`, with no dependency on what either boundary's container node actually is; only the first/last touched line need a partial-offset lookup (`itvContentOffset`, now clamped to each line's own length), every line strictly in between is taken whole from the source text. `itvLineElFor` is deleted. `docs/persistence-and-sync.md`'s "ZIP sources" section updated. `tests/philogg.regression.test.js` **Group 199**: new **199w** (Entry Detail + its resizer hide once a non-log entry is active) and **199x** (a container-level start-and-end boundary copies the whole file; a container-level end boundary alone still captures one full line; a normal cross-line selection with no container-level boundary still works).

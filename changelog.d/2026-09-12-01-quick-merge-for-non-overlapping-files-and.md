- **Quick merge for non-overlapping files, and a head/tail-only file time-range probe** (this session, 2026-09-12, person-requested feasibility follow-up). Investigating a person-reported "merge takes a few seconds for ~100MB files" observation found the actual bottleneck: `loadFileDescriptors` reads/parses each file exactly once regardless of the merge choice, so the separate merge progress bar people see afterward measures `mergeFiles`' own copy+sort step (chunked reference-copy across `MERGE_CHUNK_ENTRIES`, then `entries.sort`) — genuinely expensive at large entry counts, not a re-parse. `mergeFiles` now checks whether all sources' time ranges are pairwise disjoint (`fileEntryTimeRange`, a linear min/max scan per source, cheap next to a sort) and, if so, skips the chunked copy-with-yield and the sort entirely in favor of a plain `concat()` in chronological source order — already sorted by construction. Any overlap, including sources sharing an exact boundary timestamp, still uses the original copy+sort path unchanged. Also adds `probeFileTimeRange(file, formatId)`: reads a small head chunk and a growing tail chunk (via `getCompiledFormat`, so custom log formats are respected, not just the default) to learn a file's first/last timestamp without loading or parsing it in full — near-constant cost regardless of file size.

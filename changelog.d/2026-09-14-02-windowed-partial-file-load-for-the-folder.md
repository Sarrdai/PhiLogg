- **Windowed/partial file load for the folder-watch minimap's dragged-window Load** (this session, 2026-09-14, person-requested feasibility follow-up: does reading only the drawn time window, instead of the whole file, actually save load time for a large file?). Answer: yes, for a large file — the drawn window doesn't need the file parsed from the front to find where it starts. `findWindowStartOffset(file, formatId, targetTs)` binary-searches for (approximately) the byte offset where a target timestamp starts, via `probeTsAtOffset` (small growing chunks, the same trick `probeFileTimeRange`'s own head/tail read uses) — `O(log(file size))` small reads instead of a full sequential scan. `parseFileWindow(file, node, from, to, onProgress)` then reads/parses forward from that offset only until an entry's timestamp passes `to`, never running to EOF. Both assume the file is chronologically sorted start to end (the same assumption `mergeFiles`' quick-merge and live tailing already make elsewhere) — `findWindowStartOffset` reuses `probeFileTimeRange`'s own head+tail probe as a cheap global bookend sanity check (if the file's first entry's timestamp is already after its last entry's, it's definitely not sorted as assumed) before ever bisecting, plus a lighter in-loop monotonicity check; either one failing returns `consistent: false`. `loadFolderFileWindowed(folder, rec, from, to)` wires this into `loadFolderMinimapSelection`'s dragged-window Load path (in place of the previous full `loadFolderFile` per overlapping file), falling back to a normal full load when the file is already open (its entries already cover any window), below a `WINDOWED_LOAD_MIN_FILE_SIZE` (8MB — the bisection overhead only pays off on genuinely large files), its time range isn't known yet, or `parseFileWindow` reports the file isn't safely sorted. A node loaded this way is tagged `node.partial = { from, to }` — threaded through `snapshotSubtree`/`restoreSubtree` (undo) and `persistFileNode`/`restoreSessionFromCache` (reload) the same way `node.merged`/`node.formatId` already are, and gets its own tree-row badge (`ICON_FILE_PARTIAL`, a circled "P") plus a tooltip naming the window that was actually read; a merge of two partial sources gets the union of both windows as its own `node.partial`. Individually-picking bars (no dragged window) is unaffected — that path still always does a full load, since no window was drawn to skip past. `tests/philogg.regression.test.js` **Group 205**: `findWindowStartOffset`/`parseFileWindow` directly on a sorted fixture — correctness (only the requested window's entries) and the actual performance claim itself, via an instrumented `.slice()` byte counter showing a narrow window reads a small fraction of the file; the size/range fallback thresholds; a large file above the threshold gets only its window read and is flagged partial, with an already-open file never re-read; a file that isn't actually chronologically sorted falls back to a full load instead of silently returning wrong/missing entries; `node.partial` surviving a close+undo round trip; and `loadFolderMinimapSelection`'s merge of two windowed sources unioning their ranges.

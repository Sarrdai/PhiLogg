- **Bugfix: the viewBar toolbar's "Message"/"Extract" buttons ignored a selected Link-view pair** (this session, 2026-09-14, person-reported: "I select a message in the Link view — both parts of the link are shown selected — but clicking the 'Extract' filter button only extracts values from one of the two messages in the tuple"). Root cause: selecting a pair block in the Link view (a plain click — see Group 168) only ever sets `linkSelectedPairIndex`, never `state.selectedId`. `singleMessageActionEntry()` — the function behind the toolbar's "Message"/"Extract" row-action buttons (`handleRowActionClick`'s `filterForMessage`/`extractMessage` cases) — resolved its target purely via `currentRowActionEntry()` (`state.selectedId`), so whatever single real entry a *prior* row double-click had left there (not necessarily even part of the currently selected pair) got wildcarded instead of the whole tuple. Alt+Enter and the brace's own right-click → "Filter for this message" already special-cased the Link view's pair selection for exactly this reason (Group 168), but the toolbar buttons — added later, in the viewBar row-action reorg — were never taught the same rule. Fixed by giving `singleMessageActionEntry()` the identical Link-view pair check: when the Link view is on screen and a pair is selected, it now returns `linkPairsData[linkSelectedPairIndex].pair` (the same combined-message pair object the brace path already used) instead of falling through to the stale single-entry selection. The person's separate follow-up report — getting "stuck" on the Plot view (or once, a Filtered view of an already-deleted filter) unable to switch away via the tree or the View Toggle — could **not** be independently reproduced: extensive testing of extraction-on-a-link (both the buggy one-sided pattern and a correct full-pair pattern), Table/Plot rendering of pair entries, switching the active node away from Plot via both direct state mutation and real DOM clicks, and deleting the active node while its Plot was showing, all self-healed correctly in the current code (`renderMainView()`'s own `!extractCapable` fallback forces `fhActiveTab` back to `"filter"` the moment a non-extraction node becomes active). If it recurs after this fix, it likely needs a more exact repro. `tests/philogg.regression.test.js` **Group 213**: the Extract button's pattern covers both sides of the tuple (not the stale single entry) with a stale `state.selectedId` present; "Filter for this message" gets the same fix; a regression guard that a real full-pair extraction viewed on Plot still lets a tree click switch away and fall back to Filtered.

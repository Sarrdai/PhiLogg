- **Windows Explorer context-menu integration (desktop wrapper, Windows-only)** (this session, 2026-09-15, person-requested). Three new right-click entries, added by the Windows installer as an *optional* component (a checkbox on its own installer page) and cleanly removed on uninstall regardless of whether it was ever ticked: **"Open in PhiLogg"** on a single `.log` or `.zip` file, and **"Watch this Folder"** on a folder. Multi-selecting several `.log` files and merging them from Explorer was considered and deliberately dropped — Windows can't hand multiple selected paths to one process launch through a plain registry verb (that needs a full COM shell-extension DLL, a disproportionate maintenance cost here); each verb instead just relies on Explorer's normal per-item launch behavior, which degrades acceptably on its own for a multi-selection (see `docs/desktop.md`). Two Rust changes make this work: `windows.rs`'s `file_arg` became `classify_launch`, which now also recognizes a `.zip` path or a directory (not just `.log`) and returns which of two routes to take — `LogFile` reuses the existing, unchanged `open_file`/`philoggLoadUrl` single-URL route (that route has no ZIP awareness, so it stays `.log`-only), while the new `LocalTarget` goes through a new `open_local`, which registers the file(s)/folder(s) and calls `window.philoggLoadLocalFiles` — the same call drag-drop already makes, so a `.zip` opens via its existing zip special-case and a folder starts a watch exactly like a dropped one. A cold launch (no window yet) can't `eval()` into a page that hasn't loaded, so `open_local` stashes the payload in a new `AppState.pending_local_load` and a new `windows::flush_pending_local` (called from `commands::app_ready`, the same "first paint" signal that already dismisses the splash) runs it once the page is actually ready. On the installer side: Tauri's NSIS `installerHooks` only inject code at four fixed points *inside* the existing single install section — none of them can add a whole new wizard page — so getting a real checkbox meant forking the generated `installer.nsi` itself (`desktop/src-tauri/windows/installer.nsi`, pulled from `@tauri-apps/cli` `2.11.4`, the version `desktop/package-lock.json` resolves to) via `tauri.conf.json`'s `bundle.windows.nsis.template`, adding a `MUI_PAGE_COMPONENTS` page and one new optional `Section`, with the three previously-unnamed core sections renamed with a leading `-` (NSIS's "hidden section" convention) so they don't also show up as separate, individually-uncheckable rows. The verbs register under `HKCU\Software\Classes\SystemFileAssociations\<ext>\shell\...` and `HKCU\Software\Classes\Directory\shell\...` (not a new ProgID), so they add a menu entry without disturbing whichever app is currently the default `.log`/`.zip` handler. Not covered by the jsdom suite (Rust/NSIS/Tauri-config only, per `CLAUDE.md`'s carve-out) — verified by `cargo check` and `cd desktop && npm run build`; installing/uninstalling the built installer to confirm the registry keys appear and disappear still needs a person on a real Windows machine. See `docs/desktop.md` → "Windows Explorer context-menu integration".

- **feat: give the Files & Filters sidebar its own selection-dependent toolbar** (this session, 2026-09-15, implements `FEATURE_BACKLOG.md` #77; revised in place the same session, before ever shipping, per project-owner review — this entry describes the FINAL shape directly). New `#sidebarToolbar`, sitting between `#sidebarHeader` and the scrollable `#sidebarScroll` (always visible once a file is loaded, never scrolled away with the tree), uses the same icon+hover-label button concept as `#viewBar`/the per-view toolbars — the **"rect"** shape specifically (the per-view toolbars' own look, not `#viewBar`'s pill/circle), so it also follows the "View Toolbar button labels" Settings toggle. Its button SET tracks the current tree selection via `describeSidebarToolbarActions()`, grouped into **at most two `|`-separated groups** — "what this node itself looks like" then "library": **1 file** → Adjust clock… (omitted for a merged/empty file) `|` Apply from library…; **2+ files** → Merge `|` Apply from library… (falls back to `state.activeId`, no single node to target); **1 unlocked filter** → Rename…, Edit filter… (per-filterType), Invert (NOT) `|` Add to library…, Apply from library… (both target that specific node); **1 filter, the locked "Bookmarks" node** → nothing in group 1 (Copy is gone from the toolbar, see below) — just Apply from library…, disabled; **2+ filters, same root** → Combine (AND), OR, Link… only, no library group; **different roots / mixed** → the existing explanatory note, zero actions; **0 selected** → Apply from library… only (`state.activeId` fallback). `handleSidebarToolbarActionClick(action)` dispatches every click into the pre-existing function each action already had — zero duplicated business logic. **`copy`/`cut`/`saveFilter`/`loadFilter` are removed from the toolbar entirely, for every selection shape** — unaffected on the tree's right-click menu. **`context`/`countContext` (Time context…/Count context…) are removed from the toolbar AND from the right-click menu** (`openTreeContextMenu`'s edit bucket no longer pushes them) — there is now no user-facing way to CREATE a fresh context/countContext node at all (`FEATURE_BACKLOG.md` #79 has the reasoning + a planned replacement); existing nodes of either type — from an old session, a saved filter file, or a library preset — are completely unaffected, since only the two creation menu items were touched (`openContextDialog`/`openCountContextDialog`, the dialogs, and every `context`/`countContext` branch in `getEntries`/rendering/every persistence carrier stay fully intact, just unreferenced by any button for now). **New `addToLibrary` action + the pre-existing `applyFromLibrary` replace `#viewBar`'s dedicated `#btnAddToLibrary`/`#btnOpenLibrary` buttons** (`#libraryManageBar`, removed outright from `#viewBar`'s markup/CSS/JS) — same dialogs (`openFilterLibrarySaveDialog`/`openFilterLibraryDialog`)/icons (`ICON_DISK`/`ICON_BOOK`), now targeting the *specific selected node* instead of always `state.activeId`; `#libraryPresetBar` (pinned preset pills) is untouched. **AND/OR/Link… stay EXCLUSIVE to this toolbar** (person-confirmed, unchanged from the initial pass): removed from the old always-visible `#treeActionBar`/`renderTreeActionBar` (retired outright, its Merge case folded into this toolbar's own "2+ files" case) and from `openTreeContextMenu`'s own 2+ multi-select bulk-action rendering (Merge stays there, unaffected). **`setupHitExpandGroups` re-bind gotcha**: every pre-existing caller renders its buttons once at boot; this toolbar rebuilds its whole button set on every render and must call it again each time, which would otherwise attach a stacking, duplicate `mousemove`/`mouseleave` listener onto the same container — fixed with a small idempotency guard (`container.dataset.hitExpandBound`) plus switching the listener to re-query the container's current children on every event instead of closing over a bind-time snapshot. **Edge-of-viewport label clamping** (project-owner review): `#sidebarToolbar` sits at the app's LEFT edge, so the shared `.row-action-label` floating-pill mechanic (centered via `translateX(-50%)`, no bounds checking) could clip a nearby button's label past the browser window's edge — fixed generically inside `setupHitExpandGroups` itself (not a sidebar-specific hack, since `#viewBar`/the per-view toolbars share the same mechanic and could in principle hit the same problem near their own edges): a new pure `clampLabelOffset(rect, viewportWidth)` measures the label's own rendered `getBoundingClientRect()` against `window.innerWidth`/0 and returns the extra px to shift it back on-screen (added to the existing `translateX(-50%)` via an inline `transform` override, cleared on collapse so it never leaks into the next hover). `tests/philogg.regression.test.js` **Group 220** (`describeSidebarToolbarActions`/`handleSidebarToolbarActionClick` across every selection shape, including a dedicated absence guard for the six removed actions) and **Group 221** (toolbar visibility, the `setupHitExpandGroups` re-bind guard, AND/OR/Link's removal from the tree context menu, and `clampLabelOffset` unit-tested directly — the real `getBoundingClientRect()`/`window.innerWidth` measuring stays untested under jsdom, no layout engine); Groups 59/60/193/194 updated in place for the library-button relocation and the context/countContext menu removal; Group 182c's `#treeActionBar` PiP-hide-list entry dropped (element retired).

- **feat: entries-based (line-count) binning for the timeline minimap, as an alternative to the existing time-based layout** (this session, 2026-09-16, implements `FEATURE_BACKLOG.md` #2, person-approved design — an earlier draft of this same idea wasn't liked and was shelved pending a better approach; this session's design was worked out and confirmed with the project owner before implementation). **Problem**: the minimap's bars have always been positioned by proportion of the file's *timestamp span* — a burst of fast activity (many entries in a tight time window) compresses into a handful of pixels, while a quiet/idle stretch (few entries over a long wall-clock gap) silently eats most of the width, even though it's the least interesting part of the file. **New Settings → Timeline minimap → "Minimap binning"** select (`time` | `entries`, default `time`, `philogg-minimap-binning-mode`) switches a bar's x-position from "proportional to timestamp within the file's time span" to "proportional to entry INDEX among the root file's entries" instead — bursts now spread out evenly across the width, and idle stretches stop dominating it. **Scope, confirmed explicitly by the project owner: visualization only.** Every interaction — click-to-jump, drag-select (→ a `"timerange"` filter), the right-click time-range dialog, the two range-indicator rectangles, the hover tooltip, the selection marker — needed **zero changes of its own**, because none of them contain their own notion of "where in time/space is this pixel"; they all already routed through three low-level conversion functions, which are now the ONLY place `minimapBinningMode` is ever branched on: `minimapTsToX(ts)`/`minimapXToTs(x)` (the position pair) and the newly-factored-out `minimapBucketOf(ts)` (which bucket/bar a timestamp falls into — previously inlined separately inside `minimapBarSpan` and the render pass's own local `bucketOf` closure, now a single shared function both call, so they can never disagree with each other or with the new mode). In `"entries"` mode, `minimapXToTs` resolves a clicked/dragged pixel to the **real timestamp of the actual entry** at that index (`minimapRootEntries[idx].ts`, binary-searched via the same `lowerBoundByTs` helper used everywhere else in the file for a chronological array) rather than an interpolated point in time — this is precisely why every existing caller above the conversion layer kept working unchanged: they already handled "some entry's real ts" correctly, and now just get a more exact one instead of an approximation. `renderTimelineMinimap`'s own `bgCounts`/`ovCounts` bucketing passes got the same mode branch, but inline their own index-based formula (array position for the whole-root-file pass, `buildOrderIndexMap(rootId)` — already memoized per file — for the filtered `viewEntries` pass, since a `viewEntries` entry's array index is "Nth match", not "Nth line in the file") rather than calling `minimapBucketOf` per entry: that function's `"entries"` branch does a binary search per call, the right cost for the O(1)-ish click/hover/drag handlers, but calling it inside this O(file size) render pass — which runs on every node/filter switch, level toggle, and tail tick — would have turned it into O(file size · log file size). Both still compute the exact same formula, so the hot path and the interaction layer can never disagree on which bucket a ts belongs to. The hover tooltip's `mousemove` listener, which used to re-derive the time-proportion formula by hand (`minimapTMin + (b / bucketCount) * (minimapTMax - minimapTMin)`) instead of calling the shared functions, was rewritten to route through `minimapXToTs`/`minimapBucketOf` too — that duplication would otherwise have silently stayed correct only in time mode. **Expected side-effect of `"entries"` mode, not a bug**: the grey BACKGROUND density bars render essentially flat/uniform, since every bucket now covers the same fixed slice of the file's line count by construction rather than a data-dependent slice of wall-clock time — informative time-based background density, by design, has nothing left to vary. The value in this mode is entirely in the colored overlay bars, which still show where in the file's line order the current filtered/leveled result concentrates. `minimapBinningMode` is a plain `localStorage` UI preference (same tier as `hideMinimapFullRangeInFullView`/`contextExpandStep`), **not** a filter-node field, so no persistence-carrier threading was needed (`cloneSubtree`/`snapshotSubtree`/`serializeFilterBranch`/session-cache — see `CLAUDE.md`'s "Known gotchas"). `tests/philogg.regression.test.js` new **Group 226**: the Settings select's persistence to `localStorage` and re-hydration on (re-)init; an irregular-gap fixture (a 20-entry burst one millisecond apart, then a 20-minute idle gap, then 19 more entries a second apart) proving `minimapTsToX` resolves the post-gap entry's x by time-proportion (~98%, dominated by the idle gap) in time mode and by index-proportion (~51%, entry 20 of 39) in entries mode — a visibly different x for the exact same entry — and that the actual rendered SVG bar for a lone matched entry lands at the same index-proportional bucket `minimapBucketOf` computes; and that click-to-jump, drag-select (→ a `"timerange"` filter built from two real entries' own timestamps), and the hover tooltip all still resolve correctly with entries mode active. Every existing minimap group (31/32/34/95/119/120/197/...) keeps passing unchanged, since `"time"` stays the default. See `docs/filters.md` → "Timeline minimap: bars, range indicators, selection markers" for the full mechanism. Full suite: **4701 passed, 0 failed**.

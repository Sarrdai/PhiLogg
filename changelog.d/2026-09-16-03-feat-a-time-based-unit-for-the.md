- **feat: a TIME-based unit for the Context view's existing "expansion step" (`FEATURE_BACKLOG.md` #79, scope narrowed by the project owner)** (this session, 2026-09-16). `FEATURE_BACKLOG.md` #79's own raw text sketched a much broader, unresolved idea — making the whole Context view's visible window itself configurable, as a lighter alternative to the `context`/`countContext` filter-node types. Asked to resolve that entry's own open question, the project owner gave a concrete, narrower answer instead: **not** a new view-level window concept, but a unit toggle on the mechanism the Context view already has — "Lines revealed per step" (`contextExpandStep`, see `docs/ui-and-views.md` → "Revealing a step at a time"), which governs both a "Show more (+n)" click's own reveal size and the width of the auto-expansion window around a jump (`applyContextJumpExpansion`'s `"aroundJump"` mode). That mechanism has always measured a step in a fixed ENTRY COUNT; this session adds **Settings → Behavior → "Expand step counts in"** (`contextExpandStepUnit`, `philogg-context-expand-step-unit`, `"entries"` **default**, preserving today's behavior for anyone who never touches the new setting, | `"time"`), which switches it to a fixed TIME SPAN instead — **"Timespan revealed per step (ms)"** (`contextExpandStepMs`, `philogg-context-expand-step-ms`, default **500**, clamped to a minimum of 1 with no upper cap, same as the Time-context-filter dialog's own ms fields). In time mode, a "Show more" click reveals however many entries fall within the configured span from whichever edge it sits against — a genuinely **variable** entry count, since how many lines a fixed timespan covers depends entirely on how dense the log is at that edge — and its own label/tooltip read the fixed configured *duration* ("Show more (+500ms)", via the existing `formatMs` helper) rather than that variable count, which would promise a precision the setting doesn't actually offer. `buildContextView`'s `addHidden` computes a time-mode step's two candidate boundaries via `lowerBoundByTs`/`upperBoundByTs` — the same binary-search helpers the minimap and the Time-context filter already use — clamped so a step always reveals **at least one entry** and never crosses into rows a different run already owns; whether the step row is shown at all is derived from those same two boundaries (would this step reveal the ENTIRE remainder anyway?) rather than a separately-computed check, so the two can never disagree at an edge. The **"… N lines" filler is deliberately unchanged in both modes** — per the project owner's explicit instruction ("if less than that is available just the '...n line' as by now") it always reports a plain entry count, since it reveals the whole remaining stretch regardless of how that stretch's edges were measured. The **entries-mode path is untouched**: `addHidden`'s `"entries"` branch and `applyContextJumpExpansion`'s `lo = idx - contextExpandStep; hi = idx + contextExpandStep + 1;` are exactly the pre-existing logic, gated behind `contextExpandStepUnit !== "time"`. Both new values are plain `localStorage` UI preferences, same tier as `contextExpandStep` itself — **not** filter-node fields, so no persistence-carrier threading was needed (`cloneSubtree`/`snapshotSubtree`/`serializeFilterBranch`/session-cache — see `CLAUDE.md`'s "Known gotchas"). `tests/philogg.regression.test.js` new **Group 227**: the Settings unit select's two dependent step-width rows (each needing its own scoped `.hidden{display:none}` CSS rule — this codebase has no generic one) show/hide and persist correctly in both directions, including re-hydration from `localStorage`; the ms field's Dec/Inc/typed-value/clamp behavior, mirroring the existing entries-step field's own coverage; and, via a 71-entry fixture with a sparse stretch on one side of a jump target and a dense one on the other, that the SAME configured 500ms step reveals a starkly different entry count on each side (1 vs. 50) — the whole point of time mode — plus the "reveal at least one entry" clamp, a step correctly withheld when it would reveal everything left, and that `applyContextJumpExpansion`'s `contextAutoRanges` take-back-the-previous-jump mechanism (Group 138o) still leaves a hand-revealed range in a different gap untouched. `docs/ui-and-views.md` → "Context view (Context/Filtered split)" extended in place ("Revealing a step at a time", "Jumping in still works exactly as before").

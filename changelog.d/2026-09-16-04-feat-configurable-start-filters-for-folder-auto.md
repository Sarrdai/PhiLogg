- **feat: configurable "start filters" for folder auto-open, several selectable with one Primary (`FEATURE_BACKLOG.md` #71)** (this session, 2026-09-16). A watched folder's per-pattern rules (`docs/persistence-and-sync.md`'s "Per-folder settings", `defaultFolderPattern`/`applyFolderAutoRules`) already decide WHICH file a pattern opens on its own — "Auto-open newest file", "Auto-close — keep only N open". This session adds a fourth per-pattern setting, **"Start filters"**, that decides what happens right after: a checkbox list in the folder watch settings dialog (`#fwPatternList`, `fwPatternStartFiltersBlock`) lets a pattern reference any number of saved **Filter Library** presets (the existing named, file-agnostic filter presets from `saveFilterToLibrary`/`listFilterLibrary` — see the "Filter library" section) to apply automatically the moment that pattern's own auto-open/auto-close rule opens a file, with one of the checked presets marked **Primary** (a same-`name`-grouped native radio per pattern card, disabled until its own checkbox is checked) — person-requested, so opening a file that gets several filters applied at once still lands the person's view on one specific filter of their choosing instead of an arbitrary one. Person-requested framing throughout: the Filter Library, not a fresh ad-hoc filter editor, is the source for this selection — reusing it means no new storage tier and no new "apply" mechanism, just `applyFilterFromLibrary` invoked once per selected key, one step earlier in the same flow the right-click "Apply from library…" action already uses, so every filter re-evaluates against the newly opened file's own entries exactly like every other library application. A pattern's `startFilterKeys` (`[]` by default) are looked up and applied inside `loadFolderFile`'s existing `auto` branch (new helper `applyFolderStartFilter`), so they fire only for a file THIS RULE opened — never for one a person opens by double-click/context-menu, mirroring the "person vs. auto" distinction `rec.openedByAuto`/`rec.autoOpenFired` already draw for auto-close; `startPrimaryFilterKey` (`null` by default) is applied LAST among them, so its own `applyFilterFromLibrary` call is what actually sets `state.activeId`/reveals the view. The dialog keeps the invariant "a non-empty selection always has exactly one Primary" on its own — checking a pattern's first preset auto-picks it as Primary, unchecking the current Primary auto-promotes another still-checked preset — so there's no separate "no Primary chosen" state to stumble into by hand. Both fields travel with the rest of `folder.settings` through the existing `persistFolder`/`restoreWatchedFolders` round trip, so no new persistence carrier was needed. The folder watch settings dialog has always opened and rendered its pattern cards synchronously (no `await` between the gear click and the cards appearing), so the new checkbox list can't read the library through the always-async `listFilterLibrary()` directly without reopening that gap; it reads a new in-memory mirror instead, `filterLibraryCache`, refreshed by `refreshFilterLibraryCache()` at boot and inside all three library mutators (`saveFilterToLibrary`/`updateFilterLibraryEntry`/`deleteFilterLibraryEntry`). See `docs/persistence-and-sync.md` → "Per-folder settings"/"Storage" for both; `tests/philogg.regression.test.js` GROUP 228 covers the checkbox list, the auto-managed Primary invariant, applying several filters onto an auto-opened file with the Primary one ending up active, and the auto-vs-manual-open distinction.

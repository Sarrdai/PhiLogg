- **fix: IDE Integration's Visual Studio "Connect" swallowed every failure into the same generic "no instance found," and "Open in Rider" gave no feedback at all** (this session, 2026-09-16, person-reported after the very first real-machine test of the feature above: Visual Studio was running with a solution open and "Connect…" still reported nothing found; enabling Rider and clicking "Open in Rider" on a log row did nothing, no error). This sandbox has no Windows toolchain, so the diagnosis leaned on external research into both failure modes rather than a live repro. **Visual Studio**: `vs_integration.rs`'s PowerShell script never checked the HRESULT either `ole32.dll` P/Invoke call (`GetRunningObjectTable`/`CreateBindCtx`) returned, and any failure anywhere in the script came back as the exact same empty result as "Visual Studio really isn't running" — indistinguishable by design ("never fail outward"), which meant a genuine script bug and a clean "zero found" looked identical to the Settings dialog. Both scripts now wrap their whole body in one top-level `try`/`catch` that checks those HRESULTs explicitly and writes the real exception message to stderr (`exit 1`) instead of letting an unhandled COM/.NET exception produce an opaque result; `list_instances()`'s Tauri command (`vs_list_instances`) now returns `VsListResult { instances, error }` instead of a bare list, and the Settings dialog's "Connect…" handler shows that diagnostic text directly ("No running Visual Studio instance found — &lt;the script's own error&gt;") the next time it comes back empty. Also switched both scripts from retrieving the DTE object via `[Marshal]::BindToMoniker($name)` (a re-parse of the moniker's display-name string) to `$rot.GetObject($m)` on the already-enumerated moniker object directly — the more standard technique per the research done this session, and one fewer thing that can go wrong. **Rider**: re-verified `buildRiderUri`/`openEntryInRider` and the `open_path` bridge — both structurally correct, and (per `tauri-plugin-opener`'s own source) `open_path`/`open_url` delegate to the identical underlying OS-open call on desktop when invoked from Rust directly, so there's no obvious PhiLogg-side bug. Research strongly suggests the actual cause is that the `jetbrains://` URI scheme's registration in Windows is owned by JetBrains Toolbox App's `jetbrainsd` background service rather than a standalone Rider install — not something PhiLogg's own code can fix. Added a success toast ("Opening in Rider…") after `openPath` resolves, so a person can at least tell PhiLogg's own side ran, and documented the Toolbox prerequisite plus a Win+R self-test in `docs/desktop.md`/`desktop/README.md`. **Still unverified against a real Windows machine** (same sandbox limitation as the feature's original session) — see `desktop/README.md` → "Status".

- **fix: Visual Studio "Connect" still failed — PowerShell can't call methods on the raw COM interfaces the Running Object Table walk needs** (this session, 2026-09-16, person-tested: Rider now works after the previous fix, but "Connect" returned the exact PowerShell error `[System.__ComObject] does not contain a method named 'EnumRunning'` — the diagnostic-surfacing work from the earlier session in this same story did exactly its job, handing back a concrete, root-causable error instead of a generic "not found"). The cause: PowerShell's own dynamic (`$obj.Method()`) dispatch on a COM object only works for Automation/`IDispatch`-compatible interfaces; `IRunningObjectTable`, `IBindCtx`, `IEnumMoniker`, and `IMoniker` are plain vtable-only interfaces with no `IDispatch` support at all, so `$rot.EnumRunning()`/`$rot.GetObject($m)` (the latter added by the previous session's own hardening pass, believing it more standard/robust than `[Marshal]::BindToMoniker`) could never work from PowerShell script text, regardless of how correctly the P/Invoke signatures were declared — a COM object without a registered interop class reports its runtime type as the generic `System.__ComObject` to PowerShell's reflection-based method lookup, which then has no `IDispatch.Invoke` to fall back to. This is a PowerShell-specific limitation that doesn't affect compiled C# (where `.EnumRunning()` resolves at compile time against the *declared* interface type and never needs reflection) — every reference example for this technique found via research is C#, and none of it warned that it wouldn't translate 1:1 into a PowerShell script. Fixed in `desktop/src-tauri/src/vs_integration.rs` by moving the entire ROT walk (`GetRunningObjectTable`/`CreateBindCtx`/`EnumRunning`/`Next`/`GetDisplayName`) into a new static method on the embedded, compile-time-typed C# class (`ListVsMonikers()`), which returns only plain moniker **strings** — the one thing PowerShell can safely receive back from it. PowerShell then binds each moniker via `[Marshal]::BindToMoniker` (a plain static .NET method, not a COM call — this part was fine all along, and is exactly what the *original* version of this script did before the previous session "corrected" it to `GetObject`) and reads `Solution.FullName`/`MainWindow.Caption` off the resulting `EnvDTE.DTE`, which is itself Automation/`IDispatch`-compatible by design and works fine from PowerShell. `open_file`'s script no longer needs to re-enumerate the ROT at all (the moniker string is already known), removing the shared `ROT_SETUP` fragment and its duplication between the two scripts entirely. `docs/desktop.md` → "IDE Integration" updated in place to describe the corrected split and explain why it's necessary. No test changes: this is Windows/PowerShell-only, outside jsdom's reach. Full suite: **4806 passed, 0 failed** (unchanged — no JS touched).

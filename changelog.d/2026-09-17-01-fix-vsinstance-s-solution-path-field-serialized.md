- **fix: `VsInstance`'s `solution_path` field serialized as `solution_path`, not `solutionPath` — the Settings dialog always read `undefined` and showed "no solution open" no matter what the PowerShell/COM side actually found** (this session, 2026-09-17, person-tested: after every PowerShell/COM fix in this story checked out — confirmed via three separate standalone-script reproductions, including one byte-for-byte matching the app's exact `-EncodedCommand`/`-NonInteractive`/`CreateNoWindow` invocation, and even a 32-bit-vs-64-bit-process theory ruled out by checking Task Manager — "Connect" in the real app still showed "(no solution open)" for an instance whose solution the standalone script printed correctly. Every one of those tests exercised the PowerShell/C# side in isolation; none of them ever went through the actual Rust struct that gets serialized back to the page, which is exactly where the bug was hiding.). `VsInstance`'s `solution_path` field had no `#[serde(rename)]` (unlike the intermediate `RawInstance` used to *parse* PowerShell's own JSON, which already had `#[serde(rename = "solutionPath")]` for the same reason) — so Tauri serialized it to the page as `{"solution_path": "..."}`, and `philogg.html`'s `inst.solutionPath` read was always `undefined`, always falsy, always "(no solution open)" regardless of what PowerShell actually reported. One-line fix: `#[serde(rename = "solutionPath")]` on `VsInstance.solution_path`, matching `RawInstance`'s own convention. A good reminder that a bug can survive extensive testing of everything **except** the exact boundary it's actually sitting on.

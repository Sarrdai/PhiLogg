- **feat: "Sources" is now a real tree-level sibling of Bookmarks/Notes/Selection N (not an extra nesting level), a new "Show Sources" setting, and every merge-into-path now creates the merge first and loads sources into it without ever deleting them (this session, 2026-09-18, person-requested follow-up correcting the previous session's design)**. Three corrections to the "Sources" feature shipped last session (below): **(1) Tree structure.** "Sources" was a purely presentational group (`renderSourcesGroup`/`renderSourceRow`), not a real `state.nodes` entry, reading as an extra indentation level under a merged file instead of sitting where Bookmarks/Notes/Selection N already live. It's now a real, locked `filterType:"sources"` node created once per merge (`createMergeShell`), positioned via a new shared ordering helper — `specialChildRank`/`insertSpecialChild` (`philogg.html`, near `syncBookmarksFilterNode`) — that replaces what used to be four independent, ad hoc `unshift`/splice calls (`syncBookmarksFilterNode`, `syncNotesFilterNode`, `createSelectionFilterNode`, and now `createMergeShell`'s own Sources node) with one rank-based rule (Sources=0, Bookmarks=1, Notes=2, Selection N=3+its own creation ordinal, captured as `node.selectionOrdinal` so a later rename can't disturb sort order). A file's auto-managed rows now always read **Sources, Bookmarks, Notes, Selection 1, Selection 2, ...** regardless of creation order — previously, a second Selection node even unshifted itself *above* an existing Bookmarks/Notes node. The Sources node's own `children` stays empty (file nodes must stay root-level, per this app's own data-model invariant — they can never be reparented under a filter node); nesting is driven by the owning file's `sources` array plus each source's real file node, rendered a *second* time via the ordinary `renderNode(src.id, depth+1, {mergeSourceColor:src})` — reusing the exact same "real root node, rendered nested, skipped from the plain top-level walk" pattern the ZIP/folder-watch containers already use (new `mergeOwnerId`/`mergeSourceHidden` tags on a source file node, mirroring the existing `zipId`/`folderId` tags; `renderTree`/`renderFolderSection`/`flattenTreeIds` all gained the matching skip). The per-source color swatch moved onto that nested file row (a new `opts.mergeSourceColor` branch in `renderNode`'s existing swatch block) instead of a bespoke row type; `getEntries` on a Sources node is a pure passthrough of its parent's own result; it's excluded from the filter-tree persistence carriers exactly like Bookmarks/Notes. **(2) New Settings → Behavior → Filter tree toggle, "Show Sources"** (default **on**, `philogg-show-sources` in `localStorage`, `showSourcesSetting`) — a pure display toggle (`renderNode` simply skips rendering the node when it's off; the underlying `sources`/`mergeOwnerId` data is never touched), same `pill-toggle` shape every other Behavior-tab boolean uses. **(3) Create-merge-first loading.** Previously every "load files straight into a merge" path (meta-format split, drag-drop-then-"Merge" confirm, folder-watch's "Merge (full)"/"Merge (window)") loaded every source to completion *first* — visibly, as separate top-level rows, and for the meta-format case those virtual per-grammar files were then *deleted* once merged. `mergeFiles` (`philogg.html:9478`) is now split into `createMergeShell(name, formatId)` (builds the empty merge node + its locked Sources child, inserted into the tree immediately, before any source is even read) and `fillMergedEntries(node, files)` (the actual entries copy/sort, unchanged in substance, just now filling a node that may already have existed and been visible for a while); `mergeFiles` itself becomes a thin "sources already loaded" wrapper calling both back to back, used unchanged by the pre-existing manual "Merge N files" bulk action. `loadMetaFormatText`, `loadFileDescriptors`' merge-on-load path, and `folderMinimapMergeFull`/`folderMinimapMergeWindow` now all call `createMergeShell` first, then load each source into a `mergeOwnerId`/`mergeSourceHidden`-tagged node — pre-tagged before its own read starts where a placeholder exists to pre-tag through (`loadFileDescriptors`/`loadMetaFormatText` reuse `addFile`/`loadOneFileIntoTree`'s existing `existingNode` parameter and `createQueuedFileNode`), or tagged right after that source's own load finishes where it doesn't (folder-watch's `loadFolderFile`/`loadFolderFileWindowed` own their own node creation — an accepted, brief visibility gap rather than a larger refactor) — before finally calling `fillMergedEntries` once every source is done. **Meta-format vnodes are never deleted any more** — reversing last session's own design, they stay real, independently clickable, filterable file nodes for as long as the merge exists, reachable under "Sources". If fewer than 2 sources end up loading successfully, the shell is discarded and any lone survivor is un-tagged back to a normal, visible file. While "Show Sources" is off, a loading create-first merge's own row shows a combined **`(n+1)`-segment progress bar** instead (`node.loadSegmentSourceIds`, new `.tree-load-segments`/`.tree-load-fill-segment` CSS, `updateMergeSegmentedProgress` hooked into the existing `scheduleLoadRender` per-tick path) — one segment per source plus one for the final copy/sort step; with Sources shown, the merge row carries no bar of its own during the loading phase (each nested source's own row already shows its own ordinary single-fill bar, completely unmodified) — the existing `typeof node.loadFraction === "number"` gate already means "no bar" for free in that case, since `fillMergedEntries` is the only thing that ever sets it. `deleteNode` gained a small cleanup (drops a deleted source from its owning merge's `sources` array, wherever it's deleted from — the original top-level row or its own nested row — instead of leaving a stale reference).

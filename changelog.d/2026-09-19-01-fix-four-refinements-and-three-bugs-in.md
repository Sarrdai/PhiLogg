- **fix: four refinements and three bugs in the "Sources"/create-merge-first rework, found by actually using it** (this session, 2026-09-19, person-reported after the previous session's rework shipped). **Refinements**: (1) a nested Sources row (rendered via `opts.mergeSourceColor`) no longer carries its own ✕/middle-click delete — `renderNode`'s delete-button and `auxclick` handlers now also gate on `!(opts && opts.mergeSourceColor)` — only deletable together with its owning merge; a bulk-merge-visible source's own top-level row (no `mergeSourceColor` at that call site) is unaffected and keeps both. (2) `deleteNode` now cascades over a merge's own `node.sources`: a `mergeSourceHidden` source (create-first — no life outside the merge) is deleted right along with it; a bulk-merge-visible (`mergeOwnerId`-only) source instead survives at top level, un-orphaned (`mergeOwnerId`/`mergeSourceHidden` cleared) — previously neither case was handled, leaving hidden sources permanently orphaned (invisible, unreachable, still tagged) forever. (3) Undoing a deleted merge now restores its cascade-deleted hidden sources too: `snapshotSubtree` captures each hidden source's own full snapshot under a new `hiddenSourceSnapshots` field (root-level siblings aren't reached by the normal `children` recursion), `restoreSubtree` recreates them under a transient `hiddenSourceIds`, and `undo()`'s `"deleteFile"` branch splices each restored id back into `state.rootIds` (every file node must live there) and re-persists it. This also surfaced a latent gap: `snapshotSubtree`/`restoreSubtree` never carried a file node's own `mergeOwnerId`/`mergeSourceHidden` tags at all (never needed before, since a hidden source was never independently snapshotted) — now they do, or a restored source came back untagged. (4) `fillMergedEntries` now sets the Sources node's own `collapsed = true` once a merge completes (both the create-first and old bulk "Merge N files" paths funnel through it) — `createMergeShell` still leaves it expanded so per-source progress is visible while loading; only the completion moment changed. **Bugs**: (1) the `(n+1)`-segment combined progress bar on a create-first merge's own row was gated `&& !showSourcesSetting` — with Sources on (the default), a two-file ~100MB drag-drop merge showed **no progress at all** on the merge row while both sources loaded, only changing once each source finished; the gate is removed, the segmented bar now always shows while a create-first merge is loading, alongside each nested source's own ordinary bar when Sources is also shown. (2) the log view's scrollbar total (`#tableSpacer`'s height, which drives the native `scrollHeight`/max-`scrollTop` — there's no custom scrollbar thumb) only ever reflected the entry count as of the last full `renderTable()`, which a load tick never triggers (deliberately cheap, per the "a load tick never rebuilds `#tree`" rule) — for a large, actively-growing merge (reported: 782,000 entries across two 100MB files) the scrollbar showed a far smaller, constantly "catching up" total, and `End`/`Ctrl+End` (the browser's own native scroll-to-`scrollHeight`) could only ever reach that same stale ceiling. New `updateLiveGrowingTotal(rootId)`, called from `scheduleLoadRender`, fixes the common case cheaply: when the active node's `currentViewEntries` IS `node.entries` by reference (proven by reference-equality alone — true whenever no level filter/pinned-bookmarks union/temp anchor is narrowing the view), its `.length` is already live the instant `node.entries.push()` runs, so only the frozen spacer height needs rewriting, plus a cheap `renderVisibleRows()` — deliberately not a `renderTable()` call, which would make a many-chunk load O(n²). A narrowed view is left to catch up at the next real render, unchanged. (3) deleting a file mid-load left it leaking entries/`entryIndex` ids into the now-orphaned node for the rest of its read/parse (no existence check on any entry-write site, unlike `updateLoadRowProgress`'s own `if (!node) return;`), and the load's own completion `flushLoadRender`/render fired for the dead node regardless. `loadOneFileIntoTree` and `addFile` (a second call site with the identical unconditional-`flushLoadRender` bug, found while fixing the first) now both check `state.nodes[node.id] === node` before their trailing render; `parseLogTextAsync`'s plain-loop fallback (jsdom/this sandbox has no `Worker`, so this is also what the regression suite exercises) and `parseFileWindow` both bail out of their per-chunk yield loop once the node's gone, mirroring the guard `fillMergedEntries` already had for the identical race; `parseFileWindow`'s own caller (`loadFolderFileWindowed`) now distinguishes "unsafe window, fall back to a full reload" from "deleted mid-load, leave it deleted" instead of always reviving the node via a full-file fallback on any `false` return.

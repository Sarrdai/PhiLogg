- **fix: the log view's scrollbar was still broken for a large merge — real root cause was a hard browser height limit, not a stale-total bug; single continuous byte-weighted progress bar replaces the segmented design** (this session, 2026-09-19, immediate person-reported follow-up: the previous entry's own `updateLiveGrowingTotal` fix didn't hold up — their repro was a 2-file drag-drop merge, 822,697 entries, reproduced *after* full load completed, surviving a file switch and back, which a load-tick-only fix can never touch). Root-caused through several ruled-out hypotheses (a generic browser-height-limit guess, PhiLogg's own "UI scale" zoom setting, device pixel ratio, inflated row height from Multiline/Wrap/Notes — each directly tested via a real Playwright/Chromium harness built for this investigation and refuted) to a genuine, pre-existing browser limitation — confirmed present on `main` too, unrelated to any session's own changes: every major engine has a hard practical ceiling on a single element's CSS height, and `#tableSpacer`'s declared height had no cap at all. Chromium clamps to exactly **33,554,428px** (empirically confirmed this session); Firefox — where the person was actually testing — instead discards an oversized declaration entirely and falls back to `height:auto`, which resolves to **0px** for `#tableSpacer` since its only content (`#tableRows`) is absolutely positioned and doesn't count toward auto-sizing, exactly matching the person's own `getComputedStyle` → `"0px"` reading. Once collapsed, `#tableSpacer` stops contributing to `#tableBody`'s scrollable region at all (no `overflow:hidden` between them), leaving `#tableRows`' own drifting `top` offset as the only thing driving `scrollHeight` — explaining every symptom (~2/3 of the data unreachable, the scrollbar jumping while scrolling, the thumb shrinking while holding `End`). Fixed with `detectMaxTableScrollPx` (`philogg.html`, near `ROW_HEIGHT`): a lazy, cached, per-session **binary-search feature-detection of the actual running engine's own ceiling**, deliberately not a fixed worst-case constant — person-requested, since the app's primary target (the Tauri desktop build on Windows, embedding WebView2/Chromium) has roughly 2x Firefox's own headroom, and hardcoding to the tighter limit would needlessly halve scroll resolution there. `computeTableSpacerContentHeight` caps `#tableSpacer`'s content height under that detected ceiling and tracks a `tableScrollHeightScale` factor; `logicalToPhysicalScrollPx`/`physicalToLogicalScrollPx` convert at the boundary everywhere `#tableBody`'s scroll position is read or written for position math (`renderVisibleRows`, `scrollToIndex` + new `setTableScrollLogical`, `captureViewAnchor`, `minimapRenderedSpan`) — real on-screen row geometry (row height, viewport height, rendered row spacing) is never touched, only the compressed physical spacer position. `setTableScroll`'s existing "scroll to true bottom" callers (tail-follow) are untouched — the physical bottom already equals the logical bottom under a linear scale.

  Separately, the person clarified their earlier progress-bar request (previous entry's `(n+1)`-segment bar wasn't quite what they meant): **one continuous bar**, weighted by each source's real byte size — not an equal split — with a small reservation for the merge-copy step, and only because it's needed (a quick/disjoint merge still jumps straight to 100%). The whole segmented design (`node.loadSegmentSourceIds`, `mergeSegmentFractions`, `updateMergeSegmentedProgress`, `.tree-load-fill-segment` CSS/markup) is retired — replaced by `node.loadSources` (`{id, weight}` pairs; `weight` is a real `File.size` for `loadFileDescriptors`, a character-count proxy for `loadMetaFormatText`'s in-memory streams, and an honest equal-weight fallback for folder-watch merges, which have no size available and already load strictly sequentially) plus `updateMergeLoadFraction`, which computes one weighted `node.loadFraction` and writes it through the exact same plain `.tree-load-fill` markup/`updateLoadRowProgress` an ordinary file's own bar already uses — a net simplification, no new CSS or rendering branch. A new `MERGE_STEP_BAR_FRACTION = 0.1` constant reserves a small, deliberately fixed tail for the merge-copy/sort step (person-confirmed: not worth modeling exact relative effort); `fillMergedEntries`'s chunked-copy path rebases its own progress into that tail, and the disjoint/quick-merge fast path still sets `loadFraction = 1` — now the whole bar, not just a segment.

- **fix: holding/repeatedly pressing `End` on a height-capped merge in Firefox still couldn't reach the true last row, and the last row wandered a few pixels rather than settling** (this session, 2026-09-20, immediate person-reported follow-up after retesting the scrollbar fix directly below: the scrollbar now looked proportional, but `End` needed several presses/holds to actually get there, and continuing to press it made the display jump a few pixels forward and sometimes back with no clear final position). An Explore pass over the shipped fix ruled out every app-side feedback-loop theory first: no custom keyboard handling exists for `End`/`Home` (it's 100% native browser scroll on `#tableBody`), the `scroll` listener never writes back to `scrollTop` itself, and `tableScrollHeightScale`/`#tableSpacer`'s height are provably constant while scrolling a static, already-loaded merge (`computeTableSpacerContentHeight`'s 4 call sites are all gated on load-progress/user actions, none on scroll/resize/rAF). Working through the actual math instead exposed a real defect: `tableScrollHeightScale` was derived as `cap / contentPx` — the ratio of the two **content** heights — and applied as a linear scale straight to `#tableBody`'s native `scrollTop`. But the native scrollable *range* on each side is `scrollHeight - clientHeight`, not raw content height, so a content-ratio scale leaves the logical position computed at the true native `scrollTop` maximum short of the true logical bottom by `clientHeight * (contentPx/cap - 1)` px — several row-heights under real compression, meaning `End` could sit at its native physical ceiling while the render still never revealed the actual last rows (a residual pixel-level wobble from Firefox's own native keyboard-scroll animation, amplified by the same undersized scale, remains a separate, likely-irreducible cosmetic effect — out of scope for this round, per person's explicit choice). Fixed by deriving `tableScrollHeightScale` from the two scrollable **ranges** instead of raw content heights (`(cap - tableBody.clientHeight) / (contentPx - tableBody.clientHeight)`) in `computeTableSpacerContentHeight` — its signature, all 4 call sites, and every `logicalToPhysicalScrollPx`/`physicalToLogicalScrollPx` call site stay unchanged; only how the scale itself is computed differs. `tests/philogg.regression.test.js` GROUP 256 extended (256a's expected-scale math updated to the same range-based formula; new 256f asserts the native `scrollTop` max now converts exactly onto the true logical bottom, plus a sanity check that the old content-ratio scale really would have undershot it by more than a row).

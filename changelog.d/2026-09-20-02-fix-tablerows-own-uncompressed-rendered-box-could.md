- **fix: `#tableRows`' own uncompressed rendered box could still overhang `#tableSpacer`'s capped height at the tail — End landed short with blank space below the last row, Home needed several presses to reach the top** (this session, 2026-09-20, immediate person-reported follow-up after retesting the scale-formula fix directly below in Firefox on a real 2-file drag-drop merge: selecting the first entry then pressing `End` landed close to but not exactly at the true end — about 5 entries still below the visible area, blank space under the last row; pressing `Home` afterward only scrolled up ~5% of the log, needing several more presses, each landing further (~50%, then finally the top); pressing `End` again reversed through similar intermediate steps; Chrome unaffected). Two Explore passes confirmed a second, independent defect from the one fixed below: `#tableRows`' own rendered row heights are always TRUE/uncompressed (only its `top` offset goes through `logicalToPhysicalScrollPx`), and its `BUFFER_ROWS` lookback (`start` offset back by 10 rows, so a small scroll doesn't need a full re-render) leaves the rendered block taller than the viewport right at the tail — while `end` was always clamped to `total`, the block's `top` was still positioned via a plain top-anchored `logicalToPhysicalScrollPx(start*ROW_HEIGHT)`, which lands close enough to the physical cap at the tail that `top + true rendered height` provably exceeds `#tableSpacer`'s own capped declared height there. `#tableSpacer`/`#tableRows` are deliberately `overflow:visible` (so a long log message's horizontal overflow bleeds up to `#tableBody`'s own horizontal scrollbar — ruling out `overflow:hidden` as a fix, since CSS's own overflow-x/overflow-y pairing rule would force that axis to `auto` too and break the bleed-through), so nothing clips the overhang, letting it inflate the browser's own real `scrollHeight` beyond what `computeTableSpacerContentHeight` assumed — a smaller, render-geometry-driven resurgence of the same "no `overflow:hidden` sits between them" mechanism `PROJECT.md`'s gotcha entry already blames for the original version of this bug. This explains both symptoms: a physical `scrollTop` genuinely past the assumed max converts to a logical `start` past `total`, which (previously) had no upper clamp to catch it, producing an empty/blank render; and each native Home/End keypress (Firefox's own always-on keyboard smooth-scroll) recomputes against a `scrollHeight` that itself shifts as `#tableRows` repositions — a real feedback loop. Fixed with two changes to `renderVisibleRows()` (both branches): **(1)** bottom-anchor `#tableRows`' `top` instead of top-anchoring it whenever the render reaches the very last entry (`end === total`) and compression is active — `Math.min(naiveTop, cap - trueRenderedLogicalHeight)`, verified algebraically monotonic across the whole tail region (no visible snap/jump); **(2)** a defensive upper clamp on `start`/`centerIdx` (previously only `end` was ever clamped against `total`), so any residual out-of-range `scrollTop` still degrades to a sane last-page render instead of an empty one. `tests/philogg.regression.test.js` GROUP 256 extended again: 256g asserts the rendered block's true height never overhangs the capped spacer at the native `scrollTop` max and the true last entry is still rendered there; 256h asserts an out-of-assumed-range `scrollTop` still renders a non-empty last page reaching the true last entry.

- **feat: Custom Columns — per-format custom columns populated by Pattern/Regex captures, a configurable order, and Time/Level as the only two mandatory columns (this session, 2026-09-21, person-requested)**. Every format used to produce the same fixed six-field entry schema (`ts, level, thread, location, method, message`); this generalizes it while keeping backward compatibility exact for any format that never touches the new fields. **Time and Level are now the only two mandatory columns** (confirmed with the person during planning) — Thread/Location/Method/Message are each individually optional per format, and a format may additionally define **custom columns**: a new `%X{name}` pattern token (log4j MDC-style — captures free text into a user-chosen field name, rejecting a name that collides with one of the six reserved fields) gives Pattern mode parity with Regex mode's pre-existing `(?<name>...)` named groups (no parsing-side change needed there at all). Any captured group beyond the six reserved ones lands on a new `entry.fields` bag (`applyFormatMatch`) — a format defining none (every builtin/legacy format) shares one frozen empty object, so this costs nothing extra in the common case. **Time/Level being mandatory is a save-time-only rule** in the Format Manager (`saveFormatEdit`) — `compileFormatPattern`/`validateFormatRegex` themselves have no hard field requirement any more (every field already had a graceful runtime default: `ts`→`NaN`, `level`→`"INFO"`, `message`→the whole raw line when ungrouped), so a format saved before this rule existed, or compiled at runtime for a file already on disk, keeps parsing exactly as it always has — only *saving* a pattern/regex missing `%d`/`ts` or `%p`/`level` is newly blocked. A format's `columnDefs: [{key, kind, label}]` is its own ordered, reorderable **middle**-column list (Thread/Location/Method, each individually removable/re-addable, plus any custom columns) — edited via a new "Columns" section in the Format Manager (`renderFormatEditColumns`, same ▲/▼-reorder idiom the level list already used, plus one-click "+ Thread"-style chips to re-add a removed default and a text-field pair to add a custom column, validated live against the pattern/regex's own captured group names). Time/Level stay pinned first, never hideable, not part of this list; Message stays pinned last (the row grid's flexible `1fr` remainder when shown) with its own new `messageVisible: boolean` flag instead of an order position. `formatColumnDefs`/`formatMessageVisible` read one format's own list (falling back to the legacy fixed three / always-visible for any pre-existing record); `activeColumnDefs`/`activeMessageVisible` union every currently-loaded root file's own list (same idiom as the pre-existing `activeLevelOrder()`) and drive the row/header renderers (every column span now carries `data-col`, including Time/Level/Message which didn't before), the columns-visibility panel (now JS-rendered from the dynamic set instead of four fixed checkboxes), the context menu's generalized "Filter for this ___" (`activeTextFilterColumns()`, replacing the old fixed 6-entry `TEXT_FILTER_COLUMNS` table and its parallel `CTX_FILTER_COLUMN_CLASSES` lookup — `resolveContextFilterColumn` is now a plain `closest("[data-col]")` walk), and the filter popup's column-restriction chips (JS-rendered from the same dynamic list). `entryColumnValue(e, key)` replaces the old fixed-switch `textColumnValue` — the six reserved fields keep their historical accessors, anything else reads `e.fields[key]`. The two filter-node persistence chokepoints that used to whitelist `node.columns` against the static `TEXT_FILTER_COLUMN_KEYS` (`materializeSerializedRoots`, `materializeCachedFilters`) now validate against a new `knownTextFilterColumnKeys()` — deliberately broader (every format `state.logFormats` knows about, not just currently-loaded ones), so a saved filter's restriction to a custom column survives export/import and session-cache restore even when that column's owning format isn't open right now; a genuinely unknown key is still stripped. **Level** gained an int-or-text value type with explicit per-level colors: `LogFormat.levels` moves from a plain `string[]` to `{value, name, color}[]` (a legacy plain-string record upcasts on read, no migration needed — this project stays pre-1.0), `levelValueType: "text"|"int"` decides whether `levelBucket` matches a captured token against each level's `name` (unchanged default) or its numeric `value` (e.g. RFC 5424 syslog severity 0–7, mapped explicitly per level rather than through a fixed severity table); `color` is an explicit CSS color picked via the existing reusable color-picker popup (`openColorPicker`, already designed for a non-highlight-color caller), falling back to the automatic fixed-name/rotating-slot color when unset.

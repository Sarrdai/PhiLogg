- **fix: log view scrolling — no more snapping content or blank rows (this session, 2026-09-24, person-reported: "Scrolling … feels a bit flickering and bigger jumps always lead to empty lines that need a moment to fill up")**. Measured in headless Chromium (WebView2's engine family) on a 650k-entry / 100 MB file with the new `tools/perf/chromium-scroll-bench.js`; three causes, all fixed:
  - **Scroll-height cap detection read Chromium's number format wrong.** `detectMaxTableScrollPx` compared `parseInt(getComputedStyle(probe).height)` with the requested height, but Chromium prints lengths of 1e6px or more in exponent form (`"2e+07px"`), so every probe failed and the cap fell back to 950,000px. Every Chromium/WebView2 view above ~34k rows was therefore scroll-compressed — 650k rows about 19x: one wheel notch moved 68 rows instead of 4, every scroll render snapped the content by ~170 rows, and the 10-row buffer shrank to ~15 physical px, so scrolling up showed blank rows. Now `parseFloat` with a 1e-5 relative tolerance; a 650k-row file is no longer compressed on Chromium (compression starts at ~1.1M rows).
  - **The 100ms scroll-render throttle** (a 2026-09-21 workaround for Firefox's End key stalling on a huge compressed merge) let the viewport scroll up to six frames past the rendered rows. Replaced by `makeScrollRenderer`: one render per animation frame, reading the live position, backing off only after an expensive render (> 12ms → the next waits 3x its cost).
  - **Every scroll render rebuilt all rows** (~5.5ms, 4.5ms of it style/layout). `renderVisibleRows(true)`, passed only by the scroll listener, keeps the rows still in the window and builds just the new ones (~0.8ms), with a one-screen overscan per side; a jump with no overlap falls back to the small full rebuild. All other callers still rebuild everything.
  - **Result** (same file, wheel scrolling, `chromium-scroll-bench.js`): content jumps while scrolling down 14 of 15 renders (up to 195 rows) → 0; blank rows while scrolling up 15/15 renders → 0/40; a 400px-per-frame flick 13/15 → 0/40; a scroll render 13.8 → 0.8 ms. Results table in `docs/performance-testing.md`. The remaining case is a scrollbar-thumb drag: each step is a jump beyond any buffer and shows about one frame of stale rows — inherent to native scrolling with virtualized rows. Not yet confirmed on Windows/WebView2 or in Firefox.

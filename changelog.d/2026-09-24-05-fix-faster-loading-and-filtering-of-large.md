- **fix: faster loading and filtering of large files (this session, 2026-09-24, person-requested: four measured proposals from the previous session)**. Measured in headless Chromium 141 (WebView2's engine family, new `tools/perf/chromium-load-bench.js`, `docs/performance-testing.md` → "Level 2c") on a 650k-entry / 100 MB file through `#fileInput`, median of 4: load 2.87 → 2.10 s, longest main-thread stall 460 → 225 ms, JS heap 357 → 326 MB, level filter (162k matches) create+render 530 → 100 ms; text filter unchanged (~190–220 ms). Desktop app (WebKitGTK/Xvfb, launch-argument route): JS path 7.3 → 3.8 s, native unchanged (2.7–3.1 s).
  - **Session cache off the load path.** `persistFileNode` used to rebuild the file's text and structured-clone it into IndexedDB before the load's render (0.5–1.3 s blocked). A record now holds the original `File` (a Blob — IndexedDB copies it off the JS thread) for a drop/dialog/folder load, **only the path** for a desktop file (re-read and re-parsed from disk on restore — the person chose this over storing text: a file deleted or moved since is not restored), and rebuilt text only for merges, meta-format streams, ZIP entries and tailed files, written when idle (`persistFileNodeWhenIdle`). `fileCacheSource`, `reopenLocalPathForRestore`, `pinFileFormat`, `newTailState`. No migration (0.x).
  - **One file parses on every core.** `splitTextAtHeaderLines` cuts the text before header lines into one piece per core; each worker sends binary batches (`encodeEntryBatch`, the native parser's `batch.rs` layout, read by the same `decodeNativeBatch`; the string section is posted as a JS string, which also keeps lone surrogates intact) instead of structured-cloned entry objects — the main thread's unpacking went from ~1.4 s to ~0.2 s. Pieces are adopted in file order with ids assigned there; a failed worker rolls back and the main-thread loop takes over. Output stays byte-identical (golden fixture, GROUP 264).
  - **Per-file aggregates built during adoption** (`updateFileAggregate`, `node._agg`): level counts per raw level + format, per-level entry indices, sortedness, ts range, the longest message/line. The first render reads them instead of full passes (`getLevelCounts`, minimap via `minimapBucketBounds` + per-level overlay, `updateMinimapFullRange`, `computeMaxMessageWidth`): 230 → 118 ms on the (unsorted) test file, 43 ms on a chronological one. Incremental on tail appends; invalidated by in-place reorders (`invalidateOrderIndexMap`, now also called for a meta-format stream's sort) and clock offsets; a format level edit needs nothing (bucketed when read).
  - **The parsed batches are adopted a few at a time** (`PARALLEL_PARSE_DRAIN_BATCHES`), yielding through `queueTask` — a `MessageChannel` message: a first version yielded with `setTimeout(0)` and the desktop JS path went from 3.8 to 9.2 s, because a hidden window's timers are throttled (Xvfb's unmapped window; a minimized or tray-hidden app is the same case).
  - **Context view only while visible, match/gap part memoized.** `renderMainView` rebuilt the Context view on every render even with only the Filtered tab on screen (~300 ms for the level filter above). Hidden, it is now marked stale (`contextViewStale`) and built when revealed; `contextMatchesAndGaps` memoizes the match set, gaps and match ordinals per active node + result + root entries, and finds the root indices with one walk instead of an id map where the result is a subsequence of the file. Re-render with the Context tab showing 222 → 98 ms.

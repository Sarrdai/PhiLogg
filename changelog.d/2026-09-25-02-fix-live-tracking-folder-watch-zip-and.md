- **fix: live tracking, folder watch, ZIP and viewer performance (this session, 2026-09-25, person-requested: "Performance Review in Tracking, folder Watch (and settings), loading ZIP Files, Textiles and Images as well as partial or combined loading from folder Watch")**. Measured on the 650k-entry / 100 MB file (`docs/performance-testing.md` → "Level 2d", "Level 3b", new `tools/perf/chromium-tail-bench.js`, `desktop-tail-bench.sh`):
  - **Tail ticks re-ran every filter over the whole file.** A pure append now keeps a per-entry filter's (text, level, time range, id set, bookmarks, notes; inverted or not; whole chain per-entry) old result as `node._tailBase`; the next `getEntries()` tests only the new entries plus the previous last one (`extendCachedEntries`). Tailed files are polled concurrently. One tick with three filters: ~340 → ~57 ms (Chromium).
  - **Every tail tick re-fingerprinted the whole file** for its filter-history record (`buildFileHistoryRecords` → `getFileFullHash`, ~280 ms on 100 MB), because each tick renders and the history write is debounced from `render()`. A record is now only written when the file's filter tree changed (`_historySig`), which is what the docs already promised; the earlier record still matches the grown file via tier 2.
  - **A growing file's cache write rebuilt its whole text every 4 s.** A browser-tailed file's record is a Blob slice of a fresh handle snapshot at the tail offset (`tailSnapshotBlob`), text only as a fallback; restore resumes tailing at the Blob's exact size (`restoredTailOffset` — rebuilt text undercounted a CRLF file). Stall after the ticks: ~435 → ~35 ms.
  - **Desktop: every poll re-read the whole file.** `protocol.rs` serves `Range` requests (`read_local`/`parse_range`); tail polls, the folder minimap's head/tail probe and windowed loads read through `urlTailHandle.getRangedFile()`/`rangedUrlFile`. Idle poll of a 100 MB file: ~2,340 → ~2 ms; a poll with 1000 new lines: 2,348 → ~135 ms.
  - **Folder watch**: an in-flight minimap probe is shared instead of restarted by every render; the "Merge (full)/(window)" actions load their sources concurrently (`loadFolderMergeSources`, ids in target order) with one render per finished source instead of two; browser mtime reads run concurrently; `mergeScannedFiles`' removal check is a set lookup instead of O(n²); unopened folder and ZIP rows are reused across renders (also keeps a double-click working during a live tick) and open roots are looked up once per section.
  - **Viewers**: the text viewer rebuilds its markup only when the viewer or Pretty Print changed (unrelated renders reset folds and re-tokenized the file); the image viewer keeps its `<image>` element through pan/zoom (each mousemove re-parsed the data URL). **Bugfix**: the image's natural size was measured once for the first image ever opened and reused for all later ones — now per viewer.
  - Tried and dropped: a linear merge of sorted sources in `fillMergedEntries` — slower than the existing sort (TimSort already merges sorted runs linearly).

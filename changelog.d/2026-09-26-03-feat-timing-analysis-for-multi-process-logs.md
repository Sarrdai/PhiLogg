- **feat: timing analysis for multi-process logs — Gap filter, link Δt condition, link correlation key (2026-09-26, FEATURE_BACKLOG.md #24 + two link options)**. Motivation: in a log written by several processes/threads, the plain gap to the previous line is nearly meaningless (somebody always logs); timing only means something per thread, or between two specific messages that belong together. Current behavior: `docs/filters.md` → "Gap filter", "Correlation key", "Δt condition".
  - **Gap filter** (`filterType: "gap"`, `value: { ms, per }`): keeps entries of the parent's result whose distance to the previous entry is `>= ms`, optionally **measured per** a column (Thread, Location, Method, custom, or Source on a merge): one pass, last ts per group. New `#gapDialog` (value + ms/s/min + "measured per", the filter popup's live summary with each sample's gap), opened via **"Gap filter…"** in the tree context menu (a child of the right-clicked node), edited via Edit filter… (context menu, sidebar toolbar, Ctrl+E). The Filtered view's Δt column shows each row's **measured** gap on a gap node. No new node field: `value` carries everything. The optional Context-view "⏸ N s without entries" separator label was not done.
  - **Link Δt condition** (`linkDt: { op, ms }`): only tuples whose span (first → last real entry, new `pair.dtMs`/`tsMin`/`tsMax` from `buildPairEntry`) is `>`/`<` the limit. It's checked before a target is claimed under exclusive matches. The multi-hop dialog puts it on the last hop (total span). An extraction on link pairs gets a synthetic **Δt (ms)** column (`DT_COL = -3`) for sorting, stats, and plotting duration over time.
  - **Link correlation key** (`linkKey: { column } | { pattern }`): pair only entries with the same column value, or the same wildcard capture(s) such as `axis [*:int]`. Targets are indexed by key once per recompute, and each reference searches only its key's list with the unchanged occurrence search. So direction, N, the tie-break, exclusivity and order enforcement are all kept. The key applies to every hop, read off the entry each hop searches from.
  - **Link dialog**: the two new option rows (pill switch + inline controls, greyed out while off) and a **live preview** ("3.418 pairs" / "12 of 3.418 pairs", histogram, sample pairs with their Δt), evaluated as the would-be nested baked chain.
  - **Refactor**: the duplicated link pairing loops of `getEntriesUncached` and `getEntriesFromBaked` became one `computeLinkPairs`. The live result summary (`renderLiveResults`/`renderLiveMatchMinimap`) now takes a target container, and its CSS moved from `#filterResults…` ids to `.live-results`/`.live-match`/`.live-minimap`/`.live-samples` classes, so the new dialogs reuse it. `linkDt`/`linkKey` are threaded through every carrier via one `copyLinkOptions` (sanitizing hand-edited values).

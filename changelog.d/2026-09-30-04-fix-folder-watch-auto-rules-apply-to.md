- **fix: folder-watch auto rules apply to every listed file type, a failed folder heals, closing a folder/ZIP or deleting a file closes its files, and the tree cursor on a closed entry deselects (2026-09-30, person-reported)**
  - **Auto rules for all listed types.** "Show M newest", "Auto-close — keep only N open" and "Auto-open newest" skipped every non-log file (`applyFolderAutoRules`' `groupBy` dropped them) and judged "open" only by `rec.nodeId`, which an inline viewer never has — so a watched folder of `.json` files (the reported case, Windows desktop build) ignored all three. They now apply to everything the folder lists (logs and inline-viewable `.txt`/`.xml`/`.json`/images; never restricted to `*.log`, a pattern matching both ranks them together by mtime). New `isFolderRecOpen` (node alive OR `folder.inlineViewers` has it) and `closeFolderRec`; a newest `.json` opens as an inline viewer, `loadFolderFile`'s viewer branch now sets `rec.openedByAuto`/`autoOpenFired` like a node does, and an auto-opened viewer's row carries the same circled "A" badge/tooltip. Start filters stay log-only (filter-library records for a log node). Each auto `loadFolderFile` is wrapped in a try/catch (`console.error`) so one bad file doesn't abort the remaining rules.
  - **A failed folder is no longer dead for the session.** `folderScanTick` skipped `folder.failed` folders forever (one failed scan ended new-file detection, deletion detection and all rules), and scan + merge + rules + render shared one try, so any error there flagged the folder unreachable. Now only a failing *listing* (`scanFolderHandle`, via `scanFolderOrFail`) sets `failed` + `folder.failedMessage` (transient, never persisted); a failed folder is re-listed every tick and the first success clears it and merges (even with an unchanged key set); merge/rule/open/render errors are `console.error`ed and never flag the folder (`rescanFolder` and the new `pollFolder`, `render()` outside the try). A repeated identical failure renders nothing (Group 195 stays at zero renders on stable polls); a folder removed while its listing was in flight is not merged into. The dot's tooltip now reads `Folder can't be read — <message>. Retrying every 3 s.` The Windows-specific trigger of the reported red dot could not be reproduced (jsdom with Windows paths, the real Linux desktop build) — hence robustness plus a diagnosable message.
  - **Containers and deletions close their files.** One shared `closeInlineViewerEntry(ownerKind, ownerId, mapKey, { undo })` (the row's ✕/middle-click keeps undo for the text versions; every automatic close has none) replaces the closure in `buildInlineViewerEntryRow`. A file deleted on disk now closes through `closeFolderRec` — an open viewer, its "Filter lines" text versions and a shown viewer go too, instead of lingering with the text versions falling back to orphan top-level rows. The folder's ✕ (`removeWatchedFolder`) and the ZIP's ✕ (`removeZipSource`) close everything opened from them via `closeContainerFiles` (silent-preload jobs, nodes by `folderId`/`zipId`, viewers with their persisted records, text versions, a shown viewer / folder view) — no undo; the folder's ✕ used to detach open files as plain top-level files, the ZIP's ✕ left opened log nodes in `state.rootIds`, never rendered but still able to be the displayed active file.
  - **The tree cursor on a closed entry deselects; placeholder main view.** Alt+Arrow (or a plain click) onto a listed-but-not-loaded ZIP entry / watched-folder file used to leave the previously selected file highlighted and its content shown, so it looked as if the row under the cursor were open. New `placeCursorOnUnloaded(navId)` (used by `moveTreeSelection` and both click handlers — `renderInactiveFileRow`'s and `buildInlineViewerEntryRow`'s) sets `activeId`/`inlineViewer`/`folderView` to null, clears `multiSelect`, then `setTreeCursor`; dir rows stay cursor-only. `renderMainView` gets a branch for "no inline viewer, no folder view, no live active node": with files open it hides the log surfaces (clearing nothing) and shows `#emptyState` with texts built in JS (`showEmptyStateText`, the markup's original text restored whenever it applies): `"<name>" is not loaded` + `Press → or Alt+→ to load it, or double-click it.` while the cursor rests on an unloaded entry (`"<name>" is loading…` while its keyboard load runs — a small addition so the hint doesn't say "not loaded" for seconds on a big file), `No file selected` + `Select a file on the left.` otherwise (this also covers a shown viewer closed by an automatic close), and the original "No log file loaded yet" with no files and no such cursor. Alt+Up/Down continue from the unloaded row, Right loads and selects it (the `stillThere` check works from a null `activeId`), the cursor preload is unchanged, the previous file stays open and is selected again by ↑/↓ or a click.
  - **Null-`activeId` safety** (verified by Group 343, no error anywhere): nav history, session-meta persist/restore (no active node recorded, restore falls back to the first file), find bar, Ctrl+F / Delete / F2 / copy-paste. Two guards were needed: `commitCurrentNavPosition` now does nothing while none of the log surfaces is on screen (placeholder, inline viewer, folder minimap) — a hidden view's scroll offsets read as 0 and would have overwritten the last good waypoint of the file you walked away from (Back after Alt+Arrow over a closed entry returned to the top), which the existing inline-viewer detour suffered from too — and the Ctrl+0 focus-tree shortcut no longer picks the first root while the cursor rests on an unloaded entry.

# Extraction and Plotting

The value-extraction table (Index/t(ms) columns, virtualized rendering, live pattern preview + ignored columns), the Plot tab, value assertions, and column statistics.

## Extraction table: synthetic Index + t(ms) columns

Every extraction table leads with two synthetic columns, ahead of the pattern's own — person-requested (2026-08-17): a 0-based row-order **Index** and **t (ms)**, the *cumulative* elapsed time in ms since the extraction's first entry (0 on row 0). `INDEX_COL = -2` / `ELAPSED_COL = -1` — negative so they can never collide with `spec.columns`' dense `0..n-1` range, the same stable-`colIndex` identity scheme "Ignored columns" above already established for the pattern's own columns. Both are typed `"int"`, so they're automatically plottable/sortable/assertable/statable through every existing `colIndex`-keyed mechanism (`findExtractColumn`, `extractRowComparator`, `checkAssertion`, `computeColumnStats`, the Plot tab's axis-candidate list) with **no new code** at any of those call sites — the only places that needed to know about them at all were `renderExtractTable` (prepending the two descriptors to `extractColumns` and stamping their values) and `columnColor`.

**t(ms) is cumulative, not a row-to-row delta — a same-session correction.** It first shipped as "ΔT," the gap to the *previous* entry (blank on row 0). The person immediately flagged the design: *"deltaT macht so keinen Sinn für einen zeitlichen Plot. Der erste Eintrag müsste 0 haben, der Rest dann die bis dahin aufsummierten deltaT."* The reasoning holds up: a per-step delta can't work as a plot X value at all — row N's position on that axis would depend on the sum of every prior row's spacing, not on row N's own column value, which is exactly what a plot axis needs. Cumulative elapsed time fixes that: it's a real time axis, just relative (start = 0) rather than absolute. Renamed "t (ms)" to match, since it no longer represents a delta.

**Computation**: `values[ELAPSED_COL] = String(e.ts - entries[0].ts)` — elapsed time from the extraction's first entry, which is naturally `0` for row 0 itself (`e === entries[0]`) with no special-casing needed. Values live as **negative-index expandos on `row.values`** (`values[INDEX_COL] = String(r)` alongside it) rather than as dense array elements — every existing colIndex-keyed bracket read (`row.values[ci]`, used throughout copy/export/sort/plot/assertions) already picks these up unchanged, and `values.length` (relied on by Group 24's "matching itself is untouched" assertion) stays exactly the dense `spec.columns` count it always was, since JS arrays don't count negative-index properties toward `.length` or `.map`/`.forEach` iteration.

**Computed from the pre-sort, chronological entry order** — `entries.map((e, r) => ...)`, before `extractSortCol` is applied, and always relative to `entries[0]` regardless of any later re-sort — same as every other captured value: fixed per row at extraction time, not recomputed when the table is re-sorted by a different column. Re-sorting by Index or t(ms) itself works normally through the existing generic sort machinery.

**`#btnCopySelection`/`#btnCopyAllExtract` removed (this session, person-requested)** — the two buttons that used to sit in `.extract-toolbar-row2` (now-empty `.extract-actions` wrapper removed with them) are gone from the UI. `copyTableSelection()` is unaffected — it's reachable via Ctrl+C whenever `state.tableSelection` is non-empty, independent of any button. `copyWholeExtractTable()` (copies the whole table as TSV **with a header row**, respecting ignored columns — genuinely different output from any cell-range selection, which never includes headers) lost its only UI trigger and is currently unreachable from the UI at all; kept as a function anyway, same precedent as `jumpToFullLog` surviving un-wired to a double-click (see "The three 'active node' views" above) — still directly tested (Group 60c), in case a future entry point wants it.

**Default X axis, for free**: `renderPlotControls`' existing `plottable[0].index` fallback already picks whatever's first in `extractColumns` — since Index is now unconditionally prepended there, it becomes the default X-axis selection for every extraction's plot with no dedicated code path. The Y-column auto-pick (`plotConfig.yColsInit`) was adjusted to prefer a real pattern column over the synthetic ones (`plottable.find(c => c.index >= 0)` before falling back) — defaulting Y to t(ms) (plotted against Index) would be a much less useful first look than the pattern's actual extracted value.

**Header rendering**: the numbered, colored circle badge (`.pattern-chip-num`) that marks a column's position in the pattern is skipped for `colIndex < 0` — Index/t(ms) aren't placeholders in the regex pattern, so a number there would be misleading; they still get the ordinary sort button, type tag, and (since they're plottable) an assertion button.

**Gotcha fixed while adding this**: `columnColor(i)` used a naive `i % COLUMN_PALETTE.length`, which returns a negative result for JS's `%` on negative `i` (e.g. `-1 % 6 === -1`), indexing before the array and silently producing `undefined` → an invalid `background:undefined` inline style. Fixed to `((i % n) + n) % n`. This is exercised anywhere a negative `colIndex` reaches `columnColor` — the header swatch (moot now that the badge is skipped for negatives, but the call still happens), and, non-moot, the Plot tab's Y-column-list swatches and multi-series legend, where t(ms) can legitimately be selected as a Y series.

Regression-tested: **Group 42**, rewritten in place the same session for the cumulative correction — column descriptors/ordering, computed values (explicitly checked against what the wrong per-step value would have been), header DOM (badge presence/absence), body rendering, sorting (descending reverses order, now that every row's value is parseable — unlike the old blank-first-row delta), copy/export, the Plot tab's X/Y defaults, and the `columnColor` fix. Three older groups needed small updates because their assertions assumed the extraction table had no leading columns: **Group 5** and **Group 14** now target their sort/assert buttons by `data-sort-col`/`data-assert-col` instead of "first one in the DOM"; **Group 24**'s column/button counts and copy-export text were bumped by the 2 new always-visible columns.

## Virtualized rendering: extraction table & Link pair view

Both views now only ever put the scrolled-into-view window (plus a small buffer) into the DOM, closing the gap noted in Known limitations ("not virtualized... would need work if someone tries to extract from an entire multi-hundred-thousand-line file with a very loose pattern"). Same underlying idea as the main log table's `renderVisibleRows`/`#tableSpacer`/`#tableRows`, adapted to each view's own DOM shape.

**Extraction table** (`renderExtractVisibleRows`): `extractRowsData`/`extractColumns` always hold the FULL result — sort, cell selection, copy/export, column statistics, and the Plot tab all keep operating on the complete set exactly as before, completely unaffected by virtualization. Only the row-building loop that used to run once per `renderExtractTable()` call moved into its own function, keyed off a fixed `EXTRACT_ROW_HEIGHT` (28px, enforced via an inline `style.height` on every `<tr>`, same reasoning as the main table's `ROW_HEIGHT`) and a `EXTRACT_BUFFER_ROWS` (15) buffer above/below the viewport. Because `#extractHead`/`#extractBody` are a real `<table>` (needed for the sticky header + sticky gutter column + native cell borders the existing UI already relies on), the windowed subset can't be absolutely-positioned the way `#tableRows` is — instead **two spacer `<tr>`s** (a single `<td colspan>` each, sized via inline `height`/`padding:0`/`border:none` so no dedicated CSS rule is needed) stand in for the rows above/below the rendered window, keeping the scrollbar's range correct. `#extractHead` is itself NOT virtualized (one sticky row, always fully rendered) but its own rendered height still occupies scroll-flow space above row 0 (sticky positioning doesn't remove it from layout) — `extractHead.offsetHeight` is read directly and subtracted from `extractScroll.scrollTop` wherever the body's own scroll offset is computed, rather than assuming the header takes 0px. `applyExtractSelectionClasses()` now runs at the end of every windowed re-render (not just the initial full build), so a selection made before scrolling still shows `.cell-selected` correctly on whatever happens to scroll into view later. Switching to a different extraction node now also resets `extractScroll.scrollTop` to 0 — needed once virtualization exists (a stale deep scroll position into a much smaller new result would otherwise render starting mid-air, or entirely past the new table's own end); this was a latent gap before virtualization too, just invisible since every row always had a DOM node regardless of scroll position.

**Link pair view** (`renderLinkVisibleBlocks`): a pair-block's height varies with its tuple size (`getTupleEntries(pair).length` — 2 rows/1 delta for a plain link, N rows/N-1 deltas for a chained/multi-hop tuple, see "Link filter" above), so unlike the two fixed-row-height table views this can't just divide `scrollTop` by a constant. `computeLinkBlockOffsets()` builds a prefix-sum array (`linkBlockOffsets`, length `linkPairsData.length + 1`) analytically from each block's real-entry count via `linkBlockHeight(n) = n·LINK_PAIR_ROW_HEIGHT + (n-1)·LINK_DELTA_HEIGHT + (2n-2)·LINK_ROWS_GAP + LINK_BLOCK_MARGIN` — the exact same constants (`.pair-row`/`.pair-delta` heights now enforced via inline `style.height`, `.pair-rows`' own flex `gap`, `.pair-block`'s `margin-bottom`) the CSS already used, just made exact instead of left to natural layout, so the formula's output is guaranteed correct with no DOM measurement needed. `linkBlockIndexAtOffset()` binary-searches that array to find which block a given pixel offset falls into. The rendered window is buffered in **pixels** (`LINK_BUFFER_PX = 300`), not a row/block count, since blocks aren't uniform height. `#linkBody` moved from a plain block-flow container to the same `#linkSpacer`(`position:relative`, full height)/`#linkBody`(`position:absolute`, offset via inline `top`) split `#tableSpacer`/`#tableRows` already established, since (unlike the extraction table) it's plain `<div>`s, not a native `<table>`, so absolute positioning works directly — no spacer-row workaround needed here.

**Pair selection had to stop being DOM-class-only.** Before virtualization, `.pair-block` for every pair always had a live DOM node, so "which pair is selected" could just be read back off whichever element currently carried `.pair-selected` (`linkBody.querySelector(".pair-selected .pair-brace")`). Once a block can be torn down and rebuilt between a click and any later read (scrolled away, then back), that stops being a safe source of truth — a selection made, then scrolled out of view, would silently vanish the instant the block left the DOM, and `minimapMarkedEntries()` (which used exactly that query) would incorrectly report nothing marked. Fixed by tracking selection as `linkSelectedPairIndex` (an index into `linkPairsData`, not a DOM reference) — `applyLinkSelectionClasses()` re-applies `.pair-selected` to whichever *currently-rendered* block matches that index after every windowed re-render, and `minimapMarkedEntries()`/`applySelection()` (the "a plain row selection supersedes a stale Klammer" clearing logic) both read/write the index directly instead of touching `linkBody` at all. A side effect, not a regression: pair selection now also **persists across a re-render of the same link node** (e.g. toggling a level filter) — previously any full `renderLinkView()` rebuild silently dropped the selection since the DOM class had no state to survive the rebuild; now it does, matching how `state.tableSelection`/`state.selectedId` already behave elsewhere. Switching to a genuinely *different* link node still resets both the scroll position and `linkSelectedPairIndex` (`renderLinkView`'s `linkNodeId !== node.id` check, same pattern `renderExtractTable`'s `extractNodeId` check already used).

The minimap's own "rendered subset" sub-rectangle stays deliberately hidden for the Link view (unaffected by this work) — extending it to the Link view's own (differently-shaped) virtualization wasn't part of what this item asked for. `updateMinimapRenderedRange` enforces this with its own explicit guard (`linkWrap.style.display !== "none"`) rather than by simply never being called during the Link view — see "Timeline minimap" in `docs/filters.md` for the later session that made that guard necessary (the Full view now keeps rendering in the background even while the Link view is on screen).

Regression-tested: **Group 45** in `tests/philogg.regression.test.js` — extraction table: windowed DOM row count bounded well below a 300-row result, correct top/bottom spacer heights before and after scrolling, select-all still covering every logical cell (not just the rendered subset), a rendered cell correctly showing `.cell-selected` after a windowed re-render, and scroll resetting on a node switch; Link view: `linkPairsData`/`linkBlockOffsets` always reflecting the full 50-pair result regardless of what's rendered, a bounded rendered block count, the render window actually moving to a deterministically-computed block index on scroll, a pair selected then scrolled fully out of view keeping no stale `.pair-selected` anywhere while `minimapMarkedEntries()` still resolves it correctly, `.pair-selected` correctly reappearing once scrolled back, and both scroll position and selection resetting on a genuine node switch.

**Panel-resizer drag handlers now rAF-batch their re-render too** (code-review finding, 2026-08-18): every high-frequency scroll listener above already collapses rapid events onto `requestAnimationFrame` via a `xTicking` boolean guard — `tableBody`/`highlightBody`/`extractScroll`/`linkScroll`'s `"scroll"` listeners all follow this shape. The three panel-resize drag handlers (`#detailResizer`, `#sidebarResizer`, `#fhSplitResizer` — see "Header / toolbar layout"/"Highlight view" for what each resizes) had been missed: their `mousemove` handlers called `renderVisibleRows()`/`renderHighlightVisibleRows()`/`renderTimelineMinimap()` synchronously on every raw event. `mousemove` fires far more often than the display repaints, so a fast drag reran that work (for the sidebar case, two full row-window rebuilds *plus* a full timeline-minimap SVG rebuild — the overlay pass is O(current view size) even with the background pass memoized, see "Known limitations") once per input event instead of once per frame — visible stutter on a large filtered view. Fixed with the exact same `xTicking`/`requestAnimationFrame` guard the scroll listeners already use per handler (`detailResizeTicking`/`sidebarResizeTicking`/`fhResizeTicking`); the geometry write itself (`style.width`/`style.height`, what makes the panel visibly track the cursor) stays **outside** the throttle so there's no added input latency — only the expensive re-render is deferred and collapsed. Regression-tested: **Group 47** — for each of the three resizers, dispatching several rapid `mousemove` events confirms the style geometry updates synchronously on every one while the re-render function stays uncalled until a `setTimeout` lets the batched `requestAnimationFrame` actually fire, at which point it's been called exactly once despite the multiple input events.

## Plotting (inside the extraction table's Plot tab)

Custom SVG chart builder, no library. Line / Bar / Scatter, chosen per-plot via `plotConfig`. Only columns with a numeric-capable type (`isPlottableType`: `float`/`int`/`hex`/`time`) are offered as axis candidates; `time` values are parsed to milliseconds (`parseTimeToMs`) so time columns are plottable too.

- **Line/Bar**: multi-select Y columns (checkboxes, colored to match their extraction-table chip); line points are connected in **row order**, not sorted by X value, because extracted rows are already in the log's chronological order and that's almost always the meaningful sequence.
- **Scatter**: single X, single Y, optional third **color-by-value** column rendered with a blue→yellow→red gradient (`plotColorScale`) plus a legend.
- **Axis scaling**: `niceTicks()` is a standard "nice numbers" algorithm (picks a 1/2/5×10ⁿ step) so tick spacing looks sensible regardless of whether the data is in the hundreds (mm) or 10⁻⁵ range (µm) — this was a specific requirement, not an afterthought. Manual min/max override inputs exist per axis for when auto isn't wanted. For comparing multiple Y-series that live on very different scales in the *same* chart, there's a **"Normalize each series (0–1)"** toggle (only shown with 2+ series selected) — auto-scaling alone can't fix that case since it's one shared axis across series.
- 3D scatter was explicitly deferred (lower priority per the person).
- **Gotcha already hit and fixed**: don't auto-refill an "empty" multi-select (Y columns) on every re-render — it fights the natural "uncheck the old one, check the new one" interaction, since the render in between the two clicks sees zero-selected and silently restores a default. Fixed by only auto-picking Y defaults once per extraction (`plotConfig.yColsInit`), not every render.
- **Bugfix: tailing was silently closing an open axis dropdown** (this session, 2026-08-19, person-reported: *"während ein Log im Tailing ist, kann ich die Plots nicht korrekt Bedienen. wenn ich das dropdown zur Auswahl einer Datenspalte für z. B die x Werte öffne, schließt es sich kurz darauf von selbst."*). `renderExtractTable()` calls `renderPlotControls()` unconditionally whenever the Plot tab is open — including from `onTailChange()`'s plain `render()`, which fires on every tail poll tick while a file is actively being written to. `renderPlotControls()` did a flat `plotControls.innerHTML = html`, tearing down and recreating `#plotXSelect`/`#plotYSelectSingle`/etc. on every one of those calls — a real browser closes an open native `<select>` the instant its element is removed from the document, which is exactly what a tail tick was doing mid-interaction. This is the same class of DOM-identity bug CLAUDE.md's "Known gotchas" already documents for `renderVisibleRows()`/native `dblclick` and `renderTree()`/native `click` during a load tick — just for `<select>`/native dropdown-open state this time. The wasted rebuild itself was also just wrong on the merits: tailing only ever appends **row** data (`extractRowsData`); it never touches the pattern/columns/`plotConfig` the controls' HTML is actually built from, so the DOM never needed to change in the first place. Fixed with a content-diff guard: `html` (the string about to be written) is a pure function of `extractColumns`/`plotConfig`, so comparing it against `lastPlotControlsHtml` (the string from the last real write) is a simple, general "would this rebuild actually change anything" check — identical means skip the `innerHTML` write (and the listener re-attachment right after it, which only makes sense paired with fresh nodes) entirely, leaving whatever's currently open alone. `resetPlotConfig()` clears `lastPlotControlsHtml` too, so a genuine node switch always forces one real rebuild regardless of any coincidental string match. The chart itself (`renderPlotChart()`) is untouched by this and keeps updating live every tick, as it should — only the controls' own DOM churn is guarded. Regression-tested: new **Group 62** — a real `tailTick()` (fake `FileSystemFileHandle`, same technique Group 12 uses) that adds a new extraction row asserts both axis `<select>` elements are the SAME DOM node afterward (not recreated) while the chart's own mark count DID grow to 4; a second, empty tick is equally inert; and a genuine control change (chart type Line→Bar) still produces a new node, proving the guard doesn't suppress real updates.
- **Point/bar → log entry** (this session, 2026-08-18, from `FEATURE_BACKLOG.md`'s "Plot point → log entry" — the Plot tab used to be a dead end, an outlier visible but not reachable): every mark (line/scatter point circle, bar rect — not the assert-violation ring drawn on top of a flagged one) carries `class="plot-mark" data-row="<index into extractRowsData>"` (`p.rowIndex`, already computed for bar's group positioning, reused here). One delegated `click` listener on `#plotSvg` (not per-mark — `renderPlotChart` rebuilds the SVG's `innerHTML` wholesale every render) resolves `ev.target.closest(".plot-mark")` back to `extractRowsData[row].entry` and calls **`jumpToFullLog`** — the same destructive jump the extraction table's own row double-click already uses, for the same reason (see that function's comment): the Plot tab has no Highlight-view companion of its own to reveal into instead. Clicking chart background/axes/gridlines (no mark under the cursor) is a no-op. `.plot-mark{cursor:pointer}` + a `:hover{opacity:.7}` dim are the only visual affordance — no per-mark tooltip, kept deliberately minimal.
- **Equal axis scale** (`plotConfig.axisEqual`, this session, 2026-08-18, from `FEATURE_BACKLOG.md`'s "Axis-Equal" suggestion): a checkbox (`#plotAxisEqual`, default off, hidden for Bar — its X is categorical/one-bar-per-row, so a pixel-per-unit ratio doesn't apply) that keeps X and Y at the same pixel-per-data-unit ratio, so a plot of two same-unit quantities (the motivating case: `Position x=[value:float] y=[value:float]`) isn't visually stretched by the chart area's own aspect ratio. Implementation stays a pure presentation-layer step, deliberately not touching `niceTicks`' output: after the home domain's ticks are computed as usual, whichever axis has the smaller data-units-per-pixel (i.e. the *looser* one — more screen space than it strictly needs) gets its **pixel-mapping domain** (`xHomeDomainMin/Max`/`yHomeDomainMin/Max`, separate from the tick-generating min/max) symmetrically padded until both axes' ratios match; the tighter axis is left untouched. Ticks/gridlines still render at their original "nice" values and positions — the padding only ever adds blank margin beyond the data, it never re-buckets the ticks themselves. Ephemeral view state like `normalize`/`xMin` etc. — not threaded through any persistence carrier.

### Plot zoom / pan / hover tooltip (this session, 2026-08-18, person-requested)

Mouse-wheel zoom anchored at the cursor, middle-click-drag panning, an editable zoom-level readout (`#plotZoomBar`: +/- buttons, a typed %, Reset), left-click-drag rectangle zoom (multi-step), and a hover tooltip showing a mark's exact underlying value — for all three chart types (Line/Bar/Scatter), including Bar's categorical X.

`#plotZoomBar` itself lives in the extraction toolbar's second row (`.extract-toolbar-row2`, to the left of the Table/Plot `#extractViewTabs`), not overlaid on the chart — moved there (this session, 2026-08-28, person-requested layout change) so it doesn't cover chart content and stays visible/consistent whether or not a chart is currently zoomed. It's still hidden entirely outside the Plot tab (`updatePlotZoomIndicator`'s existing `plotLastRender`-gated show/hide is untouched). Internally it's two visually separated `.plot-zoom-bar-group`s — zoom controls (`−`/level/`+`/Reset) and the "Create filter from plot view" buttons below — divided by `.plot-zoom-bar-sep`, with a further `.extract-toolbar-row2-sep` between the whole zoom bar and the view tabs (hidden via a `#plotZoomBar.hidden + .extract-toolbar-row2-sep` CSS rule whenever the bar itself is hidden).

**Zoom state**: `plotZoom` (`{x0,x1,y0,y1}` in data-domain units, or `null` for "no zoom, show the home view") — ephemeral like `plotConfig.xMin`/`normalize`, not threaded through any persistence carrier, reset in `resetPlotConfig()` and whenever an axis-shape-changing control fires (chart type, X column, Y column(s)/scatter Y, normalize toggle, a manual X/Y range edit) since a zoom domain computed for the old axis shape is meaningless for the new one.

**"Home" domain and the zoom-out ceiling**: `renderPlotChart` first computes the exact same domain it always did with no zoom (now named `xHomeDomainMin/Max`/`yHomeDomainMin/Max`, post-`axisEqual`-padding) — this is exactly what's shown when `plotZoom` is null (the default view is completely untouched by anything below). `clampZoomAxis(homeLo, homeHi, wantLo, wantHi)`, a small helper nested in `renderPlotChart`, caps the requested span at the home span **plus a small buffer on each side** (`PLOT_ZOOM_OUT_BUFFER = 0.08`, i.e. 8% of the home span per side — bugfix, this session, 2026-08-18, person-reported: a mark sitting exactly on the home view's own edge rendered only half-visible, with the old exact-home clamp giving no way to zoom out or pan even slightly to center it) and keeps the requested position within those same widened bounds (`boundLo/boundHi = homeLo∓buffer .. homeHi±buffer`); zooming IN still has no ceiling — this is "zoom out a *little* past the current default view, zoom in unlimited," the buffer existing purely so an edge mark can be fully centered with some padding around it, not to meaningfully change what "zoomed out" means. The clamped result becomes `xDomainMin/Max`/`yDomainMin/Max`, the actual pixel-mapping domain for that render; ticks/gridlines are recomputed from this *effective* (possibly zoomed) domain every render via a fresh `niceTicks()` call, so grid density stays sensible at any zoom level instead of only ever showing the home view's spacing. Because panning goes through this exact same clamp, the buffer also quietly fixes panning: even at 100% zoom (span == home span) there's now `±buffer` of room to slide the view, where before the position clamp forced `lo === homeLo` exactly whenever `span === homeSpan`, making any pan at the default zoom level a hard no-op.

**Bar charts made zoomable/pannable in X** by generalizing what was previously bespoke `groupW`/row-index arithmetic: a bar chart's raw X domain is simply `[0, rowCount]` (row-index units), fed through `niceTicks`-free but otherwise identical to line/scatter's domain pipeline — `xPix` becomes the single source of truth for row placement (`xPix(rowIndex)`, `xPix(1)-xPix(0)` for the per-row pixel width) instead of `left + groupW*rowIndex` computed directly from `plotW/rowCount`. Zooming into a bar chart's X now shows a subset of rows, wider; the X-tick label loop only walks the row range that overlaps the current domain (`Math.floor(xDomainMin)..Math.ceil(xDomainMax)`) instead of always `0..rowCount`.

**Clipping**: since a zoomed/panned view can legitimately place a point, bar, or line segment outside the plot rectangle (SVG doesn't clip that on its own), all marks render inside a `<g clip-path="url(#plotClip)">` wrapping a `<clipPath>` rect matching the plot area exactly; every legend (the multi-series swatch row, the scatter color-scale strip) renders *after* that group closes, since both sit outside the clip rect's bounds (above/right of it) and would otherwise be invisible.

**Interaction layer** (`plotSvg`/`window` listeners, registered once, reading/writing `plotZoom` and a `plotLastRender` snapshot — geometry + domain written at the end of every `renderPlotChart()` call — so mouse handlers never recompute the chart themselves):
- **Wheel** (`zoomPlotAt(dataX, dataY, factor)`): converts the cursor to data-space via the last render's mapping, proposes a new `plotZoom` scaled around that point (`factor<1` in, `>1` out), ignored when the cursor is outside the plot rectangle. The anchor point is left fixed on screen because the new domain is built symmetrically around it before clamping.
- **Middle-click-drag pan**: rAF-batched exactly like the panel-resizer drag handlers (`plotPanTicking` guard, same shape as `xTicking` elsewhere) — translates the domain by the pixel delta converted to data units, re-clamped every frame by `renderPlotChart` itself, so panning at 100% zoom (home view, no headroom) is naturally a no-op rather than needing a special case.
- **Left-click-drag rectangle zoom** (`PLOT_DRAG_THRESHOLD_PX = 3`, same threshold convention as the timeline minimap's own drag-select): a plain `<div>` overlay (`#plotDragRect`, not SVG — same reasoning as the minimap's drag overlay, a re-render mid-drag would otherwise wipe it) tracks the dragged rectangle in `#plotChartArea`'s own coordinate space; on mouseup, the pixel rect is inverse-mapped to a data-space `{x0,x1,y0,y1}` and set as the new `plotZoom` directly — no extra logic needed for "multi-step" (zooming further into an already-zoomed view), since it's just another absolute domain, clamped the same way. The mouseup's trailing `click` event is swallowed via a one-shot `plotDragSuppressClick` flag, the exact same pattern the minimap's `minimapDragSuppressClick` already established, so a drag never also triggers the mark-click jump-to-log-entry.
- **Zoom-level readout** (`#plotZoomLevelInput`, `updatePlotZoomIndicator()`): shows `round(avg(homeXSpan/curXSpan, homeYSpan/curYSpan) * 100)` as a %, skipped while the field has focus so it doesn't fight active typing. Typing a value (`setPlotZoomLevel`) sets an **absolute** zoom relative to the home span, centered on the current view's own center — not relative to whatever's currently on screen, matching how a zoom-level number is normally read. `+`/`-` buttons call `zoomPlotAt` centered on the current view; Reset sets `plotZoom = null`.
- **Hover tooltip** (`#plotTooltip`, `plotHandleHoverMove`): reads `plotHoverPoints`, one entry per rendered mark rebuilt alongside the marks themselves every render (`{px,py,rowIndex,xCol,yCol,...}` for line/scatter, `{bx,by,bw,bh,...}` for bar). Line/scatter use nearest-point-within-`PLOT_HOVER_MAX_DIST_PX`(14) — their marks are small circles, exact-pixel hit-testing would be too finicky; Bar hit-tests the actual rect bounds directly, since adjacent bars never overlap. The tooltip always looks the value up **live** from `extractRowsData[rowIndex].values[col]` rather than caching a formatted copy, so it shows the real extracted string (the "exact value" requirement) rather than an axis-rounded one. **Positioning** (`positionPlotTooltip`, bugfix this session, 2026-08-18, person-reported: a mark far right in the chart pushed the tooltip partly outside `#plotChartArea`, since the old fixed `cursorX + 14`/`cursorY - 28` offset never accounted for the tooltip's own rendered size): the tooltip's `offsetWidth`/`offsetHeight` are measured for real (after `innerHTML`/unhiding, so they're non-zero) and used to prefer above-and-right of the cursor, flipping to below and/or left independently on whichever axis actually lacks room, then clamped a final time to `#plotChartArea`'s own bounds (`PLOT_TOOLTIP_MARGIN = 4`) as a backstop. Placing it above the cursor by default (`PLOT_TOOLTIP_GAP = 12` clearance) is also what keeps the tooltip box itself from ever overlapping the pointer, not just an accident of the old fixed offset.

### "Create filter from plot view" (`FEATURE_BACKLOG.md` #11)

Two buttons live in `#plotZoomBar` (see above — the toolbar row above the chart, not overlaid on it) alongside the zoom controls: **`#plotFilterTimeRangeBtn`** ("Filter: time range") and **`#plotFilterEntriesBtn`** ("Filter: these entries") — both create a new child filter under the extraction node (`extractNodeId`), scoped to whatever's currently visible in the plot's own zoomed/panned viewport (the home/un-zoomed domain when no zoom is active, so clicking either with no zoom applied covers the whole extraction). "Time range" creates a `"timerange"` filter (see `docs/filters.md` → "Time filters") spanning the visible rows' min/max timestamp; "These entries" creates an `"idset"` filter (`docs/filters.md` → "Entry-set filter") matching exactly those rows, not just their time span.

`getPlotViewportEntries()` is the shared "what's on screen right now" primitive: it reads `plotLastRender.xDomainMin`/`xDomainMax`/`yDomainMin`/`yDomainMax` (the last real render's effective, possibly-zoomed domain on both axes) and, for each `extractRowsData` row, derives the same X position `renderPlotChart` itself would place it at — a bar chart's row-index slot center (`r + 0.5`, since bar's X is categorical row-index space, see above) or the X column's `parseValueForPlot`-parsed value for line/scatter — so it can never drift out of sync with what's actually drawn. A row also needs a **Y** check, not just X (bugfix, this session, 2026-08-28, person-reported): a row can have an in-range X but sit above/below the current Y zoom/pan, or have no finite Y at all for any of `plotConfig.yCols` (the same NaN-drop `renderPlotChart`'s own `series` construction applies) — either way it isn't actually drawn, so it's kept only if X is in range **and** at least one selected Y column's parsed value is finite and within the Y domain. A viewport containing zero rows (e.g. zoomed into a genuine gap between data points, or panned so nothing in X range has a Y value on screen either) shows a toast and creates no filter node.

Regression-tested: **Group 123** in `tests/philogg.regression.test.js` — both buttons under the home view (covers the whole extraction), the same buttons under a real zoomed viewport (scoped to exactly the visible rows), and the empty-viewport no-op case.

## Value assertions (extraction columns)

Per numeric-capable extraction column (`isPlottableType`: `float`/`int`/`hex`/`time` — same set the Plot tab already offers as axis candidates), an optional expected-value check: either a **range** (min and/or max, either side optional) or a **target ± tolerance**. Stored as `node.assertions = { [colIndex]: { mode: "range"|"target", min, max, target, tolerance } }` on the `extract` node itself — lazily created the first time a column gets one, never on other filter types.

**Checking a value**: `checkAssertion(node, colIndex, rawValue, type)` parses the cell via the same `parseValueForPlot` the Plot tab uses, and returns `true` (violated) / `false` (passed) / `null` (no assertion configured, or the value didn't parse as a number — an unparseable cell is neither a pass nor a violation, same "leave it alone" stance sorting already takes with unparseable values). `assertionSummary(node, colIndex)` scans the current `extractRowsData` once to produce the `{violations, checked, total}` used for the header badge.

**UI**: a small target-icon button (`.extract-assert-btn`, `ICON_TARGET`) appears in every numeric column's `<th>`, next to the existing sort button — same `stopPropagation` pattern on `mousedown`/`click` so opening the dialog doesn't also trigger the header's column-selection drag. Clicking it opens `#assertDialog` (mirrors the `#contextDialog`/`#linkDialog` small-modal pattern), where Range/Target±Tolerance is a two-button mode toggle rather than a dropdown. Once a column has an assertion, its header shows a small badge — "N of M outside range" — colored via `--level-error` only once `violations > 0` (a configured-but-currently-passing assertion stays quiet, not attention-grabbing). Violating cells in the table get `.assert-violation` (a `--level-error-soft` tint + colored text, same visual language as `.log-row.lvl-error`).

**Plot tab**: a point/bar whose value on *either* axis fails that axis's column's own assertion gets an extra error-colored ring/border drawn on top (line: outlined circle; bar: colored stroke; scatter: larger outlined ring) — on the theory that a plot is often where an out-of-range value actually gets *noticed*, since the table's cell tint is easy to scroll past. The ring color (`PLOT_ASSERT_COLOR`) is a plain hex literal matching `--level-error`, not a CSS custom property — kept consistent with every other plot color (`COLUMN_PALETTE`, `PLOT_COLOR_STOPS`), since the whole chart is built as raw SVG attribute strings in JS, not as CSS-styled elements.

**Persistence**: assertions travel with the node through `serializeFilterBranch`/`importFilterJson` (filter save/load JSON) and `cloneSubtree` (copy/paste), the same way `inverted`/`linkedId`/`contextBefore` etc. do — an assertion is part of what makes an extraction "the same filter," not a transient view setting. They are **not** reset when the extraction pattern is edited to add/remove columns; a stale assertion on a column index that no longer means what it used to is a known sharp edge (see Known limitations). `node.ignoredColumns` (see "Extraction: live pattern preview + ignored columns" below) follows this exact same 4-touch-point precedent (plus `snapshotSubtree`/`restoreSubtree` for undo/redo, which assertions also already went through).

## Column statistics

Min / max / mean / stddev per numeric-capable extraction column (`computeColumnStats`), rendered directly above the table (`#extractStatsBar`, `renderStatsBar`) — no toggle, always visible when at least one column is numeric, empty (and collapsed via `:empty{display:none}`) otherwise. Single pass to collect values + running min/max/sum, second pass for the variance sum — two passes over `extractRowsData`, not `Math.min/max(...spread)`, specifically to avoid the call-stack argument-count ceiling some engines hit on very large arrays (extraction results are already documented as "not virtualized — fine for realistically-sized results," so this stays in that same performance envelope rather than trying to be smarter). Numbers are formatted with the Plot tab's existing `formatAxisNumber` (nice/short representation) rather than a separate formatter.

## Extraction: live pattern preview + ignored columns

From person-supplied `REQUIREMENTS-extract-preview-and-ignore.md`: two related gaps in the extraction workflow — no preview of what a pattern actually captures *while typing it* (only an after-the-fact match count), and no way to have a placeholder anchor the pattern without becoming a permanent column.

### Ignored columns — data model (Option B)

**Option B chosen** over the doc's alternative ("a new `[ignore]` pattern token"): `node.ignoredColumns: number[]` — indices into the compiled pattern's columns — on the `extract` node itself, lazily created the first time a column gets ignored, same convention as `node.assertions`. Chosen because it's the smaller, self-contained change the doc itself flagged as the likely winner: the regex/matching is **completely untouched** (an ignored placeholder still anchors the pattern exactly as before), it's a pure display/export-time filter, and it doesn't need to decide how a new token interacts with column auto-naming (`value`, `value 2`, ...) the way a `[ignore]` token would. `isColumnIgnored(node, colIndex)` / `setColumnIgnored(node, colIndex, ignored)` are the two small helpers everything else goes through.

**A structural consequence worth understanding before touching extraction code again**: `extractColumns` (the module-level global) is no longer a dense, positional array — it's the *currently visible* subset of the compiled pattern's columns, and it can have gaps. Each surviving element keeps its original compiled-pattern position as a stable `.colIndex` property (this is the number `node.ignoredColumns` contains, the number `data-col`/`data-sort-col`/`data-assert-col` DOM attributes carry, and the number `node.assertions`/`plotConfig.xCol`/`.yCols`/`.colorCol`/`extractSortCol` are keyed by) — while `row.values` in each `extractRowsData` entry stays the **full, unfiltered** array (one value per compiled column, ignored or not), since matching itself never changes. `findExtractColumn(colIndex)` resolves a stable `colIndex` back to its (visible) descriptor, returning `null` when that column is currently ignored — every colIndex-keyed lookup (`computeColumnStats`, `assertionSummary`, `openAssertDialog`, `extractRowComparator`, the Plot tab's axis-candidate derivation) goes through it rather than bracket-indexing `extractColumns` directly. The cell-selection subsystem (`rowCells`/`rangeCells`/`columnsRangeCells`/`allCells`) was adjusted the same way — it walks `extractColumns`' actual `.colIndex` values instead of assuming a dense `0..length-1` range, so a shift-click column-range spanning an ignored column simply skips it rather than silently selecting hidden data.

**Excluded from**, per the requirements doc's list — all confirmed by Group 24's regression coverage: the extraction table (`renderExtractTable` never emits a `<th>`/`<td>` for an ignored column), column statistics (`computeColumnStats` returns `null` for one), the Plot tab's axis-candidate list (an ignored column is simply absent from `extractColumns`, so the existing `plottable` derivation — and its already-existing stale-selection reconciliation for `plotConfig.xCol`/`.yCols`, originally built for pattern edits — transparently also handles a column being ignored/un-ignored, no extra code needed there), copy-to-Excel/TSV export (`copyWholeExtractTable` now maps through each *visible* column's `.colIndex` rather than joining `row.values` wholesale; `extractSelectionToTSV` needed no change at all, since the cell-selection generators above already never produce a selection cell for an ignored column). Value assertions: an ignored column gets no assert button (no `<th>` at all), but — same accepted sharp edge as assertions surviving a pattern edit — an assertion configured *before* a column was ignored is left in `node.assertions` untouched, not deleted; it simply stops being checked/shown while the column stays ignored (`assertionSummary`/`computeColumnStats` both return `null` via `findExtractColumn`).

**Two toggle surfaces**, both wired to the same `setColumnIgnored`:
- **Post-creation**, in the existing `#extractPatternView` (the colored-chip template view above the table): `renderExtractPatternView` gained an optional third `opts` argument, `{ onToggle(colIndex) }` — when present, every chip becomes clickable (`.chip-toggleable`) and dimmed (`.chip-ignored`) when ignored, `title` reflecting the current state. `renderExtractTable` passes the **full, unfiltered** column list here (re-derived from `spec.columns` — NOT the filtered `extractColumns` — since this function independently re-walks every raw placeholder token in the pattern text and must produce exactly one chip per token regardless of ignore state) plus an `onToggle` that calls `setColumnIgnored`/`renderExtractTable` directly on the live node.
- **While authoring**, in the new `#filterPopup` preview (see below) — clicking a highlighted span toggles a *popup-local* working set, `filterPopupIgnored` (a `Set`, module-level `let`), applied to the node only on submit. Pre-populated from the edited node's existing `ignoredColumns` in edit mode (`openEditFilterPopup`), empty in create mode, cleared on close — so a filter can be created with columns already marked ignored, and re-opening Edit shows the current state immediately. `createFilterNode`/`updateFilterNode` both gained a 5th optional `ignoredColumns` parameter for this (backward compatible — every other existing call site is unaffected).

### Live pattern preview (`#filterPatternPreview`, in `#filterPopup`)

While typing/editing a pattern, `evaluateLiveMatch`'s existing 150ms debounce now also calls `updateFilterPatternPreview(val, baseEntries)` (one shared timer, not a second competing debounce) — it finds the *first* of `baseEntries` (the same rows `evaluateLiveMatch`'s match-count already uses) the compiled pattern actually matches, and renders that real message with each capture group's substring wrapped in a `<span>` colored via the same `columnColor`/`COLUMN_PALETTE` scheme the table and post-creation pattern view use, so colors stay visually consistent across all three. `white-space:pre-wrap` (matching `#detailMessage`'s own handling) so a multi-line stack-trace sample renders faithfully. Exact per-group `[start,end]` offsets come from a **second** `RegExp` built from `spec.regexStr` with the `d` (match-indices) flag (`m.indices[i+1]`) — the compiled `regex` actually used for matching is untouched, this is purely a preview-time convenience. No matching sample yet → a muted "No matching sample message yet." note (same spirit as the live-match count's `--warn` "0 of N" state, just phrased for a single-message preview). Hidden entirely for a non-extraction (plain text) filter or an invalid pattern.

**Gotcha hit and fixed**: the preview span's click handler must call `ev.stopPropagation()`. Without it, clicking a span — whose handler synchronously does `filterPatternPreview.innerHTML = ""` to re-render — detaches the clicked span from the DOM *while the click event is still bubbling*. The existing global "click outside a popup closes it" handler (`document`'s click listener, `!filterPopup.contains(ev.target) && ...`) then sees a detached `ev.target`, `contains()` correctly returns `false` for it, and the popup closes itself out from under the click. The post-creation pattern-chip toggle already had this same guard for the identical reason (a chip click re-renders the whole `#extractPatternView`); this is the second instance of the same class of bug, worth remembering for any future click handler that re-renders its own clicked ancestor. **A third instance turned up in the very next session** (person-reported): `treeContextMenu`'s click handler — right-click → "Edit filter…" opened `#filterPopup`, then the still-bubbling click reached the same global handler and closed it right back, since `closeTreeContextMenu()` only toggles a class rather than removing the menu item, so `ev.target` was simply *outside* `#filterPopup` this time rather than detached — same root cause (a click that opens something else must not keep bubbling to a close-on-outside-click listener), different trigger. Fixed the same way; see "Status / changelog" for the bugfix-session entry.

## Extraction workflow: live match feedback & token chips

- **Live match count** (`#filterLiveMatch`, `evaluateLiveMatch()`): debounced (150ms) re-evaluation of whatever's currently typed in `#filterInput`, run against `getVisibleEntries()` — the same rows the new filter would actually apply to. For an extraction pattern (`isExtractPattern`), shows "Matches: N of M rows · K columns"; for plain text, "Matches: N of M rows"; an invalid pattern shows "Invalid pattern" in the `--level-error` color. Zero matches gets a `--warn`-colored nudge rather than an error, since "the pattern is fine but nothing matches yet" is a normal mid-typing state, not a failure.
- **Live pattern preview** (`#filterPatternPreview`, `updateFilterPatternPreview()`, same debounce as the live match count above): for an extraction pattern, shows the pattern evaluated against a real sample message with matched substrings highlighted in place — see "Extraction: live pattern preview + ignored columns" below for the full writeup, including how this doubles as the ignore-toggle UI while authoring.
- **Token chips** (`#filterTokenChips`, one button per placeholder type, now grouped directly under `#filterInput` in the popup's input section — see "Filter popup" above): clicking inserts the literal token (`[value:float]`, `[value:int]`, `[value:time]`, `[value:word]`, `[value:hex]`, or `[*]`) at the current cursor position in `#filterInput` (`insertTokenAtCursor`), replacing any active text selection, same as normal typing would. (The old `#filterHint` plain-text fallback row listing the same placeholders was removed — the chips already insert them directly, making the text redundant.)
- **Extraction table column sort** (`.extract-sort-btn`, one small button inside each `<th>`): sorts `extractRowsData` itself — numeric-capable types (`float`/`int`/`hex`/`time`) numerically via the same `parseValueForPlot` the Plot tab uses, `word` lexically via `localeCompare`, unparseable values always last regardless of direction. The sort button is a separate nested control with its own `mousedown`/`click` handlers (`stopPropagation`) specifically so it doesn't trigger the header's existing mousedown-driven column cell-selection — the two interactions share the same `<th>` but are otherwise independent. **Because the sort reorders `extractRowsData` in place** (rather than keeping a separate display-order array), it also reorders the connected **Plot tab's line-chart point order** for that extraction, since line/bar plotting reads points in row order by design (see Plotting section above) — this was accepted as a reasonable trade-off over the bookkeeping risk of two parallel orderings that could drift out of sync. Sorting also clears any active cell selection in the table (`state.tableSelection = null`), since a positional "row,col" selection would otherwise silently point at different rows post-sort. Sort state resets whenever the active extraction node changes.

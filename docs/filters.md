# Filters

Filter types, value extraction, and the filter popup — current-state reference. See `PROJECT.md` for the node tree / memoization model these filters plug into.

## Value-extraction pattern language

A filter query is a candidate for extraction (`isExtractPattern`) the moment it contains a placeholder token — but whether it actually *becomes* an `extract` filterType now also depends on the popup's **"Extract values"** checkbox (see "Filter popup: Extract values checkbox, target chain, layout" below); with the checkbox unchecked, a wildcard pattern stays a plain `text` filter, matched via the same regex but only tested, not captured into a table. `compileExtractPattern(pattern)` turns the template into `{ regex, columns, regexStr }` — `regexStr` (the raw source string, added alongside the compiled `regex`) exists purely so the live pattern preview (see "Extraction: live pattern preview + ignored columns" below) can build its own second `RegExp` with the `d` (match-indices) flag without touching the hot-path `regex` used for actual matching; the wildcard-as-filter `text` path (see below) also reuses `regexStr` directly, just rebuilt with the case-sensitivity flag the "extract" path always hardcodes to insensitive.

Placeholders: `[value:float]` `[value:int]` `[value:time]` `[value:word]` `[value:hex]` and the bare wildcard `[*]`. `time` matches either a clock time (`16:23:27.697`) or a number+unit duration (`500ms`, `3.5s`). Columns are auto-named `value`, `value 2`, `value 3`... (never the type string itself — that caused a "floatfloat" header rendering bug early on, fixed by decoupling name from type). Regex is case-insensitive; a trailing `[*]` is greedy (captures the rest of the line), a mid-pattern `[*]` is non-greedy.

Right-click a message → **"Extract numbers from this message"** auto-generates a suggested pattern (`buildNumericExtractPattern`) by replacing every number token with a typed placeholder, recognizing embedded clock times/durations as a single `[value:time]` rather than splitting on the colons. It's inserted into the filter popup for review, not auto-submitted.

### Value conditions

`FEATURE_BACKLOG.md` item 5 ("Numeric greater/less-than filter"), implemented differently than originally scoped there per explicit person instruction: not a separate filter type, but a numeric condition folded directly into a `[value:float]`/`[value:int]` placeholder, e.g. `[value:float>=10]` (single condition) or `[value:int<20,>10]` (`,`-separated conditions, AND-ed together — matches ints strictly between 10 and 20). Working through the **existing filter/extract wildcard paths only**, as requested — no new filter type, no new filter-node field (the condition lives inside the pattern string itself, `node.value`, so every persistence carrier already threads it through untouched, unlike CLAUDE.md's "Known gotchas" note on genuinely new fields).

**Same-day follow-up** (person asked whether the syntax was sensible and requested an absolute-value variant — *"größer als absolut zehn"*): the condition separator was swapped from the originally-shipped `;` to `,` (more conventional), and a condition's operator can now be prefixed with `|` to compare against the captured value's **absolute value** instead, e.g. `[value:float|>=10]` matches both `10` and `-15`. `abs` is a per-condition flag, not per-placeholder — `[value:int|>10,<=100]` mixes an abs and a plain condition on the same placeholder.

`EXTRACT_TOKEN_RE` now captures an optional condition group right inside the brackets, and `compileExtractPattern` parses it (`parseValueConditions`) onto that column as `.conditions: [{op, value, abs?}, ...]` — absent (`undefined`) for a bare placeholder, same shape as before. A condition on `time`/`word`/`hex` (no natural numeric ordering) makes the whole pattern invalid (`compileExtractPattern` returns `null`), surfacing through the exact same "Invalid pattern" feedback the popup already had for a malformed regex — no new error path. The per-condition pattern (`VALUE_CONDITION_ONE`, e.g. `\|?(?:>=|<=|==|>|<)-?\d+(?:\.\d+)?`) is a single shared string constant, built once and reused by both `EXTRACT_TOKEN_RE` (recognizing the whole conditions substring as part of a token) and `VALUE_CONDITION_RE` (re-parsing that substring into individual conditions) — the two can't drift apart into recognizing different condition syntax.

**Matching**: the regex itself is unchanged (a comparison isn't expressible as a regex quantifier) — conditions are checked as a post-match numeric step, `Math.abs()`-ing the captured value first when `.abs` is set. `wildcardMatch(regex, columns, text)` is the one shared primitive (`getEntries`'s `"extract"` branch, `textFilterMatches`' wildcard path for a plain `"text"` filter carrying wildcard tokens, and the filter popup's live-match count all call it), so extraction and the wildcard-as-filter `text` path can never disagree about what a conditioned placeholder matches.

**Visualization** ("value pills"): every place that already showed a placeholder's type visually now also shows its condition (`describeValueConditions`, e.g. `≥10`, `<20 ∧ >10`, or `|≥10` for an abs condition) — the filter popup's live pattern preview (a small `.preview-value-cond` badge next to the matched value span), the post-creation `#extractPatternView` pattern-chip, and the extraction table's column header. The pattern preview's sample-message search was also changed to require the condition to actually hold (not just a structural regex match) — before this fix it could show, say, `score=0` as the "match" for `[value:int>=10]`, which the real filter would then reject; it now walks `baseEntries` checking `valueSatisfiesConditions` alongside the regex match, same as the real filter does, and falls back to the existing "No matching sample message yet." state if no entry actually satisfies the condition. For an abs condition, this means the shown sample can legitimately be a negative value.

Regression-tested: **Group 81** — `compileExtractPattern` parsing (single condition, `,`-separated multiple conditions in order, an abs-prefixed condition, a mixed abs/plain pair, the `time`/`word`/`hex` rejection, bare-placeholder backward compatibility), extraction and wildcard-as-text-filter matching against both an abs and a non-abs condition on signed data, the extraction table header + pattern-view chip visualization (including the abs `|` prefix), and the filter popup's live-match count + pattern-preview sample/badge (including the "no entry satisfies the condition" empty state and a negative-value abs sample).

## Filter popup: Extract vs. Add filter as two buttons, target chain, sectioned layout, "Filter for this ___"

Four person-requested passes on `#filterPopup`, same week (2026-08-17: sizing/layout → a section reorg + context-menu rename, same day → a bugfix flipping a checkbox's default, same day again → the checkbox removed entirely in favor of two plain buttons — described here as the current, post-all-four-passes shape end-to-end rather than layered deltas; see "Status / changelog" below for what changed in which pass).

**Extract vs. plain filter is decided ENTIRELY by which button gets clicked — there is no other state involved.** `#filterExtractBtn` ("Extract", `type="button"`) and `#filterSubmitBtn` ("Add filter" in create mode, "Save" in edit mode, `type="submit"`) both call the same `commitFilter(asExtract)`: `asExtract === true` (the Extract button) always creates/updates an `"extract"` node; `asExtract === false` (Add filter/Save) always creates/updates a plain `"text"` node — even when its `value` happens to contain `[value:...]`/`[*]` wildcard tokens (see below). This replaced an `#filterExtractCheckbox` toggle that shipped, then was bugfixed, then was removed outright the same week, per the person's explicit design principle: *"Das Filter Edit Dialog sollte keine grundlegend unterschiedlichen Zustände kennen, sondern nur unterschied initialisiert werden. alle Zustände sind dabei im Dialog selbst visualisiert. keine versteckte Logik im Hintergrund."* A checkbox — even correctly defaulted — still leaves a checked/unchecked *state* sitting in the popup between typing and submitting; two buttons leave none, since the decision is made and consumed in the same click. `filterExtractBtn.disabled` is the only thing anything still toggles ahead of time, and it's a pure capability gate (`isExtractPattern(filterInput.value)` — is there anything to extract at all), not a decision about which outcome will happen.

**A `"text"` filter's `value` can itself contain wildcard tokens** (created by clicking "Add filter"/"Save" while the input has `[value:...]`/`[*]` in it) — `getEntries`'s `"text"` branch detects that (`isExtractPattern(node.value)`) and, instead of a literal substring `includes()`, tests a regex built from `compileExtractPattern(node.value).regexStr` (rebuilt with the right case-sensitivity flag rather than the extraction path's hardcoded `"i"`) via the same `textFilterMatches()` used everywhere else — so column-restriction, case-sensitivity, and `inverted` (NOT) all keep working normally, unlike a real `"extract"` node where NOT/case/columns are unavailable (see "Inversion (NOT)" above). No new node field: the distinction is derived purely from `filterType` + whether `value` contains tokens, so every existing persistence carrier already threads it through untouched. Because of this, NOT/case-sensitivity/column-restriction are **never** conditionally disabled or hidden by pattern content anymore (an earlier pass did this, tied to the now-removed checkbox) — they're parameters of the "Add filter" outcome only, and Extract simply never reads them, so there's nothing left to gray out based on what's typed.

**Editing an existing filter goes through the exact same `commitFilter`.** Clicking "Save" on a node that's currently `"extract"` replaces it with a plain `"text"` filter; clicking "Extract" on a node that's currently `"text"` turns it into a real extraction — `updateFilterNode` always writes whichever type the clicked button dictates, there is no "preserve the old type" step. This is what makes both explicitly requested directions possible: editing an extraction down to a plain filter, and editing a plain filter up into an extraction.

Two spots set `#filterInput.value` directly (not via a real keystroke): `insertTokenAtCursor` (a token-chip click) and the "Filter for this ___" context-menu action (below). Both must call `updateExtractAvailability()` themselves, not just `evaluateLiveMatch()` — a plain `"input"` listener never fires for a programmatic `.value` write, and without this the Extract button could get stuck disabled after a wildcard was inserted any way other than typing it.

**`#filterTargetChain`** replaces the old plain-text `"Filter on “X”:"` / `"Edit filter on “X”:"` label body with the same `.crumb`/`.crumb-sep` pill-chain visualization `#breadcrumb` uses for the active filter chain next to the level filter (`renderFilterTargetChain()`, mirroring `renderBreadcrumb()`) — `#filterPopupLabel` itself is just a short static prefix ("Filter on:" / "Edit filter on:"). Renders `getChain(filterPopupBaseId)`, the node whose entries the popup's live-match/create/edit actually run against (the active node in create mode, the edited node's existing parent in edit mode).

**Layout**, structured into distinct sections top to bottom, each divided from the one above by a thin top border rather than a text caption on every row (only the two chip rows get a small `.filter-section-label`, since they'd otherwise be ambiguous at a glance): (1) `.filter-input-section` — `#filterInput` alone on its own line, with the `[float]`/`[int]`/... wildcard chips (`#filterTokenChips`, "Insert:") directly below it; (2) `.filter-settings-row` — case-sensitive + NOT, always both enabled; (3) `#filterPatternPreview` — the live pattern preview, unchanged; (4) `#filterColumnChips` ("Applies to:") — the column-restriction chips, always visible, never hidden by pattern content; (5) `.filter-footer-row` — `#filterLiveMatch` (the match count, always previewing the "Add filter" outcome specifically — see `evaluateLiveMatch`) left-aligned, `.filter-footer-actions` (`#filterExtractBtn` then `#filterSubmitBtn`) right-aligned. `#filterExtractBtn` is styled `.btn-mini-secondary` (bordered/transparent) so `#filterSubmitBtn` (`.btn-mini`, accent-filled) stays the visually primary action. The old `#filterHint` row ("Werte extrahieren: `[value:float]` ...") was removed outright; the token chips already insert those exact wildcards directly. `#filterPopup` gained `max-height:calc(100vh - 76px); overflow-y:auto` — it previously had no size cap at all, so on a short viewport its bottom content could render past the visible viewport with no way to scroll to it; now it scales with its content up to the viewport and scrolls internally past that.

**"Filter for this ___"** (row context menu, right-click a log entry) replaced the old, message-only **"Extract numbers from this message"** (`#ctxExtractNumbers` → `#ctxFilterForColumn`). `resolveContextFilterColumn(ev)` walks up from `ev.target` (the row's `"contextmenu"` listener is attached once per row, so `ev.target` is whichever inner `.col-time`/`.col-level`/`.col-thread`/`.col-loc`/`.col-method`/`.col-msg` span the pointer actually landed on) to find which `TEXT_FILTER_COLUMNS` entry was clicked, falling back to `"message"` for anything else (row background/gutter, a link-view pair's brace). The menu label and the resulting action both read that column: `"Filter for this " + column.label`, prefilling `#filterInput` from `textColumnValue(entry, column.key)` and pre-selecting that column in `filterPopupColumns` (the "Applies to" chips) — reusing the exact same lookup table the column-chip feature already uses, so the two can't drift apart. Numeric content in that column's text still becomes a `[value:...]` wildcard pattern via the unchanged `buildNumericExtractPattern`; a column with no numeric content (most Method/Thread values, or a plain-text message) falls back to the **exact literal text** instead of a "No numeric values found" no-op toast, so the action is useful there too — "find this exact line/value again." This action never decides text-filter vs. extraction itself: it just opens the popup pre-filled, and whichever button gets clicked afterward decides, same as typing the pattern by hand would.

Regression-tested: **Group 39** covers the wildcard-as-filter matching semantics (direct `getEntries()`/`textFilterMatches()` calls — case-sensitivity, NOT, and an unaffected real `"extract"` node) and the target chain. **Group 40** covers the section reorg's DOM structure/top-to-bottom order and "Filter for this ___" across three columns (message/method/thread), including the literal-text fallback. **Group 41** is the current, canonical coverage for the two-button redesign itself: the checkbox's absence from the DOM, the original person-reported repro (context-menu prefill → "Add filter" → plain `"text"` node, never a silent extraction), the same outcome for a hand-typed Ctrl+F pattern (one shared code path, not per-entry-point branching), extraction still reachable via the Extract button, and — the part a checkbox-based design structurally couldn't do — editing an *existing* extraction and clicking "Save" to turn it back into a plain filter, and editing an *existing* plain filter and clicking "Extract" to turn it into a real extraction, both directions explicitly requested. Groups 8, 24, and 35 were updated in place where they'd relied on the checkbox (NOT staying available regardless of pattern content now, per Group 8's updated note; clicking `#filterExtractBtn` directly instead of checking a box first, in Groups 24 and 35). The `max-height`/`overflow-y` sizing fix and the buttons' visual styling are pure CSS with no jsdom-observable state and are deliberately not re-tested, same "no layout engine" gap as the `#viewBar` flex-direction regression noted in "Testing approach" below.

## Text filter: case-sensitive + target column

`FEATURE_BACKLOG.md`'s "Case-sensitive option for text filters" and "Per-filter target column", bundled into one feature (same session, 2026-08-16). Both are `text`-filter-only options (extract patterns already match via their own regex against `entry.message`, unaffected):

- **`node.caseSensitive: boolean`** (default/absent = case-insensitive, unchanged behavior). A checkbox in the filter popup, **default unchecked** as requested.
- **`node.columns: string[]`** — restricts matching to specific table columns instead of the whole raw line. Six options mirroring what the log table itself shows: `time` (`entry.tsRaw`), `level`, `thread`, `location` (`entry.locationFull`), `method`, `message`. One toggle chip per column in the popup, **same selection logic as the level filter bar** (`state.levelFilter`/`applyLevelFilter`): none selected searches every column (`entry.raw`, byte-identical to the pre-existing behavior), one or more restricts the search to just those — so selecting *every* chip and selecting *none* produce the identical matching result, just via different code paths (no special-casing to collapse "all" back to "none" in storage — not worth the complexity for a functionally-equivalent outcome).

Shared matching logic lives in `textFilterMatches(entry, value, caseSensitive, columns)` (used by both `getEntries`'s `"text"` branch and the filter popup's live-match preview, so the two never disagree) and `textColumnValue(entry, key)` (the column-key → entry-field lookup table). Popup state: `filterCaseCheckbox` (`#filterCaseCheckbox`) and `filterPopupColumns` (a working `Set`, mirrored onto `.column-chip.active` classes via `renderFilterColumnChips()`), same create/edit/submit lifecycle as the pre-existing `filterPopupIgnored` (extract's ignored-columns set) — pre-filled from the node in edit mode, applied on submit, reset on close. `updateInvertAvailability()` (already responsible for disabling NOT on an extraction pattern) now also disables the case checkbox and hides the column chips the moment the input is detected as an extraction pattern, and clears both from the node if an existing `text` filter is edited into one.

Threaded through every persistence carrier per CLAUDE.md's "Known gotchas" note on filter-node fields: `cloneSubtree`, `snapshotSubtree`/`restoreSubtree` (undo/redo), `serializeFilterBranch`/`importFilterJson` (save/load JSON — `importFilterJson` validates `columns` entries against the known column-key set, dropping unrecognized ones from a hand-edited file), and `serializeFilterTreeForCache`/`materializeCachedFilters` (session cache) — same 4-touch-point pattern already established for `node.ignoredColumns`/`node.assertions`.

Regression-tested (new **Group 35** in `tests/philogg.regression.test.js`): `getEntries` matching semantics for each column key, the "all columns = no restriction" equivalence, case-sensitive vs. case-insensitive matching, popup defaults/live-match/chip-toggling, edit-mode pre-fill and re-save, the extract-pattern field-clearing edge case, and all four persistence carriers round-tripping both fields.

## Regex filter type: "Interpret input as regex"

`FEATURE_BACKLOG.md` #16, implemented per the person's own stated refinement: not a separate filter type, but a checkbox (`#filterRegexCheckbox`, "Interpret input as regex") at the very top of `#filterPopup`, above the input itself. Toggling it on sets a new `node.isRegex: boolean` on an otherwise ordinary `"text"` filter node (default/absent = the existing wildcard-token/plain-substring behavior, completely unchanged) — this is deliberately additive to the same filterType, not a fourth match-mode competing with `"text"`'s existing plain/wildcard split, since case-sensitivity and column-restriction (both `"text"`-only options already) are exactly as meaningful for a real regex as for a plain string.

**Compilation and matching**: `compileRegexFilter(source, caseSensitive)` — `new RegExp(source, caseSensitive ? "" : "i")`, wrapped in a `try/catch` returning `null` on a `SyntaxError` — is the one shared primitive `getEntries`'s `"text"`/`isRegex` branch, `textFilterMatches` (a new optional `regexObj` parameter, checked before the existing `wildcardRegex` parameter), and the popup's `evaluateLiveMatch` all go through, so the three can never disagree about what's a valid pattern or what it matches. When `regexObj` is set, `textFilterMatches` runs `regexObj.test(...)` against either the target column(s) (same `columns`/`textColumnValue` restriction every other `"text"` mode already respects) or the whole raw line — no wildcard-token compilation, no `[value:...]` capture semantics, just a real `RegExp.test()`. An invalid regex compiles to `null` and degrades gracefully everywhere it's checked: `getEntries` returns an empty result (no throw), the popup's live-match count shows an inline `--level-error` "Invalid regex" state (the same visual language as the pre-existing "Invalid pattern" state for a malformed extraction pattern), and `commitFilter` refuses to submit, flashing `#filterInput`'s existing `input-error`-style shake animation (a parallel `input-regex-error` class/keyframe) and leaving the popup open to fix it — mirroring the extraction pattern's own "won't compile" submit guard exactly, just for a different compiler.

**UI**: `updateRegexModeUI()` toggles `#filterTokenChips`' visibility (the `[float]`/`[int]`/`[time]`/… insert chips — meaningless once the input isn't the wildcard-token language) and force-hides the live pattern preview (`#filterPatternPreview`, which only ever shows wildcard capture-group highlighting) the moment the checkbox is checked; every other section of the popup — case-sensitivity, NOT, the "Applies to" column chips, the live match count, the target chain — stays exactly as visible/usable as it already was, per the explicit instruction to hide/disable ONLY the wildcard-token-specific pieces. `updateExtractAvailability()` now also disables the Extract button whenever regex mode is on (a raw regex carries no `[value:...]` placeholder vocabulary for the extraction table to build columns from), regardless of what's typed. Opening the popup to edit an existing regex `"text"` node pre-checks the box from `node.isRegex` and runs the same UI update, same as every other popup field's edit-mode pre-fill.

Threaded through every persistence carrier per CLAUDE.md's "Known gotchas" note, the same 6-touch-point pattern `caseSensitive`/`columns` already established: `cloneSubtree`, `snapshotSubtree`/`restoreSubtree` (undo/redo via delete), the field-edit-undo `captureNodeFields`/`applyNodeFields` carrier (in-place edits, e.g. clicking "Save" on an existing node — a 4th carrier beyond CLAUDE.md's three named ones, since `updateFilterNode` calls funnel through it too), `serializeFilterBranch`/`importFilterJson` (save/load JSON), `serializeFilterTreeForCache`/`materializeCachedFilters` (session cache).

Regression-tested: **Group 122** — `getEntries`/`textFilterMatches` regex semantics (real regex anchoring/case-sensitivity, column restriction, an invalid pattern degrading to an empty result without throwing), the popup's UI (chips/preview hidden, case/NOT/columns still usable, Extract disabled, live-match count, the inline "Invalid regex" state, submit refusing an invalid pattern and staying open), and all four persistence carriers (plus the field-edit-undo carrier) round-tripping `isRegex`.

## Entry-set filter: `"idset"`

An explicit, pre-computed match set — `node.value: string[]`, an array of entry ids — matched via a plain `Set` lookup in `getEntries` (`parentEntries.filter(e => idSet.has(e.id))`). The same "second, non-rule-based source of truth" shape `"timerange"` and the auto-managed `"bookmarks"` node already use, but generic and person-creatable (unlike `"bookmarks"`, which is a singleton auto-synced from `state.bookmarks`) — built for "Create a filter from the plot view"'s part (b) below, but not itself plot-specific: anything that can name an exact set of entry ids can produce one. `idSetFilterName(ids)` names the node by count ("N entries (plot view)") since the ids alone don't say *why* they were picked — the framing lives in whichever UI action created it. No dedicated edit UI (same tier as `"and"`/`"or"`/`"link"`/`"level"` — the tree context menu's "Edit filter…" stays gated to `"text"`/`"extract"`/time-filter types).

**No new persistence-carrier code needed** — like `"timerange"`, its value rides the existing generic `node.value` field every carrier (`cloneSubtree`, `snapshotSubtree`/`restoreSubtree`, `serializeFilterBranch`/`importFilterJson`, `serializeFilterTreeForCache`/`materializeCachedFilters`) already copies/serializes for every filter type — this is the same "the gotcha doesn't apply here" case `"timerange"`'s own writeup documents, verified directly (not just assumed) via a real `cloneSubtree` copy/paste round trip in Group 123.

## "Create a filter from the plot view" (FEATURE_BACKLOG.md #11)

Resolves the backlog item's own stated open question — "which of the two (time-range vs. exact-entries), or both" — by implementing **both**, off the Plot tab's own zoomed/panned viewport (see "Plot zoom/pan" in `docs/extraction-and-plotting.md` for the zoom mechanism this reads from). Two buttons in `#plotZoomBar` (next to the existing zoom controls, following that same "small buttons in the plot's own toolbar" convention rather than a new context menu or dialog):

- **`#plotFilterTimeRangeBtn`** ("Filter: time range") creates a `"timerange"` filter (see "Time filters" above — the existing, generic time-range node, reused rather than inventing a new one) spanning the min/max timestamp of whatever's currently visible in the plot.
- **`#plotFilterEntriesBtn`** ("Filter: these entries") creates an `"idset"` filter (above) matching exactly those entries — not just their time span, but the specific rows.

Both are attached as a new child under the extraction node itself (`extractNodeId`), narrowing its own result further — the same tree position a hand-built time filter under an extraction would occupy.

**"Currently visible" = the Plot tab's own zoomed/panned viewport**, not the whole extraction result — `getPlotViewportEntries()` reads `plotLastRender`'s `xDomainMin`/`xDomainMax` (the home/un-zoomed domain when no zoom is active, so clicking either button with no zoom applied naturally covers the full extraction) and, for each `extractRowsData` row, derives its X position the *exact same way* `renderPlotChart` itself positions marks — a bar chart's categorical row-index slot center (`r + 0.5`), or the X column's own `parseValueForPlot`-parsed value for line/scatter — so this can never disagree with what's actually drawn on screen. A viewport with nothing currently visible (e.g. zoomed into a genuine data gap) shows a toast and creates no filter, rather than a broken empty one.

Regression-tested: **Group 123** — the `"idset"` `getEntries` branch and its `cloneSubtree` round trip directly, both buttons under the home (un-zoomed) view creating a filter that spans/matches the WHOLE extraction, the same buttons under a real zoomed viewport creating a filter scoped to exactly the rows visible there, and the empty-viewport no-op case.

## "Add to selection" — top-level, named, deletable `"idset"` selection filters from log rows

Turns the right-clicked log row — or the whole current multi-selection (`state.logMultiSelect`, see `docs/ui-and-views.md` → "Row multi-select + copy") when 2+ rows are selected — into (or *into an existing*) `"idset"` filter node (above) matching exactly those entries. Reuses the same generic entry-set filter type "create a filter from the plot view" introduced, rather than a second, parallel type.

Redesigned this session (person request) from the original single-item "Filter from selection" (which created a plain, nested-under-`state.activeId` `idset` node from a 2+ row multi-selection only). The person's framing: a selection is independent of whatever filters happen to sit above it in the tree, so it belongs at the **top level**, directly under the file — the same place the auto-managed "Bookmarks" node lives (`syncBookmarksFilterNode`, see "Bookmarks rework" in `PROJECT.md`) — not nested wherever the tree's active node happens to be.

**Marker field**: a selection filter is an `"idset"` node with `node.selectionFilter === true` — a new field needed because `"idset"` is shared with the plot-view producer above, whose nodes must NOT be treated as person-managed selections (excluded from the submenu below, from `selectionFilterNodesForRoot`, from everything this feature does).

**Placement**: `createSelectionFilterNode(rootId, ids)` always creates the node as a new, top-level child of the entry's root FILE node — `root.children.unshift(node.id)`, the exact same "top-level, unshifted so it stays near the top" placement `syncBookmarksFilterNode` uses for Bookmarks — never as a child of `state.activeId` like every other context-menu filter action.

**UI**: the log row right-click menu (`#contextMenu`) has `#ctxAddToSelection` ("Add to selection"), a submenu trigger next to "Filter for this ___". Clicking it opens `#addToSelectionMenu` (built on demand, same "assemble innerHTML from data" shape `#treeContextMenu` already uses), listing every existing top-level selection filter under the entry's root file by name (`selectionFilterNodesForRoot`) — clicking one calls `addRowsToSelectionFilter(nodeId, ids)`, which appends the current row(s)' ids to that node's `value` array, deduped, without touching its name (a person may have renamed it). Below a separator, "Create new selection filter" calls `createSelectionFilterNode` instead. With zero existing selections, the submenu just shows the create entry — no empty/broken list. The current row(s) are whichever the right-clicked entry is, or the full `state.logMultiSelect` when 2+ rows are multi-selected (`currentSelectionRowIds()`) — unlike the original, a *single* selected/right-clicked row now qualifies too.

**Naming**: auto-named via `nextSelectionFilterName()` at creation — a plain ordinal, "Selection 1", "Selection 2", ... (counted across every `selectionFilter` node in the tree, not per-root-file) — no dedicated naming prompt exists anywhere else in the filter tree either (every filter node is auto-named, then optionally renamed via the tree context menu's "Rename…", the same standard path a selection filter uses too). **Bugfix, this session, 2026-08-28, person-reported**: originally named via `idSetFilterName(ids, "selection")` ("N entries (selection)"), a one-time snapshot of the selection's size at creation — `addRowsToSelectionFilter` deliberately never rewrites `node.name` afterward (a person may have renamed it), so growing a selection kept its stale initial-count name forever. The plot-view producer's own `"idset"` nodes (no `selectionFilter` flag) are unaffected and still use `idSetFilterName`'s count-based name.

**Differences from Bookmarks** (all deliberate, person-specified): a selection filter is **not** `locked` — it's deletable through the normal filter-node delete action (✕ button, middle-click, tree context menu, Delete key), unlike the auto-managed, undeletable Bookmarks node. There is **no "always show" toggle** — the app's only such control, `#btnPinBookmarks` ("Pin bookmarks into Filtered View", `state.pinBookmarksInFilteredView`), is hard-wired to `state.bookmarks` specifically; nothing analogous reads or affects selection filters. And **entries added to a selection are never bookmarked** — `state.bookmarks` is never touched by any of this; membership lives purely in the idset node's own `value` array.

## Text-filter match highlighting

Lighter alternative to `FEATURE_BACKLOG.md` #13's "why is this row here" popup idea (that entry is left as-is, still unimplemented, per explicit person instruction — this feature was requested as a separate implementation, not a replacement). Marks the exact substring an active `text` filter node matched, inline in the Filter view's rows and/or the entry-detail panel, instead of requiring a click to find out why a row is present.

Runtime-only/derived — no new filter-node field, so none of the "Known gotchas" persistence carriers (CLAUDE.md) need touching. Core pieces, all just above `textFilterMatches` in `philogg.html`:

- **`getTextMatchHighlightNodes()`** — which `text` filter node(s) to pull matches from right now. Gated first by the master on/off, `textMatchHighlightEnabled` (`localStorage["philogg-text-match-highlight-enabled"]`, **default `true`**) — a **view-bar toggle button**, `#btnTextMatchHighlight` (next to `#btnPinBookmarks`/`#btnMultilineMsg`/`#btnColumns`, same plain-persistent-toggle shape — moved out of Settings same-day, person-requested: reached for while looking at the view, not an app preference). When on, `textMatchHighlightScope` (`"last"` / `"any"`, `localStorage["philogg-text-match-highlight-scope"]`, **default `"last"`**, a Settings → Behavior dropdown) picks which nodes: `"last"` = only `state.activeId` itself, and only if it IS a `text` filter — **deliberately no fallback** to a text-filter ancestor if the active node is some other type (an explicit person decision when this was scoped, not an oversight); `"any"` = every `text` filter node in the active node's own ancestor chain (`getChain`), root to active.
- **`textFilterMatchSpec(node)`** — mirrors the wildcard/token compilation `getEntries`'s `"text"` branch performs, recomputed fresh per render call (not cached on the node) so an in-place filter edit (`updateFilterNode`/`applyNodeFields`) can never leave a stale spec behind.
- **`findMatchRanges(text, spec)`** — every `[start,end)` occurrence (not just the first) of a plain substring or, for a wildcard/value-token pattern, every regex occurrence that also satisfies its numeric conditions (re-running `valueSatisfiesConditions` per occurrence, since a structurally-matching span can still fail e.g. `[value:float>=10]`).
- **`textMatchTargetColumns(node)`** / **`matchRangesFor(text, columnKey, nodes, specs)`** — a filter's own target-column restriction (see "Text filter: case-sensitive + target column" above) decides which displayed column(s) get marked; a column-less filter (which searches the whole raw line) has no single on-screen counterpart once the raw tab-separated line is thrown away, so every displayed column is searched independently. Match ranges are searched against whichever text is actually **on screen** for a field (`formatTime(e.ts)`, `e.locationShort`, ...) rather than the raw value the filter engine itself tests (`e.tsRaw`, `e.locationFull` — see `textColumnValue`); those two can diverge for "time"/"location" specifically, so searching the displayed text keeps the marked span trivially correct at the cost of occasionally under/over-marking those two columns relative to the literal underlying match — an accepted, cosmetic-only trade-off.
- **`markRangesHtml(text, ranges)`** — wraps each range in `<mark class="text-match-mark">`, `escapeHtml`-ing every other slice (log content is never trusted as markup). Styled via `color-mix(in srgb, var(--warn) 55%, transparent)`, theme-consistent without a hardcoded color.

Every node's own match test is **re-run per entry**, not "trust the chain already filtered this in" — specifically so `or`/`link` nodes elsewhere in the tree (whose entries can reach a view without having passed every linear ancestor) never produce a highlight for text that isn't actually present in that particular entry.

Two independent "where" toggles, `textMatchHighlightInRows` (`renderVisibleRows`) / `textMatchHighlightInDetail` (`updateDetailPanel`), both `localStorage`-backed and **default ON**. Both these and `textMatchHighlightScope` are a **standing preference, always visible and editable in Settings → Behavior regardless of the master button's on/off state** — an explicit same-day follow-up request: the button is just a quick flip over whatever's configured there, Settings must never depend on it (an earlier version of this feature hid those rows while the button was off; that dependency was removed outright, not just relaxed). `renderVisibleRows` computes the active match nodes/specs once per render call (not per row) and reuses them across the virtualized row loop; `updateDetailPanel` does the same per selection change, and falls back to its original plain `textContent` assignment (not `innerHTML`) whenever there's nothing to mark, preserving the pre-existing "message can never be interpreted as markup" guarantee for the common case.

`tests/philogg.regression.test.js` Group 93 (new, revised twice same-day: first for the button move, then to drop the settings-row hide/show dependency on it): master button defaults/click-toggle/persistence, and explicit assertions that the scope select and both "where" checkboxes stay visible, enabled, and changeable while the master button is off. 1766 passed, 0 failed.

## Link filter: nearest-neighbor pairing

Built for the "give me the last position reading before each offset-computed event" use case. `getEntries` for a `link` node walks its reference-side entries and, for each one, binary-searches (`lowerBoundByTs`) the target side for the Nth entry strictly before/after it in time (`findNthOccurrence`); references with no match are dropped (no placeholder rows), duplicates are allowed. Each match becomes a **pair entry** (`buildPairEntry`) that **duck-types as a normal entry** — same `id`/`ts`/`level`/`message`/`raw` fields — specifically so every other mechanism (text/time filters, the level quick-filter, and crucially the extraction engine) works on link results completely unchanged. The two real underlying entries are combined into `message`/`raw` with the separator `PAIR_SEPARATOR = " ⟶ "`, which is why an extraction pattern spanning both sides of a pair looks like:

```
Position x=[value:float] y=[value:float] ⟶ Offset computed: [value:float]
```

A pair entry's `raw` is **not** a clean concatenation the way `message` is — it's the two source entries' full raw (tab-separated) lines with metadata in between, so it's non-contiguous and a pattern spanning the `⟶` separator can't match it the way it matches `message`. **Bugfix, this session, person-reported**: a `filterType: "extract"` node and a `filterType: "text"` node holding the *identical* wildcard/extract-token pattern gave different results on link-derived pairs — Extract always found the value table, Save (`"text"`) found nothing. `getEntries()`'s `"extract"` branch always tested `wildcardMatch(spec.regex, spec.columns, e.message)`, but `textFilterMatches()`'s own wildcard-as-text branch (a `"text"` node whose value contains extract tokens, authored via "Add filter" rather than "Extract" — see `isExtractPattern`) defaulted to `e.raw` when no column restriction was set. Fixed to default to `e.message` there too, matching the extract branch. See `tests/philogg.regression.test.js` Group 134.

### Chained links (multi-hop tuples) — design, bugs fixed, and the new dialog

A "chained link" is a `link` node whose reference side was baked FROM another `link` node — building it by hand (link A→B, then link (A→B)→C, passing the first link's node id to `createLinkNode` as the second link's reference at creation time) still works exactly the same way, and it's also what the multi-hop dialog below generates under the hood. Since the `bakedA`/`bakedB` correction (see "Self-contained AND/OR/LINK" above), what actually gets stored is different: baking a `link` node (via `bakeNodeCondition`) copies its own `filterType: "link"` plus its `bakedA`/`bakedB`/`linkDirection`/`linkN`/etc. as a **nested baked predicate-pair**, not a reference to its node id — so "chained" here means "one link node's own baked condition nested inside another's `bakedA`/`bakedB`," evaluated recursively by `getEntriesFromBaked`. Three bugs in the underlying pairing mechanism were fixed in an earlier session (see `REQUIREMENTS-link-chaining-and-multiway.md`, supplied by the person, for the original repros):

- **Wrong time anchor when chaining.** `buildPairEntry(refEntry, targetEntry)` now stamps a second field, `matchTs: targetEntry.ts` — the actual matched entry's own timestamp — alongside the existing `ts` (still `refEntry.ts`, unchanged, since BASELINE anchor semantics and the display-facing pair timestamp weren't part of the bug and nothing asked for them to change). `getEntries()`'s `link` branch now searches from `refEntry.matchTs ?? refEntry.ts` instead of always `refEntry.ts`, so a second hop anchors on the *previous hop's actual match*, not the original outer reference's timestamp. A plain, non-chained `link` node is unaffected (a real entry has no `matchTs`, so this falls back to its own `.ts` exactly as before).
- **Highlighting stopped at one nesting level.** `computeHighlightMap()`'s `link` branch used to colour `pair.first.id`/`pair.second.id` directly — correct only when both sides happen to be real entries. It now calls `getTupleEntries(pair)` (below) and colours every id that comes back, so a coloured rule on a chained link colours every real entry at every nesting level.
- **Double-click jump broke on the nested side.** Same root cause, UI-facing symptom: `buildPairRow`/`revealInHighlightView` need a *real* entry id to resolve through `entryIndex`. `renderLinkView` now also flattens via `getTupleEntries(pair)` and renders one row per real entry (with `N-1` `Δ` labels between them) instead of always exactly two rows via `pair.first`/`pair.second` — so a 3+-way tuple gets a 3+-row `pair-block` in the Link view for free, and every row's double-click always has a real id.

**`getTupleEntries(entryLike)`** is the fix's shared primitive: `entryLike.isPair ? getTupleEntries(entryLike.first).concat(getTupleEntries(entryLike.second)) : [entryLike]` — recurses through arbitrarily many nesting levels instead of assuming exactly one. This is the "proposed (not mandatory) helper contract" from the requirements doc, kept as the actual implementation shape.

**Design direction chosen: A ("fix the nesting, keep pair-of-pairs"), not B ("native flat tuple").** The requirements doc offered two directions; A was chosen because it's the smaller, lower-risk diff — a chained/multi-hop tuple is still just `link` nodes referencing each other's ids via `inputA`/`inputB`, not a new shape. The cost is that consumers which used to assume "exactly one level of `.first`/`.second`" needed to switch to `getTupleEntries()` instead (three call sites: `computeHighlightMap`, `renderLinkView`, and nothing else touches `pair.first`/`pair.second` directly) — a small, closed set, which is what made A viable here. Direction B (a flat `entries: [...]` array + one `buildTupleEntry`) would have removed the "one level of nesting" assumption at its source rather than patching each consumer, but was judged not worth the larger diff (new node shape, new serialization fields, `and`/`or`'s and the extraction engine's `⟶`-joining logic would all need re-auditing against the new shape) for what direction A already delivers correctly.

### Multi-way link definition in one dialog

The bulk "Link…" action (right-click / action-bar on a 2+ filter multi-selection, same file) accepts **2 or more** filters, not just exactly 2 (`describeBulkActions`: AND/OR stay 2-filter-only — generalizing set intersection/union to N filters wasn't asked for — but Link's bulk action is offered for any 2+, labeled "Link… (N-way)" past 2). `openLinkDialog` builds a dialog with a **Reference** dropdown (`#linkRefSelect`, unchanged) plus a dynamically-rendered list of **hop rows** (`#linkHopsList`, one per remaining selected filter, `renderLinkHops()`) — each hop has its own `#` (N) input and before/after direction select, worded as "Find the Nth **{target}** entry {before/after} {anchor}", where `{anchor}` is the reference's name for the first hop and "the previous match" for every hop after that.

**Hop order = selection order** (the filters' order in the `ids` array passed to `openLinkDialog`, minus whichever one is chosen as reference) — `state.multiSelect` is a `Set`, which preserves insertion order, so this is just the order the person Ctrl-clicked the filters in. There's no separate drag-to-reorder UI; re-selecting in a different order is how to change hop order.

**Create is sugar over the existing chaining mechanism**: it walks the hop rows in order, calling `createLinkNode(curRefId, hop.targetId, hop.direction, hop.n, {orderEnforced, exclusive})` once per hop, where `curRefId` starts as the chosen reference and becomes each new hop node's own id for the next iteration — `createLinkNode` bakes THAT node's own condition via `bakeNodeCondition` at the moment it's passed in, which for a `link` node means nesting its `bakedA`/`bakedB`/`linkDirection`/etc. as the next hop's `bakedA` (see "Chained links" above) — i.e. it builds exactly the same nested-baked-link structure a person would otherwise build by hand. Each created node is placed directly under FILE per the placement rule above (`createLinkNode`/`createAndOrNode` always insert as a new top-level child of the shared root file, never nested under either input) — chaining lives entirely in the baked data, with no bearing on tree position. This is also why Bug 1's fix (`matchTs`) is what makes the dialog's multi-hop result correct, not new dialog-side logic.

### Opt-in options: order enforcement & exclusive matches

Both are per-`link`-node boolean flags (`linkOrderEnforced`, `linkExclusive`), set via the two checkboxes in `#linkDialog`, **default `false`** (unchanged behavior when off) — carried through `createLinkNode`'s new optional 5th `opts` argument (`{orderEnforced, exclusive}`), and persisted alongside `linkDirection`/`linkN` everywhere that already serialized those: `cloneSubtree` (copy/paste), `snapshotSubtree`/`restoreSubtree` (undo/redo), `serializeFilterBranch`'s `serializeSubtree` + `importFilterJson`'s `materialize` (filter save/load `.json`), and `serializeFilterTreeForCache`'s `ser` + `materializeCachedFilters`'s `materialize` (session cache). Additive-only fields, so `FILTER_FILE_VERSION` was **not** bumped — a filter file saved before this feature loads exactly as it did before (both new fields simply materialize `false`), and files saved with them set load correctly on older... well, there is no older-version reader to worry about going forward, but the point is nothing about the existing format 2 envelope changed.

- **Exclusive matches** (`linkExclusive`): once a target entry has been matched for one reference entry, no later reference entry in the *same node's* result can reuse it — implemented as `findNthOccurrenceExcluding()` (a variant of `findNthOccurrence` that skips ids in a running `usedIds` set) plus a `usedIds` `Set` scoped to one `getEntries()` call. **Scope chosen: globally across every tuple the node produces** (not per-hop-within-a-tuple) — the requirements doc flagged this as the more likely reading of the request and asked for it to be confirmed; going with it here since a chained/multi-hop tuple is still evaluated one `link` node at a time (each with its own `getEntries()` call and its own `usedIds`), so "global" here means "across this one node's reference entries," which is the natural unit exclusivity would apply to.
- **Enforce chronological order** (`linkOrderEnforced`): after a hop finds a candidate match, the match is **rejected (treated as no match, same as an unmatched reference — dropped, not retried)** if `match.ts < anchorTs` (the timestamp the hop searched from — the previous hop's `matchTs`, or the outer reference's own `ts` for the first hop). **Semantics chosen**: this makes the *whole chain's* timestamps non-decreasing hop-over-hop, regardless of which individual hop searched "before" vs "after" — chosen over the other candidate reading ("each hop's own direction is internally consistent") because it's the one that actually catches the requirements doc's own REPRO case (a "before" hop landing chronologically earlier than the very first reference entry, not just earlier than its immediate anchor) and because pairwise-adjacent monotonicity is transitively equivalent to whole-sequence monotonicity, so no extra history-tracking beyond "compare this hop's match against the anchor it was searched from" is needed.

### Same-timestamp tie-break

**Person-reported follow-up** (screenshots of the multi-hop dialog + the Full/Filtered split): linking `"Target Real"` (anchor) to the nearest preceding `"Target Vir"` matched an entry roughly 11 seconds too early, even though the Full log clearly showed a `"Target Vir…"` line immediately followed by the `"Target Real…"` reference line. Root cause, confirmed before touching anything: `findNthOccurrence`'s `before`/`after` search compares timestamps with **strict** `<`/`>`. The log format only resolves to the millisecond, and this data bursts several log lines per control-loop tick at the *exact same* millisecond — so the `"Target Vir"` line sitting right next to the reference in the file shared its exact timestamp, made it a tie, and got excluded from "before" entirely (symmetrically true for "after" — both directions already treated ties as neither before nor after, this wasn't new or asymmetric, just surprising once a log has bursts). The search then kept walking backward past the whole tied cluster until it found an entry with a *strictly* earlier millisecond — 11 seconds earlier, from the previous cycle.

**Fix, exactly as requested**: when candidates tie with the reference on `.ts`, fall back to **log/array order** to decide before-vs-after, instead of excluding them.

- `buildOrderIndexMap(fileId)` builds a fresh `Map<entry.id, index>` from the root file's own `entries` array — "log order": parse order for an ordinary file, the already-chronologically-sorted union order for a merged file (see "The node tree"). Built once per `getEntries()` recompute of a `link` node (O(file size), same cost class as the `context` filter's own per-computation pass — not cached on the file node, to avoid new invalidation bookkeeping for what's still a rare, structural-change-triggered recompute; revisit if profiling ever shows this mattering on a file with many link nodes).
- `findNthOccurrence`/`findNthOccurrenceExcluding` now take the reference **entry** (not just its `ts`) plus this map: within the contiguous run of candidates sharing the reference's exact timestamp, the map locates where the reference itself would sit by log order, splitting that run into a "before" side and an "after" side — exactly mirroring what strict `ts` comparison already does for non-tied candidates, just scoped to the tie. If either id can't be resolved in the map (e.g. a dangling `inputA`/`inputB`, or — see below — a chained link's synthetic outer reference), the comparison degrades gracefully back to the old "exclude the tie" behavior rather than guessing.
- `buildPairEntry` had the same issue one level up: which side becomes `.first`/`.second` (display order, and the `⟶`-joined `message`/`raw`) used to default to "reference first" on any tie. It now takes the same `orderIndexMap` and, when both ids resolve, breaks the tie the same way — so the *displayed* pair order matches the log, not just the *matched* pair.
- `buildPairEntry` also gained `matchEntry` (the real `targetEntry` object a hop just matched, alongside the existing `matchTs`): a **chained** link's reference entry is a synthetic pair, whose own id never appears in a file's `entries` and so can't be looked up in the order map directly — `matchEntry` gives the *next* hop's tie-break a real entry id to resolve instead, the same way `matchTs` already gives it a real anchor timestamp (Bug 1 fix, see "Chained links" above). A plain, non-chained reference has neither field, so both simply fall back to the reference entry itself.

Verified against the exact reported shape (a decoy tie 11s earlier, then a same-millisecond burst with the target immediately preceding the reference, in both `before`/`after` directions), a plain no-ties case (regression guard — completely unaffected), and tie-break combined with exclusive matches (two references and two targets all sharing one timestamp, exclusivity still hands out the log-nearest *available* target to each). See `tests/philogg.regression.test.js` Group 23.

## Self-contained AND/OR/LINK: `bakedA`/`bakedB`, placement, and Unpack

**Corrected this session** (see CHANGELOG.md — the previous, `inputA`/`inputB` design was still a LIVE node-id lookup, just a rename of the old `linkedId` model it superseded; person-reported repro: combine filter A ("Some") and B ("Entry") with AND, delete A, the AND's results vanished along with it). `and`/`or`/`link` nodes now carry `node.bakedA`/`node.bakedB` — a **flat, self-contained copy of each side's own single condition** (`filterType`, `value`, and whichever of `caseSensitive`/`columns`/`isRegex`/`contextBefore`/`contextAfter`/`countBefore`/`countAfter`/`linkDirection`/`linkN`/`linkOrderEnforced`/`linkExclusive`/`bakedA`/`bakedB` apply for that `filterType` — see `bakeNodeCondition`) — **never** a node-id reference, never an ancestor chain. Baked once at creation time (or Unpack, below); after that, `bakedA`/`bakedB` never look at `state.nodes[...]` again. Deleting, renaming, moving, or replacing the original source node(s) has **zero effect** on the combiner's result.

`getEntries()`'s `and`/`or`/`link` branch is no longer a special case at all: it reads its own input entries the ORDINARY way every other filter type does — `getEntries(node.parentId)` — then evaluates `bakedA`/`bakedB` as predicates over that pool via `getEntriesFromBaked(baked, poolEntries, fileId)`, a standalone evaluator that mirrors `getEntriesUncached`'s own per-filterType branches (same `textFilterMatches`/`wildcardMatch`/`compileRegexFilter`/`compileExtractPattern`/time-range checks/`findNthOccurrence(Excluding)`/`buildPairEntry` — so behavior for each underlying filterType stays byte-identical to a real standalone filter of that type) and recurses into `baked.bakedA`/`baked.bakedB` for a **nested baked link** (a link-of-link chain — see "Chained links" below). `and` = both predicates true, `or` = either true, applied per-entry over `getEntries(node.parentId)`; `link` builds its reference-side/target-side entry sets the same way (`getEntriesFromBaked(bakedA, ...)` / `getEntriesFromBaked(bakedB, ...)`) and runs the existing nearest-occurrence pairing machinery over those two sets exactly as before. `node.parentId` is what determines this node's INPUT pool (exactly like a plain `"text"` filter) — moving the node just re-chains it onto a different parent's output; `bakedA`/`bakedB` are never touched by a move.

**Critical correctness property, explicitly required and tested**: baking captures ONLY the clicked node's own single condition, never anything from its ancestors. If filter A sits nested under some unrelated filter C ("only entries after 10:00"), combining A with B into an AND matches "A's own condition AND B's own condition" against whatever the AND node's OWN parentId chain provides — C's restriction never implicitly leaks in.

No cycle guard is needed any more: `bakedA`/`bakedB` hold plain data, not node-id references, so there is nothing to cycle through except normal recursion into a nested baked link, bounded by ordinary data-structure depth.

**Placement on creation.** `createAndOrNode`/`createLinkNode` always insert the new node as a fresh top-level child of the two inputs' shared root file (`root.children.unshift(...)`, same "independent, near the top" placement `syncBookmarksFilterNode`/`createSelectionFilterNode` already use) — regardless of where the two inputs themselves sit in the tree. From there, the node can be moved anywhere by the user like any other node: moving it is pure display repositioning, changing only `parentId` (and therefore its input pool), never `bakedA`/`bakedB`.

**Unpack** (tree context menu, any `and`/`or`/`link` node, next to Rename/Delete): now **purely additive**. `unpackAndOrLinkNode` materializes `node.bakedA`/`node.bakedB` into two real, visible, brand-new sibling filter nodes (`materializeBakedAsNode`, same `filterType`/fields) next to the original node's own position, wired together via a **fresh, separate** `and`/`or`/`link` node (baked from THEIR condition), inserted right after the original. The original node is left completely untouched and keeps working exactly as before, using its own original `bakedA`/`bakedB` — Unpack doesn't replace anything, it just makes the two building blocks editable/visible again ("Unpack würde wieder einen 'Some'- und einen 'Entry'-Filter erzeugen").

**Persistence**: `bakedA`/`bakedB` are threaded through all four persistence carriers (see CLAUDE.md's "Known gotchas") as a plain, generic value copy — no id-remapping logic anywhere, since there's no id inside them: `cloneSubtree` (deep-copies `bakedA`/`bakedB` like any other field), `snapshotSubtree`/`restoreSubtree` (undo/redo), `serializeFilterBranch`/`importFilterJson` (see "Export/library: just this filter vs. with ancestor chain" below), and `serializeFilterTreeForCache`/`materializeCachedFilters` (session cache).

Regression-tested: **Group 128** — the exact user repro (combine "Some" AND "Entry", delete "Some", verify unchanged, delete "Entry", verify still unchanged), ancestor-independence (a filter nested under an unrelated ancestor C combines using only its own condition), placement under FILE on creation for both AND/OR and LINK, the now-additive Unpack (original node untouched, fresh combiner produces an identical result via newly-materialized, visible siblings), and all four persistence carriers round-tripping `bakedA`/`bakedB` as plain data. **Group 7** — copy/cut/paste and drag-and-drop (same-file and cross-file, both now a plain reparent/clone with no special-casing).

## Export/library: "just this filter" vs. "with ancestor chain"

**Generalized this session** — this is no longer an `and`/`or`/`link`-specific concern. The previous `and`/`or`/`link`-specific "Include source filters used by combined nodes?" dialog (`openIncludeInputsPrompt`) is removed outright (it was also the cause of a reported bug: it could appear unconditionally at app startup instead of only during an actual save/export action). Every single-filter Save JSON/Save-to-library action now asks a general **"Just this filter" vs. "Include ancestor chain"** question (`openExportScopePrompt`, a small modal in the `#linkDialog`/`#contextDialog` style, `#exportScopeDialog`) — for ANY filter type, not just combiners:

- **"Just this filter"** — `serializeFilterBranch(nodeId, false)`: exports exactly the one clicked node, no ancestors, no subtree. For `and`/`or`/`link` this trivially includes its own `bakedA`/`bakedB`, which are already fully self-contained; for any other filter type, it's just that one node.
- **"Include ancestor chain"** — `serializeFilterBranch(nodeId, true)`: today's original chain+subtree export (the ancestor chain down to the clicked node, plus its full subtree) — unchanged in shape, just no longer combiner-specific.

**Import/apply placement (both cases)**: the imported branch — whether the single node or the full chain — attaches as a child of **whatever node is currently active/selected at the moment of import**, never hardcoded to FILE (every exported root is tagged `attach:"target"`; `materializeSerializedRoots`/`importFilterJson` resolve it to the import target's own id). "Just this filter" attaches exactly one node there; "include ancestor chain" attaches the whole chain there, its own internal relative structure unchanged — only its root's attachment point moves.

This same `includeAncestors` parameter is shared by Save/Load filter JSON (`saveFilterToFile`/`importFilterJson`) and the reusable filter library (`saveFilterToLibrary`/`applyFilterFromLibrary`, which hands off to `importFilterJson` unchanged) — see `docs/persistence-and-sync.md` for the storage-layer detail.

Regression-tested: **Group 11** — both scopes round-trip correctly onto a fresh file at a non-FILE target, for an `and`/`or`/`link` node (`bakedA`/`bakedB` traveling as plain data). **Group 135** — the general option for an ORDINARY filter type too, import placement at a non-FILE target for both a plain filter and a combiner, the prompt appearing as part of the actual save action (not just save-to-library), and a regression guard that no dialog shows unconditionally at startup.

## Time filters: unified `"timerange"` type, minimap drag-select, edit dialog

One filterType, `"timerange"`, covers all from/to time filtering — `value: { from, to }`, either bound `null` meaning unbounded on that side. `getEntries`'s branch is a plain `(from == null || e.ts >= from) && (to == null || e.ts <= to)` filter over `parentEntries`. Three creation paths all produce it: the timeline minimap's drag-select (below), the row context-menu's "Filter after/before this row" (creates one bound set, the other `null`), and the minimap's right-click → time-range dialog (below), for a manual/precise range without dragging.

**Legacy `"after"`/`"before"` types**: the single-bound predecessors of `"timerange"` (value was a plain `number`, not `{from,to}`). Both stay in `FILTER_TYPES` and `getEntries` keeps their branches (`ts >= value` / `ts <= value`) — purely so a session/export saved before this feature keeps reading correctly. **Nothing creates them anymore.** Editing one through the new dialog (F2 or tree right-click "Edit filter…", both gated on `isTimeFilterType(filterType)`) migrates it to `"timerange"` in place — one-way, via `updateTimeRangeFilterNode`; there's no UI to go back to the single-bound shape, which is fine since the two are behaviorally identical whenever only one bound is set. `timeRangeOfNode(node)` normalizes any of the three shapes into a plain `{from,to}` pair, which is what lets the dialog's edit mode work uniformly across all three.

**Why one node, not after+before+AND**: the drag-select feature originally built a range from two separate filters (`"after"` + `"before"`) combined by an `"and"` node — reusing the existing AND-combinator machinery meant zero new filter-type code, but produced three tree nodes for one conceptual filter. Person-reported follow-up asked for a single filter instead; `"timerange"` replaced the after+before+AND shape everywhere it was used. Because the new `{from,to}` value is still carried under each filter node's **existing** generic `value` field (not a new top-level field like `link`'s `linkedId` or `context`'s `contextBefore`/`contextAfter`), **no persistence-carrier code needed touching** beyond adding `"timerange"` to `FILTER_TYPES` — `cloneSubtree`/`snapshotSubtree`/`restoreSubtree`/`serializeFilterBranch`/`importFilterJson`/`serializeFilterTreeForCache`/`materializeCachedFilters` all already copy/serialize `value` generically for every filter type (see CLAUDE.md's "Known gotchas" note — this is the case where that gotcha turned out not to apply, verified by round-tripping a `"timerange"` node through the real Save/Load filter JSON path in `tests/philogg.regression.test.js` Group 32). One real sharp edge avoided rather than hit: `value` is treated as **immutable by convention** — every write replaces `node.value` wholesale (`node.value = { from, to }`) rather than mutating `.from`/`.to` on the existing object in place, since `cloneSubtree`/`snapshotSubtree` copy `value` by reference (fine for the old primitive-number shape, would alias two nodes' values together under in-place mutation of the new object shape).

**Drag-select on the timeline minimap** (`FEATURE_BACKLOG.md` item): click-drag across the minimap's bars marks a range and creates a `"timerange"` filter on mouseup. A pixel-distance threshold (`MINIMAP_DRAG_THRESHOLD_PX = 3`) tells a real drag apart from a plain click (which still falls through to the pre-existing click-to-jump); a one-shot `minimapDragSuppressClick` flag stops the browser's trailing `click` event (fired after every mouseup, including one ending a drag) from being misread as a jump. The live overlay (a highlighted range + a floating "from → to · duration" label, `#timelineMinimapDragRect`/`#timelineMinimapDragLabel`) is built from plain `<div>`s positioned *outside* the minimap's `<svg>`, specifically so `renderTimelineMinimap()`'s full `innerHTML` rebuild — which can fire mid-drag on a tail tick or level toggle — doesn't wipe the in-progress selection; this also keeps the drag mechanism structurally independent of the minimap's own range-indicator rectangles (see "Timeline minimap" below), satisfying the backlog item's explicit caution that the two must not interfere.

**Bugfix, this session, 2026-08-28, person-reported ("no longer works")**: the drag's anchor (`minimapDragStartTs`, formerly `minimapDragStartX`) is captured as a real **timestamp** at mousedown, not a raw `minimapWidth`-unit x position. A mid-drag `renderTimelineMinimap()` rebuild — the same class of event the overlay's own out-of-`<svg>` placement above already has to survive — can change `minimapTMin`/`minimapTMax` (a tail tick extends them) or `minimapWidth` (a resize) out from under an in-progress gesture; re-evaluating a stored pixel-unit x against the *new* time range at mouseup no longer pointed at the entry actually dragged from, and in the worst case could flip the from/to order and silently fail the `toTs > fromTs` guard — no filter created, no error, the drag just appearing not to work. A timestamp anchor is immune: every pixel position the gesture needs (overlay, threshold check, final range) is re-derived from it via `minimapTsToX`/`minimapXToTs` against whatever is currently live. Regression-tested in Group 31 with a tail tick landing mid-drag.

**Time-range dialog** (`#timeRangeDialog`, `openTimeRangeDialog(mode, targetId, prefill)`/`closeTimeRangeDialog()`): the first edit UI `"after"`/`"before"` filters ever had (previously create-only, no edit at all). `mode: "create"` attaches a new `"timerange"` child under `targetId` (the parent); `mode: "edit"` updates the node at `targetId` in place (migrating a legacy node, see above) — same targetId-means-different-things-per-mode convention `openFilterPopup`/`openEditFilterPopup` already use for the text/extract popup. Two `<input type="datetime-local" step="0.001">` fields (`tsToLocalInputValue`/`localInputValueToTs` round-trip local time, matching `formatTime`/`parseTimestamp`'s own local-time interpretation, so a value typed in the dialog lines up exactly with what the table shows) with a small × button each to clear the field. **Empty field = unbounded** on submit — no separate "infinity" checkbox, matching the pre-existing value-assertion dialog's optional min/max range fields' own "empty = no bound" convention, rather than inventing a second idiom for the same concept. Submitting with both fields empty is rejected (inline error, dialog stays open); a reversed From/To is silently swapped rather than rejected, same behavior the minimap drag already had. Right-click on the minimap opens the dialog in create mode, prefilled with the clicked point as **both** bounds (a valid zero-width starting range the person then widens either side of), for a manual/precise range without dragging.

## Timeline minimap: bars, range indicators, selection markers

A time-scaled density strip above the log table (`renderTimelineMinimap(rootId, viewEntries)`, called from `renderTable()` and `renderLinkView()` — see below). Grey background bars show entry density across the **whole root file** (memoized, `minimapBgCache` — see "Known limitations" resolved entry); colored overlay bars show `viewEntries` on top, one bar per bucket colored by the worst (most severe) level present. Bucketing is always by `entry.ts` (`bucketOf()`, `MINIMAP_BUCKET_PX`/`MIN`/`MAX_BUCKETS` control the target bucket count), so density stays meaningful even while the table is sorted by a non-time column — `minimapInteractive = !state.sortColumn` withholds only the features that assume "adjacent row = adjacent moment" (click-to-jump, drag-select, the two range rectangles) during a column sort; hover tooltip and the selection marker(s) stay available regardless, since neither depends on row adjacency.

**`minimapBarSpan(ts)`**: maps a timestamp to the full pixel `{left, right}` span of the density bar it falls into (mirrors `bucketOf()`'s exact formula), as opposed to `minimapTsToX(ts)`'s single continuous point for that moment. Anything that needs to align with the bars *as drawn* (the two range rectangles below) uses this instead of `minimapTsToX` directly — using the raw point used to leave a rectangle's edge sitting short of the bar it was meant to fully cover (person-reported bug, fixed this session — see the changelog entry and `tests/philogg.regression.test.js` Group 33).

**Two range-indicator rectangles**, both bucket-aligned via `minimapBarSpan`:
- `#minimapFullRangeRect` (`updateMinimapFullRange`) — the whole time span `minimapLastViewEntries` (the last `viewEntries` passed to `renderTimelineMinimap`) covers, i.e. everything the active filter/Link node currently matches, independent of scroll or virtualization. Scans for real min/max rather than assuming the first/last array elements are the extremes — true for the table view's chronological `currentViewEntries`, **not** guaranteed for the Link view's flattened pair entries (a "before" hop's match can land earlier than its own reference — see "Link filter" above), so the one function stays correct for both callers. **Settings → Behavior → "Hide minimap's covered-timespan box in Full view"** (this session, FEATURE_BACKLOG.md #8, `hideMinimapFullRangeInFullView`/`philogg-hide-minimap-full-range-in-full-view`, default **off**): when on, this box hides itself whenever the Full tab is the one on screen (`fhLayout === "tabs" && fhActiveTab === "highlight"`) — it's meaningless there since the Full view always covers the whole log. Left alone in Stacked layout (the Filtered pane is visible alongside the Full pane there, so the box stays meaningful) and, of course, whenever the Filtered tab is what's showing.
- `#minimapRenderedRangeRect` (`updateMinimapRenderedRange`) — nested inside the full range, covering only the entries that currently have DOM rows in whichever pane is **actually on screen right now**. Branches on the same `fhLayout`/`fhActiveTab` check as the toggle above: Full tab active → `highlightBody.scrollTop`/`clientHeight` over `currentHighlightViewEntries` (not gated on `minimapInteractive` — no column sort exists in the Full view); otherwise → `tableBody.scrollTop`/`clientHeight` over `currentViewEntries`, as before, still withheld during a column sort. Both branches share `minimapRenderedSpan(entries, scrollEl, rowOffsets)` for the actual index/pixel math (indices clamped to the list's bounds on both ends — an earlier version only clamped the lower bound, so switching to a much smaller filtered result while scrolled deep into a larger one indexed past the array's end and threw). A guard at the very top hides the rect unconditionally whenever the Link view is on screen (`linkWrap.style.display !== "none"`) — the Link view has no row virtualization at all (every pair-block is a real DOM node already), so there's no meaningful "rendered subset" there regardless of which fh tab was last active; this can't rely on simply never being called during the Link view any more, since `renderHighlightView()` (below) keeps refreshing the Full view's own data in the background even then. `renderTable()`/`renderHighlightView()` each call this themselves right after they run, the `#tableBody`/`#highlightBody` scroll listeners call it rAF-batched on scroll, the window-resize and sidebar-resize drag handlers call it unconditionally whenever the minimap itself is visible (previously gated on the table view specifically — that gate would have wrongly skipped it while the Full tab was on screen), and `showFhTab`/`applyFhView` call both range functions on every tab/layout switch so flipping panes re-evaluates them immediately, without waiting on an unrelated scroll or render.

**Selection marker(s)** (`updateMinimapSelectionMarkers`, into `<g id="minimapSelectionMarkers">`): a thin vertical line + small flag at the exact `minimapTsToX(ts)` position of each currently "marked" entry. `minimapMarkedEntries()` resolves what's marked, in priority order: (1) a Link view pair currently selected via its brace (`.pair-brace`, "Klammer" — see "Link filter" above) — every real entry the pair/tuple is made of, read off a `data-entry-ids` attribute `renderLinkView` stashes on the brace at render time, gated on the Link view actually being the *current* active view (a stale `.pair-selected` left over from navigating away must not keep marking its old entries — `renderLinkView` only clears it by rebuilding `#linkBody` from scratch the next time *it* runs, which doesn't happen just from switching away); (2) otherwise the ordinary single selection, `state.selectedId`, resolved via `entryIndex` first, falling back to a scan of `currentViewEntries`/`currentHighlightViewEntries` for the one case `entryIndex` can't cover — a selected row that's itself a synthetic Link pair entry (duck-types as a normal entry, never `entryIndex`-registered). Wired into `applySelection()`, the single function `selectEntry`/`selectHighlightEntry`/`revealInHighlightView` all already funnel through — every existing selection path gets a marker for free, and a plain row selection there also clears any lingering Link-view brace selection so a stale "Klammer" can't keep overriding a fresh one.

**Shown during the Link view too** (previously hidden outright): pair entries duck-type as normal entries (`.ts`/`.level` — see "Link filter" above), so `renderTimelineMinimap` works on them completely unchanged; `renderLinkView` feeds it every pair's *flattened* real entries (`getTupleEntries`, concatenated across all pairs) rather than the pair objects themselves, both for the overlay-bar density and so `updateMinimapFullRange`'s min/max covers matched (target-side) entries that can fall outside their reference entries' own span.

**Drag-select** (click-drag creates a `"timerange"` filter) and the **right-click → time-range dialog** are covered in "Time filters" above — both always operate on the Filtered view/tree, unaffected by which fh tab happens to be showing. Click-to-jump (plain click, no drag) selects the nearest entry in time via `lowerBoundByTs`, same "select + scroll + flash" path a row double-click uses — and, **as of this session**, resolves against whichever pane is actually visible, the same `fhLayout`/`fhActiveTab` branch `updateMinimapRenderedRange` uses: Full tab active → `currentHighlightViewEntries` + `selectHighlightEntry` (not gated on `minimapInteractive`, same reasoning as that function); otherwise → `currentViewEntries` + `selectEntry`, gated on `minimapInteractive` as before. Previously this always resolved against `currentViewEntries`/`selectEntry` regardless of which tab was showing, so a click while the Full tab was active silently jumped the (invisible) Filtered view in the background instead of the view actually on screen.

## Time context filter: window around reference entries

Built for the "show me everything that happened around this event" use case — deliberately simpler than the link filter it's modeled on. `getEntries` for a `context` node takes its parent-chain result as reference entries, builds a `[ts - contextBefore, ts + contextAfter]` window (both in ms) around each one, merges overlapping/touching windows into a sorted, non-overlapping range list (`mergeContextRanges` — an interval merge; this is the one deliberate answer to "what happens when two references' windows overlap": they become one group rather than staying as separate, duplicate-prone groups), then binary-searches (`lowerBoundByTs`/`upperBoundByTs`) the **whole root file** for entries inside those ranges. Unlike `link`, the result is **real entries from the file**, not synthetic pair objects — so any filter can be nested underneath a `context` node exactly like under any other filter, and a reference entry's own row shows up at its normal chronological position (it's always inside its own window) rather than needing a special anchor-row construct.

`node._contextRanges` (the merged range list) and `node._anchorIds` (the set of reference entry ids) are computed alongside `node._cache` in the same `getEntries()` branch and read directly off the node by the renderer — they're not separately invalidated because they're only ever populated together with the cache they ride along with.

**Rendering**: the log view (not a separate view like the link pair view) draws a left-side bracket per row when the active node is a `context` filter — `contextRangeIndex()` (binary search over `_contextRanges`) tells `renderVisibleRows()` which merged group a row's timestamp falls into; a row gets `.ctx-start`/`.ctx-end` classes by comparing against its *actual* neighbors in `currentViewEntries` (not just the virtualized render window), so the rounded bracket caps land correctly regardless of scroll position. Reference entries get a small accent dot (`.ctx-anchor-dot`). Brackets are suppressed under an active column sort (`state.sortColumn`), since sorting would scatter a group's rows apart and the bracket would stop meaning anything.

**Creating one**: right-click a single filter node (not a 2+ multi-selection) → "Time context…" opens `#contextDialog`, a small before/after-in-milliseconds form (mirrors `#linkDialog`'s structure but needs no target-filter picker, since the target is always the root file).

This is the intended way to pull values from *both* sides of a pair into one extraction-table row.

## Count context filter: fixed number of entries around reference entries

A sibling of the Time context filter above (`filterType: "countContext"`, fields `countBefore`/`countAfter`), added this session (person-requested: *"Analog zum Time Context erstelle einen Count Context, bei dem man einfach die Anzahl der Log Einträge vor und/oder nach dem Anchor einstellen kann. Also anstatt eines Zeitfensters, eine feste Anzahl an Logeinträgen davor oder danach."*) — same "show me everything around this event" use case, but windows by a fixed **number of entries** instead of a time span, for logs whose entry density varies too much for a millisecond window to reliably capture "N entries of context" (a burst of activity vs. a quiet stretch).

`getEntries`'s `countContext` branch looks up each reference entry's own index in the root file's `entries` array (`buildOrderIndexMap`, the same helper the `link` filter's tie-break already uses) and builds an inclusive `[idx - countBefore, idx + countAfter]` **index** window per reference, clamped to `[0, pool.length - 1]`. `mergeCountContextRanges` (the count-based counterpart of `mergeContextRanges`) merges these the same way, with one deliberate difference in the merge condition: since these are discrete integer indices rather than continuous timestamps, two windows merge when they overlap **or sit back-to-back with no gap** (`next.start <= last.end + 1`) — index 10 and index 11 are adjacent with nothing between them, so they read as one continuous bracket the same way two touching time windows already do. The actual kept entries are sliced directly from the pool by index — exact, no binary search needed since the indices are already known.

**Rendering reuses the exact same mechanism as Time context** — `node._contextRanges`/`node._anchorIds` are populated in the identical shape, and `renderVisibleRows`'s bracket/anchor-dot code now checks for `filterType === "context" || filterType === "countContext"` rather than one specific type. The one wrinkle: `contextRangeIndex()` (used by the renderer) binary-searches `_contextRanges` by **timestamp**, so a `countContext` node's index ranges are re-expressed in ts-space (`{start: pool[lo].ts, end: pool[hi].ts}`) before being stored on the node — exact for the actual filtered result (computed from real indices, never from these ts bounds), with one accepted cosmetic-only edge case: a range boundary entry that happens to share its exact timestamp with an entry just outside the window (a tie) can make the bracket render one row wider/narrower than the true index window. Same class of accepted trade-off as the Time context bracket's own tie edge cases.

**Creating one**: right-click a single filter node → "Count context…" opens `#countContextDialog` (`#contextDialog`'s structural twin — same backdrop/positioning CSS, same open/close/create wiring), with "Entries before"/"Entries after" number inputs instead of milliseconds. Threaded through every persistence carrier the "Known gotchas" note requires: `cloneSubtree`, `snapshotSubtree`/`restoreSubtree`, `serializeFilterBranch`/`importFilterJson`, `serializeFilterTreeForCache`/`materializeCachedFilters`, plus `FILTER_TYPES` and the tree's type tag (`CNT`, next to `CTX` for the time-based one). Inversion (NOT) is excluded for the same reason as `context` (every window always contains its own reference entry, so a parent-relative difference would always be empty) — the fourth exclusion alongside `link`/`extract`/`context`.

# Persistence and Sync

Undo/redo, bookmarks, notes, pin-bookmarks-into-filtered-view, tailing, file loading, folder watch, filter save/load, the reusable filter library, session cache, per-file filter history, and session export/import.

## Undo / redo

Covers filter node **delete** and **move** (drag/drop reparent, and Ctrl+X-then-paste, which is also a move), plain (non-folder) **file delete**, filter **value/pattern edits** (the F2/"Edit filter…" popup and the time-range dialog, including the legacy `after`/`before` → `timerange` migration), the **invert (NOT) toggle**, **value-assertion** add/clear, and the **per-file clock offset** (see "Per-file clock offset" below — a dedicated `"clockOffset"` action kind that re-applies the inverse/forward delta rather than restoring a captured `ts`, since `snapshotSubtree` copies entries by reference). Filter creation is undoable only for the one-click analysis actions of the Patterns tab and the Facet panel (`pushCreateUndo` → a `"create"` action: undo snapshots the node's subtree and deletes it, returning to its parent; redo restores the snapshot at its old position under the original id — see `docs/ui-and-views.md` → "Patterns tab"/"Facet panel"). The LLM assistant adds a **`"batch"`** action: a list of actions undone in reverse and redone in order as ONE step — every node an assistant round created (`"create"` actions, pushed when the round ends), or the round's nodes deleted later by "undo this round" (`"delete"` actions); see `docs/llm-assistant.md` → "Undo". `undo()`/`redo()` run each kind through `undoAction`/`redoAction`, which is what makes the nesting possible. Still deliberately out of scope: other filter/file *creation*, folder-file close (not destructive — the file just returns to its folder's grayed listing, see "Folder watch"), and context-filter creation (no edit path exists for it at all). A small snapshot-based command stack was chosen over deriving undo generically from every tree-mutating function, since the tree's structural invariants are easier to reason about as "restore exactly this snapshot" than as a generic inverse of arbitrary mutations.

**Delete/move call sites**: the only two a user-facing delete/move should ever go through are `deleteFilterNodeWithUndo(nodeId)` and `moveFilterNodeWithUndo(nodeId, newParentId)` — every existing trigger (Delete key, per-row hover ✕, tree right-click menu, drag-and-drop `drop` handler, Ctrl+X-then-Ctrl+V's move branch) calls one of these instead of `deleteNode`/`moveNode` directly. Anything that bypasses them silently isn't undoable. `deleteFilterNodeWithUndo` branches three ways: a folder-loaded file (`node.folderId`) goes to `closeFolderFile` (unchanged, not undoable); any other **file** node snapshots+deletes and pushes a `"deleteFile"` action; a **filter** node does the original `"delete"` action. Deleting an `and`/`or`/`link` node only ever removes that one node plus its own real subtree — its `bakedA`/`bakedB` (see `docs/filters.md`'s "Self-contained AND/OR/LINK") are flat, already-baked data, not a reference to any other node, so there's nothing elsewhere in the tree that this delete could possibly affect.

**Snapshotting**: `snapshotSubtree`/`restoreSubtree` deep-clone a node's whole subtree the same way `cloneSubtree` does for copy/paste, with one crucial difference — **original ids are kept**, not reassigned (this mainly matters for the tree UI itself — selection/scroll position surviving an undo — not for and/or/link correctness, since `bakedA`/`bakedB` don't reference any node's id in the first place). Both functions branch on `node.type`: a **file** node's own fields (`entries`, `cacheKey`, `merged`, `tail`) are captured/restored by *reference*, not cloned — the same entry objects and live tail handle just get unplugged from `entryIndex`/`state.rootIds` on delete and plugged back in on undo, same as a real close/reopen; `restoreSubtree`'s file branch also re-adds every entry to `entryIndex` and calls `persistFileNode` (fire-and-forget, re-creating the session-cache record `cacheDeleteFile` dropped) since a file is never structurally nested, this branch only ever runs at the top of a `"deleteFile"` snapshot — its filter-type children still go through the existing branch.

**The generic "edit" kind**: unlike delete/move, a value edit has no cheap structural inverse to derive, so `captureNodeFields(node)`/`applyNodeFields(node, fields)` capture/restore a node's whole set of mutable, non-structural fields (`filterType`, `value`, `inverted`, `name`, `ignoredColumns`, `caseSensitive`, `columns`, `assertions`) wholesale. `withFieldEditUndo(nodeId, mutateFn)` captures a `before` snapshot, runs the mutation, captures `after`, and pushes `{ kind: "edit", nodeId, before, after }` — `undo()` applies `before`, `redo()` applies `after`. Four call sites: `updateFilterNodeWithUndo`/`updateTimeRangeFilterNodeWithUndo` (thin wrappers around the existing `updateFilterNode`/`updateTimeRangeFilterNode` mutators, called from `commitFilter` and the time-range dialog's submit handler), `toggleInvertWithUndo` (the tree context menu's "Invert (NOT)" action), and the value-assertion dialog's Save/Clear handlers (call `withFieldEditUndo` directly, since their mutation is a one-liner). The plain `updateFilterNode`/`updateTimeRangeFilterNode` mutators still exist undecorated — nothing else in the codebase calls them without the `WithUndo` wrapper.

**The stack**: `undoStack`/`redoStack`, capped at `UNDO_STACK_LIMIT = 50` (oldest entries drop off silently). `pushUndo()` — called only from the wrapped mutators above — always clears `redoStack`, since a genuinely new action makes any previously-undone branch unreachable (standard undo/redo semantics). `undo()`/`redo()` themselves move the same action object directly between the two stacks (applying the inverse or re-applying the forward mutation) without going through `pushUndo`, so they never clear each other's history — undoing three deletes and redoing one still leaves the other two redoable.

**UI**: `#btnUndo`/`#btnRedo` (toolbar, left of the theme toggle) — disabled via the plain `disabled` attribute when their respective stack is empty, tooltip names which action would be undone/redone next (`UNDO_KIND_LABELS` maps each `kind` to its human-readable label: delete/file delete/move/edit/clock adjust/filter creation). `Ctrl+Z` undoes, `Ctrl+Shift+Z` **and** `Ctrl+Y` both redo (the second purely for muscle-memory compatibility with editors that use one or the other). A toast (`showCopyToast`) confirms which kind of action was undone/redone, since the tree can be deep enough that the effect isn't always visually obvious at a glance.

## Bookmarks

**Reworked this session (FEATURE_BACKLOG.md "Bookmarks rework", person-requested)**: the old Bookmark Manager panel (`#btnBookmarks`/`#bookmarksPanel`/`#bookmarksList`/`renderBookmarksPanel`/`openBookmarksPanel`/`closeBookmarksPanel`/`updateBookmarksButton`) is removed entirely. Bookmarks are now surfaced as a **single, auto-managed filter node** — see "The auto-managed 'Bookmarks' filter node" below. The underlying `state.bookmarks` Set (still the actual source of truth) and the PIN-bookmark feature (`getPinnedBookmarkEntries`/`state.pinBookmarksInFilteredView`) are otherwise **unaffected** — they still read `state.bookmarks` directly, exactly as before. The bookmark's own free-text note field (`{ note, bookmarkedAt }`) is gone too — the general-purpose Notes feature (see "Notes" below) replaces it with something far more capable (any entry, not just bookmarked ones; multi-line; its own Entry Detail display).

`state.bookmarks`: `Map<entryId, { bookmarkedAt }>` — **not part of filter save/load**, since a bookmark anchors a spot in the *data*, not a filter definition; it doesn't belong in a filter-tree JSON file the way `inverted` or a value assertion does. Persisted across reloads by the session cache and session export (as file + entry ordinal, since entry ids don't survive a reload — see "Session cache"). Deliberately scoped to real log entries selected in the plain log view (`state.selectedId`) — not link-view pair entries or extraction-table rows, which have synthetic/derived ids that are never added to `entryIndex` (see Core data model), so a bookmark on one could never be resolved back to a real row later. The row context menu (`#ctxBookmark`) and `openContextMenu` hide/no-op that menu item when the right-clicked entry isn't in `entryIndex` for exactly this reason.

**Toggling**: right-click a row → "Bookmark this row" / "Remove bookmark" (`#ctxBookmark`, label reflects current state), or press **B** with a row selected (`state.selectedId`). Bookmarked rows get a small filled star (`.row-bookmark-dot`, reuses `ICON_BOOKMARK_FILLED`) in the same left-gutter slot the context-filter bracket/anchor-dot uses — the two can in principle land in the same visual spot if a row is both a context-filter reference *and* bookmarked; accepted as a minor, rare cosmetic overlap rather than reserving a second gutter slot for it. `toggleBookmark(entryId)` also calls `syncBookmarksFilterNode(rootId)` (see below) after mutating `state.bookmarks`, and repaints the sidebar tree (`renderTree()`) alongside its existing targeted row/pin repaint, since the auto node can now appear/disappear as a side effect.

**Jumping**: `jumpToEntry(entryId)` resolves an arbitrary entry's own root file via `findRootIdForEntry(entryId)` (a linear scan over `state.rootIds`, O(root file size) — fine since this only runs on a rare user click, not a render-path hot loop) before switching `state.activeId`, clearing the level filter, and setting `state.scrollTargetId`, same as `jumpToFullLog`, but working from anywhere regardless of which chain is currently active. Originally the Bookmark Manager panel's own row-click handler; kept as a general "jump to this entry" utility now that the panel is gone (still exercised by tests, e.g. the multiline virtualization group's `scrollToIndex` check).

### The auto-managed "Bookmarks" filter node

`syncBookmarksFilterNode(rootId)` creates or removes a single `filterType: "bookmarks"` node directly under the given root file, depending on whether that root currently has ≥1 entry in `state.bookmarks` — called from `toggleBookmark` (for the affected root) and from every bookmark-restore path (session cache restore, session import's `applySessionEntryByOrdinal`/`applySessionEntryByContent`), so a session that comes back with bookmarks always re-derives the node, and one with none never leaves a stale one. Idempotent — safe to call whether or not anything actually changed.

- **Matching**: `getEntries()` gained a `filterType === "bookmarks"` branch — `result = parentEntries.filter(e => state.bookmarks.has(e.id))` — following the exact same per-`filterType` branching pattern every other matcher (`text`, `level`, `context`, …) already uses, rather than a parallel code path. `FILTER_TYPES` (the save/load + cache validity `Set`) includes `"bookmarks"` for internal use, but importing/materializing a saved node of this type is explicitly **rejected** (see Persistence below) — the type exists for live matching only.
- **`locked: true`**: the node carries this new flag, checked by `deleteFilterNodeWithUndo`/`moveFilterNodeWithUndo` (both no-op/return `false` on a locked node — the single choke point every delete/drag/middle-click/Delete-key path already routes through, so no per-call-site duplication was needed) and by `renderNode`'s `row.draggable` assignment (skipped for a locked node, so a drag never even starts). The tree context menu's item-building code branches early on `node.locked`: a locked node's menu is just **"Copy"** — no rename/edit/invert/context/cut/save-to-library/delete. The `✕` delete button is omitted from the row entirely (not just disabled) for a locked node. **Not restricted**: the highlight-colour swatch (`openColorPicker`/`setHighlightColor`) — colouring/styling a locked node works exactly like any other filter node, per the feature's own requirement.
- **Icon/label**: no dedicated icon — `nodeIconHTML`'s `filterType` switch has no `"bookmarks"` case, so it falls through to the same generic default (`ICON_CLOCK`) legacy `"after"`/`"before"`/`"timerange"` nodes already use. `typeTagFor`/`ghostTypeTag` do give it its own three-letter tag (`BKM`) for the tree row's type-tag column, same as every other `filterType`.
- **Persistence — deliberately excluded from the filter-tree carriers**: `serializeFilterTreeForCache`'s `ser()` (session cache) and `serializeFilterBranch`'s recursive collector (session file JSON) both skip any child node whose `filterType === "bookmarks"` via a shared `persistableChildren(ids)` filter, and `importFilterJson`/`materializeCachedFilters`'s own `validate`/`valid` helpers reject `filterType === "bookmarks"` outright (defends against a hand-edited or pre-rework file). The node's own membership is entirely derived from `state.bookmarks`, which is *itself* persisted (see "Session cache"/"Session export/import" below) — serializing the node too would just be redundant, driftable state; re-deriving it via `syncBookmarksFilterNode` after every bookmarks-restore keeps it exactly in sync with zero extra stored shape. One accepted edge case: if a person manually adds a filter as a *child* of the locked node (not prevented — only delete/move/reorder are blocked, not "become a parent"), that child is lost along with the node the next time it's excluded from serialization. Rare enough, and easy enough to work around (create the filter one level up instead), not to warrant extra plumbing.
- **`cloneSubtree`** (copy/paste) deliberately does **not** copy `orig.locked` — pasting a copy of the auto node produces a plain, unlocked filter node (still matching whatever was bookmarked at copy time, since `filterType`/`value` themselves *are* copied) rather than a second restricted original; only `syncBookmarksFilterNode`'s own node stays locked.

### The auto-managed "Notes" filter node

Person-requested "Notes overview" (this session): a second auto-managed, restricted filter node, `syncNotesFilterNode(rootId)` — the exact same shape as `syncBookmarksFilterNode` above (idempotent create/remove keyed on "does this root have ≥1 entry with something in the corresponding Set/Map", `locked: true`, excluded from every filter-tree persistence carrier, `cloneSubtree` drops `locked` on copy), mirroring `state.notes` instead of `state.bookmarks`. Its whole point is a single place to read every note in a file at a glance, with the usual "jump into the filter tab, see the entry in context" behavior any filter node already gives for free — no bespoke notes-browsing UI was needed, just a second `filterType`.

- **Placement**: inserted directly **below** the "Bookmarks" node when one exists (found by index, spliced in right after it), or unshifted to the very top when Bookmarks isn't currently present — so the two always read as "Bookmarks, then Notes" whenever both are showing, without one ever displacing the other's slot.
- **Matching**: `getEntries()`'s `filterType === "notes"` branch is `result = parentEntries.filter(e => state.notes.has(e.id))`, the same one-line pattern the `"bookmarks"` branch uses. `FILTER_TYPES` includes `"notes"` for internal use only — a saved/imported node of this type is rejected the same way `"bookmarks"` is (`importFilterJson`'s `validate`, `materializeCachedFilters`'s equivalent).
- **Sync call sites**: `setNoteAndRepaint` (every note add/edit/delete) calls `syncNotesFilterNode(rootId)` for the note's own root and repaints the tree, same as `toggleBookmark` does for Bookmarks; every bookmark-restore call site that already called `syncBookmarksFilterNode` (session cache restore, `applySessionEntryByOrdinal`/`applySessionEntryByContent`) now also calls `syncNotesFilterNode` right after it.
- **Standing on it auto-enables Show Notes**: `render()`'s existing "did `state.activeId` change since last render" check (the same one driving `applyActivationView`) now also detects entering/leaving a `filterType: "notes"` node. Entering one snapshots the current `state.showNotes` into `notesFilterPrevShowNotes` and force-enables it if it was off — reading every note in the file only works if note-rows are actually showing. Leaving it restores whatever `state.showNotes` was before, so the toggle's own state is never permanently changed by just visiting the node. A person manually flipping `#btnNotes` while standing on the node is respected for the rest of that visit (only the *leave* transition restores the pre-entry value, comparing against the live `state.showNotes` at that moment).
- **Persistence**: excluded from `serializeFilterTreeForCache`/`serializeFilterBranch`'s persisted children the same way `"bookmarks"` is (one shared `persistableChildren` filter now checks both types) — re-derived from `state.notes` on every restore instead, for the same reasoning as Bookmarks.

## Notes

General-purpose free-text notes on *any* log line, bookmarked or not (FEATURE_BACKLOG.md "Bookmarks rework", shipped alongside the bookmarks node change above). `state.notes`: `Map<entryId, noteText>` — same id scheme as `state.bookmarks` (a real, `entryIndex`-resolvable log entry id), same persistence tier (session cache, session export/import), but a **completely separate, flat per-entry store** — not part of the filter tree, not tied to a row being bookmarked.

**Editing**: `openNoteEditor(entryId)` opens `#noteDialog` (same fixed-position, backdrop-click-to-close card pattern as `#timeRangeDialog`/`#assertDialog`), prefilled with the existing note or empty for a new one — the dialog's own title ("Add note"/"Edit note") and the presence of a "Delete" button reflect which. Reachable three ways: **`Alt+N`** on the selected row (`state.selectedId`) — no separate `F2` binding, the same shortcut opens either mode depending on whether a note already exists; the row context menu's **`#ctxNote`** item (label-swaps "Add note"/"Edit note" exactly like `#ctxBookmark` does, same `entryIndex` eligibility gate); and **double-clicking an existing rendered note-row** (`appendNoteRow`'s own `dblclick` listener, attached fresh every render — see "Rendering" below for why that's required, not just convenient). `setNoteAndRepaint(entryId, text)` is the single mutator: empty/whitespace-only text deletes the note (`state.notes.delete`) rather than storing an empty string, otherwise trailing whitespace is trimmed and the rest stored verbatim (internal formatting/indentation is the person's own). **Auto-enables Show Notes** (FEATURE_BACKLOG.md #76, person-reported: a just-created note wasn't actually visible unless the toggle already happened to be on): whenever the mutator ends up with non-empty text and `state.showNotes` is off, it flips the toggle on (`updateNotesButton()`) before the row-offset/repaint work below runs, so the new note-row is on screen immediately with no separate manual toggle click. Deleting a note never flips it back off — that stays a separate, person-controlled setting once it's on.

**Rendering**: a note renders as a **sub-row** — a plain block `div.note-row`, not part of `.row-grid` — appended as a DOM sibling directly after its entry's own row, in both the Filtered (`renderVisibleRows`) and Full (`renderHighlightVisibleRows`) views, via a shared `appendNoteRow(frag, e)` helper. No level marker (it isn't `.row-grid`, so there's no `.col-bar` to color), own colour (`--accent-strong`, italic) and left-indented (32px padding vs. the row's own 14px gutter) to read as clearly subordinate to the entry above it. Gated on `state.showNotes` (the Show/Hide Notes toggle — see below) and the entry actually having one; stays visible regardless of the active filter/level-filter, since it belongs to whichever entry row is already being rendered — a note is never itself a filter target. Its `dblclick` listener opens the editor for that entry; built fresh on every call to `appendNoteRow` rather than assumed to persist, per the CLAUDE.md gotcha ("`renderVisibleRows()` rebuilds nodes, breaking native `dblclick`" on anything that assumes DOM identity survives a re-render) — this is the same reasoning every other per-row listener in this file (`renderNode`, the row's own click/contextmenu/dblclick) already follows, just newly relevant here too.

**Height/virtualization**: a note-row's height (`noteHeightForEntry(e)`) is `0` when notes are hidden or the entry has none, otherwise `NOTE_LINE_HEIGHT (16) × line count + NOTE_ROW_VPAD (6)` — the same "count literal `\n`s, don't measure wrapped soft-lines" simplification `messageLineCount`/multiline-message rendering already uses. `rowHeightForEntry(e)` (the value fed into `buildRowOffsets`' prefix-sum array) is now `baseRowHeightForEntry(e) + noteHeightForEntry(e)` — `baseRowHeightForEntry` is the *original* `rowHeightForEntry` body (the entry's own row height, unaffected by notes), factored out so the `.log-row` element's own `style.height` can be set to just its own share, with the note-row getting the remainder as its own separate `style.height` — the two DOM elements' real heights MUST sum to exactly what `buildRowOffsets` computed, or virtualization drifts out of sync with what's actually on screen. A new `needsRowOffsets()` helper (`state.multilineMessages || state.showNotes`) replaces every direct `state.multilineMessages` check that gated the offsets-array virtualization path (`tableRowOffsets`/`highlightRowOffsets`, `buildRowOffsets`, the various `findOffsetIndex`-based branches in `renderVisibleRows`/`renderHighlightVisibleRows`/`scrollToIndex`/`scrollToHighlightIndex`) — notes showing at all now needs that path too, for the same reason multiline messages always did (rows are no longer uniformly `ROW_HEIGHT`).

**Entry Detail panel**: `updateDetailPanel()` shows the selected entry's full note text in a new `#detailNote` block below `#detailMessage` (own dashed top border, same `--accent-strong` colour as the note-row, `white-space:pre-wrap`), unconditionally — not gated on `state.showNotes`/`state.multilineMessages` — so a multi-line note stays fully readable even with note-rows hidden or MultiColumn's single-line rendering. Hidden (`display:none`) when the selected entry has no note or nothing is selected.

**Show/Hide Notes toggle**: `#btnNotes` (`state.showNotes`, default **`false`** — same "off by default" reasoning as `state.multilineMessages`: the plain fixed-`ROW_HEIGHT` virtualization path stays the unaffected default until someone actually has notes to see inline), placed in `#viewBar` next to `#btnPinBookmarks`/`#btnMultilineMsg` (same `.toolbar-icon-btn` float/margin, same extract-mode hide/show pairing). Its click handler flips the flag and calls a **full `render()`** — same "correctness over render cost for a rare click" tradeoff `#btnMultilineMsg` already makes, since toggling it can change every visible row's height at once.

**Persistence**: `buildCacheMeta()`/`buildSessionExport()` serialize `state.notes` the same ordinal-anchor way `state.bookmarks` already does (`{ file/ordinal }` for the cache, `{ ordinal, ts, raw }` fingerprint-fallback fields added for the export's tier-3 manual-match path — mirroring the bookmark record's own fields exactly), but as a **separate `notes` array**, not folded into the `bookmarks` one. `applySessionEntryByOrdinal`/`applySessionEntryByContent` (session import) and `restoreSessionFromCache` (cache restore) each gained a parallel notes-restore loop next to their existing bookmarks loop, returning/tracking `notesPlaced`/`notesTotal` alongside the existing `placed`/`total`, surfaced in the import summary toast as an additional "N of M notes placed" clause. `state.showNotes` itself persists in `settings.showNotes` on both carriers, same tier as `multilineMessages`.

## Pin bookmarks into the Filtered View

From `FEATURE_BACKLOG.md` item 1 (person-requested, modeled on glogg/klogg's "marks" — lines marked in the main view that always break through the search pattern into the filtered results, merged in log order). Deliberately built as an extension of the existing Bookmarks feature rather than a third marker type, to avoid a second visual marker competing for the same left-gutter slot the bookmark dot and context-filter anchor dot already share (see "Bookmarks"), and because a bookmark's existing meaning — "this entry matters regardless of context" — already implies the pin semantics; introducing a parallel concept would just duplicate it.

**Toggle**: `state.pinBookmarksInFilteredView` (bool, default `false`), a toolbar button `#btnPinBookmarks` (`ICON_PIN`, a map-pin glyph). It's a plain persistent on/off switch, not a popup — styled via a general-purpose `.toolbar-icon-btn.active` state (reused accent colors, same ones `.crumb.current` already uses) rather than anything bookmark-specific, so any future toolbar toggle can reuse it. Deliberately styled as its own control rather than a `.level-btn` pill: the level pills are subtractive (AND — narrows the result set; empty selection is the "show everything" special case), while pinning is additive (OR — adds entries the filter chain would otherwise exclude). Visually identical pills with inverted logic in the same row was judged a likely source of confusion, so pinning keeps its own distinct look instead. **Location (moved this session, person-requested)**: originally sat in the header next to `#btnBookmarks`; now lives in `#viewBar` itself, floated between `#fhTabs` and `#levelBar` — the row that controls what the active views show/hide, which is what this toggle does, so it belongs there rather than among the header's mostly popup-trigger buttons. The move is purely positional: same element, same id, same `.toolbar-icon-btn` class and click handler, still deliberately *not* inside `#levelBar` itself or restyled to match `.level-btn` (see "Header / toolbar layout" for the float mechanics).

**Merge logic** (`getVisibleEntries()`, the function `renderTable()`'s plain-table path already used for "node filter + level quick-filter"): when the toggle is on, the filter-tree result is unioned with the bookmarks belonging to the *active root file* — resolved via a new `getPinnedBookmarkEntries(rootId, orderIndexMap)` — and the union is re-sorted into that root's own chronological (array) order. A pin is **absolute**: it bypasses both the filter tree's own result *and* the level filter, the same way glogg/klogg's marks bypass the search pattern — consistent with the "regardless of the filters" framing the feature was originally requested with. `getPinnedBookmarkEntries` reuses `buildOrderIndexMap` (already used for the link filter's same-timestamp tie-break) as a combined membership test ("does this bookmark belong to this root") and position source for the final merge sort — a single O(root size) map build per render instead of an O(root size) scan per bookmark the way `findRootIdForEntry` would cost if reused here instead.

**Gotcha (bugfixed this session, person-reported)**: `toggleBookmark()` is a second choke point that can change WHICH rows the Filtered view shows, not just `render()`/`renderTable()` — while pin mode is on, adding or removing a bookmark can add or drop a row, so `toggleBookmark()` must recompute `currentViewEntries`/`pinnedOnlyIds` (i.e. call `getVisibleEntries()` again) itself before its own `renderVisibleRows()` repaint, guarded behind `state.pinBookmarksInFilteredView` so the common (pin-off) case is untouched. Deliberately does **not** call `renderTable()` for this — that always resets scroll to the top, which would yank the reading position on every bookmark toggle. See "Status / changelog" for the fix.

**Scope decisions made this session** (the backlog doc's open questions):
- *Persistence*: yes — part of `state`'s persisted settings, same tier as `levelFilter`/`sortColumn`. Written to and restored from all three existing settings carriers: the IndexedDB session cache (`buildCacheMeta`/`restoreSessionFromCache`), and the portable session export/import JSON (`buildSessionExport`/its import counterpart) — kept alongside `levelFilter`/`sortColumn` in all three places rather than singled out, since it's the same kind of view preference.
- *Extract / Link views*: **unaffected, deliberately** — not by an explicit guard, but structurally: `getVisibleEntries()` is only ever called from `renderTable()`, which only runs for the plain-table path (`renderMainView` routes extract nodes to `renderExtractTable()` and link nodes to `renderLinkView()` instead, neither of which calls it). This falls out of the existing view-routing, not a new special case, and matches the precedent already set by Bookmarks itself being scoped to real `entryIndex`-backed entries only (extraction rows and link pairs have synthetic ids that were never bookmarkable to begin with).
- *Visual treatment*: rows present only because of a pin (not because they matched the filter chain) get `.pinned-row` — an inset left `box-shadow` (`--accent-strong`) rather than a background tint, so it doesn't fight the existing per-level row background (`lvl-error`/`lvl-warn`/etc.). A bookmarked row that *also* genuinely matches the filter does **not** get this class — it's a normal match, not a "here only because of the pin" row, and `renderVisibleRows` distinguishes the two via a `pinnedOnlyIds` set refreshed on every `getVisibleEntries()` call. (The status strip used to surface a `"· N pinned"` suffix off this same set — removed this session, 2026-09-04, along with the status strip itself; `.pinned-row` is the only remaining signal now.)

**Non-goals**: no cross-root/cross-file pinning (scoped to the active root, same as the merge's `orderIndexMap`); no changes to the Bookmarks panel, notes, or `jumpToEntry` themselves — this is purely additive to how bookmarks are *surfaced* in the Filtered View.

## Per-file clock offset

A manual clock correction for a single **non-merged** source file (FEATURE_BACKLOG.md #29), for the case where one device's log is skewed relative to another's before you compare or merge them. Reachable only from a file node's tree-row context menu ("Adjust clock…", in the `edit` bucket of `openTreeContextMenu`).

**Approach (a) — baked, not lazy.** `applyClockOffset(fileId, deltaMs)` adds the signed millisecond `delta` to **every `entry.ts`** of that file (`shiftFileEntriesTs`) rather than applying it at read time, and accumulates the total on `node.clockOffset` (default 0) so it can be shown, re-edited and undone. `entry.raw`/`entry.tsRaw` are **deliberately left untouched** — every time display reads `formatTime(e.ts)` (both log-row renderers, the Δt column, the minimap), so shifting `ts` alone updates the whole UI, while the raw text stays the file's original bytes. It's refused for a merged file (see the gotcha below) and for a file with no entries; the menu item is likewise only offered for a non-merged file with entries.

**The dialog** (`#clockOffsetDialog`, `openClockOffsetDialog`) follows `docs/ui-standard.md`: a segmented `.assert-mode-btn` mode toggle, `.settings-row` rows, one-line hints, theme CSS vars only, and a `.btn-mini-secondary` (Cancel) + `.btn-mini` (Apply) footer in secondary→primary order. Two interpretation modes:
- **Difference**: a forgiving signed delta parsed by `parseClockDelta` — `+1500`/`-1500` (bare number = milliseconds), an explicit unit (`500ms`, `-2s`, `3m`, `1h`), or a colon time form `±[HH:]MM:SS[.mmm]`; a leading `+`, `-` or `−` sets the sign. Applied additively to all entries.
- **Start time**: a datetime input pre-filled with the file's current first `ts`; the effective delta is `desiredStart − currentFirstTs`. Because the current first `ts` already reflects any prior offset, this composes naturally with earlier adjustments.

A **live preview** shows the file's first and last log line each as old → new (`formatTime(e.ts)` → `formatTime(e.ts + delta)`), plus the resulting Δ, updating as the input changes.

**Merged-file gotcha (the reason this is non-trivial).** `mergeFiles` builds a merged file's `entries` from its sources' entry **objects reused by reference**, not clones — so shifting a source's `entry.ts` also moves those same entries *inside* any merged file that contains them, leaving that merged file's `entries` array (and its `_orderIndexMap`) mis-sorted. `shiftFileEntriesTs` therefore calls `resortMergedFilesAfterShift`, which re-sorts every merged root file's entries by `ts` and drops its order map via `invalidateOrderIndexMap` (an in-place reorder keeps the same array object and length, which the self-validating memo can't otherwise detect — the same case `mergeFiles`' own final sort has to handle). `applyClockOffset` then does a global `invalidateAllCaches()` (a rare structural-equivalent change, same reasoning as the invert toggle). The **source file's own** uniform shift preserves its order — its array/length/positions are unchanged — so its own `_orderIndexMap` stays valid untouched.

**Undo/redo** is a dedicated `"clockOffset"` action `{ nodeId, delta }`. A naive snapshot can't capture the pre-shift `ts` values, because `snapshotSubtree` copies a file's entries **by reference** — the snapshot would already hold the shifted objects. So undo re-applies the *inverse* delta (`shiftFileEntriesTs(node, -delta)`, `node.clockOffset -= delta`) and redo re-applies the forward delta; apply→undo→redo round-trips exactly. Both re-run the merged-file re-sort and `invalidateAllCaches()` via the shared `undo()`/`redo()` tail.

**Persistence.** `node.clockOffset` is a **file-node** field, threaded through every carrier that persists file-node state (per the "thread new fields through all persistence carriers" rule):
- **Session cache** (`persistFileNode`/`restoreSessionFromCache`): the cache stores the file's original content (rebuilt from the *original* `entry.raw`, the File itself, or the path to re-read — see "Session cache"), so on restore the freshly-parsed entries carry the unshifted `ts` — `restoreSessionFromCache` re-applies `rec.clockOffset` to them right after parsing to reinstate the correction.
- **Undo of a file delete** (`snapshotSubtree`/`restoreSubtree`): the entries come back by reference already carrying their shifted `ts`, so `clockOffset` here is preserved purely so the file can still be re-edited/undone after a delete+restore round-trip.
- **Session export/import** (`buildSessionExport`/`applySessionEntryByOrdinal`+`applySessionEntryByContent`): the offset travels with the export document (per the feature's requirement) so the correction survives sharing a session with a colleague. On import, `applyImportedClockOffset` re-applies it to the resolved importer file (their own copy of the log, matched by content) as the *difference* from that file's current offset — idempotent on re-import, and applied **before** any timestamp-based bookmark/note re-anchoring so the exported `ts` anchors land in the same shifted space, so the imported file's first/last timestamps match what was exported.

The four *filter-tree* carriers (`cloneSubtree`, `snapshot`/`restore`, `serializeFilterBranch`/`importFilterJson`, `serializeFilterTreeForCache`/`materializeCachedFilters`) serialize filter children, not file-node fields, so they need no change. One consequence of the raw-text round trip: a **merged** file reparses independently on session-cache restore, so it shows original timestamps for its source entries after a reload (a pre-existing merge-restore simplification, see `mergeFiles`' own comment) rather than the source's re-applied offset. Export/import's **tier-2** time-window auto-match compares the exporter's shifted span against the importer's own span, so an exporter offset can demote a match to tier-1 (content fingerprint, offset-independent — still auto-applies) or the manual tier-3 dialog; the offset itself is applied correctly however the file is resolved.

**Test coverage**: `tests/philogg.regression.test.js` Group 208 — the `parseClockDelta` forms and the context-menu item, difference mode end-to-end (incl. accumulation and order-map validity), start-time mode, the exact undo/redo round-trip, a merged view staying correctly sorted after an offset on one source (plus merged files being refused), and the `node.clockOffset` session-cache round-trip.

## Tailing (live file updates)

Files opened with a **FileSystemFileHandle** (File System Access API — the "Open files…" picker via `showOpenFilePicker`, or drag&drop via `DataTransferItem.getAsFileSystemHandle()`, both Chromium) get a `node.tail = { handle, offset, pending, failed, busy, errorCount, lastGrowth, wasLive }` and are polled every `TAIL_POLL_MS` (1500ms) by `tailTick()`: `handle.getFile()` returns a *fresh* snapshot each call, and if it grew, only the new byte range (`file.slice(offset)`) is read and parsed incrementally by `appendTailText()` into the existing `entries` array — handling chunks that start mid-entry (stack-trace continuation lines written across polls) and keeping an unterminated trailing line in `tail.pending` until its newline arrives. On any change, caches for every node whose parentId chain reaches the grown/rotated file are invalidated (`invalidateCachesForRoots`), so **filtered views update live too** — and/or/link nodes included, since they now follow the same plain parentId chain as any other filter type. Truncation/rotation (`size < offset`) resets that file's entries and re-reads from 0. Files loaded as plain `File` objects (Firefox, the legacy `<input>` fallback, drops without handle support) are byte snapshots and simply never get a `node.tail` — they load normally, without tailing. Tailed files show a pulsing accent icon (`.tree-icon-live`, on the file's own tree-row icon rather than a separate dot) in the tree.

**What one poll tick costs** (performance review, 2026-09-25). Every tailed file is polled **concurrently** (`Promise.all` over the roots — the serial awaits used to add up past `TAIL_POLL_MS` with a folder's worth of open files). A pure append (no rotation in that tick) passes `appendedFrom` (root id → entry count before the tick) to `invalidateCachesForRoots(changedRootIds, appendedFrom)`: a filter whose type is a plain per-entry test (`PER_ENTRY_FILTER_TYPES` — text, level, time range, id set, bookmarks, notes; inverted or not) and whose whole `parentId` chain up to the file is per-entry too keeps its old result as `node._tailBase` = `{ cache, stable, parentStable }` instead of losing it. `stable` is how many leading entries of that result are still exact — everything before the file's previous last entry (the *pivot*, which may have gained continuation lines and is re-tested); the next `getEntries()` runs `extendCachedEntries`, which evaluates the node (`getEntriesUncached(node, parentOverride)`) over just the parent's entries from `parentStable` on and appends that to the kept prefix. Several ticks without a read in between keep the oldest base (its prefixes stay valid under further appends). and/or/link/context/countContext, and anything under one, recompute in full as before; a rotation, the global sweep and every non-tail invalidation clear `_tailBase`. Measured on 650k entries / 100 MB with three filters, text filter active (headless Chromium, `tools/perf/chromium-tail-bench.js`): one tick incl. its render ~340 ms → ~57 ms. Under the desktop wrapper a poll reads only the new bytes (`getPartialReadFile`, see "Desktop wrapper files" below). See `tests/philogg.regression.test.js` Group 272a–c.

**The live dot means "actively receiving new entries right now", not just "still polled"** (`isTailLive(t)`, this session, 2026-08-19, person-reported): `t.lastGrowth` is stamped on every real byte-level change (a genuine append, or a truncation/rotation reset), and the dot only shows while `Date.now() - t.lastGrowth < TAIL_LIVE_MS` (10s) *and* `!t.failed` — a valid, unfailed handle alone is no longer enough. Without this, a file a writer had moved on from (idle, or rotated away from in Folder watch) kept its dot lit forever, since the handle stays perfectly readable, just idle — `t.failed` only ever flips on read errors, never on inactivity. Because a poll tick with nothing new otherwise triggers no re-render at all, `tailTick()` also does a second, cheap pass every tick comparing each tail's current live status against its own cached `t.wasLive` and fires a `renderTree()` (not a full `render()`, no caches to touch) when it flips purely from time passing — otherwise a dot could only go dark on the *next* unrelated tail change, not on its own. See `tests/philogg.regression.test.js` Group 63a/63b.

**Read failures are retried, not fatal on the first one**: a `getFile()`/read failure increments `t.errorCount` and is logged via `console.warn` (previously silent — see "Known limitations"), but only sets `failed` (which stops polling and hides the live dot) once `errorCount` reaches `TAIL_MAX_CONSECUTIVE_ERRORS` (5) **in a row** — any clean poll in between resets the streak to 0. This distinguishes a transient hiccup (most plausibly the writer briefly holding the file locked without shared-read access while it appends a line — an ordinary condition for a log actively being written to by another process) from a genuinely permanent one (moved/deleted/permission revoked), which fails every single poll and still reaches the threshold in ~7.5s.

**Survives a reload**: `persistFileNode` stashes `node.tail.handle` (if any) into the file's session-cache record, and boot-time `restoreSessionFromCache` calls `tryReattachFileTail(node, handle)` for each restored non-folder file — `handle.queryPermission({mode:"read"})` needs no user gesture, so this either silently resumes tailing (with a fresh `offset` computed from the restored text's own length) or leaves the file a static snapshot, same shape `restoreWatchedFolders` already uses for directory handles. See "Known limitations" for the bug this fixed.

**Desktop wrapper files also get tailed** (Bugfix, this session, 2026-08-22, `FEATURE_BACKLOG.md` item 11): a file opened via the desktop app's launch argument, file association, or macOS "open" goes through `loadUrlIntoTree` (see "Deep-link loading (?url=)" below), not the FileSystemHandle path above — it used to build its node from already-fetched text alone and never get a `node.tail`. `isDesktopLocalUrl(url)` now recognizes the desktop wrapper's own `philogg://local/<id>/…` scheme (every fetch to it re-reads the file fresh off disk, see `desktop/src-tauri/src/protocol.rs`) and attaches a `node.tail` whose `handle` (`urlTailHandle`) just re-`fetch()`es that same URL and wraps the bytes in a `Blob` — a drop-in stand-in for `FileSystemFileHandle.getFile()`, so it needs no changes to `tailTick`/`appendTailText` at all. An ordinary `http(s)` `?url=` (CI report link) is deliberately left untouched. **A poll reads only what it needs** (2026-09-25): `urlTailHandle.getFile()` still returns the whole file (full loads, the inline viewers), but tailing, the folder minimap's head/tail probe and a windowed load's bisection go through `getPartialReadFile(handle)` → `handle.getRangedFile()`, which learns the size from a one-byte `Range: bytes=0-0` request (`Content-Range: …/<size>`, or a 416 with `bytes */0` for an empty file) and returns `rangedUrlFile(url, size)` — a Blob-shaped `{ size, slice(), text(), arrayBuffer() }` whose reads each fetch exactly their byte range (`protocol.rs`'s `read_local`, see `docs/desktop.md`). Before, every 1.5 s poll of a 100 MB desktop file re-read and copied the whole file — ~2.3 s per poll in the desktop app, i.e. never idle; now ~2 ms idle, ~130 ms for a poll that parses 1000 new lines (`tools/perf/desktop-tail-bench.sh`). A wrapper without Range support answers 200 with the whole body, which `getRangedFile` accepts as before. A real `FileSystemFileHandle`'s `File` is already lazy, so `getPartialReadFile` just uses it. Since this reuses the same unconditional poll loop, a desktop-opened file that never grows still gets re-checked every `TAIL_POLL_MS` for as long as the file stays open — the backlog item's secondary ask ("periodically re-check static files for changes") falls out of this for free rather than needing separate handling. See `tests/philogg.regression.test.js` Group 89.

**Follow behavior**: while `state.tailFollow` is true and the active node's root file is tailed, **both** the Filtered view (`isTailedLogViewActive()`) and the Context view (`isTailedHighlightViewActive()`) scroll with the newest entry — one shared flag for both (`FEATURE_BACKLOG.md` #25, this session; previously the Highlight view stayed deliberately static while only Filtered followed). Manual scrolling away from the bottom or clicking/selecting a row (incl. arrow keys) in *either* view disengages follow (`applySelection`, shared by `selectEntry`/`selectHighlightEntry`, checks both views' active-tailed state). Two ways to re-engage it, both equivalent: click the floating **"Newest"** button over whichever view has one (`#tailJumpBtn` for Filtered, `#tailJumpBtnHighlight` for Context — both call `jumpToTailedNewest()`), or simply scroll/jump back within reach of the bottom of either view yourself (`maybeReengageTailFollow()`, fired from that view's own scroll listener once `distFromBottom` drops back under the same `ROW_HEIGHT*1.5` threshold used to detect scrolling away) — so a native "jump to the last row" shortcut has the same effect as the button, not just a plain click on it. Programmatic scrolls (follow itself, jump-to-entry, node-switch reset) are distinguished from user scrolls via a timestamp (`lastProgrammaticScrollTs`, shared — every programmatic write goes through `setTableScroll()`/`setHighlightScroll()`) so they never trigger either transition themselves. Tail-driven re-renders route through `pendingTableScroll`/`pendingHighlightScroll` (`"bottom"` = follow, `"keep"` = preserve reading position) so `renderTable()`/`renderHighlightView()`'s normal reset-to-top never yanks either view during live updates; follow only moves a view when the file *behind the current view* grew. A panel hidden behind the other tab (`display:none`) can't actually scroll while hidden (`scrollHeight` collapses along with `clientHeight`) — `showFhTab()`/`applyFhView()` resync a panel to the bottom on becoming visible again if follow is still active, so switching back to it doesn't show a stale, un-followed position. See `tests/philogg.regression.test.js` Group 97.


## File loading: usable while it loads, progress on the real row

A file being read+parsed (`loadOneFileIntoTree`, shared by `loadFileDescriptors` for a plain "Open…"/drag-drop load and `loadFolderFile` for a watched-folder file — see below) used to block the whole app behind a full-screen `#progressOverlay` pop-up. That's long gone: the **real file node exists, and is fully interactive, from the instant loading starts** — before a single byte has even been read — with just a thin progress fill riding along on its own row until parsing finishes.

**`createFileNode(name, folderId)`** builds the node (`entries: []`, `loadFraction: 0`) and inserts it into `state.nodes`/`state.rootIds`/`state.activeId` synchronously, before any async work — so by the time `loadOneFileIntoTree`/`addFile` hits their first `await`, the row is already a normal, selectable, filterable tree row (click, drag, delete, right-click all work on it exactly like any loaded file), just with zero entries so far.

**Entries stream into `node.entries` during the parse** (`parseLogTextAsync(text, node, onProgress)` pushes each completed entry onto `node.entries`/`entryIndex` as soon as it's found, instead of building a private array and handing it all over once the whole file is parsed), but that growth is **not** reflected anywhere live while the load is in progress except the loading file's own tree row — its progress fill and entry count, and nothing else. This was a deliberate simplification, arrived at over several same-session iterations documented below; jump to "Current behavior" if you just need what's true today.

### Current behavior

A load-progress tick (`readFileWithProgress`'s byte-level `onprogress`, `parseLogTextAsync`'s per-`PARSE_CHUNK_LINES`-chunk `onProgress`) calls `scheduleLoadRender(rootId)`, which runs on **every single tick** — no throttle — and does exactly one direct DOM write and **never** a `render()` of any kind — active view or a file loading in the background, no distinction:

- **`updateLoadRowProgress(rootId)`** — direct DOM writes to JUST the loading file's own row: its `.tree-load-fill` width, and its `.tree-count` text. Nothing else — not a filter row already created under it, not the level bar, not the Filtered/Full/minimap view.

Never touches `#tree`'s structure (`el.innerHTML = ""` + rebuild, which `renderTree()` does), so a native click in flight on some OTHER row is never at risk of landing on a torn-down-and-recreated element mid-gesture. Also invalidates the loading file's (and its dependents') cached `getEntries()`/`getLevelCounts()` results on every tick (same reasoning as `onTailChange`'s own `invalidateCachesForRoots` call — a file node's `entries` growing mid-parse is exactly the kind of content change those caches don't otherwise know to distrust) — its only remaining job is keeping a mid-load click onto this file (which DOES trigger a real render) from seeing a cache stale enough to matter, since nothing per-tick reads it anymore. (A real-time throttle around this whole per-tick body was tried and removed again the same session — see "How it got here" below.)

**A filter created under a still-loading file freezes its row's displayed count at whatever it was when created** (or last touched by a real render) — it does NOT keep growing live as its parent streams in more matching entries, even though `getEntries(filterId)` itself (a live query) already reflects the parent's current data at any moment; only a real render (a click, switching away and back, …) repaints it with the current true count. Same story for the level bar: its counts freeze at whatever a real render last showed and do not tick upward as more matching entries stream in.

**The Filtered/Full/minimap view for the loading file (if it's the active view) simply doesn't update again until the load finishes** — `flushLoadRender(rootId)` (`invalidateCachesForRoots` + a real, full `render()`) runs only at the true structural moments of a load: `createFileNode` (the row appearing) and natural completion (the progress fill disappearing), never per-tick. **Completion renders exactly once per file (2026-09-24):** `loadOneFileIntoTree` itself only invalidates the file's caches (it used to `flushLoadRender()` and then its caller rendered again — two full renders per loaded file, each hundreds of ms on a large one); its callers render once it returns, i.e. after the filter-history match and the tail are in place too. `loadFileDescriptors` renders as each file of a batch finishes (so a finished file shows while others still load) and adds a final render only when a file failed (its placeholder is removed without one); `loadFolderFile` and `loadUrlIntoTree`'s native branch render once at their end. Pinned by **Group 265**. Any unrelated action that calls `render()` anyway (a click, a filter edit, switching to a different already-loaded file and back) picks up the file's genuinely-current state at that moment, same as always — it's specifically the automatic per-tick refresh (of anything) that's gone.

**A previous exception to "nothing else updates live" — the log view's scrollbar total tracking a load live for the active node — was removed again (this session, 2026-09-21, person-requested: "Rendern erst wenn vollständig geladen soll für alles gelten").** For one stretch, `updateLiveGrowingTotal(rootId)` (called from `scheduleLoadRender` right alongside `updateLoadRowProgress`) rewrote `#tableSpacer`'s height and ran a cheap `renderVisibleRows()` whenever `rootId === state.activeId` and `currentViewEntries` was literally `node.entries` by reference — fixing a real bug (a large actively-growing merge showed a far smaller, constantly "catching up" scrollbar total until some unrelated full render happened to fire) but, on reflection, itself a second way partial content could leak into view before a load actually finished — alongside the meta-format per-stream focus flicker fixed in the same session (see "Create-first loading" below). Removed outright rather than narrowed further: `scheduleLoadRender` is back to doing only `updateLoadRowProgress`/`updateMergeLoadFraction`, no view/scrollbar write of any kind. **The accepted tradeoff**: `#tableSpacer`'s height (and hence `End`/`Ctrl+End`'s reach) goes back to staying stale, at whatever it was as of the last real render, until the load's natural completion — same as every other part of the view during a load, no special case left.

A person-reported repro (822,697-entry merge, Firefox) had earlier surfaced a second, independent, pre-existing bug, still relevant regardless of the above: `#tableSpacer`'s declared height had no cap at all, and every major browser engine has a hard practical ceiling on a single element's CSS height (Chromium clamps to exactly 33,554,428px, confirmed empirically; Firefox instead discards an oversized declaration entirely, falling back to `height:auto` → 0px for an element whose only content is absolutely positioned, like `#tableSpacer` over `#tableRows`). See "File merge follows the same load-progress pattern" below for the fix (`detectMaxTableScrollPx`/`computeTableSpacerContentHeight`/the `tableScrollHeightScale` conversion) — it still applies to `#tableSpacer`'s height computation at every real render, `renderTable()` included.

### How it got here (same session, 2026-08-18 through 2026-08-28)

The very first version (2026-08-18) went the opposite direction — person-requested: *"die Datei, soweit geladen, direkt zu visualisieren und die Minimap fortlaufend zu befüllen... ähnlich wie eine Datei zu tailen"* (make the file directly usable as it loads, filling the minimap in continuously — like tailing). That version drove a live, tailing-style Filtered/Full/minimap update on every single tick, plus live level-bar counts and live filter-child row counts, then went through several rounds of fixing the DOM-identity fallout that caused (a full `render()`/`renderTree()`/`renderLevelBar()` on every tick tore down rows/buttons a person might be mid-click on — same class of bug as `renderVisibleRows()`/native `dblclick` in CLAUDE.md's "Known gotchas") and, later the same day, several rounds of performance tuning (rAF-coalescing, then a real-time throttle, then skipping the view's two most expensive per-tick scans entirely) once a large/fast load turned out to still be measurably slower with the live view on than with it off — even switching away to a different, already-loaded file mid-load (which always skipped the live update) felt faster. Real decoupling (parsing on a separate thread via a Web Worker, so a render genuinely couldn't block it) was considered and rejected as unrealistic for this codebase's shape: a single 15,000-line inline-script HTML file with no build tooling, no module system to split a worker script out of, and every parse/render function reaching into shared top-level state (`state`, `entryIndex`, DOM element references) a worker couldn't touch directly.

At that point the person's own preference won out over further incremental tuning: *"Baue die Visualisierung einfach aus. Der Ladebalken genügt mir beim Laden."* (just remove the visualization — the progress bar is enough). `scheduleLoadRender` was simplified to two per-tick DOM writes (the loading file's own row, and the level bar's counts), never a `render()`; the throttle, the rAF-coalescing, the per-tick main-view render function, and the flag that used to make `renderTable()` skip its two expensive scans during a tick were all removed outright as dead code.

That still left one more round: switching to a different, already-loaded file mid-load *still* felt noticeably faster than staying on the loading one, and the person suspected the still-live level-bar counts specifically — *"Liegt das daran, dass die Zähler für die Level... noch mitzählen? Nehme (außer dem Ladebalken selbst) (und vielleicht dem Zähler daneben) alle Visualisierungen des Ladevorgangs raus. Und auch Ladebalken etc. darf eine etwas reduzierte Updaterate bekommen."* The level-bar-counts function had no other caller by this point and was deleted outright (not just unhooked); the filter-subtree walk the row-update function used to do was dropped too, narrowing it to just the loading file's own row (renamed `updateLoadRowProgress`); and `scheduleLoadRender`'s remaining work gained a real-time throttle so even the one thing still updating live would do so at a reduced rate rather than on literally every chunk/byte tick.

That throttle didn't survive its own same-day follow-up: it turned out to make no noticeable difference (the level-bar/filter-subtree removal just above was what actually mattered) and looked visibly stuttery — *"nehme die 200ms wieder raus... Das scheint keinen merklichen Unterschied zu machen und sieht so etwas 'stockend' aus. das weglassen der anderen UI Updates hat schon genug gebracht."* Taken back out outright, landing on the unthrottled, single-row-only shape "Current behavior" above describes.

**The read phase** (`readFileWithProgress`, real `File` objects only — `loadOneFileIntoTree`) still runs before there's any text to parse, so it drives `node.loadFraction` across both phases with the pre-existing `READ_WEIGHT`/`PARSE_WEIGHT` split (0.55/0.45) on the SAME row the whole time — there's no separate placeholder to hand off from/to anymore. `addFile` (text already fully in memory — session-cache restore, embedded-log import) has no read phase, so it just creates the node and parses straight into it, no weighting needed (`loadFraction` is a plain 0..1 parse fraction). A load that fails (read or parse error) removes the empty node it created (`catch` → `deleteNode`) instead of leaving a permanently-empty file behind, mirroring the old ghost-row's guaranteed cleanup on error.

**Deleting a file mid-load is guarded end to end (2026-09-19, person-reported: stale entries stayed visible after closing a still-loading file).** Every entry-write site along the parse path now checks the node is still the live one in `state.nodes` before touching it or the global `entryIndex` — `parseLogTextAsync`'s plain-loop fallback (the path jsdom's own `Worker`-less environment always takes, and so what the regression suite exercises) re-checks at each chunk boundary's yield and returns early once the node's gone; the Web Worker path's `onmessage` does the same on its `"chunk"` message and also calls `worker.terminate()` so the background parse actually stops instead of just having its writes ignored; `parseFileWindow` (windowed folder-watch loads) checks the same way inside its own per-chunk yield loop — its `node.id` is checked for truthiness first, since a node passed in without ever being registered in `state.nodes` (a direct/unit-level call, not a real load) isn't "deleted," it just was never live to begin with. Both `loadOneFileIntoTree`'s own trailing `finally` render and `addFile`'s equivalent unconditional one (a second, independently-found instance of the exact same bug) now skip their `flushLoadRender` once the node's confirmed gone, instead of firing a wasted extra render for a dead id. `loadFolderFileWindowed` (the one caller of `parseFileWindow`) distinguishes the two reasons its `ok` can come back `false`: a genuinely unsafe/non-sorted window still falls back to a full reload as before, but a `false` caused by mid-load deletion is now left alone — respecting the delete instead of silently reviving the file the person just closed.

**Rendering**: `renderNode()` draws the progress fill (`.tree-load-track`/`.tree-load-fill`, a thin 2px bar pinned to the row's bottom edge — `.tree-row` is already `position:relative`) directly on a file row whenever `typeof node.loadFraction === "number"`, alongside all its normal interactive chrome (swatch spacer, icon, label, count, delete button, click/drag handlers) — it's not a special row shape anymore, just an extra element on the same one. `renderFolderSection()` (watched-folder files) finds a still-loading root node by `(folderId, name)` among `state.rootIds` as a fallback when `rec.nodeId` isn't linked yet (that only happens once `loadFolderFile`'s own `await` resolves, well after the node itself already exists), so the real, progress-carrying row appears in place of that file's grayed `.folder-watch-file` placeholder immediately, not just once loading finishes.

**Test coverage**: `tests/philogg.regression.test.js` Group 48b/48c cover the row-identity/interactivity side — the real (not a placeholder) row exists and is clickable the instant loading starts, carries the progress fill, and the fill disappears once loading finishes, for both a plain load and a watched-folder file (via the by-name fallback, since `rec.nodeId` isn't linked yet at that point). Group 49 covers a real, EXPLICIT `render()` mid-parse (not an automatic tick): entries/tree-row-count/level-bar-counts all reflecting a genuinely mid-parse state (not zero, not the final total) on a 9000-line file forced across multiple `PARSE_CHUNK_LINES` chunks; level-bar counts being correct again once loading finishes; and the Filtered view not auto-scrolling to chase the growing content. ### Multi-file load: grayed queued placeholders + merge-on-load prompt

Person-requested, this session (2026-08-20, German): dropping/picking several files at once used to only ever show the file currently being read — the next one only appeared once its own turn to load arrived, so a 5-file drop looked like files trickling in one at a time with no visibility into what was still queued.

**`createQueuedFileNode(name)`** builds a lightweight placeholder file node (`queued: true`, empty `entries`) and inserts it into `state.rootIds` immediately — but, unlike `createFileNode`, does **not** set `state.activeId` or render: a placeholder can't be selected or filtered yet, so landing on/showing one would be actively confusing. `loadFileDescriptors` now creates one placeholder per file in the batch, in order, and calls `render()` once — so every file's eventual tree position is visible right away, before any reading starts. `renderNode()` special-cases a `queued` file node (checked first thing, before building the normal interactive row) into `renderQueuedFileRow()`: a non-interactive row — no click/drag/context-menu handlers at all, since there's nothing yet to act on — styled with the new `.tree-row-queued` CSS class, deliberately mirroring folder watch's own grayed `.folder-watch-file` look (`opacity:.55`, same tertiary text color) since it's the same "known its spot, not read yet" idea, just living directly in the main tree instead of a separate box. `flattenTreeIds()` (arrow-key tree navigation) skips queued nodes for the same reason — nothing there to land on.

**`activateQueuedFileNode(node)`** is the counterpart: clears `.queued`, sets `loadFraction = 0`, sets `state.activeId`, and calls `flushLoadRender()` — the exact "insert into the active view" job `createFileNode` normally does itself. `loadOneFileIntoTree` gained an optional 5th `existingNode` parameter: when given a queued placeholder, it calls `activateQueuedFileNode` on it and reuses it instead of calling `createFileNode` fresh — so the SAME node object flips from grayed to a normal, actively-loading row (progress fill and all — see "File loading" above) exactly when `loadFileDescriptors`' loop reaches it. `loadFolderFile` (folder watch) doesn't pass `existingNode`, so its own already-established grayed-listing mechanism (a *different* placeholder shape, `folder.files` records rather than `state.nodes` entries — see "Folder watch" below) is completely unaffected.

**Merge-on-load prompt** (second half of the same request): loading 2+ files in one batch now asks upfront, via a small promise-based dialog (`confirmMergeOnLoad`/`#mergeLoadDialog`, modeled on the existing `sessionMatchDialog` promise pattern), whether to merge them into one chronologically-sorted file (`mergeFiles` — see "File merge follows the same load-progress pattern" below) once they're all loaded. The dialog opens right after the placeholders render (before any file is actually read), so answering it doesn't block the grayed rows from showing — only the actual reading waits on the answer. The "Merge" button is focused the instant the dialog opens, so **Enter answers Yes for free** via the browser's own default button-activation behavior (a focused `<button>` responds to Enter/Space natively — no custom keydown code needed); **Escape answers No** via the existing global `Escape` keydown handler (`if (mergeLoadResolver) closeMergeLoadDialog(false);`, same pattern as `sessionMatchResolver`). A single-file load never shows this dialog at all (`descs.length > 1` gate) — matches the request's own scope ("mehrere Dateien gleichzeitig"). `loadFileDescriptors` `await`s `mergeFiles` before its own promise resolves, so callers (including the test suite) see the merged node only once it's actually finished.

**Resilience fix, needed for the above to actually work**: `loadFileDescriptors`' per-file `await` used to have no error handling at all — one file's read/parse failure threw out of the whole `for` loop, silently abandoning every file queued after it (invisible before this session, since nothing was visibly queued yet; now that every later file has a grayed placeholder on screen, an unhandled throw would leave it stuck grayed forever). Each iteration is now individually `try`/`catch`ed — a failure shows a toast (`Couldn't load "name"`, same wording style as `loadFolderFile`'s own failure toast) and the loop continues to the next file; `loadOneFileIntoTree`'s own existing `catch` (deletes the half-created node) still runs first, so the failed placeholder disappears rather than staying grayed.

### File merge follows the same load-progress pattern

`mergeFiles`/the create-first loaders below build the merged `entries` array progressively rather than in one blocking call, so several very large files being merged never freezes the UI with nothing on screen to explain why — they follow the same "insert the row first, stream progress onto it" shape `createFileNode`/`loadOneFileIntoTree` established for a real file load (see "File loading" above), split across two functions:

- **`createMergeShell(name, formatId)`** builds and inserts the empty merged node (`merged: true`, empty `entries`, `sources: []`, `loadFraction: 0`) into `state.nodes`/`state.rootIds`, plus its own locked **"Sources"** child node (see below), and activates it — a real, fully interactive tree row (same `ICON_MERGE` icon, same click/drag/delete) from the instant merging starts, before a single source has even been read.
- **`fillMergedEntries(node, files, logOrder)`** does the actual entries copy/sort once every source is a complete, loaded file node: `MERGE_CHUNK_ENTRIES`-sized chunks (20,000) pushed directly onto `node.entries` (the row's own count grows live, same idea as `parseLogTextAsync`'s streaming append) with `node.loadFraction` advancing across `MERGE_COPY_WEIGHT` (0.6) and `scheduleLoadRender(node.id)`/a `setTimeout(0)` yield after each chunk, OR — when the sources' time ranges are disjoint — a single quick concat pass; the final chronological sort (only on the overlapping path) runs as one blocking call covering the remaining weight, after the copy phase's last progress tick has already had a chance to paint. The sort is stable, so same-timestamp entries keep the order they were copied in: file by file for independent sources (no shared order exists between them); for a meta-format split, `logOrder` — every stream's entries in the physical file's line order, rebuilt by `loadMetaFormatText` from each stream's `headerOrds` (`splitTextByMetaFormat` records the position of every header line it routes, one per parsed entry) before the per-stream pre-sort, and dropped (`null`, fallback to stream order) if a stream didn't parse to exactly one entry per header line. Without it, a default line and a syslog line at the same millisecond came out in stream order, not file order (GROUP 314). `flushLoadRender(node.id)`/`persistFileNode(node)` finish it off; a `state.nodes[node.id] !== node` guard (mirroring `loadOneFileIntoTree`'s own) handles the node being deleted mid-merge.
- **`mergeFiles(fileIds)`** is the "sources already fully loaded" case (the pre-existing manual "Merge N files" bulk action, `performBulkAction`, and any other caller with complete nodes in hand): `createMergeShell` + tag each source `mergeOwnerId` (see below) + `fillMergedEntries`, back to back, in one call — unchanged in substance from before this session's create-first rework, just internally split.

**Create-first loading (person-requested): the merge exists before any source is even read.** Every "load files straight into a merge" path — `loadMetaFormatText`'s per-grammar streams, `loadFileDescriptors`' drag-drop-then-"Merge" confirm, and the folder-watch minimap's "Merge (full)"/"Merge (window)" actions — now calls `createMergeShell` FIRST, then loads each source into its own real file node **tagged `mergeOwnerId` (this merge's id) and `mergeSourceHidden: true`** the moment it's created (or, for folder-watch, the moment its own load finishes — see below), and only calls `fillMergedEntries` once every source has finished. A source tagged `mergeSourceHidden` is an implementation artifact of the merge, not something the person opened themselves — `renderTree`/`renderFolderSection`/`flattenTreeIds` all skip it from their plain top-level walks, so it's only ever reachable nested under its merge's "Sources" node (below); it is **never independently deleted** — unlike the previous session's meta-format design, a source stays a real, independently clickable, filterable file node for as long as the merge exists. `loadFileDescriptors` and `loadMetaFormatText` can pre-tag a `createQueuedFileNode` placeholder before its own read even starts (reusing `addFile`/`loadOneFileIntoTree`'s existing `existingNode` parameter — the exact seam the grayed-placeholder mechanism above already provides), so there's no top-level flash at all; the folder-watch case has no such placeholder to pre-tag through (`loadFolderFile`/`loadOneFileIntoTree` own their own node creation), so tagging happens right after that source's own load finishes instead — a brief, accepted visibility gap rather than a larger refactor. If fewer than 2 sources end up loading successfully, the shell is discarded (`deleteNode`) and any lone survivor is un-tagged back to a normal, visible file.

**A meta-format split (`loadMetaFormatText`) used to briefly steal focus onto each per-grammar stream while it loaded — fixed this session, 2026-09-21, person-reported.** Loading a stream into its own node goes through `addFile(..., placeholder)`, which internally calls `activateQueuedFileNode` — unconditionally setting `state.activeId` to that placeholder for the duration of its own read+parse, same as any other file load. For an ordinary multi-file load that's correct (the last file dropped ends up active); for a meta-format split it meant the merge's own row lost focus to whichever stream was currently loading, and that stream's own natural-completion render (a real, full `render()`) painted the Filtered/Full/minimap view with that ONE grammar's already-complete content — briefly looking like the merge itself had finished, before the loop moved to the next stream and finally restored focus to the merge. A new `metaFormatSplitInProgress` flag (mirroring the pre-existing `sessionRestoreInProgress` guard `createFileNode`/`activateQueuedFileNode` already had) is set for the whole per-stream loop and checked in both functions' `state.activeId` assignment, so the merge row — created and activated once by `createMergeShell`, before the loop starts — simply never loses focus to a stream. The merge's own view stays exactly as frozen/progress-bar-only as any other loading node throughout, consistent with "File loading" above.

The **pre-existing manual "Merge N files" bulk action is the one caller that does NOT hide its sources**: `mergeFiles` tags each source `mergeOwnerId` but deliberately leaves `mergeSourceHidden` unset, so an already-loaded, already-visible top-level file stays exactly where it was — appearing a *second* time, nested under the new merge's Sources, both DOM rows referencing the very same `state.nodes` entry.

**Deleting the merge cascades correctly, and undo restores the whole thing (2026-09-19, person-requested).** `deleteNode`, after its existing recursion over `node.children` (which never reaches `node.sources` — those are root-level siblings, not real children), now walks a merge's own `node.sources` too: a `mergeSourceHidden` source has no life outside the merge and is deleted right along with it (recursively, via the same `deleteNode`); a bulk-merge-visible (`mergeOwnerId`-only) source instead survives at top level, with `mergeOwnerId`/`mergeSourceHidden` cleared so it doesn't keep pointing at a now-dead merge id. `snapshotSubtree` (called before `deleteNode` by `deleteFilterNodeWithUndo`, so hidden sources are still live at that point) captures each hidden source's own full nested snapshot under a new `hiddenSourceSnapshots` field, since they're root-level and the function's normal `children` recursion can't reach them; `restoreSubtree` recreates them under a transient `hiddenSourceIds`, and `undo()`'s `"deleteFile"` branch splices each restored id back into `state.rootIds` (every file node must live there) right after the merge's own, and re-`persistFileNode`s each one. This also closed a latent gap: neither function had ever needed to carry a file node's own `mergeOwnerId`/`mergeSourceHidden` tags before (a hidden source was never independently the *subject* of a snapshot/restore until this), so both fields are now threaded through the file branch of each, same tier as `clockOffset`.

**"Sources" is a real, locked filter node — the same tree level as Bookmarks/Notes/Selection N, not an extra nesting level.** `createMergeShell` creates one `{type:"filter", filterType:"sources", locked:true, children:[]}` node per merge and inserts it via `insertSpecialChild` (below) at rank 0, so it always sorts first among a file's auto-managed rows. Its own `node.children` stays permanently empty — nesting is driven by the owning file's `sources` array (`{id, name, color, count}`, additively stamped by `fillMergedEntries`/`mergeFiles` onto every copied entry as `entry.sourceId`) plus each source's real file node, rendered a second time via the ordinary `renderNode(src.id, depth+1, {mergeSourceColor: src})` — reusing the exact same renderer ZIP/folder container nesting already uses for "a real root node, rendered nested, skipped from the plain top-level walk." `getEntries` on a Sources node is a pure passthrough of its parent's own result (it's a label/anchor, not a real filter); it's excluded from the filter-tree persistence carriers (`serializeFilterTreeForCache`/`materializeCachedFilters`/`importFilterJson`) exactly like Bookmarks/Notes. Its own expand/collapse uses the node's real `node.collapsed` — the same mechanism any other node's children use, no bespoke field; `createMergeShell` leaves it expanded (so per-source progress is visible while loading), and `fillMergedEntries` sets it `collapsed = true` the moment the merge finishes (2026-09-19, person-requested — applies to both the create-first and bulk-merge paths, since both funnel through `fillMergedEntries`).

A nested source row (`opts.mergeSourceColor` set) has **no ✕ or middle-click delete of its own** (2026-09-19, person-requested: "they're only deleted together with the merged entry") — `renderNode`'s delete-button and `auxclick` handlers both gate on `!(opts && opts.mergeSourceColor)` alongside the existing `!node.locked` check. The very same source's *top-level* row (the bulk-merge-visible case, rendered with no `mergeSourceColor`) is a completely ordinary, independently deletable file row — the restriction is purely about the nested rendering, not the underlying node.

Each source gets its own color swatch on its nested row, reusing the existing highlight color-picker popup: `openColorPicker` gained an optional `onPick` callback (and `commitColorPick` to dispatch through it) so a pick can land on `node.sources[i].color` instead of a filter node's `highlightColor` — the one pre-existing caller (a filter node's own swatch) is unaffected, since it passes no callback. `computeHighlightMap` gained a matching branch so a colored source's own entries (matched by `sourceId`) pick up the same gutter-marker lane filter highlights already use, composable with them — deliberately not wired into the text-underline-stripe path, which is specifically for a filter's own text match, not an entry's origin.

**A new "Show Sources" setting** (Settings → Behavior → Filter tree, default **on**, `philogg-show-sources` in `localStorage`, `showSourcesSetting`) is a pure display toggle — `renderNode` simply skips rendering a Sources node (and therefore its nested rows) while it's off; the underlying node/data are never touched.

A create-first merge's own row shows a **single continuous progress bar**, reusing the exact same plain `.tree-load-fill` markup and `updateLoadRowProgress` DOM writer an ordinary file's own bar already uses — **always, regardless of the Show Sources setting** (with Sources shown, each nested source's own row still carries its own ordinary bar too, alongside the merge row's — not instead of it). `node.loadSources` (an array of `{id, weight}`, set once per merge by whichever create-first loader populates it — real `File.size` for `loadFileDescriptors`, a character-count proxy for `loadMetaFormatText`'s in-memory streams, an equal-weight fallback for folder-watch merges, which have no size available and load strictly sequentially anyway) and `updateMergeLoadFraction` (hooked into `scheduleLoadRender`) compute one combined `node.loadFraction`: each source's own `loadFraction` weighted by its `weight` (person-requested — a two-file merge of very differently sized sources should fill proportionally to their real size, not an equal split), scaled into `1 - MERGE_STEP_BAR_FRACTION` (a fixed `0.1` reservation for the eventual merge-copy/sort step, since that's normally much faster per-byte than the read+parse phase it follows — not worth modeling exactly). `fillMergedEntries` fills the reserved tail once every source is done: a disjoint/quick merge still jumps the WHOLE bar to 100% in one step (unchanged in effect from before — just the entire bar now, not a single segment); the chunked copy/sort path fills the last `MERGE_STEP_BAR_FRACTION` incrementally. This **replaces** an earlier `(n+1)`-segment design (`node.loadSegmentSourceIds`, `.tree-load-segments`/`.tree-load-fill-segment` markup, `mergeSegmentFractions`/`updateMergeSegmentedProgress`, one equal-width segment per source plus one for the copy step) entirely — that design gated the whole bar off while Show Sources was on (a two-file ~100MB drag-drop merge showed no progress at all on the merge row while both sources loaded), and split progress into equal shares regardless of how differently sized the sources actually were; both problems are what prompted this rework.

**Ordering: Sources, Bookmarks, Notes, Selection 1, Selection 2, ...** `specialChildRank(node)`/`insertSpecialChild(root, nodeId, rank)` (near `syncBookmarksFilterNode`) replace what used to be four independent ad hoc `unshift`/splice calls with one shared, rank-based insertion rule (Sources=0, Bookmarks=1, Notes=2, Selection N=3+its own creation ordinal, captured on the node as `selectionOrdinal` so a later rename can't disturb its sort position) — `syncBookmarksFilterNode`, `syncNotesFilterNode`, `createSelectionFilterNode`, and `createMergeShell`'s own Sources node all call it. An ordinary, user-created filter node has no rank and is never displaced by any of this; a new special node is always inserted at the mathematically correct position relative to whichever special nodes already exist, regardless of creation order.

Session-only by explicit design, same as before: `sources`, `entry.sourceId`, and the Sources node itself are never written by `persistFileNode`, so a session-cache restore of a merged file comes back reparsed under one format with none of this — the same accepted gap the "Merged-file gotcha" above already documents for a merged file's clock-offset state. `sources` (and `metaFormatId`) IS threaded through `snapshotSubtree`/`restoreSubtree`'s file branch (by reference, same tier as `entries`/`tail`), and the Sources node itself rides along as an ordinary child via the *generic* filter-node branch of the same two functions (no special-casing needed) — so an in-session delete+undo of a merged file doesn't silently drop its Sources node, breakdown, or any assigned colors. As of the cascade-delete/undo fix above, the merge's *hidden sources themselves* also survive the same round trip, via `hiddenSourceSnapshots`/`hiddenSourceIds`.

**Known, accepted limitation.** Entries are shared by reference across merges (same premise the "Merged-file gotcha" above relies on) — merging an already-merged file's entries into a further merge overwrites `sourceId` on those same shared objects, so the *earlier* merge's own Sources coloring goes stale (it now reads as whichever source the *later* merge assigned). Not fixed — nested merges are an edge case, and the fix would need per-entry provenance to become a list rather than a single id.

## Deep-link loading (`?url=`)

`philogg.html?url=<encoded-url>` fetches a log at boot and opens it, straight into `addFile` — the same path a session-cache restore uses (text already fully in memory, no separate read phase). `loadFromUrlParam()` (next to `loadFileDescriptors`, "File loading & progress" above) parses `location.search`, `fetch()`s the URL, derives the tree row's name from the URL's last path segment (falls back to `"remote.log"`), and calls `addFile(name, text)` + `render()`. If the url is the desktop wrapper's own `philogg://local/…` scheme, `loadUrlIntoTree` also wires up a live `node.tail` so the file gets polled/tailed like any other locally-opened file — see "Tailing (live file updates)" above.

Two consumers this is meant for: a CI/report link straight to a build's log artifact on a webserver, and the desktop wrapper (`docs/desktop.md`), which reads a local file natively (no browser-gesture requirement) and serves it through a `philogg://` URL, reusing this exact mechanism instead of building a second, separate content-injection path.

**Requires PhiLogg itself to be served over `http(s)`** — a `file://` page can't `fetch()` anything at all, cross-origin or not (Chromium's own restriction, nothing PhiLogg can work around). `loadFromUrlParam()` checks `location.protocol` first and shows a dedicated toast instead of a confusing raw fetch error in that case. A remote log server also needs to answer with CORS headers (or be same-origin) — same browser rule as any other cross-origin `fetch()`, not something worth trying to route around.

Errors (network/CORS failure, non-2xx HTTP status) show a toast (`showCopyToast`) and add no file, instead of failing silently.

**Test coverage**: `tests/philogg.regression.test.js` Group 66 — successful load (name derived from the URL, text parsed into entries), an HTTP error status, and a rejected fetch (network/CORS), each via a fake `window.fetch` (jsdom ships none). The `file:` protocol guard itself has no jsdom coverage — jsdom treats every `file:` URL as an opaque origin and throws on the app's own boot-time `localStorage` access before `loadFromUrlParam` ever runs, for any URL shape (see `tests/README.md`'s "Known gaps") — verified instead with a real Chromium session (Playwright) against a local static server: a same-origin `?url=` load rendering the file, and an unreachable URL producing the expected error toast with zero tree rows.


## Folder watch + lazy loading

FEATURE_BACKLOG.md item, built in two rounds this session (2026-08-16): the initial build, then a person-reported follow-up in the same session covering four refinements — a unified "Open…" menu, files rendered *inside* the folder listing instead of moved out below it, a browser-capability gate, and session-cache persistence. All four are folded into the description below rather than kept as a separate "what changed" appendix.

**Entry points**: pick a whole folder via the **"Open…"** button's dropdown menu (**File(s)…** / **Folder…** — replaced two separate always-visible buttons, since the browser-support asymmetry between them, see below, made two equally-prominent buttons misleading) or drag&drop (a dropped folder resolves to a `FileSystemDirectoryHandle` via `getAsFileSystemHandle()`, same as the single-file drop path already used). Under a desktop wrapper that can list directories itself, both entry points go through the wrapper instead — `philogg.pickFolder()` for the menu item, the wrapper's own native drop for the other (see "Two kinds of directory handle" below).

**Support is checked once, upfront, not tried-and-caught per attempt**: `FOLDER_WATCH_SUPPORTED = !!window.showDirectoryPicker || FOLDER_WATCH_NATIVE`, computed at script init (`FOLDER_WATCH_NATIVE` = a desktop wrapper exposing `philogg.listFolder`). Unlike single-file loading (which has a real, fully-working fallback — the hidden `<input>`), there is **no meaningful fallback for folder watching**: without a live directory handle there's no way to list or re-scan a folder's contents at all, so a browser without the File System Access API (Firefox/Zen today) gets a clear popup instead of a silently degraded experience:
- The **"Folder…"** menu item, clicked without support, shows `showCopyToast(FOLDER_WATCH_UNSUPPORTED_MSG)` instead of opening anything.
- A dropped **folder** without support is actively *detected* — via `webkitGetAsEntry()`, which (unlike `getAsFileSystemHandle`) Firefox does implement — specifically so it can show the same popup instead of being silently misread as an empty/broken file list (which is what plain `dt.files` gives you for a dropped directory in a browser without the newer API). A dropped plain *file* is completely unaffected either way.

**Two kinds of directory handle.** The API above is a *webview engine* API and obeys the engine's rules, which is a real limit and not a theoretical one: Chromium refuses a handle for any directory on its hardcoded sensitive list ("this folder contains system files" — Desktop and Downloads among them), and no embedder can switch that off; WebKit-based webviews don't implement the API at all. So a desktop wrapper that can list a directory natively is used in preference to it: `nativeDirHandle(path, name)` (defined next to `urlTailHandle`) is a duck-typed stand-in over `window.philogg.listFolder`, implementing exactly the four members this feature uses — `name`, `values()`, `queryPermission()`, `requestPermission()` — so everything below is written against one shape and never branches on which kind it holds. Its `queryPermission()` is a constant `"granted"` (a native listing has no permission model), and each entry it yields *is* a `urlTailHandle` carrying the file's real path, which is why a file opened from such a folder tails, reveals and copies its path like any other. Only persistence has to tell the two apart — see below. The desktop wrapper provides the native route (`docs/desktop.md`); every browser build takes the `showDirectoryPicker()` one and inherits the engine's blocklist.

**Data model**: `state.folders`, a list of `{ id, name, handle, files: [{ name, relPath, handle, nodeId }], busy, failed, needsPermission, settings }`. `handle` is either a real `FileSystemDirectoryHandle` or a `nativeDirHandle` stand-in with the same four members (above), and a file record's `handle` correspondingly either a `FileSystemFileHandle` or a `urlTailHandle`. `folder.id` doubles as the persistent IndexedDB key for the folder (see "Persistence" below) — generated via the same `newCacheKey()` file nodes already use, not a throwaway `uid()`, specifically so it's stable across a reload. A file record's `nodeId` is `null` while it's still a grayed, unopened listing entry, set once it's been opened into a real `state.nodes` file node (tagged `node.folderId` with that same folder id). `relPath` is the file's path relative to the watched folder's own root (equal to `name` for a file directly in it); `folderFileKey(rec)` (`relPath || name`) is the merge identity used everywhere two scans need to be matched up, so same-named files in different subfolders don't collide. `settings` (`defaultFolderSettings()`) holds this folder's own configuration — see "Per-folder settings" below.

**Subfolder tree** (`renderPathTree`, shared with ZIP sources below): once any listed file has a `/` in its `relPath` (ZIP: `entry.name`), `buildPathTree` groups the listing into directories and each directory renders as a collapsible `.tree-row.tree-dir-row` (chevron, `ICON_FOLDER`, name, file count below it) — per level directories first, then files. Listed and opened rows inside get the depth's indent plus an (empty) chevron slot (`placeRowInPathTree`, `.folder-watch-file.in-tree`), and `decorateTreeGuides` draws the usual connector lines over the whole container tree (it is idempotent and also walks `.folder-watch-file` rows, since dir rows and listed rows are reused across renders via `cachedInactiveRow`). Expansion state is session-only, per container (`owner.expandedDirs`, a Set of relative dir paths); **collapsed by default**. `loadFolderFile(…, auto)` calls `expandPathTreeTo` so a file an auto rule opens is visible. `flattenTreeIds` skips everything inside a collapsed directory (`isInCollapsedFolderDir`, `isPathTreeVisible`, `forEachVisiblePathTreeItem`). A container without subfolders keeps the flat listing (`folderTopLevelNoChevron`) unchanged. Opened ZIP entries show their basename in the tree (`renderNode`'s `opts.labelText`), the node itself keeps the full relative path as its name.

**Scanning**: `scanFolderHandle(dirHandle, settings)` reads directory *entries* (`dirHandle.values()`) and filters by BOTH `isCompatibleFolderFile()` (currently `[".log"]`, `FOLDER_WATCH_EXTENSIONS` — an array so a future "pluggable parser" session has one obvious place to widen it) and the folder's own configured filename patterns (below) — it never reads a file's *content*. Nothing is parsed until a person actually opens one. Non-recursive by default, matching the backlog's original "list them" scope; recurses into subdirectories only when `settings.includeSubfolders` is set (walking any entry whose `values()` exists — a no-op under the desktop wrapper's native listing, which is a flat, non-recursive `read_dir`, see `docs/desktop.md`). `mergeScannedFiles(folder, scanned)` folds a fresh scan into `folder.files`, preserving each already-known entry's `nodeId` (and therefore its identity as a real vs. grayed row) while refreshing its `handle` — the one shared implementation behind the initial scan (`addWatchedFolder`→`rescanFolder`), `folderScanTick`'s repeat polls, and a restored folder's reconnect scan. An entry that no longer appears in a fresh scan — deleted on disk, or (closed only) simply stopped matching a pattern — is dropped from the listing entirely; an *open* one is closed first (`closeFolderFile`, same teardown as the person closing it by hand) so its node doesn't leak once nothing points at it anymore (person-reported fix: a file deleted outside the app used to linger in the listing forever once it had been opened). For a natively listed folder it also refreshes an open file's `sourceUrl`/`localPath` from the scan (`applyFolderFileLocation`, also called by `loadFolderFile`): the id in a wrapper's `philogg://local/<id>/…` URL is per-*process*, so a session restored from cache holds dead URLs until the first rescan re-registers each file. Every merge finishes by (awaiting) `applyFolderAutoRules(folder)` — see "Per-folder settings" below.

**Per-folder settings** (gear icon, `.folder-watch-settings`, on each folder's header — `openFolderWatchSettingsDialog`/`#folderWatchSettingsDialog`, styled with the same `settings-page-card`/`settings-row`/`settings-switch` classes as the app-wide Settings dialog, just scoped to one folder and without its section nav): **filename patterns** (`settings.patterns`, a list of `{ pattern, autoOpenNewest, autoCloseKeep, showNewest, startFilterKeys, startPrimaryFilterKey }`, default one `{ pattern: "*" }`) — a file must match at least one pattern's glob (`getCompiledGlob`, the same engine "Log Formats"' filename rules use) to be listed at all, on top of the fixed extension filter; `matchFolderPattern()` resolves a file to its first matching pattern, first-match-wins like the format rules. Each pattern carries its own three auto rules, applied by `applyFolderAutoRules()` after every merge, per pattern, in this order: (1) **"Show M newest files"** drops *closed* listing entries older than the M most recent matches (an open file is never dropped); (2) **"Auto-close — keep only N open"** is a **sliding window** over the N newest matches — it opens (via `loadFolderFile(folder, rec, true)`, awaited) whichever of those N aren't open yet and haven't already been auto-opened once (`rec.autoOpenFired`, see below), then closes (via `closeFolderFile`, stays listed grayed out, not removed) any currently-open match that fell out of the window **and was itself opened by an earlier auto rule** (`rec.openedByAuto`) — a file the person opened by hand is never auto-closed, regardless of the window. Fixed a person-reported bug: a naive "just close the oldest once too many are open" never opened the newer file that pushed the count over N in the first place — a new file arriving must itself become one of the N open ones, evicting the previous oldest, not leave the open set unchanged. (3) **"Auto-open newest file"** is the plain one-file version of the same idea for a pattern with no keep-N configured — opens the newest match if it isn't open yet and hasn't already been auto-opened once, without touching any other open file (skipped when keep-N is also set on that pattern, since its window already includes the newest). "Newest" (`sortFolderRecsByRecency`) uses each file's real `lastModified` (mtime) when it's known, falling back to name order only when it isn't — fixed a second person-reported bug: a pure filename-order heuristic silently mis-picked "newest" for any naming scheme where a chronologically newer file doesn't happen to sort last as a plain string (unpadded day-of-month, a rotated-log scheme where the *active* file has the smallest name, etc.). `scanFolderHandle` fetches each matching file's `file.lastModified` via one extra `getFile()` per file — gated behind `folderSettingsNeedRecency()` so a folder with no auto rules configured pays nothing extra on its 3s poll — and `mergeScannedFiles` carries it across rescans like `relPath`. mtime is **not** available for a natively listed folder's files (desktop wrapper — `urlTailHandle.getFile()` returns a plain fetched `Blob`, which has no `lastModified`; see `docs/desktop.md`), which is why the name-order fallback still matters rather than assuming mtime always works; the folder listing's own display order (`mergeScannedFiles`) stays name-sorted regardless — this only changes which file the *rules* treat as newest. **"Start filters"** (`startFilterKeys`/`startPrimaryFilterKey`, `FEATURE_BACKLOG.md` #71, a checkbox list next to the three rules above — `fwPatternStartFiltersBlock`) names zero or more saved **Filter Library** records (`saveFilterToLibrary`/`listFilterLibrary`, see the "Filter library" section below) to apply the moment THIS pattern's own auto-open/auto-close rule opens a file — never for a file opened by hand: `loadFolderFile`'s `auto` branch looks the keys up (`applyFolderStartFilter`) and, for each record that still exists, hands it to the same `applyFilterFromLibrary()` the "Apply from library…" context-menu action uses, so each filter is re-evaluated fresh against the newly opened file rather than replayed from wherever it was saved. Several presets can be selected (person-requested); one of them is the **Primary** (`startPrimaryFilterKey`, a same-`name`-grouped native radio per pattern card in the dialog, so exactly one can be picked among the checked presets) — `applyFolderStartFilter` applies it LAST, so its own `applyFilterFromLibrary` call is what actually decides `state.activeId`/reveals the view, meaning the person's view "jumps into" the Primary filter regardless of the other presets' own list order. The dialog keeps a non-empty selection with exactly one Primary on its own: checking a pattern's first preset auto-picks it as Primary, and unchecking the current Primary auto-promotes another still-checked preset (or clears it if none remain) — no separate "no Primary" state to reach by hand. `startFilterKeys: []`/`startPrimaryFilterKey: null` by default — a pattern that never touches the checkboxes behaves exactly as before this setting existed. Folder-wide: **include subfolders** (`settings.includeSubfolders`, drives the recursive scan above) — with subfolders in the listing, the folder section renders them as a **subfolder tree** (see "Subfolder tree" below) instead of flat `sub/App.log` labels (the old "show relative path" switch is retired). Every change in the dialog re-persists the folder and re-scans immediately (`commitFolderWatchSettings`) — no separate Save button, same immediacy as the rest of Settings.

**Auto-open/auto-close act on a file at most once each way** (person-reported): `rec.autoOpenFired` is a permanent flag set the first (and only) time either auto rule opens a given file's record — a person who closes that file again is left closed on every later rescan/poll instead of having it silently reopen. `rec.openedByAuto` records whether the file's *current* open came from an auto rule (`true`) or a person double-clicking/context-menuing it themselves (`false`, the default `loadFolderFile(folder, rec)` call with no third argument) — it both drives "auto-close — keep only N open" (above, never closes a manually opened file) and an auto-opened file's tree row: its icon swaps to `ICON_FILE_AUTO` (the same file glyph with a small circled "A" badge) with a tooltip noting it was opened automatically, so the two ways a folder-watch file ends up open read differently at a glance.

**UI — files render IN THE FOLDER, in folder order, not moved out below it** (person-reported follow-up; the initial build rendered opened files as ordinary root nodes under `#tree` and only kept not-yet-opened ones in the folder box, which lost the file's position in the folder once opened). `renderFolderSection()` now walks `folder.files` **in order** and, per entry, renders either a real `.tree-row` (`renderNode(rec.nodeId, 0, { folderTopLevelNoChevron: true, autoOpened: rec.openedByAuto })`, for an opened file — filters and all) or a grayed `.folder-watch-file` row (`renderInactiveFileRow`, for an unopened one) into the *same* `.folder-watch-files` list — so a file's spot in the folder stays visible whether it's open or not, and opening/closing it never reorders anything. The `folderTopLevelNoChevron` option (person-reported: an opened file used to read as more indented than its still-closed siblings) makes `renderNode` use the closed rows' flat 12px inset instead of the normal 8px-plus-chevron-slot one, and skip reserving the chevron slot at all when the file has no filters of its own to collapse. The "still loading" fallback that finds a not-yet-linked file's own progress-carrying row (`rec.nodeId` not set yet, but its node already exists — see "Rendering" above) matches by folder+name alone now, not additionally requiring `typeof loadFraction === "number"`: gating on that left a one-render gap, between `loadOneFileIntoTree` clearing `loadFraction` and `loadFolderFile` (its caller) setting `rec.nodeId` on the very next line, where the file briefly fell through to the closed/grayed placeholder (person-reported: "loading → indented open → briefly grayed → open" instead of a clean "loading → open"). `renderTree()` correspondingly **skips** any root id whose node has a `folderId` when building the plain top-level list — those render exclusively inside their folder's own section now. The header still shows a pulsing "ping" ring (`.folder-watch-icon.scanning`, `@keyframes folder-scan-ping`) while the folder is being actively polled, and a ✕ to stop watching (`removeWatchedFolder`).

**Sidebar rows across renders** (performance review, 2026-09-25): `renderTree()` rebuilds the folder and ZIP sections on every `render()` — every tail tick of an active live file included. An unopened row is now reused while its label is unchanged (`renderInactiveFileRow` keeps it on the rec as `rec._inactiveRow`; ZIP/folder non-log entries via `cachedInactiveRow`, keyed by the owner's `inlineViewers` map — only the unopened state is reused, an opened one's handlers close over its viewer), and the "still loading" fallback and the ZIP section look open roots up in a per-section `rootByName` map instead of scanning `state.rootIds` per listed file. Keeping the element also keeps a double-click on a grayed row working through such a render (PROJECT.md's DOM-identity gotcha). A browser folder's mtime reads (`scanFolderHandle`, only with a recency rule configured) run concurrently instead of one `getFile()` after the other on every 3 s poll, and `mergeScannedFiles`' "file disappeared" check uses the `_lastScanKeys` set instead of an O(n²) scan. Group 272g.

**Double-click, or a grayed row's own right-click → "Load file"** (`openFolderFileContextMenu`, a minimal one-item menu reusing `#treeContextMenu`, distinguished by `folderCtxTarget` instead of `treeCtxId`) calls `loadFolderFile()`, which reads+parses the file (`loadOneFileIntoTree()` — the read/parse/persist/history/tail-wiring body `loadFileDescriptors` shares with this entry point) and turns it into a **completely normal root file node**, tagged `node.folderId`. It behaves exactly like any manually opened file from there — build filters on it with Ctrl+F — and, since it was opened via a real handle, starts **tailing automatically** for free.

**"No filter can be created on / copied onto an inactive file" holds by construction, not by an extra guard**: a grayed listing row is never a `state.nodes` entry and is rendered by entirely separate DOM/CSS (`.folder-watch-file`, no `draggable`, no `dragover`/`drop` listeners, no click handler that sets `state.activeId`) from a real `.tree-row` — so there is no node id Ctrl+F/paste/drag-and-drop could ever target. Nothing had to be special-cased in `openFilterPopup`/`pasteClipboard`/the tree's drag handlers.

**Closing a folder-loaded file doesn't remove it — it goes back to grayed, in the same spot.** `deleteFilterNodeWithUndo()` special-cases any file node with `node.folderId` into `closeFolderFile()`: the node and its whole filter subtree are torn down exactly like a normal close (`deleteNode` — entries released from `entryIndex`, cache invalidated, `cacheDeleteFile` fires), but the folder's own file record just has its `nodeId` cleared back to `null` instead of being removed from `folder.files` — so it reappears in its original position in the folder's file order (same handle reused, reopening needs no re-scan) instead of disappearing or getting appended at the end. A plain file with no `folderId` is completely unaffected. `removeWatchedFolder()` (the folder's own ✕) clears `folderId` off any currently-open files from that folder first, so they become plain independent files (rendered back under the plain `#tree` list, a later close on them is then a normal full removal) before dropping the folder record and its persisted store entry (`cacheDeleteFolder`).

**New-file detection**: `folderScanTick()` polls every actively-watched folder (`handle` present, not busy, not `needsPermission`, not `failed`) every `FOLDER_SCAN_MS` (3000ms — same handle-polling shape as `tailTick`/`TAIL_POLL_MS`, one level up) via `mergeScannedFiles`. Removed files ARE detected now (see "Scanning" above — `mergeScannedFiles` drops/closes any listing entry a fresh scan no longer finds, open or not); opening a since-deleted grayed entry that a poll hasn't caught up to yet surfaces a toast instead of crashing. A read/permission failure sets `folder.failed` (stops the scanning ping) rather than throwing, same graceful-degradation shape as a tailed file's own `tail.failed`.

**`folderScanTick`'s "did anything actually change" check is against `folder._lastScanKeys`, never `folder.files`** (bugfix, person-reported: "Show M newest files" made scrolling feel laggy, and a selected row occasionally got yanked back into view on its own, both tied specifically to that setting). `folder._lastScanKeys` (a `Set` of every `relPath` the most recent `scanFolderHandle()` actually found on disk) is written inside `mergeScannedFiles` itself — the one shared merge funnel (initial scan, poll, reconnect) — so it always means "what's really out there", independent of what got merged into the listing afterward. `folderScanTick` compares each new scan against it to decide `hasNew`/`hasRemoved`. Before this, that comparison was against `folder.files` directly — which "Show newest M" (`applyFolderAutoRules`'s rule 1, above) actively *shrinks*, dropping closed listing entries beyond the newest M straight out of `folder.files` without anything actually disappearing from disk. The next poll's scan still found those files, they no longer matched anything in `folder.files`, so they looked brand new — triggering `mergeScannedFiles` (which puts them back) then `applyFolderAutoRules` (which immediately hides them again) — a merge-and-render loop that repeated on every single poll, forever, for any folder with more matching files than its "Show newest M" count. Each of those unwanted `render()` calls could also snap a deliberately-scrolled-away selection back into view (`renderTable`/`renderHighlightView`'s `captureViewAnchor`/`restoreViewAnchor`, see "Context view" above, prioritizing the still-selected row) — the exact symptom reported. `tests/philogg.regression.test.js` **Group 195** — a folder with 3 static files and "Show newest 1" configured: zero `render()` calls across 4 stable polls (verified to fail without the fix), the 2 hidden files staying hidden rather than flickering, and a genuinely new file still being detected and swapping the window onto it.

**Persistence — a watched folder now survives a reload** (person-reported follow-up: "currently no reload survives folder watch"). The mechanism relies on a real, spec-guaranteed fact: a `FileSystemHandle` is designed to survive IndexedDB's structured clone algorithm — that's the actual, standard way browsers let a handle outlive a page reload at all, no different in kind from how the pre-existing tail-handle mechanism already trusted `FileSystemFileHandle` objects to keep working across `getFile()` calls. `persistFolder(folder)` stores `{ key: folder.id, name, handle, path, settings }` in a `folders` IndexedDB object store (`CACHE_DB_VERSION` 2→3); `cacheDeleteFolder` removes it when the folder is dropped. A `nativeDirHandle` is the one thing that can't go in as-is — it holds a closure, and structured clone rejects the whole record (the same `DataCloneError` trap the `urlTailHandle` cache bug fell into) — so for one of those the `path` is stored and `handle` is `null`, and `restoreWatchedFolders` rebuilds the stand-in from it. That loses nothing: unlike a handle, a path stays valid across a restart with no permission to re-grant, so such a folder resumes silently and never reaches the Reconnect state below. Each file's own record in the existing `files` store gained a `folderId` field (written by `persistFileNode`, read back by `restoreSessionFromCache`) so an already-open file re-links to its folder by that shared, stable id after a reload.

Boot sequence: `restoreSessionFromCache()` (files, filters, bookmarks, settings — unchanged) runs first, so any restored file's `node.folderId` is already set by the time `restoreWatchedFolders()` runs right after. That function re-registers each stored folder (`needsPermission: true` to start, seeding `folder.files` with whatever already-restored nodes point at it) and calls `folder.handle.queryPermission({ mode: "read" })` — **no user gesture required** for a *query*, only for a *request*. If the browser still considers it granted, `tryReconnectFolder` flips `needsPermission` off and rescans immediately: watching resumes with no visible interruption, and `mergeScannedFiles` **reattaches a fresh tail handle** to any already-open file that doesn't have one yet (a restored folder-owned node never does — see "Tailing (live file updates)"'s note on `tryReattachFileTail` being deliberately skipped for `node.folderId` files, since a reconnected folder handle already makes reattachment possible for free for exactly the files it owns; the reattachment here is guarded on `!node.tail` so it never touches a node that's already tailing). If permission was **not** silently re-granted (typically after an actual browser restart, not just a tab reload), the folder renders with a lock icon and a **Reconnect** button instead of the scanning ring — `reconnectFolder()`, the button's click handler, is the one place `requestPermission()` is called, since that method's browser-side prompt requires an actual click to invoke at all.

**Folder-watch minimap for picking which files to load/merge** (FEATURE_BACKLOG.md #64, folder-only — a ZIP variant is not planned, see "ZIP sources" below). Clicking a folder's own title (`.folder-watch-name`, `selectFolderContainer(folder.id)`) sets `state.folderView` and switches the main content area to a per-file time-range timeline for that folder instead of any single node's log/filter view — the same "special content area, not a real node" idea as `state.inlineViewer` (mutually exclusive with it: activating either clears the other), dispatched by an early branch in `renderMainView` mirroring `state.inlineViewer`'s own. Activating any real node (loading a file, clicking a filter) clears `state.folderView` — wired through `createFileNode`/`activateNewNode`/`activateInlineViewer` and the direct tree activation path, so it can never end up stale.

The minimap shows exactly the files `folder.files` currently lists — no separate "visible subset" step: `mergeScannedFiles`/`applyFolderAutoRules` are already the one place that decides what's listed (glob patterns, "Show M newest files", …), so this view and `renderFolderSection` can never disagree. One horizontal bar per file (`renderFolderMinimap`/`renderFolderMinimapSvg`) on a shared time axis, stacking where spans overlap. Each bar's range comes from `probeFileTimeRange` (a cheap head+tail read, added last session — see above) for a file that isn't open yet, or straight from its real entries (`fileEntryTimeRange`) once it's loaded — never a full parse just to draw a bar. A probe in flight is shared (`rec._rangeProbe`) — `renderFolderMinimap` kicks off probes for every unresolved file on each of its renders, and a render while probes were still pending (a folder scan, a tail tick) used to start them all again; under the desktop wrapper a probe reads its few KB by byte range instead of the whole file (`getPartialReadFile`, see "Tailing"). A probed range is cached on the folder's own file record as `rec._range` (`probeFolderFileRange`; `undefined` = not probed yet, `null` = probed but no range found — an unrecognized format, or an empty file, rendered as a thin grayed "range unknown" placeholder that's still individually selectable but excluded from window-overlap math) so reopening the minimap doesn't re-probe every file again; `mergeScannedFiles` drops that cache whenever a file's mtime changes underneath it.

**Two ways to pick files** (mutually exclusive — whichever happens second clears the other): clicking a bar toggles it in `fmSelectedRecKeys`; dragging along the axis (mirrors the log minimap's own drag-select mechanics — `fmXToTs`/`fmTsToX`, a movement threshold) sets `fmSelectedWindow` instead. `resolveFolderMinimapTargets(folder)` is the one place "which files does this act on" is decided from either — files whose range overlaps `fmSelectedWindow` if a window is drawn, else the individually-picked bars — so the toolbar's enable/disable logic and all three actions below can never disagree.

**Hover + drag aids** (person-requested — this minimap never had one before, unlike the real log minimap): hovering the axis shows `#folderMinimapHoverLine` (a full-height crosshair — worth it here, unlike the log minimap's plain tooltip-only hover, because this minimap can have many stacked file rows and the line shows which bars a given moment actually crosses) plus `#folderMinimapTooltip` (`formatTime` at the cursor). Dragging past a movement threshold shows `#folderMinimapDragRect`/`#folderMinimapDragLabel` instead (a translucent band + a `formatTime(from) → formatTime(to) · formatMs(duration)` label), hiding the plain hover aids while it's active. All four are plain sibling `<div>`s of `#folderMinimapSvg`, not SVG children — same reasoning as the log minimap's `#timelineMinimapDragRect`/`DragLabel`: an unrelated full SVG rebuild (`folderScanTick`'s 3s poll can fire while this view is showing) must never wipe an in-progress gesture. `fmViewBoxXToBodyPx` converts the SVG's own viewBox-unit x (what `fmTsToX`/`fmXToTs` work in) into a real CSS pixel position relative to `#folderMinimapBody` (the positioned ancestor these divs are placed against); vertical span/position come from `folderMinimapSvg.offsetTop`/`offsetHeight` (layout-based, so `#folderMinimapBody`'s own vertical scroll — this minimap can be tall — never throws them off).

**Three explicit actions**, presented as icon buttons in a Controls/Settings/Actions-style toolbar row (`data-toolbar-group="actions"`, `.toolbar-icon-btn` — the same visual language `#contextToolbar`/`#tableToolbar` use, see CLAUDE.md's styling note), replacing an earlier single Load button whose effect used to be inferred from *how* files were picked:
- **Load individually** (`folderMinimapLoadEachBtn` → `folderMinimapLoadIndividually`) — `loadFolderFile` (a normal full load) on every target file, no merge; the last one loaded ends up active, same as opening several folder files by hand in sequence.
- **Merge (full)** (`folderMinimapMergeFullBtn` → `folderMinimapMergeFull`) — full-loads every target file **at the same time** (`loadFolderMergeSources`, like a multi-file drop — several large files parse on separate cores; ids collected in target order, so the merge stays deterministic; `loadFolderFile(…, quiet)` skips its own closing render since the caller renders per finished source) and `mergeFiles`'s them, with **no** `timerange` filter attached even if a window was drawn (that button means "everything, unfiltered" — a drawn window only ever decided *which* files count as targets here, same as it does for "load individually").
- **Merge (window)** (`folderMinimapMergeWindowBtn` → `folderMinimapMergeWindow`) — the windowed/partial load described next: each target (all at once, same `loadFolderMergeSources`) gets only its `[from, to]` slice read via `loadFolderFileWindowed`, merged, and a `timerange` filter for the *exact* dragged window is attached to the result (`createFilterNode(mergedId, "timerange", {from, to})` — the same call the log minimap's own drag-select makes, so the merge opens already filtered to what was drawn). Only enabled when a window is actually drawn (person-decided — no implied window from the selected bars' own ranges, even though `resolveFolderMinimapTargets` could compute one).

`updateFolderMinimapToolbar` computes each button's `disabled` state from `resolveFolderMinimapTargets`' count, with "merge (window)" additionally requiring `fmSelectedWindow` to be set.

**Windowed/partial file load** (person-requested feasibility follow-up — for a large file, does reading only the drawn window instead of the whole file actually help?). `loadFolderFileWindowed(folder, rec, from, to)` is what `folderMinimapMergeWindow` calls per target file (the other two actions always do a normal full `loadFolderFile` — nothing to skip past there). Rather than reading the whole file and hiding everything outside the window behind the `timerange` filter, `findWindowStartOffset(file, formatId, targetTs)` binary-searches for (approximately) the byte offset where the window starts — `probeTsAtOffset` reads small, growing chunks at a candidate offset (the same trick `probeFileTimeRange`'s own head/tail read uses) to compare a timestamp there against the target, `O(log(file size))` small reads instead of a full sequential scan. `parseFileWindow(file, node, from, to, onProgress)` then reads/parses forward from that offset — the same per-line header/continuation loop `parseLogTextAsync`'s plain-loop fallback uses, fed chunk-by-chunk — stopping the moment an entry's timestamp passes `to`, never reaching EOF.

Both assume the file is chronologically sorted start to end — the same assumption `mergeFiles`' quick-merge disjoint-check and live tailing already make elsewhere. `findWindowStartOffset` checks this cheaply before ever bisecting, reusing `probeFileTimeRange`'s own (already correct, backward-growing) head+tail read as a global bookend: if the file's first entry's timestamp is already after its last entry's, it's definitely not sorted as assumed (a plain forward-scanning tail probe over a fixed byte range near EOF isn't good enough for this — a single log line longer than the probe chunk would make it find nothing at all and silently skip the check). A lighter in-bisection monotonicity check (each probe compared against the previous lower-bound probe) catches some, but not all, internal violations that don't affect the file's own head/tail — both are best-effort, not a full sortedness proof. Either failing returns `consistent: false`, and `loadFolderFileWindowed` falls back to a normal full `loadFolderFile` rather than risk a wrong or incomplete result.

`loadFolderFileWindowed` also falls back to a full load when the file is already open (its entries already cover any window), when the file is smaller than `WINDOWED_LOAD_MIN_FILE_SIZE` (8MB — the extra round trips only pay off on genuinely large files), or when the file's time range (`rec._range`) isn't known yet. A node loaded via the windowed path is tagged `node.partial = { from, to }` — threaded through `snapshotSubtree`/`restoreSubtree` (so it survives a close+undo) and `persistFileNode`/`restoreSessionFromCache` (so it survives a reload) the same way `node.merged`/`node.formatId` already are; `nodeIconHTML`/`renderNode` show it with its own badge (`ICON_FILE_PARTIAL`, a circled "P") and a tooltip naming the window that was actually read, rather than looking like a normal complete file. A merge of two or more windowed sources (see `folderMinimapMergeWindow`) gets the union of their windows as its own `node.partial`.

**Folder-only.** A ZIP source's entries are deflate-compressed — there's no cheap `file.slice()` head/tail read the way a real folder file gets via `probeFileTimeRange`; getting a ZIP entry's range would mean fully inflating it via `entry.extract()` first. Deliberately not done for ZIP sources, and a ZIP variant is not planned — see "ZIP sources" below for what one would need.

## ZIP sources (open a .zip as a log source)

This session (2026-09-11). A ZIP is opened as a **one-shot, immutable listing** — deliberately the opposite design point from folder watch (above): no scanning, no polling, no auto-open/auto-close rules, nothing persisted across a reload. Only the ZIP's central directory is ever read up front; an entry's actual bytes are read+inflated lazily, only when a person double-clicks that one row.

**Entry points**: the **"Open…"** menu's new **ZIP…** item (`openZipPickerFlow`, clicks a hidden `<input type=file accept=".zip">`, `#zipInput`) or dropping a single `.zip` file — checked before the normal file/folder branches in both the browser `drop` listener and `loadDesktopLocalFiles` (the desktop wrapper's native-drop/native-picker route), so a lone zip never falls into the ordinary multi-file ingestion path. A zip mixed into a larger multi-file drop is **not** detected specially — it falls through and fails to parse as an ordinary log file, same as any other unrecognized single-file-only affordance in this app. Deliberately **not** Tauri-exclusive: the plain `<input>` works the same inside the Tauri webview, and there's no native zip-filtered picker in the `window.philogg` bridge worth adding one for.

**ZIP parsing (`readZipEntries`, next to `loadFileDescriptors`)**: reads only the End Of Central Directory record (scanned backward from the file's tail — signature `0x06054b50`) and the Central Directory File Headers it points to (signature `0x02014b50`) — name, compression method, compressed/uncompressed size, and each entry's Local File Header offset. No file *data* is read at this stage, so opening even a large archive is fast. No CRC check (per design: these files are always complete, integrity checking isn't a real problem here). **ZIP64 is not implemented** — a ZIP whose EOCD reports the ZIP64 sentinel values (`0xFFFF`/`0xFFFFFFFF`) fails to open with a toast naming the reason, rather than silently producing a truncated listing; not needed for the log files this app targets, all well under the 4 GB/65535-entry thresholds ZIP64 exists for.

**Lazy per-entry extraction (`entry.extract()`)**: reads that entry's own Local File Header (signature `0x04034b50`) — needed because its name/extra-field lengths can differ from the central directory's own copy of them, so the real compressed-data offset has to be computed from THIS header, not assumed from the central one — then reads exactly the compressed byte range and either returns it as-is (compression method 0, stored) or pipes it through `DecompressionStream('deflate-raw')` (method 8) — the one Web API this feature relies on, natively available in both the plain-browser build and the Tauri desktop build's webview (WebView2/WebKitGTK/WKWebView are all Chromium/WebKit-based), so **no unzip library was added anywhere**. Nothing else in the archive is ever touched by opening one entry.

**Data model**: `state.zips`, a list of `{ id, name, entries: [{ name, size, compressionMethod, extract() }] }` — parallel to but structurally independent from `state.folders`; a zip source is never persisted (no IndexedDB store) and never restored across a reload, since re-opening one needs the actual file picked again anyway (there's no live handle to a ZIP on disk to reconnect to, the same as a plain `<input type=file>` pick has none).

**UI (`renderZipSection`, `#zipList`, rendered by `renderTree()` right alongside `renderFolderWatchList()`)**: visually a folder-watch box — reuses `.folder-watch`/`-header`/`-name`/`-close`/`-files`/`-file`/`-file-name`/`-note` directly — but **without** the two pieces of folder-watch chrome that only make sense for something being actively watched: no scanning-ping indicator (nothing here is polled) and no settings gear (no auto-open/auto-close rules apply to an immutable archive). The header icon is `ICON_ZIP` (an archive box with a zipper strip), not the plain `ICON_FILE`/`ICON_FOLDER` the container otherwise echoes — same viewBox/stroke conventions as every other tree icon, just visually distinct from a watched folder. Every entry in the archive is listed, including subfolder entries and non-log files — `readZipEntries` reads each entry's full central-directory name (e.g. `subfolder/app.log`); subfolders render as the same collapsible **subfolder tree** as a watched folder (see "Subfolder tree" above, collapsed by default), with each entry shown by its basename. Same as folder watch's own `renderFolderSection`, `renderZipSection` mixes a real tree row (`renderNode`, for an already-opened entry) in among the inert placeholder rows (`renderZipEntryRow`) for the rest, in the entry's own archive position — see "Opening an entry" below for how an opened entry is found.

**Opening an entry (`openZipEntry`)**: same interaction folder watch's own `renderInactiveFileRow` uses for its placeholder rows — a double-click, routed to `openZipEntry(entry, zip)`. What happens next depends on `isLogZipEntry(entry)`, which reuses folder watch's own `isCompatibleFolderFile`/`FOLDER_WATCH_EXTENSIONS` notion of "log file" rather than inventing a second one:
- **A recognized log entry** calls `extract()` and feeds the result into `loadFileDescriptors([{ name, zipId: zip.id, openFile: async () => new File([await entry.extract()], entry.name) }])` — the exact same shared ingestion path every other loading route (picker, drop, folder watch's own "load this file") already funnels through, using the entry's full relative path as the loaded node's name. No `handle` is passed, so `loadOneFileIntoTree` never wires up `node.tail` for it (tailing there is gated `if (handle)`) — the resulting node is a completely ordinary, static, **non-tailable** root file node, indistinguishable from a plain `<input type=file>` pick once loaded, **except** it carries `node.zipId`. `tailTick`/`folderScanTick` need no special-casing to leave it alone: neither iterates `state.nodes` looking for live sources, only `state.folders` and tail handles that were never created here.
  - **Nesting bugfix (this session, person-reported)**: an opened entry used to land as a plain top-level file, detached from its zip's own `renderZipSection` container — folder watch's equivalent tags the node with `node.folderId` for exactly this reason (see "Folder watch" above), but the zip entry point had no such tagging at all. Fixed the same way, but under its **own** field, `node.zipId`, rather than reusing `node.folderId` itself: every consumer of `node.folderId` (`closeFolderFile`, `restoreWatchedFolders`, `persistFileNode`'s cache record, `nodeDisplayName`, …) assumes a real, possibly-reconnectable `state.folders` entry exists for it, and a zip source is deliberately never persisted (see "Data model" above) — reusing `folderId` would either need every one of those call sites defensively guarded, or leave a stale `folderId` surviving a reload pointing at a zip that no longer exists, making the node invisible (`renderTree` skips any `node.folderId` row unconditionally, with no surviving zip section left to render it into either). `loadFileDescriptors` tags the node with `zipId` from its very first (queued-placeholder) render — same "from the first moment" timing `node.folderId` gets via `createFileNode` — so `renderZipSection` can find it (`state.rootIds` filtered by `node.zipId === zip.id && node.name === entry.name`) and render it nested even while still loading. `node.zipId` is **not** written into `persistFileNode`'s cache record, so a session-restored zip-opened file simply becomes an ordinary top-level file on the next reload — correct, since there's no live zip source left to nest it back into. Closing a nested entry (✕/Delete, same path as any other file) falls through to the ordinary delete branch (not `closeFolderFile`, since `node.folderId` is unset) — the entry then just has nothing matching it in `renderZipSection`'s lookup any more, so it renders as an inert placeholder row again, the same end state folder watch's dedicated "return to grayed listing" logic achieves on purpose.
- **Any other entry** (`.txt`, `.png`, …) checks `inlineViewableKind(entry.name)` first; if it names a common text-ish or image type, `openZipEntryExternally` routes to `openInlineViewer` instead of going further. Everything else goes to the pre-existing external-open path: `extract()` is still called lazily, but the bytes go to a viewer, not `loadFileDescriptors`. Under the Tauri desktop build (`window.philogg.openExtractedEntry` present) the bytes are handed to `commands.rs::open_extracted_entry`, which writes them to a fresh OS temp file (kept under a per-call subdirectory, named after the entry's own basename so extension-based app resolution still works) and opens it via `tauri-plugin-opener`'s `open_path` — the same plugin `reveal_path`/`reveal_local_url` already depend on, so **no new Cargo crate was needed**. In the plain browser build (no `window.philogg`), there is no OS-level "open with" available at all, so the fallback is a new tab on a `Blob` URL via `window.open(URL.createObjectURL(blob))`, revoked after 60s. The Blob's MIME type comes from `safeTabBlobMimeType`, **not** `guessZipEntryMimeType` directly (security, 2026-09-13): a `Blob:` URL opened this way inherits PhiLogg's *own* origin, so an active-content type — `.html`/`.htm`/`.xhtml`/`.xht`/`.svg` — would let the archived file's scripts run against PhiLogg's `localStorage` (persisted sessions/filters/themes). `safeTabBlobMimeType` serves exactly those extensions as `text/plain` (the tab shows inert source instead of executing it) and delegates every other type to `guessZipEntryMimeType` unchanged (a small extension → MIME map covering common text/image/audio/video/pdf types, `application/octet-stream` otherwise — so images/PDF/text still render inline and unknown types download). Images never reach here anyway (they route to the inline image viewer via `inlineViewableKind`, and `.svg` is deliberately not among the inline image extensions), so no legitimate rendering is downgraded. The Tauri desktop build doesn't hit this path at all — it hands raw bytes to the OS, never building a Blob tab — so the neutralization is browser-build-only.
  - **If a future session wants to actually *render* archived HTML/SVG (not just show inert `text/plain` source)**, do it with a **sandboxed `<iframe>`**, not by relaxing `safeTabBlobMimeType`. Give it its own in-app viewer surface (mirroring `openInlineViewer`'s text/image sub-views) and feed the bytes via `srcdoc` or a `Blob:` URL into an `<iframe sandbox="">` — **no `allow-scripts`**, and *never* `allow-scripts` together with `allow-same-origin` (that combination lets the frame remove its own sandbox). The frame then renders the markup while its scripts stay dead and it sits in an opaque origin with no access to PhiLogg's `localStorage`. That is the only safe way to add HTML/SVG rendering; the current `text/plain` reroute exists precisely because there is no such sandboxed surface yet. See `FEATURE_BACKLOG.md` #75 for the complementary page-wide CSP layer. The Tauri desktop build gets the real OS-open behavior, not the browser-tab fallback — `tauri-plugin-opener` already covers "open with OS default app" (`open_path`), so the fallback path in `docs/persistence-and-sync.md`'s original constraints ("note the limitation ... if it genuinely doesn't [cover it]") never applies here.

**Inline viewers**: `inlineViewableKind(name)` recognizes `.txt`/`.xml`/`.json` (kind `"text"`) and `.jpg`/`.jpeg`/`.png`/`.tiff`/`.tif` (kind `"image"`) — these now render in the main content area (`#inlineViewerWrap`) instead of going to `openZipEntryExternally`'s OS-open/browser-tab fallback; every other extension keeps that pre-existing behavior unchanged. Deliberately zip-specific, matching `openZipEntryExternally`'s own scope: neither folder watch (`FOLDER_WATCH_EXTENSIONS` only ever lists `.log`) nor plain drag/drop hands a non-log file to any "open externally" mechanism at all — a dropped non-log file just fails to parse as a log via the ordinary `loadFileDescriptors` path — so there is no existing "open any file" system elsewhere in the app to generalize this into, and none was built.
- **Text** (`openInlineViewer`/`renderInlineTextViewer`): the extracted bytes are decoded and stored on `state.inlineViewer` (`{ kind: "text", name, text, ext, zipId, entryName }`); `.json`/`.xml` get lightweight regex-based token highlighting (`highlightJsonText`/`highlightXmlText` — the app had no existing generic syntax highlighter to reuse; its only other "highlighting" is whole-log-line coloring by level/search match, a different concept), reusing the app's own CSS color tokens so a preview reads consistently with the rest of the UI. Plain `.txt` renders escaped, unhighlighted. Tokenizing happens **per line** (the text is split on `\n` first, each line run through the tokenizer separately), not on the whole text followed by splitting the highlighted HTML — a match spanning a raw newline would otherwise leave an unclosed `<span>` dangling into the next line's markup; the accepted cost is a multi-line string/comment losing its highlighting past its first line.
  - **Line-number gutter** (later refinement, same day): each line renders as its own `.itv-line` row — a `.itv-line-num` gutter cell and a `.itv-line-content` text cell, two separate flex children rather than numbers interleaved into the copyable text, so selecting/copying from the content column never picks up the gutter (`.itv-line-num` is also `user-select:none`, belt-and-suspenders). This is a **new**, small, consistently-styled addition, not a reuse of an existing mechanism — the main log view (`renderVisibleRows`) has no literal per-line-number column to copy from; it's a field-column table (time/level/thread/location/method/message), not line-numbered free text. **Hover only** (`.itv-line:hover`, plain CSS, no JS/state) is the only per-line interaction — an earlier same-day revision also added a click-to-highlight `.itv-line-selected` toggle via a delegated click listener, but it was removed in a later bugfix session (below): the click listener fired on every drag-selection's mouseup too, interfering with normal text selection, and the person asked for hover-only anyway.
  - **Copy fix** (bugfix session, person-reported): copying a selection used to go through the browser's own DOM-to-text serialization of the `.itv-line` block structure above, which could introduce extra line breaks not in the source file (real browsers are inconsistent about newline count at a selection's first/last partial line and around genuinely empty lines). A `copy` listener on `#inlineTextViewer` now intercepts the event — only when the live selection is actually inside the viewer, otherwise it steps aside entirely — and writes plain text straight from `state.inlineViewer.text` itself via `event.clipboardData.setData('text/plain', …)` + `event.preventDefault()`, sliced to the exact line/character range the DOM selection covers. The character offset within a line is computed with `Range#toString().length` against that line's `.itv-line-content` (a `Range` from the start of the content span to the selection boundary) rather than walking DOM nodes by hand, so it stays correct regardless of how many nested tokenizer `<span>`s (`.json`/`.xml` highlighting) sit in between. The result is always byte-identical to the source text, never a reconstruction of it.
  - **A background log-row selection no longer wins the global Ctrl+C shortcut over an active viewer selection** (bugfix, person-reported): the app's pre-existing global Ctrl+C handler (`copyLogSelectionToClipboard`, bound on `keydown`) copies the selected log row's raw text whenever `state.focusRegion === "entries" && state.selectedId` — true even while an inline viewer is open and showing something else, since opening a viewer via a tree-row click deliberately leaves `focusRegion`/`selectedId` untouched (see the tree-row click handler's own comment). Selecting text *inside* the viewer, then pressing Ctrl+C, used to still copy the (unrelated) log row, because the keydown handler ran and called `preventDefault()` before the browser ever fired a native `copy` event — pre-empting `#inlineTextViewer`'s own `copy` listener above entirely, not just racing it. The handler already had one precedent for yielding to a real text selection (checking `detailPanel.contains(sel.anchorNode)` for the Entry Detail panel); the fix extends that same check to `inlineTextViewerEl.contains(sel.anchorNode)`, so a non-empty `window.getSelection()` anywhere inside the inline viewer now takes the same precedence the Entry Detail panel already had, letting the native `copy` event (and this listener) run instead.
  - **No native "drag the current selection" gesture** (bugfix, person-reported): browsers make text inside an *active* selection natively draggable by default (the same affordance that lets selected text be dragged into another input) — with no app code opting in. Clicking/dragging at or near an existing selection inside the viewer was being hijacked into that native drag instead of starting (or extending) a plain text selection, which also explained an apparently-unrelated symptom: a hijacked drag never produces a fresh `Range`, so Ctrl+C afterward copied whatever selection existed *before* the drag — typically not starting at column 0 — silently dropping a line's leading whitespace from the copy. `#inlineTextViewer` now has a `dragstart` listener that unconditionally calls `preventDefault()`, opting the whole viewer out of that native gesture; there is still no other mousedown/mousemove/custom-selection JS on the text content area at all, so click-and-drag falls straight through to the browser's own ordinary text selection.
- **Images** (`renderInlineImageViewer`, `#inlineImageViewer`): pan/zoom/reset/rect-select-zoom, modeled directly on Plot View's own interaction (`imgZoom`/`imgLastRender` mirror `plotZoom`/`plotLastRender`'s shape and role, and the same `PLOT_ZOOM_WHEEL_FACTOR`/`PLOT_ZOOM_BUTTON_FACTOR`/`PLOT_DRAG_THRESHOLD_PX` constants and `.plot-drag-rect` overlay class are reused verbatim) — wheel-zoom anchored at the cursor, left-drag-to-select-a-region-then-zoom, middle-drag pan, a Reset button, all clamped to never zoom out past the image's own "home" (fit) view. Not spliced into `#plotSvg`/`renderPlotChart` itself, since that code's domain math is built entirely around `extractRowsData`/`extractColumns` (a log extraction's numeric columns) — threading an "image mode" through every one of its data-plot branches for no shared benefit wasn't worth it, so the image viewer gets its own small SVG (`#imgViewerSvg`) and its own copy of the interaction handlers, deliberately kept name-for-name parallel to Plot View's (`imgZoomAt`/`imgSvgPointFromEvent`/`imgClampAxis` vs. `zoomPlotAt`/`plotSvgPointFromEvent`/`clampZoomAxis`) so the two stay easy to compare line-for-line if either changes.

**Open/close/select lifecycle — unified with a log file's own tree row** (later refinement, same day): a non-log inline-viewable entry's row (`renderZipEntryRow`) now carries the exact same open/close/select mechanics a log file's real `.tree-row` already has, instead of the separate `#inlineViewerCloseBtn` the viewer used to have (removed):
- **`zip.inlineViewers`** (a `Map<entryName, viewerObject>`, set on the zip at `openZipSource`) is this row's stand-in for "does `state.nodes` have an open node for this entry" — there's no real tree node to check against, since a non-log entry never enters `state.nodes`. The first open is still a double-click (`openZipEntry` → `openZipEntryExternally` → `openInlineViewer`, which caches the resulting viewer object into `zip.inlineViewers` keyed by entry name, tagged with `zipId`/`entryName`); a **plain click** on an already-opened row re-selects it (`activateInlineViewer(cachedViewer)`) without re-extracting/re-decoding anything — mirroring a plain click on an already-open log file's own tree row.
- **Row styling**: `.zip-entry-opened` (present once `zip.inlineViewers` has this entry) removes the placeholder's usual dimming — both the `opacity` AND the dim `color:var(--text-tertiary)` `.folder-watch-file`/`.zip-source-file`'s own base rule sets (bugfix, person-reported: an earlier version only reset `opacity`, so an opened-but-not-active row was technically un-dimmed but still visibly gray) — matching an opened log file's non-dimmed tree row (`color:var(--text-secondary)`). `.zip-entry-active` (present only while this entry is the one actually shown, i.e. `state.inlineViewer.zipId`/`entryName` match) additionally gets the same accent highlight `.tree-row.active` uses. An entry can be "opened" (still cached, not dimmed) without being "active" (a different row is now shown) — exactly like an open-but-not-selected log file's tree row.
- **Closing**: the row itself grows a `.tree-del` ✕ (same class/icon a log file's row uses) once opened — clicking it deletes the entry from `zip.inlineViewers` and, if it was the active one, clears `state.inlineViewer`; the row falls back to its grayed, unopened look. There is no other way to close a non-log entry's viewer any more.
- **"Only one active at a time"**: selecting a real tree row (`renderNode`'s click handler) or opening a brand-new zip log entry (`openZipEntry`) both clear `state.inlineViewer`, so switching to a log file always hides whatever non-log viewer was showing — matching "only one log's content shows at a time," now extended to non-log entries. `removeZipSource` also clears it if the removed zip owned the currently-active viewer.
  - **The other direction (bugfix, person-reported)**: every place that makes a non-log entry the active content — first open (`openInlineViewer`), re-selecting an already-opened row (the plain click above), and Alt+Up/Down landing on one (`moveTreeSelection`, below) — now goes through a single shared `activateInlineViewer(viewer)` helper (`state.activeId = null; state.inlineViewer = viewer;`) instead of assigning `state.inlineViewer` directly. Previously only the log-to-log direction cleared the other side's state; opening a non-log entry left `state.activeId` pointing at whatever log file was active before, which left that file's tree row still rendered with the `active` class (`renderNode`'s `id === state.activeId` check) and, since `renderMainView`'s `state.inlineViewer` branch never touched the minimap at all, left the minimap showing too — including staying visible after that log file was closed outright while the non-log viewer stayed open, since the branch returns before the `!hasFiles` code further down (which is the only other place that hides it) ever runs. Fixed at the one shared entry point rather than patching the tree-row class and the minimap separately.
- **Alt+Up/Down navigation** (bugfix, person-reported): `flattenTreeIds` (walked by `moveTreeSelection`, the function behind Alt+Arrow) used to only ever iterate `state.nodes`/`state.rootIds` — an opened non-log entry has no real node (it lives only in `zip.inlineViewers`), so it could never be reached by the cycle at all, unlike an opened log file's own real tree node. **Copy fidelity — cross-line Range boundaries (bugfix, person-reported)**: `itvContentOffset(container, offset, lineEl)` resolves a `Range` boundary to a character offset within its line's `.itv-line-content` text, used by the `copy` handler to slice `state.inlineViewer.text` directly (see the handler's own comment for why — cross-block-element copy serialization is unreliable across browsers). A real drag selection commonly produces exactly that boundary shape at the END of a multi-line selection — dragging past the end of a line's rendered text resolves to `(lineEl, lineEl.childNodes.length)`, i.e. the `.itv-line` DIV itself, one level above `.itv-line-content` — so a multi-line copy ending mid-to-late on its last line would silently truncate that line to empty, collapsing what looked like a full multi-line selection down to just its earlier lines' text (or, worst case with a 2-line selection, down to nothing from the last line at all). ## gzip-compressed logs (`.gz`)

A rotated log such as `app.log.1.gz` opens transparently on every route — drag-drop, the file picker, the desktop wrapper's native pick/drop, a desktop file-association/"Open in PhiLogg" launch, folder watch, a ZIP entry, `?url=`, and the format dialog's example-line loader. No library: the inflate is the browser's native `DecompressionStream("gzip")`, the same Web API the ZIP path's `deflate-raw` inflate uses, and it behaves identically in the plain-browser and desktop builds (helpers in `philogg.html` under "gzip-compressed logs", next to `readFileWithProgress`).

**Detection is by content, not by name.** `isGzipBlob`/`isGzipBytes` check the two gzip magic bytes (`1f 8b`). A file named `.gz` whose bytes aren't gzip (e.g. a server already undid the `Content-Encoding`) reads as plain text; a gzip stream without the extension is still inflated.

**Where it plugs in.**
- `loadOneFileIntoTree` — the choke point behind drop, picker, `loadDesktopLocalFiles`, `loadFolderFile` and `openZipEntry`. It calls `gunzipFileIfCompressed` right before the text read, on the JS route only. That covers the meta-format split and the fallback after a rejected native parse. The inflate is the read phase of the row's progress bar (compressed bytes consumed, `READ_WEIGHT`). The in-memory result then reads as text near-instantly.
- `loadUrlIntoTree` (`?url=`, `window.philoggLoadUrl`, the desktop launch route) — `gunzipBytesIfCompressed` on the fetched bytes, after its own native attempt.
- `reopenLocalPathForRestore` (the desktop session cache's "path" record, re-read from disk) — inflates on its JS fallback, and reports `gzip` so the restore attaches no tail.
- **Desktop native parsing never sees gzip.** `parse_log_file` (`commands.rs`) rejects a file whose bytes start with the magic (`philogg_logparse::is_gzip`) before streaming anything. Every native caller above already falls back to the JS read + parse on a rejection, and that fallback inflates. So there is no Rust-side inflate; see `docs/desktop.md` → "Native parsing".
- `fwzLoadFile` and the format-dialog branch of `loadDesktopLocalFiles` — inflate first, then take the usual 512 KB head as example lines.

**Memory.** `gunzipBlob` streams the compressed file into the decompressor chunk by chunk (`Blob.stream()`), so the whole compressed file is never buffered. It collects the inflated output once and wraps it in a `File`. That is no more resident at once than the ZIP path's own compressed + inflated pair.

**Names.** The node keeps its real name (`app.log.1.gz`), so folder-watch rows, the ZIP listing and the tree all show what is on disk. Wherever a name is interpreted, `.gz` is looked through:
- `isCompatibleFolderFile` (folder watch's and `isLogZipEntry`'s "is this a log?") accepts a `.gz` whose name without `.gz` is a log name, with a logrotate counter allowed: `app.log.gz` and `app.log.1.gz` qualify, `data.gz`/`site.tar.gz` don't. An uncompressed `app.log.1` is unchanged, still not listed.
- `fileNameGlobTest` backs format rules (`resolveFormatIdForFilename`) and folder-watch patterns (`scanFolderHandle`, `matchFolderPattern`). It tries the real name first, so an explicit `*.gz` rule wins. Then it tries the name without `.gz`, then that name without a trailing `.N` counter. So `*.log` / `app*.log` still pick up `app.log.1.gz`. A name without `.gz` is only tested as-is.

**Always a static snapshot.** Tailing the raw compressed bytes would be meaningless, so no load path attaches `node.tail` to a gzip file. Two paths could still reattach one later, knowing only the handle: session restore (`tryReattachFileTail`, from a persisted desktop `sourceUrl`) and a folder rescan (`mergeScannedFiles`). `tailTick` covers both. It checks each tail once (`tail.gzipChecked`): a 2-byte read through `getPartialReadFile`, which is a single Range request on a desktop `philogg://local` view. A handle whose file starts with the gzip magic has its tail dropped before any bytes are appended. No new node field is needed for this.

**Partial (Range) reads.** Every partial reader stays away from gzip bytes:
- The tail poll is covered by the one-time check above.
- `probeFolderFileRange` (the folder minimap's head/tail probe) checks the magic first, with the same 2-byte partial read, and returns the "no range found" sentinel. Its byte windows would be compressed data, and inflating the whole file would defeat the cheap probe.
- `loadFolderFileWindowed` needs a probed range, so for a gzip file it always falls back to a full load, which inflates.

**Session cache.** Browser files are stored as their File blob (`_cacheBlob`). For a gzip file that blob is the *inflated* File, so a restore re-parses plain text under the original name. A desktop file is stored as its path and re-read from disk (`reopenLocalPathForRestore`, above).

**Desktop wrapper.** No Rust-side decompression. The wrapper serves raw bytes over `philogg://local`, and the native parser refuses gzip; the page inflates. The wrapper changes are listed in `docs/desktop.md` → "Native parsing" and "Explorer context-menu integration".

**Not handled.** A multi-member gzip, or a `.tar.gz`: a dropped `.tar.gz` inflates to a tar stream and simply fails to parse as a log. Neither is recognized as a log by name in folder watch or ZIP listings.

## Filter save / load (JSON files)

Right-click a filter → **"Save filter…"** writes a `.json` file (`saveJsonExportFile`: `showSaveFilePicker`, download-link fallback where that API is missing). Loading one back goes through the central import (Open → "Import…" or a drop — see "Central import" below): `importFilterBranchJson` attaches it under the **active node** (walking up past a locked auto-managed node like Bookmarks) and toasts where it went ("Filter imported under …"), since a filter branch has no editor to open. `serializeFilterBranch()` / `importFilterJson()` do the actual work; format is `{ format: "philogg-filters", version, activeRef, roots: [...] }`, `FILTER_FILE_VERSION = 2`.

**What gets saved is now a general choice, for ANY filter node** (`serializeFilterBranch(nodeId, includeAncestors)`, asked via `openExportScopePrompt` — see `docs/filters.md`'s "Export/library" section for the full picture): **"just this filter"** (`includeAncestors=false`) exports exactly the one clicked node, no ancestors, no subtree; **"include ancestor chain"** (`includeAncestors=true`) exports its ancestor chain from just below the root file, plus its own full subtree — today's original default shape. The scope question is general rather than and/or/link-specific because `bakedA`/`bakedB` are flat, self-contained data (see `docs/filters.md`'s "Self-contained AND/OR/LINK") — a combiner's two sides travel inside the node itself, so there is never anything external to optionally pull in alongside it.

**and/or/link nodes and their `bakedA`/`bakedB`**: both scopes above carry `bakedA`/`bakedB` along as a plain field copy — no ref/remapping machinery, since there's no node-id inside them. For "just this filter" this is what makes an and/or/link node's export already fully self-contained with nothing else to bring along.

**Import always attaches at the current target, never FILE**: every exported root is tagged `attach: "target"`; `materializeSerializedRoots`'s `resolveParentId` resolves it to the import's target — the active node for an imported file, wherever "Apply from library…" was invoked for a preset (`loadFilterTargetId`) — true for both scopes, and for both an ordinary filter and an and/or/link node.

**Loading onto a different tree re-evaluates, it doesn't replay a stored result**: nothing beyond the filter *definitions* (type/value/inverted, `linkDirection`/`linkN`/`linkOrderEnforced`/`linkExclusive`, `contextBefore`/`After`, `bakedA`/`bakedB`) is written to the file — every load creates fresh nodes with new uids, and `getEntries()` is always computed lazily against whichever file the reconstructed chain now structurally sits under. So an `and`/`or`/`link` filter loaded onto a different file (or a different point in the same file) is re-applied against that destination's own data, not the source file's original computed entries — its own `bakedA`/`bakedB` predicates are unaffected by any of this, since they never referenced the source file to begin with.

**Known gap**: loading never checks whether the destination already has an equivalent branch — every load creates a fresh, independent copy, so loading the same file twice (or onto a tree that already has a matching chain) produces visible duplicates. No dedup/merge-with-existing-branch logic exists; flagged as a possible future addition, not built.

**Person-reported bugfix, this session**: `#exportScopeDialog` (the "Just this filter"/"Include ancestor chain" prompt above) had no CSS at all — no `.hidden{display:none}`, no fixed-overlay positioning — so it rendered as a permanently-visible inline block wherever it fell in the document instead of a proper modal. Every save/export action that goes through `openExportScopePrompt()` — Save filter to file AND "Save to library…" below — awaits that prompt's promise, which only resolves on a click on one of its two buttons; with the dialog not actually reachable as a modal, that click never happened in practice, so the promise hung forever and the save silently never completed. Fixed by giving `#exportScopeDialog` the same `position:fixed; inset:0; z-index:75` + `.hidden{display:none}` treatment every other dialog already has — no logic change was needed here or in "Reusable filter library" below.

## Central import (Open → "Import…" / drop)

Every app-internal export is a JSON file with a `format` marker, and there is **one** way in for all of them: Open (`#btnOpen`) → **"Import…"** (`importFromFilePicker` — `showOpenFilePicker`, else the hidden multi-file `#importFileInput`; `importPickedFiles` toasts "… is not a PhiLogg export" for anything else), or dropping/opening the file anywhere — `loadFileDescriptors` reads every `.json` descriptor ≤ 1 MB (`mightBePhiloggExport`, `PHILOGG_EXPORT_MAX_BYTES`) first and hands it to the import instead of loading it, so browser drop, desktop drop and the file picker all share it; any other `.json` keeps loading/opening in the inline viewer as before. `importPhiloggJsonText(text)` dispatches on `format`:

| `format` | Goes to |
|---|---|
| `philogg-session-export` | `importSessionJson` (the session matching flow, `#sessionMatchDialog` for missing logs) |
| `philogg-filters` | `importFilterBranchJson` — attached under the active node, toast says where |
| `philogg-filter-library` | "Save to filter library" dialog, prefilled (name + icon) |
| `philogg-log-format` | the format wizard, prefilled + a checkbox per filename pattern |
| `philogg-theme` | the theme editor, prefilled |
| `philogg-syntax-scheme` | the theme editor in syntax mode, prefilled |

Each element that has an editor opens **the same editor that creates it**, and saving there creates a new entry. Several files at once (a multi-file pick or drop) open one editor after another: `queueImportEditor` holds them while one of the three editors is open (`importEditorOpen`), and each editor's close calls `openNextImportEditor()`. The export side is a per-entry **Export** button on every list (log formats, custom themes, custom syntax schemes, filter library presets), plus "Save filter…" on a filter node and "Save session…"; all write through `saveJsonExportFile` (`showSaveFilePicker` or `downloadJsonFallback`). Keyboard shortcuts have no export/import. The earlier scattered entry points (Settings "Import…" for formats, "+ Import theme…"/"+ Import scheme…", "Download template…", the tree context menu's "Load filter…", "Import session…") are gone. Regression-tested: **Group 294** (dispatch, picker, filter branch under the active node, queueing across editors).

## Reusable filter library (`FEATURE_BACKLOG.md`)

Named presets, applied to **any** file in one click — the global counterpart to the per-file filter history below (see "File filter history"), and explicitly scoped simpler per the backlog item's own wording: no content-fingerprint matching, the person just picks where a preset applies.

**Saving lives in the Files & Filters sidebar toolbar** (`#sidebarToolbar`, `describeSidebarToolbarActions`/`handleSidebarToolbarActionClick` — see `docs/ui-and-views.md` → "`#sidebarToolbar`"), not the tree context menu, and — as of this session — not `#viewBar` either. **"Add to library…"** (`addToLibrary`, floppy-disk `ICON_DISK`) opens `#filterLibrarySaveDialog` (a name-prompt modal pre-filled with the node's own name) on the *specific selected filter node* — it only appears for an unlocked filter selection, since a file/folder has nothing to serialize into a preset. **"Apply from library…"** (`applyFromLibrary`, `ICON_BOOK`) opens the manage dialog `#filterLibraryDialog` on whichever node the current selection resolves to (see the sidebar-toolbar doc for the exact per-selection-shape target/fallback rules) and also stays on every node's context menu (file or filter) — it targets the right-clicked node there, which the toolbar can't address arbitrarily. (An earlier revision of this feature put "Add to Library"/"Library" as two dedicated buttons — `#btnAddToLibrary`/`#btnOpenLibrary` — in a right-aligned `#libraryManageBar` group inside `#viewBar`'s Filter-Toolbar, always acting on `state.activeId`; that group was removed outright in favor of the sidebar toolbar's per-selection targeting.) `#libraryPresetBar` (the pinned-preset pills, still inside `#viewBar`) is unaffected — only the two management buttons moved.

**Manage dialog + pinning**: each `#filterLibraryDialog` row carries a leading **icon button** (opens an inline icon grid), a **"Toolbar" pin toggle** (`showInToolbar`, the reusable `.settings-switch` pill), an **Apply** button and a delete button — all sharing a 28px height so the row lines up cleanly. Setting the pin renders the preset as a circle-pill `.row-action-btn` in the `#libraryPresetBar` "Library presets" group (appended by `renderLibraryToolbarPresets()`; the group and its leading separator collapse out when nothing is pinned); clicking that pill applies the preset onto the **active node** (`state.activeId`, same mechanism as the dialog's Apply). The pill shows the preset's assigned icon, falling back to `ICON_FILTER` when unset. Its floating label is driven by plain CSS `:hover` (the label floats and shifts no siblings, so the JS `setupHitExpandGroups` mechanism the other filter buttons use isn't needed, and a CSS rule survives the container's dynamic re-render). `renderLibraryToolbarPresets()` builds its nodes from `libraryPresetBar.ownerDocument`, not the global `document`, so a fire-and-forget re-render from a mutator can't throw if it resolves after teardown.

**Icon grid — SVG set + emoji set** (person-requested): the inline icon grid offers two sections. `LIBRARY_ICON_SET` is the original curated list of `{name, svg}` pairs (inline `ICON_*` SVGs, `stroke="currentColor"`), resolved by `libraryIconSvg(name)`. `LIBRARY_EMOJI_SET` is a flat array of ~40 native Unicode emoji characters — no image assets, rendered via the OS's own color emoji font, identically in-browser and under the Tauri desktop wrapper (Tauri just wraps the OS webview, so there is no way to force a monochrome rendering there either; only a CSS `filter:grayscale()` desaturation is available if that's ever wanted, not built here). A record's `icon` field distinguishes the two: `"emoji:<char>"` for an emoji pick (`isEmojiIcon`/`libraryIconEmojiChar` read it back), a bare or `"svg:"`-prefixed name for the SVG set (`libraryIconSvg` strips an optional `"svg:"` prefix before its lookup, so **pre-feature bare-name records keep resolving unchanged** — no migration). Below the grid, a free-text input accepts any single emoji not in the curated set (validated as exactly one Unicode codepoint via spread-length; anything else is a no-op).

**Storage**: a fourth IndexedDB object store, `filterLibrary`, in the same `philogg-session-cache` DB (`CACHE_DB_VERSION` bumped 3→4). Keyed by a random id (`newFilterLibraryKey()`), unlike `fileHistory`'s content-fingerprint key — there's no file to fingerprint here, the whole point is that a preset is file-agnostic. `saveFilterToLibrary` shows the same general "just this filter" vs. "include ancestor chain" prompt Save/Load JSON does before serializing. A record is `{ key, name, savedAt, roots, activeRef, showInToolbar, icon }`, where `roots`/`activeRef` are **exactly `serializeFilterBranch()`'s own output shape**. `showInToolbar` (bool) and `icon` (an SVG-set name, `"emoji:<char>"`, or `null`) are **library-record fields, not filter-node fields** — so they need no threading through the `cloneSubtree`/`serializeFilterBranch` carriers CLAUDE.md documents (that rule is about `node.*`). `updateFilterLibraryEntry(key, patch)` merges one field change and re-renders the pill row. Adding these fields needs no schema/version bump: IndexedDB records are schemaless, so pre-feature records simply read back with the fields absent (falsy = unpinned, no icon).

**`filterLibraryCache`** (`FEATURE_BACKLOG.md` #71) is a plain in-memory array mirroring the store, for the one UI spot that needs the current list WITHOUT an async gap before it can render: the folder watch settings dialog's "Start filter" `<select>` (`renderFwPatternList`, see the "Folder watch" section above) — that dialog has always opened and rendered its pattern cards in one synchronous tick, and reading `listFilterLibrary()` (IndexedDB, always async) directly there would reopen that gap and race the dialog's own synchronous assertions/interactions. `refreshFilterLibraryCache()` re-reads the store into it, called once at boot (fire-and-forget, alongside `renderLibraryToolbarPresets()`) and awaited inside all three mutators above, so it's never more than one save/update/delete stale.

**Applying reuses `importFilterJson()` unchanged**: `applyFilterFromLibrary(targetId, record)` sets `loadFilterTargetId = targetId` (the same module-level handoff `importFilterBranchJson` uses) and calls `importFilterJson(JSON.stringify({ format: FILTER_FILE_FORMAT, version: FILTER_FILE_VERSION, activeRef: record.activeRef, roots: record.roots }))` — wrapping the stored branch back into the exact envelope a `.json` filter file already has. This means applying a library preset gets every guarantee "Filter save / load" already documents **for free**: fresh uids every time (the same preset can be applied repeatedly without conflict), `bakedA`/`bakedB` copied through as plain data with no ref-resolution step, always attaching at the current target (never FILE), and — the important one for a preset meant to travel between files — **re-evaluated against whichever file it lands on now, never a replayed stored result**. No separate apply/materialize code path was written at all.

## Session cache (survives a browser reload)

The working session — loaded files, the complete filter tree per file, bookmarks, and a small set of view settings (level quick-filter, column sort, active node) — is persisted automatically and restored on the next page load. No user action required; a "Session restored" toast confirms it happened. Theme and the Context/Filtered/Stacked layout preference already lived in `localStorage` before this feature and stay there (display preferences, not session data).

**Storage**: IndexedDB (`localStorage`'s ~5 MB quota is far too small for log files), DB `philogg-session-cache` (`CACHE_DB_VERSION`, bumped as stores were added). `files` holds one record per root file — keyed by `node.cacheKey`, a random id assigned at file creation, because runtime node ids are fresh uids every load and can't key anything persistent — and, since the "Folder watch" feature, a `folderId` field for re-linking to a watched folder on restore. A record's **content** comes in one of three forms, cheapest first (`fileCacheSource`):

- **`path`** (no content at all): a desktop file whose OS path is known (`node.localPath`, not partial, not merged) while the wrapper can re-register a path (`window.philogg.openLocalPath`). Restore re-reads and re-parses it from disk (`reopenLocalPathForRestore`: native parser where possible, else fetched and parsed in JS, under the stored `formatId`), with this run's own `philogg://local/…` URL (those ids are per process) and tailing resumed from the bytes just read. **Person-decided trade-off (2026-09-24):** a file deleted or moved since is simply not restored — its placeholder is dropped and the rest of the session comes back — in exchange for never copying a desktop file's text into IndexedDB at all. A file that grew since comes back with its new content (bookmark/note ordinals still point at the same entries as long as the file only grew).
- **`blob`**: the original `File` a node was loaded from (drop, the file dialog, a folder-watch file in the browser), kept as `node._cacheBlob` by `loadOneFileIntoTree`. IndexedDB copies a Blob's bytes off the JS thread, so the write costs the page next to nothing; restore reads it back with `blob.text()` and parses it as before (and keeps it as the restored node's `_cacheBlob`). Only valid while the node's entries are exactly what that File parses to: `onTailChange` drops it on any tail growth or rotation. A ZIP entry never gets one — its File is only an in-memory copy of the extracted bytes. `snapshotSubtree`/`restoreSubtree` carry it across a file delete + undo (same entries).
- **`blob` snapshot of a tailed file** (2026-09-25): a browser-tailed file (real `FileSystemFileHandle`, not merged/partial) whose `_cacheBlob` a tail change dropped gets a Blob again for its debounced tail writes — `tailSnapshotBlob` takes a fresh `handle.getFile()` and slices it at the tail offset minus the still-unterminated `tail.pending` line, which is exactly the bytes the entries were parsed from. Before, every `CACHE_FILE_DEBOUNCE_MS` window of a growing 100 MB file rebuilt and cloned its text (~435 ms blocked each time in Chromium; now ~35 ms). If the snapshot can't be taken (rotated since, unreadable) or its write fails (the file changed again before IndexedDB copied it — a `File` snapshot goes stale on modification), that write falls back to `text`. Never on `pagehide` (an extra await there might not finish), where `text` is written as before. Restore uses the Blob's size as the resumed tail offset (`restoredTailOffset` — exact, CRLF line ends included; rebuilt text, the fallback, joins with `\n` and undercounts a CRLF file).
- **`text`**: everything else — merges, meta-format streams, ZIP entries, tailed files without a usable snapshot — **rebuilt from the parsed entries** (`rebuildFileText`: `entries.map(e => e.raw).join("\n")` — `raw` accumulates continuation lines, so multi-line stack traces round-trip; blank lines and pre-header junk the original parse already dropped are the only loss, and re-parsing the rebuilt text is a fixed point). Building and structured-cloning ~100 MB of text blocks the main thread for 0.5–1.5 s, so this write is deferred until the page is idle (`persistFileNodeWhenIdle`, `requestIdleCallback`, `setTimeout` where that is missing) and never runs on a load's path to its first render; one pending write per file, reading the node's state when it runs. `persistFileNode` still returns a promise that settles once the record is written, so `await persistFileNode(node)` keeps meaning "written".

Exactly one of `text`/`blob` is set on a record, or neither for a `path` record; no migration for records written before this (semver 0.x). `meta` holds a single `"session"` record: file order, serialized filter trees, bookmarks, settings. `fileHistory` is the separate per-file filter-memory store (see "File filter history" below). `folders` stores watched folders (see "Folder watch + lazy loading" above) — either the directory handle itself, since a `FileSystemHandle`, unlike the plain-data records the other three stores hold, is specced to survive IndexedDB's structured clone with its methods intact (the whole mechanism that lets a browser-picked folder resume after a reload at all), or, for a natively listed folder, its path, from which the stand-in is rebuilt.

**Filter serialization** reuses the filter-save/load JSON's field set and `ref` indirection (`serializeFilterTreeForCache` / `materializeCachedFilters`, deliberately parallel to `serializeFilterBranch` / `importFilterJson`) — always the "whole tree" shape, since the cache writes each file's *entire* filter tree, not a single-node-vs-chain choice. `bakedA`/`bakedB` (for and/or/link nodes) copy straight across as plain data, same as any other field — no ref-resolution step needed for them at all, since they hold no node id.

**Bookmarks** are persisted as *(file cacheKey, entry ordinal, note, bookmarkedAt)* — entry ids don't survive a reload, but entry order within a rebuilt file is identical, so the ordinal is a stable address. An entry shared between a merged file and a source file is recorded against the first root that contains it (save and restore use the same first-wins scan order). Dangling bookmark ids (entry lost to tail rotation / file delete) just don't get written. This supersedes the old "bookmarks are session-only" limitation; they're still deliberately **not** part of the filter save/load JSON (a bookmark anchors a spot in the data, not a filter definition).

**Write strategy**: `meta` is small and rewritten via a single debounced hook at the end of `render()` (`schedulePersistMeta`, 400 ms) — every state mutation already ends in a `render()`, so no per-mutation persistence calls exist anywhere. File records are written once on load (`loadOneFileIntoTree`, just before its caller's render — cheap for a `blob`/`path` record, deferred to idle time for a `text` one, see above) / merge (`mergeFiles`), and debounced per-file on tail changes (`schedulePersistFileNode`, 4 s — well above `TAIL_POLL_MS`, since rebuilding a large file's text every poll tick would be wasteful). A `pagehide` listener flushes pending debounces and pending idle writes (an IndexedDB write started there normally completes even though its promise never resolves). Deleting a file deletes its `files` record immediately (`cacheDeleteFile`); the meta record follows via the normal render-hook rewrite.

**View settings in `meta.settings`**: the `settings` object `buildCacheMeta()` writes and `restoreSessionFromCache()` reads back carries `levelFilter`, `sortColumn`/`sortDir`, `pinBookmarksInFilteredView`, `multilineMessages`, **`wrapMessages`** and **`wrapTextView`** (the two word-wrap toggles — FEATURE_BACKLOG.md #68, see `docs/ui-and-views.md` → "Word-wrap toggles"), `showNotes`, `columnVisible`/`columnWidths`, and the `active` node. All are global view preferences, additive fields with no `CACHE_FORMAT_VERSION` bump, restored by their respective `update*Button()` reflectors on boot (`updateWrapMsgButton()`/`updateWrapTextViewButton()` for the two wrap flags). These live in the browser-local cache only — the portable `buildSessionExport` JSON carries the narrower `levelFilter`/`sortColumn`/`pinBookmarksInFilteredView` set, not the display toggles.

**Restore** (`restoreSessionFromCache`) runs once at boot, after the initial empty-state render. It's guarded by `sessionRestoreInProgress` so its own intermediate renders don't persist half-restored state, and any error abandons the restore (whatever loaded stays usable) rather than blocking the app on a corrupt cache. Every failure path in the storage layer (`openCacheDb`/`cacheStoreOp`) resolves `null` instead of throwing — no IndexedDB (private mode, old jsdom) just means the feature silently turns off and the app behaves exactly as before it existed.

**Every restored file shows up as a grayed placeholder immediately, not one at a time as each PRIOR file finishes its own full parse** (person-reported, this session: *"wenn Dateien beim neu laden der Anwendung wiederhergestellt werden, blende sie schon ausgegraut ein. aktuell erscheinen sie erst nachdem die vorherige Datei geladen wurde."*). Mirrors `loadFileDescriptors`' own multi-file-open shape (see "Multi-file load" below): a first pass fetches every restored file's metadata and inserts a `createQueuedFileNode` placeholder for each one, in order, with a single `render()` — so a session with several large files shows all of their rows immediately instead of a growing gap where the next one will eventually appear. A second pass then turns each placeholder into a real, actively-loading row in turn, via `activateQueuedFileNode` — reached through a new `existingNode` 5th parameter on `addFile` (mirroring the one `loadOneFileIntoTree` already had), rather than `addFile` always calling `createFileNode` fresh.

`createFileNode` reads `sessionRestoreInProgress` to skip its own `state.activeId = node.id` side effect while restoring (see "File-selection clarity: no more activeId thrash on restore" in the changelog) — without that guard the tree's active-row highlight visibly bounced through every restored file in turn before `restoreSessionFromCache`'s own final `s.active` handling corrected it. `activateQueuedFileNode` needed the exact same guard added once restore started routing through it too — it unconditionally set `state.activeId` (the multi-file-open path never needed a guard there, since that path never runs during a restore), which would have reintroduced the identical thrashing bug through this new call path otherwise.

**Text and image viewers** (2026-09-25, person-requested: restore them *"genau wie Logdateien … auf dem gleichen Pfad"*). An opened loose (direct open/drop) or folder-watch viewer is persisted by `persistViewer` when it opens: a `files` record under a `"viewer-…"` key (`VIEWER_CACHE_PREFIX`, `viewer: true`) holding the file's **path** when the desktop wrapper can reopen it (`localPath` — from the load descriptor, or the folder file handle's), else the File/bytes as a **Blob**. `meta.viewers` (`persistedViewerList`) lists the open ones — owner kind/id, map key, name, kind, Pretty Print — and `meta.activeViewer` the one shown. `restoreViewersFromCache` runs after `restoreSessionFromCache` and `restoreWatchedFolders` (so a folder viewer's folder exists), from the meta **read once at boot before either** (`bootMeta` — a render in between rewrites the meta before any viewer is back): it re-reads each (`readViewerRecordBytes` — the path through `openLocalPath` + fetch, or the Blob), skips one whose file is gone, rebuilds it under its old map key (`buildInlineViewer` + `registerInlineViewer`, the two halves of `openInlineViewer`), re-shows the active one, and deletes every viewer record the meta no longer lists (closed viewers, removed folders). Closing a viewer deletes its record right away. A "Filter lines" text version is an ordinary file record that also carries `viewerSource`/`textSyntax`, so it nests under its restored viewer again. ZIP viewers aren't persisted — a ZIP isn't restored at all (see "ZIP sources"). Group 275.

**Escape hatch**: `localStorage["philogg-cache-enabled"] = "0"` disables the whole feature. Deliberately no UI for it — clearing happens naturally by deleting files, and a toolbar toggle for a should-just-work feature felt like clutter; revisit if a real need shows up.

**Test coverage** of the three content forms: Group 267 (a File load cached as its blob with no rebuilt text, restored identically; the idle-deferred text write; a tail append dropping the blob; the desktop `path` record, re-read from disk with a fresh URL and resumed tailing, and a deleted file dropped). The jsdom suite's `structuredClone` shim turns jsdom Blobs into Node Blobs for fake-indexeddb, which a real browser's IndexedDB needs no help with.

**Test coverage**: `tests/philogg.regression.test.js` Group 127 — two sizable files persisted in one window, restored in the next; polls for both root nodes existing (the structural "both placeholders are in the tree together" moment) well before either file's parse can plausibly have finished, confirms the second file is still either genuinely queued (`.tree-row-queued`) or at least demonstrably not yet fully loaded while the first is already actively parsing, then polls further until both reach their full, correct entry counts with no leftover `queued`/`loadFraction` state.

## File filter history (per-file memory across sessions)

Person-requested follow-up to the session cache, from a design discussion the same session (2026-08-14) before being built. Solves a different problem than the session cache: the session cache restores a whole *session* automatically on reload; this remembers filters *per file*, indefinitely, independent of any particular session, and offers them back — never auto-applies them — the next time a file with matching content is opened, even in a brand new tab/session that never touched the old one.

**Storage**: a third IndexedDB object store, `fileHistory`, in the same `philogg-session-cache` DB (`CACHE_DB_VERSION` bumped 1→2 so `onupgradeneeded` creates it for existing users). One record per qualifying file, **keyed by the file's own content fingerprint** (`getFileFullHash`) rather than by session/`cacheKey` — this is the mechanism that makes the memory outlive a session: nothing about "which session wrote this" is stored at all, only "what content this filter tree belongs to". A record holds `{ name, fullHash, entryCount, timeSpan, filters, savedAt }` — `filters` is the same `serializeFilterTreeForCache` shape the session cache and filter-save/load JSON already use. **Deliberately scoped to the filter tree only** — no bookmarks, no view settings, no active-node ref — at the person's explicit request when this was scoped; those live in the session cache already, and duplicating them here would raise exactly the staleness/re-anchoring questions the session cache's own bookmark-ordinal scheme already has to deal with, for a part of the feature nobody asked for.

**Qualifying** = a real (non-merged) file with at least one real filter child. An empty tree has nothing worth remembering; a merged file is excluded even once it has its own filters, since `mergeFiles` starts every merge with a deliberately empty tree by design (see "Tree interactions" / multi-select bulk actions) — remembering filters *for a merge* would be remembering filters for a combination that's unlikely to recur byte-for-byte across sessions the way a single source file's content can.

**No cap on the number of remembered files.** This was an open question going into the build (an earlier draft considered a "last 10–20 files" LRU cap) — resolved against a cap because the two things that usually justify one don't apply here: storage size doesn't scale with log file size (a serialized filter tree is a few KB at most, not the log text itself — unlike the session cache's `files` store), and the natural per-record key (content fingerprint) already means loading the same content twice overwrites in place rather than accumulating duplicates, so there's no unbounded-growth-from-normal-use failure mode to cap against either. A long tailing session doesn't spam the store: `persistFileHistoryNow` runs debounced from `render()` (`schedulePersistFileHistory`, same 400 ms window as `schedulePersistMeta`), but `buildFileHistoryRecords` only writes a file's record when its serialized filter tree differs from the last one written (`node._historySig`, the key it went under in `node._historyKey`) — tail growth under an unchanged tree writes nothing and, crucially, doesn't re-fingerprint the grown text (until 2026-09-25 it did: every tail tick renders, so every tick re-hashed the whole file, ~280 ms on 100 MB). The record under the earlier fingerprint still matches the grown file via tier 2; the next filter change writes a new record under the then-current fingerprint, and each earlier snapshot's record is left behind, which is a *feature* here (see tier 2 below), not a leak. An emptied tree deletes the record once, under `_historyKey`. If unbounded growth ever becomes a real concern in practice (long-lived shared/kiosk profiles), the natural follow-up is a **time-based expiry** (drop records unmatched for N months) rather than a count cap, since relevance here tracks recency of a match, not an arbitrary "last N files" number — deliberately deferred rather than speculatively built.

**Matching** (`matchFileHistory`) reuses the exact same tiered content-fingerprint technique Session export/import's `matchExportedFile` already established, just run in the opposite direction: one just-loaded candidate file checked against every stored record (since the history store is unbounded, unlike export/import's "handful of currently loaded files"), instead of one export record checked against a handful of loaded candidates. **Tier 1**: exact whole-file fingerprint match. **Tier 2**: the loaded file's own time span fully *contains* a stored (smaller) snapshot's span — the file has grown (typically via tailing) since that snapshot was saved — confirmed by re-slicing the loaded file down to that historical window (`windowSlice`, reusing `lowerBoundByTs`/`upperBoundByTs`) and checking both the entry count and the window's own fingerprint match the stored record exactly. Ties within tier 2 (a file grown past several old snapshots) resolve to the most recently saved one. **Tier 3 deliberately gets no preview at all**, not a lighter-weight one — an ambiguous/unverifiable match here would need the same manual-disambiguation machinery Session export/import's tier 3 dialog uses, which is disproportionate for a convenience feature; a miss just costs a missed convenience, never a wrong restore.

**Where the lookup happens**: `loadFileDescriptors` (the single funnel behind Open Files, drag-drop, and File System Access picker loads), right after the file finishes parsing and its `cacheKey` write fires — a freshly loaded file always starts with zero filter children at that point, so the lookup can only ever attach a *candidate* match, never something that competes with real filters already on screen. The result is stored as `node.filterHistoryMatch = { filters, tier }` on the file node itself. **Not run** for `mergeFiles` (excluded by design, see "Qualifying" above) or `restoreSessionFromCache` (that flow already brings its own filters back via the session cache — running this lookup there too would be redundant and could theoretically flash a ghost preview mid-restore for no benefit).

**UI**: a "ghost preview" (`renderFilterHistoryPreview`, called from `renderNode`) renders directly under a file's tree row, in the same visual slot real filter children would occupy, whenever `node.children.length === 0 && node.filterHistoryMatch` — condition-based, not event-based: no separate "was this offered/dismissed already" flag exists anywhere. One grayed, non-interactive row per node in the stored tree (`renderGhostRow` — icon, name, type tag, mirroring `renderNode`'s own visual language closely enough to read as "this is what your filters looked like", but with no click/drag/context-menu handlers at all), a short note line (entry count, "File has grown since —" prefix on a tier-2 match), and two buttons: **Restore filters** calls the existing `materializeCachedFilters(fileNode, match.filters)` and re-renders; **Cancel** (person-requested, this session — previously the only way to get rid of an unwanted ghost preview was to create a real filter yourself) just sets `fileNode.filterHistoryMatch = null` and re-renders, dismissing the preview without building anything. **Disappears automatically** the instant the file gets *any* real filter child — whether via Restore or the person just creating their own filter without ever clicking it — because that's the entire visibility condition; Cancel reaches the same end state (`filterHistoryMatch` gone) through the other half of that same condition instead. Cancel is a plain, session-local dismissal, not "forget this content's history forever": it deliberately does NOT set `node.filterHistoryTouched` (unlike actually gaining then losing a real filter, see the "Emptying the tree" paragraph below) — the underlying stored `fileHistory` record is untouched, so the same match can still resurface if this exact content is opened again later.

**(Resolved) Emptying the tree back out now overwrites the old restore state instead of resurrecting it.** Previously `node.filterHistoryMatch` was never deleted, only hidden by the `children.length` condition above — so deleting every filter the person had just added made the tree empty again, the condition flipped back to "showable", and the ghost preview resurfaced showing the *original, pre-session* filters, not anything reflecting what the person had just done. Fixed this session (2026-08-14, person-reported via screenshot): `buildFileHistoryRecords()` (see "Storage" above) now tracks a per-file, session-only `node.filterHistoryTouched` flag, set the first time `children.length` goes from 0 to >0 (own filter or a Restore) — at that same moment `filterHistoryMatch` is cleared to `null`, so it can never resurface later purely because the tree emptied back out. If the tree is later emptied again (`children.length` back to 0) while `filterHistoryTouched` is set, the persist cycle now **deletes** that file's stored record instead of leaving it untouched — both directions (gaining a filter, losing the last one) overwrite whatever restore memory came before, and a file with no filters left is indistinguishable from one that never had any, including on the next reload. A freshly loaded file whose ghost preview hasn't been acted on yet (`filterHistoryTouched` still unset) is unaffected — nothing is decided about it until the person actually does something.

**Test coverage**: `tests/philogg.regression.test.js` Group 30 (jsdom + `fake-indexeddb`) — 30a: tier-1 exact-match persistence and restore across two windows sharing one `IDBFactory` (same reload-simulation pattern Group 20 established), including the ghost preview's row count/content, the Cancel button dismissing it without creating any filter (and the match being able to resurface afterward, proving Cancel didn't touch the underlying stored record), and the Restore button materializing the tree; 30b: tier-2 matching against a grown file, plus the negative case (a genuinely unrelated file's span doesn't overlap at all, so it's not even a near-miss); 30c: the exclusion rules (merged files, empty filter trees), the ghost preview's auto-hide once the file gets any real filter child, and (extended this session) the in-memory match actually clearing once the tree is populated; 30d: the same tier-1 round trip but through the REAL `loadFileDescriptors` entry point — an actual `File` read via `FileReader` (jsdom implements both natively, no stubbing needed), proving the `persistFileNode` → `matchFileHistory` hook wired inside `loadFileDescriptors` itself works end-to-end, not just the lower-level pieces 30a-c exercise directly; **30e (new, this session)**: the full reported bug scenario end-to-end — session 1 saves a tree, session 2 loads the same content, creates its own filter (old record correctly overwritten, already worked), deletes that filter again (ghost stays hidden, in-memory match stays cleared, stored record is removed — the actual bug), then a simulated session 3 reload of the same content finds no match at all.

## Session export / import (sharing an analysis with a colleague)

**"Export session…"** lives behind `#btnSave` in `#sidebarHeader`; **import** goes through the central **"Import…"** behind `#btnOpen`'s dropdown (`#openMenu`, alongside File(s)…/Folder…/ZIP…) or a dropped session file (see "Central import") in the same header (see "Header / toolbar layout" → "Toolbar regroup" for the FEATURE_BACKLOG.md #56 move that put both there, and the earlier `#btnSession`/`#sessionMenu` pairing they replaced). Both actions used to live in the tree's per-node context menu instead (next to Save/Load filter, plus a dedicated empty-background context menu just to keep "Import session…" reachable with zero files loaded) — moved out of there since neither action is actually about whichever file/filter the context menu was opened on; the buttons work identically regardless of how many files are loaded, so the empty-background special case is gone too, not just relocated. `openSessionExportDialog()`/`importSessionJson()` were already self-contained (the export dialog guards on `state.rootIds.length` itself, the import flow needs no node reference at all), so both moves were pure UI wiring with no logic change. Format is `{ format: "philogg-session-export", version, exportedAt, files: [...], settings }`, `SESSION_FILE_VERSION = 1`.

**What gets exported**: a user-picked subset of the currently loaded root files (`#sessionExportDialog`, one row per file with an include checkbox), each file's *complete* filter tree (reusing `serializeFilterTreeForCache`/`materializeCachedFilters` from the session cache — no branch/chain-pulling needed since the whole tree goes anyway), that file's bookmarks (first-wins scan across files, same convention as `buildCacheMeta`), and session-wide settings (level filter, sort, active node — recorded as `{exportId, ref}` since export ids are only stable within one export document). A per-file **"embed log text"** checkbox (deliberately per-file, not global — some logs in a session may be sensitive while others aren't) includes `rebuildFileText(node)` in that file's record, making the export self-contained for that file.

**The core problem this solves**: the person importing almost certainly has their *own* copy of the same log, not the exporter's literal file — same name, different name, or (for a tailed/live log) a newer snapshot that kept growing after the export was made. `matchExportedFile()` resolves each exported file against the importer's currently loaded files in three tiers:

1. **Tier 1 — full-content match**: the export carries a whole-file fingerprint (`fullHash`, via `fingerprintText`); any loaded file whose own full fingerprint (`getFileFullHash`, cached on `node._fullHash`) matches is a confident hit. Applied silently.
2. **Tier 2 — overlapping time window**: covers the motivating scenario (receiving copy of a tailed log kept growing past the exported snapshot). The exported file's timestamp span must be **fully contained** in the loaded file's span — a file that only partially overlaps (e.g. a rotated/truncated head) can't be verified this way and falls through to tier 3. Within the window: entry-count pre-filter first (cheap, and a strong signal — same density in the same window), then a fingerprint of the concatenated raw text of just that window, compared against the export's `fullHash`. An appended entry whose timestamp lands exactly on the window's end boundary inflates the count and correctly demotes the match to tier 3 rather than silently misapplying. Surfaced via a passive toast (`"X matched via overlapping time range"`) — applied automatically, but the person is told why, since it's a weaker guarantee than tier 1.
3. **Tier 3 — manual reassignment** (`#sessionMatchDialog`, one dialog per unresolved file, sequential): near-misses from tiers 1–2 (right file, wrong count/hash, or partial overlap) are shown first and badged "possible match"; other loaded files follow; then **"Load a file from disk…"** (opens the normal file picker, re-runs tiers 1–2 against the newly loaded file, loops back to the dialog if that still doesn't resolve it); **"Load the embedded log"** (only shown when the export has `text` for that file — materializes it via `addFile`, treated as tier-1-trustworthy since re-parsing the exporter's own rebuilt text is a fixed point); and **"Skip this file"**. Cancel on the dialog skips this file and every remaining unresolved one (already-applied files are kept). No backdrop-click dismissal on this dialog (unlike the export dialog) — a stray click mid-import shouldn't silently count as a decision.

**Bookmarks**: tier 1/2 targets are provably identical inside the exported window, so a bookmark's stored **ordinal** is trusted outright (`applySessionEntryByOrdinal`, same scheme as the session cache). A tier-3 manually-picked file has no such guarantee, so bookmarks there are re-anchored by **timestamp** (binary search via `lowerBoundByTs`) and confirmed against the hit ± 2 neighbours by **raw-line fingerprint** (`applySessionEntryByContent`) — enough slack to absorb small insertions/deletions elsewhere in the file without losing every bookmark to one nearby edit. A bookmark that can't be confirmed is dropped and shows up in the final summary toast as unplaced (`"N of M bookmarks placed"`), never silently misplaced onto the wrong line.

**Fingerprinting is deliberately not `crypto.subtle`/SHA-256**: it's a matching aid, not a security boundary (the worst-case cost of a collision is a wrongly-*suggested* match that the person can still reject in the tier-3 dialog), Web Crypto's async API is awkward for hashing several loaded files as a synchronous pre-filter, and its availability under a `file://` origin (this app's primary deployment mode) isn't worth depending on. `fingerprintText()` runs two 32-bit FNV-1a passes with different offset bases and concatenates them into 16 hex chars — cheap, synchronous, good enough for a matching aid.

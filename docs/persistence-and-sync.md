# Persistence and Sync

Undo/redo, bookmarks, notes, pin-bookmarks-into-filtered-view, tailing, file loading, folder watch, filter save/load, the reusable filter library, session cache, per-file filter history, and session export/import.

## Undo / redo

Covers filter node **delete** and **move** (drag/drop reparent, and Ctrl+X-then-paste, which is also a move), plain (non-folder) **file delete**, filter **value/pattern edits** (the F2/"Edit filter…" popup and the time-range dialog, including the legacy `after`/`before` → `timerange` migration), the **invert (NOT) toggle**, and **value-assertion** add/clear. Still deliberately out of scope: filter/file *creation*, folder-file close (not destructive — the file just returns to its folder's grayed listing, see "Folder watch"), and context-filter creation (no edit path exists for it at all). A small snapshot-based command stack was chosen over deriving undo generically from every tree-mutating function, since the tree's structural invariants are easier to reason about as "restore exactly this snapshot" than as a generic inverse of arbitrary mutations.

**Delete/move call sites**: the only two a user-facing delete/move should ever go through are `deleteFilterNodeWithUndo(nodeId)` and `moveFilterNodeWithUndo(nodeId, newParentId)` — every existing trigger (Delete key, per-row hover ✕, tree right-click menu, drag-and-drop `drop` handler, Ctrl+X-then-Ctrl+V's move branch) calls one of these instead of `deleteNode`/`moveNode` directly. Anything that bypasses them silently isn't undoable. `deleteFilterNodeWithUndo` branches three ways: a folder-loaded file (`node.folderId`) goes to `closeFolderFile` (unchanged, not undoable); any other **file** node snapshots+deletes and pushes a `"deleteFile"` action; a **filter** node does the original `"delete"` action. Deleting an `and`/`or`/`link` node only ever removes that one node plus its own real subtree — its `bakedA`/`bakedB` (see `docs/filters.md`'s "Self-contained AND/OR/LINK") are flat, already-baked data, not a reference to any other node, so there's nothing elsewhere in the tree that this delete could possibly affect.

**Snapshotting**: `snapshotSubtree`/`restoreSubtree` deep-clone a node's whole subtree the same way `cloneSubtree` does for copy/paste, with one crucial difference — **original ids are kept**, not reassigned (this mainly matters for the tree UI itself — selection/scroll position surviving an undo — not for and/or/link correctness, since `bakedA`/`bakedB` don't reference any node's id in the first place). Both functions branch on `node.type`: a **file** node's own fields (`entries`, `cacheKey`, `merged`, `tail`) are captured/restored by *reference*, not cloned — the same entry objects and live tail handle just get unplugged from `entryIndex`/`state.rootIds` on delete and plugged back in on undo, same as a real close/reopen; `restoreSubtree`'s file branch also re-adds every entry to `entryIndex` and calls `persistFileNode` (fire-and-forget, re-creating the session-cache record `cacheDeleteFile` dropped) since a file is never structurally nested, this branch only ever runs at the top of a `"deleteFile"` snapshot — its filter-type children still go through the existing branch.

**The generic "edit" kind**: unlike delete/move, a value edit has no cheap structural inverse to derive, so `captureNodeFields(node)`/`applyNodeFields(node, fields)` capture/restore a node's whole set of mutable, non-structural fields (`filterType`, `value`, `inverted`, `name`, `ignoredColumns`, `caseSensitive`, `columns`, `assertions`) wholesale. `withFieldEditUndo(nodeId, mutateFn)` captures a `before` snapshot, runs the mutation, captures `after`, and pushes `{ kind: "edit", nodeId, before, after }` — `undo()` applies `before`, `redo()` applies `after`. Four call sites: `updateFilterNodeWithUndo`/`updateTimeRangeFilterNodeWithUndo` (thin wrappers around the existing `updateFilterNode`/`updateTimeRangeFilterNode` mutators, called from `commitFilter` and the time-range dialog's submit handler), `toggleInvertWithUndo` (the tree context menu's "Invert (NOT)" action), and the value-assertion dialog's Save/Clear handlers (call `withFieldEditUndo` directly, since their mutation is a one-liner). The plain `updateFilterNode`/`updateTimeRangeFilterNode` mutators still exist undecorated — nothing else in the codebase calls them without the `WithUndo` wrapper.

**The stack**: `undoStack`/`redoStack`, capped at `UNDO_STACK_LIMIT = 50` (oldest entries drop off silently). `pushUndo()` — called only from the wrapped mutators above — always clears `redoStack`, since a genuinely new action makes any previously-undone branch unreachable (standard undo/redo semantics). `undo()`/`redo()` themselves move the same action object directly between the two stacks (applying the inverse or re-applying the forward mutation) without going through `pushUndo`, so they never clear each other's history — undoing three deletes and redoing one still leaves the other two redoable.

**UI**: `#btnUndo`/`#btnRedo` (toolbar, left of the theme toggle) — disabled via the plain `disabled` attribute when their respective stack is empty, tooltip names which action would be undone/redone next (`UNDO_KIND_LABELS` maps each `kind` to its human-readable label: delete/file delete/move/edit). `Ctrl+Z` undoes, `Ctrl+Shift+Z` **and** `Ctrl+Y` both redo (the second purely for muscle-memory compatibility with editors that use one or the other). A toast (`showCopyToast`) confirms which kind of action was undone/redone, since the tree can be deep enough that the effect isn't always visually obvious at a glance.

## Bookmarks

**Reworked this session (FEATURE_BACKLOG.md "Bookmarks rework", person-requested)**: the old Bookmark Manager panel (`#btnBookmarks`/`#bookmarksPanel`/`#bookmarksList`/`renderBookmarksPanel`/`openBookmarksPanel`/`closeBookmarksPanel`/`updateBookmarksButton`) is removed entirely. Bookmarks are now surfaced as a **single, auto-managed filter node** — see "The auto-managed 'Bookmarks' filter node" below. The underlying `state.bookmarks` Set (still the actual source of truth) and the PIN-bookmark feature (`getPinnedBookmarkEntries`/`state.pinBookmarksInFilteredView`) are otherwise **unaffected** — they still read `state.bookmarks` directly, exactly as before. The bookmark's own free-text note field (`{ note, bookmarkedAt }`) is gone too — the general-purpose Notes feature (see "Notes" below) replaces it with something far more capable (any entry, not just bookmarked ones; multi-line; its own Entry Detail display).

`state.bookmarks`: `Map<entryId, { bookmarkedAt }>` — **not part of filter save/load**, since a bookmark anchors a spot in the *data*, not a filter definition; it doesn't belong in a filter-tree JSON file the way `inverted` or a value assertion does. Persisted across reloads by the session cache and session export (as file + entry ordinal, since entry ids don't survive a reload — see "Session cache"). Deliberately scoped to real log entries selected in the plain log view (`state.selectedId`) — not link-view pair entries or extraction-table rows, which have synthetic/derived ids that are never added to `entryIndex` (see Core data model), so a bookmark on one could never be resolved back to a real row later. The row context menu (`#ctxBookmark`) and `openContextMenu` hide/no-op that menu item when the right-clicked entry isn't in `entryIndex` for exactly this reason.

**Toggling**: right-click a row → "Bookmark this row" / "Remove bookmark" (`#ctxBookmark`, label reflects current state), or press **B** with a row selected (`state.selectedId`). Bookmarked rows get a small filled star (`.row-bookmark-dot`, reuses `ICON_BOOKMARK_FILLED`) in the same left-gutter slot the context-filter bracket/anchor-dot uses — the two can in principle land in the same visual spot if a row is both a context-filter reference *and* bookmarked; accepted as a minor, rare cosmetic overlap rather than reserving a second gutter slot for it. `toggleBookmark(entryId)` also calls `syncBookmarksFilterNode(rootId)` (see below) after mutating `state.bookmarks`, and repaints the sidebar tree (`renderTree()`) alongside its existing targeted row/pin repaint, since the auto node can now appear/disappear as a side effect.

**Jumping**: `jumpToEntry(entryId)` resolves an arbitrary entry's own root file via `findRootIdForEntry(entryId)` (a linear scan over `state.rootIds`, O(root file size) — fine since this only runs on a rare user click, not a render-path hot loop) before switching `state.activeId`, clearing the level filter, and setting `state.scrollTargetId`, same as `jumpToFullLog`, but working from anywhere regardless of which chain is currently active. Originally the Bookmark Manager panel's own row-click handler; kept as a general "jump to this entry" utility now that the panel is gone (still exercised by tests, e.g. the multiline virtualization group's `scrollToIndex` check).

### The auto-managed "Bookmarks" filter node

`syncBookmarksFilterNode(rootId)` creates or removes a single `filterType: "bookmarks"` node directly under the given root file, depending on whether that root currently has ≥1 entry in `state.bookmarks` — called from `toggleBookmark` (for the affected root) and from every bookmark-restore path (session cache restore, session import's `applySessionEntryByOrdinal`/`applySessionEntryByContent`), so a session that comes back with bookmarks always re-derives the node, and one with none never leaves a stale one. Idempotent — safe to call whether or not anything actually changed.

- **Matching**: `getEntries()` gained a `filterType === "bookmarks"` branch — `result = parentEntries.filter(e => state.bookmarks.has(e.id))` — following the exact same per-`filterType` branching pattern every other matcher (`text`, `level`, `context`, …) already uses, rather than a parallel code path. `FILTER_TYPES` (the save/load + cache validity `Set`) includes `"bookmarks"` for internal use, but importing/materializing a saved node of this type is explicitly **rejected** (see Persistence below) — the type exists for live matching only.
- **`locked: true`**: the node carries this new flag, checked by `deleteFilterNodeWithUndo`/`moveFilterNodeWithUndo` (both no-op/return `false` on a locked node — the single choke point every delete/drag/middle-click/Delete-key path already routes through, so no per-call-site duplication was needed) and by `renderNode`'s `row.draggable` assignment (skipped for a locked node, so a drag never even starts). The tree context menu's item-building code branches early on `node.locked`: a locked node's menu is just **"Copy"** — no rename/edit/invert/context/cut/save-to-library/delete. The `✕` delete button is omitted from the row entirely (not just disabled) for a locked node. **Not restricted**: the highlight-colour swatch (`openColorPicker`/`setHighlightColor`) — colouring/styling a locked node works exactly like any other filter node, per the feature's own requirement.
- **Icon/label**: no dedicated icon — `nodeIconHTML`'s `filterType` switch has no `"bookmarks"` case, so it falls through to the same generic default (`ICON_CLOCK`) legacy `"after"`/`"before"`/`"timerange"` nodes already use. `typeTagFor`/`ghostTypeTag` do give it its own three-letter tag (`BKM`) for the tree row's type-tag column, same as every other `filterType`.
- **Persistence — deliberately excluded from the filter-tree carriers**: `serializeFilterTreeForCache`'s `ser()` (session cache) and `serializeFilterBranch`'s recursive collector (session file JSON) both skip any child node whose `filterType === "bookmarks"` via a shared `persistableChildren(ids)` filter, and `importFilterJson`/`materializeCachedFilters`'s own `validate`/`valid` helpers reject `filterType === "bookmarks"` outright (defends against a hand-edited or pre-rework file). The node's own membership is entirely derived from `state.bookmarks`, which is *itself* persisted (see "Session cache"/"Session export/import" below) — serializing the node too would just be redundant, driftable state; re-deriving it via `syncBookmarksFilterNode` after every bookmarks-restore keeps it exactly in sync with zero extra stored shape. One accepted edge case: if a person manually adds a filter as a *child* of the locked node (not prevented — only delete/move/reorder are blocked, not "become a parent"), that child is lost along with the node the next time it's excluded from serialization. Rare enough, and easy enough to work around (create the filter one level up instead), not to warrant extra plumbing.
- **`cloneSubtree`** (copy/paste) deliberately does **not** copy `orig.locked` — pasting a copy of the auto node produces a plain, unlocked filter node (still matching whatever was bookmarked at copy time, since `filterType`/`value` themselves *are* copied) rather than a second restricted original; only `syncBookmarksFilterNode`'s own node stays locked.

### The auto-managed "Notes" filter node

Person-requested "Notes overview" (this session): a second auto-managed, restricted filter node, `syncNotesFilterNode(rootId)` — the exact same shape as `syncBookmarksFilterNode` above (idempotent create/remove keyed on "does this root have ≥1 entry with something in the corresponding Set/Map", `locked: true`, excluded from every filter-tree persistence carrier, `cloneSubtree` drops `locked` on copy), mirroring `state.notes` instead of `state.bookmarks`. Its whole point is a single place to read every note in a file at a glance, with the usual "jump into the filter tab, see the entry in context" behavior any filter node already gives for free — no bespoke notes-browsing UI was needed, just a second `filterType`.

- **Placement**: inserted directly **below** the "Bookmarks" node when one exists (found by index, spliced in right after it), or unshifted to the very top when Bookmarks isn't currently present — so the two always read as "Bookmarks, then Notes" whenever both are showing, without one ever displacing the other's slot.
- **Matching**: `getEntries()`'s `filterType === "notes"` branch is `result = parentEntries.filter(e => state.notes.has(e.id))`, the same one-line pattern the `"bookmarks"` branch uses. `FILTER_TYPES` includes `"notes"` for internal use only — a saved/imported node of this type is rejected the same way `"bookmarks"` is (`importFilterJson`'s `validate`, `materializeCachedFilters`'s equivalent).
- **Sync call sites**: `setNoteAndRepaint` (every note add/edit/delete) calls `syncNotesFilterNode(rootId)` for the note's own root and repaints the tree, same as `toggleBookmark` does for Bookmarks; every bookmark-restore call site that already called `syncBookmarksFilterNode` (session cache restore, `applySessionEntryByOrdinal`/`applySessionEntryByContent`) now also calls `syncNotesFilterNode` right after it.
- **Standing on it auto-enables Show Notes**: `render()`'s existing "did `state.activeId` change since last render" check (the same one driving `applyActivationView`) now also detects entering/leaving a `filterType: "notes"` node. Entering one snapshots the current `state.showNotes` into `notesFilterPrevShowNotes` and force-enables it if it was off — reading every note in the file only works if note-rows are actually showing. Leaving it restores whatever `state.showNotes` was before, so the toggle's own state is never permanently changed by just visiting the node. A person manually flipping `#btnNotes` while standing on the node is respected for the rest of that visit (only the *leave* transition restores the pre-entry value, comparing against the live `state.showNotes` at that moment).
- **Persistence**: excluded from `serializeFilterTreeForCache`/`serializeFilterBranch`'s persisted children the same way `"bookmarks"` is (one shared `persistableChildren` filter now checks both types) — re-derived from `state.notes` on every restore instead, for the same reasoning as Bookmarks.

## Notes

General-purpose free-text notes on *any* log line, bookmarked or not (FEATURE_BACKLOG.md "Bookmarks rework", shipped alongside the bookmarks node change above). `state.notes`: `Map<entryId, noteText>` — same id scheme as `state.bookmarks` (a real, `entryIndex`-resolvable log entry id), same persistence tier (session cache, session export/import), but a **completely separate, flat per-entry store** — not part of the filter tree, not tied to a row being bookmarked.

**Editing**: `openNoteEditor(entryId)` opens `#noteDialog` (same fixed-position, backdrop-click-to-close card pattern as `#timeRangeDialog`/`#assertDialog`), prefilled with the existing note or empty for a new one — the dialog's own title ("Add note"/"Edit note") and the presence of a "Delete" button reflect which. Reachable three ways: **`Alt+N`** on the selected row (`state.selectedId`) — no separate `F2` binding, the same shortcut opens either mode depending on whether a note already exists; the row context menu's **`#ctxNote`** item (label-swaps "Add note"/"Edit note" exactly like `#ctxBookmark` does, same `entryIndex` eligibility gate); and **double-clicking an existing rendered note-row** (`appendNoteRow`'s own `dblclick` listener, attached fresh every render — see "Rendering" below for why that's required, not just convenient). `setNoteAndRepaint(entryId, text)` is the single mutator: empty/whitespace-only text deletes the note (`state.notes.delete`) rather than storing an empty string, otherwise trailing whitespace is trimmed and the rest stored verbatim (internal formatting/indentation is the person's own).

**Rendering**: a note renders as a **sub-row** — a plain block `div.note-row`, not part of `.row-grid` — appended as a DOM sibling directly after its entry's own row, in both the Filtered (`renderVisibleRows`) and Full (`renderHighlightVisibleRows`) views, via a shared `appendNoteRow(frag, e)` helper. No level marker (it isn't `.row-grid`, so there's no `.col-bar` to color), own colour (`--accent-strong`, italic) and left-indented (32px padding vs. the row's own 14px gutter) to read as clearly subordinate to the entry above it. Gated on `state.showNotes` (the Show/Hide Notes toggle — see below) and the entry actually having one; stays visible regardless of the active filter/level-filter, since it belongs to whichever entry row is already being rendered — a note is never itself a filter target. Its `dblclick` listener opens the editor for that entry; built fresh on every call to `appendNoteRow` rather than assumed to persist, per the CLAUDE.md gotcha ("`renderVisibleRows()` rebuilds nodes, breaking native `dblclick`" on anything that assumes DOM identity survives a re-render) — this is the same reasoning every other per-row listener in this file (`renderNode`, the row's own click/contextmenu/dblclick) already follows, just newly relevant here too.

**Height/virtualization**: a note-row's height (`noteHeightForEntry(e)`) is `0` when notes are hidden or the entry has none, otherwise `NOTE_LINE_HEIGHT (16) × line count + NOTE_ROW_VPAD (6)` — the same "count literal `\n`s, don't measure wrapped soft-lines" simplification `messageLineCount`/multiline-message rendering already uses. `rowHeightForEntry(e)` (the value fed into `buildRowOffsets`' prefix-sum array) is now `baseRowHeightForEntry(e) + noteHeightForEntry(e)` — `baseRowHeightForEntry` is the *original* `rowHeightForEntry` body (the entry's own row height, unaffected by notes), factored out so the `.log-row` element's own `style.height` can be set to just its own share, with the note-row getting the remainder as its own separate `style.height` — the two DOM elements' real heights MUST sum to exactly what `buildRowOffsets` computed, or virtualization drifts out of sync with what's actually on screen. A new `needsRowOffsets()` helper (`state.multilineMessages || state.showNotes`) replaces every direct `state.multilineMessages` check that gated the offsets-array virtualization path (`tableRowOffsets`/`highlightRowOffsets`, `buildRowOffsets`, the various `findOffsetIndex`-based branches in `renderVisibleRows`/`renderHighlightVisibleRows`/`scrollToIndex`/`scrollToHighlightIndex`) — notes showing at all now needs that path too, for the same reason multiline messages always did (rows are no longer uniformly `ROW_HEIGHT`).

**Entry Detail panel**: `updateDetailPanel()` shows the selected entry's full note text in a new `#detailNote` block below `#detailMessage` (own dashed top border, same `--accent-strong` colour as the note-row, `white-space:pre-wrap`), unconditionally — not gated on `state.showNotes`/`state.multilineMessages` — so a multi-line note stays fully readable even with note-rows hidden or MultiColumn's single-line rendering. Hidden (`display:none`) when the selected entry has no note or nothing is selected.

**Show/Hide Notes toggle**: `#btnNotes` (`state.showNotes`, default **`false`** — same "off by default" reasoning as `state.multilineMessages`: the plain fixed-`ROW_HEIGHT` virtualization path stays the unaffected default until someone actually has notes to see inline), placed in `#viewBar` next to `#btnPinBookmarks`/`#btnMultilineMsg` (same `.toolbar-icon-btn` float/margin, same extract-mode hide/show pairing). Its click handler flips the flag and calls a **full `render()`** — same "correctness over render cost for a rare click" tradeoff `#btnMultilineMsg` already makes, since toggling it can change every visible row's height at once.

**Persistence**: `buildCacheMeta()`/`buildSessionExport()` serialize `state.notes` the same ordinal-anchor way `state.bookmarks` already does (`{ file/ordinal }` for the cache, `{ ordinal, ts, raw }` fingerprint-fallback fields added for the export's tier-3 manual-match path — mirroring the bookmark record's own fields exactly), but as a **separate `notes` array**, not folded into the `bookmarks` one. `applySessionEntryByOrdinal`/`applySessionEntryByContent` (session import) and `restoreSessionFromCache` (cache restore) each gained a parallel notes-restore loop next to their existing bookmarks loop, returning/tracking `notesPlaced`/`notesTotal` alongside the existing `placed`/`total`, surfaced in the import summary toast as an additional "N of M notes placed" clause. `state.showNotes` itself persists in `settings.showNotes` on both carriers, same tier as `multilineMessages`.

## Pin bookmarks into the Filtered View

From `FEATURE_BACKLOG.md` item 1 (person-requested, modeled on glogg/klogg's "marks" — lines marked in the main view that always break through the search pattern into the filtered results, merged in log order). Deliberately built as an extension of the existing Bookmarks feature rather than a third marker type, to avoid a second visual marker competing for the same left-gutter slot the bookmark dot and context-filter anchor dot already share (see "Bookmarks"), and because a bookmark's existing meaning — "this entry matters regardless of context" — already implies the pin semantics; introducing a parallel concept would just duplicate it.

**Toggle**: `state.pinBookmarksInFilteredView` (bool, default `false`), a toolbar button `#btnPinBookmarks` (`ICON_PIN`, a map-pin glyph). It's a plain persistent on/off switch, not a popup — styled via a general-purpose `.toolbar-icon-btn.active` state (reused accent colors, same ones `.crumb.current` already uses) rather than anything bookmark-specific, so any future toolbar toggle can reuse it. Deliberately styled as its own control rather than a `.level-btn` pill: the level pills are subtractive (AND — narrows the result set; empty selection is the "show everything" special case), while pinning is additive (OR — adds entries the filter chain would otherwise exclude). Visually identical pills with inverted logic in the same row was judged a likely source of confusion, so pinning keeps its own distinct look instead. **Location (moved this session, person-requested)**: originally sat in the header next to `#btnBookmarks`; now lives in `#viewBar` itself, floated between `#fhTabs` and `#levelBar` — the row that controls what the active views show/hide, which is what this toggle does, so it belongs there rather than among the header's mostly popup-trigger buttons. The move is purely positional: same element, same id, same `.toolbar-icon-btn` class and click handler, still deliberately *not* inside `#levelBar` itself or restyled to match `.level-btn` (see "Header / toolbar layout" for the float mechanics).

**Merge logic** (`getVisibleEntries()`, the function `renderTable()`'s plain-table path already used for "node filter + level quick-filter"): when the toggle is on, the filter-tree result is unioned with the bookmarks belonging to the *active root file* — resolved via a new `getPinnedBookmarkEntries(rootId, orderIndexMap)` — and the union is re-sorted into that root's own chronological (array) order. A pin is **absolute**: it bypasses both the filter tree's own result *and* the level filter, the same way glogg/klogg's marks bypass the search pattern — consistent with the "regardless of the filters" framing the feature was originally requested with. `getPinnedBookmarkEntries` reuses `buildOrderIndexMap` (already used for the link filter's same-timestamp tie-break) as a combined membership test ("does this bookmark belong to this root") and position source for the final merge sort — a single O(root size) map build per render instead of an O(root size) scan per bookmark the way `findRootIdForEntry` would cost if reused here instead.

**Gotcha (bugfixed this session, person-reported)**: `toggleBookmark()` is a second choke point that can change WHICH rows the Filtered view shows, not just `render()`/`renderTable()` — while pin mode is on, adding or removing a bookmark can add or drop a row, so `toggleBookmark()` must recompute `currentViewEntries`/`pinnedOnlyIds` (i.e. call `getVisibleEntries()` again) itself before its own `renderVisibleRows()` repaint, guarded behind `state.pinBookmarksInFilteredView` so the common (pin-off) case is untouched. Deliberately does **not** call `renderTable()` for this — that always resets scroll to the top, which would yank the reading position on every bookmark toggle. See "Status / changelog" for the fix.

**Scope decisions made this session** (the backlog doc's open questions):
- *Persistence*: yes — part of `state`'s persisted settings, same tier as `levelFilter`/`sortColumn`. Written to and restored from all three existing settings carriers: the IndexedDB session cache (`buildCacheMeta`/`restoreSessionFromCache`), and the portable session export/import JSON (`buildSessionExport`/its import counterpart) — kept alongside `levelFilter`/`sortColumn` in all three places rather than singled out, since it's the same kind of view preference.
- *Extract / Link views*: **unaffected, deliberately** — not by an explicit guard, but structurally: `getVisibleEntries()` is only ever called from `renderTable()`, which only runs for the plain-table path (`renderMainView` routes extract nodes to `renderExtractTable()` and link nodes to `renderLinkView()` instead, neither of which calls it). This falls out of the existing view-routing, not a new special case, and matches the precedent already set by Bookmarks itself being scoped to real `entryIndex`-backed entries only (extraction rows and link pairs have synthetic ids that were never bookmarkable to begin with).
- *Visual treatment*: rows present only because of a pin (not because they matched the filter chain) get `.pinned-row` — an inset left `box-shadow` (`--accent-strong`) rather than a background tint, so it doesn't fight the existing per-level row background (`lvl-error`/`lvl-warn`/etc.). A bookmarked row that *also* genuinely matches the filter does **not** get this class — it's a normal match, not a "here only because of the pin" row, and `renderVisibleRows` distinguishes the two via a `pinnedOnlyIds` set refreshed on every `getVisibleEntries()` call. (The status strip used to surface a `"· N pinned"` suffix off this same set — removed this session, 2026-09-04, along with the status strip itself; `.pinned-row` is the only remaining signal now.)

**Non-goals**: no cross-root/cross-file pinning (scoped to the active root, same as the merge's `orderIndexMap`); no changes to the Bookmarks panel, notes, or `jumpToEntry` themselves — this is purely additive to how bookmarks are *surfaced* in the Filtered View.

## Tailing (live file updates)

Files opened with a **FileSystemFileHandle** (File System Access API — the "Open files…" picker via `showOpenFilePicker`, or drag&drop via `DataTransferItem.getAsFileSystemHandle()`, both Chromium) get a `node.tail = { handle, offset, pending, failed, busy, errorCount, lastGrowth, wasLive }` and are polled every `TAIL_POLL_MS` (1500ms) by `tailTick()`: `handle.getFile()` returns a *fresh* snapshot each call, and if it grew, only the new byte range (`file.slice(offset)`) is read and parsed incrementally by `appendTailText()` into the existing `entries` array — handling chunks that start mid-entry (stack-trace continuation lines written across polls) and keeping an unterminated trailing line in `tail.pending` until its newline arrives. On any change, caches for every node whose parentId chain reaches the grown/rotated file are invalidated (`invalidateCachesForRoots`), so **filtered views update live too** — and/or/link nodes included, since they now follow the same plain parentId chain as any other filter type. Truncation/rotation (`size < offset`) resets that file's entries and re-reads from 0. Files loaded as plain `File` objects (Firefox, the legacy `<input>` fallback, drops without handle support) are byte snapshots and simply never get a `node.tail` — they load normally, without tailing. Tailed files show a pulsing accent icon (`.tree-icon-live`, on the file's own tree-row icon rather than a separate dot) in the tree.

**The live dot means "actively receiving new entries right now", not just "still polled"** (`isTailLive(t)`, this session, 2026-08-19, person-reported): `t.lastGrowth` is stamped on every real byte-level change (a genuine append, or a truncation/rotation reset), and the dot only shows while `Date.now() - t.lastGrowth < TAIL_LIVE_MS` (10s) *and* `!t.failed` — a valid, unfailed handle alone is no longer enough. Without this, a file a writer had moved on from (idle, or rotated away from in Folder watch) kept its dot lit forever, since the handle stays perfectly readable, just idle — `t.failed` only ever flips on read errors, never on inactivity. Because a poll tick with nothing new otherwise triggers no re-render at all, `tailTick()` also does a second, cheap pass every tick comparing each tail's current live status against its own cached `t.wasLive` and fires a `renderTree()` (not a full `render()`, no caches to touch) when it flips purely from time passing — otherwise a dot could only go dark on the *next* unrelated tail change, not on its own. See `tests/philogg.regression.test.js` Group 63a/63b.

**Read failures are retried, not fatal on the first one**: a `getFile()`/read failure increments `t.errorCount` and is logged via `console.warn` (previously silent — see "Known limitations"), but only sets `failed` (which stops polling and hides the live dot) once `errorCount` reaches `TAIL_MAX_CONSECUTIVE_ERRORS` (5) **in a row** — any clean poll in between resets the streak to 0. This distinguishes a transient hiccup (most plausibly the writer briefly holding the file locked without shared-read access while it appends a line — an ordinary condition for a log actively being written to by another process) from a genuinely permanent one (moved/deleted/permission revoked), which fails every single poll and still reaches the threshold in ~7.5s.

**Survives a reload**: `persistFileNode` stashes `node.tail.handle` (if any) into the file's session-cache record, and boot-time `restoreSessionFromCache` calls `tryReattachFileTail(node, handle)` for each restored non-folder file — `handle.queryPermission({mode:"read"})` needs no user gesture, so this either silently resumes tailing (with a fresh `offset` computed from the restored text's own length) or leaves the file a static snapshot, same shape `restoreWatchedFolders` already uses for directory handles. See "Known limitations" for the bug this fixed.

**Desktop wrapper files also get tailed** (Bugfix, this session, 2026-08-22, `FEATURE_BACKLOG.md` item 11): a file opened via the desktop app's launch argument, file association, or macOS "open" goes through `loadUrlIntoTree` (see "Deep-link loading (?url=)" below), not the FileSystemHandle path above — it used to build its node from already-fetched text alone and never get a `node.tail`. `isDesktopLocalUrl(url)` now recognizes the desktop wrapper's own `philogg://local/<id>/…` scheme (every fetch to it re-reads the file fresh off disk, see `desktop/src-tauri/src/protocol.rs`) and attaches a `node.tail` whose `handle` (`urlTailHandle`) just re-`fetch()`es that same URL and wraps the bytes in a `Blob` — a drop-in stand-in for `FileSystemFileHandle.getFile()`, so it needs no changes to `tailTick`/`appendTailText` at all. An ordinary `http(s)` `?url=` (CI report link) is deliberately left untouched. Since this reuses the same unconditional poll loop, a desktop-opened file that never grows still gets re-checked every `TAIL_POLL_MS` for as long as the file stays open — the backlog item's secondary ask ("periodically re-check static files for changes") falls out of this for free rather than needing separate handling. See `tests/philogg.regression.test.js` Group 89.

**Follow behavior**: while `state.tailFollow` is true and the active node's root file is tailed, **both** the Filtered view (`isTailedLogViewActive()`) and the Context view (`isTailedHighlightViewActive()`) scroll with the newest entry — one shared flag for both (`FEATURE_BACKLOG.md` #25, this session; previously the Highlight view stayed deliberately static while only Filtered followed). Manual scrolling away from the bottom or clicking/selecting a row (incl. arrow keys) in *either* view disengages follow (`applySelection`, shared by `selectEntry`/`selectHighlightEntry`, checks both views' active-tailed state). Two ways to re-engage it, both equivalent: click the floating **"Newest"** button over whichever view has one (`#tailJumpBtn` for Filtered, `#tailJumpBtnHighlight` for Context — both call `jumpToTailedNewest()`), or simply scroll/jump back within reach of the bottom of either view yourself (`maybeReengageTailFollow()`, fired from that view's own scroll listener once `distFromBottom` drops back under the same `ROW_HEIGHT*1.5` threshold used to detect scrolling away) — so a native "jump to the last row" shortcut has the same effect as the button, not just a plain click on it. Programmatic scrolls (follow itself, jump-to-entry, node-switch reset) are distinguished from user scrolls via a timestamp (`lastProgrammaticScrollTs`, shared — every programmatic write goes through `setTableScroll()`/`setHighlightScroll()`) so they never trigger either transition themselves. Tail-driven re-renders route through `pendingTableScroll`/`pendingHighlightScroll` (`"bottom"` = follow, `"keep"` = preserve reading position) so `renderTable()`/`renderHighlightView()`'s normal reset-to-top never yanks either view during live updates; follow only moves a view when the file *behind the current view* grew. A panel hidden behind the other tab (`display:none`) can't actually scroll while hidden (`scrollHeight` collapses along with `clientHeight`) — `showFhTab()`/`applyFhView()` resync a panel to the bottom on becoming visible again if follow is still active, so switching back to it doesn't show a stale, un-followed position. See `tests/philogg.regression.test.js` Group 97.


## File loading: usable while it loads, progress on the real row

A file being read+parsed (`loadOneFileIntoTree`, shared by `loadFileDescriptors` for a plain "Open…"/drag-drop load and `loadFolderFile` for a watched-folder file — see below) used to block the whole app behind a full-screen `#progressOverlay` pop-up. That's long gone: the **real file node exists, and is fully interactive, from the instant loading starts** — before a single byte has even been read — with just a thin progress fill riding along on its own row until parsing finishes.

**`createFileNode(name, folderId)`** builds the node (`entries: []`, `loadFraction: 0`) and inserts it into `state.nodes`/`state.rootIds`/`state.activeId` synchronously, before any async work — so by the time `loadOneFileIntoTree`/`addFile` hits their first `await`, the row is already a normal, selectable, filterable tree row (click, drag, delete, right-click all work on it exactly like any loaded file), just with zero entries so far.

**Entries stream into `node.entries` during the parse** (`parseLogTextAsync(text, node, onProgress)` pushes each completed entry onto `node.entries`/`entryIndex` as soon as it's found, instead of building a private array and handing it all over once the whole file is parsed), but that growth is **not** reflected anywhere live while the load is in progress except the loading file's own tree row — its progress fill and entry count, and nothing else. This was a deliberate simplification, arrived at over several same-session iterations documented below; jump to "Current behavior" if you just need what's true today.

### Current behavior

A load-progress tick (`readFileWithProgress`'s byte-level `onprogress`, `parseLogTextAsync`'s per-`PARSE_CHUNK_LINES`-chunk `onProgress`) calls `scheduleLoadRender(rootId)`, which runs on **every single tick** — no throttle — and does exactly one direct DOM write and **never** a `render()` of any kind — active view or a file loading in the background, no distinction:

- **`updateLoadRowProgress(rootId)`** — direct DOM writes to JUST the loading file's own row: its `.tree-load-fill` width, and its `.tree-count` text. Nothing else — not a filter row already created under it, not the level bar, not the Filtered/Full/minimap view.

Never touches `#tree`'s structure (`el.innerHTML = ""` + rebuild, which `renderTree()` does), so a native click in flight on some OTHER row is never at risk of landing on a torn-down-and-recreated element mid-gesture. Also invalidates the loading file's (and its dependents') cached `getEntries()`/`getLevelCounts()` results on every tick (same reasoning as `onTailChange`'s own `invalidateCachesForRoots` call — a file node's `entries` growing mid-parse is exactly the kind of content change those caches don't otherwise know to distrust) — its only remaining job is keeping a mid-load click onto this file (which DOES trigger a real render) from seeing a cache stale enough to matter, since nothing per-tick reads it anymore. (A real-time throttle around this whole per-tick body was tried and removed again the same session — see "How it got here" below.)

**A filter created under a still-loading file freezes its row's displayed count at whatever it was when created** (or last touched by a real render) — it does NOT keep growing live as its parent streams in more matching entries, even though `getEntries(filterId)` itself (a live query) already reflects the parent's current data at any moment; only a real render (a click, switching away and back, …) repaints it with the current true count. Same story for the level bar: its counts freeze at whatever a real render last showed and do not tick upward as more matching entries stream in.

**The Filtered/Full/minimap view for the loading file (if it's the active view) simply doesn't update again until the load finishes** — `flushLoadRender(rootId)` (`invalidateCachesForRoots` + a real, full `render()`) runs only at the true structural moments of a load: `createFileNode` (the row appearing) and natural completion (the progress fill disappearing), never per-tick. Any unrelated action that calls `render()` anyway (a click, a filter edit, switching to a different already-loaded file and back) picks up the file's genuinely-current state at that moment, same as always — it's specifically the automatic per-tick refresh (of anything) that's gone.

### How it got here (same session, 2026-08-18 through 2026-08-28)

The very first version (2026-08-18) went the opposite direction — person-requested: *"die Datei, soweit geladen, direkt zu visualisieren und die Minimap fortlaufend zu befüllen... ähnlich wie eine Datei zu tailen"* (make the file directly usable as it loads, filling the minimap in continuously — like tailing). That version drove a live, tailing-style Filtered/Full/minimap update on every single tick, plus live level-bar counts and live filter-child row counts, then went through several rounds of fixing the DOM-identity fallout that caused (a full `render()`/`renderTree()`/`renderLevelBar()` on every tick tore down rows/buttons a person might be mid-click on — same class of bug as `renderVisibleRows()`/native `dblclick` in CLAUDE.md's "Known gotchas") and, later the same day, several rounds of performance tuning (rAF-coalescing, then a real-time throttle, then skipping the view's two most expensive per-tick scans entirely) once a large/fast load turned out to still be measurably slower with the live view on than with it off — even switching away to a different, already-loaded file mid-load (which always skipped the live update) felt faster. Real decoupling (parsing on a separate thread via a Web Worker, so a render genuinely couldn't block it) was considered and rejected as unrealistic for this codebase's shape: a single 15,000-line inline-script HTML file with no build tooling, no module system to split a worker script out of, and every parse/render function reaching into shared top-level state (`state`, `entryIndex`, DOM element references) a worker couldn't touch directly.

At that point the person's own preference won out over further incremental tuning: *"Baue die Visualisierung einfach aus. Der Ladebalken genügt mir beim Laden."* (just remove the visualization — the progress bar is enough). `scheduleLoadRender` was simplified to two per-tick DOM writes (the loading file's own row, and the level bar's counts), never a `render()`; the throttle, the rAF-coalescing, the per-tick main-view render function, and the flag that used to make `renderTable()` skip its two expensive scans during a tick were all removed outright as dead code.

That still left one more round: switching to a different, already-loaded file mid-load *still* felt noticeably faster than staying on the loading one, and the person suspected the still-live level-bar counts specifically — *"Liegt das daran, dass die Zähler für die Level... noch mitzählen? Nehme (außer dem Ladebalken selbst) (und vielleicht dem Zähler daneben) alle Visualisierungen des Ladevorgangs raus. Und auch Ladebalken etc. darf eine etwas reduzierte Updaterate bekommen."* The level-bar-counts function had no other caller by this point and was deleted outright (not just unhooked); the filter-subtree walk the row-update function used to do was dropped too, narrowing it to just the loading file's own row (renamed `updateLoadRowProgress`); and `scheduleLoadRender`'s remaining work gained a real-time throttle so even the one thing still updating live would do so at a reduced rate rather than on literally every chunk/byte tick.

That throttle didn't survive its own same-day follow-up: it turned out to make no noticeable difference (the level-bar/filter-subtree removal just above was what actually mattered) and looked visibly stuttery — *"nehme die 200ms wieder raus... Das scheint keinen merklichen Unterschied zu machen und sieht so etwas 'stockend' aus. das weglassen der anderen UI Updates hat schon genug gebracht."* Taken back out outright, landing on the unthrottled, single-row-only shape "Current behavior" above describes.

**The read phase** (`readFileWithProgress`, real `File` objects only — `loadOneFileIntoTree`) still runs before there's any text to parse, so it drives `node.loadFraction` across both phases with the pre-existing `READ_WEIGHT`/`PARSE_WEIGHT` split (0.55/0.45) on the SAME row the whole time — there's no separate placeholder to hand off from/to anymore. `addFile` (text already fully in memory — session-cache restore, embedded-log import) has no read phase, so it just creates the node and parses straight into it, no weighting needed (`loadFraction` is a plain 0..1 parse fraction). A load that fails (read or parse error) removes the empty node it created (`catch` → `deleteNode`) instead of leaving a permanently-empty file behind, mirroring the old ghost-row's guaranteed cleanup on error.

**Rendering**: `renderNode()` draws the progress fill (`.tree-load-track`/`.tree-load-fill`, a thin 2px bar pinned to the row's bottom edge — `.tree-row` is already `position:relative`) directly on a file row whenever `typeof node.loadFraction === "number"`, alongside all its normal interactive chrome (swatch spacer, icon, label, count, delete button, click/drag handlers) — it's not a special row shape anymore, just an extra element on the same one. `renderFolderSection()` (watched-folder files) finds a still-loading root node by `(folderId, name)` among `state.rootIds` as a fallback when `rec.nodeId` isn't linked yet (that only happens once `loadFolderFile`'s own `await` resolves, well after the node itself already exists), so the real, progress-carrying row appears in place of that file's grayed `.folder-watch-file` placeholder immediately, not just once loading finishes.

**Test coverage**: `tests/philogg.regression.test.js` Group 48b/48c cover the row-identity/interactivity side — the real (not a placeholder) row exists and is clickable the instant loading starts, carries the progress fill, and the fill disappears once loading finishes, for both a plain load and a watched-folder file (via the by-name fallback, since `rec.nodeId` isn't linked yet at that point). Group 49 covers a real, EXPLICIT `render()` mid-parse (not an automatic tick): entries/tree-row-count/level-bar-counts all reflecting a genuinely mid-parse state (not zero, not the final total) on a 9000-line file forced across multiple `PARSE_CHUNK_LINES` chunks; level-bar counts being correct again once loading finishes; and the Filtered view not auto-scrolling to chase the growing content. Group 50 covers the current per-tick shape directly: `render()` mocked to count calls, proving zero `render()` calls ever, active view or background; the loading file's own row updates on every single tick, matching the live data exactly each time; the Filtered view's actual painted DOM (`#tableSpacer`'s height) stays stale throughout, never auto-refreshed; and the row's count reaches the true final total only once the load's natural-completion render runs (re-queried fresh, since that render rebuilds the row's own DOM element). Group 51 covers the tree-identity guarantee (now unconditional, not just active-view-specific): `renderTree()`/`render()` both mocked to count calls, proving zero of either across several real parse ticks while the loading file IS the active view; a different, already-loaded row's DOM element captured right after the one legitimate structural rebuild (the loading file's own creation) stays the exact same object through every subsequent tick; and — the strongest proof — a real click dispatched on that held reference still switches to it. Group 52 covers that level-filter buttons and filter creation stay usable (never blocked, never torn down mid-load) despite NEITHER auto-updating live anymore: `renderLevelBar()` mocked to count calls, proving zero calls across several real parse ticks while its `.cnt` text stays frozen at its last-real-render value (a real render — the click itself — DOES show the true current count immediately after, proving the staleness is specifically about automatic per-tick updates) and a click on the SAME held button reference still correctly toggles the level filter; a filter created mid-load has its own row's displayed count also stay frozen across further ticks even though its live-queried match count (`getEntries()`) has genuinely grown past it.

### Multi-file load: grayed queued placeholders + merge-on-load prompt

Person-requested, this session (2026-08-20, German): dropping/picking several files at once used to only ever show the file currently being read — the next one only appeared once its own turn to load arrived, so a 5-file drop looked like files trickling in one at a time with no visibility into what was still queued.

**`createQueuedFileNode(name)`** builds a lightweight placeholder file node (`queued: true`, empty `entries`) and inserts it into `state.rootIds` immediately — but, unlike `createFileNode`, does **not** set `state.activeId` or render: a placeholder can't be selected or filtered yet, so landing on/showing one would be actively confusing. `loadFileDescriptors` now creates one placeholder per file in the batch, in order, and calls `render()` once — so every file's eventual tree position is visible right away, before any reading starts. `renderNode()` special-cases a `queued` file node (checked first thing, before building the normal interactive row) into `renderQueuedFileRow()`: a non-interactive row — no click/drag/context-menu handlers at all, since there's nothing yet to act on — styled with the new `.tree-row-queued` CSS class, deliberately mirroring folder watch's own grayed `.folder-watch-file` look (`opacity:.55`, same tertiary text color) since it's the same "known its spot, not read yet" idea, just living directly in the main tree instead of a separate box. `flattenTreeIds()` (arrow-key tree navigation) skips queued nodes for the same reason — nothing there to land on.

**`activateQueuedFileNode(node)`** is the counterpart: clears `.queued`, sets `loadFraction = 0`, sets `state.activeId`, and calls `flushLoadRender()` — the exact "insert into the active view" job `createFileNode` normally does itself. `loadOneFileIntoTree` gained an optional 5th `existingNode` parameter: when given a queued placeholder, it calls `activateQueuedFileNode` on it and reuses it instead of calling `createFileNode` fresh — so the SAME node object flips from grayed to a normal, actively-loading row (progress fill and all — see "File loading" above) exactly when `loadFileDescriptors`' loop reaches it. `loadFolderFile` (folder watch) doesn't pass `existingNode`, so its own already-established grayed-listing mechanism (a *different* placeholder shape, `folder.files` records rather than `state.nodes` entries — see "Folder watch" below) is completely unaffected.

**Merge-on-load prompt** (second half of the same request): loading 2+ files in one batch now asks upfront, via a small promise-based dialog (`confirmMergeOnLoad`/`#mergeLoadDialog`, modeled on the existing `sessionMatchDialog` promise pattern), whether to merge them into one chronologically-sorted file (`mergeFiles` — see "File merge follows the same load-progress pattern" below) once they're all loaded. The dialog opens right after the placeholders render (before any file is actually read), so answering it doesn't block the grayed rows from showing — only the actual reading waits on the answer. The "Merge" button is focused the instant the dialog opens, so **Enter answers Yes for free** via the browser's own default button-activation behavior (a focused `<button>` responds to Enter/Space natively — no custom keydown code needed); **Escape answers No** via the existing global `Escape` keydown handler (`if (mergeLoadResolver) closeMergeLoadDialog(false);`, same pattern as `sessionMatchResolver`). A single-file load never shows this dialog at all (`descs.length > 1` gate) — matches the request's own scope ("mehrere Dateien gleichzeitig"). `loadFileDescriptors` `await`s `mergeFiles` before its own promise resolves, so callers (including the test suite) see the merged node only once it's actually finished.

**Resilience fix, needed for the above to actually work**: `loadFileDescriptors`' per-file `await` used to have no error handling at all — one file's read/parse failure threw out of the whole `for` loop, silently abandoning every file queued after it (invisible before this session, since nothing was visibly queued yet; now that every later file has a grayed placeholder on screen, an unhandled throw would leave it stuck grayed forever). Each iteration is now individually `try`/`catch`ed — a failure shows a toast (`Couldn't load "name"`, same wording style as `loadFolderFile`'s own failure toast) and the loop continues to the next file; `loadOneFileIntoTree`'s own existing `catch` (deletes the half-created node) still runs first, so the failed placeholder disappears rather than staying grayed.

### File merge follows the same load-progress pattern

Person-requested, same session, immediate follow-up: *"Für ein File Merge folge der gleichen Logik. Lege den Eintrag zuerst an und Zeige den Fortschritt des Merge an diesem Eintrag."* — `mergeFiles` used to build the whole merged `entries` array synchronously in one blocking call (`flatMap` + `sort`) before the node ever existed in the tree; for several very large files that could freeze the UI for a noticeable moment with nothing on screen to explain why. It's now `async` and follows the exact same "insert the row first, stream progress onto it" shape `createFileNode`/`loadOneFileIntoTree` established for a real file load (see "File loading" above):

- The merged node (`merged: true`, empty `entries`, `loadFraction: 0`) is inserted into `state.nodes`/`state.rootIds` and made the active view immediately, via `flushLoadRender()` — a real, fully interactive tree row (same `ICON_MERGE` icon, same click/drag/delete) from the instant merging starts, just like a freshly-opened file's row.
- Entries are copied from every source file in `MERGE_CHUNK_ENTRIES`-sized chunks (20,000), pushed directly onto `node.entries` (so the row's own count grows live during this phase, same idea as `parseLogTextAsync`'s streaming append), with `node.loadFraction` advancing across `MERGE_COPY_WEIGHT` (0.6) and `scheduleLoadRender(node.id)`/a `setTimeout(0)` yield after each chunk — mirrors `READ_WEIGHT`/`PARSE_WEIGHT`'s role for a real load's two phases.
- The final chronological sort (`node.entries.sort(...)`) isn't itself chunkable, so it runs as one blocking call covering the remaining `MERGE_SORT_WEIGHT` (0.4) — but only after the copy phase's last progress tick has already had a chance to paint, thanks to that phase's own trailing yield.
- `flushLoadRender(node.id)` clears `loadFraction` and does a real, full render once sorting finishes, same as a real load's natural-completion step; a `state.nodes[node.id] !== node` guard (mirroring `loadOneFileIntoTree`'s own) handles the node being deleted mid-merge.

**Call sites**: `performBulkAction`'s "Merge N files" action and `loadFileDescriptors`' merge-on-load path (above) both call `mergeFiles` — the former fire-and-forget (its own synchronous prefix already inserted the row by the time `performBulkAction` returns and calls its own `render()`), the latter `await`ed so the batch's own promise doesn't resolve until the merge is genuinely done. `persistFileNode`/entry-reuse-by-reference semantics are unchanged from before this session.

**Test coverage**: `tests/philogg.regression.test.js` Group 69 — the merged row exists as a real, interactive, progress-carrying row (not the grayed queued-placeholder row multi-file *loads* use) the instant `mergeFiles` is called, before any chunk has finished copying; `loadFraction`/the progress fill are gone once merging completes; the final result is in correct chronological order (an earlier-timestamped source file's entries sort to the front, not just appear in call order) with the right total count. The two pre-existing direct `mergeFiles()` callers in the suite (Groups 10 and 30c, originally synchronous) were updated to `await` it.

**Test coverage**: `tests/philogg.regression.test.js` Group 68 — 68a: a 3-file batch shows all 3 as grayed placeholders (in order) with zero real rows before the merge dialog is answered, `#mergeLoadDialog` open with its Merge button focused, Escape closing it and each placeholder flipping to a real loading row in turn as the batch actually processes, and no merged file at the end. 68b: answering Yes (click) produces a merged file node once both sources finish loading, sources kept (same as the manual bulk action). 68c: a single-file load never opens the dialog. 68d: one file that fails to read (a non-Blob object forcing `FileReader.readAsText` to throw synchronously) doesn't stop a second, valid file in the same batch from loading, and produces a toast naming the failed file.

## Deep-link loading (`?url=`)

`philogg.html?url=<encoded-url>` fetches a log at boot and opens it, straight into `addFile` — the same path a session-cache restore uses (text already fully in memory, no separate read phase). `loadFromUrlParam()` (next to `loadFileDescriptors`, "File loading & progress" above) parses `location.search`, `fetch()`s the URL, derives the tree row's name from the URL's last path segment (falls back to `"remote.log"`), and calls `addFile(name, text)` + `render()`. If the url is the desktop wrapper's own `philogg://local/…` scheme, `loadUrlIntoTree` also wires up a live `node.tail` so the file gets polled/tailed like any other locally-opened file — see "Tailing (live file updates)" above.

Two consumers this is meant for: a CI/report link straight to a build's log artifact on a webserver, and the desktop wrapper (`docs/desktop.md`), which reads a local file natively (no browser-gesture requirement) and serves it through a `philogg://` URL, reusing this exact mechanism instead of building a second, separate content-injection path.

**Requires PhiLogg itself to be served over `http(s)`** — a `file://` page can't `fetch()` anything at all, cross-origin or not (Chromium's own restriction, nothing PhiLogg can work around). `loadFromUrlParam()` checks `location.protocol` first and shows a dedicated toast instead of a confusing raw fetch error in that case. A remote log server also needs to answer with CORS headers (or be same-origin) — same browser rule as any other cross-origin `fetch()`, not something worth trying to route around.

Errors (network/CORS failure, non-2xx HTTP status) show a toast (`showCopyToast`) and add no file, instead of failing silently.

**Test coverage**: `tests/philogg.regression.test.js` Group 66 — successful load (name derived from the URL, text parsed into entries), an HTTP error status, and a rejected fetch (network/CORS), each via a fake `window.fetch` (jsdom ships none). The `file:` protocol guard itself has no jsdom coverage — jsdom treats every `file:` URL as an opaque origin and throws on the app's own boot-time `localStorage` access before `loadFromUrlParam` ever runs, for any URL shape (see `tests/README.md`'s "Known gaps") — verified instead with a real Chromium session (Playwright) against a local static server: a same-origin `?url=` load rendering the file, and an unreachable URL producing the expected error toast with zero tree rows.


## Folder watch + lazy loading

FEATURE_BACKLOG.md item, built in two rounds this session (2026-08-16): the initial build, then a person-reported follow-up in the same session covering four refinements — a unified "Open…" menu, files rendered *inside* the folder listing instead of moved out below it, a browser-capability gate, and session-cache persistence. All four are folded into the description below rather than kept as a separate "what changed" appendix.

**Entry points**: pick a whole folder via the **"Open…"** button's dropdown menu (**File(s)…** / **Folder…** — replaced two separate always-visible buttons, since the browser-support asymmetry between them, see below, made two equally-prominent buttons misleading) or drag&drop (a dropped folder resolves to a `FileSystemDirectoryHandle` via `getAsFileSystemHandle()`, same as the single-file drop path already used). Under a desktop wrapper that can list directories itself, both entry points go through the wrapper instead — `philogg.pickFolder()` for the menu item, the wrapper's own native drop for the other (see "Two kinds of directory handle" below).

**Support is checked once, upfront, not tried-and-caught per attempt**: `FOLDER_WATCH_SUPPORTED = !!window.showDirectoryPicker || FOLDER_WATCH_NATIVE`, computed at script init (`FOLDER_WATCH_NATIVE` = a desktop wrapper exposing `philogg.listFolder`). Unlike single-file loading (which has a real, fully-working fallback — the hidden `<input>`), there is **no meaningful fallback for folder watching**: without a live directory handle there's no way to list or re-scan a folder's contents at all, so a browser without the File System Access API (Firefox/Zen today) gets a clear popup instead of a silently degraded experience:
- The **"Folder…"** menu item, clicked without support, shows `showCopyToast(FOLDER_WATCH_UNSUPPORTED_MSG)` instead of opening anything.
- A dropped **folder** without support is actively *detected* — via `webkitGetAsEntry()`, which (unlike `getAsFileSystemHandle`) Firefox does implement — specifically so it can show the same popup instead of being silently misread as an empty/broken file list (which is what plain `dt.files` gives you for a dropped directory in a browser without the newer API). A dropped plain *file* is completely unaffected either way.

**Two kinds of directory handle.** The API above is a *webview engine* API and obeys the engine's rules, which is a real limit and not a theoretical one: Chromium refuses a handle for any directory on its hardcoded sensitive list ("this folder contains system files" — Desktop and Downloads among them), and no embedder can switch that off; WebKit-based webviews don't implement the API at all. So a desktop wrapper that can list a directory natively is used in preference to it: `nativeDirHandle(path, name)` (defined next to `urlTailHandle`) is a duck-typed stand-in over `window.philogg.listFolder`, implementing exactly the four members this feature uses — `name`, `values()`, `queryPermission()`, `requestPermission()` — so everything below is written against one shape and never branches on which kind it holds. Its `queryPermission()` is a constant `"granted"` (a native listing has no permission model), and each entry it yields *is* a `urlTailHandle` carrying the file's real path, which is why a file opened from such a folder tails, reveals and copies its path like any other. Only persistence has to tell the two apart — see below. The desktop wrapper provides the native route (`docs/desktop.md`); every browser build takes the `showDirectoryPicker()` one and inherits the engine's blocklist.

**Data model**: `state.folders`, a list of `{ id, name, handle, files: [{ name, relPath, handle, nodeId }], busy, failed, needsPermission, settings }`. `handle` is either a real `FileSystemDirectoryHandle` or a `nativeDirHandle` stand-in with the same four members (above), and a file record's `handle` correspondingly either a `FileSystemFileHandle` or a `urlTailHandle`. `folder.id` doubles as the persistent IndexedDB key for the folder (see "Persistence" below) — generated via the same `newCacheKey()` file nodes already use, not a throwaway `uid()`, specifically so it's stable across a reload. A file record's `nodeId` is `null` while it's still a grayed, unopened listing entry, set once it's been opened into a real `state.nodes` file node (tagged `node.folderId` with that same folder id). `relPath` is the file's path relative to the watched folder's own root (equal to `name` for a file directly in it); `folderFileKey(rec)` (`relPath || name`) is the merge identity used everywhere two scans need to be matched up, so same-named files in different subfolders don't collide. `settings` (`defaultFolderSettings()`) holds this folder's own configuration — see "Per-folder settings" below.

**Scanning**: `scanFolderHandle(dirHandle, settings)` reads directory *entries* (`dirHandle.values()`) and filters by BOTH `isCompatibleFolderFile()` (currently `[".log"]`, `FOLDER_WATCH_EXTENSIONS` — an array so a future "pluggable parser" session has one obvious place to widen it) and the folder's own configured filename patterns (below) — it never reads a file's *content*. Nothing is parsed until a person actually opens one. Non-recursive by default, matching the backlog's original "list them" scope; recurses into subdirectories only when `settings.includeSubfolders` is set (walking any entry whose `values()` exists — a no-op under the desktop wrapper's native listing, which is a flat, non-recursive `read_dir`, see `docs/desktop.md`). `mergeScannedFiles(folder, scanned)` folds a fresh scan into `folder.files`, preserving each already-known entry's `nodeId` (and therefore its identity as a real vs. grayed row) while refreshing its `handle` — the one shared implementation behind the initial scan (`addWatchedFolder`→`rescanFolder`), `folderScanTick`'s repeat polls, and a restored folder's reconnect scan. An entry that no longer appears in a fresh scan — deleted on disk, or (closed only) simply stopped matching a pattern — is dropped from the listing entirely; an *open* one is closed first (`closeFolderFile`, same teardown as the person closing it by hand) so its node doesn't leak once nothing points at it anymore (person-reported fix: a file deleted outside the app used to linger in the listing forever once it had been opened). For a natively listed folder it also refreshes an open file's `sourceUrl`/`localPath` from the scan (`applyFolderFileLocation`, also called by `loadFolderFile`): the id in a wrapper's `philogg://local/<id>/…` URL is per-*process*, so a session restored from cache holds dead URLs until the first rescan re-registers each file. Every merge finishes by (awaiting) `applyFolderAutoRules(folder)` — see "Per-folder settings" below.

**Per-folder settings** (gear icon, `.folder-watch-settings`, on each folder's header — `openFolderWatchSettingsDialog`/`#folderWatchSettingsDialog`, styled with the same `settings-page-card`/`settings-row`/`settings-switch` classes as the app-wide Settings dialog, just scoped to one folder and without its section nav): **filename patterns** (`settings.patterns`, a list of `{ pattern, autoOpenNewest, autoCloseKeep, showNewest }`, default one `{ pattern: "*" }`) — a file must match at least one pattern's glob (`getCompiledGlob`, the same engine "Log Formats"' filename rules use) to be listed at all, on top of the fixed extension filter; `matchFolderPattern()` resolves a file to its first matching pattern, first-match-wins like the format rules. Each pattern carries its own three auto rules, applied by `applyFolderAutoRules()` after every merge, per pattern, in this order: (1) **"Show M newest files"** drops *closed* listing entries older than the M most recent matches (an open file is never dropped); (2) **"Auto-close — keep only N open"** is a **sliding window** over the N newest matches — it opens (via `loadFolderFile(folder, rec, true)`, awaited) whichever of those N aren't open yet and haven't already been auto-opened once (`rec.autoOpenFired`, see below), then closes (via `closeFolderFile`, stays listed grayed out, not removed) any currently-open match that fell out of the window **and was itself opened by an earlier auto rule** (`rec.openedByAuto`) — a file the person opened by hand is never auto-closed, regardless of the window. Fixed a person-reported bug: a naive "just close the oldest once too many are open" never opened the newer file that pushed the count over N in the first place — a new file arriving must itself become one of the N open ones, evicting the previous oldest, not leave the open set unchanged. (3) **"Auto-open newest file"** is the plain one-file version of the same idea for a pattern with no keep-N configured — opens the newest match if it isn't open yet and hasn't already been auto-opened once, without touching any other open file (skipped when keep-N is also set on that pattern, since its window already includes the newest). "Newest" (`sortFolderRecsByRecency`) uses each file's real `lastModified` (mtime) when it's known, falling back to name order only when it isn't — fixed a second person-reported bug: a pure filename-order heuristic silently mis-picked "newest" for any naming scheme where a chronologically newer file doesn't happen to sort last as a plain string (unpadded day-of-month, a rotated-log scheme where the *active* file has the smallest name, etc.). `scanFolderHandle` fetches each matching file's `file.lastModified` via one extra `getFile()` per file — gated behind `folderSettingsNeedRecency()` so a folder with no auto rules configured pays nothing extra on its 3s poll — and `mergeScannedFiles` carries it across rescans like `relPath`. mtime is **not** available for a natively listed folder's files (desktop wrapper — `urlTailHandle.getFile()` returns a plain fetched `Blob`, which has no `lastModified`; see `docs/desktop.md`), which is why the name-order fallback still matters rather than assuming mtime always works; the folder listing's own display order (`mergeScannedFiles`) stays name-sorted regardless — this only changes which file the *rules* treat as newest. Folder-wide: **include subfolders** (`settings.includeSubfolders`, drives the recursive scan above) and **show relative path** (`settings.showRelativePath`, only surfaced once subfolders are included — shows e.g. `sub/App.log` instead of `App.log` in the grayed listing, `renderInactiveFileRow`). Every change in the dialog re-persists the folder and re-scans immediately (`commitFolderWatchSettings`) — no separate Save button, same immediacy as the rest of Settings.

**Auto-open/auto-close act on a file at most once each way** (person-reported): `rec.autoOpenFired` is a permanent flag set the first (and only) time either auto rule opens a given file's record — a person who closes that file again is left closed on every later rescan/poll instead of having it silently reopen. `rec.openedByAuto` records whether the file's *current* open came from an auto rule (`true`) or a person double-clicking/context-menuing it themselves (`false`, the default `loadFolderFile(folder, rec)` call with no third argument) — it both drives "auto-close — keep only N open" (above, never closes a manually opened file) and an auto-opened file's tree row: its icon swaps to `ICON_FILE_AUTO` (the same file glyph with a small circled "A" badge) with a tooltip noting it was opened automatically, so the two ways a folder-watch file ends up open read differently at a glance.

**UI — files render IN THE FOLDER, in folder order, not moved out below it** (person-reported follow-up; the initial build rendered opened files as ordinary root nodes under `#tree` and only kept not-yet-opened ones in the folder box, which lost the file's position in the folder once opened). `renderFolderSection()` now walks `folder.files` **in order** and, per entry, renders either a real `.tree-row` (`renderNode(rec.nodeId, 0, { folderTopLevelNoChevron: true, autoOpened: rec.openedByAuto })`, for an opened file — filters and all) or a grayed `.folder-watch-file` row (`renderInactiveFileRow`, for an unopened one) into the *same* `.folder-watch-files` list — so a file's spot in the folder stays visible whether it's open or not, and opening/closing it never reorders anything. The `folderTopLevelNoChevron` option (person-reported: an opened file used to read as more indented than its still-closed siblings) makes `renderNode` use the closed rows' flat 12px inset instead of the normal 8px-plus-chevron-slot one, and skip reserving the chevron slot at all when the file has no filters of its own to collapse. The "still loading" fallback that finds a not-yet-linked file's own progress-carrying row (`rec.nodeId` not set yet, but its node already exists — see "Rendering" above) matches by folder+name alone now, not additionally requiring `typeof loadFraction === "number"`: gating on that left a one-render gap, between `loadOneFileIntoTree` clearing `loadFraction` and `loadFolderFile` (its caller) setting `rec.nodeId` on the very next line, where the file briefly fell through to the closed/grayed placeholder (person-reported: "loading → indented open → briefly grayed → open" instead of a clean "loading → open"). `renderTree()` correspondingly **skips** any root id whose node has a `folderId` when building the plain top-level list — those render exclusively inside their folder's own section now. The header still shows a pulsing "ping" ring (`.folder-watch-icon.scanning`, `@keyframes folder-scan-ping`) while the folder is being actively polled, and a ✕ to stop watching (`removeWatchedFolder`).

**Double-click, or a grayed row's own right-click → "Load file"** (`openFolderFileContextMenu`, a minimal one-item menu reusing `#treeContextMenu`, distinguished by `folderCtxTarget` instead of `treeCtxId`) calls `loadFolderFile()`, which reads+parses the file (`loadOneFileIntoTree()` — the read/parse/persist/history/tail-wiring body `loadFileDescriptors` shares with this entry point) and turns it into a **completely normal root file node**, tagged `node.folderId`. It behaves exactly like any manually opened file from there — build filters on it with Ctrl+F — and, since it was opened via a real handle, starts **tailing automatically** for free.

**"No filter can be created on / copied onto an inactive file" holds by construction, not by an extra guard**: a grayed listing row is never a `state.nodes` entry and is rendered by entirely separate DOM/CSS (`.folder-watch-file`, no `draggable`, no `dragover`/`drop` listeners, no click handler that sets `state.activeId`) from a real `.tree-row` — so there is no node id Ctrl+F/paste/drag-and-drop could ever target. Nothing had to be special-cased in `openFilterPopup`/`pasteClipboard`/the tree's drag handlers.

**Closing a folder-loaded file doesn't remove it — it goes back to grayed, in the same spot.** `deleteFilterNodeWithUndo()` special-cases any file node with `node.folderId` into `closeFolderFile()`: the node and its whole filter subtree are torn down exactly like a normal close (`deleteNode` — entries released from `entryIndex`, cache invalidated, `cacheDeleteFile` fires), but the folder's own file record just has its `nodeId` cleared back to `null` instead of being removed from `folder.files` — so it reappears in its original position in the folder's file order (same handle reused, reopening needs no re-scan) instead of disappearing or getting appended at the end. A plain file with no `folderId` is completely unaffected. `removeWatchedFolder()` (the folder's own ✕) clears `folderId` off any currently-open files from that folder first, so they become plain independent files (rendered back under the plain `#tree` list, a later close on them is then a normal full removal) before dropping the folder record and its persisted store entry (`cacheDeleteFolder`).

**New-file detection**: `folderScanTick()` polls every actively-watched folder (`handle` present, not busy, not `needsPermission`, not `failed`) every `FOLDER_SCAN_MS` (3000ms — same handle-polling shape as `tailTick`/`TAIL_POLL_MS`, one level up) via `mergeScannedFiles`. Removed files ARE detected now (see "Scanning" above — `mergeScannedFiles` drops/closes any listing entry a fresh scan no longer finds, open or not); opening a since-deleted grayed entry that a poll hasn't caught up to yet surfaces a toast instead of crashing. A read/permission failure sets `folder.failed` (stops the scanning ping) rather than throwing, same graceful-degradation shape as a tailed file's own `tail.failed`.

**Persistence — a watched folder now survives a reload** (person-reported follow-up: "currently no reload survives folder watch"). The mechanism relies on a real, spec-guaranteed fact: a `FileSystemHandle` is designed to survive IndexedDB's structured clone algorithm — that's the actual, standard way browsers let a handle outlive a page reload at all, no different in kind from how the pre-existing tail-handle mechanism already trusted `FileSystemFileHandle` objects to keep working across `getFile()` calls. `persistFolder(folder)` stores `{ key: folder.id, name, handle, path, settings }` in a `folders` IndexedDB object store (`CACHE_DB_VERSION` 2→3); `cacheDeleteFolder` removes it when the folder is dropped. A `nativeDirHandle` is the one thing that can't go in as-is — it holds a closure, and structured clone rejects the whole record (the same `DataCloneError` trap the `urlTailHandle` cache bug fell into) — so for one of those the `path` is stored and `handle` is `null`, and `restoreWatchedFolders` rebuilds the stand-in from it. That loses nothing: unlike a handle, a path stays valid across a restart with no permission to re-grant, so such a folder resumes silently and never reaches the Reconnect state below. Each file's own record in the existing `files` store gained a `folderId` field (written by `persistFileNode`, read back by `restoreSessionFromCache`) so an already-open file re-links to its folder by that shared, stable id after a reload.

Boot sequence: `restoreSessionFromCache()` (files, filters, bookmarks, settings — unchanged) runs first, so any restored file's `node.folderId` is already set by the time `restoreWatchedFolders()` runs right after. That function re-registers each stored folder (`needsPermission: true` to start, seeding `folder.files` with whatever already-restored nodes point at it) and calls `folder.handle.queryPermission({ mode: "read" })` — **no user gesture required** for a *query*, only for a *request*. If the browser still considers it granted, `tryReconnectFolder` flips `needsPermission` off and rescans immediately: watching resumes with no visible interruption, and `mergeScannedFiles` **reattaches a fresh tail handle** to any already-open file that doesn't have one yet (a restored folder-owned node never does — see "Tailing (live file updates)"'s note on `tryReattachFileTail` being deliberately skipped for `node.folderId` files, since a reconnected folder handle already makes reattachment possible for free for exactly the files it owns; the reattachment here is guarded on `!node.tail` so it never touches a node that's already tailing). If permission was **not** silently re-granted (typically after an actual browser restart, not just a tab reload), the folder renders with a lock icon and a **Reconnect** button instead of the scanning ring — `reconnectFolder()`, the button's click handler, is the one place `requestPermission()` is called, since that method's browser-side prompt requires an actual click to invoke at all.

## Filter save / load (JSON files)

Right-click a filter → **"Save filter…"** writes a `.json` file via `showSaveFilePicker` (download-link fallback where that API is missing); right-click any node (filter or file) → **"Load filter…"** reads one back via `showOpenFilePicker` (hidden `<input>` fallback), inserting the result at the clicked node. `serializeFilterBranch()` / `importFilterJson()` do the actual work; format is `{ format: "philogg-filters", version, activeRef, roots: [...] }`, `FILTER_FILE_VERSION = 2`.

**What gets saved is now a general choice, for ANY filter node** (`serializeFilterBranch(nodeId, includeAncestors)`, asked via `openExportScopePrompt` — see `docs/filters.md`'s "Export/library" section for the full picture): **"just this filter"** (`includeAncestors=false`) exports exactly the one clicked node, no ancestors, no subtree; **"include ancestor chain"** (`includeAncestors=true`) exports its ancestor chain from just below the root file, plus its own full subtree — today's original default shape. The scope question is general rather than and/or/link-specific because `bakedA`/`bakedB` are flat, self-contained data (see `docs/filters.md`'s "Self-contained AND/OR/LINK") — a combiner's two sides travel inside the node itself, so there is never anything external to optionally pull in alongside it.

**and/or/link nodes and their `bakedA`/`bakedB`**: both scopes above carry `bakedA`/`bakedB` along as a plain field copy — no ref/remapping machinery, since there's no node-id inside them. For "just this filter" this is what makes an and/or/link node's export already fully self-contained with nothing else to bring along.

**Import always attaches at the current target, never FILE**: every exported root is tagged `attach: "target"`; `materializeSerializedRoots`'s `resolveParentId` resolves it to wherever "Load filter…"/"Apply from library…" was invoked (`loadFilterTargetId`) — true for both scopes, and for both an ordinary filter and an and/or/link node.

**Loading onto a different tree re-evaluates, it doesn't replay a stored result**: nothing beyond the filter *definitions* (type/value/inverted, `linkDirection`/`linkN`/`linkOrderEnforced`/`linkExclusive`, `contextBefore`/`After`, `bakedA`/`bakedB`) is written to the file — every load creates fresh nodes with new uids, and `getEntries()` is always computed lazily against whichever file the reconstructed chain now structurally sits under. So an `and`/`or`/`link` filter loaded onto a different file (or a different point in the same file) is re-applied against that destination's own data, not the source file's original computed entries — its own `bakedA`/`bakedB` predicates are unaffected by any of this, since they never referenced the source file to begin with.

**Known gap**: loading never checks whether the destination already has an equivalent branch — every load creates a fresh, independent copy, so loading the same file twice (or onto a tree that already has a matching chain) produces visible duplicates. No dedup/merge-with-existing-branch logic exists; flagged as a possible future addition, not built.

**Person-reported bugfix, this session**: `#exportScopeDialog` (the "Just this filter"/"Include ancestor chain" prompt above) had no CSS at all — no `.hidden{display:none}`, no fixed-overlay positioning — so it rendered as a permanently-visible inline block wherever it fell in the document instead of a proper modal. Every save/export action that goes through `openExportScopePrompt()` — Save filter to file AND "Save to library…" below — awaits that prompt's promise, which only resolves on a click on one of its two buttons; with the dialog not actually reachable as a modal, that click never happened in practice, so the promise hung forever and the save silently never completed. Fixed by giving `#exportScopeDialog` the same `position:fixed; inset:0; z-index:75` + `.hidden{display:none}` treatment every other dialog already has — no logic change was needed here or in "Reusable filter library" below.

## Reusable filter library (`FEATURE_BACKLOG.md`)

Named presets, applied to **any** file in one click — the global counterpart to the per-file filter history below (see "File filter history"), and explicitly scoped simpler per the backlog item's own wording: no content-fingerprint matching, the person just picks where a preset applies. A filter node's context menu gains **"Save to library…"** (opens `#filterLibrarySaveDialog`, a small name-prompt modal pre-filled with the node's own name); every node's context menu (file or filter, mirroring where "Load filter…" already appears) gains **"Apply from library…"** (opens `#filterLibraryDialog`, a list of saved presets each with its own Apply/delete button).

**Storage**: a fourth IndexedDB object store, `filterLibrary`, in the same `philogg-session-cache` DB (`CACHE_DB_VERSION` bumped 3→4). Keyed by a random id (`newFilterLibraryKey()`), unlike `fileHistory`'s content-fingerprint key — there's no file to fingerprint here, the whole point is that a preset is file-agnostic. `saveFilterToLibrary` shows the same general "just this filter" vs. "include ancestor chain" prompt Save/Load JSON does before serializing. A record is `{ key, name, savedAt, roots, activeRef }`, where `roots`/`activeRef` are **exactly `serializeFilterBranch()`'s own output shape** — the same `includeAncestors` choice "Filter save / load" above already established is reused unchanged, just written to IndexedDB instead of a `.json` file.

**Applying reuses `importFilterJson()` unchanged**: `applyFilterFromLibrary(targetId, record)` sets `loadFilterTargetId = targetId` (the same module-level handoff `loadFilterFromFile` uses) and calls `importFilterJson(JSON.stringify({ format: FILTER_FILE_FORMAT, version: FILTER_FILE_VERSION, activeRef: record.activeRef, roots: record.roots }))` — wrapping the stored branch back into the exact envelope a `.json` filter file already has. This means applying a library preset gets every guarantee "Filter save / load" already documents **for free**: fresh uids every time (the same preset can be applied repeatedly without conflict), `bakedA`/`bakedB` copied through as plain data with no ref-resolution step, always attaching at the current target (never FILE), and — the important one for a preset meant to travel between files — **re-evaluated against whichever file it lands on now, never a replayed stored result**. No separate apply/materialize code path was written at all.

**Deliberately no dedup/matching logic** (unlike the per-file filter history's tiered fingerprint matching) — the backlog item scoped this explicitly simpler: "storage tier and matching rules would be much simpler (no content fingerprinting — the person picks)". Deleting a saved preset (`deleteFilterLibraryEntry`) is immediate, no confirmation dialog — consistent with the rest of the app's undo-first-not-confirm-first convention (filter node deletion, bookmark deletion, etc. all work the same way; a preset is easy to re-save if deleted by mistake, and low-stakes since it's a saved definition, not live data).

Regression-tested: **Group 59** — 59a (context menu → naming dialog, pre-filled name, blank-name no-op, the saved record's shape); 59b (applying onto a DIFFERENT, previously-untouched file — fresh uid, same filter definition, re-evaluated against that file's own data rather than the source file's; delete-from-library, both the dialog's own re-render and the actual IndexedDB record); 59c (persistence across a simulated reload — a separate store from the session cache's own `meta` record, readable with zero files loaded and no boot-time restore wait unlike `restoreSessionFromCache`).

## Session cache (survives a browser reload)

The working session — loaded files, the complete filter tree per file, bookmarks, and a small set of view settings (level quick-filter, column sort, active node) — is persisted automatically and restored on the next page load. No user action required; a "Session restored" toast confirms it happened. Theme and the Context/Filtered/Stacked layout preference already lived in `localStorage` before this feature and stay there (display preferences, not session data).

**Storage**: IndexedDB (`localStorage`'s ~5 MB quota is far too small for log files), DB `philogg-session-cache` (`CACHE_DB_VERSION`, bumped as stores were added). `files` holds one record per root file — keyed by `node.cacheKey`, a random id assigned at file creation, because runtime node ids are fresh uids every load and can't key anything persistent. The stored text is **rebuilt from the parsed entries** (`rebuildFileText`: `entries.map(e => e.raw).join("\n")` — `raw` accumulates continuation lines, so multi-line stack traces round-trip; blank lines and pre-header junk the original parse already dropped are the only loss, and re-parsing the rebuilt text is a fixed point) and, since the "Folder watch" feature, also carries a `folderId` field for re-linking to a watched folder on restore. `meta` holds a single `"session"` record: file order, serialized filter trees, bookmarks, settings. `fileHistory` is the separate per-file filter-memory store (see "File filter history" below). `folders` stores watched folders (see "Folder watch + lazy loading" above) — either the directory handle itself, since a `FileSystemHandle`, unlike the plain-data records the other three stores hold, is specced to survive IndexedDB's structured clone with its methods intact (the whole mechanism that lets a browser-picked folder resume after a reload at all), or, for a natively listed folder, its path, from which the stand-in is rebuilt.

**Filter serialization** reuses the filter-save/load JSON's field set and `ref` indirection (`serializeFilterTreeForCache` / `materializeCachedFilters`, deliberately parallel to `serializeFilterBranch` / `importFilterJson`) — always the "whole tree" shape, since the cache writes each file's *entire* filter tree, not a single-node-vs-chain choice. `bakedA`/`bakedB` (for and/or/link nodes) copy straight across as plain data, same as any other field — no ref-resolution step needed for them at all, since they hold no node id.

**Bookmarks** are persisted as *(file cacheKey, entry ordinal, note, bookmarkedAt)* — entry ids don't survive a reload, but entry order within a rebuilt file is identical, so the ordinal is a stable address. An entry shared between a merged file and a source file is recorded against the first root that contains it (save and restore use the same first-wins scan order). Dangling bookmark ids (entry lost to tail rotation / file delete) just don't get written. This supersedes the old "bookmarks are session-only" limitation; they're still deliberately **not** part of the filter save/load JSON (a bookmark anchors a spot in the data, not a filter definition).

**Write strategy**: `meta` is small and rewritten via a single debounced hook at the end of `render()` (`schedulePersistMeta`, 400 ms) — every state mutation already ends in a `render()`, so no per-mutation persistence calls exist anywhere. File texts are written once on load (`loadFileDescriptors`) / merge (`mergeFiles`), and debounced per-file on tail changes (`schedulePersistFileNode`, 4 s — well above `TAIL_POLL_MS`, since rebuilding a large file's text every poll tick would be wasteful). A `pagehide` listener flushes pending debounces (an IndexedDB write started there normally completes even though its promise never resolves). Deleting a file deletes its `files` record immediately (`cacheDeleteFile`); the meta record follows via the normal render-hook rewrite.

**Restore** (`restoreSessionFromCache`) runs once at boot, after the initial empty-state render. It's guarded by `sessionRestoreInProgress` so its own intermediate renders don't persist half-restored state, and any error abandons the restore (whatever loaded stays usable) rather than blocking the app on a corrupt cache. Every failure path in the storage layer (`openCacheDb`/`cacheStoreOp`) resolves `null` instead of throwing — no IndexedDB (private mode, old jsdom) just means the feature silently turns off and the app behaves exactly as before it existed.

**Every restored file shows up as a grayed placeholder immediately, not one at a time as each PRIOR file finishes its own full parse** (person-reported, this session: *"wenn Dateien beim neu laden der Anwendung wiederhergestellt werden, blende sie schon ausgegraut ein. aktuell erscheinen sie erst nachdem die vorherige Datei geladen wurde."*). Mirrors `loadFileDescriptors`' own multi-file-open shape (see "Multi-file load" below): a first pass fetches every restored file's metadata and inserts a `createQueuedFileNode` placeholder for each one, in order, with a single `render()` — so a session with several large files shows all of their rows immediately instead of a growing gap where the next one will eventually appear. A second pass then turns each placeholder into a real, actively-loading row in turn, via `activateQueuedFileNode` — reached through a new `existingNode` 5th parameter on `addFile` (mirroring the one `loadOneFileIntoTree` already had), rather than `addFile` always calling `createFileNode` fresh.

`createFileNode` reads `sessionRestoreInProgress` to skip its own `state.activeId = node.id` side effect while restoring (see "File-selection clarity: no more activeId thrash on restore" in the changelog) — without that guard the tree's active-row highlight visibly bounced through every restored file in turn before `restoreSessionFromCache`'s own final `s.active` handling corrected it. `activateQueuedFileNode` needed the exact same guard added once restore started routing through it too — it unconditionally set `state.activeId` (the multi-file-open path never needed a guard there, since that path never runs during a restore), which would have reintroduced the identical thrashing bug through this new call path otherwise.

**Escape hatch**: `localStorage["philogg-cache-enabled"] = "0"` disables the whole feature. Deliberately no UI for it — clearing happens naturally by deleting files, and a toolbar toggle for a should-just-work feature felt like clutter; revisit if a real need shows up.

**Test coverage**: `tests/philogg.regression.test.js` Group 127 — two sizable files persisted in one window, restored in the next; polls for both root nodes existing (the structural "both placeholders are in the tree together" moment) well before either file's parse can plausibly have finished, confirms the second file is still either genuinely queued (`.tree-row-queued`) or at least demonstrably not yet fully loaded while the first is already actively parsing, then polls further until both reach their full, correct entry counts with no leftover `queued`/`loadFraction` state.

## File filter history (per-file memory across sessions)

Person-requested follow-up to the session cache, from a design discussion the same session (2026-08-14) before being built. Solves a different problem than the session cache: the session cache restores a whole *session* automatically on reload; this remembers filters *per file*, indefinitely, independent of any particular session, and offers them back — never auto-applies them — the next time a file with matching content is opened, even in a brand new tab/session that never touched the old one.

**Storage**: a third IndexedDB object store, `fileHistory`, in the same `philogg-session-cache` DB (`CACHE_DB_VERSION` bumped 1→2 so `onupgradeneeded` creates it for existing users). One record per qualifying file, **keyed by the file's own content fingerprint** (`getFileFullHash`) rather than by session/`cacheKey` — this is the mechanism that makes the memory outlive a session: nothing about "which session wrote this" is stored at all, only "what content this filter tree belongs to". A record holds `{ name, fullHash, entryCount, timeSpan, filters, savedAt }` — `filters` is the same `serializeFilterTreeForCache` shape the session cache and filter-save/load JSON already use. **Deliberately scoped to the filter tree only** — no bookmarks, no view settings, no active-node ref — at the person's explicit request when this was scoped; those live in the session cache already, and duplicating them here would raise exactly the staleness/re-anchoring questions the session cache's own bookmark-ordinal scheme already has to deal with, for a part of the feature nobody asked for.

**Qualifying** = a real (non-merged) file with at least one real filter child. An empty tree has nothing worth remembering; a merged file is excluded even once it has its own filters, since `mergeFiles` starts every merge with a deliberately empty tree by design (see "Tree interactions" / multi-select bulk actions) — remembering filters *for a merge* would be remembering filters for a combination that's unlikely to recur byte-for-byte across sessions the way a single source file's content can.

**No cap on the number of remembered files.** This was an open question going into the build (an earlier draft considered a "last 10–20 files" LRU cap) — resolved against a cap because the two things that usually justify one don't apply here: storage size doesn't scale with log file size (a serialized filter tree is a few KB at most, not the log text itself — unlike the session cache's `files` store), and the natural per-record key (content fingerprint) already means loading the same content twice overwrites in place rather than accumulating duplicates, so there's no unbounded-growth-from-normal-use failure mode to cap against either. A long tailing session doesn't spam the store: a new record is only written when the filter tree is actually saved (debounced from `render()`, `schedulePersistFileHistory`, same 400 ms window as `schedulePersistMeta`), not on every tail-growth tick — a file that keeps growing under a stable filter tree just keeps overwriting its own single record under its (also-changing) current fullHash, and each earlier snapshot's record is left behind, which is a *feature* here (see tier 2 below), not a leak. If unbounded growth ever becomes a real concern in practice (long-lived shared/kiosk profiles), the natural follow-up is a **time-based expiry** (drop records unmatched for N months) rather than a count cap, since relevance here tracks recency of a match, not an arbitrary "last N files" number — deliberately deferred rather than speculatively built.

**Matching** (`matchFileHistory`) reuses the exact same tiered content-fingerprint technique Session export/import's `matchExportedFile` already established, just run in the opposite direction: one just-loaded candidate file checked against every stored record (since the history store is unbounded, unlike export/import's "handful of currently loaded files"), instead of one export record checked against a handful of loaded candidates. **Tier 1**: exact whole-file fingerprint match. **Tier 2**: the loaded file's own time span fully *contains* a stored (smaller) snapshot's span — the file has grown (typically via tailing) since that snapshot was saved — confirmed by re-slicing the loaded file down to that historical window (`windowSlice`, reusing `lowerBoundByTs`/`upperBoundByTs`) and checking both the entry count and the window's own fingerprint match the stored record exactly. Ties within tier 2 (a file grown past several old snapshots) resolve to the most recently saved one. **Tier 3 deliberately gets no preview at all**, not a lighter-weight one — an ambiguous/unverifiable match here would need the same manual-disambiguation machinery Session export/import's tier 3 dialog uses, which is disproportionate for a convenience feature; a miss just costs a missed convenience, never a wrong restore.

**Where the lookup happens**: `loadFileDescriptors` (the single funnel behind Open Files, drag-drop, and File System Access picker loads), right after the file finishes parsing and its `cacheKey` write fires — a freshly loaded file always starts with zero filter children at that point, so the lookup can only ever attach a *candidate* match, never something that competes with real filters already on screen. The result is stored as `node.filterHistoryMatch = { filters, tier }` on the file node itself. **Not run** for `mergeFiles` (excluded by design, see "Qualifying" above) or `restoreSessionFromCache` (that flow already brings its own filters back via the session cache — running this lookup there too would be redundant and could theoretically flash a ghost preview mid-restore for no benefit).

**UI**: a "ghost preview" (`renderFilterHistoryPreview`, called from `renderNode`) renders directly under a file's tree row, in the same visual slot real filter children would occupy, whenever `node.children.length === 0 && node.filterHistoryMatch` — condition-based, not event-based: no separate "was this offered/dismissed already" flag exists anywhere. One grayed, non-interactive row per node in the stored tree (`renderGhostRow` — icon, name, type tag, mirroring `renderNode`'s own visual language closely enough to read as "this is what your filters looked like", but with no click/drag/context-menu handlers at all), a short note line (entry count, "File has grown since —" prefix on a tier-2 match), and two buttons: **Restore filters** calls the existing `materializeCachedFilters(fileNode, match.filters)` and re-renders; **Cancel** (person-requested, this session — previously the only way to get rid of an unwanted ghost preview was to create a real filter yourself) just sets `fileNode.filterHistoryMatch = null` and re-renders, dismissing the preview without building anything. **Disappears automatically** the instant the file gets *any* real filter child — whether via Restore or the person just creating their own filter without ever clicking it — because that's the entire visibility condition; Cancel reaches the same end state (`filterHistoryMatch` gone) through the other half of that same condition instead. Cancel is a plain, session-local dismissal, not "forget this content's history forever": it deliberately does NOT set `node.filterHistoryTouched` (unlike actually gaining then losing a real filter, see the "Emptying the tree" paragraph below) — the underlying stored `fileHistory` record is untouched, so the same match can still resurface if this exact content is opened again later.

**(Resolved) Emptying the tree back out now overwrites the old restore state instead of resurrecting it.** Previously `node.filterHistoryMatch` was never deleted, only hidden by the `children.length` condition above — so deleting every filter the person had just added made the tree empty again, the condition flipped back to "showable", and the ghost preview resurfaced showing the *original, pre-session* filters, not anything reflecting what the person had just done. Fixed this session (2026-08-14, person-reported via screenshot): `buildFileHistoryRecords()` (see "Storage" above) now tracks a per-file, session-only `node.filterHistoryTouched` flag, set the first time `children.length` goes from 0 to >0 (own filter or a Restore) — at that same moment `filterHistoryMatch` is cleared to `null`, so it can never resurface later purely because the tree emptied back out. If the tree is later emptied again (`children.length` back to 0) while `filterHistoryTouched` is set, the persist cycle now **deletes** that file's stored record instead of leaving it untouched — both directions (gaining a filter, losing the last one) overwrite whatever restore memory came before, and a file with no filters left is indistinguishable from one that never had any, including on the next reload. A freshly loaded file whose ghost preview hasn't been acted on yet (`filterHistoryTouched` still unset) is unaffected — nothing is decided about it until the person actually does something.

## Session export / import (sharing an analysis with a colleague)

**"Export session…"** lives behind `#btnSave` in `#sidebarHeader`; **"Import session…"** lives behind `#btnOpen`'s dropdown (`#openMenu`, alongside File(s)…/Folder…) in the same header (see "Header / toolbar layout" → "Toolbar regroup" for the FEATURE_BACKLOG.md #56 move that put both there, and the earlier `#btnSession`/`#sessionMenu` pairing they replaced). Both actions used to live in the tree's per-node context menu instead (next to Save/Load filter, plus a dedicated empty-background context menu just to keep "Import session…" reachable with zero files loaded) — moved out of there since neither action is actually about whichever file/filter the context menu was opened on; the buttons work identically regardless of how many files are loaded, so the empty-background special case is gone too, not just relocated. `openSessionExportDialog()`/`importSessionFromFile()` were already self-contained (the export dialog guards on `state.rootIds.length` itself, the import flow needs no node reference at all), so both moves were pure UI wiring with no logic change. Format is `{ format: "philogg-session-export", version, exportedAt, files: [...], settings }`, `SESSION_FILE_VERSION = 1`.

**What gets exported**: a user-picked subset of the currently loaded root files (`#sessionExportDialog`, one row per file with an include checkbox), each file's *complete* filter tree (reusing `serializeFilterTreeForCache`/`materializeCachedFilters` from the session cache — no branch/chain-pulling needed since the whole tree goes anyway), that file's bookmarks (first-wins scan across files, same convention as `buildCacheMeta`), and session-wide settings (level filter, sort, active node — recorded as `{exportId, ref}` since export ids are only stable within one export document). A per-file **"embed log text"** checkbox (deliberately per-file, not global — some logs in a session may be sensitive while others aren't) includes `rebuildFileText(node)` in that file's record, making the export self-contained for that file.

**The core problem this solves**: the person importing almost certainly has their *own* copy of the same log, not the exporter's literal file — same name, different name, or (for a tailed/live log) a newer snapshot that kept growing after the export was made. `matchExportedFile()` resolves each exported file against the importer's currently loaded files in three tiers:

1. **Tier 1 — full-content match**: the export carries a whole-file fingerprint (`fullHash`, via `fingerprintText`); any loaded file whose own full fingerprint (`getFileFullHash`, cached on `node._fullHash`) matches is a confident hit. Applied silently.
2. **Tier 2 — overlapping time window**: covers the motivating scenario (receiving copy of a tailed log kept growing past the exported snapshot). The exported file's timestamp span must be **fully contained** in the loaded file's span — a file that only partially overlaps (e.g. a rotated/truncated head) can't be verified this way and falls through to tier 3. Within the window: entry-count pre-filter first (cheap, and a strong signal — same density in the same window), then a fingerprint of the concatenated raw text of just that window, compared against the export's `fullHash`. An appended entry whose timestamp lands exactly on the window's end boundary inflates the count and correctly demotes the match to tier 3 rather than silently misapplying. Surfaced via a passive toast (`"X matched via overlapping time range"`) — applied automatically, but the person is told why, since it's a weaker guarantee than tier 1.
3. **Tier 3 — manual reassignment** (`#sessionMatchDialog`, one dialog per unresolved file, sequential): near-misses from tiers 1–2 (right file, wrong count/hash, or partial overlap) are shown first and badged "possible match"; other loaded files follow; then **"Load a file from disk…"** (opens the normal file picker, re-runs tiers 1–2 against the newly loaded file, loops back to the dialog if that still doesn't resolve it); **"Load the embedded log"** (only shown when the export has `text` for that file — materializes it via `addFile`, treated as tier-1-trustworthy since re-parsing the exporter's own rebuilt text is a fixed point); and **"Skip this file"**. Cancel on the dialog skips this file and every remaining unresolved one (already-applied files are kept). No backdrop-click dismissal on this dialog (unlike the export dialog) — a stray click mid-import shouldn't silently count as a decision.

**Bookmarks**: tier 1/2 targets are provably identical inside the exported window, so a bookmark's stored **ordinal** is trusted outright (`applySessionEntryByOrdinal`, same scheme as the session cache). A tier-3 manually-picked file has no such guarantee, so bookmarks there are re-anchored by **timestamp** (binary search via `lowerBoundByTs`) and confirmed against the hit ± 2 neighbours by **raw-line fingerprint** (`applySessionEntryByContent`) — enough slack to absorb small insertions/deletions elsewhere in the file without losing every bookmark to one nearby edit. A bookmark that can't be confirmed is dropped and shows up in the final summary toast as unplaced (`"N of M bookmarks placed"`), never silently misplaced onto the wrong line.

**Fingerprinting is deliberately not `crypto.subtle`/SHA-256**: it's a matching aid, not a security boundary (the worst-case cost of a collision is a wrongly-*suggested* match that the person can still reject in the tier-3 dialog), Web Crypto's async API is awkward for hashing several loaded files as a synchronous pre-filter, and its availability under a `file://` origin (this app's primary deployment mode) isn't worth depending on. `fingerprintText()` runs two 32-bit FNV-1a passes with different offset bases and concatenates them into 16 hex chars — cheap, synchronous, good enough for a matching aid. Do not swap in Web Crypto in a future session without revisiting this reasoning.

**Settings/active-node application is all-or-nothing per import, not per file**: if every exported file ends up skipped, session-wide settings (level filter, sort, active node) are left untouched rather than clobbering the current view for zero gained files.

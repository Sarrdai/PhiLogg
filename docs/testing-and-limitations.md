# Testing and Limitations

Testing approach used during development, and known limitations / intentionally deferred items.

## Testing approach used during development

No test framework is shipped with the file (it's a deployed artifact, not a repo with CI). Verification during development used **jsdom** (`npm install jsdom` in a scratch dir), loading the real `philogg.html` with `runScripts: "dangerously"` and driving it through the actual DOM — simulating file drops via a synthetic `drop` event with a `File`, clicking real buttons/rows, and reading back rendered DOM state — rather than re-implementing logic in isolation, which repeatedly caught real integration bugs (stray event-listener bubbling closing a just-opened popup, a closure-over-a-shared-loop-variable bug in hover handlers, stale-DOM assumptions in multi-step interactions). **If asked to verify a change**, prefer this approach — spin up jsdom, load the file, and drive it like a user — over just reading the code and reasoning about it, since several real bugs here were only caught this way. Needs `clientHeight`/`getBoundingClientRect` stubbed (jsdom has no real layout engine) and `navigator.clipboard` stubbed for copy-related tests. jsdom also ships **no IndexedDB** — the session-cache group injects a `fake-indexeddb` `IDBFactory` via `beforeParse` (now a devDependency in the suite's `package.json`); passing the *same* factory instance into two successive jsdom windows simulates a browser reload against the same "disk". All other groups run without it, which doubles as a test of the cache's graceful-degradation path (`openCacheDb` resolves `null`, feature silently off).

**The most consequential bug caught this way**: double-click-to-jump-to-full-log silently stopped working entirely, on every row, every time. Root cause — `selectEntry()`'s plain-click path called `renderVisibleRows()`, which does `tableRows.innerHTML = ""` and rebuilds every row as a *new* DOM node on every single click, including the first click of a double-click. Browsers only count a second click toward a `dblclick` if it lands on the *same element* as the first; since that element no longer existed by the time the second click landed, `dblclick` never fired — not intermittently, but always. Confirmed via jsdom by asserting `row === document.querySelector('[data-entry-id="..."]')` was still true *after* dispatching a plain `"click"` event on it. Fixed by having a plain click only toggle the `.selected` class on the existing rendered elements (`updateSelectedRowClass`) instead of tearing the row list down; the arrow-key path still goes through `renderVisibleRows()` via `scrollToIndex()` since it may need to bring an off-screen row into view. **Lesson for future work on this file**: recreating a DOM element in response to the first half of any multi-step native browser gesture (double-click, drag, anything relying on element identity across events) will silently defeat that gesture — verify element identity survives a single interaction before assuming a click/drag handler is "just cosmetic."

**jsdom gotcha worth knowing before writing more tests**: top-level `function` declarations in the inline `<script>` become `window` properties (so `window.render()`, `window.createFilterNode(...)` etc. work directly from a Node test), but top-level `let`/`const` — `state`, `extractRowsData`, `plotConfig`, `undoStack`/`redoStack`, and most other module state — do **not**; they only live in the shared global lexical scope, per spec, same as in a real browser. Reading (or resetting) them from outside requires injecting a second `<script>` element into the same jsdom document (`document.body.appendChild(...)`) whose body exposes getters (`window.__t = { get state() { return state; }, ... }`) or small helper functions (`window.__resetUndoRedo = () => { undoStack = []; redoStack = []; }`) — since that injected script runs in the same realm's global lexical scope, it can see the bindings directly. `window.state.foo = x` (mutating a property of the object the getter returns) works fine without a setter; `window.state = x` (replacing the binding itself) does not and fails silently.

One thing jsdom **can't** catch: real hit-testing / paint order (`elementFromPoint`, whether a `position:fixed` overlay visually covers something and intercepts its clicks) — jsdom has no layout or rendering engine, so this class of bug (e.g. the message-popover issue above, or the file-drop overlay swallowing tree drag events) has to be reasoned about directly from CSS (`position`, `z-index`, `pointer-events`) and event bubbling/timing, then verified by state-based proxies (checking `hidden`/`show` classes at the right moments) rather than by literally observing an element being obscured.

## Known limitations / intentionally deferred

- Value assertions **and `node.ignoredColumns`** are keyed by column **index**, not name — editing an extraction pattern so columns shift position (e.g. removing an earlier placeholder) leaves any assertion, or any ignored-column marker, on a later column silently pointing at the wrong data. No migration or warning exists; re-set the assertion / re-check ignored columns after a pattern edit that reorders columns. For ignored columns this also applies one level earlier: the filter popup's `filterPopupIgnored` working set is pre-populated from the node's `ignoredColumns` when Edit is opened, so it can go stale if the pattern text is then heavily retyped in the same edit session.
- **AND/OR over a `link` node is unsupported** — a link's result is synthetic pair entries whose ids never appear in a plain entry pool, so an AND could only be empty and an OR type-mixed. `canBeCombined` refuses such a side and the bulk menu offers only "Link…" for it; chaining onto a link goes through the link dialog instead, whose evaluator understands pair entries.
- **Filter files and library presets written before the `bakedA`/`bakedB` model can't be loaded.** Such a combiner carried node-id references to its two sides, which mean nothing under the self-contained model, so `importFilterJson` rejects it with a message rather than creating a filter that silently matches nothing. There is no migration path (the referenced nodes aren't in the file); re-create the combiner instead. `FILTER_FILE_VERSION` was deliberately not bumped for this — the rejection is per-node and precise, where a version gate would reject whole files that contain no combiner at all.
- **Cross-file filter combination** (AND/OR/Link across two different root files) is unsupported by design — merge the files first. `describeBulkActions` enforces the shared-root check and says so in the menu.
- **Filter inversion (NOT)** is unsupported by design for `link` (pair-entry ids don't correspond to `parentEntries` ids), `extract` (an inverted match set has nothing left to extract) and `context`/`countContext` (every window contains its own reference entry, so an inverted result would always be empty). See "Inversion (NOT)" in `PROJECT.md`.
- **Undo/redo doesn't cover node *creation*** — not filter creation, file creation, Unpack, context-filter creation, or folder-file close (itself non-destructive: the file returns to its folder's grayed listing). Delete, move, value/pattern edits, the invert toggle and assertion changes are covered. See "Undo / redo" for why a snapshot stack was chosen over deriving undo generically.
- **Session cache**: a restored merged file no longer shares entry objects with its source files — it's rebuilt from its own cached text, so `mergeFiles`' identity-sharing doesn't survive a reload (each file still works standalone; it costs duplicate memory, and a bookmark on a shared entry resolves to only one of the files). Undo/redo stacks and the clipboard are deliberately session-only. Disabling the cache has no UI — `localStorage["philogg-cache-enabled"] = "0"` is the escape hatch.
- **Session export/import**: tier-2 matching only covers a loaded file whose time span *fully contains* the exported span, so a rotated/truncated partial overlap always falls to the manual tier-3 dialog even when a human could tell at a glance it's the right file. Import has no dedup against an already-present equivalent branch (same gap as filter save/load — re-importing produces visible duplicate filter trees). Fingerprinting is O(file size) and runs synchronously on the main thread, not chunked like the initial parse, so a very large file can cause a brief UI stall during export or tier-1/2 matching. A merged file re-matches only best-effort: it round-trips when it happens to reproduce the same combined content and entry count, with no identity-matching path for "this merged file's *sources* changed".
- **Filter save/load never checks for an equivalent existing branch** — every "Load filter…" creates a fresh independent copy, so re-loading the same file produces visible duplicates.
- **Tailing requires the File System Access API** (Chromium); Firefox and the legacy `<input>` fallback load files as one-time snapshots with no live updates. Byte-offset slicing assumes the writer flushes whole UTF-8 characters (log writers do). On rotation/truncation the node's entries are replaced and the old ids released from `entryIndex` (`releaseEntriesFromIndex`); a merged file that reused those entry objects intentionally keeps them alive. Within a changed file, filters recompute from scratch each tick — an incremental filter-append is the next optimization if a single very large tailed file with deep filter chains ever feels sluggish (filters under *untouched* files already stay cached, see `invalidateCachesForRoots`).
- **The `context` filter's bracket rendering** resolves group start/end caps against the full result array, so caps are always correct — but if a group's start scrolls more than `BUFFER_ROWS` above the viewport, only the rows that actually exist as DOM nodes get a bracket line. Cosmetic only.
- **Sorting the extraction table** reorders `extractRowsData` directly rather than keeping a separate display order, so it also reorders the connected Plot tab's line/bar point sequence for that extraction. Accepted trade-off.
- **The Highlight view has no tail auto-follow** — the Filter view scrolls with new tailed entries (`state.tailFollow`), the Highlight view keeps its scroll position. Deliberate: it's meant as a stable reference view while browsing, and follow-to-bottom would fight that.
- **Highlight-rule matching walks every colored node** on every Highlight-view render (memoized per node via `getEntries`'s cache, so cheap in practice) — the first thing to optimize if someone colors a very large number of nodes.
- **The hue wheel in the highlight-colour picker only picks hue**; saturation/lightness are fixed at 68%/55%. Chosen for a simpler, more predictable widget — the preset row covers cases needing a specific exact color.
- **A row that is both highlight-matched and inside a time-context bracket** shows both markers in the same left-gutter slot (`.hl-markers`/`.ctx-bracket` both at `left:-9px`), overlapping rather than each getting a lane. Accepted trade-off.
- **The collapsed sidebar's 40px rail** shows only the active node's ancestor chain (or the root files when nothing is active), not the whole tree — a 40px strip can't fit a large tree, and hover-peek exists to show the real thing. Jumping to a sibling branch while collapsed means peeking rather than clicking a rail marker.

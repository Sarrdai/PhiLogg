# Testing and Limitations

Testing approach used during development, and known limitations / intentionally deferred items.

## Testing approach used during development

No test framework is shipped with the file (it's a deployed artifact, not a repo with CI). Verification during development used **jsdom** (`npm install jsdom` in a scratch dir), loading the real `philogg.html` with `runScripts: "dangerously"` and driving it through the actual DOM — simulating file drops via a synthetic `drop` event with a `File`, clicking real buttons/rows, and reading back rendered DOM state — rather than re-implementing logic in isolation, which repeatedly caught real integration bugs (stray event-listener bubbling closing a just-opened popup, a closure-over-a-shared-loop-variable bug in hover handlers, stale-DOM assumptions in multi-step interactions). **If asked to verify a change**, prefer this approach — spin up jsdom, load the file, and drive it like a user — over just reading the code and reasoning about it, since several real bugs here were only caught this way. Needs `clientHeight`/`getBoundingClientRect` stubbed (jsdom has no real layout engine) and `navigator.clipboard` stubbed for copy-related tests. jsdom also ships **no IndexedDB** — the session-cache group injects a `fake-indexeddb` `IDBFactory` via `beforeParse` (now a devDependency in the suite's `package.json`); passing the *same* factory instance into two successive jsdom windows simulates a browser reload against the same "disk". All other groups run without it, which doubles as a test of the cache's graceful-degradation path (`openCacheDb` resolves `null`, feature silently off).

**The most consequential bug caught this way**: double-click-to-jump-to-full-log silently stopped working entirely, on every row, every time. Root cause — `selectEntry()`'s plain-click path called `renderVisibleRows()`, which does `tableRows.innerHTML = ""` and rebuilds every row as a *new* DOM node on every single click, including the first click of a double-click. Browsers only count a second click toward a `dblclick` if it lands on the *same element* as the first; since that element no longer existed by the time the second click landed, `dblclick` never fired — not intermittently, but always. Confirmed via jsdom by asserting `row === document.querySelector('[data-entry-id="..."]')` was still true *after* dispatching a plain `"click"` event on it. Fixed by having a plain click only toggle the `.selected` class on the existing rendered elements (`updateSelectedRowClass`) instead of tearing the row list down; the arrow-key path still goes through `renderVisibleRows()` via `scrollToIndex()` since it may need to bring an off-screen row into view. **Lesson for future work on this file**: recreating a DOM element in response to the first half of any multi-step native browser gesture (double-click, drag, anything relying on element identity across events) will silently defeat that gesture — verify element identity survives a single interaction before assuming a click/drag handler is "just cosmetic."

**jsdom gotcha worth knowing before writing more tests**: top-level `function` declarations in the inline `<script>` become `window` properties (so `window.render()`, `window.createFilterNode(...)` etc. work directly from a Node test), but top-level `let`/`const` — `state`, `extractRowsData`, `plotConfig`, `undoStack`/`redoStack`, and most other module state — do **not**; they only live in the shared global lexical scope, per spec, same as in a real browser. Reading (or resetting) them from outside requires injecting a second `<script>` element into the same jsdom document (`document.body.appendChild(...)`) whose body exposes getters (`window.__t = { get state() { return state; }, ... }`) or small helper functions (`window.__resetUndoRedo = () => { undoStack = []; redoStack = []; }`) — since that injected script runs in the same realm's global lexical scope, it can see the bindings directly. `window.state.foo = x` (mutating a property of the object the getter returns) works fine without a setter; `window.state = x` (replacing the binding itself) does not and fails silently.

One thing jsdom **can't** catch: real hit-testing / paint order (`elementFromPoint`, whether a `position:fixed` overlay visually covers something and intercepts its clicks) — jsdom has no layout or rendering engine, so this class of bug (e.g. the message-popover issue above, or the file-drop overlay swallowing tree drag events) has to be reasoned about directly from CSS (`position`, `z-index`, `pointer-events`) and event bubbling/timing, then verified by state-based proxies (checking `hidden`/`show` classes at the right moments) rather than by literally observing an element being obscured.

## Known limitations / intentionally deferred

- Value assertions **and `node.ignoredColumns`** are keyed by column **index**, not name — editing an extraction pattern so columns shift position (e.g. removing an earlier placeholder) leaves any assertion, or any ignored-column marker, on a later column silently pointing at the wrong data. No migration/warning exists yet; re-set the assertion / re-check ignored columns after a pattern edit that reorders columns. For ignored columns specifically, this also means the filter popup's `filterPopupIgnored` working set (pre-populated from the node's `ignoredColumns` when Edit is opened) can go stale if the pattern text is then heavily retyped in the same edit session — same sharp edge, one level earlier.
- (Resolved) Bookmarks used to be session-only; the session cache now persists them (with files, filters, and settings) across reloads. (Resolved) **Tail handles are now persisted too** — see "Tailing (live file updates)" below for `tryReattachFileTail()`. Remaining session-cache limitations: **A restored merged file no longer shares entry objects with its source files** — it's rebuilt from its own cached text, so the identity-sharing described in `mergeFiles` doesn't survive a reload; each file still works standalone, it just costs the duplicate memory and a bookmark on a shared entry resolves to only one of the files. **Undo/redo stacks and the clipboard are not persisted** — they're deliberately session-only, same as before this session's scope extension. Disabling the cache has no UI — `localStorage["philogg-cache-enabled"] = "0"` is the escape hatch.
- Session export/import (see "Session export / import" above): tier-2 matching only covers a loaded file whose time span **fully contains** the exported span — a receiving file that's a rotated/truncated *partial* overlap of the export can't be auto-verified and always falls to the manual tier-3 dialog, even though a human could often tell at a glance that it's the right file. Import has no dedup against an already-present equivalent branch, same known gap as filter save/load — re-importing the same session twice produces visible duplicate filter trees. Fingerprinting/hashing a file is O(file size) and runs synchronously on the main thread; not chunked/yielded like the initial parse, so a very large file could cause a brief UI stall during export or tier-1/2 matching on import. A merged file's re-matching is best-effort only: it round-trips fine when it happens to reproduce the same combined content and entry count, but there's no dedicated identity-matching path for "this merged file's *sources* changed" the way there is for a plain file.
- Undo/redo still doesn't cover filter/file *creation*, folder-file close, or context-filter creation (see "Undo / redo" for the full current scope and why) — everything else named in the original feature-backlog item (file deletion, value/pattern edits, invert toggle, assertion changes) is now covered.
- Filter inversion (NOT) is unsupported by design for `link` (pair-entry ids don't correspond to `parentEntries` ids — see "Inversion (NOT)"), `extract` (an inverted match set has nothing left to extract), and `context` (every window contains its own reference entry, so an inverted result would always be empty).
- The `context` filter's bracket rendering resolves group start/end caps against the full result array (not just the virtualized render window), so caps are always correct — but if a group's start scrolls more than the row buffer (`BUFFER_ROWS`) above the viewport, only what's actually rendered gets a bracket; the line simply doesn't extend into rows that were never created as DOM nodes. Cosmetic only, no functional impact.
- 3D scatter plot (explicitly lower priority, not built).
- Cross-file filter combination (AND/OR/Link across two different root files) is unsupported by design — merge first.
- Filter save/load never checks whether the destination tree already has an equivalent branch — every "Load filter…" creates a fresh independent copy, so re-loading the same file (or loading onto a tree with a matching chain) produces visible duplicates. See "Filter save / load" section above.
- (Resolved) Extraction table and link pair view are now both row/block-virtualized — see "Virtualized rendering: extraction table & Link pair view".
- (Resolved) The timeline minimap used to rebuild its whole-file background buckets (an O(root file size) pass) on every `renderTable()` call. The background pass is now memoized (`minimapBgCache`, keyed on root id + entry count + time span + bucket count — so it self-invalidates on tail append, rotation, and resize); only the overlay pass (O(current view)) still runs per render. This was the biggest fixed cost when switching between filters on large files.
- Sorting the extraction table (per-column sort buttons) reorders `extractRowsData` directly rather than keeping a separate display order, so it also reorders the connected Plot tab's line/bar point sequence for that extraction — accepted trade-off, see "Extraction workflow" above.
- (Resolved, this session, 2026-08-17, from `FEATURE_BACKLOG.md`) Level colors are now re-themed for light mode instead of reusing the dark-mode hex values verbatim — see "Light theme" below.
- Tailing requires the File System Access API (Chromium) — Firefox and the legacy `<input>` fallback load files as one-time snapshots without live updates. Byte-offset slicing assumes the writer flushes whole UTF-8 characters (log writers do). On rotation/truncation the file node's entries are replaced and the old ids are released from `entryIndex` via `releaseEntriesFromIndex()` (no per-rotation index leak anymore); a merged file that reused the old entry objects still keeps the stale ones — and, because it references them, also keeps them alive in the index, which is intentional. Each tail change now invalidates only the caches that actually depend on the changed file(s) (`invalidateCachesForRoots`, see Memoization) instead of every cache globally — filters under untouched files stay cached across polls. Within the changed file itself, filters still recompute from scratch each tick; an incremental filter-append remains the next optimization if a single very large tailed file with deep filter chains ever feels sluggish. (Resolved, this session, 2026-08-17, person-reported) A plain (non-folder) file's tail now survives a page reload too, same as a watched folder's own files already did: `persistFileNode` stashes `node.tail.handle` alongside the file's text, and `restoreSessionFromCache` calls the new `tryReattachFileTail(node, handle)` — `handle.queryPermission({mode:"read"})` (no user gesture needed) either resumes tailing invisibly (fresh `offset` computed from the restored text's own length, so the next poll only reads genuinely new bytes) or leaves the file a static snapshot, same graceful-degradation shape `restoreWatchedFolders` already used for directory handles. Root cause of the person-reported bug: a file the session cache silently auto-restored on relaunch — experienced as just "opening the file" — never got a `node.tail` at all, so an actively-growing log neither updated nor showed the pulsing live dot until manually re-opened. Skipped for folder-owned files (`node.folderId`), which keep reattaching via `restoreWatchedFolders`/`mergeScannedFiles` as before. (Resolved, same day, person-reported same-session follow-up) With that fix in place, tailing DID start updating and showing the live dot — but stopped again a few seconds later. Root cause: `tailTick`'s catch block treated ANY `getFile()`/read failure as permanent (`t.failed = true` on the very first one) and logged nothing at all, so there was no way to tell a transient failure (most plausibly the writer briefly holding the file locked without shared-read access — an ordinary condition for a log actively being appended to) from a genuinely permanent one, or even to see that a failure had happened. Fixed with a consecutive-failure counter, `t.errorCount`/`TAIL_MAX_CONSECUTIVE_ERRORS` (5) — see "Tailing (live file updates)" → "Read failures are retried, not fatal on the first one."
- The Highlight view has no tail auto-follow of its own — while the Filter view scrolls with new tailed entries (`state.tailFollow`), the Highlight view just keeps whatever scroll position it had. Deliberate v1 scope: it's meant as a stable reference view while browsing, and follow-to-bottom would fight that. Revisit if this turns out to matter for live-tailing workflows.
- The hue wheel in the highlight-colour picker only picks hue — saturation/lightness are fixed (68%/55%) rather than a full 2D color picker. Chosen for a simpler, more predictable widget; the preset row covers cases where a specific exact color matters.
- (Resolved) In stacked Filter/Highlight layout, the Filter/Highlight tab buttons used to stay visible but functionally inert. The tri-state Full/Filtered/Stacked toggle now switches straight out of Stacked into tabs mode on the clicked panel instead of doing nothing — see "Highlight view (Filter/Highlight split)".
- A row that's both highlight-matched and part of an active time-context filter's bracket shows both markers in the same left-gutter slot (`.hl-markers`/`.ctx-bracket` both sit at `left:-9px`), overlapping rather than each getting its own lane. Accepted trade-off, not expected to come up often — revisit if it does.
- Highlight-rule matching walks every colored node in the tree on every Highlight-view render (memoized per-node via `getEntries`'s own cache, so cheap in practice) — would be the first thing to optimize if someone sets colors on a very large number of nodes at once.
- The collapsed sidebar's 40px rail (see "Collapsible sidebar / detail panel" below) shows only the active node's ancestor chain (or root files if nothing's active), not the whole tree — a 40px strip can't fit a large tree anyway, and hover-peek exists precisely to show the real thing. A person wanting to jump to a sibling branch while collapsed has to peek (hover) rather than click a rail marker for it directly.

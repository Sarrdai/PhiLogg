# UI and Views

Header/toolbar layout, the three active-node views, the Context/Filtered split (internally still the "Highlight" view), tree interactions, theming, and the app's visual language.

## Header / toolbar layout

The header (`#toolbar`) is a plain flex row, left to right: `.brand` (wordmark, fixed at the left), the back/forward nav group, a `.toolbar-spacer` that eats the remaining width, then `.toolbar-right` (status text, undo/redo, Export / Share `#btnExport` — see `docs/export.md` — and settings) flush against the right edge. `.brand` is itself a column: `.brand-row` (the mark + "PhiLogg" name) on top, `.brand-version` (`#brandVersion`, the short commit-hash build tag) in a smaller line directly underneath. The header used to also carry a small subtitle ("local, single-file log viewer") next to the brand name — removed per a person UI-adjustment request; `.brand-tag` no longer exists in either markup or CSS.

**Toolbar regroup (FEATURE_BACKLOG.md #56, this session, person-requested):** `#btnOpen`/`#openMenu` and the former `#btnSession`/`#sessionMenu` used to live in `#toolbar`'s right side. Both moved into `#sidebarHeader` (the "Files & filters" section header, between the label and `#sidebarToggle`) as small icon-only buttons styled with `.panel-toggle-btn` (the same 24x24 shape as `#sidebarToggle`) instead of the old pill-shaped `#btnOpen, #btnSession{...}` rule, which was removed. "Open…" now covers every "bring something in" action — File(s)…/Folder…/ZIP…/Import… (the central import, see `docs/persistence-and-sync.md` → "Central import") — via `#openMenu`'s dropdown; "Session…" as a separate button is gone, and `#btnSave` is a single icon button (no dropdown, since there's only the one action) that calls `openSessionExportDialog()` directly. See "Session export / import" further down for the current session-export/import writeup.

**Back/forward navigation (FEATURE_BACKLOG.md #53, this session, person-requested, placement adjusted same session per follow-up feedback):** `#btnNavBack`/`#btnNavForward` step through a history of previously-visited filter nodes — modeled on browser/IDE back/forward, explicitly distinct from Undo/Redo (which tracks tree *edits*, not view visits; `undo()`/`redo()` never touch `navHistory` or scroll position). They first landed in `#sidebarHeader` alongside Open/Save, then moved into `#toolbar` itself — same row as Settings/Undo/Redo, but grouped with `.brand` on the LEFT side of `.toolbar-spacer` instead of the right, so they sit right next to the wordmark, closer to it than the rest of the toolbar's controls (which stay flush right exactly as before). The version tag moved the other way in the same follow-up: out of `#toolbar`'s right side, into `.brand-version` under the wordmark (see above) — neither move touches `.toolbar-right`'s own contents or the desktop wrapper's injected window-control block, which is appended into it (`docs/desktop.md`).

Implementation lives just above `render()` in `philogg.html`, under its own "Back/forward 'where I looked' navigation" header comment, which carries the full tier list. The feature is explicitly distinct from Undo/Redo (tree *edits*, not view visits; `undo()`/`redo()` never touch `navHistory` or scroll position).

**What counts as a "meaningful interaction"** (person-requested this session, modeled on Visual Studio / JetBrains Rider — *"oft verliert man sich im Code und kann so nochmal zurückfinden auf was man zuvor angeschaut hat"*). Three tiers; anything not in A or B never produces a waypoint.

- **A — always, no condition.** An explicit relocation. **A1** `state.activeId` changes (tree click, Alt+Arrow tree nav, creating/editing a filter, drag-drop reparent, an undo/redo landing on another node) — detected in `render()` via the same `lastActiveIdForReveal` check `revealFilteredView()` uses, which is the one place all ~30 `state.activeId` call sites funnel through. **A2** `revealInHighlightView()` (double-click / Enter into the Context view). **A3** `revealInFilteredView()` (extraction table row, into the SAME node's Filtered view — this session's follow-up feature; see "The three 'active node' views" below) / `revealInTableView()` (plot mark, into that same node's Table row instead, revised 2026-09-05, person-requested). **A4** `jumpToEntry()`. **A5** the timeline minimap's click-to-jump. **A6** `jumpToTailedNewest()`. A2–A6 each call `commitCurrentNavPosition()` *before* the jump and `pushNavWaypoint()` *after* it — without the first half the origin is lost, which is precisely what the original implementation got wrong (it overwrote the current entry's `scrollTop` on every scroll event, so the spot being left was already gone by the time you left it).
- **B — only when the test passes.** **B1 scroll + dwell**: `NAV_DWELL_MS` (700ms) after the last *user* scroll event, a waypoint is pushed iff the view has travelled at least one viewport height (`scrollEl.clientHeight`, falling back to `NAV_MIN_SCROLL_PX = 400`) from the current waypoint's own remembered position; otherwise that waypoint is just refreshed in place. Every further scroll restarts the timer, so a fast flick to the end of a file yields **one** waypoint at the destination, not fifty on the way. Measuring against the *waypoint* rather than against where this particular burst started is what makes several short bursts in the same direction accumulate into one eventual waypoint, and what keeps the origin intact while you are far away from it. One handler (`onNavScroll`) is wired to all four scroll containers (`#tableBody`, `#extractScroll`, `#linkScroll`, `#highlightBody`); the dwell timer is global because only one of them can be scrolled at a time.
- **C — never.** Anything while `navigatingHistory`; **programmatic scrolls** (tail-follow, a jump's own scroll, a history restore), recognized through `lastProgrammaticScrollTs` — the same 150ms window the tail-follow listeners use, with the accepted consequence that a person's scroll landing inside that window is ignored too; the Context/Filtered/Stacked toggle and the automatic `revealFilteredView()` (the view mode is stored *in* a waypoint and restored, but switching it is not itself a step — same as a tool window in an IDE); level quick-filter, sort, multiline/notes toggles, column changes, gap expand/collapse; hover, popups, settings. **Selection is not a waypoint either** — it rides along on whatever waypoint is current (every capture reads `state.selectedId`), so an arrow-key sweep through rows produces none, and once it has scrolled far enough B1 puts exactly one at the destination.

**The waypoint** is `{ nodeId, fhLayout, fhActiveTab, entriesView, selectedId, filterAnchor, contextAnchor, rawScrollTop, contextScrollTop }` — it used to be just `{nodeId, scrollTop}`. `filterAnchor`/`contextAnchor` are `{id, offset}` pairs from the existing `captureViewAnchor()`/`restoreViewAnchor()` (see "General 'don't jump' scroll anchoring" below), one per pane because the Stacked layout shows both at once. **An anchor row instead of a raw pixel offset** is the point: a raw `scrollTop` means something different after a tail tick, a level-filter change, a multiline toggle or a re-sort, whereas an entry id plus its on-screen offset survives all four and degrades gracefully when the row is gone. The trade-off is that the no-selection case is **row-granular** — `captureViewAnchor`'s fallback reports the topmost visible entry at offset 0, so a restore lands that row's top edge at the viewport top rather than reproducing a sub-row pixel offset. `rawScrollTop` still covers the extraction table and the link pair view, which have no entry-keyed row list to anchor in (`activeNavScroller()` picks the container, mirroring `renderMainView()`'s own isExtract/isLink branching).

**Restoring** (`applyNavWaypoint`) sets the node and selection, renders, *then* applies `fhLayout`/`fhActiveTab` — after the render, because `render()`'s own A1 branch calls `revealFilteredView()` for a filter node and would otherwise override the pane the waypoint was recorded in — and restores `entriesView` last of all, after both of those, since either can route through `showFhTab`, which pins `entriesView` to the visible pane in tabs layout (see "Arrow-key navigation" below). A selection whose entry no longer exists leaves the current one alone rather than blanking the detail panel, and a live tail is disengaged on arrival — navigating to a remembered spot means wanting to look at it, the same reason picking a row disengages follow. `contextExpansions` is deliberately **not** part of a waypoint: the restore calls `applyContextJumpExpansion()` on the context anchor instead, exactly as `revealInHighlightView` does, which is all the correctness the restore actually needs (a target inside a collapsed gap has no row to scroll to). Two dedup/limit rules keep the history honest: `isSameNavPlace()` merges a push into the current waypoint when node, pane and anchor row all match — which is also what stops A3/A4 from recording twice, since they change `activeId` and therefore trigger A1 as well — and `NAV_HISTORY_LIMIT = 50` (same cap and reasoning as `UNDO_STACK_LIMIT`) drops the oldest entry.

An A1 waypoint is pushed at the *top* of `render()`, before the view it belongs to has been rebuilt, so its positions are filled in at the *end* of that same render (`navFillPending`) rather than captured against the outgoing DOM — gated on the flag, so this costs one capture per navigation, not one per render. Going back/forward onto a since-deleted node drops that stale entry and retries in the same direction (`goToNavHistoryIndex`'s self-recursion); an entry whose *anchor row* is gone is **not** stale — it still names a live node, and the anchor restore falls back to the view's own default. The buttons carry a dynamic tooltip naming their destination ("Back to: `<node>` · `<time>`"), the same courtesy `updateUndoRedoButtons()` already extends via `UNDO_KIND_LABELS`. Browser/OS back/forward mouse buttons (`ev.button === 3`/`4`) drive the same `navigateBack()`/`navigateForward()` via a `document` `mouseup` listener, with `preventDefault()` so the browser/OS chrome doesn't also try to navigate the page itself. There is deliberately **no keyboard shortcut** (person-requested): `Alt+←/→` belongs to tree navigation and `Ctrl+-` to zoom-out, and nothing in `SHORTCUT_ACTIONS` was changed. The history is session-only, like `undoStack` — entry ids (`uid("e")`) do not survive a reload, and a "where was I" history is not worth the ordinal re-keying `buildCacheMeta` does for bookmarks.

**`#viewBar`** — a single row at the top of `#content`, above `#fhSplit`, that merges what used to be **three separate toolbar rows**: the breadcrumb (active filter chain), the level quick-filter, and the Context/Filtered/Stacked toggle. `#fhTabs` (the toggle), `#btnPinBookmarks` (the pin-bookmarks toggle, moved in from the header — see "Pin bookmarks into the Filtered View") and `#levelBar` are `float:left`, so they stay **pinned to the top-left line** no matter how long the filter chain gets, in that DOM order (tabs, then the pin toggle, then the level pills); `#breadcrumb` is a plain block (not flex) with `display:inline-block` chips, so it flows text-style around those three floats on the first line(s) and then uses the **full row width** on any line it wraps to below them — a filter chain long enough to wrap doesn't push the toggle/pin/level-filter down or squeeze itself into a narrow leftover column, it just drops to its own full-width line(s) underneath. `#viewBar` itself is `display:flow-root` so its own height always reaches the floats' bottom edge even when the breadcrumb is short or empty (a plain float doesn't otherwise contribute to a parent's auto height). Flexbox can't produce this "first line shares space, later lines full width" shape — a flex item's box is always one rectangle — hence floats + normal block flow instead; see the CSS comment directly above `#viewBar` if this needs touching again. **`#viewBar` also needs its own `flex:0 0 auto`** — that's a separate concern (how `#viewBar` behaves as a flex ITEM of its parent `#content`, a flex column, not how it lays out its own children) that got dropped once already and let `#content`'s flex-shrink algorithm compress `#viewBar` below the floats' actual height whenever the window was short on vertical space, clipping/overlapping the toggle+level-filter against the table below; `#timelineMinimap` carries the same declaration for the same reason. **(Updated, this session, 2026-08-18, person-requested)** The row used to be always visible with zero files loaded (just an empty `#fhTabs`/`#levelBar`/`#breadcrumb` shell) — now `renderMainView()` hides `#viewBar` itself (`viewBarEl.style.display = hasFiles ? "" : "none"`, the `""` restoring the CSS class's own `display:flow-root` rather than hardcoding a value) whenever no file is loaded, so `#emptyState`'s centered hint is the only thing on screen instead of an empty toolbar row above it — see "No-file-loaded state" below for the other two hints removed alongside this. With files loaded, the row is visible exactly as before. **(Superseded this session — "Unified toolbar: Context/Filtered/Table/Plot" below, `docs/ui-implementation-plan.md`)** `#fhTabs` no longer hides for an extraction node — Table/Plot joined the same tab group Context/Filtered/Stacked already lived in, so an extraction node is now an ordinary node with its own Context/Filtered view too, and `#fhTabs` is only ever hidden with zero files loaded (`fhTabs.style.display` tracks `hasFiles`, same as `#viewBar` itself). `#levelBar`/`#btnPinBookmarks`/`#btnMultilineMsg`/`#btnColumns`/`#btnTextMatchHighlight`/`#btnHighlightMatchText` (`updateLogToggleVisibility()`) instead hide/show based on **which tab is active**, not the node's type: hidden while `fhActiveTab` is `"table"`/`"plot"` (none of the six apply to what's on screen there), visible for `"highlight"`/`"filter"`/the Stacked tab — so switching an extraction node from its Table tab to its Filtered tab shows the level filter/toggles again, the same as any other filter node. `renderExtractTable()` still calls `applyLevelFilter()` internally against whatever the quick-filter was last set to; there's just no visible pill row to change it from while Table/Plot is showing. Which view activating a node lands on (Filtered by default for a first-ever visit, or the Settings-driven remember-last/always-Filtered choice for a node visited before) is `applyActivationView()`'s call — see below; the `isExtract` branch inside `renderMainView()` itself is gone entirely; the function now always renders `#viewBar` the same way and only swaps which content component (`#fhSplit` vs `#extractWrap`) is visible based on `fhActiveTab`. See "Unified toolbar" below for the full picture, including the deliberate scope-cut versus the original plan's "physical slot row" idea (the six toggles/level filter/`#contextToolbar`/`#extractToolbar`/`#plotToolbar` all stay in their pre-existing DOM locations; only their show/hide condition changed). `#btnPinBookmarks` keeps its own `.toolbar-icon-btn`/`.active` look (an icon button, styled like the other header toggles it used to sit next to) rather than being restyled as a `.level-btn` pill — it's an additive OR toggle, not a subtractive level filter, and looking identical to the pills would misrepresent what it does; it's positioned in the same floated row as the level pills, not literally nested inside `#levelBar`. **Sizing (bugfix, same session)**: `.toolbar-icon-btn`'s fixed `29x29px` box is correct in the header, where every neighboring button is the same square — but here it made `#btnPinBookmarks` visibly taller than `#fhTabs`/`#levelBar`/`#breadcrumb`, which all get their height from `padding:4px` + `border:1px` + content instead of a fixed box (see `.crumb`'s own CSS comment for the underlying mechanic). Fixed with a `#btnPinBookmarks{width:auto; height:auto; padding:4px 8px}` override, scoped to the id (not `.toolbar-icon-btn` itself, so the header buttons using that class are untouched) — the button now sizes around its 12x12 icon exactly the way `.level-btn` sizes around its text, landing at the same row height instead of towering over it. See "Context view (Context/Filtered split)" → "Layout" for the toggle itself.

**Vertical centering (this session, 2026-09-07, person-requested):** the four floated controls in `#viewBar` (`#fhTabs`/`#levelBar`/`#btnApplyLevelToTree`/`#viewBar .row-actions`) carried a vestigial `margin-bottom:6px` left over from when the breadcrumb used to wrap *below* them inside the same row — with the breadcrumb long gone into its own `#breadcrumbBar`, that 6px made the row's effective bottom spacing (6px margin + 8px padding) larger than its 8px top padding, so the controls sat a few px above vertical center. The bottom margin was removed (now `margin:0 14px 0 0`, and `.row-actions` just `margin:0`), leaving the symmetric 8px top/bottom padding to center them. Keep the bottom margin off if this row is touched again — it only belonged to the pre-reorg breadcrumb-wrap layout.

**Breadcrumb bar removed (2026-09-23, person-requested).** The active filter chain used to be shown as a row of clickable `.crumb` chips (`#breadcrumb` inside its own `#breadcrumbBar` row between the timeline minimap and `#viewBar`). It is gone entirely — `renderBreadcrumb`, `#breadcrumbBar`/`#breadcrumb` and their CSS were deleted — and the chain is now drawn as highlighted connector lines in the filter tree itself; see "Tree row layout" → "Connector lines" below. **Round 4 (person screenshot, this session, 2026-08-14): #fhTabs is the actual height reference, not the pills.** Despite three rounds of matching `.crumb`/`.level-btn` to *each other* (padding, then `line-height:normal`, then `vertical-align:top`), the View-Toggle (`#fhTabs`) still rendered visibly taller than everything beside it — because none of those rounds ever compared against `#fhTabs` itself. Root cause: `#fhTabs` is structurally a **nested double box** — `.view-tabs`' own `padding:2px`+`border:1px`, wrapping `.view-tab`'s own `padding:4px 11px` — while `.crumb`/`.level-btn`/`#btnPinBookmarks` are each a **single box** (one padding+border layer). At equal content height, that's an inherent ~4px of extra chrome on `#fhTabs`' side that no amount of padding/line-height *parity between the pills* could ever close — the three earlier rounds were solving the wrong equation. Also discounted incorrectly by round 2's reasoning (see its comment above): a flex container's own auto height **is** affected by `line-height` when the flex item is inline text (verified empirically this session), so `.level-btn` was never actually immune to line-height the way that comment claimed. Fixed by pinning **explicit, non-`"normal"` `line-height` values** (removing all remaining font-metric/platform dependence — `var(--font-ui)`/`var(--font-mono)` are system-font stacks, which is exactly why "close but not quite" kept recurring across rounds) so the arithmetic is provably equal regardless of platform: `.view-tab`'s `line-height:12px` reproduces `#fhTabs`' own pre-existing rendered height (no visible change to the reference itself) — outer `padding(4)+border(2)` + inner `padding(8)+line-height(12)` = 26px total. `.level-btn`/`.crumb` get `line-height:16px` — `padding(8)+border(2)+line-height(16)` = 26px, matching exactly (the extra 4px of line-height is precisely what the missing nested-box chrome cost them). `#btnPinBookmarks` gets a direct `height:26px` (simplest option there, since it's already flex-centered — no line-height math needed). `.crumb-sep`'s top margin grew `4px → 7px` to keep its glyph roughly centered against `.crumb`'s now-taller box. Verified against a real Chromium render (not just jsdom, which has no layout engine and could only assert the declared CSS values): all four elements now measure exactly 26px. See `.view-tab`/`.level-btn`/`.crumb`/`#btnPinBookmarks`'s own CSS comments for the full arithmetic if this row needs touching again.

**Shortcut Manager (`Settings` → `Shortcuts`)** (this session, 2026-08-26, `FEATURE_BACKLOG.md` #48; header button removed in a same-topic follow-up, see below). The reference list of shortcuts used to be a permanent strip pinned to the bottom of the sidebar, then (2026-08-20) a standalone popup (`#shortcutsPanel`) behind a header `#btnShortcuts` button. Both the popup and (in the follow-up) the button itself are gone now — the section lives only inside Settings, reachable by opening Settings and clicking "Shortcuts" in its nav like any other section, with no dedicated shortcut of its own to jump there directly. That section has two parts. **(1) A rebindable-actions table** (`#shortcutBindingsList`, `renderShortcutBindingsList()`) — `SHORTCUT_ACTIONS`, an array of single-purpose, unambiguous keyboard-only actions (new filter, the find bar's open/next/previous, rename/edit filter, mute/unmute a filter, close file, toggle sidebar/detail, undo/redo, bookmark, add note, focus tree, the view switches, Context match navigation, zoom in/out, Focus Mode), each with a `default` combo (`{ctrl, shift, alt, key}`) and optionally a `browserDefault` used instead in the plain browser build (`!window.philogg`, read at call time) — `defaultShortcutBinding(action)` picks the right one and every default read goes through it; only `closeFile` has one (Alt+W in the browser, Ctrl+W on desktop). `comboFromEvent` falls back to `ev.code` (`KeyN`, `Digit5`) when Alt is down and `ev.key` is not a plain letter/digit (only then — `ev.code` is the US key position, so QWERTZ/AZERTY letters would swap otherwise), because macOS Option+letter yields a dead key / special character in `ev.key`. A per-action override lives in `shortcutBindingOverrides`, persisted as one JSON blob under `localStorage["philogg.shortcutBindings"]`; `getShortcutBinding(actionId)` returns the override or falls back to the default. The main keydown handler (see "Keyboard shortcuts" below) calls `matchesShortcut(ev, actionId)` for each of these instead of a hardcoded key comparison, so a rebind takes effect immediately with no other code path touched. Clicking "Change" sets `shortcutRecordingId`; the very first line of the main keydown handler checks that flag and, if set, routes the event to `onShortcutRecordingKeydown` instead of any binding logic — deliberately not a second `capture:true` listener, since a keydown event whose target is `document` itself (true both for this app's real dispatch and for every synthetic event the regression suite fires) reaches same-target listeners in plain registration order regardless of the capture flag, so a listener added later would actually run *after* the long-lived main handler, not before it; checking the flag first in the one shared handler sidesteps that. `findShortcutConflict` blocks assigning a combo already claimed by another rebindable action (surfaced via `#shortcutConflictNote`, not silently allowed to steal it); per-row and "Reset all to defaults" (`#btnResetShortcuts`) buttons both just delete the relevant override(s) and re-render. **(2) Fixed shortcuts** (`FIXED_SHORTCUTS`, an array of `{label, display}` — `display` is an array of key labels or `null` for a mouse-only action) for everything NOT in that table — mouse-driven actions (right-click, drag, double-click) and shortcuts too context-dependent to safely rebind in one place (Ctrl+C/X/V, Del, Enter, arrow keys). Updated 2026-08-26 (`FEATURE_BACKLOG.md` #55, person-requested cleanup): these are no longer a separate prose-heavy block below the table — `renderShortcutBindingsList()` appends them as extra rows into the SAME `#shortcutBindingsList`, styled `.shortcut-row-fixed` (dimmed, greyed-out text) and with no Change/Reset controls, so they read as part of one complete, at-a-glance list without looking editable. The old `.settings-section-desc` usage-instruction paragraph above the table ("Rebind the shortcuts below…") and the "Everything else (fixed reference, not rebindable)" subsection heading are both gone — the section title and the list speak for themselves.

### Fullscreen Focus Mode (FEATURE_BACKLOG.md #66)

A distraction-free, fullscreen mode, toggled by `toggleFocusMode(on)` (a
body-level `body.focus-mode` class flip — one toggle, so it never rebuilds
the tree; see the render-scope gotcha in `PROJECT.md`). It is desktop-only in
practice, because entering it also requires **real OS fullscreen**, which is a
Tauri-only capability (see `docs/desktop.md` → "F11 and Focus Mode").

What it does on enter:
- The header (`#toolbar`) is **removed entirely** — a single CSS rule
  `body.focus-mode #toolbar { display:none !important; }`, no hover reveal.
- The **Files & Filters** sidebar and the **Entry Detail** panel are
  **force-collapsed** to their edge-hover overlays, and their hover-reveal is
  **forced on regardless of the user's normal Settings** (`hoverExpandSidebar`/
  `hoverExpandDetail`). This deliberately **reuses the existing** collapse +
  hover-peek mechanism — `toggleSidebarCollapsed`/`toggleDetailCollapsed` and
  the `hoverExpand*` flags described under "Collapsible sidebar / detail
  panel" — rather than a second mechanism. The `hoverExpand*` flags are set in
  memory only (never written to `localStorage`), so the person's saved "open
  on hover" preference is untouched.
- `#viewBar` and the timeline minimap stay visible, and the
  active log/extraction view takes the freed space through the normal flex
  layout (no special maximize logic needed).

On enter `toggleFocusMode` records the prior state — each panel's collapsed
flag and both `hoverExpand*` flags — in `focusModePrevState`; on exit it
restores **exactly** what it captured (a sidebar that was already collapsed
before entering stays collapsed; a `hoverExpand*` that was off goes back off),
clears `focusModePrevState`, and removes the class.

**Exit paths**: F11 again (primary), or **Esc** (secondary). Esc's exit is
guarded by `anyEscapeOverlayOpen()` — captured at the top of the global Escape
handler *before* its own closes run — so a single Esc closes an open popup/
menu/dialog first and only leaves Focus Mode when nothing else is consuming
that Esc, never both at once.

**The F11 shortcut is rebindable** in the Shortcut Manager (new `toggleFocus`
action in `SHORTCUT_ACTIONS`, default `F11`), but it is only ever **handled**
under the desktop wrapper: the main keydown handler gates it on
`!!window.philogg`, so in the plain browser build F11 is not bound at all and
the browser's own F11 keeps priority. Entering/leaving asks the wrapper for
real OS fullscreen via `setDesktopFullscreen()` →
`window.philogg.setFullscreen(on)` (absent in the browser build, so that half
is simply a no-op there). Covered by `tests/philogg.regression.test.js`
Group 208 (page side; the desktop/Rust half isn't jsdom-testable).

## The three "active node" views

`renderMainView()` picks a view based on the active node's `filterType`, all mutually exclusive:

1. **Log view** (default) — virtualized (`ROW_HEIGHT = 28`, `BUFFER_ROWS = 10`) so it stays smooth at any file size; only the rows in/near the viewport are ever real DOM nodes. Scrolling renders once per frame and keeps the rows already in the window, building only the ones scrolling in, with a one-screen overscan — see PROJECT.md → "Known gotchas" ("Scroll renders"). Has the level quick-filter bar, click-to-select + arrow-key navigation, right-click context menu (filter before/after this, extract numbers), double-click **reveals the entry in the Context view** (see below) with flash highlight, and a resizable detail panel at the bottom (drag the handle above it) showing the full selected message with preserved line breaks. The tree sidebar's width (`#sidebarResizer`) and, in Stacked layout, the Context/Filtered split (`#fhSplitResizer`) are resizable the same way — see "Context view" below.
2. **Extraction table** (an extraction-capable `"text"` node — `nodeHasExtractableWildcards(node)`, see "filterType merge" below; there is no separate `"extract"` filterType anymore) — spreadsheet-style grid, not virtualized (extraction results are expected to be selective). Cell selection is a `Set` of `"row,col"` keys (not a rectangle) specifically so Ctrl+click can build **non-contiguous** selections (e.g. columns 1 and 3, skipping 2) — plain click/drag/shift-click still do contiguous ranges. Copy is always plain TSV (paste-ready for Excel) via `copyTextToClipboard` (Clipboard API with an `execCommand` fallback for `file://` contexts where the modern API may be restricted). The pattern is shown above the table as numbered, colored chips (`COLUMN_PALETTE`, cycles if >6 columns) with **bidirectional hover linking**: hover a column header/cell → its chip highlights; hover a chip → its column highlights; hover a row number → all chips highlight (the whole pattern produced that row). Double-click **reveals the entry in the SAME node's own Filtered view** (`revealInFilteredView`, this session's follow-up feature — previously `jumpToFullLog`'s destructive jump away to the raw file, back when an extraction node had no Filtered view of its own) — see "filterType merge" below.
   **Table/Plot are tabs in the main `#fhTabs` group, not a separate sub-toggle** (`docs/ui-implementation-plan.md`, this session) — see "Unified toolbar: Context/Filtered/Table/Plot" further down for the full picture, including how an extraction node now ALSO gets an ordinary Context/Filtered view of its own matched entries.
3. **Link pair view** (`filterType === "link"`) — each pair rendered as two individually-clickable/double-clickable rows joined by a visual brace with a Δ-time label between them. Right-click the brace = context menu on the *combined* pair entry (so "Extract numbers" works across both sides); right-click one row = context menu on just that side; double-click a row = reveals that row's real underlying entry in the Highlight view, same as the log view (see below — link view is a Filter-view "flavor" for this purpose, not a separate case).

**Log view and link view are both "Filter view" flavors**, each paired with a **Context view** — see the dedicated section below.

## Patterns tab (message-pattern clustering)

`#patternsWrap`, shown by `renderMainView()` when `fhActiveTab ===
"patterns"` (it replaces `#fhSplit`/`#extractWrap`, hides the entry-detail
panel like Table/Plot, keeps the minimap). It groups the active node's result
— `getEntries(activeId)` plus the level quick-filter, i.e. exactly what the
Filtered view lists, without pinned bookmarks — by message shape.

- **Normalization** (`normalizeMessagePattern`): the first line of the
  message (capped at `PATTERN_MAX_CHARS` = 400) goes through one regex pass
  (`PATTERN_TOKEN_RE`), alternatives in priority order: GUID → `<guid>`,
  IPv4 with optional port → `<ip>`, a `"quoted string"` → `"<str>"`,
  a Windows/UNC or multi-segment Unix path → `<path>`, a hex literal/hash
  (`0x…`, or 8+ hex digits mixing letters and digits) → `<hex>`, any other
  number → `<#>` (a sign only when not glued to a word: `Worker-3` →
  `Worker-<#>`). URLs keep their `//host/path` literal apart from numbers.
  Placeholders are private-use characters inside the group key, so a key
  splits back into literal text and placeholders unambiguously
  (`PATTERN_PH_SPLIT_RE`); `patternDisplayText` renders them as `<#>` etc.
  A per-group float mask records which number placeholders ever held a
  decimal point.
- **Columns**: Count, %, Level (the group's most severe level —
  lowest `levelSortRank`), Pattern, First/Last (time of day; line numbers
  for a plain-text file). Header click sorts (`patternsComparator`): Count
  starts descending, the rest ascending, a second click flips; Count
  ascending surfaces rare messages.
- **Actions** (`applyPatternAction`), delegated on `#patternsRows`: a plain
  click adds a text filter under the active node, `columns: ["message"]`,
  value built by `patternFilterValue` with every placeholder as `[*]`
  (`Axis [*] position [*] reached in [*] ms`) and lands on Filtered;
  Alt+click or the row's ⊘ adds the same as NOT and **stays on Patterns**,
  so noise can be peeled off step by step; the table icon ("Extract") types
  the number placeholders (`[*:int]`/`[*:float]` per the float mask) and
  opens the new node's Table; the arrow jumps to the group's first entry
  (`revealInFilteredView`). A plain click creates a node, so there is no
  double-click (the node switch would rebuild the row between the clicks).
  Each created node is one undo step (`"create"`, see
  `docs/persistence-and-sync.md` → "Undo/redo").
- **Rendering**: virtualized like the extraction table (one absolutely
  positioned block of rows inside `#patternsSpacer`, `EXTRACT_ROW_HEIGHT`
  per row, `makeScrollRenderer` on scroll). Row clicks never take keyboard
  focus (`mousedown` → `preventDefault`). Same unmitigated
  `count × rowHeight` spacer as the extraction table — a result with more
  than ~600k *distinct* shapes would hit the browsers' element-height
  ceiling (see PROJECT.md → "Known gotchas").
- **Computation** (shared with the Facet panel): `makeEntryAnalysis` caches
  one result per node result in a `WeakMap` keyed by the entry array
  (`node._cache`, or a file's `entries`), validated against its length and
  the level quick-filter. A pure in-place append (a tailed file) folds in
  only the new entries; any other change (a new array) rescans.
  `startEntryScan` runs results up to `ANALYSIS_SYNC_LIMIT` (50,000)
  synchronously and larger ones in 12ms slices through `queueTask`, showing
  "Grouping N entries… x%" meanwhile; starting another scan cancels a
  running one. A component benchmark (Node/V8, 1M synthetic messages) put the
  normalization at ~1.5s of total CPU — hence the slicing; not yet measured
  in the real app.

## Facet panel (value distribution per column)

`#facetPanel`, a column on the right of `#viewArea` (280px by default) — the row that
now holds whichever content component is displayed (`#fhSplit`,
`#extractWrap`, `#patternsWrap`, the empty state, the inline viewer, the
folder minimap). Toggled by `#btnFacets` (floated right in `#viewBar`), its

`philogg-facets-open`. It stays beside every tab (Context/Filtered/Table/
Plot/Patterns), is hidden with the inline viewer, folder minimap, empty
state and PiP, and reads "Not available for a link filter" on a `link` node
(pair entries have no single column values).

- **Level colour**: each value's name is drawn in the colour of the most
  severe level among its entries in the current result (`createFacetAcc`
  tracks a `levelSortRank` minimum per value, same ranking as the Patterns
  tab's Level column; `levelClass` → `.facet-value-name.lvl-*`). A value
  with only unrecognized levels keeps the default text colour.
- **Width**: `#facetResizer`, a grip on the panel's left edge (same look as
  `#sidebarResizer`), drags the width via `flex-basis` — dragging left
  grows it, clamped to 180px … `#viewArea` width − 240px
  (`setFacetPanelWidth`). The handle is a child of `#facetPanel`, so every
  path that hides the panel hides it too. Rows re-render per animation
  frame while dragging; one `renderMainView()` runs on release (plot/table
  widths). Session-only, like the sidebar/detail resizers.

- **Sections** (`facetColumnsFor`): every middle column of the loaded
  formats (`activeColumnDefs`: Thread/Location/Method/custom columns), then

  Message are left out (near-unique). Each section lists the top

  (active node + level quick-filter), cached and time-sliced by the same

- **Clicks** (`createFacetFilter`) add a child of the active node: Level →
  a `level` node for that bucket; Source → an `idset` node of that source's

## Context view (Context/Filtered split)

Two views of the same file, introduced together as `#fhSplit`. The **Filter view** (UI label "Filtered") is the pre-existing log/link view, narrowed by the active filter-tree node. The **Context view** (UI label "Context") shows **the active node's own result with the log around it**: the matches, and everything the filter rejected collapsed into expandable gap strips between them. Internally every identifier still says "Highlight" (`renderHighlightView`, `#highlightWrap`, `highlightColorMap`, `fhLayout`, `fhActiveTab === "highlight"`, …) — the same naming compromise the earlier "Full" rename made, for the same reason: a full internal rename is a much bigger, riskier diff than the UI change it would serve. Context-view-specific identifiers added since do use a `context*` prefix (`buildContextView`, `contextGaps`, `contextStrips`, …).

**Why it was reworked** (person-reported): the view used to be `state.nodes[rootId].entries` — the root file's raw entry array, *regardless of `state.activeId`*. That made it pixel-identical on a filter node and on a file node, so people read "Full" as having switched them onto the file node and were surprised the filter was still active. There was no wrong signal to correct; there was no signal at all. Reframing it as "your result, seen in context" is what the view was for in the first place (*"den Kontext der Filterergebnisse sehen, ohne im Tree umherzuspringen und immer wieder auf dem Root-Knoten zu landen"*), and it also retires the misleading Full/Filtered opposition — "Context" and "Filtered" describe a containment relation, not two filter strengths.

**What counts as a match** (`buildContextView`): `getEntries(state.activeId)` — the active node's own result set. Deliberately **not** `applyLevelFilter()`'d and not unioned with pinned bookmarks. Person-stated rule: *"egal was für eine Art Filter vorausging: der Output sind die Ergebnisse, alles andere ist Kontext"* — the level quick-filter (in `"explicit"` mode) hides result rows from the *Filtered view's display*; they never leave the result set, so they stay matches here. That keeps the older "the level filter must not narrow the whole-file view" requirement true, and `renderLevelBar()`'s click handler still calls `revealFilteredView()` so a level change is visible where it actually applies. `link` nodes contribute their real underlying entries via `getTupleEntries()`, not their synthetic pair ids — exactly as `computeHighlightMap` treats them.

**Built only while on screen, match part memoized.** `renderMainView` builds the Context view (`renderHighlightView`) only while it is visible — Stacked, or its own tab (`contextViewVisible`); hidden, it is only marked stale (`contextViewStale`), and whatever reveals it builds it then: `showFhTab("highlight")`, `applyFhView("stacked")`, a jump into it (`revealInHighlightView` renders it itself). Inside a `render()` (`renderDepth`), a reveal leaves the build to that render's own `renderMainView`. The nav history doesn't record a stale list's anchor, only its scroll position. Of the build itself, the half that depends only on the matches — the match id set, the gaps, each match's ordinal (`contextMatchPos`) — is memoized by `contextMatchesAndGaps` per (active node, its `getEntries()` result, the root's entries array + length + `_orderVersion`, bumped by `invalidateOrderIndexMap` on an in-place reorder); `contextMatchIds`/`contextGaps`/`contextMatchPos` are the memo's own objects, read-only like they always were. Only the expansion-dependent rows, strips and runs are rebuilt on every call. A non-link result is normally a subsequence of the root's entries, so its root indices come from one walk along both arrays; a link node's flattened pairs (and anything else that doesn't fit, an "or" re-sorted by ts) go through `buildOrderIndexMap`. Measured on 650k entries in Chromium: a 162k-match level filter created with the Filtered tab showing went from ~530 ms to ~100 ms; a re-render with the Context tab showing from ~230 ms to ~100 ms; switching to the Context tab now carries the one build (~125 ms) that every render used to pay. Tests: GROUP 270.

**On a file node there is nothing to be outside of**: `contextActive` stays `false`, no row is marked, nothing is collapsed, and the view renders the plain whole file exactly as it did before the rework. That is what keeps its other, older purpose available — tracking two or three coloured highlight rules across a whole file while the Filtered view stays narrowed to something specific.

**The gap model.** A gap is the root-file index range `[start, end)` hidden between two consecutive matches, plus the leading range before the first match and the trailing one after the last. A gap is **not binary**: `contextExpansions` is a `Map` from `gap.start` to the list of root-file index ranges `[{from, to}, …]` inside that gap that are currently **revealed** — sorted, disjoint and merged, an invariant established by the only three writers (`revealContextRange`, `hideContextRange`, and the wholesale re-seeding in `buildContextView`). That list is what makes each end of a hidden stretch expandable a step at a time and independently of the other (see "Revealing a step at a time" below), and it is also what an auto-expansion around a jump needs, since that reveals a window in the *middle* of a gap. `currentHighlightViewEntries` stays a flat array of real entries (matches plus revealed context rows, in root order), so the ~15 places that consume it — minimap, selection, Shift-click ranges, arrow-key nav, `captureViewAnchor` — needed no changes. `contextExpansions` is module-level and session-only, deliberately **not** on the node: that keeps it out of `cloneSubtree`/`snapshotSubtree`/`serializeFilterBranch`/`serializeFilterTreeForCache`, which every persisted node field has to be threaded through. It survives re-renders of the same node (a tail tick or a colour edit never hides what you just revealed) and is dropped wholesale when `state.activeId` changes, since a different result set makes the old index ranges meaningless. A companion list, `contextAutoRanges` (`[{gapStart, from, to}]`), holds exactly the ranges `applyContextJumpExpansion` revealed for the *last* jump and that nobody has touched by hand since — i.e. exactly what the *next* jump is allowed to take back (see "Jumping in" below). Every hand action drops the gap it touched out of that list (`forgetAutoRangesForGap`), which is the whole mechanism behind "what you revealed or hid by hand keeps that state"; a jump also only records what it *actually* revealed (`contextHiddenPartsOf`), so a range that was already open by hand stays hand-owned. Stacked layout always **seeds** a freshly-activated node's gaps fully revealed, regardless of `contextInitialExpansion` below (person-requested — Stacked's Context pane sits right next to the plain Filtered result, so there is less reason to hide anything there); it is a one-time seed like any other, not a standing override, so manually hiding a run in Stacked survives a flip to Tabs and back.

**Revealing a step at a time** (person-requested, 2026-09-02 — the binary gap that shipped before this made "show me a bit more" impossible to express). Settings → Behavior → "Lines revealed per step" (`contextExpandStep`, `philogg-context-expand-step`, default **10**, clamped 1–1000) is the width of one expansion step *per direction*. A still-hidden stretch renders as up to three filler rows (`appendContextFillers`, all of them `.ctx-gap-placeholder`-shaped so the virtualization math stays one number):

```
[match A]
 …revealed rows…            ← a run against the top of the stretch
 Show more (+10)            ← only while more than one step is still hidden
 … 19 lines                 ← reveals the whole remaining stretch
 Show more (+10)            ← only while more than one step is still hidden
 …revealed rows…            ← a run against the bottom of the stretch
[match B]
```

A "Show more (+n)" row exists only on a side that already has revealed rows against it (there is nothing to grow otherwise — a click on the match row itself is what opens the first step, see "Jumping in") and only while the remainder is longer than one step, since below that it would do exactly what the "… N lines" row next to it does. The two ends are therefore separately operable: growing the run above a stretch never also grows the one below it. `buildContextView`'s `addHidden` is the one place that decides which fillers exist where, and the ordering — step row *between* its own run and the "… N lines" row — is what keeps each button next to the rows it grows.

**What a step is MEASURED IN is itself a setting** (`FEATURE_BACKLOG.md` #79, scope narrowed by the project owner from that entry's own broader "make the whole Context view window configurable" idea down to this concrete unit toggle on the mechanism above). Settings → Behavior → "Expand step counts in" (`contextExpandStepUnit`, `philogg-context-expand-step-unit`, `"entries"` **default** | `"time"`) picks what `contextExpandStep` (above) and a new counterpart, "Timespan revealed per step (ms)" (`contextExpandStepMs`, `philogg-context-expand-step-ms`, default **500**, clamped to a minimum of 1 with **no upper cap** — same as the Time-context-filter dialog's own ms fields), each mean. The two step-width rows are mutually exclusive in Settings — only the one matching the current unit is shown, the other carries its own `.hidden{display:none}` CSS rule (this codebase has no generic `.hidden` rule; every toggled row needs its own). `"entries"` mode is `addHidden`'s original logic, byte-for-byte unchanged: a step is `hs + contextExpandStep` / `he - contextExpandStep`, shown while more than one step remains hidden. `"time"` mode instead computes two candidate boundaries via the same `lowerBoundByTs`/`upperBoundByTs` binary-search helpers the minimap and the Time-context filter already use — a top step's boundary is the first index whose timestamp exceeds *the row above the stretch's own timestamp* + `contextExpandStepMs` (clamped so it always reveals **at least one entry** and never crosses past the far end of the stretch); a bottom step's boundary is the mirror, measured backward from the row below the stretch. Whether a step row is shown at all is derived from those SAME two boundaries (`topBoundary < he` / `bottomBoundary > hs`) rather than a separately-computed "how much time is left" check — deriving both from one pair of numbers is what keeps them from ever disagreeing at an edge, e.g. exactly one step's worth of time remaining in the stretch (where the step would show the same thing as the "… N lines" row and is correctly withheld, same rule as entries mode). The entry COUNT a time-mode step reveals is therefore **not fixed** — it varies with how dense the log is at that edge, which is the whole point: a fixed line count reveals wildly different amounts of wall-clock time depending on how bursty the file is around the spot you're looking at, while a fixed timespan reveals a consistent "peek this far either way" regardless. The "Show more" row's own label/tooltip follow suit — in time mode they read the fixed configured duration (`formatMs(contextExpandStepMs)`, e.g. "Show more (+500ms)"), not the entry count the click happens to reveal here, since showing that count would promise a precision the setting doesn't actually offer. The **"… N lines" row is deliberately unaffected by the unit** (person-requested: "if less than that is available just the '...n line' as by now") — it always reports the exact remaining entry count in both modes, since it reveals the whole stretch regardless of how that stretch's edges were measured.

**A step click grows its own side and holds the other one still** (person-reported: *"Der visuelle Eindruck soll sein: 'Ich bin noch an der gleichen Stelle und sehe oben/unten jetzt mehr', also ohne einen zusätzlichen Sprung"*). Each of these actions names the one row whose on-screen position must survive the rebuild, and `commitContextExpansionChange` pins it there (`captureContextRowPin`/`restoreContextRowPin` — an entry id plus its pixel distance from the scroll container's top edge; the row is found again in the rebuilt list through `contextWouldBeIndex`'s binary search rather than a `findIndex` over what can be the whole file):

A step row **belongs to the revealed run it sits against**, and that run is what stays put while the block unfolds *away* from it — so the step at the bottom of a block unfolds downwards, the one at its top unfolds upwards. (The first cut had this the other way round, holding the far side, and a person reported that every block therefore grew in the direction opposite to the button they had just clicked.)

A **"… N lines" row has no such run**: it is the stretch *between* two blocks — in the normal shape it has a revealed run on both sides — and it reveals all of it, so neither side is "its own". It holds whichever side the **selection** is on instead (person-requested, weighed against just always holding the row above: that is deterministic but got the "reading below the stretch" case backwards, and this is the only rule that gets both cases right). Same idea said differently: keep the row the person is actually working on where it is. Under the auto-expand default the selection is always the match whose context borders the stretch, so it reads as "the block I am reading stays put and the lines appear on its far side". A selection that is absent, in another file, or *inside* the stretch (no row to hold yet) falls back to holding the row above.

| action | pinned row | effect |
|---|---|---|
| top step (`side: "top"`, sits at the **bottom** of its block) | the row *before* the filler group — i.e. its own run's last row | the block unfolds **downwards**, what follows the stretch is pushed down |
| bottom step (`side: "bottom"`, sits at the **top** of its block) | the row *after* the group — i.e. its own run's first row | the block unfolds **upwards**, taking `scrollTop` with it |
| "… N lines" | the side the **selection** is on: the row *after* the group when the selected entry sits at or below the stretch's end, the row before it otherwise (`contextSelectionAtOrBelow`) | the block being read stays put and the lines appear on its far side |
| collapsing a run | the row before the run | folds up from below, nothing above moves |

This is deliberately **not** `captureViewAnchor`/`restoreViewAnchor`, which the whole-view actions (expand-all/collapse-all) and every other list-changing action in the file still use: that pair prefers `state.selectedId` and, when the selected row is off screen, reveals it *centred* — which is exactly the extra jump being reported here, since the selection at the time of a step click is usually somewhere else entirely. An index outside the list ("nothing on that side to hold") leaves `scrollTop` untouched, which produces the same effect.

**Filler rows** (`.ctx-gap-placeholder`, `appendContextFillers`): one slightly dimmed row per filler — an ellipsis icon (`ICON_ELLIPSIS`) plus "*N* lines" for the stretch itself, a plus (`ICON_PLUS_SMALL`) plus "Show more (+*n*)" in the accent colour for a step row (`.ctx-show-more`). The whole row is the click target (same convention as `.tree-row`/`.crumb`), not just the icon. **The label is centred on the visible area**, not on the row (person-requested): the row can be far wider than the panel now that the view scrolls horizontally, so the label lives in its own `.ctx-filler-inner` box — `position:sticky; left:0` against `#highlightBody`, a negative margin undoing `#highlightRows`' own `--rows-pad-left` so "pinned at 0" means the panel's left edge, and a width `renderHighlightVisibleRows` sets from `highlightBody.clientWidth`. It therefore stays on the middle of what is actually on screen at any horizontal scroll offset. They render as plain block siblings after their preceding row — the same shape `appendNoteRow` uses — with their height folded into the virtualization math (see "Rendering" below). Revealed rows cost no filler at all: each carries its run's own line instead (see "Row treatment"). `contextStrips` maps a row index → the **array** of fillers rendered directly after it (`-1` = above row 0), so one row can carry several; `contextRuns` lists each contiguous revealed run once (`{firstRow, lastRow, gapStart, from, to}`) and `contextRunAt` binary-searches it per visible row, rather than keying a map by row — a fully expanded file would otherwise cost a map the size of the file.

**Row treatment**: a match gets `ctx-row ctx-match` plus the **same `.ctx-anchor-dot` the `context`/`countContext` filter already draws next to its reference entries in the Filtered view** — one dot per result, in the gutter lane, at full row width and with no indentation. It used to reuse that filter's `.ctx-bracket` instead; that was dropped (person-requested, 2026-09-02) because a bracket says "these rows belong together", which is true of a time window but false of a filter result whose matches are scattered across the file — and it occupied the lane the run line now needs. A revealed context row gets `ctx-context` and **no treatment of its own at all**: not dimmed (that fought the `.lvl-error`/`.lvl-warn` row tinting, the most important colour information in a log view) and, since 2026-09-02, not indented either. Instead every revealed row carries `.ctx-run-line` — a full-row-height `border-left` in that same gutter lane, so stacking the rows of a run draws **one continuous line** from its first row to its last, capped at either end by a caret (`.ctx-run-cap`, pointing INWARD toward the run's own centre — the direction it collapses to) pointing into the fold; a single-row run gets one cap, not two. The line *is* the button: clicking anywhere along it collapses the whole run (`collapseContextRun`), which is what makes a block foldable from wherever you happen to be reading it, and its handler `stopPropagation`s so the click doesn't also select the row underneath. **Hovering any one slice highlights the whole run** (person-requested): since each row's slice is its own separate DOM button, plain CSS `:hover` only ever lit up that one segment — every slice of a run now carries a shared `data-run-id` (`run.firstRow`), and `mouseenter`/`mouseleave` (`makeContextRunHandle`) toggle a `.ctx-run-hover` class across every slice sharing that id (queried within `#highlightRows`), including both end caps' carets, so the whole line lights up together no matter which point along it the pointer is over. Dots and lines share one x (`--ctx-lane-x`, defined once on `#highlightRows.ctx-active`), which is why the marker column reads as one thing: a dot per result, a line per revealed run — and why no log text ever moves sideways when a run opens.

**Toolbar** (`#contextToolbar`, `updateContextToolbar`, wired once by `initContextToolbar`): a real row **inside the table, directly under `#highlightHeader`** — person-requested, 2026-09-02, replacing the floating corner chip this used to be (and with it the "which corner" setting the floating version needed, since there is no corner to pick any more). This session (2026-09-04, "Per-view toolbars"/"Filter-Toolbar" reorganization above) it grew a display-toggles group ahead of the original navigation one: five of the six log-display toggles (`.toggle-notes`/`.toggle-multiline`/`.toggle-columns`/`.toggle-textmatch`/`.toggle-highlightmatch` — no `.toggle-pin`, meaningless here), then the original navigation group: `‹`/`›` (previous/next match, `moveContextMatchSelection`, `ICON_CARET_LEFT`/`ICON_CARET_RIGHT`) and a bare "*n* / *m*" position readout (`#contextNavLabel`; the position comes from `contextMatchPos`, an id → ordinal map built during `buildContextView`'s own walk, so it can refresh on every selection change without an O(rows) scan) — the three wrapped together in one `.stepper.stepper-nav` pill since this session's UI harmonization (see "Shared 'stepper' control" below), so the buttons and the label between them read as one connected control instead of three separately-bordered pieces — and **three** fold buttons: reveal one expansion step around every match (`#ctxExpandAround`, `ICON_EXPAND_AROUND`, `expandAroundAllMatches` — the same window a jump opens, via `contextStepEdge`, so it honours `contextExpandStepUnit`; like its siblings it sets an absolute state rather than adding to what is open, and the result is hand-owned, so no later jump takes it back; disabled when there are no gaps), reveal everything and collapse everything (`ICON_EXPAND_ALL`/`ICON_COLLAPSE_ALL`, `setAllGapsExpanded`), the latter two each disabled when they would do nothing. (The row-actions button group — filter-CREATING controls — lives in `#viewBar` instead, not here; see "Per-view toolbars" above for why.) All of them are `.toolbar-icon-btn` — the app's one icon-button shape, full 28x28 size (a brief 22px scoped-down override was reverted the same session — see "Per-view toolbars" above); icon-only, each explained by its `title`. The nav group's markup is static and only its label and the `disabled` flags are refreshed per render; the toggle group's `.active` state is refreshed by the toggles' own update functions instead. Hidden entirely on a file node (nothing to navigate or fold) and whenever the Context panel isn't the one on screen — this hides the WHOLE toolbar, toggles included, not just the nav group.

**The bar is in flow, not overlaid** — it takes `CONTEXT_TOOLBAR_HEIGHT` (30px, and the CSS `height` must stay equal to the constant) out of `#highlightBody`'s viewport rather than covering log lines. On its own that would slide every rendered row down by exactly that much the moment the bar appears, so `setContextToolbarVisible` compensates the scroll position by the same number in the same step, leaving each row where it already was on screen (person-requested). The compensation is deliberately scoped to a bar appearing/disappearing **while the panel stays on screen** — activating a file node, or a filter one, without leaving the Context view. A tab switch hides or shows the whole panel, where there is no visible movement to cancel out and compensating would only perturb the reading position the pane remembers, so `updateContextToolbar` passes `false` there.

**Match-to-match navigation**: `Ctrl+↓`/`Ctrl+↑` (`nextMatch`/`prevMatch` in `SHORTCUT_ACTIONS`, rebindable) walk the real matches, skipping revealed context rows — the point being that you can work the result without going back to the tree. Their check sits right after the Alt+Arrow tree-nav block and ahead of *both* arrow-key blocks below it: an explicit modifier chord should do its one thing regardless of which region holds focus, and the plain-row block matches on `ev.key` alone with no modifier check, so it would otherwise swallow `Ctrl+Arrow` outright. With no filter active the chord degrades to plain row-to-row navigation rather than doing nothing.

**Initial state** — Settings → Behavior → "Context view starts out" (`contextInitialExpansion`, `philogg-context-initial-expansion`, plain `localStorage` preference): `"aroundJump"` (**default** since 2026-09-02, person-requested — labelled "Auto expand around the selected row": nothing revealed up front, but landing on a row reveals `contextExpandStep` lines on either side of it and takes the previous jump's window back, see "Jumping in" below), `"collapsed"` (nothing revealed until asked for — the view then opens *as* the filter result), or `"expanded"` (everything revealed, i.e. the pre-rework whole-file view, still collapsible run by run). Governs the **Tabs** layout's Context tab only — Stacked always seeds fully expanded regardless of this setting (see "The gap model" above).

**Jumping in still works exactly as before** — double-click in the Filter view, `Enter` on a single selection, a link-view pair row — all still route through `revealInHighlightView(entry, …)`, which selects the entry, reveals the Context panel and scrolls it there preserving the row's on-screen pixel offset, **without** touching `state.activeId` or the level filter. It first calls `applyContextJumpExpansion(entryId)`, which makes the target reachable — a correctness requirement, not a preference, since a target with no row has nowhere to be scrolled to — so something happens for every setting value: `"collapsed"`/`"expanded"` reveal the whole gap the target is buried in and nothing else. `"aroundJump"` instead reveals a `contextExpandStep`-wide window on either side of the target (clipped to whichever gaps that window falls in, which covers the target itself on the way) and **takes the previous jump's own window back** in the same step.

`contextExpandStepUnit` (see "What a step is MEASURED IN is itself a setting" above) governs this window's width the same way it governs a "Show more" step's: in `"entries"` mode the window is `[idx - contextExpandStep, idx + contextExpandStep + 1)` in root-file indices, unchanged from before this setting existed; in `"time"` mode it's instead `[lowerBoundByTs(all, refTs - contextExpandStepMs), upperBoundByTs(all, refTs + contextExpandStepMs))` — the same pair of binary-search helpers `addHidden` uses, applied to the target's own timestamp rather than to a neighboring revealed row's. Everything downstream of that window — clipping it to the gaps it falls in, the `contextAutoRanges` bookkeeping, taking the previous jump's window back — is entirely unit-agnostic: both modes produce the same shape of root-file index range, so nothing else in this mechanism needs to know which one is active.

**Switching onto the Context tab is a jump too** (person-reported, 2026-09-25: the surroundings only opened after the next click): `showFhTab("highlight")` runs `expandContextAroundSelection()` — `applyContextJumpExpansion(state.selectedId)` under `"aroundJump"`, nothing under the other two settings — and rebuilds via `renderHighlightView` when that changed anything, whose anchor pair keeps the selected row where it was or centres it. A stale Context view (hidden while `render()` ran) still has the previous `contextGaps`, so there — and when the switch happens inside a `render()` — it only sets `contextSelectionExpansionPending`, which `renderHighlightView` consumes right after `buildContextView`.

**Match navigation is a jump too** (person-requested follow-up): `moveContextMatchSelection` — the toolbar's `‹`/`›` buttons and `Ctrl+↑/↓` — routes through the same `applyContextJumpExpansion` before it selects, so under `"aroundJump"` walking match to match carries **one open window along the file** instead of leaving a trail behind it: the lines around the match you land on are revealed, and the ones the *previous* jump revealed are hidden again in the same step. What that step may take back is exactly `contextAutoRanges` (see "The gap model" above) — and `hideContextRange` removes precisely that range, splitting a revealed run that merely straddles it, so a hand-revealed stretch that overlaps the jump's window survives intact; a range that was already open by hand when a jump wants it is never adopted in the first place (`contextHiddenPartsOf`). Under `"collapsed"`/`"expanded"` nothing is hidden and nothing is tracked: the arrows leave every stretch exactly as it is (a match always has a row of its own, so the correctness half never fires there). Because the row list changes underneath it, `moveContextMatchSelection` rebuilds (`buildContextView` + `rebuildHighlightOffsets`) before selecting and lets `selectHighlightEntry` look the row up in the **new** list rather than passing the index it computed pre-expansion; it deliberately uses no `captureViewAnchor`/`restoreViewAnchor` pair (unlike a hand action's `commitContextExpansionChange`) since centering the target is what positions the view.

**A plain click on a match row is a jump too** (`selectContextRowByClick`, same person-requested round): picking another result with the mouse reveals and hides exactly as walking there with the arrows does, and the toolbar's "*n* / *m*" follows because it follows the selection. Two deliberate differences from the arrows. First, **only a real match counts** — a click on one of the revealed context rows is not a move to another result (and the chip has no position to show for it), so it selects and nothing else; a Shift/Ctrl click is a multi-selection gesture and is routed straight to `selectHighlightEntry` too, since rebuilding the list mid-gesture would move the rows out from under it. Second, **the view must not be re-positioned**: the clicked row has to stay exactly where the pointer left it, and what opens above it is not the same height as what shuts above it, so `scrollTop` no longer means the same thing after the rebuild. The row's on-screen offset is captured *before* it (`captureRowScreenOffset`, the pair `revealInHighlightView` already uses) and restored against the **new** offsets array via `scrollToHighlightIndex`'s `opts.offset` — `selectHighlightEntry` forwards that option for this. Accepted consequence, and why this is confined to the case that actually changes the list: a rebuild replaces the row's DOM node, so while `"aroundJump"` is on, a native `dblclick` on a Context match row no longer fires (the DOM-identity trap `updateSelectedRowClass` exists to avoid). That handler only scrolls the row into view, which the offset restore has just done. `moveHighlightSelection` has the matching courtesy: a selected entry with no row here (hidden in a gap, or left over from another node) continues from its **would-be** position (`contextWouldBeIndex`, a binary search over the root order) instead of snapping back to the top of the list — the same idea the Filtered view's temp anchor already applies.

**Turning on a highlight rule**: each filter-type tree row (not file rows, not `extract` rows — see `renderNode`) has a small colour **swatch** button where the old multi-select checkbox used to be (see "Tree interactions" below for where that checkbox went). Click it to open a small custom colour picker (`#colorPickerPopup`) — a hue wheel (`conic-gradient` disc, click anywhere to pick a hue at a fixed 68%/55% saturation/lightness) plus a row of curated presets, deliberately **not** the native `<input type="color">` (Windows' native picker UX varies too much to be predictable here). Right-click the swatch, or "Clear colour" in the picker, clears it. The colour **is** the on/off state — no separate boolean; an uncoloured node just isn't a highlight rule. Two colours can coincide across different nodes (not deduplicated — may be intentional grouping) and travel with the node through filter save/load JSON, copy/paste (`cloneSubtree`), and undo/redo (`snapshotSubtree`/`restoreSubtree`), the same way `inverted`/`bakedA`/`bakedB` do.

**Computing matches** (`computeHighlightMap(fileId)`): walks every node under the file (not just the active chain — a highlight rule anywhere in the tree should show up), and for each coloured filter node adds its colour to every entry it matches, via `getEntries(node.id)` — cheap since `getEntries` is already memoized per node. `link` nodes are a special case: their results are synthetic pair entries, not real ones, so every real underlying entry — via `getTupleEntries(pair)`, which recurses through arbitrarily many nesting levels for a chained/multi-hop link, not just `pair.first`/`pair.second` one level deep, see "Link filter" → "Chained links" — gets the colour instead of the synthetic pair id. A row matching several rules gets several small colour markers (`.hl-marker`, thin stripes in the left gutter) rather than one blended colour — there's no natural priority between arbitrary user rules the way `LEVEL_SORT_RANK` orders log levels, so no attempt is made to pick a "winning" colour. **Shown in both views**: originally Full-view-only, `renderVisibleRows()` (the Filtered view) now renders the same markers from the same `highlightColorMap`, computed once per `renderMainView()` call (before either view's own render) rather than twice, so the Filtered view's first paint after a node/filter switch already has the right colours instead of showing the previous node's map until the next scroll. **A coloured `text` rule also underlines the matched substring itself**, in the rule's own colour, inline in both views' rows and the entry-detail panel — see `docs/filters.md` → "Highlight-rule match text" for how that stacks with the filter path's own match marking and with several rules covering the same characters; its view-bar toggle is `#btnHighlightMatchText`, default on. The Filtered view's own `.ctx-bracket` (time-context filter) uses the same left gutter slot — a row that's both context-bracketed and highlight-matched shows both markers overlapping; accepted as a known edge case rather than adding a second gutter lane.

**Filter-path match marking stays Filtered-view-only** (`textMatchHighlightInRows`, Settings → Behavior → "Show matches in log rows"): `renderVisibleRows` marks the active filter path's matched substrings inline via the `buildMatchMarkContext`/`markFieldHtml` bundle (alongside the highlight rules, above). The Context view is deliberately filter-path-independent — `renderHighlightVisibleRows` builds that same bundle with `includeFilterMatches = false`, so a row there carries only the highlight rules' marks, never the active filter's own. The two toggles (`.toggle-textmatch` and `.toggle-highlightmatch` — see "Per-view toolbars" below for why they're classes, not ids) are independent.

**Selection stays unified**: `state.selectedId` is shared between both views (it always was, for the detail panel — see `updateDetailPanel`), so `updateSelectedRowClass` syncs the `.selected` class on whichever of `#tableRows`/`#highlightRows` currently has that row rendered, regardless of which view the click came from; it also refreshes the nav chip, whose "*n* / *m*" follows the selection. Plain click in either view just selects (`selectEntry`/`selectHighlightEntry`) — no scrolling of the other view.

**Layout**: a single tri-state toggle (`#fhTabs`, three buttons: "Context" / "Filtered" / "Stacked") — `applyFhView(view)` is the one entry point, `fhLayout` ("tabs" | "stacked") and `fhActiveTab` ("filter" | "highlight") are still the two pieces of underlying state, persisted to `localStorage` the same way the theme toggle is (a display preference, not session/filter data). "Context"/"Filtered" set `fhLayout` to `"tabs"` and pick which panel shows; "Stacked" sets `fhLayout` to `"stacked"` directly, showing both panels at once, **Context on top / Filtered on the bottom** (that's the actual DOM order inside `#fhSplit`, not a CSS `order` override) — `#filterSlot` at a resizable explicit height (`#fhSplitResizer`, drag handle between the two panels, same mechanism as the detail panel's resizer below, and same bottom-panel sign convention: dragging the handle down shrinks the panel below it), `#highlightWrap` filling whatever's left above it. Session-only, not persisted, same as the detail panel height. Stacked keeps its point after the rework: the result in context on top, the bare result underneath. The Filtered panel still carries a Stacked-only `.fh-panel-badge`; the Context panel's badge became `#contextToolbar` (above).

`#fhTabs` itself lives inside `#viewBar`, alongside `#levelBar` — the row now holds ONLY these two, identical across every tab including Table/Plot (see "Per-view toolbars" below for this session's reorganization); `#breadcrumb` moved into its own `#breadcrumbBar` row right underneath. Only `#fhTabs`'s own visibility is toggled by `renderMainView()` (hidden with no file loaded); `#levelBar`/`#breadcrumb` stay visible in every state.

**Rendering**: the Context view has its own complete copy of the Filter view's virtualization scheme (`renderHighlightView`/`renderHighlightVisibleRows`/`scrollToHighlightIndex`/`setHighlightScroll`, `#highlightBody`/`#highlightSpacer`/`#highlightRows`) — a second, independent scroll container. It reuses the Filter view's `.row-grid`/`.log-row`/`.col-*` CSS wholesale (extended the relevant ID selectors rather than duplicating rules) so the two views' rows line up visually. Two things differ from `renderTable()`:

- **It always uses the offsets-array path.** Filler rows make row tops variable regardless of `state.multilineMessages`/`state.showNotes`, so `rebuildHighlightOffsets()` always builds `highlightRowOffsets` via `buildContextRowOffsets(entries, strips)` — same contract as `buildRowOffsets` (`offsets[i]` = pixel top of row `i`, one extra trailing slot for the total), with each row's own fillers' height (`fillers.length * CONTEXT_STRIP_HEIGHT`, since a row can carry more than one) added to the row they follow and the *leading* fillers, which have no row to follow, folded into `offsets[0]`. Keeping that contract intact is what lets `findOffsetIndex`/`topVisibleEntryId`/`captureViewAnchor`/`restoreViewAnchor`/`minimapRenderedSpan` keep working unchanged; the one place that has to know is `renderHighlightVisibleRows`, where row 0's window must still start at `0` rather than at `offsets[0]`. `minimapRenderedSpan` was re-keyed from `needsRowOffsets()` to the offsets array's own presence for the same reason. In the common (collapsed) case this is *cheaper* than before the rework: the array is sized by the number of visible rows, i.e. the match count, not the whole file.
- **It scrolls horizontally, like the Filter view** (person-requested, 2026-09-02 — it used to clip with an ellipsis instead). Same two-part mechanism, mirrored: `.col-msg{min-width:max-content}` now covers `#highlightRows` too so the message track refuses to shrink below its own text; `syncHighlightRowsWidth()` gives `#highlightRows` an explicit width from the widest message in the current list (`cachedMaxHighlightMsgPixelWidth`, recomputed in `rebuildHighlightOffsets` alongside the row heights) whenever that exceeds the viewport; and `syncHighlightHeaderWidth()` plus a `scroll` listener keep `#highlightHeader` — a flex *sibling* of the scrolling body, not a descendant — the same width and at the same `scrollLeft`. The one difference from `syncTableRowsWidth`: the padding is read off the element instead of being hardcoded the way `TABLE_ROWS_H_PADDING` is, because this one changes with `ctx-active` (the marker lane) as well as with `--color-mark-w`.
- **It does not reset scroll to the top on every render.** The Filter view resets on every tree/filter change because that always means "new content" there; resetting the Context view every time would make it useless as a stable reference while browsing the Filter view. It only resets when the root file itself changes (`lastHighlightRootId`). Opening or closing a gap goes through `captureViewAnchor`/`restoreViewAnchor` (`setGapOpen`/`setAllGapsExpanded`) so rows appearing above or below a fold push the content visually instead of yanking the scroll.

## Find bar: incremental find in the current view (`FEATURE_BACKLOG.md` #3)

`#findBar` is a non-destructive search over whichever log view is current, so "just look for this string once" no longer costs a filter node (Ctrl+F always creates one). Search first; promote the search to a filter only when it's worth keeping.

**Shortcuts (decision).** `Ctrl+F` deliberately stays "New filter" — the app's core idiom, in every user's muscle memory and in the empty-state hint — and the find bar takes the browser's own "find next" keys instead, which the app didn't use: **`Ctrl+G`** opens the bar (focuses it if it's open, steps to the next hit if its input already has focus — browser find-next), **`F3` / `Shift+F3`** step next/previous from anywhere (F3 with the bar closed reopens it on the remembered query and steps), **`Enter` / `Shift+Enter`** step inside the input, **`Ctrl+Enter`** in the input is "Add as filter", **`Esc`** closes it (via the global Escape handler; `closeFindBar` also blurs the input, so app shortcuts work again). The three chords are `SHORTCUT_ACTIONS` entries (`findInView`/`findNext`/`findPrev`) — rebindable in the Shortcut Manager; Enter/Ctrl+Enter are `FIXED_SHORTCUTS` rows. `handleFindShortcut` runs in the main keydown handler right after the `newFilter` check and *before* the `inInput` bail-out, so the keys keep working while typing in the find input — and ignores them while any other visible text field has focus (a regex being typed into the filter popup) or, with the bar closed, while a dialog/popup is open.

**What is searched.** `findTargetView()`: in the Tabs layout the tab on screen, in Stacked the pane last selected in (`state.entriesView`, the same rule arrow-key navigation follows) — the Context view's `currentHighlightViewEntries` (matches plus revealed context rows; a collapsed gap isn't in the view and isn't searched) or the Filtered view's `currentViewEntries` (post chain, post level quick-filter, in its displayed sort order). Table/Plot and the Link view have no plain entry list; the counter says "Not in this view" there. The search runs over that **array** (the data model), never the DOM, so off-screen rows of the virtualized list count.

**Query language = a text filter's.** The query is compiled with `textFilterMatchSpec` (a pseudo-node `{value, caseSensitive, isRegex}`) and tested per entry with `textFilterMatches` — literal substring on the raw line (case-insensitive unless **Aa**), a `[*:…]`/`[*]` wildcard pattern (message only, like a filter), or a real RegExp with **.\***. An invalid regex/pattern flags the input and disables "Add as filter". Because it is exactly the filter's own test, **Add as filter** keeps exactly the rows the search counted.

**Hits, counter, navigation.** Hits are *rows*: `findState.hits` holds ascending indices into the searched array. The counter reads `n / m` while the selection is on hit *n*, `m matches` otherwise, `No results`, or a running `k…` while a scan is still going. A step starts from the selected row when it's in the view, otherwise from the top visible row (same as the Context view's match navigator), binary-searches `hits`, wraps around, and selects the hit centered (`selectEntry`/`selectHighlightEntry` with `center`); repeated F3 from the current hit skips the anchor lookup entirely. Typing is debounced (`FIND_DEBOUNCE_MS`, 150ms, same as the filter popup's live match) and then jumps to the first hit at-or-after the anchor (find-as-you-type); Enter pressed before the debounce fires runs that search immediately. A temporary-anchor row (`_tempAnchor`, the selection carried over from another file and spliced into the list) is not a member of the view, so the scan never counts it as a hit — the counter matches the badge and what "Add as filter" keeps.

**Scale.** `startFindScan()` is time-sliced: batches of 2048 entries until `FIND_SCAN_SLICE_MS` (12ms) is used up, then `setTimeout(0)`; a scan generation counter cancels a superseded scan. A small view finishes inside the first, synchronous slice. A step requested mid-scan is remembered (`pendingDelta`) and applied when the scan finishes (after typing's own jump, so typing-then-F3 lands on the second hit).

**Staying in sync.** `findRefresh()` is called from `render()`, the tail of `renderMainView()`, `applyFhView()`, the column-sort click, `selectEntry`/`selectHighlightEntry`, and the one direct `renderHighlightView()` caller in nav history. It compares the current view's array against the scanned one by **identity** and rescans on a change (new filter, tail append, re-sort, tab switch); on a file node the Context and Filtered views share the file's own `entries` array, so there only the target view (`findState.kind`) switches, the hits stay valid.

**Marks.** While the bar is open, `buildMatchMarkContext()` carries `findSpec` (`activeFindSpec()`), and `markFieldHtml()` passes `findMatchRanges(text, findSpec)` to `markCombinedHtml()` as a third range list — every displayed column, both views and the Entry Detail panel, independent of the "Show matches"/"Underline highlights" toggles (it's an explicit transient search). A find segment gets `mark.find-match-mark` (accent tint, stronger on the `.selected` row, i.e. the current hit) instead of the filter's `--warn` `text-match-mark`; highlight-rule stripes still stack on it. Changing the query re-renders only the visible windows (`refreshFindMarks`: `renderVisibleRows`/`renderHighlightVisibleRows`/`updateDetailPanel`); closing the bar drops the marks the same way.

**Add as filter.** `addFindAsFilter()` calls the same `createFilterNode(state.activeId, "text", query, false, null, caseSensitive, null, isRegex, false)` the Ctrl+F popup's `commitFilter` calls, then closes the bar, `revealFilteredView()` and `render()` — the node has exactly a popup-created node's shape (no new node field, so nothing new to thread through the persistence carriers). The query is used untrimmed so the node keeps the searched rows exactly.

**Recent searches.** `#findInput` shares the filter popup's recent-filter dropdown (`createRecentDropdown`, docs/filters.md -> "Recent-filter suggestions"): opening the bar and typing list matching earlier filters/searches; applying one sets the query plus Aa and `.*` and re-runs the search. Enter and "Add as filter" record the term (source `find`, case/regex only), typing alone does not; Escape closes the list before the bar.

**Placement.** The bar floats over `#fhSplit`'s top-right corner (`position:absolute`, `#fhSplit` is `position:relative`), out of flex flow, so opening/closing it never moves a log row; being inside `#fhSplit` it disappears with it on Table/Plot. It does not close on an outside click (a find bar persists while you work, like a browser's).

### Cross-file hit counts (`FEATURE_BACKLOG.md` #30)

While the bar is open with a valid, non-empty query and at least two real file roots are loaded (queued placeholders and `mergeSourceHidden` sources don't count), every file root row in the tree shows a `.tree-hit-badge` directly before its `.tree-count`: how many entries of the **whole file** (`state.nodes[id].entries`, not the active filter chain, active file included) match the query — the find bar's own `findState.test`, so Aa / regex / `[*:…]` patterns apply. `#findCount` ("n / m") is unchanged (current view). The badges are read-only: no filter node, nothing persisted, F3/Enter/arrows still step only inside the current view. Independent of the current view (Table/Plot, inline viewer, folder view): the counts are about the loaded files, not about what is on screen. One root = one badge (merged / meta-format files count once). Badge states: `…` (`pending`), the number in an accent pill (title `17 matches for "x" in the whole file — click to jump to the first`), or a dimmed `0` (`zero`, no jump). With fewer than two files, an empty/invalid query or a closed bar there is no badge at all.

**Click = jump.** A click on a badge with n > 0 (`stopPropagation`), or on a file row whose badge has n > 0 while that file is not the active node, activates the file exactly like a row click and sets `findState.jumpFirst`; `onFindScanDone` then selects the new view's first hit (`findGoToHit(0)`, centered) instead of "next from anchor". If the new view has no hit (e.g. a level quick-filter hides them) the counter just reads "No results". A badge click on the already-active file selects its first hit in the current view.

**Scan.** `findX` (`findXStart`) runs only after the current-view scan (`onFindScanDone`), time-sliced like `startFindScan` (batches of 2048, `FIND_SCAN_SLICE_MS`, `setTimeout(0)`) with its own generation counter; a new query (`applyFindQuery`), a view rescan (`startFindScan`) or closing the bar cancels it. `findX.cache` maps root id → `{ entries, len, count, ready }` for the current query key (query + Aa + regex); a file is recounted only when the key or its `entries` array identity changes, a same-array tail append counts just the new tail (the old count stays visible meanwhile). `findRefresh` → `findXSync` notices changed/grown arrays and opened/closed files; closing a file drops its cache entry. Badges are updated **in place** (`findXPaint`, `.tree-row[data-node-id]`, never `renderTree()` from a scan tick); `renderNode` adds the badge from the cache for file rows so an ordinary `renderTree()` keeps them. With the sidebar collapsed, `#findCount`'s `title` lists `name: count` per file, one line each (`findXCounterTitle`); it is cleared otherwise.

## Level bar: filter-tree mode (`FEATURE_BACKLOG.md` #10)

Settings → Behavior's `#settingsLevelFilterTreeMode` (`levelFilterTreeMode`, plain `localStorage`-persisted preference, same tier as `textMatchHighlightScope`) picks how the level bar (`#levelBar`) behaves — two modes, not a replacement of one by the other:

- **`"auto"` (default)**: clicking a level button no longer touches the old `state.levelFilter` Set at all. Instead it **upserts a single `filterType:"level"` node** (`value`: array of active level names, e.g. `["ERROR","WARN"]`, in canonical `activeLevelOrder()` order — see "Per-format log levels" below) **at the current tree position** — a real, visible, undoable, persisted filter-tree node, evaluated exactly like any other filter type via `getEntries`'s new `"level"` branch (`parentEntries.filter(e => node.value.includes(levelBucket(e.level)))`). `applyLevelSelectionToTree(levels)` is the one function behind this: if `state.activeId` is *already* a `"level"` node, it's edited in place (`updateFilterNodeWithUndo`) rather than nested under itself; toggling every level back off **deletes** the node (`deleteFilterNodeWithUndo` — a real, undoable action, unlike filter *creation* elsewhere in the app, which deliberately isn't undoable — see "Undo/redo" below) and `state.activeId` reverts to its parent (`deleteNode`'s own existing behavior); otherwise a fresh child node is created under the active node and becomes active, same shape as any other "Add filter" flow (`ctxAfter`/`commitFilter`). The level bar's own `.active` highlighting and per-button preview counts follow the tree position instead of a global flag: `activeLevelSetForBar()` reflects the active node's own `value` when it's a `"level"` node (empty otherwise — there's no "current selection" outside of an actual node anymore), and `levelBarCountsBaseId()` counts against the level node's *parent* (not its own already-narrowed result) so each button still previews "how many entries would this level admit here", the same question the counts always answered.
- **`"explicit"`**: the level bar keeps its original, tree-independent behavior byte-for-byte — a plain `state.levelFilter` Set, applied only inside `getVisibleEntries` (`applyLevelFilter`, unaffected by which tree node is active — see "Context view" above ("What counts as a match") for why the Context view has never seen it). A new toolbar button, `#btnApplyLevelToTree` ("Add to tree"), shown only in this mode (hidden in `"auto"`, where the level bar already writes into the tree — `updateApplyLevelToTreeButtonVisibility()`), pushes the current `state.levelFilter` selection into the tree on demand through the exact same `applyLevelSelectionToTree()` upsert logic, so re-clicking it while already positioned on the node it created edits that node instead of duplicating it. Disabled while nothing is selected on the level bar.

Switching modes **clears `state.levelFilter`** (the settings `<select>`'s `change` handler) so a quick-filter left set in one mode can't silently keep affecting the Filtered view once invisible in the other — filter-tree nodes already created are untouched either way, since only the level bar's own client-side behavior is mode-gated, not the tree's contents.

**No new persistence carrier work needed**: a `"level"` node's `value` is a plain array riding the existing generic `value` field every filter node already carries through `cloneSubtree`, `snapshotSubtree`/`restoreSubtree`, `serializeFilterBranch`/`importFilterJson`, and `serializeFilterTreeForCache`/`materializeCachedFilters` — the only change any of them needed was adding `"level"` to the shared `FILTER_TYPES` validation Set (otherwise `materializeCachedFilters`/`importFilterJson` would silently drop the node as an "unknown filter type"). Tree UI is equally generic: `typeTagFor`/`ghostTypeTag` gained a `"LVL"` case and `nodeIconHTML`/`ghostIconFor` a new ascending-bars `ICON_LEVEL`, same pattern every other filter type already follows.

**Tree-row label colored by the level(s) it filters, one solid color per word** (same-day follow-up, person-requested: *"schreibe die Einträge im Files & Filter Tree in der Farbe des Log Levels. auch kombiniert wenn mehrere Level an sind."*, then *"ohne Farbgradient, jedes Wort in der eigenen Farbe"* — a first cut used a `background-clip:text` gradient for a combined node, replaced same-day with this per-word version). `buildLevelNodeLabelContent(node)` — used by the real tree row (`renderNode`; originally also shared by the breadcrumb child-nav flyout row, removed 2026-08-25, see "Header / toolbar layout" above) — builds a `"level"` node's `.tree-label` content as real DOM nodes: one `<span>` per level in `node.value`, each with a plain `style.color = var(--level-error|warn|info|debug|trace)` (the same vars the level bar/log-row tinting already use), comma-separated with plain text nodes so the rendered text reads identically to the node's own plain-text name (e.g. "ERROR, INFO") — just with each word in its own color, no blending. Built via `createElement`/`textContent` rather than an HTML string, so a value smuggled in through a hand-edited/corrupt filter-file import (`importFilterJson` doesn't otherwise validate a `"level"` node's `value` array contents) can't inject markup — an unrecognized entry (not one of the five colored buckets in `ALL_LEVELS`) just renders in the default text color instead of a level color. Every other filter type's label is untouched. Regression-tested: **Group 95** (assertions rewritten in place for the per-word version, not a new group) — one colored `<span>` for a single level; two independently-colored spans (not a gradient) for a combination, with the label's own combined `textContent` still reading exactly like the plain name; word/color order follows `value`'s own array order; a plain `text` node gets no spans at all (the child-nav flyout row's own matching assertion was later removed along with that feature, 2026-08-25). 1812 passed, 0 failed.

### Per-format log levels (`FEATURE_BACKLOG.md` #47)

Which level buttons the bar shows, and in what order, comes from the **log format** a file was parsed under, not from one global list. A `LogFormat` carries an ordered `levels` array (`formatLevels(formatId)`): any subset of the five names that own a dedicated theme color (`ALL_LEVELS` = `ERROR, WARN, INFO, DEBUG, TRACE`), in any order, **plus any number of custom names of its own** (`NOTICE`, `CRITICAL`, `VERBOSE`, …). `OTHER` is never listed — it stays the implicit catch-all. A format with no `levels` field — every builtin, and every format created before this existed — falls back to `LEVELS` = `ERROR, WARN, INFO, DEBUG`, so single-format usage behaves exactly as it did before.

**Per-entry passes memoize it** (2026-09-24): the O(n) loops — level counts (`getLevelCounts`), the level filter and level filter nodes, the timeline minimap's overlay colors, the filter popup's match histogram — go through `makeLevelBucketer()`, which resolves each distinct (format, level) pair once per pass instead of once per entry (`levelBucket` re-resolves the format's level list on every call, which cost hundreds of ms per render on a large file). Scoped to one pass on purpose, so an edited format's levels are never served stale.

**Bucketing is format-aware**: `levelBucket(level, formatId)` (the `formatId` comes off the entry itself, stamped at parse time) resolves a raw level string in three steps — an **exact, case-insensitive match against the owning format's own `levels` list** wins first, which is what gives a custom name its own named, colored bucket; otherwise the historical prefix cascade (`ERR`/`FATAL`→ERROR, `WARN`, `INFO`, `DEBUG`, `TRACE`) still applies, so the five known buckets keep their forgiving matching even for a format whose list omits one of them; otherwise `OTHER`. Unrecognized free text deliberately never becomes a bucket of its own — only names a format explicitly lists are, which keeps the level bar and the count aggregation bounded by configuration rather than by log content. `formatLevels()` normalizes (trims/uppercases) and de-duplicates its list and drops the reserved `OTHER`, so a hand-edited record can't collide with the catch-all.

**Colors for custom names** come from a rotating categorical palette, `--level-custom-1` … `--level-custom-6`, defined per theme block (six genuinely distinct hues each, picked in the spirit of `COLUMN_PALETTE`, plus one `--level-custom-on` for text sitting on top of them; `-soft` shades are derived with `color-mix` rather than getting vars of their own). They are deliberately **not** in `THEME_COLOR_KEYS`, so an imported custom theme (which predates them) stays valid and simply inherits the `:root` values. `customLevelSlot(name, formatId)` assigns a slot by the name's **position among that format's custom names**, wrapping after six — so the same format always paints the same custom level the same color; with no format context (a bare bucket name, e.g. a level-bar button or a filter-node label) every stored format is searched in order, first match wins. `levelClass(level, formatId)` returns `lvl-custom-N` for those, `lvl-error`/`lvl-warn`/… for the known five, and `lvl-other` otherwise; matching rules exist alongside every existing `lvl-*` consumer (`.level-btn` + `.active`, `.col-bar`, `.level-badge`, `.log-row` + `:hover`, `.pair-row-bar`, `.minimap-lvl-*`). `levelSortRank()` ranks custom buckets between `TRACE` and `OTHER` by their slot, which is also the minimap's per-bucket "most severe" index (the minimap keeps the bucket **name** alongside the rank now, since a rank no longer identifies a bucket on its own).

**Integer-valued levels + explicit per-level colors (Custom Columns, later session)**: a format's `levelValueType` (`"text"`, the default, or `"int"`) decides how `levelBucket(level, formatId)` matches a captured level token against `formatLevelDefs(formatId)` — in `"text"` mode (unchanged from above) it matches each level's `name`; in `"int"` mode it instead matches the captured token, verbatim, against each level's `value` — a numeric code, e.g. RFC 5424 syslog severity 0–7, explicitly mapped by the person to a name (no fixed 8-entry severity table, no `%severity`/`%pri` token needed: any code can map to any name). An unmapped code falls into `OTHER`; the historical text-prefix cascade doesn't apply in int mode (a numeric code has no natural relationship to `ERR`/`WARN`/…). Each level definition (`{value, name, color}`) may also carry an **explicit color** picked in the format editor instead of the automatic fixed-name/rotating-slot one — `explicitLevelColor(name, formatId)`/`levelColorVar` consult it first (a literal CSS color, e.g. `"#ff4444"`, used exactly like a `var(--level-*)` reference at every call site), falling back to the automatic behavior above when `color` is `null`. A record saved before this feature (a plain `levels: string[]`) upcasts on read to `{value: name, name, color: null}` for every entry — `formatLevels(formatId)` (the plain-name-list accessor every pre-existing consumer above uses) is unchanged, now just derived from `formatLevelDefs(formatId).map(d => d.name)`.

With several files open under different formats, `activeLevelOrder()` returns the **union**: each open root file's format list, concatenated in tree order, de-duplicated as names first appear (e.g. a `["ERROR","WARN","TRACE"]` file plus an `["INFO","ERROR"]` file gives `ERROR, WARN, TRACE, INFO`). That single order drives both `renderLevelBar()`'s buttons and `canonicalLevelOrder(levels)`, which re-sorts a level node's `value` array (used by the bar's own click handler and by `#btnApplyLevelToTree`) — names outside the union (e.g. `OTHER`, a custom name from a format no longer open, or one a format has since dropped, arriving via an imported filter file or a persisted tree) are kept and appended rather than dropped; such a node keeps its value, simply stops matching, and renders its label in the default text color instead of crashing. `getLevelCounts()` keys its counts off **each entry's own computed bucket** rather than iterating a fixed name list, so per-format custom buckets are counted for free. Entries are stamped with their `formatId` at both parse sites (`parseLogTextAsync`, `appendTailText`).

`TRACE` only became a level-bar button through this feature, so it gained the `.level-btn.lvl-trace` / `.level-btn.active.lvl-trace` rules it never had; its active-state text color is a single `--level-trace-on: var(--level-debug-on)` in `:root`, resolving per theme via the `--level-debug-on` every theme already defines (same neutral grey family as `--level-trace`).

**Editing it**: the format dialog (Settings → Log Formats → Add/Edit, see "Format dialog" below — which also auto-fills this list from the example lines for a new format and lets a custom level be renamed in place) has a "Log levels" list — the five fixed bucket names are always present as rows with a checkbox and ▲/▼ reorder buttons (same idiom as the filename-rule list), and beneath the list a text field + **Add** button (Enter works too) appends a **custom** row. A custom row is always checked and carries a ✕ delete control (`.filter-library-row-del`, the same icon button the format/rule lists use) instead of being uncheckable — it isn't part of a fixed set to toggle back on, so removing means deleting the row; it reorders with the same ▲/▼ and previews its palette color live (`formatEditLevelSlot`, computed from the in-progress working order, since `customLevelSlot` reads the *saved* record). Adding is rejected, with an inline error, for empty/whitespace-only input, the reserved name `OTHER`, and any case-insensitive duplicate of a row already in the list (fixed rows included — that's a re-check, not a new row). The saved `levels` is the checked rows in the arranged order; unchecked fixed rows keep their position in the editor (so unchecking and re-checking doesn't lose it) but never reach the record. Saving with nothing checked is refused. Reset (builtin default row) restores the original four. No new persistence carrier: `levels` is a plain field on the `LogFormat` record already written whole to the `logFormats` IndexedDB store — since Custom Columns, the saved shape is `{value,name,color}[]` (see above) rather than a plain name array, still one field, still written whole.

**Editing int-mode + explicit colors (Custom Columns, later session)**: a **Text/Integer** toggle (`formatEditLevelValueType`, same `.assert-mode-btn` look as the Pattern/Regex/Meta mode toggle) sits above the level list; in Integer mode every row grows a small numeric `value` field (defaults to the level's own name, e.g. "ERROR", until the person types a real code). Every row (fixed or custom) also gets a color swatch (`.format-level-swatch`, after the ▲/▼/delete controls — deliberately trailing, so `rows()[i].querySelector("button")` still reliably means "the ▲ button" for every existing/future row-based test, same convention every other reorderable list in this file follows) that opens the existing reusable color-picker popup (`openColorPicker(null, swatch, onPick)` — already designed for a non-highlight-color caller) instead of a dedicated new picker; picking "Clear" in that popup resets the row to its automatic color (`meta.color = null`) rather than needing a separate reset control.

Regression-tested: **Group 116** — default-format behavior unchanged, a custom format's own subset/order driving the bar, the two-format union, `canonicalLevelOrder`'s effect on a level node's `value` and its colored tree label, and the editor's save/reopen/IndexedDB round trip incl. the empty-selection guard and Reset — and **Group 117** for custom names: `levelBucket`'s three-step resolution (exact/cascade/OTHER, incl. case and whitespace normalization and the "another format's name isn't borrowed" case), per-format positional slot assignment and the resulting `lvl-custom-N` classes on bar buttons and log rows, custom buckets in the bar/counts/quick-filter/tree label, `levelSortRank` placing them between TRACE and OTHER, the editor's add/duplicate-reject/blank-reject/Enter/reorder/delete flow with an IndexedDB round trip, and a level filter node left pointing at a level its format no longer defines. **Group 260** (Custom Columns) adds int-mode value matching, the text-mode/int-mode `OTHER` fallback difference, explicit-color precedence over the automatic fixed-name/rotating-slot color, and the legacy plain-string-array upcast.

## Log format export/import (JSON)

The one place a log format is defined. Settings → Log Formats → **"+ Add format…"** or a row's **Edit** opens `#formatDialog`, a large dialog stacked **on top of** Settings (z-index 80).   - **Editing the list**: middle columns reorder with ▲/▼ and are removable. A removed default gets a "+ Thread"-style re-add chip. A **new column title** field adds a custom column right before Message; its capture name is derived from the title (`fwzLabelToKey`: "Request Id" → `requestId`, umlauts transliterated, never a reserved field name or a duplicate).
  - **Renaming**: double-clicking a column's title renames it in place (`fwzStartColumnRename`; Enter/blur commits, Esc cancels). Only the label changes; the capture name stays.
  - **Active column and colors**: clicking a row makes it the **active** column (`fwzSetActive` toggles the class in place instead of re-rendering, so the second click of a rename double-click lands on the same node). Each column owns a hue, and its marks use the same color.
  - **Order**: the list order is the log view's column order; the regex's group order follows the marks' positions in the line.
- **Example lines** (`#fwzSample`):
  - **Input**: Ctrl+V pastes (the `paste` event, so no clipboard permission is needed), the **Paste** button uses `navigator.clipboard.readText()` when allowed, and **Open file…** uses a file input.
  - **Drop**: a **file dropped anywhere while the dialog is open** becomes example lines instead of being loaded into the tree. Both the window-level `drop` handler and, under the desktop wrapper, `loadDesktopLocalFiles` check `formatDialogOpen()` first, and the global drop overlay stays hidden meanwhile.
  - **Limits**: incoming text is appended, never replaced. Blank lines are dropped, lines are truncated at 2000 chars, and at most 200 lines are kept (`FWZ_MAX_LINES`). A file contributes only its first 512 KB. **Clear marks** and **Clear all** reset.
- **Marking**: select text inside **one** line (drag, or double-click a word). On `mouseup` the selection becomes a mark `{line, start, end, key}` for the active column. Offsets come from a `Range` over the line's text element, so existing mark spans don't disturb them. Surrounding whitespace is trimmed. A column has at most one mark per line, and an overlapping mark is replaced. Clicking a solid mark removes it, and a line's ✕ clears all its marks.

**The stand-in regex (automatic suggestion)**: while no line is marked, `fwzRefreshFallback` picks the regex that pre-marks the examples (faint "suggested" marks) and drives the preview. The first match wins:
1. A regex **typed into the Regex field** (see below).
2. When **editing** a format: that format's **own** regex, always — even if newly pasted examples don't match it. The status line then warns that it matches none of them. For a Pattern-mode format this is its compiled pattern, with the date's inner groups made non-capturing (`compileFormatPattern(..., {plainDateGroups: true})`). The format's own timestamp format is left alone too.
3. For a **new** format, or after **Re-suggest**: the **automatic suggestion** (`fwzSuggestFromLines`). It runs `suggestPatternFromSample` on the first line that starts with a recognizable timestamp.
   - **What it claims**: timestamp, level word, quoted/parenthesized thread, bracketed method, and a **path-like field** between two of those as **Location** (e.g. the default format's `C:\src\App.cs\tline 12`). Left literal, a path would pin the suggestion to that one line's file and match no other line. The rest after a short separator becomes the Message, minus a closing quote that matches an opening one.
   - **Generalizing**: its claimed spans (`fields`, on the trimmed line) are fed straight into `deriveFormatRegexFromMarks` as virtual marks, so the suggestion generalizes exactly like hand marks (space padding, "up to the next separator" classes). They're deliberately NOT re-derived by running the raw suggestion regex, which can fail even on its own line — its thread is `\S+`, and a quoted thread like `"(1) "` contains a space.
   - **Timestamp**: it also fills the timestamp field, unless that was edited by hand.

The status line says which kind is in place.

**Re-suggest** (`#fwzResuggest`, enabled once there are examples) is the explicit way to start over — also, and mainly, when editing.
- **Confirmation**: it first shows an inline warning (`#fwzResuggestConfirm`) that the current marks, the regex and the timestamp format will be discarded, with **Re-suggest** / **Keep current**.
- **Confirming** (`fwzResuggest`) clears the marks and any typed regex, sets `forceSuggestion` (so an edited format's own regex stops being the stand-in), hands the timestamp field back to the suggestion, and adds any column the suggestion captures but the list lacks.
- **Undo**: it's one undo checkpoint (`forceSuggestion` is part of the snapshot), so a single Undo restores everything, including the format's own regex as the stand-in.

**Editing the regex directly** (`#formatEditRegex`, editable): typing makes the typed text the stand-in.
- **Marks and columns**: typing clears all marks; they're re-shown as suggested marks from the typed regex. Any named group the column list doesn't have yet is added as a column (a default one for thread/location/method, else custom with the group name as its title).
- **Undo**: the typing session gets one undo checkpoint (`regexEditCheckpointed`, reset on focus), so one Undo brings the previous marks back.
- **Invalid regex**: an invalid regex shows in the status line and blocks Save.
- **Marking afterwards**: marking a line after typing re-derives the regex from the marks (the typed one is only the stand-in). While the field has focus, re-renders never overwrite it.

**Learning lines vs. continuation lines**: only lines with at least one mark feed the derivation. An unmarked stack-trace line can't skew it. Whether a line starts a new entry or continues the previous one is still decided by the regex alone, exactly like parsing. The preview table shows the result, so a regex that is too loose shows up as an extra row.

**Derivation** (`deriveFormatRegexFromMarks(lines, marks, {tsFormat, labels})`, pure):

- **Column consistency**: every learning line must mark the same columns in the same order. Otherwise the result is an error naming both lines and their column titles. Message marked on only *some* lines is tolerated: those trailing Message marks are dropped and the tail rule covers them.
- **Separators** (text before, between, and after marks):
  - identical on every learning line → literal, with every run of plain spaces loosened to `\s+`, because space padding like `INFO  ` vs. `ERROR ` rarely shows in full (`fwzSepLiteral`)
  - whitespace only but varying → `\s+`, or `\s*` when some line has none
  - anything else → `.*?`
- **Column values** (`fwzColumnFrag`):
  - Time uses the detected/entered timestamp format's own fragment, non-capturing, when every value fits it.
  - Level uses `\w+` when every value is a word.
  - Everything else takes the first of these that fits: `\d+`; `[^c]+`, where `c` is the next literal separator character and appears in no value (`\S+` when `c` is whitespace), which generalizes best from few examples ("main" and "worker-1" are both "up to the `]`"); `\w+`; `\S+`; `.+?`.
  - Message is `.*` at the end, `.*?` elsewhere.
- **Tail**: with Message unmarked, the rest of the line after the last column becomes `(?<message>.*)`, minus a separator run (`: `, `] `, ` - `, …) that every learning line shares.
- **Optional closing text**: with Message marked as the **last** column, the literal text after it (typically its closing quote) is **optional**: `"(?<message>.*?)(?:")?$`. A multi-line message only closes on a later continuation line. Requiring the quote would make that entry's own header line not match at all, gluing it onto the previous entry. This is the same tolerance the builtin default's header check has.
- **Closing a multi-line quoted message**: a message whose closing quote only comes on a continuation line is handled at parse time. `messageWrapQuote(src)` recognizes a regex ending in `"(?<message>…)(?:")?$`. When a header line lacks the closing quote, `markOpenMessageQuote` tags the entry with `msgOpenQuote`. `appendContinuationLine` — the one shared "append a non-header line" step of the main-thread parser, the worker (serialized with it), tailing (`appendTailText`), and the dialog preview — drops the quote from the continuation line that ends with it. Without this, the message would lose its opening quote (literal in the regex) but keep the closing one. The entry's `raw` keeps every line verbatim.
- **Anchoring**: the regex is anchored `^…$`.
- **Self-check**: each learning line is re-matched with the `d` flag, and any line the regex splits differently than marked is named in a warning.
- **Timestamp format** (`detectTsFormatFromValues`): classifies the first value's digit runs as `yyyy-MM-dd`, `dd.MM.yyyy`, or `MM/dd/yyyy` (day-first if a first part is > 12), then `HH:mm[:ss[<sep>SSS]]`, and keeps its non-digit separators literal. It returns a format only if every marked value round-trips through `compileDateFormat`. Anything else, such as month names or a timezone suffix, gives `""`: the free-form `Date.parse` fallback plus a warning. Typing in the timestamp field overrides detection, and emptying the field hands it back.

**Live feedback**: after every change, the stand-in is refreshed, the regex is re-derived, and the result is applied to every line.

- **Suggested marks**: lines with no marks but a matching regex get faint suggested marks.
- **Continuation lines**: a line that doesn't match, after an entry has started, belongs to that entry's Message, exactly as the parser appends it. It shows **one Message mark across the whole line** (`.fwz-continuation`: faint, dashed underline, titled with the line the entry starts on), minus the closing quote of a quoted multi-line message (`messageWrapQuote`, same rule as `appendContinuationLine`). It is not a hand mark: not removable, and not a learning line.
- **Adopting suggestions**: marking a line that only has suggested marks first **adopts** them as real marks, then applies the new one. Correcting one wrong column of the automatic suggestion never means re-marking the rest. A suggested Message is adopted only if there are no learning lines yet or they mark Message too, to keep column sets consistent.
- **Table preview** (`fwzParsePreview`): parses lines like `parseLogTextAsync` (header line → new entry, anything else appended to the previous message; lines before the first entry listed as dropped). It renders Time (formatted), Level, the captured middle columns, and Message (multi-line) in a grid shaped like the log view.
  - **Level badges** resolve against the dialog's **current, unsaved** level list (`fwzResolveLevel` — the same text-mode exact-then-cascade / int-mode code matching as `levelBucket`) and take that level's explicit or automatic color. OTHER shows grey.
  - **Clicking a badge** scrolls the level list to that level and flashes it (`fwzRevealLevel`).

**Log levels** (sidebar; the same list editor as before — checkbox, ▲/▼, delete for custom rows, color swatch, Text/Integer toggle, add field):
- **Auto-fill** (`fwzSyncLevels`, run after every change from the level values the current regex captures in the examples): while the list is untouched (a **new** format), it's computed entirely from those values.
  - **All numeric**: Integer mode, one checked level per distinct code, in numeric order, each initially **named after its own code** (`3` → `3`) for the person to rename.
  - **Otherwise**: Text mode — the four defaults, plus every fixed level a value cascades to (`WARNING` → WARN), plus every other value as a checked custom level.
- **Hand edits**: any hand edit (`formatEditLevelsChanged` — check, reorder, add/remove, color, code, rename, Text/Integer) sets `levelsTouched`. From then on, and always for an existing format, newly seen values are only **appended** as custom levels, never reshuffled.
- **Renaming**: custom levels have an editable name field (`renameFormatEditLevel`). Renaming onto a fixed name that isn't in use yet **merges** into that fixed row — it gets the code, color and position (`3` → `error` maps code 3 to ERROR). Any other existing name is refused.
- **Code field**: in Integer mode it shows a numeric code even when it equals the level's name.

**Finding a preview row's source**: double-clicking a preview row (delegated on `#fwzPreview`, since its rows are rebuilt on every change) scrolls `#fwzSample` so that example line sits in the middle and flashes it (`fwzRevealLine`, `.fwz-line-flash`). Each preview entry carries `srcLine`, the example line it starts at.

**Undo/redo**: Undo/Redo buttons, plus Ctrl+Z and Ctrl+Y / Ctrl+Shift+Z, so one wrong mark never costs the earlier ones.
- **What is recorded**: before every mutating action, `fwzCheckpoint()` stores a whole-state snapshot of lines, marks, columns, the active column, the timestamp field, the typed regex, and the Re-suggest flag. Mutating actions are mark add, replace, and remove; line clear; lines appended; Clear marks and Clear all; column add, remove, move, and rename; a regex typing session; and Re-suggest.
- **Stacks**: undo holds at most 100 snapshots (`FWZ_UNDO_LIMIT`), and any new action clears redo. Level-list edits keep their own immediate effect and aren't part of this history.
- **Keyboard**: the keys are handled at the top of the main keydown handler while the dialog is open (`fwzHandleUndoKeydown`), so they never reach the filter tree's own undo behind the dialog. Inside text fields they're left to the field's native undo.

**Save** (`saveFormatEdit`) re-checks what the status line shows (`fwzSaveBlocker`): a name, consistent marks, a valid regex with both a `ts` and a `level` group (Time and Level are mandatory), and at least one checked level. For Meta, at least 2 targets. It writes:
- **Regex mode only** (`mode: "regex"`, `pattern: ""`): an existing Pattern-mode format is saved back as its compiled regex. The Pattern text field is gone, and a stored Pattern-mode format still parses unchanged until it's saved here. Editing the builtin default sets `edited`, as before, and Reset restores its original pattern.
- The timestamp format and the levels (`levelValueType`, `{value, name, color}` items).
- **Only the middle columns the regex actually captures**: listed but uncaptured ones are named in the status line beforehand.
- `messageVisible`.
- **`fmt.sampleSetup = {lines, marks}`**: the first 50 lines, or up to the last marked line if that's further down. It's removed when there are no examples or for a Meta format. `openFormatEditDialog` seeds it back, so reopening a saved format restores its examples, marks, and columns and re-derives the same regex.
- The optional filename rule (see above).

## General "don't jump" scroll anchoring + auto-reveal Filtered

Person-requested this session (2026-08-19; German: *"Stelle sicher, dass beim ändern der angezeigten Log-Level, die aktive Zeile nicht aus dem Bild springt, sondern sich das Log darüber/darunter erweitert. Generell gilt: wechsel von Filtern, Log-Leveln, Message Expand etc. die aktive Zeile bleibt sichtbar (sofern sie im Ziel-View vorhanden ist)... Das Ziel soll sein, dass ein Wechsel zwischen unterschiedlichen Anzeigen, nicht als Sprung wahrgenommen wird, insbesondere wenn ein Element ausgewählt ist. Bei wechsel zu einem anderen Filter, wechsle automatisch vom Full zum Filtered View (wenn Stacked aktiv ist, keine Änderung)"*). Two related but separate fixes:

**1. Scroll anchoring, generalized.** The multiline toggle (see below) previously had its own one-shot re-anchor mechanism (`topVisibleEntryId` + `pendingTableTopAlignId`/`pendingHighlightTopAlignId`, manually captured by that one button's click handler right before `render()`). Every OTHER view-changing action — a level-filter pill click, switching the active tree node/filter, a column sort — still fell through `renderTable()`'s old default: *"any other change to the displayed set starts back at the top of the new list."* That default is exactly what read as a jarring jump, especially with a row selected.

Replaced with `captureViewAnchor(entries, offsets, scrollEl)` / `restoreViewAnchor(anchor, entries, offsets, scrollEl, setScrollFn)` (declared together, right above `renderVisibleRows()`), called automatically **inside** `renderTable()`/`renderHighlightView()` themselves on every render — no call site needs to remember to invoke anything:

- `captureViewAnchor()` runs first, against the OLD (pre-change) entries/offsets/scroll position, before the caller recomputes them. If `state.selectedId` is present in the OLD entries, it's the anchor — pixel offset from the top of the viewport captured too when the row is currently on screen (`onScreen`), or `null` when it isn't (nothing to preserve, just an obligation to reveal it once restored). With no selection, it falls back to `topVisibleEntryId()` (the multiline toggle's original fallback, now the general one) — the entry currently at the very top of the viewport, offset `0`.
- `restoreViewAnchor()` runs after the NEW entries/offsets exist, looking the anchored id up in the NEW list. Found + had a pixel offset → `setScrollFn(newRowTop - offset)`, landing the SAME row at the exact SAME screen position it had before (the log visibly "expands/collapses" above or below it, not a jump). Found + no prior offset (was selected but off-screen) → centers it in the viewport instead of edge-snapping, so a stale-but-selected row actually gets revealed rather than staying hidden. Not found at all (filtered out, or nothing was anchored and even the fallback list was empty) → returns `false`, and the caller falls back to its own pre-existing default (`renderTable()`: reset to top, same as always; `renderHighlightView()`: leave `scrollTop` exactly as it was — that view's own established default, see "Context view" above, only ever actively touched on a genuine root-file switch).
- `topVisibleEntryId()`/`captureViewAnchor()`/`restoreViewAnchor()` all key variable-vs-flat row-height math off **`offsets` truthiness**, not `state.multilineMessages` directly — the global flag can already reflect a NEWER mode than the specific entries/offsets pair being captured (e.g. right after the multiline toggle flips it but before the affected view actually re-renders), so the offsets array's own presence is the only reliable signal for "were THESE rows laid out with variable heights."
- `renderTable()` now calls `captureViewAnchor()` unconditionally as its first real step (right after the `!hasFiles` early return) and tries `restoreViewAnchor()` after `state.scrollTargetId`/`pendingTableScroll` (both explicit navigation intents, still highest priority) have had their turn. `renderHighlightView()` only attempts capture/restore when the root file hasn't changed (`sameRoot`, computed once and reused) — a genuine root switch has nothing worth preserving from the old viewport, same as before.
- `#btnMultilineMsg`'s click handler lost its entire manual-capture block (including the old Link-view `isLinkActive` guard) — trivial now, just flip the flag and `render()`. The Link-view case needs no guard at all anymore: `captureViewAnchor()` only ever runs from inside `renderTable()`, and `renderMainView()` calls `renderLinkView()` instead of `renderTable()` while a `link` node is active, so there's simply no call for it to make during that whole period — nothing stale can linger.

Regression-tested: **Group 61** (`tests/philogg.regression.test.js`) — 61a: selecting a row, scrolling it to a known on-screen offset, then clicking a level-filter pill that removes many rows above it — asserts the resulting `scrollTop` keeps that row's on-screen pixel offset bit-for-bit unchanged in the Filtered view (its Full-view assertion was updated same-day per point 3 below — Full no longer narrows at all, so there's nothing to re-anchor there). 61b: a selected row that gets filtered OUT entirely falls back to reset-to-top, same as no selection. 61d: a selected row that was off-screen before the change (never previously visible) gets revealed centered once it survives into the new view, instead of staying scrolled away. Group 55d (still passing, updated in place — see "Multiline message display toggle" below) covers the no-selection fallback path this generalization also has to keep working, plus the Link-view case specifically.

**2. Switching filters auto-reveals the Filtered view from Context.** A newly *created* or *edited* filter already called `revealFilteredView()` (switches `fhActiveTab` from `"highlight"` to `"filter"` when in tabs layout; no-op in Stacked, both panels already visible — see "Context view" above) at each of its own call sites, so its result would actually be on screen. Simply *switching* the active node to an already-existing filter — via the tree, the breadcrumb, arrow-key nav, drag-drop reparenting, undo/redo, or any of the ~30 other places `state.activeId` gets set directly — did not, so browsing filters while on the Context tab silently showed nothing changing.

Fixed once, centrally, instead of touching every one of those call sites: `render()` now tracks the active id across calls (module-level `lastActiveIdForReveal`, updated at the top of every `render()`) and calls `revealFilteredView()` itself whenever `state.activeId` changed AND the new active node's `type === "filter"` — this works because "every state mutation ends in a `render()`" (see `render()`'s own comment) is already an established invariant across the whole app, so a check inside `render()` sees every real activeId change regardless of which of the ~30 call sites caused it. Switching to a plain FILE node deliberately does NOT trigger this — a file node has no filter result to reveal, and the Context view shows the whole file there anyway.

Regression-tested: **Group 61c** — switching between two filter nodes while on the Context tab reveals Filtered; already being on Filtered is a no-op; Stacked layout stays unchanged; switching to a plain file node does not reveal.

**3. Same-day follow-up: the level quick-filter does not narrow the Context view, and changing it ALSO auto-reveals Filtered from Context** (person-requested: *"die Log Level Filter sollen sich nicht mehr auf das full Log auswirken. stattdessen soll ein andern der Log Level Filter auch zu einem automatischen Sprung von Full nach Filtered führen"*). `renderHighlightView()` stopped calling `applyLevelFilter()` and has never called it since; the Context view rework kept that true for the same reason, now stated as a rule — the level quick-filter narrows the Filtered view's *display*, those rows never leave the result set, so they stay matches in the Context view (see "What counts as a match" above). `renderLevelBar()`'s click handler gained the same `revealFilteredView()` call point 2 added for node switches, so a level-filter change made while on the Context tab jumps to Filtered the same way.

Regression-tested: **Group 61e** — the Context view's own entry count is unchanged across a level-filter toggle (Filtered's own count still narrows as expected); changing the level filter while on Context reveals Filtered; already on Filtered is a no-op; Stacked stays unchanged. Group 4 carries the same dual-view assertion (rewritten twice: 32e282b4 originally asserted Full ALSO narrows, then that it does not, and now that the Context view's match set is untouched). **Groups 138/147/151** cover the Context view itself (model, jump expansion, toolbar).

## Cross-view jumps preserve screen position (double-click, `revealInFilteredView`)

Person-requested this session (2026-08-27; German: *"Bei allen Wechseln zwischen views, egal ob Doppelklick, Klick auf Filter, Alt+Pfeiltasten, etc. versuche den selektierten Logeintrag an seiner aktuellen Position zu halten. (Doppelklick springt zum Beispiel aktuell in die Mitte). Wenn im Ziel View nicht genügend Einträge oberhalb des Eintrags vorhanden sind, darf der Eintrag entsprechend nach oben springen. In allen anderen Fällen soll beim Wechsel sichergestellt werden, dass der Eintrag an der gleichen Stelle zu sehen ist wie im vorherigen View."*).

The tree-click/Alt+Arrow path already preserved the selected row's on-screen pixel offset via `captureViewAnchor`/`restoreViewAnchor` (see above) — including the "not enough rows above" case, since `setTableScroll`/`setHighlightScroll` already clamp to `Math.max(0, …)`, which naturally pins the row as high as it can go instead of the exact requested offset. The gap was every jump that goes through `state.scrollTargetId`/`state.highlightScrollTargetId` instead — `revealInHighlightView()` (double-click/Enter reveal into the Highlight view) and `jumpToFullLog()`/`jumpToEntry()` at the time (extraction table row double-click into the Filtered view — `jumpToFullLog` has since been replaced on that trigger by `revealInFilteredView`, see "filterType merge" in `docs/extraction-and-plotting.md`, but the offset-preservation mechanism below carried over unchanged) — these bypassed the anchor mechanism entirely and always centered (`scrollToIndex`/`scrollToHighlightIndex`'s `opts.center`).

Fixed by adding a third scroll mode alongside `opts.center`: `opts.offset` (a pixel value), which lands the target row at that exact distance from the viewport's top instead of centering — `target = rowTop - opts.offset`, clamped to 0 by `setTableScroll`/`setHighlightScroll` the same way `restoreViewAnchor` already relies on. The offset is captured from the SOURCE row at the moment of the jump via `captureRowScreenOffset(rowEl, scrollEl)` (`rowEl.getBoundingClientRect().top - scrollEl.getBoundingClientRect().top`, `null` if the row isn't actually on screen) — real layout geometry rather than an offsets-array lookup, so it works uniformly across every source view regardless of whether that view is virtualized (Filter/Highlight tables) or not (the Link view, the Extraction table).

- `revealInHighlightView(entry, sourceRowEl, sourceScrollEl)` now takes the clicked/Enter-selected row and its container, captures the offset into `state.highlightScrollTargetOffset` before `renderHighlightView()` runs, which passes it through to `scrollToHighlightIndex(idx, { offset, flash: true })` when known, falling back to `{ center: true, flash: true }` when not (e.g. the row happened to be off-screen already — nothing to preserve, same convention as `restoreViewAnchor`'s own off-screen fallback).
- `jumpToFullLog(entry, sourceRowEl, sourceScrollEl)` does the same via `state.scrollTargetOffset`, consumed by `renderTable()`'s `scrollTargetId` branch — still true today even though no UI action calls it anymore (see below). `revealInFilteredView(entry, sourceRowEl, sourceScrollEl)`, its replacement on the extraction table row's double-click, reuses the exact same `scrollTargetId`/`scrollTargetOffset` mechanism. `jumpToEntry()` (bookmark-panel jumps) deliberately passes no source row — a bookmark click has no "previous screen position" in a log view to preserve, so it keeps centering.

## Multiline message display toggle

`#btnMultilineMsg` (`#viewBar`, next to `#btnPinBookmarks`) toggles `state.multilineMessages` — default `false` (unchanged behavior: with word-wrap also off, `.col-msg` stays `white-space:nowrap` + ellipsis, one truncated line per row — see "Word-wrap toggles" below for the distinct, independent soft-wrap toggle that reuses this same variable-height machinery). On: a `.multiline-messages` class on `<body>` (toggled by `updateMultilineMsgButton()`, the same "reflect state on the button" helper pattern `updatePinBookmarksButton()` uses) switches `.col-msg` to `white-space:pre` — literal `"\n"`s in `e.message` (continuation lines the parser already folds in for stack traces, see "The log format it parses" above) render as real line breaks. Applies to **both** views that render `.col-msg`: the Filtered table (`renderVisibleRows`) and the Context view (`renderHighlightVisibleRows`) — a single body-level class reaches both without per-row class bookkeeping. The Extraction table and Link pair view don't use `.col-msg` at all and are untouched.

**Deliberately `pre`, not `pre-wrap`**: a long single line is never soft-wrapped to fit the column width, only the message's own embedded breaks produce new lines. This isn't just fidelity to the request's literal wording ("gemäß der Zeilenumbrüche in der Message") — it's what keeps a row's rendered height **exactly derivable from its message's line count**, with no DOM measurement involved: `messageLineCount(message)` (`message.split("\n").length`) and `rowHeightForEntry(e)` (`ROW_HEIGHT + (n-1) * MULTILINE_LINE_HEIGHT` for `n > 1` lines, else plain `ROW_HEIGHT`) are pure functions of the entry, computable before the row ever touches the DOM. `MULTILINE_LINE_HEIGHT = 15` (px) is duplicated as a literal in the `.multiline-messages .col-msg` CSS rule's `line-height:15px` — the two values must stay in sync by hand if either ever changes, there's no shared source (a CSS custom property would remove that risk if this needs touching again).

**Why the height needs to be exact, not just "close enough": variable-height virtualization.** The Log view's `ROW_HEIGHT = 28`/`BUFFER_ROWS = 10` virtualization (see "Log view" above) assumes every row is the same height — `index * ROW_HEIGHT` locates any row's pixel offset in O(1), which is what makes scrolling a 100k-row file smooth. Multiline mode breaks that assumption (rows vary in height), so exact-but-not-measured heights let a **prefix-sum array** stand in for the same O(1)-ish lookup instead of falling back to a full non-virtualized render (which would have defeated the whole "stays smooth at any file size" goal) or a measure-as-you-scroll virtualizer (real complexity for no benefit when the exact height is already knowable in advance):

- `buildRowOffsets(entries)` returns a `Float64Array` of length `entries.length+1` where `offsets[i]` is the cumulative pixel height of every row before index `i` (`offsets[0] = 0`). Built once whenever the current view list changes — `renderTable()`/`renderHighlightView()`, and the `pinBookmarksInFilteredView`-triggered partial refresh in `toggleBookmark`'s caller — never per scroll frame. `tableRowOffsets`/`highlightRowOffsets` hold the two views' arrays; both stay `null` when `state.multilineMessages` is off, so that path's virtualization code is untouched (`if (state.multilineMessages && tableRowOffsets) { … } else { /* original ROW_HEIGHT arithmetic, byte-for-byte */ }` at every call site below).
- `findOffsetIndex(offsets, y)` binary-searches for the largest row index whose offset is `<= y` — "which row is pixel position y inside." Used everywhere the old code did `Math.floor(scrollTop / ROW_HEIGHT)`.
- Every call site that used to do index↔pixel math via `ROW_HEIGHT` now branches on `state.multilineMessages`: `renderVisibleRows`/`renderHighlightVisibleRows` (which rows to render + the container's `top` offset), `renderTable`/`renderHighlightView` (the scroll spacer's total height — `offsets[total]+22` instead of `total*ROW_HEIGHT+22`), `scrollToIndex`/`scrollToHighlightIndex` (both the target row's top AND its own height, needed for the center/into-view math — a tall row centers differently than a 28px one), and `updateMinimapRenderedRange` (which entries the minimap's "currently rendered subset" rectangle spans).
- The tail-follow "how far from the bottom is the user scrolled" heuristic (`ROW_HEIGHT * 1.5` threshold in the `#tableBody` scroll listener) was deliberately left as a flat constant — it's a coarse "close enough to the bottom" check, not a per-row lookup, and a taller effective threshold under multiline mode is if anything more forgiving, not wrong.

**Toggling re-anchors on the top-visible entry, not on scroll position 0** — originally a dedicated one-shot mechanism built just for this toggle, **superseded this session (2026-08-19) by the general "don't jump" scroll anchoring** described in its own section right after "Context view" above: `captureViewAnchor()`/`restoreViewAnchor()`, called automatically inside `renderTable()`/`renderHighlightView()` on every render, not just this one toggle. `#btnMultilineMsg`'s click handler itself is now trivial again — flip `state.multilineMessages`, call `render()` — with no manual capture step of its own. See that section for the current mechanism (including how it now also prioritizes the *selected* row, not just the topmost-visible one).

Regression-tested: **Group 55d** — scrolled well past three rows that are about to grow, toggling on grows `scrollTop` by exactly the sum of those rows' height increase (not 0, not an unchanged raw pixel value) in both views, with the same entry's DOM row still actually rendered at the top afterward; toggling back off shrinks `scrollTop` back to the exact original pixel value; the degenerate already-at-0 case stays at 0; and the Link-view case (toggling while a `link` node is active, no table rendered that cycle) — updated in place this session to assert the view now re-anchors on the entry that was on screen before the Link-view interruption instead of resetting to top, since "reset to top on any other change" is exactly the old default this session's general fix replaced.

**Persistence**: `state.multilineMessages` rides in the exact same `settings` object `buildCacheMeta()`/`restoreSessionFromCache()` already carry `pinBookmarksInFilteredView` in — additive field, no `CACHE_FORMAT_VERSION` bump (same reasoning already established for `linkOrderEnforced`/`linkExclusive`, see "Link filter" above). This is the browser-local IndexedDB session cache specifically — **not** threaded into the separate `buildSessionExport`/`runSessionImport` JSON session-file feature, since the request asked for state "im Cache gespeichert" (in the cache), a narrower, different mechanism than that portable-file export.

Regression-tested: **Group 55** (`tests/philogg.regression.test.js`) — 55a covers default-off, per-row heights in both views, the spacer summing real heights, and exact reversion on toggle-off; 55b builds a 50-entry file with one 21-line entry positioned before a jump target and asserts `scrollToIndex` (via `jumpToEntry`) lands on the pixel offset the tall row's real height demands, with the target's DOM row actually rendered — proving the offset-based windowing, not just the toggle's on/off state; 55d (see "re-anchors on the top-visible entry" above) covers the scroll-preservation fix; 55c round-trips the setting through a simulated reload via the shared session-cache mechanism, same pattern as Group 20.

## Word-wrap toggles (FEATURE_BACKLOG.md #68)

Two independent soft-wrap toggles, each in its own view's toolbar, both **distinct from the multiline toggle above**: multiline renders the message's own embedded `"\n"` breaks; word-wrap soft-wraps a single long line so it no longer needs horizontal scrolling. They combine freely (a message can both break on its `"\n"`s and wrap each resulting line).

**Log view (`state.wrapMessages`).** A `.toggle-wrap` button lives in **both** log toolbars — `#filteredToolbar` and `#contextToolbar`, next to `.toggle-multiline` (icon `ICON_WRAP`; collected as `btnWrapMsg = elAll(".toggle-wrap")`, so clicking either reflects on both). `updateWrapMsgButton()` — the same "reflect state on the button" helper pattern `updateMultilineMsgButton()` uses — toggles a `.wrap-messages` class on `<body>`. CSS then switches `.col-msg` from its default `white-space:nowrap` to:
- `white-space:normal` when wrap-only (multiline off) — literal `"\n"`s collapse to spaces exactly as the default nowrap view already shows them, and the line soft-wraps;
- `white-space:pre-wrap` when wrap **and** multiline — `"\n"`s still break, and each line then wraps.

Both use `word-break:break-all`, and that is **load-bearing, not cosmetic**: it packs every visual line to exactly the message track's character capacity, so a row's wrapped line count is `ceil(chars / columns)` — computable from data alone, which is what lets wrap reuse the multiline feature's exact-height offsets virtualization (see "Multiline message display toggle" above) with **no per-row DOM measurement**. A true word-boundary wrap would make a row's height depend on where words fall, which the windowing math can't predict without measuring every row — the same trade-off the multiline feature already refused. The helpers:
- `wrapColsForBody(bodyEl)` computes the message track's character capacity for a scroll body: `(clientWidth − TABLE_ROWS_H_PADDING − lastColumnEdgeX − COLUMN_GRID_GAP) / charWidth`, **biased one column conservative** (`Math.floor((track − cw) / cw)`) so the estimate can only ever over-allocate a row (a hair of trailing blank space), never under-allocate it and clip the last line. Returns `0` when wrap is off or the body isn't measurable yet (e.g. `clientWidth` 0), so the plain non-wrapped `ROW_HEIGHT` path is used then. `charWidth` comes from one real `measureMsgWidth("0000000000")/10` measurement (the log font is monospace).
- `messageWrapLines(message, cols)` returns the exact `ceil(chars / cols)` line count (summed per `"\n"`-line when multiline is on; over the whitespace-collapsed string when it's off).
- `baseRowHeightForEntry(e, cols)` folds this in: `n` = wrapped line count when `state.wrapMessages && cols >= 1`, else the multiline line count, else `1`; height is `ROW_HEIGHT + (n−1) * MULTILINE_LINE_HEIGHT`. The two views can differ in width (Stacked shows both), so `buildRowOffsets`/`buildContextRowOffsets` each compute and cache their own column count (`tableWrapCols`/`highlightWrapCols`) when building offsets, and `renderVisibleRows`/`renderHighlightVisibleRows` read the matching one when setting each row's `style.height` — so offsets and rendered heights always agree. `needsRowOffsets()` now returns true for `multilineMessages || showNotes || wrapMessages`. With wrap on, `syncTableRowsWidth`/`syncHighlightRowsWidth` short-circuit to no forced row width (the message wraps within the viewport, so there is nothing to scroll to horizontally).

**Entry Detail follows the log-view toggle.** The detail panel shows the *selected log entry*, so `.wrap-messages` also governs `#detailMessage`: off (default) it is `white-space:pre` and `#detailBody` scrolls horizontally; on it is `white-space:pre-wrap; word-break:break-word`. No separate control — the log-view toggle is the one that owns "how a log message is shown."

**Text View (`state.wrapTextView`).** A **separate** `#itvWrapBtn` toggle in the inline-viewer toolbar (`#inlineViewerToolbar`'s Settings group, which now shows for **any** text file so this toggle is reachable on `.txt`/`.xml`/`.json`; Pretty Print stays JSON-only and hides itself otherwise — see "Inline text/image viewer" below). `updateWrapTextViewButton()` toggles a `.textview-wrap` class on `<body>`: off (default) `#inlineTextViewer` is `white-space:pre` and `#inlineViewerBody` scrolls horizontally; on it is `white-space:pre-wrap`. **The line number is a CSS `::before` counter on each `.itv-line` (one element per LOGICAL source line)**, so a wrapped display line stays inside its `.itv-line` and shares that line's number — wrapping never adds or shifts a line number. Toggling is a pure CSS switch (no `innerHTML` rebuild), so the viewer's scroll position and selection are undisturbed; the click handler just flips the flag, updates the class/button, and calls `schedulePersistMeta()`.

**Persistence**: both `state.wrapMessages` and `state.wrapTextView` ride in the same `settings` object `buildCacheMeta()`/`restoreSessionFromCache()` already carry `multilineMessages`/`pinBookmarksInFilteredView` in — additive fields, no `CACHE_FORMAT_VERSION` bump. Browser-local IndexedDB session cache only, **not** the portable `buildSessionExport` JSON (same tier decision as `multilineMessages`). See `docs/persistence-and-sync.md` → "Session cache".

Regression-tested: **Group 211** (`tests/philogg.regression.test.js`) — 211a: the log-view toggle flips `state.wrapMessages` + the `.wrap-messages` body class on both toolbars' buttons, makes a long-message row taller than one `ROW_HEIGHT`, stays independent of the multiline toggle, and round-trips both flags through the session cache's `meta.settings`; 211b: the Text-View toggle flips `state.wrapTextView` + `.textview-wrap` without changing the number of numbered `.itv-line` elements (a wrapped display line shares its logical line's number), independent of the log-view toggle.

## Entry detail: Pretty — format + syntax highlight embedded XML/JSON

**Pretty**, the default stage of `#detailViewTabs` (see "Entry detail: Raw | Parsed | Pretty" below — until 2026-09-27 this was the separate `#detailFormatToggle` on/off button), pretty-prints and syntax-highlights XML/JSON fragments **embedded anywhere inside** the entry detail message's free text (e.g. `Sending Control <ctrl><cmd>reset</cmd></ctrl> successful`, or `Response: {"status":"ok"} done`); **Parsed** is the same message without it. `updateDetailPanel()` computes `formatMessageWithHighlight(entry.message)` in Pretty, but only actually USES that output in place of `markFieldHtml` text-match marking when it contains a fragment (a `syn-block` span) — a message with no embedded XML/JSON/dump (the common case) falls through to `markFieldHtml`/plain text exactly as in Parsed, so the default view doesn't silently break text-match highlighting for messages that have nothing to format. Combining fragment-highlighting and text-match marking on the *same* substring space is still out of scope — a message that has both wins on the fragment side.

**Two-pass detection, never trust a regex alone**: `findEmbeddedFragments(text)` scans left to right for CANDIDATE spans — a `<letter...` open tag through its balanced matching close tag (`matchXmlSpanEnd`, nesting of any tag names allowed, text content between tags skipped over freely, a self-closing `<tag/>` matches itself) or a `{`/`[` through its bracket-matched, double-quote-string-aware close (`matchBracketSpanEnd`) — then validates each candidate before ever treating it as a hit: `isWellFormedXml` parses it via `DOMParser`/`"application/xml"` and checks for a `parsererror` node; `isValidJson` runs it through `JSON.parse`. A candidate that fails validation (unbalanced, malformed, or just not actually well-formed) is left as plain text and the scan resumes one character later — this is what keeps a stray `<` or `{` used as everyday punctuation (`if (x < y) { ... }`) from ever misfiring; conservative by construction, not by a blocklist of "risky" characters.

**Rendering, always via `escapeHtml`**: `formatMessageWithHighlight` walks the hit list and, for each one, calls `formatXmlFragmentHtml`/`formatJsonFragmentHtml` — both re-walk the ALREADY-VALIDATED parsed structure (the DOM tree from `DOMParser`, or the value from `JSON.parse`) and rebuild it as indented, `<span class="syn-*">`-wrapped HTML, escaping every actual piece of text (tag/attribute names, attribute/string values, JSON keys) through `escapeHtml` same as the rest of the app — only the `<span>` wrapper tags themselves are real markup, so an attacker-shaped-but-unmatched fragment (e.g. an unclosed `<img onerror=...>`) never becomes live DOM, it just renders as escaped text like any other non-matching span. Everything between hits is escaped the same way plain messages always were. Highlighted token classes: `.syn-tag`/`.syn-attr-name`/`.syn-attr-value` (XML), `.syn-key`/`.syn-string`/`.syn-number`/`.syn-bool-null` (JSON), `.syn-punct` (both — brackets/braces/colons/commas/quotes-as-markup). `.syn-block` wraps each fragment as `white-space:pre` (its own pretty-printed indentation should render exactly as built, unlike the surrounding message's `white-space:pre-wrap` reflow).

**Each block on its own, left-aligned line (person-requested, 2026-09-04)**: `formatMessageWithHighlight` inserts a literal newline right before and right after each fragment's `<span class="syn-block ...">`, unless one is already there (a fragment at the very start/end of the message gets no leading/trailing blank line; a message that already put the fragment on its own line via `\n` doesn't get a doubled one). `#detailMessage`'s `white-space:pre-wrap` turns those into real line breaks, and `.syn-block`'s own `display:inline-block` then simply starts flush at that new line's left edge — no extra CSS needed, the newline alone is what makes it "left-aligned" rather than sitting wherever it happened to fall inline with the surrounding text.

**A third fragment type, `"dump"` — .NET-style `ToString()` object dumps (this session, 2026-09-04, person-reported follow-up)**: a candidate `{...}` span that fails `isValidJson` (e.g. `TestProcedureParameters { Type = MyProgramRecipe, ViewerName = , MyProgramRecipeId = 4c382e97-... }` — unquoted keys, `=` instead of `:`, blank values) is now tried against `parseKeyValueDump` before being given up on as plain text. `splitTopLevelByComma` cuts the span's inside on top-level commas only (same depth/quote tracking as `matchBracketSpanEnd`, so a nested `{ }`/`[ ]` or a `"..."` string inside a value doesn't get split apart); each non-blank segment must match `identifier = value` (`DUMP_KV_RE`) with at least one such segment, or the whole candidate is rejected and left as plain text — same conservative "every piece must fit, or none of it lights up" rule the XML/JSON paths already follow, so a genuine code block like `if (x < y) { do(); other() }` (no `=` in its one segment) or `{ a = 1, just some text }` (one segment that doesn't fit) never misfires. `formatDumpFragmentHtml` renders it flat (one level, not recursively re-parsing a nested dump inside a value) via the same `syn-key`/`syn-string`/`syn-punct` classes JSON already uses — no new CSS needed. Wired into `formatMessageWithHighlight` as the third branch alongside `"xml"`/`"json"`.

**Not a fragment: an empty `[]`/`{}` glued to an identifier.** A .NET stack-trace frame such as `Execute(ObjectMethodExecutor executor, Object controller, Object[] arguments)` used to yield the candidate `[]` (valid JSON), which `formatMessageWithHighlight` then broke onto its own line. `findEmbeddedFragments` skips a bracket span whose inside is blank when the character before it is a word character (`isWordChar`) — a type or index suffix, not a value. `items: []`, `{"a":[]}` and non-empty spans such as `Foo["x"]` are judged as before.

**Colors** are `--syntax-tag`/`--syntax-attr-name`/`--syntax-attr-value`/`--syntax-string`/`--syntax-number`/`--syntax-key`/`--syntax-boolean-null`/`--syntax-punct` — see "Theming" → "Syntax-highlight colors" below for how they fit the theme var system (`SYNTAX_COLOR_KEYS`, fixed defaults for Dark/Light, optional per every other theme) and for the separately-selectable syntax scheme (FEATURE_BACKLOG.md #67) that can drive them independently of the app theme.

Regression-tested: **Group 169** (`tests/philogg.regression.test.js`) — Pretty is the default, persists, and gates plain-vs-formatted rendering; XML detection + highlight (tag/attr-name/attr-value spans, nesting, self-closing, surrounding plain text preserved); JSON detection + highlight (keys, string/number/boolean/null values); conservative detection (`a < b`, `if (x < y) { ... }`, an unclosed `<open>`, a malformed `{"bad": }` all stay plain text); XSS safety (an unmatched tag never becomes real DOM markup, a validated fragment's escaped characters are re-escaped, not injected raw); the theme export/import round trip for the optional `syntaxHighlightColors` block; 169g/h cover the `.NET`-style dump detection and its own conservative no-misfire cases.

## Entry detail: Raw | Parsed | Pretty

`#detailViewTabs` — a three-option `.view-tabs` switch in `#detailPanelHeader`, left of the collapse button — picks what `#detailMessage` shows, three stages of the same entry (person-requested: *raw → parsed → pretty*):

- **Raw**: the entry's original text, `entry.raw` — every physical line of a multi-line entry, tabs, indentation and the message's quotes kept, nothing parsed away. Blank lines inside an entry are not part of `raw` (the parser drops them as continuation lines for every format except plain text), so Raw can't show them either.
- **Parsed**: the parsed message, fields in the header line.
- **Pretty** (default): Parsed, plus embedded XML/JSON pretty-printed and highlighted (the section above).

One global choice, persisted (`localStorage["philogg-detail-view"]` = `raw`/`parsed`/`pretty`, `detailView`, `setDetailView`, restored by `initDetailViewSetting`; an unset or unknown value means Pretty) — it's a way of reading entries, not a property of one entry. The header line (level, time, thread, location, method) is the same in all three.

Per entry kind:

- **Formatted logs** (default, pattern, regex): the header line plus its continuation lines, exactly as read (CRLF line ends normalized to `\n`).
- **JSON Lines**: the compact JSON line from the file; Parsed shows the message key's value.
- **Plain text**: the line itself — identical to Parsed.
- **Link pairs**: a filter *under* a link node lists pairs in the ordinary log table, and a pair row now reaches the detail panel too (`selectedEntry()` looks a `pair:` id up in `currentViewEntries`, since pairs never enter `entryIndex`; row actions still resolve via `currentRowActionEntry()`, which returns `null` for a pair instead of throwing). A pair's `raw` is not a contiguous piece of any file (`buildPairEntry` joins the sides with ` ⟶ `), so Raw shows each real entry's own `raw` in its own block (`entryRawParts` → `getTupleEntries`, `.detail-raw-part` with a dashed separator) and no synthetic separator. The Link view itself (`renderLinkView`) has no detail-panel wiring; its pair blocks are unaffected.

**Match marking in Raw** (`markRawHtml`): a filter without a column restriction tests the whole raw line, so its matches are marked anywhere in the raw text; a column-restricted filter or highlight rule has no reliable place in it and marks nothing there. The find bar marks everything, as in every other view.

## Log view column visibility / width (`FEATURE_BACKLOG.md`; generalized for Custom Columns)

`#btnColumns` (`#viewBar`, next to `#btnMultilineMsg`) opens `#columnsPanel`. **Since Custom Columns** (later session — per-format custom columns, see `PROJECT.md` → "The log formats it parses"), the checkbox list is no longer a fixed four: `renderColumnsPanel()` JS-renders it from **Δt** (fixed) + `activeColumnDefs()` (the dynamic union of every currently-loaded format's own Thread/Location/Method/custom columns) + **Message** (fixed — hideable per format now too, via a format's own `messageVisible` flag, though the panel's checkbox is still the one global user-preference layer on top, same as any other column). Time/Level stay always-visible, no checkbox, no width of their own beyond their fixed default. `#tableHeader`'s row-grid content (`.th` cells + `.col-resize-handle` drag handles) is likewise JS-built now (`renderColumnHeader`/`buildRowGridHeaderHtml`/`buildResizeHandlesHtml`), rebuilt whenever the active column set changes (`refreshColumnState()`, called from file add/remove and a Format Manager save); `columnResizeHandleEls`/`columnToggleInputs` are collected fresh each time rather than being fixed DOM refs grabbed once at load. Message still has no width of its own when shown — it's the grid's `1fr` flexible remainder — but the remainder track now writes an explicit `0px` instead of `1fr` when the format(s) in play hide it, so a hidden Message doesn't still silently claim the row's leftover width.

**Applied entirely through `--row-grid`, the CSS custom property `.row-grid` (shared by `#tableHeader`, `#highlightHeader`, and every `.log-row` data row in both Log views) already used as its `grid-template-columns`** — `applyRowGrid()` recomputes the whole string from `columnWidthFor(key)`/`columnVisibleFor(key)` (lookups into `state.columnWidths`/`state.columnVisible` with a sane per-key fallback — `FIXED_COLUMN_WIDTHS[key]` for a legacy column, `DEFAULT_CUSTOM_COLUMN_WIDTH` for a freshly-authored custom one — so neither object needs an entry pre-created for every possible key) and writes it via `document.documentElement.style.setProperty`. This is the reason the feature costs essentially nothing at render time: flipping a checkbox or dragging a handle just changes one CSS variable, and every row (Filter + Highlight, virtualized or not) reflows natively — no per-row DOM writes, no `render()` needed for the drag itself (only at drag-end, to persist). A hidden column's track collapses to `0px` (not removed from the grid, not `display:none` on the per-row `.col-*`/`.col-custom` spans) specifically to avoid corrupting CSS Grid's row auto-placement — see the mobile-breakpoint paragraph below for the bug this exact mistake caused elsewhere in the same feature.

**Resize handles are positioned via JS, not nested inside `.th`**: `.th` has `overflow:hidden` for its own text-ellipsis truncation, which would clip an absolutely-positioned handle poking out past its own border box. Instead, `.col-resize-handle` spans sit as siblings of the `.th` elements inside `#tableHeader .row-grid` (`position:relative`, scoped to the header only — `.row-grid` is shared with every data row, which must NOT become a positioning context), each with `data-col` and a `left` computed by `applyRowGrid()` itself (cumulative `COLUMN_BAR_WIDTH + Σ(gap + column width)`, iterating Time/Δt/Level then `activeColumnDefs()`). Being `position:absolute`, they're out of grid flow entirely and don't consume an auto-placement slot among the real grid items — the same property that makes the 0px-track (not `display:none`) choice above necessary for the *real* row items. Drag-resize and double-click-autofit are wired via **event delegation on `#tableHeader` itself** (`ev.target.closest(".col-resize-handle")`) rather than one listener per handle — a deliberate choice for Custom Columns, since the handle set is now rebuilt whenever the active column set changes, and delegation means resize/autofit keep working after a rebuild with no re-attachment step.

**Mobile breakpoint bug found and fixed while building the original feature**: the pre-existing `@media (max-width:760px)` rule set its own `:root{--row-grid:...}` override AND `.col-thread,.col-loc,.col-method{display:none;}` directly in CSS. Both had to go: (1) an inline style (what `applyRowGrid()` now always sets) unconditionally wins over any media-query rule, so the old override would simply never have applied again once this feature shipped; (2) independently of that, the `display:none` half was **its own latent bug** — a `display:none` grid item doesn't reserve its track, so with grid items removed from participation the remaining ones auto-place sequentially into the wrong tracks, silently shifting Message into a collapsed column's slot instead of the real `1fr` track. Fixed by folding the narrow-viewport override into `applyRowGrid()` itself (`COLUMN_MOBILE_BREAKPOINT = 760`) — same 0px-track mechanism as the desktop visibility toggle, so no auto-placement risk. Since Custom Columns, the force-hidden set on mobile is every column in `activeColumnDefs()` (Thread/Location/Method plus any custom columns) — Δt stays visible, just narrower, same as the original feature's own mobile rule. `window.addEventListener("resize", applyRowGrid)` keeps it live across the breakpoint.

**Persistence**: `state.columnVisible`/`state.columnWidths`, same `settings` tier as `multilineMessages`/`pinBookmarksInFilteredView` (`buildCacheMeta`/`restoreSessionFromCache`) — global, not per-file, and (since Custom Columns) restored by whatever keys the persisted object itself has rather than a fixed key list, so a custom column's remembered width/visibility survives a reload too. `FIXED_COLUMN_WIDTHS` (was `DEFAULT_COLUMN_WIDTHS`) matches the original hardcoded `--row-grid` values exactly for the six legacy keys, so a first-ever load (or "Reset widths" in the popup, which now resets to `{...FIXED_COLUMN_WIDTHS}`, clearing any custom column's width back to its own default) is visually identical to before either feature existed. `COLUMN_MIN_WIDTH = 40` clamps a drag from shrinking a column to nothing.

Regression-tested: **Group 58** — 58a (checkbox toggle collapsing/restoring a track and its own handle's visibility, Reset widths), 58b (drag-resize live width update + `COLUMN_MIN_WIDTH` clamp + no stray effect after mouseup), 58c (persistence across a simulated reload), 58d (the mobile-breakpoint fix — forces Thread/Location/Method to 0px without mutating the stored preference, restores on widening back past the breakpoint) — updated in place for the dynamic panel (checkboxes now queried by `[data-col]` inside `#columnsList`, not fixed `#colToggle*` ids) and the "loc"→"location" key rename (bundled cleanup while touching this code — CSS class `.col-loc`→`.col-location`, `data-col="loc"`→`"location"` — closing a pre-existing split between the grid-track key and the filter/context-menu key, which had used `"location"` all along).

**Middle-click a header title to hide it, double-click a resize handle to auto-fit (person-requested).** Two quick alternates to the popup/drag interactions above, wired on top of the same shared state: (1) middle-clicking a hideable header's title (Δt, or any column in `activeColumnDefs()`, or Message — Time/Level have no `data-col` and stay unaffected) sets `state.columnVisible[key] = false`, the exact same effect as unchecking it in `#columnsPanel`, including syncing the checkbox itself if the popup happens to be open and already rendered; wired on **both** `#tableHeader` and `#highlightHeader` (`toggleColumnFromHeaderClick`, `auxclick` with a `mousedown` `preventDefault` twin to suppress the browser's middle-click autoscroll indicator, same pattern the tree row's middle-click-to-delete handler already established) since both headers' `.th` spans carry the matching `data-col` attribute and both views reflow off the one shared `--row-grid`. (2) Double-clicking a `.col-resize-handle` (`autofitColumnWidth`) sets that column's width to the widest rendered value **across the whole active file's entries** (`state.nodes[getRootFileId(state.activeId)].entries`), not just `currentViewEntries` — the point is fitting everything the column could ever need to show, the same reasoning `computeMaxMessageWidth` already applies to the message column's horizontal-scroll width (see above); for a custom column (or any key beyond time/delta/location) the on-screen text comes from the same `entryColumnValue(e, key)` the row renderers use. Measured via `measureColumnText`, one cached off-screen `<span>` per column reusing `columnCssClass(key)` (a built-in field's own class, or the shared `.col-custom` for anything else — `.col-level` additionally nests a `.level-badge` span so its padding/border are measured too) — same shrink-to-fit-then-`offsetWidth` technique and jsdom-blind-spot character-count fallback (`MONO_CHAR_WIDTH_FALLBACK`) as `measureMsgWidth`. `COLUMN_AUTOFIT_PADDING = 8` adds a little slack so the widest value isn't flush against the handle; still clamped to `COLUMN_MIN_WIDTH`. **Perf fix, same day (person-reported: auto-fit was slow on a large file):** the original loop called `measureColumnText()` — a real `offsetWidth` read — once *per entry*, each one a forced synchronous reflow; on a big file that meant thousands of layout thrashes. Fixed the same way `computeMaxMessageWidth` already avoids that for the message column: a cheap O(n) character-length scan (no layout) finds the single longest string, then exactly ONE real measurement of just that string — monospace font, so longest-in-characters is also widest-in-pixels. Regression-tested: **Group 154** — 154a (middle-click hides + syncs the popup checkbox, non-middle button is a no-op, always-visible columns unaffected), 154b (Highlight view's header hides the same shared column), 154c (auto-fit grows a column past its default to fit the file's actual longest value, floor at `COLUMN_MIN_WIDTH`) — 154a updated in place for the dynamic panel/renamed key, same as Group 58 above.

## Log row multi-select + copy (`FEATURE_BACKLOG.md` suggestion, person-requested this session)

Ctrl+click toggles a row into/out of `state.logMultiSelect` (a `Set` of entry ids); Shift+click selects the contiguous range from the last-clicked anchor (`logMultiSelectAnchorId`), replacing the set — standard file-explorer semantics, including that a repeated Shift+click re-derives the range from the SAME anchor, not the previous Shift+click's own target. A plain click keeps its pre-existing single-selection behavior unchanged and clears the multi-selection. The first Ctrl+click after a plain click folds the existing `state.selectedId` into the set too, so "click A, then Ctrl+click B" reads as "A and B selected" rather than silently dropping A. `handleLogRowClick(ev, entryId, viewEntries, selectFn)` is the one shared handler wired onto both Log views' row `click` listeners (`currentViewEntries`/`selectEntry` for the Filter table, `currentHighlightViewEntries`/`selectHighlightEntry` for the Context view) — `state.logMultiSelect` is shared between them exactly like `state.selectedId` already is, so a range built in one view's rows shows the same tint on the other view's copy of the same entries.

**Ctrl+C copies the raw text** (`copyLogSelectionToClipboard`) — the multi-selected entries (or just `state.selectedId` alone when nothing's multi-selected), looked up via the global `entryIndex` and joined by `entry.raw` (which already accumulates continuation lines for multi-line stack traces, see "The log format it parses"), **sorted chronologically by timestamp** rather than click/DOM order, so a series of out-of-order Ctrl+clicks still copies in log order. Both this and the row context menu's own "Copy" item (below) build their clipboard text through the one shared `formatEntriesForClipboard(entries)` (`entries.map(e => e.raw).join("\n")`), so the two paths can never format the same rows differently. This takes priority in the keydown handler over the tree's own filter-node clipboard (`state.clipboard`, existing Ctrl+C/X/V) — but only when `state.focusRegion === "entries"` (the log view, not the tree, was the last thing interacted with); the tree-node copy is otherwise unaffected. **Exception, added 2026-08-26 (`FEATURE_BACKLOG.md` #55, person-requested)**: the Entry Detail panel (`#detailMessage`) has always been selectable text (no `user-select:none`), but Ctrl+C previously ignored that and always overrode it with the full raw line. Now the handler checks `window.getSelection()` first — if there's a non-empty selection anchored inside `#detailPanel`, it returns without calling `preventDefault()` or `copyLogSelectionToClipboard()`, letting the browser's native copy grab just the selected substring. With no such selection, behavior is unchanged.

**"Copy" — bottom item of the row context menu (`#ctxCopy`, `FEATURE_BACKLOG.md` #78, person-confirmed semantics)**: right-click and "Copy" does NOT just call `copyLogSelectionToClipboard()` — that would silently ignore which row was actually right-clicked in favor of whatever `state.logMultiSelect`/`state.selectedId` happens to hold. Instead: if the right-clicked entry's id is a member of the current `state.logMultiSelect`, it copies the **whole current selection** (calls `copyLogSelectionToClipboard()` unmodified, so multi-select's own chronological sort applies); otherwise — the row is outside the current selection, or nothing is selected at all — it copies **just that one right-clicked row** via `formatEntriesForClipboard([entry])`. Always shown (a right-click always has a concrete row to act on, unlike Bookmark/Note/Time-filter-from-selection, which hide when they don't apply). Also reachable from a Link-view pair block's own right-click (`entry.id` there is a synthetic `"pair:..."` id, never a member of `logMultiSelect`, so a pair block always copies just itself via its own `entry.raw`).

**Rendering**: no full re-render on Ctrl/Shift+click — `updateLogMultiSelectClasses()` toggles the `.row-multi-selected` class directly on whichever rows are currently in the DOM, same in-place-toggle technique `updateSelectedRowClass` already uses and for the same reason (a full `renderVisibleRows()`/`innerHTML` rebuild on every click would break native `dblclick` detection — see CLAUDE.md's gotcha list). A normal `render()` (e.g. after Escape clears the set) still bakes the class into each row's `className` string directly from `state.logMultiSelect` at render time, so scrolling the virtualized window afterward stays correct without any extra sync call.

**CSS pitfall hit and fixed while building this, caught via a real-browser (Playwright) screenshot check, not just the jsdom suite**: the first cut styled `.row-multi-selected` with a plain `background`. It rendered completely invisible except on rows with no level class. Root cause: `.log-row.lvl-error`/`.lvl-warn`/etc. (the existing per-level row tinting) ALSO set `background`, at equal specificity (`.log-row` + one class, `0,0,2` either way) and later in the stylesheet — so the level tint always won outright, not blended. This is the *exact* fight `.pinned-row`'s own comment already documents and solves the same way: switched to `box-shadow:inset 0 0 0 2px var(--accent-strong)` instead, which doesn't touch `background-color` at all and so composes over any level tint unconditionally. Since `.selected` also uses `box-shadow` (a single-value property — two separate class rules setting it don't stack, only one wins per the cascade), an explicit `.log-row.selected.row-multi-selected{box-shadow:inset 0 0 0 1px var(--accent), inset 0 0 0 3px var(--accent-strong);}` combines both shadows for a row that's simultaneously the multi-select's focused row and a member of the set — its higher specificity (three classes vs. two) wins over either rule alone regardless of source order. **Lesson for future row-decoration work here**: `background` is claimed by the level-tinting rules; any new per-row visual state needs `box-shadow` (or a `left`/gutter marker, see `.pinned-row`/`.ctx-bracket`/`.hl-markers`), not `background`, unless the new state is meant to compete with (or is mutually exclusive with) level tinting.

Regression-tested: **Group 57** — plain click behavior unchanged; first Ctrl+click folding the prior selection in; Ctrl+click toggle-off (and its anchor move); Shift+click range selection (replace, not extend) and repeated-Shift-click re-deriving from the same anchor; Ctrl+C priority over the tree clipboard gated on `focusRegion`; Escape clearing state + DOM class; and the selection/class being shared between the Filter and Highlight views. The CSS specificity bug above was caught via manual Playwright screenshot review (jsdom has no layout/paint engine, see "Testing approach" below), not by the automated suite — same class of gap the multiline-toggle CSS-flex-direction bugfix note already flags. **Group 223** covers `#ctxCopy`'s selection-aware semantics: right-clicking a row outside the current selection (or with nothing selected) copies just that row; right-clicking a row that IS part of an active multi-selection copies the whole selection, byte-identical to calling `copyLogSelectionToClipboard()` directly.

### Tree row layout: indentation, collapse/expand, type indicator

Person-reported/requested reworks (this session, screenshot-driven) to `renderNode`'s row structure:

- **Indentation**: `row.style.paddingLeft = 8 + depth * TREE_INDENT_STEP` with `TREE_INDENT_STEP = 10` (18px until 2026-09-27 — once the connector lines carried the hierarchy the wide step only wasted sidebar width, person-reported). Absolute positioning keeps them out of the row's flex layout (no gap, no shift) and `pointer-events:none` keeps every click on the row. Load ticks don't touch the guides (they update rows in place); every `render()` rebuilds them with the tree.

  `Rename… | Edit filter… | Invert (NOT) | Mute` · `Adjust clock…` · `Add to library…`

## Theming

Rewritten this session (2026-08-22) from a two-way Light/Dark toggle into a full theme picker: six built-in themes (Dark, Light, and four Catppuccin flavors — https://catppuccin.com/palette/) plus unlimited user-imported custom themes, all selected from one `<select id="settingsThemeSelect">` dropdown in Settings → Appearance (previously an `.assert-mode-btn` Light/Dark button pair, see `tests/philogg.regression.test.js` Group 3/70h/70h2's updated text and the new Group 85).

**The var surface** (`THEME_COLOR_KEYS` in the Theme script section) is unchanged from before: `--bg-app`, `--bg-panel`, `--bg-elevated(-2)`, `--border(-soft)`, `--text-primary/secondary/tertiary`, `--accent(-strong/-soft)`, `--level-error/warn/info/debug/trace` (+ `-soft` alpha variants), `--warn`. `--level-error/warn/info/debug-on` + `--accent-on` (`THEME_ON_KEYS`) are the text/label color for the level-quick-filter buttons (always-on now, see "Level-bar shape and position" above — they're solid-filled regardless of `.active`) and for anything sitting on a solid `var(--accent)` surface (brand mark, Save button, active chips/badges) — split out of the level/accent colors themselves into their own vars (defaulting to near-black in `:root`) precisely so a theme can flip them to white without a dedicated CSS selector per theme. `--border-hover` is *derived*, not stored — `color-mix(in srgb, var(--border) 70%, var(--text-tertiary) 30%)` in `:root`, so every theme (including a custom one applying vars inline) gets a correct hover-state border automatically from its own `--border`/`--text-tertiary` with no extra required JSON key.

**Stylesheet audit, same session, follow-up ("Prüfe... ob Du das konsequent umgesetzt hast").** A pass over every rule outside the `:root[data-theme=...]` blocks found ~18 places still hardcoding the DARK theme's own hex/rgba values instead of the var every sibling rule already used — invisible on Dark (where the hardcoded value and the themed one happened to match) but wrong on every other theme: the scrollbar thumb, `#btnOpen`/`#btnSession`/`.toolbar-icon-btn` hover borders, `.brand-mark`'s gradient/text, `.toolbar-badge`/`.column-chip.active`/`.btn-mini` text, and — the highest-impact group — `.crumb.current`/`.level-btn.lvl-*`/`.level-badge`/`.log-row.lvl-*:hover`/`.token-chip`'s alpha-tinted borders and backgrounds, all still using the dark theme's specific level-color rgba() triplets regardless of the active theme. Fixed via `--accent-on`/`--border-hover` above for the flat-color cases, and `color-mix(in srgb, var(--x) N%, transparent)` for the alpha-tinted ones (CSS can't apply an arbitrary alpha to a `var()` color any other way; every browser this app targets — Chromium, for the File System Access API it already requires — supports `color-mix()`). The timeline minimap was audited too and needed no changes: `.minimap-lvl-*`/`.minimap-bg-bar`/`.minimap-full-range`/etc. were already `fill:var(--level-error)` etc. from when the minimap was first built. **Deliberately left alone**: modal/dialog backdrop scrims (`rgba(16,19,26,.7-.88)`) and `box-shadow`s (`rgba(0,0,0,...)`) — a dark dimming layer and a black shadow are a normal convention regardless of the app's own light/dark theme, not a theming bug; and `COLUMN_PALETTE`'s 6 fixed extraction-column/plot colors (`.pattern-chip-num`'s `color:#0b1016`) — see "Visual language" below, deliberately theme-independent by design, unrelated to `--accent-on` despite the visual similarity. Group 82a is a static regression guard (`.textContent` of `<style>`, not computed style — jsdom can't resolve `color-mix()`) against the specific hardcoded literals this audit found creeping back in.

**Two application mechanisms, one var surface.** The six built-ins are plain CSS: one `:root[data-theme="<id>"]{...}` override block per theme (Light's block also sets the four `-on` vars to white, same as before; Catppuccin Latte does too — both are light-background themes whose level colors are too dark for the near-black default). Custom/imported themes have no CSS block — `applyTheme(themeId)` sets `data-theme` on `<html>` either way, but for a custom theme it also walks `THEME_COLOR_KEYS`/`THEME_ON_KEYS` and sets each one as an inline `style.setProperty("--x", ...)` on `document.documentElement`, after first clearing every one of those properties (so switching *back* to a built-in never leaves a stale inline override shadowing its CSS block — verified in Group 81b). `setTheme()` calls `applyTheme()` then persists the id to `localStorage` (`philogg-theme`, same key/tier as before); `initTheme()` on load resolves a stored id through `resolveThemeId()` (falls back to `"dark"` if it names a since-deleted custom theme — Group 81c) or, with nothing stored yet, falls back to `prefers-color-scheme` same as before. `initTheme()` itself only runs at the very end of the big inline `<script>`, which would otherwise leave a visible flash of the default dark `:root` values before it does (worst on Light/Latte) — a tiny synchronous `<script>` right after `<body>` (this session, 2026-09-08) reads the same `localStorage["philogg-theme"]` key (or `prefers-color-scheme`) and sets `data-theme` immediately, without duplicating `resolveThemeId()`'s custom-theme lookup; `initTheme()` still runs later and corrects a stale/unresolvable id.

**Custom themes** are stored as `{id, name, colors: {...THEME_COLOR_KEYS}, activeTextLight, syntaxColors?, highlightPalette?}` in a `customThemes` array persisted to `localStorage` (`philogg-custom-themes`) — same tier as the theme choice itself, not IndexedDB (unlike the Log Formats/Filter Library lists, which expect larger/more numerous entries; a handful of ~25-key color maps doesn't need that). Settings → Appearance has a "Custom themes" card (reuses the `filter-library-row` list styling from Log Formats) with **"+ New theme…"** (`#btnThemeNew`) and, per row, a 4-stripe swatch (bg/accent/error/info), click-to-activate, **Edit**, **Export** and delete (falls back to Dark if the deleted theme was active). The "Custom syntax schemes" card is the same with "+ New scheme…" (`#btnSyntaxNew`).

**Theme editor** (`#themeEditorDialog`, `openThemeEditor(kind, opts)` — kind `"theme"` or `"syntax"`; stacked above Settings at z-index 80 like `#formatDialog`, Esc closes it — an open color picker on top first). Opened for a new entry (starts from the *currently active* colors via `getComputedStyle`), for **Edit** on a custom entry (renaming included — saving replaces the entry under its own id and re-applies it if active), or prefilled from an imported file (`opts.prefill`; saving adds a new entry). **Syntax-highlight colors** (`SYNTAX_COLOR_KEYS` — `--syntax-tag`/`--syntax-attr-name`/`--syntax-attr-value`/`--syntax-string`/`--syntax-number`/`--syntax-key`/`--syntax-boolean-null`/`--syntax-punct`; see "Entry detail: format + syntax highlight embedded XML/JSON" above for the feature that uses them). A parallel array to `THEME_COLOR_KEYS`, but unlike it, **no theme is required to define these** — fixed hardcoded defaults live only in bare `:root` and `:root[data-theme="light"]` (Dark/Light get real, curated values), and every other theme (the four Catppuccin flavors, and any custom/imported theme) is free to skip the block entirely and simply inherit those `:root` defaults through the normal CSS cascade.

**Independently selectable scheme (FEATURE_BACKLOG.md #67, 2026-09-13).** The syntax colors are no longer tied to the app theme. Settings → Appearance has a **Syntax highlighting** picker (`#settingsSyntaxSchemeSelect`, `populateSyntaxSchemeSelect`) separate from the app-theme dropdown, with three kinds of choice:
- **"Follow app theme"** (`FOLLOW_THEME_SYNTAX_ID`, the default) — tracks the active app theme. For a **built-in** app theme, `applySyntaxScheme()` applies that theme's own `BUILTIN_SYNTAX_SCHEMES` pendant inline, same as if it had been explicitly picked (fixed 2026-09-14, person-reported: previously this branch was a no-op relying purely on the CSS cascade, so `--syntax-*` only ever changed between Dark and Light — the four Catppuccin flavors have no `[data-theme]` `--syntax-*` block of their own in CSS, so they all silently inherited Dark's colors and "Follow app theme" never visibly changed between them or when switching into/between them). For a **custom** app theme (no matching `BUILTIN_SYNTAX_SCHEMES` id), it's still the pre-#67 no-op: `--syntax-*` come from that theme's own optional `syntaxColors` block (below) or the `:root`/light cascade defaults. Not written to `localStorage` unless explicitly chosen.
- **A built-in scheme** — `BUILTIN_SYNTAX_SCHEMES`, one curated pendant per built-in app theme (Dark/Light reproduce the `:root` defaults; the four Catppuccin flavors map each flavor's own named colors onto the eight keys — tags/keys=Blue, attr-name=Yellow, attr-value/string=Green, number=Peach, boolean-null=Mauve, punct=Subtext0). Selectable regardless of which app theme is active.
- **A custom scheme** — created or edited in the theme editor's syntax mode ("+ New scheme…"/Edit, see "Theme editor" above) or imported (central import → the same editor, prefilled), stored as `{id, name, colors}` in `customSyntaxSchemes` (persisted to `localStorage["philogg-custom-syntax-schemes"]`); a new one is switched to immediately. Each list row has a swatch, click-to-activate, Edit, Export (`philogg-syntax-scheme` JSON — `format`, `version`, `name`, `colors` of the eight keys, `*.syntax.json`) and delete (falls back to follow-theme if the deleted scheme was active).

The chosen scheme id persists to `localStorage["philogg-syntax-scheme"]` (same tier as the theme/accent choices); `resolveSyntaxSchemeId()` falls a stale/deleted id back to follow-theme on init (`initSyntaxScheme`, called from `initTheme` before the first `applyTheme`). **How it layers**: `applyTheme()` first clears every `--syntax-*` inline prop (its existing `style.removeProperty` sweep, `THEME_COLOR_KEYS.concat(THEME_ON_KEYS, SYNTAX_COLOR_KEYS)`) and, for a custom *theme*, re-applies that theme's own `syntaxColors`; then it calls `applySyntaxScheme()`, which — when a specific scheme is chosen — overrides the eight vars inline from that scheme's `colors`, decoupling them from the app theme entirely, and — for follow-theme on a built-in app theme — from that theme's own `BUILTIN_SYNTAX_SCHEMES` pendant instead (see above). `setSyntaxScheme()` re-runs `applyTheme(currentThemeId())` so the clear+reapply+override sequence is uniform whether the app theme or the scheme changed.

**A custom theme may still carry its own `syntaxColors` block** (unchanged, honored under "Follow app theme"): `applyTheme()` mirrors `THEME_COLOR_KEYS`'s optional-set pattern — `if (custom.syntaxColors) SYNTAX_COLOR_KEYS.forEach(k => { if (custom.syntaxColors[k]) style.setProperty(...) })`. In a theme file it's the optional `syntaxHighlightColors` block; the theme editor stores it only while "Part of this theme" is checked (missing entirely just means "use the default"). This theme-embedded block and the independent scheme picker coexist: with follow-theme selected the theme's block (if any) wins; with a scheme selected the scheme's colors override it.

Level colors (`--level-error/warn/info/debug/trace` + `-soft`) were re-themed for Light back in 2026-08-17 (from `FEATURE_BACKLOG.md` — previously reused the dark-mode hex values verbatim, which read poorly against the light panel background); values unchanged this session. Not regression-tested for actual rendered color (jsdom can't assert CSS color values or contrast — see "Testing approach" / `tests/README.md`'s "Known gaps"), but Group 81a does assert the resolved `getComputedStyle(...).getPropertyValue("--x")` string for a couple of load-bearing vars per built-in theme, which at least catches a wrong/typo'd hex or a misrouted `[data-theme]` block.

## Inline text/image viewer (`.txt`/`.json`/`.xml`/etc., `.jpg`/`.png`/etc.)

Opening a non-log file of a common text or image type (`inlineViewableKind`) shows it in `#inlineViewerWrap`/`#inlineTextViewer`/`#inlineImageViewer` (`openInlineViewer`, `state.inlineViewer`) instead of loading it as a log file. Works uniformly regardless of HOW the file enters the app — a ZIP entry, a folder-watched file, or a direct open/drag-drop — see "General file support across entry points" below for how each one routes into the same `openInlineViewer`.

**Tokenizers** (`jsonTokenRanges`/`xmlTokenRanges`) return `{start, end, cls}` ranges over the raw line; `highlightJsonText`/`highlightXmlText` render them via `tokenRangesHtml`, and a plain-text file's log rows reuse the same ranges (see "Filter lines" below).

**Line rendering**: each source line is a single inline `<span class="itv-line" data-line="i">` holding the line's raw text directly (tokenizer `<span>`s for JSON/XML syntax highlighting only, see `highlightJsonText`/`highlightXmlText`), all inside one `<pre id="inlineTextViewer">`. **Line numbers are a CSS `::before` counter** (`counter-reset:itv-line` on `#inlineTextViewer`, `counter-increment`/`content:counter(itv-line)` on `.itv-line`, positioned at `left:1.3em` in the line's own `4.6em` left-padding gutter) — generated content, never a DOM text node, so it categorically cannot enter a text selection or a `copy` event; native browser select/copy is correct by construction, including leading whitespace/tabs, with no `copy` event interception needed anywhere. Hover highlight is pure CSS `:hover` on `.itv-line`, no listener/state. The `dragstart` prevention on `#inlineTextViewer` opts out of the browser's native "drag the current selection" gesture, which otherwise hijacks a re-selection click near an existing selection.

**Collapsible JSON/XML sections**: `findJsonFoldRanges`/`findXmlFoldRanges` do a lightweight bracket/tag-matching scan (not a full parser, in the same spirit as the regex tokenizers) over the raw text to find multi-line `{...}`/`[...]` or `<tag>...</tag>` ranges — a single-line construct doesn't fold. `buildFoldTree` nests the resulting ranges (they never cross, coming from a stack matcher) into a tree of line/fold nodes; `renderFoldNode` wraps each range's lines in `<span class="itv-fold" data-start data-end">`, with a small real (non-pseudo, since it needs to be clickable) `.itv-fold-toggle` glyph — `left:0` in its own slot immediately left of the line-number counter — on the opening line. Clicking it toggles a `collapsed` class on the `.itv-fold` — pure CSS (`.itv-fold.collapsed > :not(:first-child):not(.itv-fold-ellipsis){display:none}`) hides every line but the opening one and shows a `.itv-fold-ellipsis` (`…`) placeholder; no re-render, so scroll position/selection elsewhere in the viewer is undisturbed. The ellipsis is `padding-left:1.3em`'d in to line up with the line-number column (person-requested) rather than sitting flush-left under the fold-toggle arrow — it's a plain inline element right after the block-level opening `.itv-line`, not a descendant of it, so without that padding it starts a fresh line back at column 0.

**Toolbar**: `#inlineViewerToolbar` (between `#inlineViewerHeader` and `#inlineViewerBody`) is a real toolbar row, not the image viewer's own former floating overlay pill — same Controls | Settings grouping convention `#contextToolbar`/`#plotToolbar` already use. Both sub-viewers share ONE toolbar: Controls holds the image zoom/pan/reset buttons (`#imgZoomOutBtn`/`#imgViewerZoomLevel`/`#imgZoomInBtn`/`#imgZoomResetBtn`), Settings holds `#itvPrettyPrintBtn`. `updateInlineViewerToolbar(v)` (called from both `renderInlineTextViewer`/`renderInlineImageViewer`) toggles each `.toolbar-group`'s own `hidden` class based on `v.kind`/`v.ext`, the separator between them, and the whole toolbar row (hidden entirely for a plain `.txt`/`.xml` file, which has neither).

**Not rebuilt by unrelated renders** (performance review, 2026-09-25): `renderMainView` calls the viewer's renderer on every `render()` (a folder scan, a sidebar click). `renderInlineTextViewer` rebuilds its markup only when the viewer object or its Pretty Print state changed (`inlineTextViewerEl._shownViewer`/`_shownPretty`) — re-tokenizing a large file each time cost seconds and reset collapsed folds and the selection. `renderInlineImageViewer` replaces the `<image>` element only for a different viewer (`imgViewerSvg._shownViewer`); pan and zoom (every mousemove of a drag, every wheel step) only move the viewBox, where each event used to re-parse the multi-MB `data:` URL into a fresh element. The image's natural size lives on its viewer (`v.naturalSize`, measured once by a probe `Image`): the old module-level `imgNaturalSize` was measured for the first image ever opened and reused for every later one, which drew a second image with the first one's dimensions. Group 272h.

**JSON Pretty Print**: `#itvPrettyPrintBtn` shows only when `state.inlineViewer.ext === "json"` (via its Settings group, above). Toggles `viewer.prettyPrint`; when on, `renderInlineTextViewer` derives the text it folds/tokenizes/renders from `JSON.stringify(JSON.parse(v.text), null, 2)` instead of `v.text` — `v.text` itself (and so `state.inlineViewer.text`, what copy/select ultimately reads) is never mutated, so turning it back off always restores the exact original bytes. Invalid JSON refuses to turn the toggle on (a `showCopyToast` names the file) rather than silently rendering nothing or the untouched original.

**Viewer separation bugfix** (person-reported: the previously-open XML's fold arrows/text still showed "behind"/around a newly opened image): every other `.hidden`-toggled element in this file gets its own `#id.hidden{display:none}` rule (there is deliberately no bare `.hidden{display:none}` — see the stylesheet-audit comment near `#sidebarResizer.hidden`) — `#inlineTextViewer` never had one, so the JS toggling its `hidden` class did nothing visually: the `<pre>` stayed in normal flow underneath/around `#inlineImageViewer`'s `position:absolute` box instead of actually disappearing. Fixed with `#inlineTextViewer.hidden{display:none;}`.

**Image zoom precision bugfix** (person-reported: drag-to-zoom was imprecise — the selection wasn't fully shown, its center didn't land at screen center). Root cause: the viewBox used to be built from the raw selection's own aspect ratio and left to the SVG's own default `preserveAspectRatio` ("xMidYMid meet") to fit it into the viewport — which silently adds its OWN extra letterbox bars whenever that aspect doesn't match the viewport's, on top of a separate manually-computed pixel-to-SVG-unit `scale` factor this code already applied. Every pointer-to-data mapping (`imgSvgPointFromEvent`) assumed the viewport's full `clientWidth`/`clientHeight` maps 1:1 to the current domain span — true only when there's no such hidden extra letterbox. Fixed by removing the separate `scale` factor entirely (viewBox units are now raw image-pixel units) and setting `preserveAspectRatio="none"` on `#imgViewerSvg` (stretch exactly, no independent fitting), paired with `imgAspectFit(centerX, centerY, spanX, spanY, aspectWH)`: given a requested center+span, expands whichever axis is proportionally too small (never crops) so the result always has exactly the viewport's own aspect ratio — the "letterbox" now lives in DATA space (extra domain around the content), which the pointer mapping already accounts for correctly. `homeFit` (the whole image, aspect-fit to the viewport) is what "zoomed all the way out" means now, and what `imgClampAxis` clamps every further zoom/pan against — not the raw image domain. The drag-select mouseup handler also clips the raw dragged rectangle to the image's own bounds FIRST (only the part that actually intersects the image counts), then calls `imgAspectFit` around that clipped rectangle's own center.

**"Filter lines" — a text file as a filterable file** (`#itvFilterLinesBtn`, funnel icon, in the Settings group for every text viewer): `openInlineViewerAsTextLog(v)` loads the text the viewer **displays** (`inlineViewerDisplayedText` — the pretty-printed JSON while Pretty Print is on, the file's own text otherwise; the same function `renderInlineTextViewer` renders from, so the two can't disagree) as a new root file pinned to the **Plain text** format (`PLAINTEXT_FORMAT_ID`, see `PROJECT.md` → "The log formats it parses"), named `"<file> (pretty)"` when pretty-printed. The viewer closes and the new file's log view takes its place. **Ctrl+F** (the `newFilter` shortcut) on a text viewer does the same and then opens the filter popup on the text version. Taking the displayed text is the point: a minified JSON document is a single line, and only its pretty-printed form is line-filterable. What a plain-text file looks like in the log view:
- **No level badge.** Its entries have no level, so rows, pair rows and the entry detail render no `.level-badge` at all (`levelCellHtml`/`levelBadgeHtml`) — an empty badge still paints its padding and background as a small block.
- **Minimap**: at most one bucket per line (consecutive line numbers would otherwise leave every other bucket empty).
- **Line instead of Time.** Its entries' `ts` is the line number, shown as such everywhere (`entryTimeText`, `formatTsFor`): the Time cell, entry detail, context-menu header, minimap ("Lines N", tooltip and drag label in lines) and time-filter names ("line 2 → line 3" — "Filter after/before this" and a minimap drag-select become line ranges). No Δt on its rows.
- **With only plain-text files loaded** (`allRootsPlainText`): the header's Time column reads "Line" and uses its own width key `line` (default 64px), Δt and Level collapse to 0px (and the Columns panel doesn't offer Δt), the level bar has no buttons (the format has no levels), and "Filter for this ___"/the filter chips offer Line and Message. Loading any real log brings the ordinary columns back.
- **Table/Plot**: the extraction table's second synthetic column (`ELAPSED_COL`) is **Line** — the absolute line number — instead of `t (ms)`, and a fresh plot's X axis defaults to it.
- **Indentation and syntax colors.** Its message cells are `.col-msg.plaintext` (`msgColClass`: `white-space:pre`, `pre-wrap` under word wrap, `tab-size:4`), so leading spaces/tabs stay. A JSON/XML text version (`plainTextSyntaxOf`: `node.textSyntax`, else derived from the name) is highlighted with the viewer's own tokenizers, as token *ranges* (`jsonTokenRanges`/`xmlTokenRanges`) that `markCombinedHtml` merges as the innermost layer with filter and highlight-rule marks — a finished HTML string couldn't be merged with those. Only visible rows are tokenized (the views are virtualized).
- **Tree placement.** The new file carries `node.viewerSource` (the viewer's `ownerKind`/`ownerId`/`mapKey`) and renders one level below its viewer entry's row (`buildInlineViewerEntryRow` appends `renderNode(id, 1)` for each of `viewerTextLogIds` and draws its connector lines with `decorateTreeGuides` — renderNode only does that for depth-0 subtrees), with its filters below it; `renderTree`/`flattenTreeIds` skip it at top level while `isNestedUnderViewer` holds (its viewer entry is still open) and walk it right after the viewer's nav id. "Filter lines" again for the same version re-activates it; closing the viewer entry closes its text versions too (undoable, `deleteFile` undo — not through `deleteFilterNodeWithUndo`, whose quit-on-last-file-closed would fire while the viewer is still open). Both survive a reload: the text version's file record keeps `viewerSource`/`textSyntax`, and the viewer itself is restored (see `docs/persistence-and-sync.md` → "Session cache" → "Text and image viewers"); from a ZIP (not restored) it comes back top-level.
- Plain-text files are refused as merge sources (`describeBulkActions`).

**General file support across entry points**: originally ZIP-only; generalized so a folder-watched or directly-opened/dropped file gets the same treatment.
- **ZIP**: `zip.inlineViewers` (`Map<entryName, viewer>`) is the "opened" cache; `renderZipEntryRow` is now a thin wrapper around the shared `renderInlineViewerEntryRow(ownerKind, ownerId, viewersMap, mapKey, displayLabel, openFn)`.
- **Folder watch**: `scanFolderHandle`'s listing filter (and the native-desktop `window.philogg.listFolder` extension list) now also admits `inlineViewableKind` files, not just `.log` (`isCompatibleFolderFile` itself keeps meaning "is a log file" — `isLogZipEntry` and `applyFolderAutoRules`' auto-open/auto-close/show-newest rules still key off it alone, deliberately never applying to a non-log file). Each folder object gets its own `inlineViewers: Map` (same role as `zip.inlineViewers`); `loadFolderFile` branches to `openInlineViewer` before ever reaching `loadOneFileIntoTree`; `renderFolderSection` renders such a row via the same shared `renderInlineViewerEntryRow`.
- **Direct open / drag-drop**: `loadFileDescriptors` filters out `inlineViewableKind` descriptors up front — before the queued-placeholder/merge-confirmation machinery that exists purely for the log-parsing pipeline — and opens each individually. These have no natural owning container, so they're tracked in `state.looseInlineViewers` (`Map<syntheticId, viewer>`) and rendered as their own top-level rows directly in `renderTree`, after the real tree rows.
- **Closing**: every one of these rows gets a `.tree-del` ✕ (click) and middle-click (`auxclick`) close, exactly like a real log tree row's own affordance (`renderNode`'s `mousedown`/`auxclick` pair). Bugfix (person-reported): the close button was present in the DOM but invisible/inert on every one of these rows — `.tree-del`'s hover-to-reveal CSS was scoped to `.tree-row:hover .tree-del`, and these rows are `.folder-watch-file`/`.zip-source-file`, never `.tree-row` — fixed by adding a `.folder-watch-file:hover .tree-del{opacity:1;}` rule alongside the original.
- **Identity/navigation**: a viewer object carries `ownerKind` (`"zip"`/`"folder"`/`"loose"`), `ownerId` (the zip/folder's own id, or `"loose"`), and `mapKey` (its key in the owning Map) instead of the old ZIP-only `viewer.zipId`. `viewerNavId`/`isViewerNavId`/`parseViewerNavId`/`viewerMapForOwner` (generalized from the old `zipViewerNavId`) give `flattenTreeIds`/`moveTreeSelection` a virtual nav id for Alt+Up/Down to land on, for all three owner kinds — a non-log entry never gets a real `state.nodes` id.

# UI and Views

Header/toolbar layout, the three active-node views, the Context/Filtered split (internally still the "Highlight" view), tree interactions, theming, and the app's visual language.

## Header / toolbar layout

The header (`#toolbar`) is a plain flex row, left to right: `.brand` (wordmark, fixed at the left), the back/forward nav group, a `.toolbar-spacer` that eats the remaining width, then `.toolbar-right` (status text, undo/redo, settings) flush against the right edge. `.brand` is itself a column: `.brand-row` (the mark + "PhiLogg" name) on top, `.brand-version` (`#brandVersion`, the short commit-hash build tag) in a smaller line directly underneath. The header used to also carry a small subtitle ("local, single-file log viewer") next to the brand name — removed per a person UI-adjustment request; `.brand-tag` no longer exists in either markup or CSS.

**Toolbar regroup (FEATURE_BACKLOG.md #56, this session, person-requested):** `#btnOpen`/`#openMenu` and the former `#btnSession`/`#sessionMenu` used to live in `#toolbar`'s right side. Both moved into `#sidebarHeader` (the "Files & filters" section header, between the label and `#sidebarToggle`) as small icon-only buttons styled with `.panel-toggle-btn` (the same 24x24 shape as `#sidebarToggle`) instead of the old pill-shaped `#btnOpen, #btnSession{...}` rule, which was removed. "Open…" now covers all three "bring something in" actions — File(s)…/Folder…/Import session… — via `#openMenu`'s dropdown; "Session…" as a separate button is gone, and `#btnSave` is a single icon button (no dropdown, since there's only the one action) that calls `openSessionExportDialog()` directly. See "Session export / import" further down for the current session-export/import writeup.

**Back/forward navigation (FEATURE_BACKLOG.md #53, this session, person-requested, placement adjusted same session per follow-up feedback):** `#btnNavBack`/`#btnNavForward` step through a history of previously-visited filter nodes — modeled on browser/IDE back/forward, explicitly distinct from Undo/Redo (which tracks tree *edits*, not view visits; `undo()`/`redo()` never touch `navHistory` or scroll position). They first landed in `#sidebarHeader` alongside Open/Save, then moved into `#toolbar` itself — same row as Settings/Undo/Redo, but grouped with `.brand` on the LEFT side of `.toolbar-spacer` instead of the right, so they sit right next to the wordmark, closer to it than the rest of the toolbar's controls (which stay flush right exactly as before). The version tag moved the other way in the same follow-up: out of `#toolbar`'s right side, into `.brand-version` under the wordmark (see above) — neither move touches `.toolbar-right`'s own contents or the Electron titlebar-overlay padding rule that targets it (`desktop/main.js`).

Implementation lives just above `render()` in `philogg.html`: `navHistory` is an array of `{nodeId, scrollTop}`, `navHistoryIndex` the current position. `render()` already detects every `state.activeId` change in one place (`lastActiveIdForReveal`, used for `revealFilteredView()` — the ~30 call sites that set `state.activeId` directly all funnel through here), so `recordNavVisit()` piggybacks on that same check instead of instrumenting each call site: a real navigation (not one caused by clicking back/forward itself, guarded by the `navigatingHistory` flag) truncates any forward entries past the current index and appends a new one. The active node's scroll container (`tableBody`/`extractScroll`/`linkScroll`, matching `renderMainView()`'s own isLink/isExtract branching — see `activeNavScroller()`) is tracked continuously via a `scroll` listener while the user dwells on an entry, so Back-then-Forward restores exactly where they'd scrolled to, not just the position at the moment they navigated away. Going back/forward that lands on a since-deleted node drops that stale entry and retries in the same direction (`goToNavHistoryIndex`'s self-recursion) rather than getting stuck. Browser/OS back/forward mouse buttons (`ev.button === 3`/`4`) are wired to the same `navigateBack()`/`navigateForward()` via a `document` `mouseup` listener, with `preventDefault()` so the browser/OS chrome doesn't also try to navigate the page itself.

**`#viewBar`** — a single row at the top of `#content`, above `#fhSplit`, that merges what used to be **three separate toolbar rows**: the breadcrumb (active filter chain), the level quick-filter, and the Context/Filtered/Stacked toggle. `#fhTabs` (the toggle), `#btnPinBookmarks` (the pin-bookmarks toggle, moved in from the header — see "Pin bookmarks into the Filtered View") and `#levelBar` are `float:left`, so they stay **pinned to the top-left line** no matter how long the filter chain gets, in that DOM order (tabs, then the pin toggle, then the level pills); `#breadcrumb` is a plain block (not flex) with `display:inline-block` chips, so it flows text-style around those three floats on the first line(s) and then uses the **full row width** on any line it wraps to below them — a filter chain long enough to wrap doesn't push the toggle/pin/level-filter down or squeeze itself into a narrow leftover column, it just drops to its own full-width line(s) underneath. `#viewBar` itself is `display:flow-root` so its own height always reaches the floats' bottom edge even when the breadcrumb is short or empty (a plain float doesn't otherwise contribute to a parent's auto height). Flexbox can't produce this "first line shares space, later lines full width" shape — a flex item's box is always one rectangle — hence floats + normal block flow instead; see the CSS comment directly above `#viewBar` if this needs touching again. **`#viewBar` also needs its own `flex:0 0 auto`** — that's a separate concern (how `#viewBar` behaves as a flex ITEM of its parent `#content`, a flex column, not how it lays out its own children) that got dropped once already and let `#content`'s flex-shrink algorithm compress `#viewBar` below the floats' actual height whenever the window was short on vertical space, clipping/overlapping the toggle+level-filter against the table below; `#statusStrip`/`#timelineMinimap` carry the same declaration for the same reason. **(Updated, this session, 2026-08-18, person-requested)** The row used to be always visible with zero files loaded (just an empty `#fhTabs`/`#levelBar`/`#breadcrumb` shell) — now `renderMainView()` hides `#viewBar` itself (`viewBarEl.style.display = hasFiles ? "" : "none"`, the `""` restoring the CSS class's own `display:flow-root` rather than hardcoding a value) whenever no file is loaded, so `#emptyState`'s centered hint is the only thing on screen instead of an empty toolbar row above it — see "No-file-loaded state" below for the other two hints removed alongside this. With files loaded, the row is visible exactly as before, and only `#fhTabs` is separately hidden/shown by `renderMainView()` within that: the active node is an extraction filter (no Context companion) → `fhTabs.style.display = "none"`; otherwise `"flex"`. **(Updated again, same session, person-requested)** `#levelBar`, `#btnPinBookmarks`, `#btnMultilineMsg`, `#btnColumns` and `#breadcrumb` used to all stay visible and populated in every loaded-file state, including extract mode — that's now narrowed: extract mode hides everything in `#viewBar` except `#breadcrumb` (only `#fhTabs` used to hide there; now `#levelBar`/`#btnPinBookmarks`/`#btnMultilineMsg`/`#btnColumns` join it, all four reset back to visible — `style.display = ""`, restoring each one's own base CSS `display` value — the moment `renderMainView()` leaves extract mode). None of the four apply to what's actually on screen in the extraction table (its own columns aren't `--row-grid`-based, and it has no Context companion to pin/multiline-toggle), so hiding them isn't just decluttering — they were genuinely inert there. `renderExtractTable()` still calls `applyLevelFilter()` internally against whatever the quick-filter was last set to; there's just no visible pill row to change it from while this view is showing. If `#viewBar` needs touching again: extract mode's own branch in `renderMainView()` is now the one place that hides more than `#fhTabs` — everything else in the row stays a simple visible/hidden pair tied to `hasFiles` (see the paragraph above). `#btnPinBookmarks` keeps its own `.toolbar-icon-btn`/`.active` look (an icon button, styled like the other header toggles it used to sit next to) rather than being restyled as a `.level-btn` pill — it's an additive OR toggle, not a subtractive level filter, and looking identical to the pills would misrepresent what it does; it's positioned in the same floated row as the level pills, not literally nested inside `#levelBar`. **Sizing (bugfix, same session)**: `.toolbar-icon-btn`'s fixed `29x29px` box is correct in the header, where every neighboring button is the same square — but here it made `#btnPinBookmarks` visibly taller than `#fhTabs`/`#levelBar`/`#breadcrumb`, which all get their height from `padding:4px` + `border:1px` + content instead of a fixed box (see `.crumb`'s own CSS comment for the underlying mechanic). Fixed with a `#btnPinBookmarks{width:auto; height:auto; padding:4px 8px}` override, scoped to the id (not `.toolbar-icon-btn` itself, so the header buttons using that class are untouched) — the button now sizes around its 12x12 icon exactly the way `.level-btn` sizes around its text, landing at the same row height instead of towering over it. See "Context view (Context/Filtered split)" → "Layout" for the toggle itself.

**Breadcrumb chips are sized to match the level filter pills** (`.crumb`'s `font-size`/`padding` mirror `.level-btn`'s exactly — same 10.5px text, same 4px 9px padding — so the two pill styles read as one consistent row instead of the breadcrumb looking subtly smaller/shorter). **Matching font-size and padding alone wasn't actually enough** — `#breadcrumb` used to carry `line-height:26px` (leftover from before the chips were resized, meant to space wrapped lines apart), silently inherited by the inline-block `.crumb`/`.crumb-sep` and adding ~26px on top of their padding, since an inline-block's own single line of text IS sized by line-height. `.level-btn` never showed the equivalent problem because it's a flex container — flex layout ignores line-height for its own box sizing entirely, so the mismatch was invisible on the level side and only visible on the breadcrumb side. Fixed by removing the line-height from `#breadcrumb` and setting `line-height:normal` explicitly on `.crumb`/`.crumb-sep` instead; the gap between wrapped lines now comes purely from their own vertical margin. **Lesson for future work here**: `font-size`/`padding` parity between two differently-laid-out elements (flex vs. inline-block) doesn't guarantee height parity — check `line-height` too, since it only affects one of the two layout modes.

**Same row, a third round: top alignment.** Even with matching height, `.crumb`'s chips weren't reliably lining up vertically with `#fhTabs`/`#levelBar`'s floated tops — `vertical-align:middle` aligns an inline-block relative to its *parent's* font baseline/x-height, not to wherever a float happens to start; the two only coincided by accident, dependent on inherited font metrics, and could drift. Fixed by switching `.crumb`/`.crumb-sep` to `vertical-align:top` with `margin-top:0` — since `#fhTabs`/`#levelBar` are the first content in `#viewBar` and floats don't push the following normal-flow content's *starting* y-position down (they only narrow the available width), a float's top and `#breadcrumb`'s first line both begin flush at `#viewBar`'s content-box top; pinning `.crumb` to the top of its own line box (instead of centering it against a font-metric reference) makes it coincide with that same y-position structurally, not by coincidence. The wrapped-line spacing that used to come from `.crumb`'s top+bottom margin now comes from `margin-bottom` alone (`0 4px 6px 0`), matching `#fhTabs`/`#levelBar`'s own `margin-bottom` for a consistent gap. `.crumb-sep` keeps a small top margin (`4px 3px 6px`) to roughly center its thin "›" glyph against the taller padded pill beside it, rather than sharing the pill's own top-alignment reference — it has no padding/border of its own, so top-aligning it flush would visually sit too high next to the pill's text. **Chips are also clickable**: `renderBreadcrumb()` attaches a click handler per chip that sets `state.activeId`/`state.multiSelect` to just that node and calls `render()` — the exact same single-select behavior a plain (non-Ctrl) tree-row click already does (see `renderNode`'s row click handler) — so the breadcrumb doubles as a quick "jump to an ancestor filter" shortcut without any new selection machinery. Works for every node in the chain, including the file root at the start and the currently-active node's own chip (a harmless no-op re-selection).

**(Removed 2026-08-25, person-requested — superseded by Alt+Arrow tree navigation, see "Tree interactions" below)** Hovering the current breadcrumb chip used to pop up a flyout listing the active node's children, letting you jump deeper in the filter tree without opening the sidebar. **Round 4 (person screenshot, this session, 2026-08-14): #fhTabs is the actual height reference, not the pills.** Despite three rounds of matching `.crumb`/`.level-btn` to *each other* (padding, then `line-height:normal`, then `vertical-align:top`), the View-Toggle (`#fhTabs`) still rendered visibly taller than everything beside it — because none of those rounds ever compared against `#fhTabs` itself. Root cause: `#fhTabs` is structurally a **nested double box** — `.view-tabs`' own `padding:2px`+`border:1px`, wrapping `.view-tab`'s own `padding:4px 11px` — while `.crumb`/`.level-btn`/`#btnPinBookmarks` are each a **single box** (one padding+border layer). At equal content height, that's an inherent ~4px of extra chrome on `#fhTabs`' side that no amount of padding/line-height *parity between the pills* could ever close — the three earlier rounds were solving the wrong equation. Also discounted incorrectly by round 2's reasoning (see its comment above): a flex container's own auto height **is** affected by `line-height` when the flex item is inline text (verified empirically this session), so `.level-btn` was never actually immune to line-height the way that comment claimed. Fixed by pinning **explicit, non-`"normal"` `line-height` values** (removing all remaining font-metric/platform dependence — `var(--font-ui)`/`var(--font-mono)` are system-font stacks, which is exactly why "close but not quite" kept recurring across rounds) so the arithmetic is provably equal regardless of platform: `.view-tab`'s `line-height:12px` reproduces `#fhTabs`' own pre-existing rendered height (no visible change to the reference itself) — outer `padding(4)+border(2)` + inner `padding(8)+line-height(12)` = 26px total. `.level-btn`/`.crumb` get `line-height:16px` — `padding(8)+border(2)+line-height(16)` = 26px, matching exactly (the extra 4px of line-height is precisely what the missing nested-box chrome cost them). `#btnPinBookmarks` gets a direct `height:26px` (simplest option there, since it's already flex-centered — no line-height math needed). `.crumb-sep`'s top margin grew `4px → 7px` to keep its glyph roughly centered against `.crumb`'s now-taller box. Verified against a real Chromium render (not just jsdom, which has no layout engine and could only assert the declared CSS values): all four elements now measure exactly 26px. See `.view-tab`/`.level-btn`/`.crumb`/`#btnPinBookmarks`'s own CSS comments for the full arithmetic if this row needs touching again.

## The three "active node" views

`renderMainView()` picks a view based on the active node's `filterType`, all mutually exclusive:

1. **Log view** (default) — virtualized (`ROW_HEIGHT = 28`, `BUFFER_ROWS = 10`) so it stays smooth at any file size; only the rows in/near the viewport are ever real DOM nodes. Has the level quick-filter bar, click-to-select + arrow-key navigation, right-click context menu (filter before/after this, extract numbers), double-click **reveals the entry in the Context view** (see below) with flash highlight, and a resizable detail panel at the bottom (drag the handle above it) showing the full selected message with preserved line breaks. The tree sidebar's width (`#sidebarResizer`) and, in Stacked layout, the Context/Filtered split (`#fhSplitResizer`) are resizable the same way — see "Context view" below.
2. **Extraction table** (`filterType === "extract"`) — spreadsheet-style grid, not virtualized (extraction results are expected to be selective). Has its own Table/Plot tab switcher (see Plotting below). Cell selection is a `Set` of `"row,col"` keys (not a rectangle) specifically so Ctrl+click can build **non-contiguous** selections (e.g. columns 1 and 3, skipping 2) — plain click/drag/shift-click still do contiguous ranges. Copy is always plain TSV (paste-ready for Excel) via `copyTextToClipboard` (Clipboard API with an `execCommand` fallback for `file://` contexts where the modern API may be restricted). The pattern is shown above the table as numbered, colored chips (`COLUMN_PALETTE`, cycles if >6 columns) with **bidirectional hover linking**: hover a column header/cell → its chip highlights; hover a chip → its column highlights; hover a row number → all chips highlight (the whole pattern produced that row). The only view with **no Highlight-view companion** — double-click still does the old destructive full-log jump (`jumpToFullLog`), since there's nowhere else in this view to reveal the entry.
3. **Link pair view** (`filterType === "link"`) — each pair rendered as two individually-clickable/double-clickable rows joined by a visual brace with a Δ-time label between them. Right-click the brace = context menu on the *combined* pair entry (so "Extract numbers" works across both sides); right-click one row = context menu on just that side; double-click a row = reveals that row's real underlying entry in the Highlight view, same as the log view (see below — link view is a Filter-view "flavor" for this purpose, not a separate case).

**Log view and link view are both "Filter view" flavors**, each paired with a **Context view** — see the dedicated section below.

## Context view (Context/Filtered split)

Two views of the same file, introduced together as `#fhSplit`. The **Filter view** (UI label "Filtered") is the pre-existing log/link view, narrowed by the active filter-tree node. The **Context view** (UI label "Context") shows **the active node's own result with the log around it**: the matches, and everything the filter rejected collapsed into expandable gap strips between them. Internally every identifier still says "Highlight" (`renderHighlightView`, `#highlightWrap`, `highlightColorMap`, `fhLayout`, `fhActiveTab === "highlight"`, …) — the same naming compromise the earlier "Full" rename made, for the same reason: a full internal rename is a much bigger, riskier diff than the UI change it would serve. Context-view-specific identifiers added since do use a `context*` prefix (`buildContextView`, `contextGaps`, `contextStrips`, …).

**Why it was reworked** (person-reported): the view used to be `state.nodes[rootId].entries` — the root file's raw entry array, *regardless of `state.activeId`*. That made it pixel-identical on a filter node and on a file node, so people read "Full" as having switched them onto the file node and were surprised the filter was still active. There was no wrong signal to correct; there was no signal at all. Reframing it as "your result, seen in context" is what the view was for in the first place (*"den Kontext der Filterergebnisse sehen, ohne im Tree umherzuspringen und immer wieder auf dem Root-Knoten zu landen"*), and it also retires the misleading Full/Filtered opposition — "Context" and "Filtered" describe a containment relation, not two filter strengths.

**What counts as a match** (`buildContextView`): `getEntries(state.activeId)` — the active node's own result set. Deliberately **not** `applyLevelFilter()`'d and not unioned with pinned bookmarks. Person-stated rule: *"egal was für eine Art Filter vorausging: der Output sind die Ergebnisse, alles andere ist Kontext"* — the level quick-filter (in `"explicit"` mode) hides result rows from the *Filtered view's display*; they never leave the result set, so they stay matches here. That keeps the older "the level filter must not narrow the whole-file view" requirement true, and `renderLevelBar()`'s click handler still calls `revealFilteredView()` so a level change is visible where it actually applies. `link` nodes contribute their real underlying entries via `getTupleEntries()`, not their synthetic pair ids — exactly as `computeHighlightMap` treats them.

**On a file node there is nothing to be outside of**: `contextActive` stays `false`, no row is marked, nothing is collapsed, and the view renders the plain whole file exactly as it did before the rework. That is what keeps its other, older purpose available — tracking two or three coloured highlight rules across a whole file while the Filtered view stays narrowed to something specific.

**The gap model.** A gap is the root-file index range `[start, end)` hidden between two consecutive matches, plus the leading range before the first match and the trailing one after the last. Each carries `before`/`after` — how many of its rows are currently revealed from the top and from the bottom — so the still-hidden remainder is always **one contiguous run**, which is what keeps a gap to a single strip however it was opened. `currentHighlightViewEntries` stays a flat array of real entries (matches plus revealed context rows, in root order), so the ~15 places that consume it — minimap, selection, Shift-click ranges, arrow-key nav, `captureViewAnchor` — needed no changes. Expansions live in `contextExpansions` (`gap.start -> {before, after}`), module-level and session-only, deliberately **not** on the node: that keeps them out of `cloneSubtree`/`snapshotSubtree`/`serializeFilterBranch`/`serializeFilterTreeForCache`, which every persisted node field has to be threaded through. They survive re-renders of the same node (a tail tick or a colour edit never shuts a gap you just opened) and are dropped wholesale when `state.activeId` changes, since a different result set makes the old index ranges meaningless.

**Gap strips** (`.ctx-gap`, `appendContextGapStrip`) are the GitHub-diff expander: `⌃` reveals `CONTEXT_EXPAND_STEP` (25) rows at the top of the hidden run, the middle button reveals all of it, `⌄` reveals a step at the bottom; the chevrons are withheld when less than a step is hidden. A fully open gap's strip turns into a "collapse" control and sits at the *top* of the revealed block. Strips render as plain block siblings after their preceding row — the same shape `appendNoteRow` uses — with their height folded into the virtualization math (see "Rendering" below).

**Row treatment**: a match gets `ctx-row ctx-match` plus `ctx-start`/`ctx-end` caps and the **same `.ctx-bracket` the `context`/`countContext` filter already draws in the Filtered view** — reusing a visual people read as "this is what the filter produced" is what makes the view legible without explanation. It gets its own gutter lane on `#highlightRows` (class `ctx-active`, left of the bookmark icon) rather than sharing `.hl-markers`' slot: in the Filtered view that overlap is a rare documented edge case, but here *every* match is bracketed, so sharing would collide constantly. A revealed context row gets `ctx-context` and recedes to `opacity:.5` — opacity only, never a colour change, or the `.lvl-error`/`.lvl-warn` row tinting (the most important colour information in a log view) would flatten; `:hover` and `.selected` restore full strength, since reading those rows is the entire point. A row carrying a highlight-rule colour is **never** dimmed, so "bright" means "relevant right now" whether that comes from the active filter or from a colour rule.

**Nav chip** (`#contextNav`, `updateContextNav`): replaces the Context panel's old `.fh-panel-badge` and, unlike that badge, is shown in tabs layout too — it *is* the view's answer to "am I still on a filter?", the question the view kept failing to answer. Holds `‹`/`›` (previous/next match, `moveContextMatchSelection`), the active node's name, "*n* / *m* matches" (the position comes from `contextMatchPos`, an id → ordinal map built during `buildContextView`'s own walk, so the chip can refresh on every selection change without an O(rows) scan), and one expand-all/collapse-all button. `pointer-events` are on, which is safe because `#highlightHeader` has no sortable columns underneath, unlike `#tableHeader`. The Filtered panel keeps its plain Stacked-only badge.

**Match-to-match navigation**: `Ctrl+↓`/`Ctrl+↑` (`nextMatch`/`prevMatch` in `SHORTCUT_ACTIONS`, rebindable) walk the real matches, skipping revealed context rows — the point being that you can work the result without going back to the tree. Their check sits right after the Alt+Arrow tree-nav block and ahead of *both* arrow-key blocks below it: an explicit modifier chord should do its one thing regardless of which region holds focus, and the plain-row block matches on `ev.key` alone with no modifier check, so it would otherwise swallow `Ctrl+Arrow` outright. With no filter active the chord degrades to plain row-to-row navigation rather than doing nothing.

**Initial state** — Settings → Behavior → "Context view starts out" (`contextInitialExpansion`, `philogg-context-initial-expansion`, plain `localStorage` preference): `"collapsed"` (default — the view then opens *as* the filter result, the strongest available "you are still on a filter" signal), `"expanded"` (every gap open, i.e. the pre-rework whole-file view, still collapsible per gap), or `"aroundJump"` (collapsed, but jumping into an entry also opens the gaps on either side of it).

**Jumping in still works exactly as before** — double-click in the Filter view, `Enter` on a single selection, a link-view pair row — all still route through `revealInHighlightView(entry, …)`, which selects the entry, reveals the Context panel and scrolls it there preserving the row's on-screen pixel offset, **without** touching `state.activeId` or the level filter. New: it first calls `applyContextJumpExpansion(entry.id)`, which opens the gap the target is hidden in. That is a correctness requirement, not a preference — a target inside a collapsed gap has no row to be scrolled to — so it happens for every setting value; `"aroundJump"` only adds the neighbouring gaps on top. `moveHighlightSelection` has the matching courtesy: a selected entry with no row here (hidden in a gap, or left over from another node) continues from its **would-be** position (`contextWouldBeIndex`, a binary search over the root order) instead of snapping back to the top of the list — the same idea the Filtered view's temp anchor already applies.

**Turning on a highlight rule**: each filter-type tree row (not file rows, not `extract` rows — see `renderNode`) has a small colour **swatch** button where the old multi-select checkbox used to be (see "Tree interactions" below for where that checkbox went). Click it to open a small custom colour picker (`#colorPickerPopup`) — a hue wheel (`conic-gradient` disc, click anywhere to pick a hue at a fixed 68%/55% saturation/lightness) plus a row of curated presets, deliberately **not** the native `<input type="color">` (Windows' native picker UX varies too much to be predictable here). Right-click the swatch, or "Clear colour" in the picker, clears it. The colour **is** the on/off state — no separate boolean; an uncoloured node just isn't a highlight rule. Two colours can coincide across different nodes (not deduplicated — may be intentional grouping) and travel with the node through filter save/load JSON, copy/paste (`cloneSubtree`), and undo/redo (`snapshotSubtree`/`restoreSubtree`), the same way `inverted`/`bakedA`/`bakedB` do.

**Computing highlight-rule matches** (`computeHighlightMap(fileId)`): walks every node under the file (not just the active chain — a highlight rule anywhere in the tree should show up), and for each coloured filter node adds its colour to every entry it matches, via `getEntries(node.id)` — cheap since `getEntries` is already memoized per node. `link` nodes are a special case: their results are synthetic pair entries, not real ones, so every real underlying entry — via `getTupleEntries(pair)`, which recurses through arbitrarily many nesting levels for a chained/multi-hop link, not just `pair.first`/`pair.second` one level deep, see "Link filter" → "Chained links" — gets the colour instead of the synthetic pair id. A row matching several rules gets several small colour markers (`.hl-marker`, thin stripes in the left gutter) rather than one blended colour — there's no natural priority between arbitrary user rules the way `LEVEL_SORT_RANK` orders log levels, so no attempt is made to pick a "winning" colour. **Shown in both views**: `renderVisibleRows()` (the Filtered view) renders the same markers from the same `highlightColorMap`, computed once per `renderMainView()` call (before either view's own render) rather than twice, so the Filtered view's first paint after a node/filter switch already has the right colours instead of showing the previous node's map until the next scroll. The Filtered view's own `.ctx-bracket` (time-context filter) uses the same left gutter slot — a row that's both context-bracketed and highlight-matched shows both markers overlapping; accepted as a known edge case rather than adding a second gutter lane.

**Text-filter match marking is shown in both views too** (`textMatchHighlightInRows`, Settings → Behavior → "Show matches in log rows"): `renderHighlightVisibleRows` runs the same `getTextMatchHighlightNodes`/`matchRangesFor`/`markRangesHtml` pipeline `renderVisibleRows` does. In Stacked layout the same entry is on screen in both panes at once, and marking it in only one of them read as two different rows.

**Selection stays unified**: `state.selectedId` is shared between both views (it always was, for the detail panel — see `updateDetailPanel`), so `updateSelectedRowClass` syncs the `.selected` class on whichever of `#tableRows`/`#highlightRows` currently has that row rendered, regardless of which view the click came from; it also refreshes the nav chip, whose "*n* / *m*" follows the selection. Plain click in either view just selects (`selectEntry`/`selectHighlightEntry`) — no scrolling of the other view.

**Layout**: a single tri-state toggle (`#fhTabs`, three buttons: "Context" / "Filtered" / "Stacked") — `applyFhView(view)` is the one entry point, `fhLayout` ("tabs" | "stacked") and `fhActiveTab` ("filter" | "highlight") are still the two pieces of underlying state, persisted to `localStorage` the same way the theme toggle is (a display preference, not session/filter data). "Context"/"Filtered" set `fhLayout` to `"tabs"` and pick which panel shows; "Stacked" sets `fhLayout` to `"stacked"` directly, showing both panels at once, **Context on top / Filtered on the bottom** (that's the actual DOM order inside `#fhSplit`, not a CSS `order` override) — `#filterSlot` at a resizable explicit height (`#fhSplitResizer`, drag handle between the two panels, same mechanism as the detail panel's resizer below, and same bottom-panel sign convention: dragging the handle down shrinks the panel below it), `#highlightWrap` filling whatever's left above it. Session-only, not persisted, same as the detail panel height. Stacked keeps its point after the rework: the result in context on top, the bare result underneath. The Filtered panel still carries a Stacked-only `.fh-panel-badge`; the Context panel's badge became `#contextNav` (above).

`#fhTabs` itself lives inside `#viewBar`, a single merged toolbar row that also holds `#levelBar` and `#breadcrumb` (see "Header/toolbar layout" below) — only `#fhTabs`'s own visibility is toggled by `renderMainView()` (hidden with no file loaded or on an extraction node, since extract has no Context companion); `#levelBar`/`#breadcrumb` stay visible in every state.

**Rendering**: the Context view has its own complete copy of the Filter view's virtualization scheme (`renderHighlightView`/`renderHighlightVisibleRows`/`scrollToHighlightIndex`/`setHighlightScroll`, `#highlightBody`/`#highlightSpacer`/`#highlightRows`) — a second, independent scroll container. It reuses the Filter view's `.row-grid`/`.log-row`/`.col-*` CSS wholesale (extended the relevant ID selectors rather than duplicating rules) so the two views' rows line up visually. Two things differ from `renderTable()`:

- **It always uses the offsets-array path.** Gap strips make row tops variable regardless of `state.multilineMessages`/`state.showNotes`, so `rebuildHighlightOffsets()` always builds `highlightRowOffsets` via `buildContextRowOffsets(entries, strips)` — same contract as `buildRowOffsets` (`offsets[i]` = pixel top of row `i`, one extra trailing slot for the total), with each strip's height added to the row it follows and the *leading* strip, which has no row to follow, folded into `offsets[0]`. Keeping that contract intact is what lets `findOffsetIndex`/`topVisibleEntryId`/`captureViewAnchor`/`restoreViewAnchor`/`minimapRenderedSpan` keep working unchanged; the one place that has to know is `renderHighlightVisibleRows`, where row 0's window must still start at `0` rather than at `offsets[0]`. `minimapRenderedSpan` was re-keyed from `needsRowOffsets()` to the offsets array's own presence for the same reason. In the common (collapsed) case this is *cheaper* than before the rework: the array is sized by the number of visible rows, i.e. the match count, not the whole file.
- **It does not reset scroll to the top on every render.** The Filter view resets on every tree/filter change because that always means "new content" there; resetting the Context view every time would make it useless as a stable reference while browsing the Filter view. It only resets when the root file itself changes (`lastHighlightRootId`). Opening or closing a gap goes through `captureViewAnchor`/`restoreViewAnchor` (`setGapExpansion`/`setAllGapsExpanded`) so rows appearing above the strip push the content down visually instead of yanking the scroll.

## Level bar: filter-tree mode (`FEATURE_BACKLOG.md` #10)

Settings → Behavior's `#settingsLevelFilterTreeMode` (`levelFilterTreeMode`, plain `localStorage`-persisted preference, same tier as `textMatchHighlightScope`) picks how the level bar (`#levelBar`) behaves — two modes, not a replacement of one by the other:

- **`"auto"` (default)**: clicking a level button no longer touches the old `state.levelFilter` Set at all. Instead it **upserts a single `filterType:"level"` node** (`value`: array of active level names, e.g. `["ERROR","WARN"]`, in canonical `activeLevelOrder()` order — see "Per-format log levels" below) **at the current tree position** — a real, visible, undoable, persisted filter-tree node, evaluated exactly like any other filter type via `getEntries`'s new `"level"` branch (`parentEntries.filter(e => node.value.includes(levelBucket(e.level)))`). `applyLevelSelectionToTree(levels)` is the one function behind this: if `state.activeId` is *already* a `"level"` node, it's edited in place (`updateFilterNodeWithUndo`) rather than nested under itself; toggling every level back off **deletes** the node (`deleteFilterNodeWithUndo` — a real, undoable action, unlike filter *creation* elsewhere in the app, which deliberately isn't undoable — see "Undo/redo" below) and `state.activeId` reverts to its parent (`deleteNode`'s own existing behavior); otherwise a fresh child node is created under the active node and becomes active, same shape as any other "Add filter" flow (`ctxAfter`/`commitFilter`). The level bar's own `.active` highlighting and per-button preview counts follow the tree position instead of a global flag: `activeLevelSetForBar()` reflects the active node's own `value` when it's a `"level"` node (empty otherwise — there's no "current selection" outside of an actual node anymore), and `levelBarCountsBaseId()` counts against the level node's *parent* (not its own already-narrowed result) so each button still previews "how many entries would this level admit here", the same question the counts always answered.
- **`"explicit"`**: the level bar keeps its original, tree-independent behavior byte-for-byte — a plain `state.levelFilter` Set, applied only inside `getVisibleEntries` (`applyLevelFilter`, unaffected by which tree node is active — see "Context view" above ("What counts as a match") for why the Context view has never seen it). A new toolbar button, `#btnApplyLevelToTree` ("Add to tree"), shown only in this mode (hidden in `"auto"`, where the level bar already writes into the tree — `updateApplyLevelToTreeButtonVisibility()`), pushes the current `state.levelFilter` selection into the tree on demand through the exact same `applyLevelSelectionToTree()` upsert logic, so re-clicking it while already positioned on the node it created edits that node instead of duplicating it. Disabled while nothing is selected on the level bar.

Switching modes **clears `state.levelFilter`** (the settings `<select>`'s `change` handler) so a quick-filter left set in one mode can't silently keep affecting the Filtered view once invisible in the other — filter-tree nodes already created are untouched either way, since only the level bar's own client-side behavior is mode-gated, not the tree's contents.

**No new persistence carrier work needed**: a `"level"` node's `value` is a plain array riding the existing generic `value` field every filter node already carries through `cloneSubtree`, `snapshotSubtree`/`restoreSubtree`, `serializeFilterBranch`/`importFilterJson`, and `serializeFilterTreeForCache`/`materializeCachedFilters` — the only change any of them needed was adding `"level"` to the shared `FILTER_TYPES` validation Set (otherwise `materializeCachedFilters`/`importFilterJson` would silently drop the node as an "unknown filter type"). Tree UI is equally generic: `typeTagFor`/`ghostTypeTag` gained a `"LVL"` case and `nodeIconHTML`/`ghostIconFor` a new ascending-bars `ICON_LEVEL`, same pattern every other filter type already follows.

**Tree-row label colored by the level(s) it filters, one solid color per word** (same-day follow-up, person-requested: *"schreibe die Einträge im Files & Filter Tree in der Farbe des Log Levels. auch kombiniert wenn mehrere Level an sind."*, then *"ohne Farbgradient, jedes Wort in der eigenen Farbe"* — a first cut used a `background-clip:text` gradient for a combined node, replaced same-day with this per-word version). `buildLevelNodeLabelContent(node)` — used by the real tree row (`renderNode`; originally also shared by the breadcrumb child-nav flyout row, removed 2026-08-25, see "Header / toolbar layout" above) — builds a `"level"` node's `.tree-label` content as real DOM nodes: one `<span>` per level in `node.value`, each with a plain `style.color = var(--level-error|warn|info|debug|trace)` (the same vars the level bar/log-row tinting already use), comma-separated with plain text nodes so the rendered text reads identically to the node's own plain-text name (e.g. "ERROR, INFO") — just with each word in its own color, no blending. Built via `createElement`/`textContent` rather than an HTML string, so a value smuggled in through a hand-edited/corrupt filter-file import (`importFilterJson` doesn't otherwise validate a `"level"` node's `value` array contents) can't inject markup — an unrecognized entry (not one of the five colored buckets in `ALL_LEVELS`) just renders in the default text color instead of a level color. Every other filter type's label is untouched. ### Per-format log levels (`FEATURE_BACKLOG.md` #47)

Which level buttons the bar shows, and in what order, comes from the **log format** a file was parsed under, not from one global list. A `LogFormat` carries an ordered `levels` array (`formatLevels(formatId)`): any subset of the five names that own a dedicated theme color (`ALL_LEVELS` = `ERROR, WARN, INFO, DEBUG, TRACE`), in any order, **plus any number of custom names of its own** (`NOTICE`, `CRITICAL`, `VERBOSE`, …). `OTHER` is never listed — it stays the implicit catch-all. A format with no `levels` field — every builtin, and every format created before this existed — falls back to `LEVELS` = `ERROR, WARN, INFO, DEBUG`, so single-format usage behaves exactly as it did before.

**Bucketing is format-aware**: `levelBucket(level, formatId)` (the `formatId` comes off the entry itself, stamped at parse time) resolves a raw level string in three steps — an **exact, case-insensitive match against the owning format's own `levels` list** wins first, which is what gives a custom name its own named, colored bucket; otherwise the historical prefix cascade (`ERR`/`FATAL`→ERROR, `WARN`, `INFO`, `DEBUG`, `TRACE`) still applies, so the five known buckets keep their forgiving matching even for a format whose list omits one of them; otherwise `OTHER`. Unrecognized free text deliberately never becomes a bucket of its own — only names a format explicitly lists are, which keeps the level bar and the count aggregation bounded by configuration rather than by log content. `formatLevels()` normalizes (trims/uppercases) and de-duplicates its list and drops the reserved `OTHER`, so a hand-edited record can't collide with the catch-all.

**Colors for custom names** come from a rotating categorical palette, `--level-custom-1` … `--level-custom-6`, defined per theme block (six genuinely distinct hues each, picked in the spirit of `COLUMN_PALETTE`, plus one `--level-custom-on` for text sitting on top of them; `-soft` shades are derived with `color-mix` rather than getting vars of their own). They are deliberately **not** in `THEME_COLOR_KEYS`, so an imported custom theme (which predates them) stays valid and simply inherits the `:root` values. `customLevelSlot(name, formatId)` assigns a slot by the name's **position among that format's custom names**, wrapping after six — so the same format always paints the same custom level the same color; with no format context (a bare bucket name, e.g. a level-bar button or a filter-node label) every stored format is searched in order, first match wins. `levelClass(level, formatId)` returns `lvl-custom-N` for those, `lvl-error`/`lvl-warn`/… for the known five, and `lvl-other` otherwise; matching rules exist alongside every existing `lvl-*` consumer (`.level-btn` + `.active`, `.col-bar`, `.level-badge`, `.log-row` + `:hover`, `.pair-row-bar`, `.minimap-lvl-*`). `levelSortRank()` ranks custom buckets between `TRACE` and `OTHER` by their slot, which is also the minimap's per-bucket "most severe" index (the minimap keeps the bucket **name** alongside the rank now, since a rank no longer identifies a bucket on its own).

With several files open under different formats, `activeLevelOrder()` returns the **union**: each open root file's format list, concatenated in tree order, de-duplicated as names first appear (e.g. a `["ERROR","WARN","TRACE"]` file plus an `["INFO","ERROR"]` file gives `ERROR, WARN, TRACE, INFO`). That single order drives both `renderLevelBar()`'s buttons and `canonicalLevelOrder(levels)`, which re-sorts a level node's `value` array (used by the bar's own click handler and by `#btnApplyLevelToTree`) — names outside the union (e.g. `OTHER`, a custom name from a format no longer open, or one a format has since dropped, arriving via an imported filter file or a persisted tree) are kept and appended rather than dropped; such a node keeps its value, simply stops matching, and renders its label in the default text color instead of crashing. `getLevelCounts()` keys its counts off **each entry's own computed bucket** rather than iterating a fixed name list, so per-format custom buckets are counted for free. Entries are stamped with their `formatId` at both parse sites (`parseLogTextAsync`, `appendTailText`).

`TRACE` only became a level-bar button through this feature, so it gained the `.level-btn.lvl-trace` / `.level-btn.active.lvl-trace` rules it never had; its active-state text color is a single `--level-trace-on: var(--level-debug-on)` in `:root`, resolving per theme via the `--level-debug-on` every theme already defines (same neutral grey family as `--level-trace`).

**Editing it**: the Format Manager's format editor (Settings → Log Formats → Edit) has a "Log levels" list — the five fixed bucket names are always present as rows with a checkbox and ▲/▼ reorder buttons (same idiom as the filename-rule list), and beneath the list a text field + **Add** button (Enter works too) appends a **custom** row. A custom row is always checked and carries a ✕ delete control (`.filter-library-row-del`, the same icon button the format/rule lists use) instead of being uncheckable — it isn't part of a fixed set to toggle back on, so removing means deleting the row; it reorders with the same ▲/▼ and previews its palette color live (`formatEditLevelSlot`, computed from the in-progress working order, since `customLevelSlot` reads the *saved* record). Adding is rejected, with an inline error, for empty/whitespace-only input, the reserved name `OTHER`, and any case-insensitive duplicate of a row already in the list (fixed rows included — that's a re-check, not a new row). The saved `levels` is the checked rows in the arranged order; unchecked fixed rows keep their position in the editor (so unchecking and re-checking doesn't lose it) but never reach the record. Saving with nothing checked is refused. Reset (builtin default row) restores the original four. No new persistence carrier: `levels` is a plain field on the `LogFormat` record already written whole to the `logFormats` IndexedDB store.

Regression-tested: **Group 116** — default-format behavior unchanged, a custom format's own subset/order driving the bar, the two-format union, `canonicalLevelOrder`'s effect on a level node's `value` and its colored tree label, and the editor's save/reopen/IndexedDB round trip incl. the empty-selection guard and Reset — and **Group 117** for custom names: `levelBucket`'s three-step resolution (exact/cascade/OTHER, incl. case and whitespace normalization and the "another format's name isn't borrowed" case), per-format positional slot assignment and the resulting `lvl-custom-N` classes on bar buttons and log rows, custom buckets in the bar/counts/quick-filter/tree label, `levelSortRank` placing them between TRACE and OTHER, the editor's add/duplicate-reject/blank-reject/Enter/reorder/delete flow with an IndexedDB round trip, and a level filter node left pointing at a level its format no longer defines. 2225 passed, 0 failed.

Regression-tested: **Group 94** — default mode, node creation/in-place-edit/deletion-on-empty (undo included) in `"auto"`, the classic Set + `#btnApplyLevelToTree` round trip in `"explicit"`, the mode-switch clearing side effect, and a direct `serializeFilterTreeForCache`/`materializeCachedFilters` round trip proving the generic `value` field and the `FILTER_TYPES` addition both work without special-casing. ## General "don't jump" scroll anchoring + auto-reveal Filtered

Person-requested this session (2026-08-19; German: *"Stelle sicher, dass beim ändern der angezeigten Log-Level, die aktive Zeile nicht aus dem Bild springt, sondern sich das Log darüber/darunter erweitert. Generell gilt: wechsel von Filtern, Log-Leveln, Message Expand etc. die aktive Zeile bleibt sichtbar (sofern sie im Ziel-View vorhanden ist)... Das Ziel soll sein, dass ein Wechsel zwischen unterschiedlichen Anzeigen, nicht als Sprung wahrgenommen wird, insbesondere wenn ein Element ausgewählt ist. Bei wechsel zu einem anderen Filter, wechsle automatisch vom Full zum Filtered View (wenn Stacked aktiv ist, keine Änderung)"*). Two related but separate fixes:

**1. Scroll anchoring, generalized.** The multiline toggle (see below) previously had its own one-shot re-anchor mechanism (`topVisibleEntryId` + `pendingTableTopAlignId`/`pendingHighlightTopAlignId`, manually captured by that one button's click handler right before `render()`). Every OTHER view-changing action — a level-filter pill click, switching the active tree node/filter, a column sort — still fell through `renderTable()`'s old default: *"any other change to the displayed set starts back at the top of the new list."* That default is exactly what read as a jarring jump, especially with a row selected.

Replaced with `captureViewAnchor(entries, offsets, scrollEl)` / `restoreViewAnchor(anchor, entries, offsets, scrollEl, setScrollFn)` (declared together, right above `renderVisibleRows()`), called automatically **inside** `renderTable()`/`renderHighlightView()` themselves on every render — no call site needs to remember to invoke anything:

- `captureViewAnchor()` runs first, against the OLD (pre-change) entries/offsets/scroll position, before the caller recomputes them. If `state.selectedId` is present in the OLD entries, it's the anchor — pixel offset from the top of the viewport captured too when the row is currently on screen (`onScreen`), or `null` when it isn't (nothing to preserve, just an obligation to reveal it once restored). With no selection, it falls back to `topVisibleEntryId()` (the multiline toggle's original fallback, now the general one) — the entry currently at the very top of the viewport, offset `0`.
- `restoreViewAnchor()` runs after the NEW entries/offsets exist, looking the anchored id up in the NEW list. Found + had a pixel offset → `setScrollFn(newRowTop - offset)`, landing the SAME row at the exact SAME screen position it had before (the log visibly "expands/collapses" above or below it, not a jump). Found + no prior offset (was selected but off-screen) → centers it in the viewport instead of edge-snapping, so a stale-but-selected row actually gets revealed rather than staying hidden. Not found at all (filtered out, or nothing was anchored and even the fallback list was empty) → returns `false`, and the caller falls back to its own pre-existing default (`renderTable()`: reset to top, same as always; `renderHighlightView()`: leave `scrollTop` exactly as it was — that view's own established default, see "Context view" above, only ever actively touched on a genuine root-file switch).
- `topVisibleEntryId()`/`captureViewAnchor()`/`restoreViewAnchor()` all key variable-vs-flat row-height math off **`offsets` truthiness**, not `state.multilineMessages` directly — the global flag can already reflect a NEWER mode than the specific entries/offsets pair being captured (e.g. right after the multiline toggle flips it but before the affected view actually re-renders), so the offsets array's own presence is the only reliable signal for "were THESE rows laid out with variable heights."
- `renderTable()` now calls `captureViewAnchor()` unconditionally as its first real step (right after the `!hasFiles` early return) and tries `restoreViewAnchor()` after `state.scrollTargetId`/`pendingTableScroll` (both explicit navigation intents, still highest priority) have had their turn. `renderHighlightView()` only attempts capture/restore when the root file hasn't changed (`sameRoot`, computed once and reused) — a genuine root switch has nothing worth preserving from the old viewport, same as before.
- `#btnMultilineMsg`'s click handler lost its entire manual-capture block (including the old Link-view `isLinkActive` guard) — trivial now, just flip the flag and `render()`. The Link-view case needs no guard at all anymore: `captureViewAnchor()` only ever runs from inside `renderTable()`, and `renderMainView()` calls `renderLinkView()` instead of `renderTable()` while a `link` node is active, so there's simply no call for it to make during that whole period — nothing stale can linger.

Regression-tested: **Group 61** (`tests/philogg.regression.test.js`) — 61a: selecting a row, scrolling it to a known on-screen offset, then clicking a level-filter pill that removes many rows above it — asserts the resulting `scrollTop` keeps that row's on-screen pixel offset bit-for-bit unchanged in the Filtered view (its Full-view assertion was updated same-day per point 3 below — Full no longer narrows at all, so there's nothing to re-anchor there). 61b: a selected row that gets filtered OUT entirely falls back to reset-to-top, same as no selection. 61d: a selected row that was off-screen before the change (never previously visible) gets revealed centered once it survives into the new view, instead of staying scrolled away. Group 55d (still passing, updated in place — see "Multiline message display toggle" below) covers the no-selection fallback path this generalization also has to keep working, plus the Link-view case specifically.

**2. Switching filters auto-reveals the Filtered view from Context.** A newly *created* or *edited* filter already called `revealFilteredView()` (switches `fhActiveTab` from `"highlight"` to `"filter"` when in tabs layout; no-op in Stacked, both panels already visible — see "Context view" above) at each of its own call sites, so its result would actually be on screen. Simply *switching* the active node to an already-existing filter — via the tree, the breadcrumb, arrow-key nav, drag-drop reparenting, undo/redo, or any of the ~30 other places `state.activeId` gets set directly — did not, so browsing filters while on the Context tab silently showed nothing changing.

Fixed once, centrally, instead of touching every one of those call sites: `render()` now tracks the active id across calls (module-level `lastActiveIdForReveal`, updated at the top of every `render()`) and calls `revealFilteredView()` itself whenever `state.activeId` changed AND the new active node's `type === "filter"` — this works because "every state mutation ends in a `render()`" (see `render()`'s own comment) is already an established invariant across the whole app, so a check inside `render()` sees every real activeId change regardless of which of the ~30 call sites caused it. Switching to a plain FILE node deliberately does NOT trigger this — a file node has no filter result to reveal, and the Context view shows the whole file there anyway.

## Cross-view jumps preserve screen position (double-click, `jumpToFullLog`)

Person-requested this session (2026-08-27; German: *"Bei allen Wechseln zwischen views, egal ob Doppelklick, Klick auf Filter, Alt+Pfeiltasten, etc. versuche den selektierten Logeintrag an seiner aktuellen Position zu halten. (Doppelklick springt zum Beispiel aktuell in die Mitte). Wenn im Ziel View nicht genügend Einträge oberhalb des Eintrags vorhanden sind, darf der Eintrag entsprechend nach oben springen. In allen anderen Fällen soll beim Wechsel sichergestellt werden, dass der Eintrag an der gleichen Stelle zu sehen ist wie im vorherigen View."*).

The tree-click/Alt+Arrow path already preserved the selected row's on-screen pixel offset via `captureViewAnchor`/`restoreViewAnchor` (see above) — including the "not enough rows above" case, since `setTableScroll`/`setHighlightScroll` already clamp to `Math.max(0, …)`, which naturally pins the row as high as it can go instead of the exact requested offset. The gap was every jump that goes through `state.scrollTargetId`/`state.highlightScrollTargetId` instead — `revealInHighlightView()` (double-click/Enter reveal into the Highlight view) and `jumpToFullLog()`/`jumpToEntry()` (extraction table/plot-mark double-click into the Filtered view) — these bypassed the anchor mechanism entirely and always centered (`scrollToIndex`/`scrollToHighlightIndex`'s `opts.center`).

Fixed by adding a third scroll mode alongside `opts.center`: `opts.offset` (a pixel value), which lands the target row at that exact distance from the viewport's top instead of centering — `target = rowTop - opts.offset`, clamped to 0 by `setTableScroll`/`setHighlightScroll` the same way `restoreViewAnchor` already relies on. The offset is captured from the SOURCE row at the moment of the jump via `captureRowScreenOffset(rowEl, scrollEl)` (`rowEl.getBoundingClientRect().top - scrollEl.getBoundingClientRect().top`, `null` if the row isn't actually on screen) — real layout geometry rather than an offsets-array lookup, so it works uniformly across every source view regardless of whether that view is virtualized (Filter/Highlight tables) or not (the Link view, the Extraction table).

- `revealInHighlightView(entry, sourceRowEl, sourceScrollEl)` now takes the clicked/Enter-selected row and its container, captures the offset into `state.highlightScrollTargetOffset` before `renderHighlightView()` runs, which passes it through to `scrollToHighlightIndex(idx, { offset, flash: true })` when known, falling back to `{ center: true, flash: true }` when not (e.g. the row happened to be off-screen already — nothing to preserve, same convention as `restoreViewAnchor`'s own off-screen fallback).
- `jumpToFullLog(entry, sourceRowEl, sourceScrollEl)` does the same via `state.scrollTargetOffset`, consumed by `renderTable()`'s `scrollTargetId` branch. `jumpToEntry()` (bookmark-panel jumps) deliberately passes no source row — a bookmark click has no "previous screen position" in a log view to preserve, so it keeps centering.
- The Highlight view's own row double-click (self-reveal, previously always `{ center: true }`) now scrolls with no `opts` at all — the clicked row is already on screen at the moment of the dblclick, so the plain nearest-edge-snap default is a no-op there, same net effect without a special case.
- The timeline minimap's click-to-jump and a plot-mark click into `jumpToFullLog` still hard-center — neither has a meaningful "current screen position" to preserve (a minimap click can jump to an arbitrary, previously-invisible timestamp; a plot mark isn't a log row).

Regression-tested: **Group 118** — 118a: a double-click (`revealInHighlightView`) from a known 140px on-screen offset in the Filter view lands the entry at that exact 140px offset in the Highlight view, not centered. 118b: the same jump from a row too close to the top (2 rows / 56px above it, offset would need 300px) clamps to the top instead of centering. 118c: `jumpToFullLog` from the Extraction table preserves its own row's on-screen offset into the Filter view the same way.

## Multiline message display toggle

`#btnMultilineMsg` (`#viewBar`, next to `#btnPinBookmarks`) toggles `state.multilineMessages` — default `false` (unchanged behavior: `.col-msg` stays `white-space:nowrap` + ellipsis, one truncated line per row). On: a `.multiline-messages` class on `<body>` (toggled by `updateMultilineMsgButton()`, the same "reflect state on the button" helper pattern `updatePinBookmarksButton()` uses) switches `.col-msg` to `white-space:pre` — literal `"\n"`s in `e.message` (continuation lines the parser already folds in for stack traces, see "The log format it parses" above) render as real line breaks. Applies to **both** views that render `.col-msg`: the Filtered table (`renderVisibleRows`) and the Context view (`renderHighlightVisibleRows`) — a single body-level class reaches both without per-row class bookkeeping. The Extraction table and Link pair view don't use `.col-msg` at all and are untouched.

**Deliberately `pre`, not `pre-wrap`**: a long single line is never soft-wrapped to fit the column width, only the message's own embedded breaks produce new lines. This isn't just fidelity to the request's literal wording ("gemäß der Zeilenumbrüche in der Message") — it's what keeps a row's rendered height **exactly derivable from its message's line count**, with no DOM measurement involved: `messageLineCount(message)` (`message.split("\n").length`) and `rowHeightForEntry(e)` (`ROW_HEIGHT + (n-1) * MULTILINE_LINE_HEIGHT` for `n > 1` lines, else plain `ROW_HEIGHT`) are pure functions of the entry, computable before the row ever touches the DOM. `MULTILINE_LINE_HEIGHT = 15` (px) is duplicated as a literal in the `.multiline-messages .col-msg` CSS rule's `line-height:15px` — the two values must stay in sync by hand if either ever changes, there's no shared source (a CSS custom property would remove that risk if this needs touching again).

**Why the height needs to be exact, not just "close enough": variable-height virtualization.** The Log view's `ROW_HEIGHT = 28`/`BUFFER_ROWS = 10` virtualization (see "Log view" above) assumes every row is the same height — `index * ROW_HEIGHT` locates any row's pixel offset in O(1), which is what makes scrolling a 100k-row file smooth. Multiline mode breaks that assumption (rows vary in height), so exact-but-not-measured heights let a **prefix-sum array** stand in for the same O(1)-ish lookup instead of falling back to a full non-virtualized render (which would have defeated the whole "stays smooth at any file size" goal) or a measure-as-you-scroll virtualizer (real complexity for no benefit when the exact height is already knowable in advance):

- `buildRowOffsets(entries)` returns a `Float64Array` of length `entries.length+1` where `offsets[i]` is the cumulative pixel height of every row before index `i` (`offsets[0] = 0`). Built once whenever the current view list changes — `renderTable()`/`renderHighlightView()`, and the `pinBookmarksInFilteredView`-triggered partial refresh in `toggleBookmark`'s caller — never per scroll frame. `tableRowOffsets`/`highlightRowOffsets` hold the two views' arrays; both stay `null` when `state.multilineMessages` is off, so that path's virtualization code is untouched (`if (state.multilineMessages && tableRowOffsets) { … } else { /* original ROW_HEIGHT arithmetic, byte-for-byte */ }` at every call site below).
- `findOffsetIndex(offsets, y)` binary-searches for the largest row index whose offset is `<= y` — "which row is pixel position y inside." Used everywhere the old code did `Math.floor(scrollTop / ROW_HEIGHT)`.
- Every call site that used to do index↔pixel math via `ROW_HEIGHT` now branches on `state.multilineMessages`: `renderVisibleRows`/`renderHighlightVisibleRows` (which rows to render + the container's `top` offset), `renderTable`/`renderHighlightView` (the scroll spacer's total height — `offsets[total]+22` instead of `total*ROW_HEIGHT+22`), `scrollToIndex`/`scrollToHighlightIndex` (both the target row's top AND its own height, needed for the center/into-view math — a tall row centers differently than a 28px one), and `updateMinimapRenderedRange` (which entries the minimap's "currently rendered subset" rectangle spans).
- The tail-follow "how far from the bottom is the user scrolled" heuristic (`ROW_HEIGHT * 1.5` threshold in the `#tableBody` scroll listener) was deliberately left as a flat constant — it's a coarse "close enough to the bottom" check, not a per-row lookup, and a taller effective threshold under multiline mode is if anything more forgiving, not wrong.

**Toggling re-anchors on the top-visible entry, not on scroll position 0** — originally a dedicated one-shot mechanism built just for this toggle, **superseded this session (2026-08-19) by the general "don't jump" scroll anchoring** described in its own section right after "Context view" above: `captureViewAnchor()`/`restoreViewAnchor()`, called automatically inside `renderTable()`/`renderHighlightView()` on every render, not just this one toggle. `#btnMultilineMsg`'s click handler itself is now trivial again — flip `state.multilineMessages`, call `render()` — with no manual capture step of its own. See that section for the current mechanism (including how it now also prioritizes the *selected* row, not just the topmost-visible one).

Regression-tested: **Group 55d** — scrolled well past three rows that are about to grow, toggling on grows `scrollTop` by exactly the sum of those rows' height increase (not 0, not an unchanged raw pixel value) in both views, with the same entry's DOM row still actually rendered at the top afterward; toggling back off shrinks `scrollTop` back to the exact original pixel value; the degenerate already-at-0 case stays at 0; and the Link-view case (toggling while a `link` node is active, no table rendered that cycle) — updated in place this session to assert the view now re-anchors on the entry that was on screen before the Link-view interruption instead of resetting to top, since "reset to top on any other change" is exactly the old default this session's general fix replaced.

**Persistence**: `state.multilineMessages` rides in the exact same `settings` object `buildCacheMeta()`/`restoreSessionFromCache()` already carry `pinBookmarksInFilteredView` in — additive field, no `CACHE_FORMAT_VERSION` bump (same reasoning already established for `linkOrderEnforced`/`linkExclusive`, see "Link filter" above). This is the browser-local IndexedDB session cache specifically — **not** threaded into the separate `buildSessionExport`/`runSessionImport` JSON session-file feature, since the request asked for state "im Cache gespeichert" (in the cache), a narrower, different mechanism than that portable-file export.

Regression-tested: **Group 55** (`tests/philogg.regression.test.js`) — 55a covers default-off, per-row heights in both views, the spacer summing real heights, and exact reversion on toggle-off; 55b builds a 50-entry file with one 21-line entry positioned before a jump target and asserts `scrollToIndex` (via `jumpToEntry`) lands on the pixel offset the tall row's real height demands, with the target's DOM row actually rendered — proving the offset-based windowing, not just the toggle's on/off state; 55d (see "re-anchors on the top-visible entry" above) covers the scroll-preservation fix; 55c round-trips the setting through a simulated reload via the shared session-cache mechanism, same pattern as Group 20.

## Log view column visibility / width (`FEATURE_BACKLOG.md`)

`#btnColumns` (`#viewBar`, next to `#btnMultilineMsg`) opens `#columnsPanel`, a small fixed-position popup with checkboxes for **Δt/Thread/Location/Method** — Time/Level/Message stay always-visible, no checkbox. Each of the six columns (Time/Δt/Level/Thread/Location/Method) also has a drag handle in `#tableHeader` (`.col-resize-handle`) for live width resizing; Message has no width of its own — it's the grid's `1fr` flexible remainder, so growing/shrinking any other column resizes it automatically.

**Applied entirely through `--row-grid`, the CSS custom property `.row-grid` (shared by `#tableHeader`, `#highlightHeader`, and every `.log-row` data row in both Log views) already used as its `grid-template-columns`** — `applyRowGrid()` recomputes the whole string from `state.columnWidths`/`state.columnVisible` and writes it via `document.documentElement.style.setProperty`. This is the reason the feature costs essentially nothing at render time: flipping a checkbox or dragging a handle just changes one CSS variable, and every row (Filter + Highlight, virtualized or not) reflows natively — no per-row DOM writes, no `render()` needed for the drag itself (only at drag-end, to persist). A hidden column's track collapses to `0px` (not removed from the grid, not `display:none` on the per-row `.col-*` spans) specifically to avoid corrupting CSS Grid's row auto-placement — see the mobile-breakpoint paragraph below for the bug this exact mistake caused elsewhere in the same feature.

**Resize handles are positioned via JS, not nested inside `.th`**: `.th` has `overflow:hidden` for its own text-ellipsis truncation, which would clip an absolutely-positioned handle poking out past its own border box. Instead, six `.col-resize-handle` spans sit as siblings of the `.th` elements inside `#tableHeader .row-grid` (`position:relative`, scoped to the header only — `.row-grid` is shared with every data row, which must NOT become a positioning context), each with `data-col` and a `left` computed by `positionColumnResizeHandles`-equivalent logic folded into `applyRowGrid()` itself (cumulative `COLUMN_BAR_WIDTH + Σ(gap + column width)`). Being `position:absolute`, they're out of grid flow entirely and don't consume an auto-placement slot among the real 8 grid items — the same property that makes the 0px-track (not `display:none`) choice above necessary for the *real* row items.

**Mobile breakpoint bug found and fixed while building this**: the pre-existing `@media (max-width:760px)` rule set its own `:root{--row-grid:...}` override AND `.col-thread,.col-loc,.col-method{display:none;}` directly in CSS. Both had to go: (1) an inline style (what `applyRowGrid()` now always sets) unconditionally wins over any media-query rule, so the old override would simply never have applied again once this feature shipped; (2) independently of that, the `display:none` half was **its own latent bug**, discovered by reasoning through it while designing the handles above — a `display:none` grid item doesn't reserve its track, so with 3 of the row's 8 real grid items removed from participation, the remaining 5 (bar/time/delta/level/msg) auto-place sequentially into tracks 1-5, meaning **Message would silently render in track 5** (Thread's slot, 0px wide in the mobile `--row-grid`) instead of track 8 (`1fr`). Neither this session's own reuse of the mechanism nor the original narrow-viewport feature had ever exercised this path in a way that surfaced it. Fixed by folding the narrow-viewport override into `applyRowGrid()` itself (`COLUMN_MOBILE_BREAKPOINT = 760`, `COLUMN_MOBILE_FORCE_HIDDEN = ["thread","loc","method"]` — deliberately narrower than the visibility toggle's own `HIDEABLE_COLUMNS`, since the old mobile rule kept Δt visible, just narrower) — same 0px-track mechanism as the desktop visibility toggle, so no auto-placement risk. `window.addEventListener("resize", applyRowGrid)` keeps it live across the breakpoint.

**Persistence**: `state.columnVisible`/`state.columnWidths`, same `settings` tier as `multilineMessages`/`pinBookmarksInFilteredView` (`buildCacheMeta`/`restoreSessionFromCache`) — global, not per-file. `DEFAULT_COLUMN_WIDTHS` matches the original hardcoded `--row-grid` values exactly, so a first-ever load (or "Reset widths" in the popup) is visually identical to before this feature existed. `COLUMN_MIN_WIDTH = 40` clamps a drag from shrinking a column to nothing.

Regression-tested: **Group 58** — 58a (checkbox toggle collapsing/restoring a track and its own handle's visibility, Reset widths), 58b (drag-resize live width update + `COLUMN_MIN_WIDTH` clamp + no stray effect after mouseup), 58c (persistence across a simulated reload), 58d (the mobile-breakpoint fix — forces Thread/Location/Method to 0px without mutating the stored preference, restores on widening back past the breakpoint).

## Log row multi-select + copy (`FEATURE_BACKLOG.md` suggestion, person-requested this session)

Ctrl+click toggles a row into/out of `state.logMultiSelect` (a `Set` of entry ids); Shift+click selects the contiguous range from the last-clicked anchor (`logMultiSelectAnchorId`), replacing the set — standard file-explorer semantics, including that a repeated Shift+click re-derives the range from the SAME anchor, not the previous Shift+click's own target. A plain click keeps its pre-existing single-selection behavior unchanged and clears the multi-selection. The first Ctrl+click after a plain click folds the existing `state.selectedId` into the set too, so "click A, then Ctrl+click B" reads as "A and B selected" rather than silently dropping A. `handleLogRowClick(ev, entryId, viewEntries, selectFn)` is the one shared handler wired onto both Log views' row `click` listeners (`currentViewEntries`/`selectEntry` for the Filter table, `currentHighlightViewEntries`/`selectHighlightEntry` for the Context view) — `state.logMultiSelect` is shared between them exactly like `state.selectedId` already is, so a range built in one view's rows shows the same tint on the other view's copy of the same entries.

**Ctrl+C copies the raw text** (`copyLogSelectionToClipboard`) — the multi-selected entries (or just `state.selectedId` alone when nothing's multi-selected), looked up via the global `entryIndex` and joined by `entry.raw` (which already accumulates continuation lines for multi-line stack traces, see "The log format it parses"), **sorted chronologically by timestamp** rather than click/DOM order, so a series of out-of-order Ctrl+clicks still copies in log order. This takes priority in the keydown handler over the tree's own filter-node clipboard (`state.clipboard`, existing Ctrl+C/X/V) — but only when `state.focusRegion === "entries"` (the log view, not the tree, was the last thing interacted with); the tree-node copy is otherwise unaffected. **Exception, added 2026-08-26 (`FEATURE_BACKLOG.md` #55, person-requested)**: the Entry Detail panel (`#detailMessage`) has always been selectable text (no `user-select:none`), but Ctrl+C previously ignored that and always overrode it with the full raw line. Now the handler checks `window.getSelection()` first — if there's a non-empty selection anchored inside `#detailPanel`, it returns without calling `preventDefault()` or `copyLogSelectionToClipboard()`, letting the browser's native copy grab just the selected substring. With no such selection, behavior is unchanged.

**Rendering**: no full re-render on Ctrl/Shift+click — `updateLogMultiSelectClasses()` toggles the `.row-multi-selected` class directly on whichever rows are currently in the DOM, same in-place-toggle technique `updateSelectedRowClass` already uses and for the same reason (a full `renderVisibleRows()`/`innerHTML` rebuild on every click would break native `dblclick` detection — see CLAUDE.md's gotcha list). A normal `render()` (e.g. after Escape clears the set) still bakes the class into each row's `className` string directly from `state.logMultiSelect` at render time, so scrolling the virtualized window afterward stays correct without any extra sync call.

**CSS pitfall hit and fixed while building this, caught via a real-browser (Playwright) screenshot check, not just the jsdom suite**: the first cut styled `.row-multi-selected` with a plain `background`. It rendered completely invisible except on rows with no level class. Root cause: `.log-row.lvl-error`/`.lvl-warn`/etc. (the existing per-level row tinting) ALSO set `background`, at equal specificity (`.log-row` + one class, `0,0,2` either way) and later in the stylesheet — so the level tint always won outright, not blended. This is the *exact* fight `.pinned-row`'s own comment already documents and solves the same way: switched to `box-shadow:inset 0 0 0 2px var(--accent-strong)` instead, which doesn't touch `background-color` at all and so composes over any level tint unconditionally. Since `.selected` also uses `box-shadow` (a single-value property — two separate class rules setting it don't stack, only one wins per the cascade), an explicit `.log-row.selected.row-multi-selected{box-shadow:inset 0 0 0 1px var(--accent), inset 0 0 0 3px var(--accent-strong);}` combines both shadows for a row that's simultaneously the multi-select's focused row and a member of the set — its higher specificity (three classes vs. two) wins over either rule alone regardless of source order. **Lesson for future row-decoration work here**: `background` is claimed by the level-tinting rules; any new per-row visual state needs `box-shadow` (or a `left`/gutter marker, see `.pinned-row`/`.ctx-bracket`/`.hl-markers`), not `background`, unless the new state is meant to compete with (or is mutually exclusive with) level tinting.

Regression-tested: **Group 57** — plain click behavior unchanged; first Ctrl+click folding the prior selection in; Ctrl+click toggle-off (and its anchor move); Shift+click range selection (replace, not extend) and repeated-Shift-click re-deriving from the same anchor; Ctrl+C priority over the tree clipboard gated on `focusRegion`; Escape clearing state + DOM class; and the selection/class being shared between the Filter and Highlight views. The CSS specificity bug above was caught via manual Playwright screenshot review (jsdom has no layout/paint engine, see "Testing approach" below), not by the automated suite — same class of gap the multiline-toggle CSS-flex-direction bugfix note already flags.

## Theming

Rewritten this session (2026-08-22) from a two-way Light/Dark toggle into a full theme picker: six built-in themes (Dark, Light, and four Catppuccin flavors — https://catppuccin.com/palette/) plus unlimited user-imported custom themes, all selected from one `<select id="settingsThemeSelect">` dropdown in Settings → Appearance (previously an `.assert-mode-btn` Light/Dark button pair, see `tests/philogg.regression.test.js` Group 3/70h/70h2's updated text and the new Group 85).

**The var surface** (`THEME_COLOR_KEYS` in the Theme script section) is unchanged from before: `--bg-app`, `--bg-panel`, `--bg-elevated(-2)`, `--border(-soft)`, `--text-primary/secondary/tertiary`, `--accent(-strong/-soft)`, `--level-error/warn/info/debug/trace` (+ `-soft` alpha variants), `--warn`. `--level-error/warn/info/debug-on` + `--accent-on` (`THEME_ON_KEYS`) are the text color for the four *active* level-quick-filter buttons and for anything sitting on a solid `var(--accent)` surface (brand mark, Save button, active chips/badges) — split out of the level/accent colors themselves into their own vars (defaulting to near-black in `:root`) precisely so a theme can flip them to white without a dedicated CSS selector per theme. `--border-hover` is *derived*, not stored — `color-mix(in srgb, var(--border) 70%, var(--text-tertiary) 30%)` in `:root`, so every theme (including a custom one applying vars inline) gets a correct hover-state border automatically from its own `--border`/`--text-tertiary` with no extra required JSON key.

**Stylesheet audit, same session, follow-up ("Prüfe... ob Du das konsequent umgesetzt hast").** A pass over every rule outside the `:root[data-theme=...]` blocks found ~18 places still hardcoding the DARK theme's own hex/rgba values instead of the var every sibling rule already used — invisible on Dark (where the hardcoded value and the themed one happened to match) but wrong on every other theme: the scrollbar thumb, `#btnOpen`/`#btnSession`/`.toolbar-icon-btn` hover borders, `.brand-mark`'s gradient/text, `.toolbar-badge`/`.column-chip.active`/`.btn-mini` text, and — the highest-impact group — `.crumb.current`/`.level-btn.lvl-*`/`.level-badge`/`.log-row.lvl-*:hover`/`.token-chip`'s alpha-tinted borders and backgrounds, all still using the dark theme's specific level-color rgba() triplets regardless of the active theme. Fixed via `--accent-on`/`--border-hover` above for the flat-color cases, and `color-mix(in srgb, var(--x) N%, transparent)` for the alpha-tinted ones (CSS can't apply an arbitrary alpha to a `var()` color any other way; every browser this app targets — Chromium, for the File System Access API it already requires — supports `color-mix()`). The timeline minimap was audited too and needed no changes: `.minimap-lvl-*`/`.minimap-bg-bar`/`.minimap-full-range`/etc. were already `fill:var(--level-error)` etc. from when the minimap was first built. **Deliberately left alone**: modal/dialog backdrop scrims (`rgba(16,19,26,.7-.88)`) and `box-shadow`s (`rgba(0,0,0,...)`) — a dark dimming layer and a black shadow are a normal convention regardless of the app's own light/dark theme, not a theming bug; and `COLUMN_PALETTE`'s 6 fixed extraction-column/plot colors (`.pattern-chip-num`'s `color:#0b1016`) — see "Visual language" below, deliberately theme-independent by design, unrelated to `--accent-on` despite the visual similarity. Group 82a is a static regression guard (`.textContent` of `<style>`, not computed style — jsdom can't resolve `color-mix()`) against the specific hardcoded literals this audit found creeping back in.

**Two application mechanisms, one var surface.** The six built-ins are plain CSS: one `:root[data-theme="<id>"]{...}` override block per theme (Light's block also sets the four `-on` vars to white, same as before; Catppuccin Latte does too — both are light-background themes whose level colors are too dark for the near-black default). Custom/imported themes have no CSS block — `applyTheme(themeId)` sets `data-theme` on `<html>` either way, but for a custom theme it also walks `THEME_COLOR_KEYS`/`THEME_ON_KEYS` and sets each one as an inline `style.setProperty("--x", ...)` on `document.documentElement`, after first clearing every one of those properties (so switching *back* to a built-in never leaves a stale inline override shadowing its CSS block — verified in Group 81b). `setTheme()` calls `applyTheme()` then persists the id to `localStorage` (`philogg-theme`, same key/tier as before); `initTheme()` on load resolves a stored id through `resolveThemeId()` (falls back to `"dark"` if it names a since-deleted custom theme — Group 81c) or, with nothing stored yet, falls back to `prefers-color-scheme` same as before.

**Custom themes** are plain JSON, validated and stored as `{id, name, colors: {...THEME_COLOR_KEYS}, activeTextLight}` in a `customThemes` array persisted to `localStorage` (`philogg-custom-themes`) — same tier as the theme choice itself, not IndexedDB (unlike the Log Formats/Filter Library lists, which expect larger/more numerous entries; a handful of ~25-key color maps doesn't need that). Settings → Appearance has a "Custom themes" card (reuses the `filter-library-row` list styling from Log Formats) with:
- **Download template…** (`buildThemeTemplateJson`) — seeds the JSON from the *currently active* theme's own `getComputedStyle` values (whichever theme that is, built-in or custom), so the file that comes out is always already valid and ready to tweak, not a fixed baseline disconnected from what's on screen. Ships via the same `showSaveFilePicker`/`downloadJsonFallback` pattern as `saveFilterToFile`.
- **+ Import theme…** (`importThemeJson`, via `#themeFileInput` / `showOpenFilePicker`, same pattern as `loadFilterFromFile`) — rejects malformed JSON, a missing/wrong `format` tag (`"philogg-theme"`), a newer `version`, or a `colors` object missing any required key (reports which ones), each via `showCopyToast`. A valid import gets a generated id (`"custom:" + timestamp + random`), is appended to `customThemes`, and is switched to immediately.
- Each row in the list: a small 4-stripe swatch (bg/accent/error/info) built from the theme's own colors, click-to-activate, and a delete button (falls back to Dark if the deleted theme was active).

`activeTextLight` is the one JSON field a theme author needs for text contrast — a boolean, not the five raw `-on` keys — since which text color to use is an implementation detail of these specific button/badge states, not something a template-filling user should have to reason about; `true` sets all five `THEME_ON_KEYS` (four level-on + `accent-on`) to white, `false`/omitted leaves the dark near-black defaults (which is also what every Catppuccin dark flavor, and both Dark/Light for `accent-on` specifically, relies on implicitly by not overriding it — every built-in `--accent` stays bright/mid-bright by design, verified across all six).

**Highlight-color picker "Theme" mode** (same session, follow-up request): the per-filter-node highlight-color picker (`#colorPickerPopup`, opened from a tree row's swatch — see "Tree interactions" — entirely separate from app theming before this session) now has a `highlightPalette` concept of its own. **Accent color** (same-day clarification: "Highlightfarbe" turned out to mean the app's own accent/selection color — the one already driving `.toolbar-icon-btn.active`, `.crumb.current`, `.btn-mini`, and the minimap's `.minimap-full-range`/`.minimap-rendered-range` time-span highlight, all confirmed already `var(--accent...)`-driven by the stylesheet audit above — not the per-filter-node picker covered just above, which stays as a separate, unrelated feature). **Catppuccin style-guide compliance audit** (this session, 2026-08-22, person-requested against https://github.com/catppuccin/catppuccin/blob/d09787dd98ca6fba08af5ef2ae94a7e09f17daca/docs/style-guide.md's "General Usage" table — the only section of that guide aimed at a general app rather than a terminal/code-editor; fetched fresh for this session, not recalled from training). Three confirmed gaps, all fixed:
- **"On Accent" text = Base**, not black/white. All four flavors now point `--accent-on`/`--level-*-on` at `var(--bg-app)` (Base, per the background remap directly below) instead of the generic near-black/`#fff` every other theme uses. `applyAccentChoice()` (Accent color, above) still computes its OWN black-or-white via `relativeLuminance()` when a person re-picks `--accent` to something outside the palette's originally-paired set — Base is guaranteed readable against Catppuccin's own small set of default accent/level colors (that's the guide's point), but not necessarily against an arbitrary one of the 14 named colors used as a full accent surface, which the re-pick feature allows; kept as a deliberate two-tier design (spec-correct default, safety-net override) rather than only one or the other.
- **"Selection Background" = Overlay 2 @ 20-30% opacity**, not the accent tint. New `--selection-bg` var (`:root` default = `var(--accent-soft)`, i.e. unchanged for Dark/Light/custom themes, which the guide doesn't govern) overridden per Catppuccin flavor to `color-mix(in srgb, var(--level-debug) 25%, transparent)` — reusing `--level-debug`, already mapped to Overlay 2 per flavor, rather than a new hardcoded hex. `::selection` now reads `var(--selection-bg)`.
- **Background Pane / Secondary Panes hierarchy, remapped on person direction** (initially flagged as a deliberate deviation and left alone — kept to preserve visual consistency with Dark/Light's own pre-existing hierarchy — then explicitly asked to be remapped to match the guide instead; see Group 88). The guide's roles: `--bg-app` (the page/table background, i.e. the actual "Background Pane") = **Base**; `--bg-panel` (toolbar/sidebar/dialogs, "Secondary Panes") = **Mantle**; `--bg-elevated`/`--bg-elevated-2`/`--border-soft`/`--border` ("Surface Elements" + one "Overlay" for the most prominent stroke) = **Surface 0/1/2, Overlay 0** in ascending prominence. The SAME role mapping applies to all four flavors, including Latte — Base is the brightest token there (unlike the three dark flavors, where it's a mid tone), so `--bg-app` still lands on "the main pane," it just means Latte's main content area now reads as the single brightest surface in the app, with its Surface-tier dialogs/popups reading progressively grayer/darker against it — the mirror image of how the three dark flavors' Surface tier reads progressively brighter, both the expected shape for their own flavor rather than a special case. This flips which surface reads as "brighter" for Catppuccin flavors specifically (sidebar/toolbar now read darker than the log table, unlike Dark/Light's own look) — a real, visible, intentional difference from Dark/Light now, not a bug.

**Known, deliberate deviations** (same audit, not changed — flagged for a person decision rather than silently "fixed"):
- **Warnings = Peach, not Yellow.** The guide's "General Usage" table says Yellow; its own "Code Editors → General Editor Elements" table separately lists "Warnings: Yellow, Peach" (both allowed there). Peach was chosen to match PhiLogg's own pre-Catppuccin warn semantic (`--warn`/`--level-warn`, amber-ish, not yellow) — see the Catppuccin CSS blocks' own comment. Yellow remains unused as a level color across every Catppuccin flavor.
- **Information/`--level-info` = Blue, not Teal** (the "General Editor Elements" table's "Information: Teal" — no equivalent line exists in "General Usage"). Teal is already `--accent`; reusing it for `--level-info` would make INFO-level rows visually collide with active/selected UI state. Blue was already this app's pre-Catppuccin info color too.
- "Tags, Pills" (guide: Blue) — PhiLogg's chips (breadcrumb, column, token) use `--accent` (Teal for the dark flavors), not Blue. Lower-confidence mapping (PhiLogg's chips aren't quite the guide's "tag/pill" use case), not changed.
- `Cursor` (guide: Rosewater) has no PhiLogg equivalent — `<input>` fields use the browser's native caret, not a CSS-stylable color the app currently sets (`caret-color` is unused).

Level colors (`--level-error/warn/info/debug/trace` + `-soft`) were re-themed for Light back in 2026-08-17 (from `FEATURE_BACKLOG.md` — previously reused the dark-mode hex values verbatim, which read poorly against the light panel background); values unchanged this session. Not regression-tested for actual rendered color (jsdom can't assert CSS color values or contrast — see "Testing approach" / `tests/README.md`'s "Known gaps"), but Group 81a does assert the resolved `getComputedStyle(...).getPropertyValue("--x")` string for a couple of load-bearing vars per built-in theme, which at least catches a wrong/typo'd hex or a misrouted `[data-theme]` block.

## Visual language (for consistency in future work)

Dark theme by default, five other built-in themes (Light + four Catppuccin flavors) and unlimited custom ones selectable via the Settings → Appearance dropdown (see Theming above) — all surface/text/accent colors are CSS custom properties at `:root`, precisely so every theme stays in sync from one set of rules. Key ones: `--bg-app` / `--bg-panel` / `--bg-elevated(-2)` for surface layering, `--accent` (teal in dark mode, `#4fc7c3`) for selection/active states, `--level-error/warn/info/debug/trace` (+ `-soft` low-alpha variants) for log-level coloring, each with its OWN value per theme (fully re-themed, not just carried over from Dark — see Theming above) — applied to the row background now, not just the badge/accent-bar (an earlier iteration only tinted the badge; rows are fully tinted per level today, with hover states that intensify rather than replace the tint, via `color-mix(in srgb, var(--level-x) N%, transparent)` since this session's audit — see Theming). `--font-mono` for anything log-data-shaped, `--font-ui` for chrome. Icons are small hand-drawn inline SVGs (`ICON_FILE`, `ICON_FILTER`, `ICON_CLOCK`, `ICON_TABLE`, `ICON_MERGE`, `ICON_COMBINE`, `ICON_LINK`, `ICON_CONTEXT`, `ICON_CLOSE`, `ICON_COPY`, `ICON_CUT`, `ICON_PASTE`, `ICON_SAVE`, `ICON_LOAD`, `ICON_SESSION_EXPORT`, `ICON_SESSION_IMPORT`, `ICON_HELP`, `ICON_PIN`) — follow that pattern (no icon font/library) if a new node type needs one. `COLUMN_PALETTE` (6 colors, teal/violet/amber/blue/pink/green) is reused for both extraction-column chips and plot series, and is the one deliberate exception to "every color is a theme var" — checked and left alone in this session's stylesheet audit (see Theming), since its whole point is a fixed set of colors that reads consistently regardless of theme. **Any new color needs a CSS variable, not a hardcoded hex** — that's what keeps every theme override a single block instead of a parallel hunt through the stylesheet (this session's audit exists precisely because that rule wasn't followed consistently before — see Theming's "Stylesheet audit" for what it found).

**Shared control box model** (this session, 2026-08-22, "Main window visual consistency fix" — extends the Settings dialog's own `.btn-mini`/`.btn-mini-outline`/`.btn-mini-secondary`/`.btn-icon` system to the toolbar/view-bar row, which had drifted into per-control hand-tuned CSS over several sessions — see the now-removed "height-parity bugfix" comment history in git blame for what that drift cost). One height (28px), one centering mechanism (`display:flex; align-items:center; justify-content:center`, or `inline-flex` for an inline-flowing chip like `.crumb`), shared by role instead of copy-pasted line-height/padding arithmetic per control: **icon-button shape** (28x28, `border-radius:7px`) — `.toolbar-icon-btn`, reused as-is (no id override needed) by `#btnPinBookmarks`/`#btnMultilineMsg`/`#btnColumns`, and by every header icon button (`#btnUndo`/`#btnRedo`, the only two left since `#btnShortcuts`/`#btnLicense` were removed); **pill shape** (`border-radius:20px`, height:28px) — `.level-btn`/`.crumb`; `.view-tabs`/`.view-tab` get the same 28px height via `height:100%` on the tab filling its 28px-tall container, rather than a line-height chosen to arithmetically sum to 28px. `#btnOpen`/`#btnSession` (previously two byte-for-byte-identical rule blocks) were merged into one and given the same 28px height. **When adding a new control to the toolbar/view-bar row, reuse one of these two shapes (or add a new one to this same shared system) instead of hand-tuning padding/line-height to visually match its neighbors** — that arithmetic is exactly what broke three separate times before this session. `.tree-action-btn`/`.folder-watch-reconnect`/`.tree-ghost-restore-btn` were deliberately left as their own rules — they don't sit in a row requiring cross-control height alignment, so folding them into this system would be scope creep without a concrete visual bug to fix. (`#btnOpen`/`#btnSession`'s merged pill-shaped rule from this pass was later removed outright — see "Toolbar regroup" above — once both moved into `#sidebarHeader` and switched to the `.panel-toggle-btn` shape instead.)

The three panel resizers (`#sidebarResizer`/`#fhSplitResizer`/`#detailResizer`, see "Collapsible sidebar / detail panel" and the fhSplit/detail-panel sections) now show a permanent grip bar (a short rounded 3px-thick bar, `var(--border)` at rest, brightening to `var(--accent)` on hover/drag) instead of being fully transparent until dragged — a bare transparent 7px hit area between two `--bg-panel` surfaces read as a stray dark seam (showing the darker `--bg-app` through), not an intentional divider. Also fixed the same session: `#timelineMinimap`'s `border-bottom` used `--border-soft` while `#sidebar`'s `border-right` (the adjoining seam) used `--border` — now both use `--border`. **Every border meeting at a sidebar/content/resizer seam should use `--border`, not `--border-soft`** (border-soft is for internal, lower-emphasis dividers within a single panel, e.g. `#sidebarHeader`'s own bottom border against the tree below it).

Selection styling convention established through iteration: **rings/outlines for "selected", not background fills** — a filled background for selection was found to be visually indistinguishable from the neutral hover fill, causing a "why are two rows highlighted" confusion. Log-row selection and extraction cell selection still use `box-shadow: inset ... var(--accent)` only, per that reasoning. **Multi-select in the tree is the one deliberate exception**: checked/multi-selected rows get both the ring *and* an `--accent-soft` background fill, because that state now has an explicit, always-visible checkbox as its primary affordance (see Tree interactions) — the fill reinforces "this row is part of a bulk action set" rather than competing with a hover state for meaning. If adding a new kind of selection indicator, default to ring-only unless it has the same kind of unambiguous explicit-control backing that multi-select has.


## Log view: column sort, status strip

- **Column sort** (`Time`/`Level`/`Thread`/`Location` headers, `.th-sortable`): clicking toggles ascending/descending (`state.sortColumn`, `state.sortDir`, arrow indicator via `updateSortIndicators()`). Applied in `renderTable()` to a **copy** of `getVisibleEntries()` (`entryComparator`) — never sorts the underlying node/file arrays in place. This matters: those arrays must stay chronological for the link filter's binary search (`lowerBoundByTs`) and the OR-filter's chronological merge to keep working; sorting only the display copy keeps the sort a pure presentation feature with zero risk to the rest of the pipeline. `Method`/`Message` aren't sortable columns (no obviously useful ordering for free text).
- **Status strip** (`#statusStrip`, `renderStatusStrip()`): a single always-visible line above the table — "N of M shown" (M = the active node's root file's total entry count via `getRootFileId`, N = `currentViewEntries.length` after node filter + level quick-filter) plus "filtered to X, Y" when level toggles are active. Only shown in the log view (hidden for the extraction table and link pair view, which have their own info lines).
- **Message hover popover — removed.** `#msgPopover` used to replace the native `title` tooltip on `.col-msg` cells with a delayed, selectable preview. It was removed for two reasons: (1) it duplicated what the detail panel (bottom of the log view, always shows the full selected message) already covers, so it added interaction surface without adding capability; (2) it caused a real, hard-to-spot bug — the popover for the *previously* hovered row lingers (by design, to avoid flicker while scanning) for up to 150ms after the pointer moves to an adjacent row, and since it's `position:fixed` with `pointer-events:auto` sitting right below/above the row it describes, it could swallow a click meant for the row now under the cursor. Caught via jsdom by checking the popover's `hidden`/`show` classes across a simulated row-to-row hover transition — see Testing approach below.
- The severity color bar (`.col-bar`, first column of `--row-grid`) was widened from 3px to 5px, since it remains the primary at-a-glance signal for scanning a long list.
